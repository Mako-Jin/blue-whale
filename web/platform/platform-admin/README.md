# platform-admin — 权限管理后台

权限域实体（用户 / 租户）的管理界面，同时是 **ADR-0018 第③段**的验证载体：
**同一个页面、同一段代码，管理员看到完整的操作条，只读账号只看得到列表。**

它不是产品功能，而是"权限判定单点计算、结果下发"这件事的**可运行证明**。

---

## 一、为什么"按钮级权限"值得单独做一个应用

只种一个超级管理员时，"权限到底生效没有"是**验证不了**的：所有接口对唯一身份都放行，
权限标识拼错、资源漏配、前端把显隐判反，症状都只是"看起来很正常"。

这个应用的两侧因此被刻意拉开：

| 身份                  | 权限                                       | 界面上应该看到                       |
| --------------------- | ------------------------------------------ | ------------------------------------ |
| `admin`（超级管理员） | `auth:user:*` / `auth:tenant:*` 全 8 项    | 列表 + 新建 / 编辑 / 重置口令 / 删除 |
| `auditor`（审计员）   | 只有 `auth:user:read` / `auth:tenant:read` | 列表；一个写操作入口都不出现         |

**差异不写在代码里，只写在权限集合里** —— 页面代码里没有任何 `if (username === 'auditor')`，
这就是全程唯一要证明的东西。

服务端同样拦一道：审计员构造请求直接 `POST /api/auth/users`，返回 `40301`（不是 401）。
**前端显隐只是体验，权限边界在服务端** —— 把按钮藏起来当权限控制是这套东西最常见的误用。

## 二、跑起来

```bash
# 1. 后端（默认 8080，h2 内存库；种子数据只在 h2 profile 打开）
cd server && mvn -DskipTests install
java -jar sts-app/sts-app-server/target/sts-app-server-0.0.1-SNAPSHOT.jar

# 2. 前端（独立打开）
cd web && pnpm install
pnpm --filter platform-admin dev            # http://127.0.0.1:3500

#    或经基座打开（会带上登录页与导航）
pnpm --filter platform-portal dev           # http://127.0.0.1:3000 → 导航「权限管理」
```

开发期 `/api` 由 vite 代理到 `127.0.0.1:8080`；被基座加载时请求走**基座页面**的 `/api`
（也由基座的代理转发）—— 两条路径都通，所以代码里始终只写相对路径。

## 三、令牌从哪来：认证端口

本应用**不含登录页**（`docs/decisions/0018` 第 8 条：子应用不得再实现一套登录，
否则会立刻长出第二份会话逻辑）。它只关心一件事 —— **从哪取令牌、谁负责刷新**，
这件事被收成一个两个方法的接口（`src/auth/index.ts` 的 `AuthPort`）：

| 运行方式   | 令牌来源                                  | 刷新                   | 起步方式                                       |
| ---------- | ----------------------------------------- | ---------------------- | ---------------------------------------------- |
| 被基座加载 | 基座通过 `HostProps.auth` 下发的能力      | 基座（并发合并成一次） | 基座的登录页                                   |
| 独立运行   | 本应用自己的会话（同一份 `session` 实现） | 本应用自己的通道       | 已有刷新令牌则静默续期，否则用开发账号自动登录 |

两条路走的都是 `common-api` 的 `createAuthChannel` / `common-tools/session`，
区别只在"谁提供会话"。因此 `src/api.ts` 与页面代码**完全不区分运行方式**。

### 为什么下发的是"能力"而不是令牌值

`HostProps.auth` 只给两个动作：`getAccessToken()` 与 `reauthenticate()`。

- **令牌值会陈旧**：基座在后台静默刷新一次之后，子应用手里那份就是作废的令牌，
  而它自己并不知道 —— 症状是"刚才还好好的，突然所有请求都 401"。函数是按需取，一定是最新的。
- **刷新必须全应用一次**：刷新令牌是轮换的，重复使用会被服务端判为重放攻击并撤销该用户**全部**会话
  （`docs/decisions/0018` 第 7 条）。子应用若各自刷，就把这个坑复制到了每个子应用里。

## 四、权限从哪来：只用基座下发的集合

`src/auth/permissions.ts` 是全局唯一的权限来源：

- 被基座加载 → 读 `HostGlobalState.permissions`（**基座算好下发**）
- 独立运行 → 读本应用自己的会话

**本应用不调用 `/api/auth/me`**：多一个调用点就多一处"只判了登录、忘了判权限"的可能。

`ready` 与"没有权限"被刻意分开：`ready` 为假时按钮也不显示，但页面给的是"正在获取权限…"
而不是"无权限"—— 后者在独立运行的首次加载时会是一屏假象。

### 显隐而不是禁用

禁用态点开 DevTools 就知道功能存在，而权限的语义是"这个入口与你无关"；
更要紧的是**显隐是二值的、可以被断言**，禁用态下"该灰"与"判错了才灰"在界面上没有区别。
每个按钮都把判定依据写在 `data-permission` 上，排查"按钮为什么没出现"时不用读代码。

## 五、它同时是一个 qiankun 子应用

| 关注点   | 做法                                                                                        |
| -------- | ------------------------------------------------------------------------------------------- |
| 应用名   | `platform-admin`，必须与基座 `src/micro/apps.ts` 的注册名**逐字一致**（不一致只卡"加载中"） |
| 路由     | 基座 `/admin/*`，`basename` 由基座下发                                                      |
| `base`   | dev `/`（带前缀会让热更新静默失效），build `/admin/`                                        |
| 端口     | `3500` + `strictPort` + `cors`                                                              |
| 挂载顺序 | `bindHost` → `initializeAuth()` → `connectPermissionSource()` → `render()`                  |
| 卸载顺序 | `destroy()`（含断开权限订阅）→ `unbindHost()`                                               |

> **`bindHost` 必须在 `initializeAuth` 之前**：认证端口靠 `HostProps.auth` 判断自己是"被基座加载"
> 还是"独立运行"，顺序反了会误判成独立运行，然后自己建一份会话 —— 两份会话并存，刷新各自失效。

> **权限订阅必须在 `mount` 里建立、`unmount` 里断开**，不能写在模块顶层：
> 子应用模块在多次挂载之间是复用的，而基座桥在 `unbindHost` 时会清空全部订阅者，
> 顶层订阅在第二次挂载后就再也收不到推送（症状是"第二次进入页面按钮全没了"）。

## 六、目录结构

```
src/
├── api.ts                    # 接口客户端（把认证端口接到传输内核的鉴权钩子上）
├── errors.ts                 # 异常 → 用户可读文案（403 不等于登录失效）
├── format.ts                 # 时间 / 状态格式化
├── permission-codes.ts       # 权限标识（转出 common-api 的 AccessPermissions）
├── auth/
│   ├── index.ts              # 认证端口：基座桥 or 自建会话；独立运行时的开发账号登录
│   ├── permissions.ts        # 权限快照 store（模块级订阅 + 断开）
│   └── hooks.ts              # useSyncExternalStore 适配：usePermission 等
├── components/
│   ├── PermissionButton.tsx  # 按权限显隐的按钮
│   └── Dialog.tsx            # 极简对话框
├── pages/
│   ├── Users/                # 用户列表 + 新建 / 编辑 / 重置口令 / 删除
│   └── Tenants/              # 租户列表 + 新建 / 编辑 / 删除
├── styles/                   # 设计令牌 + 全局样式（**令牌本应用一份，不跨应用引用**）
├── App.tsx                   # 顶栏（身份与权限集合）+ 标签页
└── main.tsx                  # 独立运行分支 + qiankun 生命周期
```

## 七、设计取舍

- **不做"通用表格组件"**：用户页与租户页的字段、操作、约束都不同（租户编码不可改、
  有子租户时不可删），抽象一层省下的代码远小于它带来的间接层。真正重复的只有显隐与错误提示，
  那两样已各有一份实现。
- **不做登录页**：见第三节。独立运行以"开发账号自动登录"起步，且只在 `import.meta.env.DEV` 下生效。
- **不做路由**：两个模块用标签页切换就够，引入路由会让子应用的 `basename` 与基座前缀再叠一层。
- **`usePermission` 未就绪时返回 `false`**：宁可少显示一个按钮，也不能默认放行 ——
  少显示会被下一次推送纠正，放行一旦渲染出来就可能被点到。
- **权限标识不在本应用里重写一份**：从 `common-api` 的 `AccessPermissions` 转出，
  那上面有一条"逐字钉死"的测试。前端拼一个 `auth:user:ceate` 不会报错，只会让按钮永远不出现。
