# platform-admin — 权限管理后台

权限域实体（用户 / 租户 / 资源 / 角色 / 用户组 / 组织）的管理界面，同时是 **ADR-0018 第③段**的验证载体：
**同一个页面、同一段代码，管理员看到完整的操作条，只读账号只看得到列表。**

六个标签页的顺序刻意分成两段：

- `资源`（能做什么）→ `角色`（打包 + 授资源 + 挂成员）→ `用户组`（把角色批量授给一群人），
  `用户` 页则回答反向的问题 —— **这个人现在持有的角色是从哪来的**（`角色来源` 反查）。
  这一段是"谁能做什么"的授权链路，从左到右读过去就是它的顺序。
- `组织` 排在最后，因为它回答的是**另一个问题**：`用户 → 主岗 → 组织` 决定
  **他看得到哪些数据**（`DEPT` / `DEPT_AND_CHILD` 两档数据范围的取值来源）。
  它不参与上面那条从左到右的链，硬插在中间会让人以为它也是授权的一环。

至此"谁能做什么"与"谁看得到哪些数据"在界面上都可读、可配、可追。

它不是产品功能，而是"权限判定单点计算、结果下发"这件事的**可运行证明**。

## 一、为什么"按钮级权限"值得单独做一个应用

只种一个超级管理员时，"权限到底生效没有"是**验证不了**的：所有接口对唯一身份都放行，
权限标识拼错、资源漏配、前端把显隐判反，症状都只是"看起来很正常"。

这个应用的两侧因此被刻意拉开：

| 身份                  | 权限                                                                                                               | 界面上应该看到                                                                                                            |
| --------------------- | ------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------- |
| `admin`（超级管理员） | **45 项**：27 项读写（六个模块各 4 + 审计读 1 + 日志读 1 + 事件读 1）+ **18 条菜单码**（5 个应用级 + 13 个页面级） | 六个标签页的完整操作条                                                                                                    |
| `auditor`（审计员）   | **14 项**：`auth:user:read` / `auth:tenant:read` / `auth:audit:read` + **11 条菜单码**（权限管理 7 + 审计日志 4）  | 六个标签页都在（菜单码是另一层），用户列表 + 「角色来源」「组织归属」「数据范围」三个反查；**所有写操作一个入口都不出现** |

`auditor` 能看到 `用户` 页的三个反查按钮，是因为**反查的权限归 `auth:user:read`**
（读的是"某个用户"的信息，与列表 / 详情同类），而它对用户组配置一律 `40301` ——
这两件事是分开决定的，界面上因此呈现出"同一个只读账号，有的模块点得动、有的模块点进去是空的"。

**这条划分在组织域上最完整，值得单独说清**（后端 `UserController` 的注释里写明了）：

| 读什么                              | 归哪个权限       | 后果                                                                |
| ----------------------------------- | ---------------- | ------------------------------------------------------------------- |
| 组织**树**（`/api/auth/orgs/tree`） | `auth:org:read`  | 审计员打开「组织」页会看到 `缺少权限：auth:org:read`，树上 0 个节点 |
| 某个人的**组织归属**与**数据范围**  | `auth:user:read` | 审计员照常可用                                                      |

两者**不互相蕴含**，因此都是"信息不足"而不是越权，方向是安全的：
只有 `org:read` 的人能改组织结构却看不到某个人在哪些部门；
只有 `user:read` 的人能反查个人归属却看不到树本身。

> **菜单与页面级过滤已完成**（`docs/decisions/0031`）：标签页按 `ui:admin_*:view` 过滤，
> 基座导航按 `ui:*:view` 过滤，且直接敲 URL 也会被 `RequireMenu` 送回概览并说明缺哪个码。
> 本应用与基座读的是同一份权限集合，因此"看不见"与"进不去"永远一致 ——
> 只过滤一侧的话，地址栏就是后门。
>
> 审计员被授了本应用的全部 7 个菜单码（1 个应用级 + 6 个页面级），因此六个标签页**都在**。
> 这是刻意的：**菜单码是布局、读写权限才是边界** ——
> 他进得去「组织」页，但那一页会因为缺 `auth:org:read` 显示 403（见上表）。
> 二者的分工记在 `docs/decisions/0031` 第 1 条。

**差异不写在代码里，只写在权限集合里** —— 页面代码里没有任何 `if (username === 'auditor')`，
这就是全程唯一要证明的东西。

服务端同样拦一道：审计员构造请求直接 `POST /api/auth/users`，返回 `40301`（不是 401）。
**前端显隐只是体验，权限边界在服务端** —— 把按钮藏起来当权限控制是这套东西最常见的误用。

> `40301` 是**业务码**，因此线上是 HTTP 200 + `code=40301`（本仓铁律：业务失败返 HTTP 200）。
> 前端 `errors.ts` 走的是 `BusinessError` 分支，直接显示服务端文案「缺少权限：auth:xxx」——
> 它比裸的 403 更有用：**指名道姓说出了缺哪一个权限码**。

## 二、跑起来

```bash
# 1. 后端（默认 8080，h2 内存库；种子数据只在 h2 profile 打开）
cd server && mvn -DskipTests install
java -jar sts-app/sts-app-server/target/sts-app-server-0.0.1-SNAPSHOT.jar

# 2. 前端（独立打开）
cd web && pnpm install
pnpm --filter platform-admin dev            # http://127.0.0.1:3500

#    或经基座打开（会带上登录页与导航）
pnpm --filter platform-portal dev           # http://127.0.0.1:3000 → 导航「权限管理」
```

开发期 `/api` 由 vite 代理到 `127.0.0.1:8080`；被基座加载时请求走**基座页面**的 `/api`
（也由基座的代理转发）—— 两条路径都通，所以代码里始终只写相对路径。

## 三、令牌从哪来：认证端口

本应用**不含登录页**（`docs/decisions/0018` 第 8 条：子应用不得再实现一套登录，
否则会立刻长出第二份会话逻辑）。它只关心一件事 —— **从哪取令牌、谁负责刷新**，
这件事由 `common-api` 的 `createConsoleAuth` 单点决定（`src/auth/index.ts` 里只剩应用名与开发账号）：

| 运行方式   | 令牌来源                                  | 刷新                   | 起步方式                                       |
| ---------- | ----------------------------------------- | ---------------------- | ---------------------------------------------- |
| 被基座加载 | 基座通过 `HostProps.auth` 下发的能力      | 基座（并发合并成一次） | 基座的登录页                                   |
| 独立运行   | 本应用自己的会话（同一份 `session` 实现） | 本应用自己的通道       | 已有刷新令牌则静默续期，否则用开发账号自动登录 |

两条路走的都是 `common-api` 的 `createAuthChannel` / `common-tools/session`，
区别只在"谁提供会话"。因此 `src/api.ts` 与页面代码**完全不区分运行方式** ——
`consoleAuth.port` 每次取令牌时才问"基座在不在"，所以客户端可以在模块加载时就装配好
（**这里曾经是一个延迟创建的函数**，因为端口要先 `initializeAuth()` 才能确定；
`docs/decisions/0034` 把两段式初始化取消后，那层延迟也就没有理由了）。

### 为什么下发的是"能力"而不是令牌值

`HostProps.auth` 只给两个动作：`getAccessToken()` 与 `reauthenticate()`。

- **令牌值会陈旧**：基座在后台静默刷新一次之后，子应用手里那份就是作废的令牌，
  而它自己并不知道 —— 症状是"刚才还好好的，突然所有请求都 401"。函数是按需取，一定是最新的。
- **刷新必须全应用一次**：刷新令牌是轮换的，重复使用会被服务端判为重放攻击并撤销该用户**全部**会话
  （`docs/decisions/0018` 第 7 条）。子应用若各自刷，就把这个坑复制到了每个子应用里。

## 四、权限从哪来：只用基座下发的集合

`src/auth/permissions.ts` 是全局唯一的权限来源：

- 被基座加载 → 读 `HostGlobalState.permissions`（**基座算好下发**）
- 独立运行 → 读本应用自己的会话

**本应用不调用 `/api/auth/me`**：多一个调用点就多一处"只判了登录、忘了判权限"的可能。

`ready` 与"没有权限"被刻意分开：`ready` 为假时按钮也不显示，但页面给的是"正在获取权限…"
而不是"无权限"—— 后者在独立运行的首次加载时会是一屏假象。

### 显隐而不是禁用

禁用态点开 DevTools 就知道功能存在，而权限的语义是"这个入口与你无关"；
更要紧的是**显隐是二值的、可以被断言**，禁用态下"该灰"与"判错了才灰"在界面上没有区别。
每个按钮都把判定依据写在 `data-permission` 上，排查"按钮为什么没出现"时不用读代码。

### 一个菜单码都没有时看到的是什么

一个标签页都不渲染，页面给出一句 `admin-empty`。这句话必须说清**这件事为什么自己解决不了**：

> 授权就在本后台内，而进本后台同样需要菜单码 —— 只能由**另一个**已持有 `ui:admin_*` 的账号来授。

**"给自己授权"是一条闭合路径**（需要 `ui:admin_role:view` 才看得到「角色」标签页，而菜单码正是在那个标签页里授的），
所以首次可用性只能由种子账号或库侧提供 —— 那是 `docs/decisions/0031` 决策 1 推到尽头的推论，
不是待修的缺陷。要防的是**用户以为这是他能自己解决的事**：不说清，他只会反复刷新、怀疑应用坏了。

生效方式只说**"刷新本页"**，不说"回门户顶栏点「重新检查权限」"：
本应用**可以独立运行**（`docs/decisions/0018` 第 8 条），那时没有门户也没有顶栏，
而"刷新本页"在两种形态下都成立（独立运行时它自己走刷新接口，被基座加载时由基座走并把权限下发）。
理由与取舍见 `docs/decisions/0048`。

同理，**新建用户**成功后的通知会带上"下一步"：新账号默认没有任何菜单码（`0031` 决策 2），
所以"建出来了"与"能用"之间隔着一步授权。只报"已新建用户「x」"会让管理员认为工作已经完成 ——
直到那个人登录进来说"里面是空的"才回头查，而那时现场已经不在管理员手上了。

**但这句通知不能写死。** 租户配了「默认角色」（`docs/decisions/0049`）之后，
建号那一刻服务端已经替他做完了那一步 —— 此时照旧报"默认没有任何菜单码"，
会在同一句通知里**既说错事实、又把人指去重复做一件已经做完的事**。
因此它按响应的 `UserVO.defaultRoleNames` 分岔：非空就说"并按租户默认角色自动授予：…"，
为空才走上面那段。空的原因**分不出**"该租户没配"与"配了的都已停用"，所以两种都写出来，
而不是替用户认定一个 —— 认定的那个会让他去错的地方找。

## 五、它同时是一个 qiankun 子应用

| 关注点   | 做法                                                                                        |
| -------- | ------------------------------------------------------------------------------------------- |
| 应用名   | `platform-admin`，必须与基座 `src/micro/apps.ts` 的注册名**逐字一致**（不一致只卡"加载中"） |
| 路由     | 基座 `/admin/*`，`basename` 由基座下发                                                      |
| `base`   | dev `/`（带前缀会让热更新静默失效），build `/admin/`                                        |
| 端口     | `3500` + `strictPort` + `cors`                                                              |
| 挂载顺序 | `bindHost` → `connectPermissionSource()` → `render()`                                       |
| 卸载顺序 | `destroy()`（含断开权限订阅）→ `unbindHost()`                                               |

> **`bindHost` 必须在 `connectPermissionSource()` 之前**：权限 store 在 `connect` 时**读一次**身份，
> 而"用宿主下发的身份还是自己的会话"这个判据是"**有没有宿主桥**"。顺序反了会把它误判成独立运行，
> 然后自己建一份会话 —— 两份会话并存，刷新各自失效。
> （`0034` 之前这里还夹着一步 `initializeAuth()`；那个函数已随两段式初始化一起取消，
> 但**顺序约束没有消失，只是换了位置**。）

> **权限订阅必须在 `mount` 里建立、`unmount` 里断开**，不能写在模块顶层：
> 子应用模块在多次挂载之间是复用的，而基座桥在 `unbindHost` 时会清空全部订阅者，
> 顶层订阅在第二次挂载后就再也收不到推送（症状是"第二次进入页面按钮全没了"）。

## 七、设计取舍

- **不做"通用表格组件"**：用户页与租户页的字段、操作、约束都不同（租户编码不可改、
  有子租户时不可删），抽象一层省下的代码远小于它带来的间接层。真正重复的只有显隐与错误提示，
  那两样已各有一份实现。
- **不做登录页**：见第三节。独立运行以"开发账号自动登录"起步，且只在 `import.meta.env.DEV` 下生效。
- **不做路由**：六个模块用标签页切换就够，引入路由会让子应用的 `basename` 与基座前缀再叠一层。
- **不做"通用成员对话框"**：角色的成员允许 `USER` / `GROUP`，用户组与组织的成员只允许 `USER`
  （组的嵌套在判定链路里只跳一层）。三者外形相似但**取值域不同**，
  合并成一个会得到一个"参数控制谁能被选"的组件 —— 那种组件最容易在某条路径上悄悄放开限制。
- **组织页只有树视图，没有列表视图**：资源页给了两个切面（树看结构、列表看检索），
  因为资源是扁平目录、条目多；组织不同 —— **它本身就是一棵树、`parentId` 是唯一的关系**，
  而部门树是人手维护量级。契约里确实有分页接口（支持按编码 / 名称 / 全称搜索），
  那是给 API 调用方用的；在这里再渲染一遍同样的行，只能得到一份丢掉层级的平铺列表。
  与其做一个半吊子的第二视图，不如不做。
- **组织页的"移动"是独立入口，不在编辑里**：它会把**整棵子树**的层级、物化路径与全称一起重写，
  而路径正是 `DEPT_AND_CHILD` 的求值口径 —— 一次移动会同时改变子树上每个人的可见范围。
  因此它的对话框第一段就明说这件事，审计动作也是独立的（`auth.org.move`）。
- **编辑组织前必须先回查详情**：树节点不带 `orgType` / `managerId` / `description` / 联系方式。
  直接拿树节点填表单，会把这几项渲染成空 —— 而保存时它们会以空值提交，
  于是"我只是改了个名字"会把描述与联系方式一起清掉，且不报错。
  这里的分工是：**树提供结构与导航，详情提供表单初值**，两者都不能省。
- **不提供会骗人的开关**：用户组表单里没有"分组方式"选择（只支持 `STATIC`，直接显示成禁用文本）、
  没有 `filterJson` / `orgScopeJson` 输入框，组织表单里**没有层级 / 路径 / 全称**（由服务端派生）、
  编辑态**没有上级选择器**（改层级会被服务端以 40001 拒掉，渲染一个能改的下拉等于给一个必然报错的开关）。
  角色表单的数据范围下拉**只有四档**：`CUSTOM` 被去掉 —— 它要 `filterJson`，而本仓不解析、
  界面也无处填写，摆出来就是"选了也配不了、配了也不生效"。存量角色若正是 `CUSTOM`，
  仍在编辑对话框里作为**历史值**显示（不让它变成空白，否则会被误读成"数据范围丢了"）。
  **接受一个没人读的字段，最坏后果是填的人以为它生效了。**
  **资源表单里的「免鉴权」按同一条规则撤下了**（`docs/decisions/0052`）：判定的唯一来源是
  **接口上有没有 `@RequiresPermission`**，而真正公开的接口（登录 / 健康检查 / 上报）
  在资源表里**一行都没有** ⇒ 这一列对本表里存在的每一行都只能诚实地填 0，
  摆一个「是（白名单）」的选项，等于让人在那里记下一句反话。
  它仍留在表单状态里**原样回传**，不是忘了删：资源更新是全量覆盖
  （`ResourceService#update` 调 `applyTo`，缺省值落 0），不发这个字段会被后端按缺省值落库 ——
  那是"改个图标顺手把备注抹掉"。
- **角色表单里的「默认角色」是"先实现、后摆出来"的**：这一列早在建表时就有
  （`bw_auth_role.is_default`，注释原文就是"新用户自动授予"），但它此前**没有任何读取方** ——
  因此它一直与 `inheritStrategy` / `filterJson` 并列在"不进表单"那一类里，
  理由是"只存不用的字段不给它配的样子"。`docs/decisions/0049` 把消费方（建号时按它自动授予）
  补上之后，这条界线**自己把它纳了进来**，不是有人决定"放开"它。
  顺序很要紧：反过来做（先摆出来、后实现），它就是下一条 `CUSTOM`。
  同一处还有一条**契约上的陷阱**：`isDefault` 是非必填 `Integer`，
  后端按"字段是否为 `null`"决定要不要 `SET` 这一列 —— 所以**取消勾选必须显式传 `0`**，
  传 `undefined` 会被读成"不改这一列"而**静默失效**。有一条用例专门盯这件事，
  因为"`checked ? 1 : undefined`"是个看起来完全正确的写法。
- **`usePermission` 未就绪时返回 `false`**：宁可少显示一个按钮，也不能默认放行 ——
  少显示会被下一次推送纠正，放行一旦渲染出来就可能被点到。
- **权限标识不在本应用里重写一份**：从 `common-api` 的 `AccessPermissions` 转出，
  那上面有一条"逐字钉死"的测试。前端拼一个 `auth:user:ceate` 不会报错，只会让按钮永远不出现。
