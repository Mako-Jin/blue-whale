## 新增公共能力包 common-tools + 公共依赖治理（catalog）

舰长要求：查看 `platform-terminator/packages/common-tools`，给新项目加一个存放公共内容的包，并把其中的 logger「颜色、格式、层级、配置」全部优化。

### 一、先回答"存放公共依赖的包"

**结论：不需要这样的包。** "公共依赖"其实是两件事，混在一起两头都错：

| 诉求 | 正确做法 |
|------|----------|
| 第三方依赖的**版本**统一管 | pnpm **catalog**（写在 `web/pnpm-workspace.yaml`） |
| 自研**公共代码**复用 | `packages/common-<能力>` 包 |

- 建"存放依赖的包"会产生**幽灵依赖**：库能被引用到，却没出现在引用方的 `package.json` 里，运行时解析不到、IDE 也提示不出来。
- catalog 只统一版本号，依赖归属仍留在各自 `package.json`，两者兼得。

## 日志上报与配置服务：评价 + 落地 LogRecord 契约

舰长提出两个架构问题，要求先评价再决定改不改。

### 一、评价结论

**① 日志上报：事件机制与异步 HTTP 不是二选一，是两层。**

- 事件 / 输出通道 = 应用**内部**的分发解耦；HTTP = 众多出口中的**一种传输方式**。
- **"直接用异步 HTTP 调用"是明确不推荐的做法**，四条理由：
  1. 页面关闭时 `fetch` 被取消 → **最需要的那条日志必丢**（用户崩溃后关页面）。可靠手段是 `navigator.sendBeacon()`。
  2. 写放大 → 日志量 = 用户数 × 会话时长 × 密度，后端会被自己的客户端打挂。
  3. 日志雪崩 → 上报失败产生 error 日志 → 又触发上报，递归。
  4. 敏感信息外泄 → 脱敏必须在采集层，不能指望后端。
- 正确链路：**埋点 → 聚合（批量·采样·去重·脱敏·限流·断路）→ 传输（beacon 优先，fetch 兜底）→ 服务端**。
- 采样/限流是**必选项**不是优化项；traceId 跨端打通是最高优先级。

**关键诊断：现有 `LogSink` 不适合当上报钩子。** 它是 `(method, args) => void` 的 **console 代理**，拿的是**渲染后**的字符串：
- **级别有损**：`LEVEL_CONSOLE_METHOD` 把 `info`/`success` 都映射为 `'log'`，`trace`/`debug`/`perf` 都成 `'debug'`。
- **元数据被拍平**：命名空间、时间戳、traceId 全被拼进字符串（`formatContext` 拼成 `k=v` 尾巴），要拿结构化字段只能反向解析自己的格式。

**② 配置服务：别把"配置"当一个东西做，否则必然长成上帝对象。** 按「作用域 + 敏感度」分三层：

| 层 | 内容 | 载体 | 归属 |
|---|---|---|---|
| 业务运行期配置 | 开关、灰度、主题、超时、接口地址 | **自研**，走 OpenAPI 契约 | 本项目 |
| 部署级配置 | 数据源、中间件、线程池、限流 | **成熟组件** Nacos/Apollo | 运维 |
| 密钥级配置 | 数据库密码、第三方 Key、证书 | **Vault/KMS** | 安全 |

**自研范围只有业务运行期这一层**（只有它有业务语义、需要两端共享类型）。客户端配置五条底线：首屏零阻塞、兜底默认值必须在客户端、版本化+缓存+变更通知、配置项有 schema 与类型、环境物理隔离。
