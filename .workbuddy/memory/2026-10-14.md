## ADR-0047 轮 · 登出的两条语义与「退出所有设备」

**一句话**：`0046` 留的「退出所有设备缺独立入口」不是"缺一条接口"—— **能力早在，它只是没有名字**，
而那条路径上叠着四个后果（全撤没有写法 · 危险动作当省略的默认值 · 未认证时静默成功 · 零用例）。
判据：**一个动作如果"省略它"会得到更重的后果，那它不是可省略的 —— 它该有名字。**

### 核出的（`0046` 那句话的两处）

- **预设"那条接口还需要一个权限码"被推翻**：与 `/api/auth/password` 同一条判据（能登录就该能踢掉
  自己的会话），**不该有权限码** —— 挂上会让没被授权的用户永远清不掉自己名下的会话，
  而那正是他怀疑账号被人登着时唯一能自救的动作。
- **`/api/auth/logout` 此前零用例覆盖**（`grep -rn "logout" --include=*.java server/` 只命中 main）。
  一个"两条语义共用一条路径、靠请求体在不在区分"的接口，一条用例都没有 —— 那两个问题才会一直活着。
- **最诚实的证据是前端被逼出来的防御性代码**：`channel.ts` 里 `if (refreshToken) await authApi.logout(...)`。
  一个工程师遇到"省略有语义"时的处置 —— 不这么写，"本地没有令牌"这条兜底路径就会变成一次全设备踢出。
- **顺带纠正 `0046` 的一处事实**：改绑邮箱/手机**今天就能改**（`UserService#update` 里有 `setEmail`/`setPhone`
  + 唯一性校验），所以"要不要清会话"那一问不是假想的。答案也不是"照着清"：要撤的**不是会话**，
  而是**旧邮箱上未完成的找回凭证**（口令泄露撤的是"攻击者手上的令牌"，换绑撤的是"发往旧地址的那些链接"）。
  并核出**换绑邮箱在审计里与"改了个昵称"长得一样**（`AuditLogEntity` 没有"改了哪个字段"这一列）。

### 改动与验证

- `logout` 的 `requestBody` 改必填（语义收窄为"撤请求体里那一个会话"）· 新增 `POST /api/auth/logout-all`
  （`require()` 定死作用域、不接参数、不记审计但记 INFO）· 前端 `logoutAll` 失败**抛出且不清本地会话**（与 `logout` 相反）·
  门户顶栏新增入口 + 确认对话框（对话框外壳抽到 `components/dialog.less`，与改密共用）·
  4 个真机脚本的登出选择器改成 `[data-testid="sign-out"]`（原先是"登出恰好是最后一个按钮"的位置假设）。
- 后端 **214 例 / 34 报告文件 / 0 失败** · 前端 **8 包 571 例** + typecheck/lint/format 全通过 ·
  三个零前置守卫全绿（文档索引 47 篇 `0001~0047` 连续 · 契约 69 接口 / 45 路径 · nginx）。
- 提交 `c9377c1`（26 文件）与记忆一笔。**推送成功**（`8e1fcd8..c9377c1`，三笔全上）。

## ADR-0048 轮 · 授权生效路径与"给自己授权"的闭合路径

**一句话**：`0031` 那句"新账号一概没有菜单码"把后果写在**"谁来授权"**上；这一轮查的是
**被授权之后** —— 那一侧有两个缺口，一个在界面上，另一个在**闭合的路径**上。

### 核出的三件事

- **两处空态只说了"缺什么"**（`home-empty` / `admin-empty`）：没说去哪补，也没说**补完怎么生效**。
  后一件涉及真实链路 —— 权限只在**登录与刷新令牌**时回来（`LoginVO` 类注释与
  `platform-portal/src/auth/index.ts` 写着同一件事），于是"管理员授好了"与"界面能看见了"
  之间隔着**一次会话更新**，而当时**没有任何东西能让它提前发生**。
- **`AuthChannel.reload()` 零调用方**：声明就是为这件事写的、实现三行（`/me` →
  `session.updateUser` → 订阅者重渲染）、有文档有类型 —— **就是没人调**。
  与 `0045` 零写入方 / `0046` 位置错了 / `0047` 没有名字同族，但**形状不同、更难发现**：
  它不是死代码（类型检查不报），只是**永不执行**。这一族的第四种形状 → 记成"**没有入口**"。
- **"给自己授权"是闭合路径**：授菜单码在管理台「角色」页，而进管理台本身要菜单码 ⇒
  一个没有任何 `ui:admin_*` 的账号**无论持多少读写权限**都补不上自己的码。
  这是 `0031` 决策 1 推到尽头的推论，不是待修的缺陷 —— 但要**别让用户以为他能自己解决**。

### 改动与判据

- 基座顶栏加「重新检查权限」（`auth.reload()`）：三种结果分开表达，
  **"没有变化"必须说出来**（否则"界面没动"与"点了没生效"同形 ⇒ 重复点或去走更贵的
  "重新登录"，而真实原因常是**授错了账号**）；失败不结束会话（一次查询失败不是凭据失效的
  证据，`0045` 判据）；补了 `:disabled` 样式（`&__action` 此前只有 `:hover`，禁用后看着仍能点）。
- **不放子应用**：被基座加载时权限由基座下发、子应用不得自调 `/me`（`0018` 第 3 条）
  ⇒ 改了也不生效 = 假开关。所以 `reload()` **不向子应用开放**（"暂时不给"改判为"给了必然错"）。
- 两处空态说满**缺什么 / 到哪补 / 补完怎么生效**；管理台那句如实说出"自己授不了"、
  生效方式**只说"刷新本页"**（该应用可独立运行，`0018` 第 8 条）；建号通知带上"下一步"。
- **顺带核出一处前端陷阱并当场修掉**：JSX 会把**跨行文本按空格拼接**，prettier
  （`printWidth: 100`）又会重排超宽行 ⇒ 中文句子里凭空多出空格。**第一版就写出来了**：
  prettier 折行后渲染成 `只能由另一个 已持有 ui:admin_* 的账号来授 （在角色 页…`。
  处置不是"写完记得看一眼"，而是让它在结构上不可能发生：**每行一句 + 行尾 `<br />` 断
  + 每行不超 printWidth**；并各补一条**按整段断言**的用例 —— 逐词断言抓不到它
  （关键词本身没被改动）。同一坑在 `Home` 的 `home__desc`（三行文本）里**早已存在**
  （多出的是标点后的空格，比词间空格更不显眼），**旧文案本轮不改**，只在新文案上立规矩。

### 验证与提交

- 前端 **8 包 581 例**（基座 44 → **52**、管理台 29 → **31**）· lint 10/10 · typecheck 10/10 ·
  format ✓ · 守卫三项全绿（**文档索引 48 篇 `0001~0048` 连续** · 契约 69 接口 / 45 路径 · nginx）。
- 提交 `9a33d0c`（14 文件）并推送成功（`b8e4c26..9a33d0c`）；`git show --name-only` 复核无多带。
- **一次自伤与处置**：给 `common-api/README.md` 加行时 `old_string` 多带了一个换行，
  把 `reload()` 与 `reauthenticate()` **并成了同一行**。⇒ 用 Node 脚本按列宽重建，
  并**先拿相邻一行做"逐字符一致"自检**再改（算法第一次差 1 列，正是这一步抓出来的）。
  教训：**改对齐表格别手填空格**，用脚本 + 一行基准复核。

### 方法论

- 同一族缺陷的**第四种形状**：`0045` 零写入方 · `0046` 位置错了 · `0047` 没有名字 ·
  `0048` **没有入口**。前三种都能被 grep 到（写到别处了 / 没写 / 写了别的），
  第四种**写对了、写全了、写着呢**，只是**没有任何东西会执行它** ——
  要发现它，得问"这个能力**由谁触发**"，而不是"这个能力在不在"。
- **"没有变化"也是一种必须说出来的结果。** 反馈设计里容易被忽略的一类：
  界面毫无动静与"动作没生效"在用户眼里**完全同形**，于是他会重复动作 ——
  而真实原因往往在**别处**（这次是管理员授错了账号）。凡是"点了可能什么都没发生"的入口，
  都要回答"如果什么都没发生，用户怎么知道原因不在他这边"。

- **租户级开关这个模式已经存在，而且是空的。** `bw_auth_tenant.allow_register`（注释"是否允许自助注册"）
  与 `allow_add`（"是否允许下级创建租户"）：列 / 三方言迁移 / 契约 / 写入 / 回显全在，
  但 `getAllowRegister()` / `getAllowAdd()` **全仓零调用**，租户表单**没有开关**（只有编码 / 名称 / 描述），
  而 `allow_register` 描述的动作**根本不存在**（auth 域无注册端点，`grep -rni register` 只命中它自己）。
  ⇒ **生产者与消费者两头都空，只剩中间那截管道。** 那一族缺陷的**第五种形状：契约里的空位**
  （连"假开关"都算不上 —— 假开关至少有个能被点的东西）。
- **`bw_auth_role.is_default` 不是空位，是半成品。** 数据库注释原文就是"是否默认角色（**新用户自动授予**）"，
  写入 / 入口校验（只收 0/1，且有专门用例）/ 契约 / VO / 种子全齐，**唯独"读它去授予"没写**；
  而且角色表单**刻意不摆它**（与 `inheritStrategy` / `filterJson` 并列），理由是"只存不用的字段不给它配的样子"
  —— 写得对，只是描述的是**当时**的状态。
- **我自己上一轮推荐错了**：提 `tenant.default_role_id` 时**漏看了这一列**。它才是为这件事造的、
  位置就在角色表上，且天然支持"一个租户多个默认角色"。⇒ 改用它（当场跟用户重拍了一次）。
- **同一件事，两句相反的话写在两份文档里**：`0022` 决策 11 把 `isDefault` 归进"**会被判定链路读取**"
  （作为严格校验的理由），而 `RoleSaveRequest` 的 `@Schema` 与 `api/README.md` 都写"**当前只存不用**"。
  隔 98 行、各自被读过、**从没被放在一起读过**。真实的错法是**按形状归类而不是按判据归类**。
- **"租户管理员"在本仓还不是一个概念**：种子只有 `admin`（`data_scope=ALL`）+ `auditor`，权限扁平，
  `auth:tenant:*` **没有租户内隔离**（持码者能改所有租户）；`DataScope` 的消费方只有一个：审计查询。
  ⇒ 如实写进文档，不让它读起来像已隔离。

### 改了什么

后端：`RoleMemberService.grantDefaultRolesTo`（新，复用 `bind` 不另写插入；只取 `status=ENABLED`；
不记审计但记 `log.info`）· `UserService#create` 同事务调用、异常照抛 · `UserVO.defaultRoleNames`

文档：ADR-0049 + `docs/README.md` §四索引（首列宽 62）与 §二**新增一行**「租户级配置开关」·
`server/README.md` 硬规则表（首列宽 68）· `api/README.md` 模型表两行 · `platform-admin/README.md`
（空状态节 + 设计取舍节）· 契约重导出 + `schema.d.ts` 重生成。

### 两次踩坑（都是自己写出来的）

- **契约陷阱**：`isDefault` 是非必填 `Integer`，后端按"字段是否为 `null`"决定要不要 `SET`
  ⇒ **取消勾选必须显式传 0**；`checked ? 1 : undefined` 是个**看起来完全正确**的写法，
  而它会让"取消默认角色"**静默失效**。前后端各一条用例钉住。
- **JSX 跨行注入空格又踩了一次**（`0048` 刚立过规矩）：给角色表单的 `form__tip` 加行时没给每行结尾加 `<br />`，
  渲染成"只存不用， 是"。⇒ 改成**每一行都以 `<br />` 收尾**（元素隔在中间时，紧贴标签的含换行空白会被 JSX 丢掉，
  所以 prettier 无论怎么折行都不会再注入空格），并补一条**按整段断言**的用例。

### 验证与状态

- 后端 `mvn verify` **220 例 / 35 报告文件 / 0 失败**（+6 = 新增 `DefaultRoleOnCreateApiTest`）
- 前端 **8 包 583 例**（管理台 **31 → 33**）· lint / typecheck **各 10/10** · format ✓
- 守卫三项全绿：**文档索引 49 篇 `0001~0049` 连续** · 契约 69 接口 / 45 路径 · nginx
- 提交 `4c6e548`（**17 文件**，`git show --name-only` 复核无多带）
- **推送未成功**：代理 502 ×3，默认凭据路 `schannel: server closed abruptly` / `Empty reply from server`
  ⇒ 按规矩收手，**领先 1**，下次开工先补推

### 方法论（这条比改动本身值钱）

- **"半成品"与"契约里的空位"是两种缺陷，处置相反。** 空位（`allow_register`）两头都空，
  要么补消费方、要么承认它是空的；**半成品（`is_default`）只差最后一步，而它往往带着"为什么停在这里"的档案**
  —— 动手前**先读那份档案**，否则会像我一样差点在它旁边再加一个同义字段。
- **同一件事的两句话写在两份文档里，各自被读过却从没被放在一起读过。** 这类矛盾**守卫抓不到**
  —— 守卫只能守"有权威源"的那种（契约 → 文档、代码 → 契约）；文档内部的互相矛盾没有权威源，
  只能靠**在改动时顺手去搜它的反话**（这次是 `grep "只存不用"` 才把两句撞到一起）。
- **按形状归类而不是按判据归类**，是比笔误更常见的错法：两个字段形状一样（都是开关），
  语义可能一个早已落地、另一个还是空的 —— `0022` 决策 11 就是这么把 `isDefault` 列进去的。

## 0050 —— 「租户存在性」的四个属主（用户域是唯一不校验的那一处）

**起点**：补 `0049` 未覆盖 1（"租户管理员"）时顺手核"哪几处能跨租户"，核出的却是另一件事。
**缺陷**：四个带 `tenant_id` 的域（用户 / 角色 / 组织 / 用户组）各写一遍同名私有 `resolveTenantId`，
用户域那份**漏了存在性校验**；而另外三处的 javadoc 都写着"与 `UserService` 的『只取不校验』**有意不同**"
—— 三处都只说了"不同"，没有一处写下"为什么可以不同"，且 `resolveTenantId` / "只取不校验" 在 `docs/` 下**零命中**。
DDL 里**零 `FOREIGN KEY`、零 `CONSTRAINT`** ⇒ 应用层不挡就没人挡。
**红证**（源码 stash 回旧版、用例不动）：`POST /api/auth/users` 带一个不存在的 `tenantId` 返 **`code: 0` ——
账号被成功建出来了**（永远登不进来，却永久占着 `uk_bw_auth_user_tenant_username`）；列表带不存在租户返空列表；
而三个 sibling 域在旧代码上**本来就返 40002** —— 反证只有用户域缺那一步。

**改**：`TenantService#assertExists` 成为 `40002` 与文案的**唯一属主**（与 `requireTenant` / `40402` 刻意分开）；
四域都调它 ⇒ 三个服务**不再注入 `TenantMapper`**；`UserService.resolveTenantId` 不再是 `static`。
新增 `TenantReferenceApiTest` 5 例 —— **断言的是"四个域给同一个答案"**，不只是用户域（只测用户域挡不住再漂一次），
另配两条正例（不传落自己租户、显式指定的**存在**租户被尊重：补校验最容易把"跨租户建号"一起挡掉）。
顺带订正 `docs/api/README.md` 里 `UserGroupSaveRequest`「**没有 `tenantId`**」那句 —— 契约里它有，
而同表 13 行外的 `ResourceSaveRequest` 写的同样的话**是对的**。

**验证**：后端 `mvn verify` **225 例 / 36 报告文件 / 0 失败**（+5）· 守卫：文档索引 **50 篇 `0001~0050` 连续** · 契约清单 ✓
· 提交 `bd745b0`（**10 文件**，`git show --name-only` 复核无多带）· **推送仍未成功**（代理 `schannel: server closed abruptly` 3 次、直连 21 秒超时）⇒ **领先 3**

### 方法论（这一轮新长出来的）

- **"复制 + 用注释追认"比"漏写注释"更难发现**：疏漏会在评审时被问，而"有意不同"是一个答案。
  与 `0049` 那条是同一家族 —— 信息写得够多，但从没被放在一起读过。
- **同一段 helper 复制 N 份时，漂移的不是"逻辑"而是"少了一步"**，而且漂移点常能被**静态特征**指出来：
  用户域那份是四份里**唯一 `static` 的**、唯一不持有 `TenantMapper` 的 ——
  "要不要校验"的答案，恰好落在"有没有那个依赖"上。
- **根因是"规则没有属主"**，所以修根因 = 给规则一个属主（判定收进 `TenantService`），
  而不是只把漏掉的那一份补上 —— 只补一份，下次还能再漂。
- **一句话被顺口复制到它不成立的地方**，是同一族的第三种形态（`0049` 是"两句话写在两份文档里"）：
  它**没有守卫**（`verify-api-contract.mjs` 核的是接口清单，不核字段级散文）⇒ 改法是**把规则收成一条、
  写在一处**，而不是逐个模型复述。


## ADR-0051 —— 引用的租户「存在 ≠ 可用」（提交 `04582f5`）

起点是 `0050` 的两条尾巴。**先去核那条标着"本轮没有验证"的**（软删租户能不能被引用）：

- 核完发现**本来就覆盖了** —— `bw_auth_tenant` 有 `deleted`，`BaseEntity` 上标了 `@TableLogic`，
  全局配置（`application.yml` 的 `mybatis-plus.global-config` 只有 `banner: false`）没覆盖默认值
  ⇒ `selectById` 自带 `deleted = 0` ⇒ 逻辑删除的租户在应用层**等于不存在**，走既有的 `40002`。
  一条用例钉住（`shouldTreatDeletedTenantAsAbsent`）。**"未验证"关闭的代价是一条用例，不是一段推理。**

### 顺着"可用"再往下一格，撞见新的

- `bw_auth_tenant.status` 在全仓**只有一个读者 = 登录**（`AuthService#login`），且刻意返 `40101`。
  ⇒ 四个域往**已停用**租户里建数据全部 `code: 0`（实测 4 条）：账号永远登不进来、
  **永久占着 `uk_bw_auth_user_tenant_username`** —— 与 `0050` 修掉的那批是**同一个东西**，
  差别只在成因"主键错" vs "状态错"。
- **仓里已有同一条先例**：`OrganizationService#resolveParent` 拒绝挂到停用的父组织下
  （"会得到一个算不出范围的分支"）—— 而**停用的租户更强**：那个组织只是不参与范围求值，
  这个租户连登录都进不去。这条先例是本轮判据的直接依据（不是我新发明的规则）。

### 实现要点

- `TENANT_DISABLED(40920)` 与 `40002` **分成两格**（处置不同：等启用 / 改主键）。
- `TenantService#assertAcceptsNewData`，与 `assertExists` 共用 `requireReferencedTenant`
  —— **分成两个方法不该让同一种输入出现两种答案**（同一次查询、同一份文案）。
- **只挂四个域的 `create`，刻意不放进 `resolveTenantId`**：那个方法**同时服务读与写**
  （每域两处调用点就是这两条路）。判据若被后来者挪进去，就有用例先红
  （`shouldStillReadDataOfDisabledTenant` 钉的就是这条边界）。

### 本轮最有价值的一条：实测出、**没修**

- **停用租户对"已经在用的人"不生效。** 探针（写完即删、不入库）实测：
  停用后重新登录 `40101`，但**续期 `code: 0` 通**、旧访问令牌调 `/me` 也通。
  根因就在 `AuthService#refresh` 那一行上，**不对称就在同一行**：
  `tenant == null || user == null || !Status.ENABLED.equals(user.getStatus())` ——
  **用户判了状态，租户只判了非 `null`**。加上 `AuthTokenFilter` 无状态不查库、
  访问令牌 2 小时、刷新令牌**轮换** ⇒ 只要一个会话在被用，它就永远续得下去。
  这是"**状态列没有读者**"那一族的又一例（`0022` 停用角色、`0024` 停用用户组），
  而 `0045` 已经就同一件事下过结论（"只在登录拦是不够的"）。
- **它不修的理由是耦合**：一旦续期也判租户状态，"停用自己所在租户"就**立刻**变成
  "一次点击把全租户锁在门外、恢复只能改库" —— 因为**本仓没有"租户之外"的平台账号**。
  两条必须一起决定。所以我先只做与这个答案无关的那一半（新账号登不进来）。

### 方法论（这一轮新长出来的）

- **"先辨真伪"用在"上轮的未验证项"上收益极高**：核完发现它本来就成立 ——
  那就**用一条用例关闭它**，而不是继续把它留在文档里当"未知"。
  未验证项的成本不在"不知道"，在它会让后面每一步都要重算一次前提。
- **一个缺口的两半可能是同一个东西**：`0050` 的产物与 `0051` 的产物在**四个维度上完全同形**
  （登不进来 / 匹配不上判定 / 占唯一索引 / 无提示），只有成因不同。
  认出这一点，第二次修复的判据、错误码分格、测试形状全都直接沿用。
- **判定要放在"它被需要的那一层"**：`assertExists` 放 `resolveTenantId`（读也走它是对的），
  `assertAcceptsNewData` 放 `create`（读不该走它）—— **位置本身就是边界**，
  所以位置要配一条用例。
- **再顺手核出第三处**：`server/README.md` 的错误码表从 `0030` 起就没跟
  （`40919` / `40410` 都没登记）。要往一张表里加新行时，**先看上一行是不是也缺**。
- **探针（一次性测试）是"实测未修项"的正确工具**：它给出的是可引用的结果，
  又不会把"当前行为"钉成"约定行为"（等真的决定落定再补用例）。

## ADR-0052 —— 一份「安全评审清单」字段的两次追认（提交见下）

### 先做了两件"顺手但必要"的事

- **推上去了**（领先 6 的六笔走代理一次成功；`unable to write credential store` 是无害项）。
- **终于看了 CI**：`~/.git-credentials` 有**两条** github 行，`head -1`（`gho_`、user=`Mako-Jin`）
  能用，另一条（`ghp_`、user=邮箱）**返 401**。取错那条就会得出"私有库 404 / CI 看不了"的
  错误结论 —— 这才是"CI 没人看过"的真实原因。换回第一条后拉到 **16 次运行**：
  除一次 `cancelled` 外**全绿**；我们刚推的六笔对应的 run#16 **success**，逐 step 看
  **一个 `skipped` 都没有** —— `契约与代码是否同步`（`0042` 的字节判据**第一次真跑**，过）、
  `server-mysql` 的**防假绿自检**（过 ⇒ `services:` 在 runner 上**确实**起来了）、
  `产物自检 —— 种子口令不得进包`（过）。三条"从未验证过"的欠账一次清掉。

### 方法论：这一轮换了个做法

- `0051` 那一族的开关列缺陷**全是逐个偶然撞见的** ⇒ 本轮**把全部开关列一次扫完**
  （DDL 里 `status`/`is_*`/`enabled`/`allow_*`/`deleted`/`has_*`/`lock_*`，共 **27 个**）。
  结论：绝大多数有确定读者、且大部分就写在判定链路的两条 SQL 里（对照表已进 ADR）。
  **零读取方的只有四个**，三个早有记录，从未被记录的只有 `bw_auth_resource` 上那两个。
- **"哪些接口是公开的"不能靠读文本回答**：我先扫了三遍源码，**三遍三个答案**
  （第一次把 `/api/auth/login` 归成"有注解" —— 上下文窗口串到了上一个方法的注解；
  第二次路由名被字符串解析吃掉；第三次按"映射数 vs 注解数"手工数，
  `ResourceController` 多出的那一个其实是**类注释里提到过这个词**）。
  三次都在**最重要的那个端点**上给出相反结论 ⇒ 只能用框架自己的映射表
  （`RequestMappingHandlerMapping` + 与拦截器**同一个** `AnnotatedElementUtils.findMergedAnnotation`）。
- **守卫必须证明不是空转**（`0040` 的做法）：三处扰动全部非零退出且指名道姓
  （登记一个不存在的端点 / 摘掉一个真登记的端点 / **摘掉一个受保护端点的注解**）——
  第三条正是真正的失败模式：**"忘了写注解 = 静默公开"从静默变成构建失败**。

### 核心：字段的"两次追认"

- `bw_auth_resource` 上三个字段实现事实**完全一样**（`applyTo` 写、`toVO` 读），
  但契约里的自我描述是三种态度：`resourceVersion` 诚实写着"当前只存不用"；
  `isDeprecated` 什么都没写；**`isWhitelist` 写着"这是安全评审要看的一份清单" —— 而它不可能是**。
- **不可能是**的三条证据：① 种子资源 = `AuthPermissions.ALL` ⇒ **只有带权限码的接口才有行**，
  而公开接口（登录 / 健康检查 / 上报）**一行都没有**；② 于是该列**恒为 0**，
  读起来像"没有接口是公开的"（实际 9 个）—— **一份能给出相反结论的清单比没有清单更危险**；
  ③ 判定源是"**白名单反着写的**"那条规则（`0026` 的根因），所以它**没有可同步的对象**。
- 处置：新增 `AuthPublicEndpoints`（公开端点**唯一登记处**）+ 守卫；订正实体注释与两处 `@Schema`；
  `isDeprecated` 补"当前只存不用"；**资源表单的「免鉴权」撤下控件**（保留原样回传：
  更新是全量覆盖、不发会被按缺省值 0 落库）；不删列、不改契约结构、**DDL 列注释不回改**（checksum）。
- **前端的「不提供会骗人的开关」那条边界早就写下了**，只是没人拿它检查资源页 ——
  这次是那条规则**自己**把一个字段纳了进来（与 `0049` 反过来：那次是补上消费者后界线自己放行）。

### 顺手核出的两条本机坑（已进 MEMORY §1）

- `~/.git-credentials` **两条** github 行，只有 `head -1` 那条有效（前缀 `gho_`）。

## 第三轮：`has_child` 那一格（ADR-0053）—— 一个派生值被记成了开关

**起点**：`0052` 自己留下的唯一待核项（"`has_child` 是冗余列、只被删除守卫读，本轮没有核"）。
核完发现**两处都写错了**。

### 订正的内容

- `0052` 说 `has_child` 的读者是"删除守卫"。事实：两处 `delete` 的守卫都是
  **真查一次** `parent_id` 的计数（`TenantService:114` / `OrganizationService:335`）。
- `git log -S "getHasChild"` 在 `TenantService` 上**只命中建库那一笔**（`b76fed7`），
  而同一笔也正是引入 `eq(parent_id, id)` 的那一笔 ⇒ **这个列从第一天起就没进过任何守卫**。
- **改完之后全仓 `getHasChild()` 的读取点只剩三处**：两个 `toVO` + 组织侧 `updateColumns` 的原样回传。
- 这一格是怎么错的：列注释 + 紧邻的 delete 方法体 ⇒ "守卫读它"是**从邻接关系推出来的**。
  与 `0052` §三（"不能靠读文本回答"）是**同一个错误的第二次发生**，只是这次在它自己身上。
- **关键推论**：这一格写错了**不会有任何测试变红** —— 守卫读不读它，两种实现的可观察行为完全相同。
  所以它只能靠核代码 + ADR 记下来，**没有断言可以表达它**。

### 顺带撞出的真缺陷（已修）

- 租户侧 `markParentHasChild` 只做 0→1、**反向不重算**；理由（"租户树没有移动"）写在
  `OrganizationService`「三点差异」里 —— 但**删除**在租户侧存在，而删除正是唯一能把它从 1 变 0 的动作
  ⇒ 建个子租户再删掉，父级**永远返回 `hasChild: 1`**，对一个不存在的子节点说"是"。
- 修法：`markParentHasChild` → `refreshHasChild`（数一次 `parent_id`、无条件 `set`，与组织侧同形）；
  顺带删掉 `delete` 里那次多余的 `selectById(parent)`（旧签名要传完整实体）。「三点差异」→ 两点。
- 扰动验收：摘掉 `delete` 里那行 ⇒ 红，消息 `删掉最后一个子租户之后，父级 hasChild 应为 0 ==> expected: <0> but was: <1>`。
  如实记：**第一条用例（40913 守卫）在扰动下照常通过** —— 它钉的是守卫，守卫从来不看这列。

### 顺带数出来的第三条（未处置，进了未覆盖）

- `HIERARCHY_CYCLE` 在主代码里 **13 处用法**（8 处"成环/自挂" + 5 处"删除守卫"），5 个域形状相同：
  组织 / 资源 / 用户组 **有断言**，**角色侧与租户侧两个域的删除守卫都没有**
  （`RoleApiTest` 里 `40913` 零命中）。本轮只补了租户那条（因为要订正的错误说法指的正是它），
  **角色那条记成未覆盖** —— 角色树压根没有 `has_child` 这一列，补它属于扩大射程。

### 本轮的规矩（写进 `server/README.md` 硬规则表）

- **任何"某列被谁读"的说法，必须用 `getXxx` 的调用点核**（`grep -rn "getXxx()"`），
  不能用列名、注释或**邻接关系**核。
- `has_child` 与 `org_level` / `code_path` / `full_name` 同级：**派生列 —— 不入参、不参与判定、由 `parent_id` 真值算出**。

## 第九轮 · ADR-0059：`404` 家族的「点名」住在码里

## 第十一轮 · ADR-0061（名称不唯一）

**起点**：`0060` 未覆盖 2 —— 三个 `*_NAME_EXISTS` 码（`40907`/`40909`/`40911`）该不该实现。

**侦察的转折**：本来准备"实现名称唯一"，读码后**整个人被推翻两次**。
- 第一次推翻：`server/README.md:314` 与 `OrganizationService.create` 的 javadoc 里，
  **`40909` 早有一条成文的反向决策**（"不同上级下同名是合理的"）—— 它不是"忘了做"。
- 第二次推翻：我先用"角色/用户组没有 `fullName` 这类消歧列"去论证它们**该**唯一，
  结果核到 `Users/index.tsx:810` **同时渲染了 `roleCode` 与 `roleName`** ——
  名字旁边本来就有唯一标识。**我的推论是错的**，于是换了判据。

**真正立住的依据（`0056` 第五节，早就写好的）**：
> **没有唯一索引的列不许顺手一起挡** —— 索引不挡这些列，**库里本来就不认为它们唯一**。
⇒ "实现名称唯一"**必须连带加三方言唯一索引**（再定软删语义：索引不含 `deleted`，
软删行永久占着那个名字，而名称侧没有"复活原记录"这条路）。**没有"只在服务层挡"这个中立项。**

**结论**：三个码一律 `intentional`。因为**四个域（租户/组织/角色/用户组）全带 `parent_id`**，
层级的语义就是"同一名字可在不同上级下复用"；组织的成文理由对角色与用户组**同构成立**。
⇒ **身份是编码，不是名字；消歧靠"名字旁边有没有唯一标识"，不靠禁止同名**（与 `0059` 同源）。
顺手排掉一个歧义：`USERNAME_EXISTS` **不算**（`username` 是有索引的**标识列**，与 `*_code` 同类）。

**唯一真正缺的东西**：同一屏上，用户页「角色来源」里角色列是 `roleCode`+`roleName` 并排、
组织归属列渲染 `fullName` 全路径，而**来源用户组列只有一个 `groupName`**（`UserRoleVO` 漏了
`groupCode`）。⇒ **修的是补编码，不是禁止同名。**

**顺带查出一处既有缺口**：`TENANT_NAME_EXISTS` 是四域里唯一被实现的名称判重，而
`tenant_name` 上**没有唯一索引** ⇒ 它是 `0056` 那句点名的对象；落到今天的后果是
**并发下没有第二道防线**（`40900` 那条兜底对它不可达 —— 库里不认为它唯一）。
`server/README.md` 那句"第二道防线"**对编码成立、对名称不成立**，已订正。本轮**不改行为**。

## 第十二轮 · ADR-0062（判重看语义不看索引）

**起点**：`0061` 未覆盖 1 —— `TENANT_NAME_EXISTS(40905)` 是四个层级域里唯一"库里不挡、
服务层挡"的那一个，要不要与另外三个统一。

**侦察的三次转向**（两次把我自己的判断推翻）：
1. 本以为要"实现名称唯一"，读码后发现 `40905` 是**全仓唯一一处**"无索引 + 判重 + 零理由"
   —— 没有别处按 `tenantName` 查租户、前端完全不认这个码。
2. **`0061:110` 那句"有用例钉着"是过度表述**（grep 全仓 `40905`：枚举定义 + 两处抛出点
   + 两条测试注释，**一条断言都没有**）。而那句正是让删判重看起来"破坏性"的理由 ——
   它是本轮真正要推翻的前提。
3. 顺手挖出 `idx_bw_auth_user_tenant_email` / `_phone` 是**普通索引**（不是 UNIQUE）
   ⇒ `40902`/`40903` 与 `40905` **同形态**。但再核一层发现它们**不是同一类**：
   `0047` 正文写着「邮箱 / 手机当前只参与唯一性校验与展示」，`UserService` 的注释
   写明它们的软删语义是**有意选的**（"那会让一次误删把邮箱永久锁住，而没有任何唯一约束
   要求这么做"）⇒ 它们有语义依据，`tenant_name` 没有。

**立住的判据（本轮把 `0061` 那条推进一步）**：
> **判一个列该不该挡重名，看它在语义上是否指认唯一对象 —— 不看它有没有唯一索引。**
`0061` 用的是"有没有索引"，但那条按字面会把 `email`/`phone` 也判成该松，而松掉显然不对。
三分：**标识**（`*_code`/`username`，指认系统内对象 ⇒ 唯一索引 + 判重 + 兜底）·
**寻址**（`email`/`phone`，指认现实世界主体 ⇒ 服务层判重、不加索引，**有意**接受并发漏网）·
**标签**（四个 `*_name` ⇒ **不挡**）。

**方向①（加唯一索引）本轮实测关闭**：`UNIQUE(tenant_name)` 不含 `deleted` ⇒ 软删行永久占名
⇒ 与 `0056` 第五节那条 + `UniqueCodeReuseApiTest` 的注释（"如果哪天有人把名称判重也改成
看得见软删行，这条会红 —— 那正是它该做的事"）直接冲突；`UNIQUE(name, deleted)` 只能有一行
软删同名；软删时置空名字是篡改数据。⇒ **技术上无解，不是偏好问题。**

**决定**：删掉 `TenantService#create` / `#update` 两处判重（`create` 的 javadoc 补一段
"这里刻意没有名称判重"，免得后来者顺手加回来）；`40905` 保留在枚举里，与三个 `*_NAME_EXISTS`
**并列**进守卫的 `intentional` 栏 —— **这才是"统一"该有的形状**：不是都挡、也不是都删枚举，
而是同一件事的四个码在同一栏里共用一个理由。零 DDL 改动、零接口形状改动。

**新加一条用例**（`UniqueCodeReuseApiTest#shouldAllowTwoTenantsWithTheSameName`）：
两个同名（逐字相同）租户都建成功、各自取回来名字相同编码不同。放在这个类里是因为
它的类注释本来就在讲 `tenant_name`；类注释的"两条反例"也跟着改成"三条"。
