# 2026-10-10：数据源双轨（H2 / 本机 MySQL）+ Flyway 迁移机制

## 一、起因

舰长问"后端用的哪个数据库？是我本地的吗？你能启动并连接、建表建库吗"。
答：当时用的是 **H2 内存库**（`jdbc:h2:mem:bluewhale`），跑在 JVM 进程内存里，
跟本机装没装数据库无关；进程一停数据全没。本机装着 MySQL 8.0.26（服务 Stopped），
里面已有另一个项目的 11 个库（`yc-sts-db-*` / `sts-db-*` / `parallel_world_server`）。

舰长拍板：**双 Profile 共存**、库名 `bluewhale`、MySQL root 凭据由舰长提供（**不记录在仓库与记忆中**）。

## 二、做了什么

1. **启动本机 MySQL**（`net start MySQL`，成功；3306 监听，既有 11 个库一个未动），
   建库 `bluewhale`（utf8mb4 / utf8mb4_0900_ai_ci）
2. **application.yml 拆三份**：公共 + `application-h2.yml`（默认）+ `application-mysql.yml`；
   凭据走 `BW_DB_PASSWORD` 环境变量（依据 ADR-0003，密码不进 git 历史）
3. **建表机制 spring.sql.init → Flyway 12.4.0**，迁移脚本按厂商分目录由领域模块自带：
   `sts-server-log/src/main/resources/db/migration/{h2,mysql}/V1__create_bw_client_log.sql`
4. 依赖：`mysql-connector-j`(9.7.0) + `spring-boot-starter-flyway` + **`flyway-mysql`**（必加）
5. 新增 ADR-0009；同步 server/README（新增第六节「数据源与数据库迁移」）、根 README、
   docs/README、AGENTS（环境坑表 +3 条 + 三条写库前必读）、CONTRIBUTING、demo README

## 三、两个真坑（这次踩得很值，都写进文档 + 测试了）

### 坑 1：MySQL 保留字 `release` —— 而且修一次不够

`release`（发布版本号）是自然的领域命名，但 **`RELEASE` 是 MySQL 8 保留字**，
而 **H2 不认它**。同一个列名：H2 全绿、MySQL `ERROR 1064`。

> 这是最难查的一类差异：只在其中一个库上暴露。

修复踩了第二层：把列名改 `app_release`、Java 属性仍叫 `release` 并加 `@TableField("app_release")`
→ 编译过、H2 过、MySQL 依然 1064。原因是 **MyBatis-Plus 发现"列名 ≠ 属性名"会自动补别名**
`app_release AS release`，别名把保留字原样带回。
**最终做法**：属性名与列名同构 —— `appRelease` ← 由 `map-underscore-to-camel-case` 推导出
`app_release`（与 `traceId → trace_id` 一致），**刻意不加 `@TableField`**。对外字段仍是 `release`。

反编译 MP 的 `TableFieldInfo` 构造函数确认了别名生成条件（`sqlSelect = column`，
当列名与属性名不一致时追加 `" AS " + property`）。

### 坑 2：Flyway 10+ 的数据库支持是模块化的

`flyway-core` 只内置 H2 / SQLite（jar 里能列出 `internal/database/h2/`，没有 mysql 包）。
缺 `flyway-mysql` 的症状：H2 profile 一切正常，切 mysql 启动报 `Unsupported Database: MySQL 8.0`。
与 MyBatis-Plus 拆 `mybatis-plus-jsqlparser` 同一类陷阱。

### 附带发现

`insertBatch` 里的 `#{it.release}` 是 **OGNL 字符串，编译器管不到** —— 属性改名后
只在运行时报错，靠接口测试（`ClientLogApiTest`）才抓到。这是本次唯一被测试当场拦下的问题。

## 四、新增的回归断言（重要）

`ClientLogEntityMappingTest`（日志模块）直接用 `TableInfoHelper` 构造 `TableInfo`，
断言生成的 SQL：① 含 `app_release` ② 不含 `AS release`。
**为什么必须这样测**：默认 profile 是 H2，它不认这些保留字，跑用例永远是绿的 ——
这类问题只能对"生成物"做断言。

## 五、验证

- 后端 10/10 模块、**24 个测试全绿**（日志 12 + 应用层 12）
- mysql profile：Flyway 识别 `MySQL 8.0` → 执行 V1 → 5 个接口（上报/分页/详情/链路/聚合）全通，
  中文与 emoji 落库无损
- **重启验证**：重启后 Flyway 报 `Schema is up to date. No migration necessary.`，
  数据仍在（这是 H2 做不到的）
- h2 profile：仍正常（`profile=h2`，H2 2.4），同一 app 在 H2 下 total=0 —— 两库完全独立
- 走 vite 代理（前端实际路径）读写全通
- 契约**完全没变**，前端零影响

## 六、环境坑

- **Chrome headless 截图/CDP 本次失效**：最小用例（data URL）也静默失败、退出码 0 但不产出文件。

# 追加：国产库达梦 DM8 支持（同日 · ADR-0010）

## 一、需求与选型

舰长：「现阶段最起码需要支持一种国产库，支持一种主流库。」主流已有（MySQL），本轮补国产库。

按「方言距离 × 本机可验证性」筛候选，选 **达梦 DM8**：信创代表 + 方言最远（最能压测架构）+ 有 Windows 版。
舰长同时拍板：**先不验证，先交付改动，明确标注未验证**。

本机环境限制（本轮查清）：**没有 Docker**；`wsl.exe` 与 `sc.exe` 在**程序黑名单**里不能调用；
本机无任何国产库。→ openGauss / OceanBase / TiDB（仅 Linux 版）在本机根本起不了实例。

## 二、最大的意外收获：MyBatis-Plus 原生内置达梦方言

`mybatis-plus-annotation` 3.5.17 的 `DbType` 枚举里**有 `DM`**（值 `"dm"`），
`mybatis-plus-extension` 的 `JdbcUtils` 用正则 `:dm\d*:` 匹配 URL → `DbType.DM`。
**结论：`DbAutoConfiguration` 里那个刻意不指定 DbType 的分页拦截器，只要 URL 写对就自动用达梦方言
—— 分页 / 防全表更新 / 乐观锁零代码改动。**

枚举里还有一长串国产库：`KINGBASE_ES`、`OPENGAUSS`、`GAUSS`、`GAUSS_DB`、`OCEAN_BASE`、
`XU_GU`、`SINODB`、`OSCAR`、`UXDB`、`VASTBASE`、`GOLDENDB`、`YASDB`、`GBASE` 系列。
**将来再换库，先查这张枚举表。**

## 三、Flyway 对达梦零支持 —— 本轮核心取舍

中央仓 42 个 `flyway-*` 构件里没有任何达梦坐标（国产库只有 `flyway-database-oceanbase` /
`flyway-database-tidb`，而它们本质是 MySQL 协议）。两条路都否决：

1. 引社区 `db-migration` 扩展 → 为一个库引入个人维护的外部依赖
2. 自研 `DatabaseType` → 接口在 `org.flywaydb.core.internal.*`，`BaseDatabaseType` 尚有 8 个抽象方法，
   `createDatabase`/`createParser` 还需配套 Database/Schema/Parser 子类，约 300–400 行，
   **全部绑定 Flyway 内部 API，升级即可能破**；在没有实例可验证时是纯负债

**决定：达梦 profile `flyway.enabled=false`，DDL 走交付脚本**（信创常规做法：DDL 交付、DBA 执行）。
脚本仍放 `db/migration/dameng/`、编号仍 `V1__` —— 不是为了 Flyway，是为了三套脚本能按同一时间线对照；
将来若恢复自动迁移，文件无需挪位改名。

## 四、达梦方言要点

| 项目       | MySQL 8                          | 达梦 DM8                                                |
| ---------- | -------------------------------- | ------------------------------------------------------- |
| 自增主键   | `AUTO_INCREMENT`                 | `BIGINT IDENTITY(1,1) NOT NULL`                         |
| 变长字符串 | `VARCHAR(64)` 按字符             | `VARCHAR(64 CHAR)` —— **默认按字节**，中文必须显式 CHAR |
| 列注释     | inline `COMMENT '...'`           | `COMMENT ON COLUMN t.c IS '...'` 独立语句               |
| 表选项     | ENGINE / CHARSET / COLLATE       | 不支持，写了报错                                        |
| 标识符     | 受 `lower_case_table_names` 影响 | 不加引号一律**转大写**（同 Oracle）                     |

`CHAR` 那条是真问题：Java 侧 truncate 按**字符**、达梦 VARCHAR(n) 按**字节**，
UTF-8 汉字 3 字节 → 255 字符的中文是 765 字节，塞不下且报错只说"数据超长"。

## 五、保留字核对（本表零冲突，结论带版本限定）

达梦查法：`SELECT KEYWORD FROM V$RESERVED_WORDS WHERE RESERVED='Y'`。
逐项核对：表名 / 4 个索引名 / 约束名 / 14 个列名 **全部无冲突**。

- `LEVEL` 在达梦关键字表里但**非保留**（可作列名）
- **`RELEASE` 达梦完全不认** —— 与 ADR-0009 恰好相反
  → **保留字风险按库各算，两库结论不可互推。**（达梦升级会加关键字：8.1.3→8.1.4 增 78 个）

# （续）行为事件管道：前端埋点内核 + 服务端落库 + 端到端演示

## 一、起因

舰长：「接下来在前端封装统一的事件机制，发布和订阅。在用户有操作的时候，都发布事件，
异步记录到服务端，之后计划接入大数据，测试阶段可使用普通数据库。用于分析用户行为。
**你觉得这个可行不**」

先论证再动手。四个决策经 AskUserQuestion 全部按推荐项拍板：
① 语义化 `track()` + 内部总线（不做通用全局事件总线）② 上报器下沉到公共包复用
③ 维度列 + props JSON（不每类事件一张宽表）④ 本轮做前端内核 + 服务端落库 + demo 页

## 二、核心判断：这是**第三条管道**，不是日志的一个新维度

|                                                                            | 技术日志     | 审计日志           | **行为事件**               |
| -------------------------------------------------------------------------- | ------------ | ------------------ | -------------------------- |
| 回答                                                                       | 系统在干什么 | 谁干了什么（合规） | **用户做了什么**           |
| 采样                                                                       | 可以         | 不可以             | **不可以**（一采漏斗就断） |
| 契约稳定度                                                                 | 可自由加字段 | 中                 | **改一个字段名就永久断代** |
| 消费方                                                                     | 运维/开发    | 审计/风控          | **分析/数仓**              |
| → 内容不同 ⇒ 独立模块、独立表；**通道相同 ⇒ `json` + `report` 必须复用**。 |

## 三、动手前先摆正一处位置错误（本轮最有价值的一步）

`平台-log-console/src/reporter.ts` 里那套批量上报器，住在 demo 应用里。
它的四条约束（批量 / 有界 / 退避 / 不抛异常）**是通道属性，与上报内容无关** ——
事件管道需求逐条相同。若不先下沉，两份实现立刻开始漂移（一份修了并发缺陷，另一份没修）。
→ 先抽 `common-tools/report` 的 `BatchChannel`，再把 log-console 改成薄封装
（原 8 个 `reporter.test.ts` 用例**原样通过**，证明下沉忠实）。
`platform-log-console/src/console.ts` 的本地 `sanitize` 同样下沉为 `common-tools/json`。

## 五、刻意的设计取舍（都写进了 ADR-0011）

- **事件名是永久契约**：正则 `^[a-z][a-z0-9_]*(\.[a-z][a-z0-9_]*)+$`，前后端**同一条**；
  非法名丢弃且**只报一次**（上限 50，否则每次交互都刷屏）
- **双时间戳**：`clientTime`（不可信，仅展示）/ `serverTime`（排序过滤唯一依据）
- **`event_id` 刻意不建唯一索引**：一条重复不能让整批 INSERT 失败，唯一性在消费侧
- **`propsVersion` 按次传**（`TrackOptions`）而非全局配置：版本属于"某个事件的结构"
- **卸载兜底用 `fetch(keepalive)` 而非 `sendBeacon`**：后者发 JSON 触发预检 → 静默失败；
  keepalive 上限 64KB，按体积裁剪且**优先保住最近的批次**
- **身份缝合**：`deviceId`（匿名期）+ `userId`（登录期）同时挂在事件上
- **`EventEnvelope` 刻意不含 `traceId`**：契约没这一列，加了就是"发出去也没人接"的假字段
- **登录/登出顺序相反且有意为之**：登录先写上下文再发事件；登出先发事件再 `clearUser()`

## 六、两个真 bug（均由本轮扩大校验范围后暴露）

1. **Flyway 版本号冲突**（子代理主动上报）：所有模块共用同一个 `spring.flyway.locations`，
   版本号**全仓唯一**，事件表从 V1 起编号会在**启动阶段**直接失败
   `Found more than one migration with version 1` → 改 `V2__create_bw_client_event.sql`，
   并在 ADR-0009「补充」章节里把三条候选方案逐条评估后选定"取下一个空闲号"
2. **LESS 令牌跨应用引用**：`platform-event-console/src/App.less` 的 `.pill--err` 引了
   日志控制台才有的 `@level-error`。**dev server 与单元测试都不会报错**（前者按需编译，
   没人访问那条样式分支就不编译；后者不碰样式），只有 `vite build` 失败
   → 补 `@event-error` 令牌；并把这条写进 AGENTS 环境坑表
   **教训：新增/复制版式的应用，`vite build` 必须实际跑过。**

# 2026-10-10（续）：前端微前端接线 —— 两个控制台被基座加载

## 一、起因：指令的前提是错的

舰长说「之前前端使用了qiankun，主应用和子应用搭建了，现在可以调试了」。
实际勘察：`platform-portal` 只把 `qiankun` 写在依赖里，全仓 `registerMicroApps` /
`start` / `initGlobalState` **零命中**；两个控制台是独立应用（入口直接
`createRoot().render()`、无 `__POWERED_BY_QIANKUN__` 判断、vite 未配 `base`）；
`web/README.md` 的待办项里也早写着"尚未接入"。
**没有顺着错误前提动手**，先出图纠正前提，再用提问拿到两个决策（均选推荐项）：
先改造两个控制台（不新建 user/admin）· 接入方式用 `vite-plugin-qiankun`（不做 UMD）。

## 二、先读内核再写代码（这一步省掉了返工）

通读 `qiankun/es/addons/engineFlag.js`、`es/loader.js`、`import-html-entry/lib/index.js`、
`vite-plugin-qiankun/dist/{index,helper}.js` 后才动手：

- 插件靠两个全局桥接交换生命周期：`__POWERED_BY_QIANKUN__`（engineFlag 挂）与
  `window.proxy`（`import-html-entry` 执行脚本前设）
- `import-html-entry` 用 **`eval` 执行脚本文本 ⇒ module script 跑不了** —— 这才是
  必须用插件的根本原因，不是"图方便"
- 原本担心关沙箱会破坏插件，读源码后推翻：沙箱靠 `with(window)` 劫持全局，
  **包不住 ESM 模块作用域**，对 Vite 子应用本就无效

## 三、做了什么（改动清单）

- **基座接线** `platform-portal/src/micro/`（5 文件）：`types`（全用 `type` 不用
  `interface` —— qiankun 泛型约束 `T extends Record<string, any>`，interface 无隐式索引签名）
  · `apps`（注册表 + `resolveEntry`）· `state`（**自留副本**补 `initGlobalState` 没有
  `getGlobalState` 的缺口）· `loader`（`loadMicroApp` + `sandbox:false` +

## 四、真问题与修复

1. **`SyntaxError: Cannot use import statement outside a module`**（真实浏览器才暴露）：

   `import-html-entry` 用 `eval` 执行 ⇒ 必炸，且 Fast Refresh 全局钩子永远装不上。
   → 写 `qiankunDevPreamble()` 把静态 import 改写成 `await import()` 并去掉 `type="module"`
2. **生产构建 TS7016**：`common-config/vite` 隐式 any → 补 `.d.ts`，exports 改 `{types, import}`
3. **`platform-portal` 下没链接 common-tools**：分两次编辑 `package.json` 后没重跑
   `pnpm install` → 重跑即好
4. **A/B 对照排除自身改动**：怀疑 preamble 修复导致热更新失效 → 注释掉重启验证，
   **关掉后同样不生效** ⇒ 与本轮改动无关，恢复启用并如实写进 ADR

舰长指令：搭一个子应用，qiankun 状态用传入容器、独立启动用自建容器，与任何应用无关，加 threejs 依赖。

## 十四、古建筑场景第一阶段：主人公操控与小地图（ADR-0015）

舰长指令：搭古建筑第一阶段 —— 地面广场、左上角小地图（人物视角 + 指北）、
可操控主人公（上下左右 + 缩放视角）、右键设行动终点。

**四个关键决策（详见 ADR-0015）**：

1. **交互是场景的能力，不是舞台的能力**：`SceneBuild.createControls?(context)` 可选契约，
   舞台管控制器生命周期（装载造/每帧驱动/切场景销毁），场景不碰帧循环
2. **相机跟随 = "整体平移"**：控制器只上报 `focus()`，舞台把相机与轨道目标挪**同样的位移**
   —— 只改 target 不动相机会变成原地转头。相机仍由舞台持有（ADR-0013 未被破坏）
3. **左键/滚轮仍归 OrbitControls**，控制器只借走键盘与右键；有控制器的场景
   `orbit.enablePan=false`（右键让给设终点）。已读源码确认：OrbitControls 的 contextmenu
   只 preventDefault、键盘监听需显式 `listenToKeyEvents()`，不冲突
4. **小地图自绘 canvas 不走 React 状态**（60fps setState 是最贵手段做最便宜的事）；
   数据经 `stage.interaction()` 逐帧读，`SceneView` 用 `onReady` 把舞台交给 App

**架构落点**：

- `scene/player/motor.ts` —— 移动**纯内核**（相机相对位移/目标点行走/最短转向/
  边界夹取/沿穿透最浅的一边推出障碍），不碰 three 不碰 DOM，20+ 条单测
- `scene/player/avatar.ts`（斗笠人造型，正前方 = 本地 +Z）· `scene/player/controls.ts`（输入装配）
- `scene/minimap.ts` —— 投影/方向/扇形/箭头全是**纯函数**；世界 +X→右、+Z→下、-Z→上（北），
  方向向量 `(sin a, cos a)` 在两个坐标系同形 ⇒ **世界→地图零角度补偿**
- 角度约定全应用统一：0 = 朝 +Z、`(sin a, cos a)`；改错符号的症状是"按上往后走"
- 小地图地物与碰撞矩形**同源**（场景声明一份）；正北朝上，指北针是静态 N；
  人物朝向 = 箭头、相机视野 = 扇形（半径随滚轮缩放）—— 两个独立信息不混用
- 右键射线打**地面平面 y=0** 不打网格（网格随开关存在）；画布尺寸 0 必须返回 null（防 NaN）
- 古建筑：广场 halfExtent 40 + 压边石 + 220 地面 + 雾推到 26/85（不然人走远被雾洗白）+
  太阳阴影范围 24→30（否则走出阴影范围影子无声消失）；障碍 = 台基 + 台阶两块矩形

**验证（全绿）**：environment **147** 用例（93→147）；typecheck/eslint/stylelint/build 全过；
