## 第十三轮 · ADR-0063（判重与唯一索引对账守卫）

**起点**：`0062` 未覆盖 2 —— "挡不挡重名"的分类没有机械守卫，`0062` 那轮的手工对账
只做了一次，谁把名称判重"顺手"加回来没有东西拦。

### 侦察 → 设计

- 判重抛出点删完名称类后剩 **10 处 / 8 个码**（6 个编码 + email/phone 各两处）；
  模式规整：Mapper 查询 + `*_EXISTS` 抛出，码名与列一一对应 ⇒ 锚定**码的引用**（语法级），
  不解析"先查后写"的写法。
- 三方言 DDL 的 `CREATE UNIQUE INDEX` **语法完全一致**（各 7 条），可同正则抽三份对账；
  `email`/`phone` 上是普通索引 `idx_*`。
- 四格表：只有"服务层判重 + 无索引 + 不在白名单"要红；"有 UNIQUE 却不判重"（`jti`）
  合法（`40900` 兜底），刻意不查。

### 落地

- **新守卫 `scripts/verify-unique-columns.mjs`**（零前置，进 CI `guards` 第五步），四件事：
  ① 每个被引用的 `*_EXISTS` 码在 `JUDGED` 登记"判的哪一列"（8 条）—— 登记即回答 `0062` 的问题；
  ② 登记的码仍要有落点（腐烂检查，`0062` 式删判重时会提醒"删登记、挪白名单"）；
  ③ 三方言唯一索引集合一致（**白捡的一条**：`0038` 同构此前没人守）；
  ④ 判重列要么有 UNIQUE、要么在 `NO_INDEX_ALLOWED`（`email`/`phone` 两条，理由引 `0062`/`0047`）。
- **首跑即全绿**：180 源文件 · 三方言各 11 列 · 有索引 6 列 + 白名单 2 列 —— 与手工对账一致。
- **扰动验位三方向全红**（exit=1）：① `JUDGED` 加假码 ⇒ "登记的码都还有落点"红；
  ② 白名单豁免键改名 ⇒ "判重列"红；③ 只给 h2 加 email UNIQUE ⇒ "三方言一致" + "白名单腐烂"

  `ci.yml`（guards 加第五步，注释"四条"→"五条"）。

## 第十四轮 · ADR-0064（消歧手段的普查 + 被否掉的守卫）

**起点**：`0061`-3 / `0063`-1 —— 「名字旁边必须有唯一标识」是纸面规则。

### 侦察 → 穷举（#343）

### 决策：**刻意不做守卫**（#345，本轮的核心）

认真评估"能不能像 `0060` / `0063` 那样写零前置守卫"—— **不能**。实测三种口径：

| 口径 | 结果 |
| --- | --- |
| `*Name` 同行还有别的可见内容 ⇒ 必须有标识 | 28 命中 **≥4 处误报**（表单 label / 自由文本 `positionName` / 演练模板串 / `fullName` 全路径） |

**判据落成一句**：`0060`/`0063` 成立是因为锚定**无歧义 token 形状**；
"名字旁有标识"是 **JSX 树 + 展示语义**属性，给不了"不误报"这个前提 ——
**会误报的守卫比没有更糟（它训练人去忽略它）**。

## 第十五轮 · ADR-0065 文本相等的语义

**起点**：第十四轮末尾推荐的备选第 1 条 —— `0062`「未覆盖」1：`email` / `phone`
要不要从"业务规则级唯一"升成"数据约束级唯一"。它是"标识 / 寻址 / 标签"三分里
唯一还没被机械守卫动过形态的那一类，且 `0063` 守卫已把两列钉死在白名单
（`NO_INDEX_ALLOWED`）⇒ 一旦改，守卫立刻红、落点已铺好。

**侦察转向**：核问题本身时发现它**缺一个前提** —— "唯一"是相对某个**相等关系**
说的，而"两个文本什么时候算相等"在本仓**从来没被回答过**（`grep` 不到任何
`COLLATE` 决策），于是由三个方言各自的默认排序规则代答。于是本轮先去量
"三个默认值到底一样不一样"。

**实测（两台引擎、同一段 SQL，探针按 `V3` 里 `bw_auth_user` 的形状建）**：

| 探针（已存 `a@b.com`/`admin`） | H2 2.4.240 | MySQL `_ai_ci` | `_as_cs` | `_bin` |
| --- | --- | --- | --- | --- |
| `= 'A@B.COM'` | 0 | 1 | 0 | 0 |
| `= 'a@b.com '`（尾空格） | 0 | 0 | 0 | **1** |
| `= 'á@b.com'`（重音） | 0 | 1 | 0 | 0 |
| `WHERE username='Admin'` | 0 | 1 | 0 | 0 |
| 唯一索引插 `Admin`（有 `admin`） | 允许 | 拒绝 | 允许 | 允许 |

  仍 FALSE）。⇒ `_as_cs` 是四格全对的唯一候选。
- **顺带查出**：`40902`/`40903`（邮箱/手机判重）在 `server/sts-app` 下**零用例**。

## 第十六轮 · ADR-0066 搜索的匹配语义

**起点**：第十五轮末尾推荐的备选第 1 条 —— `0065`「未覆盖」3：
"前端侧的相等语义没查（`platform-admin` 会不会按邮箱 / 手机号做本地过滤）"。

**侦察结论是「否证」**：前端**一处本地过滤都没有**。
- 全仓 `toLowerCase` / `toUpperCase` / `localeCompare` 只 **11 处**（含用例）；
  非测试的仅 2 处：`common-tools/http/client.ts:57`（HTTP **头名**大小写无关查找）、
  `common-tools/logger/logger.ts:264`（日志标题**显示**大写）。
- 对 `email` / `phone` 的**比较 = 0 处**（只被回显与提交）。
- 前端 `.filter` / `.includes` / `.startsWith` / `.indexOf` 的落点全是权限码 /
  className / 树节点 id / 按键码（`Arrow`）/ URL 前缀 —— 没有一处筛用户记录。
- 六个页面（Users / UserGroups / Tenants / Roles / Resources / Organizations）对
  `keyword` 只做 **`.trim()`**，然后**原样发给后端**。
⇒ `0065` 担心的"JS `===` 巧合"**不成立**，因为 JS 的比较根本没参与。

**但顺藤摸出一个 `0065` 没料到的口子**：搜索走后端 `LIKE '%kw%'`，
而 **`LIKE` 的敏感性同样跟着列排序规则走** ⇒ `V8` 顺手把它也改了。

**实测（两台引擎、同一段 SQL；存 `admin` / `Admin@Example.com`）**：

| 探针 | H2 | `_ai_ci`（改前） | `_as_cs`（改后） | `_bin` |
| --- | --- | --- | --- | --- |
| `username LIKE '%ADMIN%'` | 0 | **1** | 0 | 0 |
| `username LIKE '%admin%'` | 1 | 1 | 1 | 1 |
| `email LIKE '%ADMIN@%'` | 0 | **1** | 0 | 0 |
| `email LIKE '%Admin@%'` | 1 | 1 | 1 | 1 |

⇒ **改前两个 profile 在搜索上本来就是分歧的**（且比等值面更早被碰到 —— 搜索框天天在用）；
`V8` 把两边**对齐到了"敏感"那一侧**（顺带结果，此前没人写过、也没用例）。
**"搜索该不该区分大小写"本仓从来没决定过。**

**舰长裁决**：**接受 —— 搜索沿用列排序规则、跟着等值一起区分大小写**。

**落地（零生产代码改动）**：

## 第十七轮 · ADR-0067 搜索关键词的转义

**起点**：第十六轮末尾推荐的备选第 1 条 —— `0066`「未覆盖」1：
**`LIKE` 的通配符没有被转义**（"输 `%` = 匹配一切"，机制确定但当时没改）。

**侦察射程**：`keyword` 出自 7 处搜索（用户 3 列 / 用户组 2 / 租户 2 / 角色 2 /
资源 2 / 组织 3 / 客户端日志 1，共 **15 个列条件**）。另两处
`likeRight(codePath, prefix)` **不在射程** —— `code_path` 是 `pathOf()` 拼的
**"各级主键 + 斜杠"**（形如 `/1/5/`），只有数字与 `/`（注：`org_code` 本身允许
下划线，但 `code_path` 里不含编码）。

**机制（字节码级）**：`javap` 读 MP 3.5.17 的
`SqlUtils#concatLike` —— 只有三条 `"%" + 值` / `值 + "%"` / `"%" + 值 + "%"`，
**没有任何转义**；`SqlLike` 枚举也只有 `LEFT`/`RIGHT`/`DEFAULT`。

**⚠️ 先纠正一个会骗人的探针**（本轮最大的方法论收获）：
第一版用 **SQL 字面量**量转义（`c LIKE 'a\%b'`），H2 上"转义前的 `abc`"也命中，
看着像"转义没生效"。真因是 **H2 的 `MODE=MySQL` 会把字面量里的 `\` 当转义符吃掉**
（`'a\%b'` 到 `LIKE` 时已是 `'a%b'`）—— 量到的是**解析器**，不是 `LIKE`。
⇒ 改用 **`PreparedStatement` 绑定参数**（MyBatis 的传参形态）才是 `LIKE` 的行为。

**实测（绑定参数，存 `abc`/`a%b`/`a_b`/`aXb`）**：

| 探针 | H2 2.4.240 | MySQL `_as_cs` | MySQL + `NO_BACKSLASH_ESCAPES` |
| --- | --- | --- | --- |
| 现状：输 `%` | **4（全表）** | **4（全表）** | **4（全表）** |
| 现状：输 `a_b` | **3** | **3** | **3** |
| 现状：输 `a_c` | 1（命中的是 **`abc`**） | 1（`abc`） | 1（`abc`） |
| 甲：实参转义 `\%`（默认转义符） | 1 ✓ | 1 ✓ | **0 —— 静默失效** |
| 乙：`LIKE ? ESCAPE '!'` + 实参转义 | 1 ✓ | 1 ✓ | **1 ✓** |

⇒ **"怎么转义"本身还有一次分叉，而甲方案会静默骗人**（MySQL 开
`NO_BACKSLASH_ESCAPES` 后用户输自己完整的登录名反而搜不到、不报错）。
这是 `0065` 教训的直接复用：别让默认值代答。

**舰长裁决**：**转义 + 显式 `ESCAPE '!'`**。

**落地**：
- `sts-common-db` 新增 `KeywordLike`（`pattern()` 出转义后的实参、
  `condition("列")` 出 `列 LIKE {0} ESCAPE '!'`；列名有形状断言，把
  "绝不拼外部输入"变成运行期检查）。**15 个条件全改用它**，`auth` 与 `log`
  两个模块共 7 个 service。各域原有判空口径**一个字没改**（4 处 `normalize`
  含 trim、3 处只判空）—— 那是另一件事，留在未覆盖。

  不许再有裸 `like*`（白名单只登记 `code_path` 那两处）+ 带 `LIKE` 的片段
  同一行必须有 `ESCAPE` + **白名单逐条核对条数**。

## 第十八轮 · ADR-0068 搜索关键词的规范化

**起点**：第十七轮末尾推荐的备选第 1 条 —— `0067`「未覆盖」3：
**关键词的规范化各域不一致**。

**侦察**：7 处搜索分两种口径 —— 组织 / 角色 / 用户组走各自私有的 `normalize`
（`null` 进 `null` 出、全空白也出 `null`、否则 `trim()`），用户 / 租户 / 资源 /
客户端日志直传给 `KeywordLike.pattern()`（只判空）。两种口径对 `null` 与**只含空白**
一致，**唯一的分叉是两端带空白**。`normalize` 是同一份实现、在 **5 个 service 里各一份**
（另两份给 `ResourceService` / `OrganizationMemberService` 的非 keyword 过滤值用）。

**关键发现（证伪一句被用来开脱的旧话）**：前端**不是"全都 trim 了"** ——
五个管理页确实在提交时 `setKeyword(keywordInput.trim())`，但**客户端日志页一次都不 trim**
（逐键上送、连提交中间态都没有），而**组织页根本没有搜索框**（刻意只有树视图，
页面顶部写着"平铺列表会丢掉唯一的有效信息（层级）"；那个按编码 / 名称 / 全称搜索的
分页接口是给 **API 调用方**的）。⇒ `0066` 的"六个搜索框（… / 资源 / 组织）全都把
`keyword` 发给后端，前端只做 `.trim()`"与 `0067` 的"前端六个搜索框（… / 组织）"
**都不准确**（后者的表格里 7 个域是对的，错在"搜索框"这个计数）。
两篇是已定稿 ADR，按"不回改旧文"的约定不在原文改，已在 `0068` 与活文档里订正。

**先写能红的用例**（`SearchKeywordTrimApiTest`，4 例、**跨 profile**、不 `@Transactional`），
**不改代码跑一次 = 2 红 2 绿**：用户域那条**红**（命中 0 条）、**同形的组织域那条绿**
⇒ 同一条关键词在两个域上结果不同，这就是"不一致"的现场证据，不必靠读代码推断。
（另一条红是"只吃两端、不吃中间"，同一个根因；第 3 条"纯空白 = 不过滤"是**回归钉**
—— 下沉时最容易顺手弄坏的一支；第 2 条的绿是**对照组**：把组织域也改成不 trim 它会红。）

**决策**：规范化收进 `KeywordLike.pattern()`、**不放调用方**（后端是权威边界，
API 调用方不走前端那层）；吃掉**两端**、**不吃中间**（`LIKE '%…%'` 下前后空白
不承载任何区分能力，只能造成"在某些页面上搜不到"；`a b` 里的空格是关键词的一部分）；
`null` 与只含空白 = 不过滤（与改前一致）；7 处取值统一成 `pattern(query.getKeyword())`；
**前端日志页在发请求时 trim、不在 `onChange` 里**（逐键上送，输入过程中 trim
会把用户刚敲的空格当场吃掉，值与光标都会跳）。

**落地**：`KeywordLike.pattern()` 加 `trim()` + 类注释加一节"关键词的规范化也在这里"；
三处 service 删掉 `normalize(query.getKeyword())` 那层，并把"先取局部变量"的长注释
挪到它真正描述的 `status` / `category` 之前（它讲的是 `eq(条件, 列, 值)` 的实参无条件求值，
与关键词无关 —— 留着会让人以为 `pattern(...)` 那行也在取局部变量）；7 处注释统一成一句；
前端新增 `cleanFilter()`，`level` / `namespace` / `keyword` 三个值发请求前过一遍。

即"只含空白"退化成"搜三个空格"）。已还原，`grep` 确认无残留。

## 第十九轮 · ADR-0069 过滤值的规范化

**领**：`0068` 未覆盖 3（非关键词的过滤值仍不 trim，射程约 20 处取值）+ 未覆盖 4
（`normalize` 仍有 5 个副本，上收对象应是"所有过滤值的规范化"），合起来做。

**侦察（先把射程弄清楚 —— 结论是"不是两种风格，而是三种形态"，29 处字符串过滤值）**：

- **枚举归一（4 处，已健壮）**：角色 `status` · 资源 `resourceType` · 用户组与角色成员
  `memberType`。走 `Xxx.parse(raw)`，内部是 `type.wire.equalsIgnoreCase(value.trim())`
  —— 自带 trim 且顺带归一大小写，**比 trim 更强，不能替换成 trim**（那是功能退化）。
- **纯 trim（5 处，已健壮）**：组织 `status` / `orgType`、角色与用户组 `category`、
  资源 `parentCode`。走本域私有 `normalize()`（`null` 进 `null` 出、空串转 `null`、
  否则 `trim()`）—— 同一份实现**在 5 个 service 里各一份**。
- **只判空（20 处，本轮改的）**：用户 / 租户的 `status`，日志 / 事件 / 审计三域各 5 列。
  `hasText()` 或 `!= null && !isBlank()` 之后**把原值**交给 `eq`
  ⇒ 两端带空白时一条也匹配不到。

**⚠️ 顺手挖出一处真实缺陷**：日志 / 事件 / 审计的**聚合统计走手写 SQL**，判空写在 SQL 的
Ognl 里（`<if test="app != null and app != ''">`），而**同一个请求的列表**走 Java 的
`hasText()`（`isBlank`）。两者对 `"   "` 的判定**相反**：前者"给了值" ⇒ `AND app = '   '`、
后者"没给" ⇒ 不过滤 ⇒ **同一个响应里出现「总数 3、各级别之和 0」**。实测读数确认。

**先写能红的用例**：`FilterValueTrimApiTest`（6 例，**跨 profile** —— 本仓第四处，形状同
`TextEqualityApiTest` / `SearchMatchApiTest` / `SearchWildcardApiTest` /
`SearchKeywordTrimApiTest`：不 `@Transactional`、不按 profile 跳过）。不改代码跑一次
= **4 红 2 绿**：

| 用例 | 改前 | 改后 |
| --- | --- | --- |
| 用户域 `"  ENABLED  "` 与 `ENABLED` 结果集相同 | 红（2 vs 0） | 绿 |
| 组织域：同上（**对照组**） | 绿 | 绿 |
| 租户域：同上 | 红（1 vs 0） | 绿 |
| 日志域 `"  <app>  "` 与 `<app>` 相同 | 红（1 vs 0） | 绿 |
| 日志域**聚合的级别条数之和 = 总数**（空白 app） | 红（总数 3、各级别之和 **0**） | 绿 |
| 纯空白 = 不过滤（三域同义） | 绿（**回归钉**） | 绿 |

第三条红就是内部不一致的现场证据；第二条红是"对照组"（组织域本来就有 `normalize`）；
最后一条是回归钉。`assertSameResultSet` 先断言 `cleanTotal > 0`（防"两边都 0 条"平凡通过）。

**决策（6 条）**：

1. 规范化的**真值来源收敛到一处**：新建 `FilterValue.text()`（`null` 进 `null` 出、
   否则 `trim()`、空则 `null`）。手法与 `0065` 把"文本相等"收进一个 API、
   `0067` 把转义收进 `KeywordLike` 同源 —— **一处定义、多处引用**。
2. **下沉**：`0068` 把关键词规范化收进 `KeywordLike.pattern()`，本轮把它下沉到更基础的
   `FilterValue` —— 因为精确匹配的过滤值也要用它，而过滤值不该依赖"LIKE 那个类"；
   `pattern()` 内部改调 `FilterValue.text()`。
3. **枚举归一那 4 处不动**（`parse()` 自带 trim 且归一大小写，替换即退化）。
4. **纯 trim 那 5 处也不动**（行为已等价），**没有**顺手合并它们 —— 与本轮 20 处不同源。
5. 手写 SQL 与 lambda wrapper **共用同一个局部变量**（`stats` 里算一次传下去）⇒
   一致性由"只有一个来源"保证，而不是"两处各写一遍相同的判空"。
6. `level` 那处 `toLowerCase` **不下沉**：那是"该列存小写"的**列比较语义**
   （如资源域的 `method` 往反方向归一），不是通用规范化。

**落地**（10 个已跟踪文件 +142 −47，4 个新文件，**前端零改动**）：
新 `FilterValue` · `KeywordLike.pattern()` 改调它 · `UserService` / `TenantService` /
