## 咨询：权限放基座还是独立子应用（待舰长确认，未落地）

结论建议「三分法」，不是二选一：

1. **会话（认证/令牌）**：逻辑下沉 `packages`（`common-api` 接线 + `common-tools/http` 注入令牌与 401/403 分流 + session 令牌存取），**基座只做装配**（登录页、路由守卫、全局状态下发）。理由：子应用要保留独立运行分支（ADR-0012），登录逻辑写死在基座组件里则子应用单跑时没有登录能力。
2. **权限判定**：算在基座（`/api/auth/me` 的权限集合），经既有 `HostGlobalState` 通道下发（现只有 theme/locale/userId），子应用用 `onHostGlobalStateChange` 消费，不自己调认证接口。
3. **权限管理界面**（组织/角色/用户组/资源 CRUD）：独立子应用 `platform-admin`，基座保持「壳薄」。

**不推荐开「认证子应用」的理由**：鸡生蛋（登录前要先远程加载子应用 + 初始化 qiankun 沙箱，与 ADR-0003「首屏零阻塞」冲突）；令牌持有者在子应用、消费方却在别处，还得再上交基座下发，绕一圈回到方案 1；登录页是壳级能力（未登录时基座导航都不该出现），放子应用会让守卫逻辑分裂两处。

顺带待定项：令牌存哪（短效 access 放内存 + refresh 持久化 vs httpOnly cookie 需后端配合）。

## ADR-0018 权限在微前端中的归属（已落地为文档）

舰长确认「按你建议的来」后落笔 `docs/decisions/0018-权限在微前端中的归属.md`（168 行，9 条决策 + 落地顺序三段 + 未覆盖清单）。

**写之前先从后端实现里挖出两条会决定前端形状的事实**（不挖就会写出与实现不符的决策）：

1. **权限不在令牌里** —— `JwtCodec` 载荷只有 `sub/uid/tid/uname/typ/jti/iss/aud/iat/exp`，`roles`/`permissions` 是 `LoginVO`/`MeVO` 的字段 ⇒ 刷新页面**必须做会话恢复**（调 `/me`），不能靠解析令牌。
2. **刷新令牌轮换 + 重放检测** ⇒ 前端**并发刷新会被后端判定为重放**，撤销该用户**全部**刷新令牌。所以「401 刷新必须单飞」不是性能优化而是正确性要求 —— 这是本次最有价值的一条推导。

其余决策：会话实现下沉 `packages/`（子应用要保留独立运行分支，写死在基座则单跑没有登录能力）· 权限判定基座单点计算、`HostGlobalState` 增 `roles`/`permissions` 下发、子应用禁自调 `/me` · 权限码复用后端 `AuthPermissions` 的 `域:资源:动作`、前端禁拼接 · 管理界面独立成 `platform-admin` · **不开认证子应用**（首屏零阻塞 / 令牌绕圈 / 守卫分裂）· access 放内存 + refresh 持久化（轮换与重放检测兜底 XSS）、httpOnly cookie 列为将来项 · 403 不跳登录（对齐 ADR-0016）。

## ADR-0018 第①段落地：契约与传输层（认证链路）

代码在 `web/packages/`，四件事：

1. **`common-tools/http` 加三个注入位**：`accessTokenProvider`（注入 Bearer）· `onUnauthorized`（401 时问"还能救吗"）· `onAuthLost`（救不回来通知界面）。内核仍不认识刷新接口与登录页。
   - 只救 401（403 换令牌换不来权限）· 只重试一次 · **重试前重新取令牌**（否则带作废令牌再撞）· 未带令牌的 401 不触发 · 恢复钩子抛错按未恢复处理

   - `skipAuth` / `skipAuthRetry` 两个开关，刷新接口自身必须带后者（否则递归刷新）
2. **`common-tools/session` 新模块**：access 只在内存、refresh 持久化（带版本号、读不懂即丢弃）· 快照引用稳定（`useSyncExternalStore` 要）· commit 只比引用不比字段（手写清单漏项会静默丢更新）· 存储读写全包 try（无痕/配额都会抛）

### 决策第 9 条：基座下发"认证能力"而非令牌值

`HostAuthBridge = { getAccessToken(): string | null; reauthenticate(): Promise<boolean> }`，经 `HostProps.auth` 下发。
- **不给令牌值的原因**：基座会在 401 时静默刷新，子应用手里缓存的令牌会**陈旧**（拿作废令牌去请求）；而刷新这件事**必须全应用只做一次**（刷新令牌轮换 + 重放检测，并发刷新会被判定成攻击）。
- **刻意不提供"清空会话"**：登出是基座的事，子应用没有立场替用户登出。

### 会话级单飞（在 AuthChannel 里再合并一次）

`common-tools/http` 的 `pendingReauth` 是**按客户端**合并的；而基座自己的客户端 + 若干子应用经桥委托过来的请求是**跨客户端并发**的。
所以 `common-api/channel.ts` 的 `reauthenticate()` 必须**在会话层再合并一次**（`pendingRefresh` + `finally` 清位）。补两条单测：三个并发只打一次刷新；一次失败后再调用仍能真的刷新。

### `common-api` 新增 `access` 域

`access.ts`：users 六个操作（page / detail / create / update / resetPassword / **remove**）+ tenants 五个操作（page / detail / create / update / remove）。
类型全部由契约推导（`DataOf` / `BodyOf` / `QueryOf` / `PathOf`），`PATH_USERS` / `PATH_TENANTS` 用 `satisfies keyof paths` 钉住；导出 `AccessPermissions` 八个常量（**与后端 `AuthPermissions` 逐字一致，前端禁拼接自造**）。删除方法刻意叫 `remove`。

## 打通本地 MySQL（真实库首跑）

目标：把默认的 h2 内存库切成"数据真的留得住"的本机 MySQL，并让整条链路（含前端端到端）在真实库上复验一遍。

### 环境

本机 MySQL 是**便携版** `D:/tools/installer/mysql`（8.0.26，无 `my.ini`：basedir 由可执行文件位置推出 → `datadir=basedir\data`），所以启动就是
`D:/tools/installer/mysql/bin/mysqld.exe --datadir=D:/tools/installer/mysql/data`。
`bluewhale` 库早已建好（utf8mb4 / utf8mb4_0900_ai_ci）。**root 口令由舰长现场提供，不写进任何文件与记忆**（沿用 2026-10-10 的约定）；后续命令一律用 `MYSQL_PWD=<口令>` 环境变量传，不进仓库。
本机另有 11 个别的项目的库（`sts-db-*` / `yc-sts-db-*` / `parallel_world_server`）—— **一个都没碰**。

### 关键发现：V3 从没在 MySQL 上跑过

`flyway_schema_history` 只有 2 行（V1 日志、V2 事件，2026-10-10 落的），**V3（权限域 12 张表）从来没在 MySQL 上执行过** —— 权限域是在 h2 上开发验证的（ADR-0016 那段），切库这事一直没做。

切过去之后一次成功：`Migrating schema bluewhale to version "3 - create bw auth tables"` → **0.603s 成功**，12 张 `bw_auth_*` 建出，共 15 张表。**没有校验和不匹配、没有保留字 1064** —— 说明 V3 的 mysql 方言脚本当初写对了，只是没跑过。

### 第二个发现：真实库上没有任何账号可登录

登录接口怎么试都失败，根因不是 bug 而是**刻意的设计**：
`bluewhale.auth.seed-admin` / `seed-auditor` 只在 `application-h2.yml` 里开启，且 h2 那份注释就写着"换到 mysql / dameng 时本项不生效：真实库里的账号应由运维显式创建，而不是让应用每次启动都去补一个固定口令的管理员"。
`bluewhale` 库的 `bw_auth_user` 是 0 行 —— 而建账号的接口本身要求已登录，形成引导死锁。

**处理：不往 `application-mysql.yml` 加种子开关**（那会推翻上面这条设计），而是**显式开一次**：

```bash
BW_DB_PASSWORD=<口令> java -jar sts-app-server.jar --spring.profiles.active=mysql \
  --bluewhale.auth.seed-admin.enabled=true --bluewhale.auth.seed-auditor.enabled=true
```

种子是 `ensure*` 幂等语义，重复执行无副作用。种下：admin(id=1) / auditor(id=2)、租户 `default`、角色 `SUPER_ADMIN`+`AUDITOR`、资源 8 条、角色-资源关系 10 条。
随后**不带开关重启**，两个账号照样登录 → **留存这件事本身被验证了**（h2 做不到这一点，这正是切库的意义）。
