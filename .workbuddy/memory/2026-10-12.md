## 咨询：权限放基座还是独立子应用（待舰长确认，未落地）

结论建议「三分法」，不是二选一：

1. **会话（认证/令牌）**：逻辑下沉 `packages`（`common-api` 接线 + `common-tools/http` 注入令牌与 401/403 分流 + session 令牌存取），**基座只做装配**（登录页、路由守卫、全局状态下发）。理由：子应用要保留独立运行分支（ADR-0012），登录逻辑写死在基座组件里则子应用单跑时没有登录能力。
2. **权限判定**：算在基座（`/api/auth/me` 的权限集合），经既有 `HostGlobalState` 通道下发（现只有 theme/locale/userId），子应用用 `onHostGlobalStateChange` 消费，不自己调认证接口。
3. **权限管理界面**（组织/角色/用户组/资源 CRUD）：独立子应用 `platform-admin`，基座保持「壳薄」。

**不推荐开「认证子应用」的理由**：鸡生蛋（登录前要先远程加载子应用 + 初始化 qiankun 沙箱，与 ADR-0003「首屏零阻塞」冲突）；令牌持有者在子应用、消费方却在别处，还得再上交基座下发，绕一圈回到方案 1；登录页是壳级能力（未登录时基座导航都不该出现），放子应用会让守卫逻辑分裂两处。

顺带待定项：令牌存哪（短效 access 放内存 + refresh 持久化 vs httpOnly cookie 需后端配合）。

## ADR-0018 权限在微前端中的归属（已落地为文档）

舰长确认「按你建议的来」后落笔 `docs/decisions/0018-权限在微前端中的归属.md`（168 行，9 条决策 + 落地顺序三段 + 未覆盖清单）。

**写之前先从后端实现里挖出两条会决定前端形状的事实**（不挖就会写出与实现不符的决策）：

1. **权限不在令牌里** —— `JwtCodec` 载荷只有 `sub/uid/tid/uname/typ/jti/iss/aud/iat/exp`，`roles`/`permissions` 是 `LoginVO`/`MeVO` 的字段 ⇒ 刷新页面**必须做会话恢复**（调 `/me`），不能靠解析令牌。
2. **刷新令牌轮换 + 重放检测** ⇒ 前端**并发刷新会被后端判定为重放**，撤销该用户**全部**刷新令牌。所以「401 刷新必须单飞」不是性能优化而是正确性要求 —— 这是本次最有价值的一条推导。

其余决策：会话实现下沉 `packages/`（子应用要保留独立运行分支，写死在基座则单跑没有登录能力）· 权限判定基座单点计算、`HostGlobalState` 增 `roles`/`permissions` 下发、子应用禁自调 `/me` · 权限码复用后端 `AuthPermissions` 的 `域:资源:动作`、前端禁拼接 · 管理界面独立成 `platform-admin` · **不开认证子应用**（首屏零阻塞 / 令牌绕圈 / 守卫分裂）· access 放内存 + refresh 持久化（轮换与重放检测兜底 XSS）、httpOnly cookie 列为将来项 · 403 不跳登录（对齐 ADR-0016）。

## ADR-0018 第①段落地：契约与传输层（认证链路）

代码在 `web/packages/`，四件事：

1. **`common-tools/http` 加三个注入位**：`accessTokenProvider`（注入 Bearer）· `onUnauthorized`（401 时问"还能救吗"）· `onAuthLost`（救不回来通知界面）。内核仍不认识刷新接口与登录页。
   - 只救 401（403 换令牌换不来权限）· 只重试一次 · **重试前重新取令牌**（否则带作废令牌再撞）· 未带令牌的 401 不触发 · 恢复钩子抛错按未恢复处理

   - `skipAuth` / `skipAuthRetry` 两个开关，刷新接口自身必须带后者（否则递归刷新）
2. **`common-tools/session` 新模块**：access 只在内存、refresh 持久化（带版本号、读不懂即丢弃）· 快照引用稳定（`useSyncExternalStore` 要）· commit 只比引用不比字段（手写清单漏项会静默丢更新）· 存储读写全包 try（无痕/配额都会抛）

### 决策第 9 条：基座下发"认证能力"而非令牌值

`HostAuthBridge = { getAccessToken(): string | null; reauthenticate(): Promise<boolean> }`，经 `HostProps.auth` 下发。
- **不给令牌值的原因**：基座会在 401 时静默刷新，子应用手里缓存的令牌会**陈旧**（拿作废令牌去请求）；而刷新这件事**必须全应用只做一次**（刷新令牌轮换 + 重放检测，并发刷新会被判定成攻击）。
- **刻意不提供"清空会话"**：登出是基座的事，子应用没有立场替用户登出。

### 会话级单飞（在 AuthChannel 里再合并一次）

`common-tools/http` 的 `pendingReauth` 是**按客户端**合并的；而基座自己的客户端 + 若干子应用经桥委托过来的请求是**跨客户端并发**的。
所以 `common-api/channel.ts` 的 `reauthenticate()` 必须**在会话层再合并一次**（`pendingRefresh` + `finally` 清位）。补两条单测：三个并发只打一次刷新；一次失败后再调用仍能真的刷新。

### `common-api` 新增 `access` 域

`access.ts`：users 六个操作（page / detail / create / update / resetPassword / **remove**）+ tenants 五个操作（page / detail / create / update / remove）。
类型全部由契约推导（`DataOf` / `BodyOf` / `QueryOf` / `PathOf`），`PATH_USERS` / `PATH_TENANTS` 用 `satisfies keyof paths` 钉住；导出 `AccessPermissions` 八个常量（**与后端 `AuthPermissions` 逐字一致，前端禁拼接自造**）。删除方法刻意叫 `remove`。

## 打通本地 MySQL（真实库首跑）

目标：把默认的 h2 内存库切成"数据真的留得住"的本机 MySQL，并让整条链路（含前端端到端）在真实库上复验一遍。

### 环境

本机 MySQL 是**便携版** `D:/tools/installer/mysql`（8.0.26，无 `my.ini`：basedir 由可执行文件位置推出 → `datadir=basedir\data`），所以启动就是
`D:/tools/installer/mysql/bin/mysqld.exe --datadir=D:/tools/installer/mysql/data`。
`bluewhale` 库早已建好（utf8mb4 / utf8mb4_0900_ai_ci）。**root 口令由舰长现场提供，不写进任何文件与记忆**（沿用 2026-10-10 的约定）；后续命令一律用 `MYSQL_PWD=<口令>` 环境变量传，不进仓库。
本机另有 11 个别的项目的库（`sts-db-*` / `yc-sts-db-*` / `parallel_world_server`）—— **一个都没碰**。

### 关键发现：V3 从没在 MySQL 上跑过

`flyway_schema_history` 只有 2 行（V1 日志、V2 事件，2026-10-10 落的），**V3（权限域 12 张表）从来没在 MySQL 上执行过** —— 权限域是在 h2 上开发验证的（ADR-0016 那段），切库这事一直没做。

切过去之后一次成功：`Migrating schema bluewhale to version "3 - create bw auth tables"` → **0.603s 成功**，12 张 `bw_auth_*` 建出，共 15 张表。**没有校验和不匹配、没有保留字 1064** —— 说明 V3 的 mysql 方言脚本当初写对了，只是没跑过。

### 第二个发现：真实库上没有任何账号可登录

登录接口怎么试都失败，根因不是 bug 而是**刻意的设计**：
`bluewhale.auth.seed-admin` / `seed-auditor` 只在 `application-h2.yml` 里开启，且 h2 那份注释就写着"换到 mysql / dameng 时本项不生效：真实库里的账号应由运维显式创建，而不是让应用每次启动都去补一个固定口令的管理员"。
`bluewhale` 库的 `bw_auth_user` 是 0 行 —— 而建账号的接口本身要求已登录，形成引导死锁。

**处理：不往 `application-mysql.yml` 加种子开关**（那会推翻上面这条设计），而是**显式开一次**：

```bash
BW_DB_PASSWORD=<口令> java -jar sts-app-server.jar --spring.profiles.active=mysql \
  --bluewhale.auth.seed-admin.enabled=true --bluewhale.auth.seed-auditor.enabled=true
```

种子是 `ensure*` 幂等语义，重复执行无副作用。种下：admin(id=1) / auditor(id=2)、租户 `default`、角色 `SUPER_ADMIN`+`AUDITOR`、资源 8 条、角色-资源关系 10 条。

# 第三条管道：审计日志（ADR-0019）

`docs/decisions/0004` 与 `0011` 都把审计写成"三条并列管道"的第三条、且是**唯一由后端产生**的一条，却长期停在"已设计未实现"：契约里没有一条审计接口，只在 `ClientLogController` 的注释里写着"审计日志不走本接口"。原料（`AuthContext` / `AuthInterceptor` / `GlobalExceptionHandler`）全在，缺的只是落地。今天补完。

## 动手前必须回答的四个问题

| 问题 | 答案 |
| --- | --- |
| **"不可篡改"怎么保证？** | **不靠权限 —— 靠接口不存在**。加权限码只能挡住没权限的人。落地成组"结构上做不到"的事实：无写接口（POST → `40500`）· `AuditLogService` 无写方法 · 实体不继承 `BaseEntity`（故无 `update_*`）· 表无 `deleted` 列 · 前端 `AuditApi` 无写方法 |
| **谁产生？** | 拦截器 + **显式 `@Audited`**，不自动拦所有非 GET。自动拦会把登录 / 上报 / 健康检查全记进去（审计表被自己的上报灌满），而且 **HTTP 方法推不出"做了什么"**：`PUT /api/auth/users/{id}` 既可能是改邮箱也可能是重置口令 |
| **成败怎么判？** | 本仓"业务失败仍返回 HTTP 200"，响应状态码上看不出结果 → 新增中立通道 `ResponseOutcome`（在 `sts-common-web`，**不认识审计域**） |
| **注解与域放哪？** | 权限域要标它、审计域要读它，互相依赖会成环 → 下沉 `sts-components`（**该层首次落地**，ADR-0005 预留已久） |

## 三处踩过源码才敢写的结论

1. **`afterCompletion` 的 `exception` 参数恒为 null。** 核对 spring-webmvc 6.2.11 与 7.0.1：`DispatcherServlet.processDispatchResult` 调的就是 `triggerAfterCompletion(request, response, null)`。异常早被 `HandlerExceptionResolver` 处理完，走到这里只剩一个成功的 200。**光靠这个参数判不出失败。**
2. **审计拦截器必须排在鉴权之前。** `HandlerExecutionChain.applyPreHandle` 记录 `interceptorIndex`，`triggerAfterCompletion` 从该下标倒序回调 → **鉴权失败时排在其后的拦截器 `afterCompletion` 永不执行**。排在后面，"越权尝试"这类最该留痕的记录会**静默丢失**。顺序收进 `WebInterceptorOrder`（`AUDIT=-100 < AUTHORIZATION=-50 < DEFAULT=0`）。
3. **`REQUIRES_NEW` 必须配"异常处理留在调用方"。** 业务回滚时审计不能跟着回滚（"被拒绝"恰恰最需要留痕）；而 try/catch 若写在 `AuditRecorder` 内部方法里，self-invocation 会让 `@Transactional` 静默失效。

## 真的写错了一处：三套标识

| 类别 | 形状 | 例子 | 常量类 |
| --- | --- | --- | --- |
| 资源标识 | `域:资源` | `auth:user` | `AuthResources` |
| 权限码 | `域:资源:动作` | `auth:user:create` | `AuthPermissions` |
| 动作标识 | `域.资源.动作` | `auth.user.create` | `AuthAuditActions` |

第一版把 `@Audited(resource = ...)` 填成了**权限码**。后果是**静默**的：存进去的是 `auth:user:create`，而"按资源过滤审计"查的是 `auth:user` → 查不到任何东西且不报错。`AuditApiTest` 的两条失败暴露了它。修完补 `AuthTaxonomyTest`（5 例）把三者的形状与归属关系钉死。

## 发现的既有缺陷：`verify-micro-frontend.mjs` 从 ADR-0018 起就是坏的

它**没有任何登录步骤** —— 而基座自 ADR-0018 起有登录守卫，未登录访问 `/` 会被弹到 `/login`，于是 `.basic-layout__link` 与 `.home__link` 都是空的，报出来的却是一句 `页面内求值失败："Uncaught"`（`.find(...)` 返回 `undefined` 再 `.click()`）。

顺带：脚本原来点的「登录」调试开关已被真实会话取代，改成"断言子应用拿到的身份非空 + 点「全局主题」断言 `theme=` 跟着变"。

## 一处被记录的架构偏离

`sts-server-audit` → `sts-server-auth` 是**同层 Maven 依赖**，而 `architecture/后端分层与依赖方向.md` 写的是「同层 ✗」。范围可枚举：审计域只**读**权限域的两样词汇 ——「当前操作人」（`AuthContext`）与「权限码」（`@RequiresPermission` + `AuthPermissions.AUDIT_READ`），不调用任何权限域服务。

# 二次回访参照实现的权限域：这次**借鉴**了什么（ADR-0020）

上午那轮（ADR-0016）问的是"哪些**不**照搬"；舰长这次把问题**反过来**问：

> 「和 `D:\workspace\SystemTerminator` 里面的权限服务对比一下，看有没有值得借鉴的地方，有的话，借鉴过来，没有就算了。」

"没有就算了"是明确的许可 —— 所以第一步不是找可抄的东西，而是**先判断值不值得抄**。

## 方法：先辨真伪，再谈借鉴

参照实现的权限域约 **515 个文件**，本仓 **69 个**。但**数量不等于可用**。
逐一核对"有没有实现类、有没有调用方"之后，它的真实面貌是**大量构件停在设计阶段**：

| 构件 | 表面 | 实情 |
| --- | --- | --- |
| `PasswordPolicy`（值对象，含 `validate()`） | 完整 | **全仓零调用** —— 被 `TenantConfigEntity` 持有，却从未接进登录或改密 |
| `PasswordHistoryEntity` + `PasswordHistoryPo` | 完整 | **没有对应的 Repository** |
| `InheritStrategyEnums`（NONE/FULL/INCREMENTAL/OVERRIDE） | 四值俱全 | 只是 `RoleInfoAggregate` 的一个字段，**没有任何继承逻辑** |
| `CaptchaService` | 是个服务 | **空接口**，一个方法都没有 |
| `LoginAttemptService` / `BlackWhiteListDomainService` | 有接口 | **没有实现类** |
| `AuthApplicationServiceImpl.authentication(...)` | 有方法 | **`return null`** —— 核心链路是空的（ADR-0016 已记） |

它的 `AuthSecurityDomainServiceImpl`（312 行）是**真实现**（账户锁定、验证码阈值、可信设备、黑白名单匹配都在里面），
但**从未被接进登录链路** —— 唯一的调用点就在那个 `return null` 的方法里。

**本仓的问题恰好相反**：链路是通的（登录 / 刷新 / 登出 / 鉴权 / 审计都在跑），但**策略粗糙** ——
口令只校验长度，锁定是固定时长。所以方向不是"抄功能"，而是
**把那些设计良好却始终没接通的策略模型，接到本仓已经通了的链路上**。

## 核实时发现的一处真实缺陷：登录失败锁定**从来没生效过**

核对"锁定到底有没有用"时发现的。原实现：

```java
@Transactional
public LoginVO login(...) {
    if (!passwordHasher.matches(...)) {
        registerFailure(user, now);                               // 写 failed_attempts / locked_until
        throw AuthResultCode.BAD_CREDENTIALS.businessException(); // RuntimeException
    }
```

`BusinessException` 是 `RuntimeException`，`@Transactional` 默认对它回滚 ——
**失败计数连同这次回滚一起消失**。下次请求读到的仍是初值 0，阈值永远达不到、账号永远不会被锁定；
而且连"账号已被锁定"那句 WARN 也到不了（它同样在阈值之后）。
表象是"字段齐全、方法齐全、日志语句齐全，**什么都不会发生**"。

修法：`LoginAttemptRecorder`（**独立 Bean** + `REQUIRES_NEW`，且**按主键重读用户** ——
调用方那个实体属于已被挂起的事务）。与 `AuditRecorder` 是**同一条理由的两种表现**：
**"因为这次操作失败而产生的记录"，恰恰不能跟着这次失败一起回滚**。

> 这个缺陷**用带 `@Transactional` 的测试测不出来**：测试事务把请求包进同一事务，未提交的写自己可见，
> "根本没写进库"被完全掩盖。所以本轮的端到端测试 `PasswordHardeningApiTest` **刻意不加 `@Transactional`**。

## 落地六项

| # | 内容 | 关键点 |
| --- | --- | --- |
| 1 | `PasswordPolicy`（纯函数） | 借鉴**意图**，不借鉴"复杂度等级"枚举（等级表达不了"要特殊字符但不要大写"）；返回**未满足项列表**而非 boolean，`describe()` 让提示随配置走 |
| 2 | 口令强度**只有一个来源** | 删掉两个 DTO 的 `@Size(min = 8)`，只留 `max`。两处都判会让"口令太短"返回**两种错误码** |
| 3 | `bw_auth_password_history`（V5 三方言） | append-only，**不继承 `BaseEntity`**（`RefreshTokenEntity` 之后第二例）；防重用**当前值也要比**；**按条数裁剪不按时间**（表规模 = "要防几次重用"这个量本身） |
| 4 | `LoginLockPolicy`：指数退避 | 第 n 次 = `5 × 2^(n-1)` 分钟、封顶 24 小时。纯函数 → 三条硬边界（**翻倍 / 封顶 / 不溢出**）可单测。`lock_level` 记"被锁过几次"，只在登录成功时清零 |
| 5 | `LoginAttemptRecorder`（`REQUIRES_NEW`） | 见上一节。调用方**吞掉**异常（计数写不进去不该把 40101 变成 500） |
| 6 | 端到端测试不加 `@Transactional` | 见上 |

错误码：`40003`（口令强度不足，400xx 段）· `40914`（该口令已使用过，409xx 段）。
配置新增 `min-length` / `require-{uppercase,lowercase,digit,special}` / `history-count`、
`lock-growth-factor` / `max-lock-duration`，并把 `lock-duration` 从 15m 改成 5m。

## 独立 HTTP 校验又逮到一处：状态**落库了，但接口看不见**

单测全绿之后，我另写了一个**直接打运行中应用**的校验脚本（不经过测试上下文），
结果 `lockLevel` 那一条 FAIL —— 而同一个断言在单测里是 PASS 的。

原因：单测从**库里**读 `lockLevel` 断言，`UserVO` 却根本没这个字段。
**"读库断言"证明的是"写进去了"，不证明"读得出来"。** 出参缺失的后果是：
运维在界面上看到"锁定至明天"，却不知道原因、也不知道是第几次 —— 无从判断退避在不在生效。

修法：`lockLevel` 与 `lockReason`（后者本就是既有缺口）都补进 `UserVO` +
`PasswordHardeningApiTest` 补一条**经 `GET /api/auth/users/{id}` 的断言**，
"落库"与"可见"由两次断言分别钉住。

> 这两个独立校验（HTTP 脚本 + 手动刷新令牌链路）都保留了：刷新 / 轮换 / 重放检测
> （旧令牌重放得 `40106`）逐一确认过，确认本次改动没有碰坏旁边的刷新链路。

## 顺带修掉的坑：`gen:api` 的输出没归一

`openapi-typescript` 的输出是 **4 空格缩进 + 双引号**，而入库的是 **Prettier 归一后的样子**
（2 空格 + 单引号）。两者不一致时，即使契约只改一个字段，`git diff` 也是**整文件重排**
（本次实测 1811 行增删），真正那一处改动被淹没 —— 这个坑本轮**踩了两次**，
每次都是生成后手工补一次 Prettier 才收敛回几行。

## 权限模型盘点（舰长问「是什么模型 / 能不能兼容菜单按钮与数据权限」）

**结论**：RBAC 为骨架，且底子是照 IAM 铺的，不是朴素 RBAC —— 四个超出项：
`GrantEffect.DENY`（显式拒绝优先于 ALLOW）· 多态成员（角色可授用户也可授用户组，`member_type`）·
时态授权列 `effective_from/to`（**三处都有**：角色成员 / 角色资源 / 资源实例，判定未纳入）·
`ResourceType` 九分类 + `isRequestScoped()`（只有 API / BUTTON 参与后端判定，MENU / PAGE 刻意不参与）。
ABAC 挂点已留：`RoleEntity.dataScope` + `filterJson`、`bw_auth_rel_role_resource_instance`。

**四类出口的落地状态（关键事实，省下次重查）**：

| 出口 | 判定入口 | 状态 |
| --- | --- | --- |
| API | `@RequiresPermission` + `AuthInterceptor` → `PermissionChecker` | ✅ 通 |
| BUTTON | `platform-admin/components/PermissionButton.tsx`（`data-permission` 写进 DOM 供 e2e 断言） | ✅ 通 |
| MENU / PAGE | — | ⏳ **模型就绪，零落地** |
| DATA | — | ⏳ **表与字段就绪，求值未做** |

**两个容易踩的认知**：

1. **按钮不是"补丁"，它和后端准入共用同一份判定** —— BUTTON 的 `resource_code` 与
   `@RequiresPermission` 的字符串是同一个，所以不存在"两套权限"。菜单/页面则是
   `requestScoped=false`（**可见性不是安全边界**，刻意不进后端判定）；路由层已由
   ADR-0018 的声明式 `<Navigate>` 守卫兜住，"不可见 ≠ 不可达"这一点已经解决。
2. **MENU / PAGE 在库里是零数据**：`DefaultAdminSeeder.ensureResources()` 把
   `AuthPermissions.ALL` 全部建成 `ResourceType.API`。做菜单权限前必须先让资源表里
   真的有 MENU / PAGE 行（带 `parent_code` 构成树），否则前端没有数据可过滤 ——
   **这是"模型兼容"与"能跑起来"之间的真实缺口**。

**顺带发现的两处不一致（未改，待决）**：

- 组织 / 角色 / 用户组 / 资源的**管理接口全都没有**（表 + 实体 + Mapper 已落地，无
  Controller / Service）→ 现在配权限只能靠种子数据或直接改库，**这是菜单权限与
  数据权限"能不能用起来"的第一道坎**，比判定本身更靠前。
- `common-api/src/access.ts` 的 `AccessPermissions` 只有 8 个（user / tenant × 4），
  **不含 `auth:audit:read`**；`platform-audit-console` 在自己应用内声明了它。
  与 ADR-0018「前端不得自造权限码、只能引用后端一致的字面量」有轻微偏斜。


## 资源目录接口落地（ADR-0021）—— 把权限配置从"改库"变成"调接口"

**为什么先做这一条**：组织 / 角色 / 用户组 / 资源四类管理接口全缺，是菜单权限与数据
权限"能不能用起来"的第一道坎，比判定本身更靠前；而资源是另外三条管理的共同前置
（角色要先能选到资源才谈得上授权）。表结构早已定死，纯 CRUD，无架构风险。

**交付**：`sts-server-auth/.../resource/` 下 8 个类 —— `ResourceController`
（`/api/auth/resources`：分页 / tree / 详情 / 建 / 改 / 删 6 个映射）、`ResourceService`、
`ResourceMapper`（含两个刻意绕过 `@TableLogic` 的手写 SQL）、`ResourceQuery`、
`ResourceSaveRequest`、`ResourceVO`、`ResourceTreeNode`；权限码 `auth:resource:{read,create,
update,delete}` 进 `AuthPermissions.ALL`（9 → 13 项），资源标识 `auth:resource`，动作
`auth.resource.{create,update,delete}`，新错误码 `RESOURCE_IN_USE(40915)`。

**过程中挖出并修掉的 4 个真问题**（都不是"顺手改"，是测试逼出来的）：

1. **软删撞键兜底成 50000** —— `uk_bw_auth_resource_code` 建在 `resource_code` **单列**、
   不含 `deleted`，而 MyBatis-Plus 每条查询自动追加 `deleted = 0`，于是**看不见软删行**
   → 唯一性检查通过 → insert 撞键 → `GlobalExceptionHandler` **没有**
   `DuplicateKeyException` / `DataIntegrityViolationException` 处理器 → 兜底 50000。
   正解是**复活**原记录（手写 `selectAnyByCode` / `restoreDeletedById`，并在内存里
   `setDeleted(0)`，因为 `updateById` 会把非空字段写进 SET）。
   **`updateById` 对软删行的 WHERE 也带 `deleted = 0` → 永远匹配不到且不报错（静默 0 行）**，
   这是同一条坑的另一面。
2. **`page()` NPE** —— `Cannot invoke "String.trim()" because getParentCode() is null`。
   **MyBatis-Plus `eq(条件, 列, 值)` 的"值"参数是无条件求值的**（Java 先算实参），
   `x.getParentCode().trim()` 在 null 时照样炸，那个 `!= null` 判断看着像保护其实救不了。
   修法：过滤值先取局部变量。
3. **`tree()` NPE** —— `canAttach` 对"父不存在"返回 `true`，随后 `byCode.get(parentCode)`
   是 null。**这条是专门为验证"孤儿降级"而写的用例逮到的** → 函数开头加
   `if (!byCode.containsKey(parentCode)) return false;`。
4. **计数型文档漂移** —— 管理员权限数 9 → 13，散布在 e2e 断言 + 四份 README +
   `AuthApiTest`。可推导的那处（`AuthApiTest`）改为 `AuthPermissions.ALL.size()`；
   其余四处显式改字面量并记入 ADR-0021「发现但未处理」。

**刻意没做**（都是"看着该做、其实不该做"）：

- **不动 `AuthorizationMapper`** —— 它的注释与 SQL 不一致（只按 `ro.tenant_id` 过滤），
  但那是**安全判定本身**，顺手改等于悄悄改安全边界。
- **不动前端 `access.ts`** —— 规则是"只列前端真的用到的"，资源域前端还没接线。
- **不扫描 Controller 自动登记资源** —— `request_url` / `request_method` 是**单值列**，
  表达不了"一个权限码保护多个接口"（`auth:user:read` 同时管 `GET /users` 与
  `GET /users/{id}`）。
- **不种 `MENU` / `PAGE` 资源** —— 无消费方 = 不预置空壳。

**校验**：后端 `mvn -B clean install` **BUILD SUCCESS · 109 例**（log 12 · track 8 ·
auth 32 · audit 10 · app 47），0 失败 0 错误；实测管理员 **13 项权限** / 13 条资源 /
树 13 个根节点；契约 **23 路径 / 34 接口 / 57 模型**（+7 Resource 模型）；前端类型 diff
**376 增 / 8 删**（纯语义增量，非整文件重排 —— 证明 ADR-0020 给 `gen:api` 挂 Prettier 生效）。

**收尾**：前端逐包校验 **39/39 全绿 · 485 例**；e2e 四脚本
`verify-micro-frontend` / `verify-admin-permissions` / `verify-audit-pipeline` 通过，
`verify-portal-auth` 首跑在"刷新恢复会话"一步超时 —— **与前端逐包校验（含 `vite build`）
并发跑、CPU 争抢所致**，单独复跑 8 步全过（`perm=13`）。提交 `57c3b16`（25 文件
+2836/−61，Husky lint-staged 通过）。**推送仍被沙箱代理阻断**：`github.com` 报
`CONNECT tunnel failed, response 502` / `Empty reply from server`（`api.github.com`、
`codeload.github.com` 正常）→ `main` 领先 `origin/main` **3 个提交**，待网络放行后
`git push origin main` 即可。

**教训（值得记住）**：**e2e 脚本不要与前端构建并发跑**。看起来都"只是读页面"，
但 `vite build` 会把 CPU 占满，导致刷新恢复会话这类**有时限的等待**超时，
表现成"业务回归"（掉登录），实际是环境噪声 —— 先看是否与其他重任务并发，
再怀疑代码。
