## ADR-0027 上报限流归网关层（本机）

承接 `0026` 的「发现但未处理」第 2 条 —— 我上一轮给的下一步建议 ①「上报限流」。

### 先辨真伪：动手前的侦察推翻了默认思路

舰长原本按建议选了 ①，但侦察后发现"把限流写进 `server/`"是错的：

- **服务端一条限流也没有**：`RateLimit`/`Bucket`/`TokenBucket`/`Throttle`/`Semaphore`/`Quota`/
  `maxRequestSize`/`concurrent` 在 `server/` 下**全部零命中**；也没有 bucket4j / resilience4j /
  guava / caffeine 任何依赖（15 个 `pom.xml` 都没有）。
- **唯一的体量闸门是 Bean Validation 的单批 500 条**；`server.tomcat.*` 一个字没配过。
- **`42900` 归给了一个从未存在过的组件**：`ResultCode.TOO_MANY_REQUESTS` 早在枚举里，
  `server/README.md` 错误码表的"抛出方式"列写着"限流组件" —— 那个组件本仓没有。
- **三条既有约定同时指向"不该写在应用里"**：`infra/README.md` 约定 4（限流在 `nginx/` 或
  网关层解决，**不要散落在各应用里**）、`0003`（限流阈值属**部署级配置**）、
  后端 **5 处**「`X-Forwarded-For` 可被伪造，不可作为鉴权或风控依据」。

### 决定性的一条被误读了

那 5 处注释说的是"应用层不能用它"。但**成立的原因不是"IP 不可信"，而是"应用无法判断
自己前面有几跳、该信哪几跳"** —— 直连公网的进程与两层 CDN 后的进程读到同一个头、
含义完全不同，应用无从区分，所以最保守的做法只能是一概不信。

**nginx 知道答案，因为它自己就是那个代理。** 所以：限流不是"不该做"，
而是**只有在这一层才可能做对**。在应用层按 IP 限流会是"伪造一个头即绕过"的**假开关** ——
比不做更坏，因为它看起来像有防护。

→ 因此**先向舰长汇报并让他选落点**（这是本轮唯一一次提问），舰长选**网关层**。

### 交付

```
infra/nginx/
├── README.md                        定位 / 部署 / 渲染 / 未验证声明
├── .env.example                     11 个部署级变量
├── conf.d/bluewhale.conf.template   zone + map + upstream + server
└── snippets/
    ├── bluewhale-real-ip.conf       真实 IP（**默认全注释**）
    └── bluewhale-proxy.conf         转发到后端的公共指令
scripts/verify-nginx-config.mjs      结构性自检（不需要 nginx）
```

**后端与前端零改动** —— 无新依赖、无新接口、无新权限码、契约不变、测试数不变。唯一改到的
后端文档是 `server/README.md` 错误码表的"抛出方式"列（`42900` 的来源从"限流组件"改成"网关"）。

四条设计要点：

1. **真实 IP 分三态**：前方有代理**必须**开 `set_real_ip_from`（否则所有客户端共用一个 IP，
   限流退化成"全局一个桶"，表现为"人一多就整片 429"，真攻击者毫发无损）；本机是边缘**绝不能**开
   （否则用可伪造的头覆盖真实 IP）；开启时只写自己那台代理。**两个方向配错都不报错**，
   这是整份配置里最危险的一段，因此校验脚本专门盯它。
2. **上报与查询共用 URI**（`POST /api/logs/client` 上报、`GET` 同路径查询）→ 只能用
   `map $request_method` 把非 POST 的 key 置空区分。依据是 nginx 源码
   `if (key.len == 0) { return NGX_DECLINED; }` —— 空 key 不计入。不这么做，查询会被上报配额挤掉。
3. **429 的形态**：`error_page 429` → 命名 location → JSON `{"code":42900,...}`，
   **刻意不带 `timestamp`**（nginx 拿不到 epoch 毫秒，`$msec` 是秒 + 三位小数；
   格式对、数值错比没有更坏）。前端**无需改动** —— 核查过 `readBody()` 容忍非 JSON
   （`client.ts:72-77`），429 在 `errors.ts` 里 `retryable === true`，上报通道随即指数退避。
4. **阈值全走 `.env.example`**（部署级配置）。默认值刻意给宽：上报 `20r/s`，
   而客户端默认 3 秒才 1 个请求 —— **宁可拦不住异常放大，也不误伤正常用户**（NAT 下大量真实用户共用 IP）。

### 校验脚本第一次跑就抓到两个问题

`verify-nginx-config.mjs` 补的是 `nginx -t` **查不到**的那类错（zone 名拼错、模板变量漏在
`.env.example` 外、envsubst 白名单漏项、网段配成 `0.0.0.0/0`）。首次运行报 2 项失败：

- **误报**：模板注释里字面写着占位符示意（`${...}`），被 `[^}]*` 的残留检查抓到了。
  → 把残留检查收紧为**变量形状**（`\$\{[A-Z][A-Z0-9_]*\}`），并改掉那句散文。
- **脚本自身的作用域漏了**：`$host` / `$remote_addr` / `$scheme` / `$proxy_add_x_forwarded_for`
  住在 `bluewhale-proxy.conf`（模板只是 `include` 它），而检查只扫了模板 → 假警报。
  → 改成在"渲染后的模板 + 两个 snippet"上查（那才是部署后拼出来的完整配置）。

再补**两个负例**证明它不是空转：改错 zone 名 → 命中"每个被引用的 zone 都已定义"；
把 `set_real_ip_from` 改成 `0.0.0.0/0` → 命中"没有把可信网段写成 `0.0.0.0/0`"。

> 还原负例时踩了一下：`bluewhale-real-ip.conf` 是**未跟踪的新文件**，
> `git checkout --` 恢复不了它 → 得手工改回。记下来：**负例要用备份文件还原，别指望 git**。

- 根级 `README.md` / `CONTRIBUTING.md` / `AGENTS.md` **符合** prettier 默认风格；
- `docs/` `server/` `scripts/` `infra/` 下的 md **本来就都不符合**（改动前就不符合），

→ 结论：这些目录的 md **没有格式化门禁**，改它们时按**现有手写风格**对齐即可。

## ADR-0028 上报限流的阈值标定与网关侧实测（本机）

承接 0027 的两条尾巴。舰长本轮提了两个问题（外加一个指路）：

> 1、这个 nginx 只有一些配置，能使用吗？`D:\tools\installer\nginx` 有安装包，可以拷贝过来
> 2、日志上报不应该限流吧？达到阈值就舍弃了？

### 问题 1：能使用吗 → 能，而且真跑了

**0010 达梦那句"开发机没有 XX"是我的默认假设被推翻的第三次。** 上一轮 0027 写「开发机**既无 nginx 也无 docker**」——`nginx -v` / `docker --version` 确实 command not found，但舰长指出本机有**安装包**。

把 `D:\tools\installer\nginx\nginx-1.20.1` **只读拷贝**到 `/tmp/bw-nginx/dist` 后：

- 基线 `nginx -t` **通过**（`syntax is ok` / `test is successful`）；
- 阈值压到 `2r/s burst 2` → 实测 `200×3 / 429×12`，响应体 `{"code":42900,"message":"请求过于频繁","data":null}`；
- **同一 URI 的 15 个 GET 全 200** → 0027 决策三（`map $request_method` 置空 key）**从推断变成实测**；
- 等 2.2s 再打 5 个 → `200×3 / 429×2`（桶按 `rate` 回填，不是"一次超限就长封"）；
- 默认值下 450 连续 POST → `200×216 / 429×234`，`error.log` 记 `limiting requests, excess: 3.000 by zone …`。

**顺带推翻 0027 的一条错误断言**：原文写「`limit_req zone=xxx` 引用不存在的 zone，`nginx -t` **只在启动时**才发现」。实测把 `zone=bluewhale_report_global` 改成 `…globalX` 后，`nginx -t` **当场**报 `[emerg] zero size shared memory zone "xxx"`。

→ 这是"**把工具想象得比实际弱**"，后果是 `verify-nginx-config.mjs` 的价值被自己高估了一格。已在 0028 与两处 README 改正。

### 问题 2：不该限流吧？达到阈值就舍弃了？

**不是"是/否"。两条都要答，而且第二条推翻了我自己的阈值。**

**（a）429 ≠ 丢弃。** `common-tools` 的 `BatchChannel`（`web/packages/common-tools/src/report/index.ts`，`BATCH_DEFAULTS = { batchSize: 20, flushIntervalMs: 3000, maxBuffer: 500, maxBackoffMs: 30_000 }`）：

- `flush()` 的 `catch` 分支把该批 `buffer.unshift(...)` **退回队首**，退避 `min(flushIntervalMs × 2^失败次数, maxBackoffMs)` —— **封顶 30s**；
- 只有退回去装不下的那部分才计入 `state.dropped`；`push()` 溢出时 `buffer.splice(0, overflow)` 丢的是**最旧**的一批。

⇒ **短暂超限 = 延迟；持续超限 = 丢最旧的一批。** 网关限流保护后端、客户端退避防止它变成丢数据，**两者互补，不是矛盾**。

**（b）真正错的是标定公式。** 0027 的 `.env.example` 写「20r/s …… 正常使用每 IP 每 3 秒才 1 个请求」—— 这把「**1 个客户端 = 1 个 IP**」当成了前提。NAT / 办公网出口 / CDN 回源下真实速率是 `N/3 r/s`，**20r/s 只够约 60 人**。

同时暴露 0027「未覆盖」里那条「按 IP 的 `limit_req` 挡不住**很多来源各打一点**」—— **没有任何一层在管总量**。

**病根：把"隔离"和"容量"压在同一个阈值上。** 隔离要按"最大的那个来源"标定，容量要按"后端能吸收多少"标定，两者数量级不同，压在一起只能是折中、两个方向都会错。

### 交付：两层限流

| 层 | key | 职责 | 标定依据 |
| --- | --- | --- | --- |
| 按 IP `bluewhale_report_per_ip` | `$bluewhale_report_key` | **隔离** | 最大的 NAT 出口 ⇒ `N/3 r/s` |
| 全局 `bluewhale_report_global` | 常量 `"bluewhale-report"` | **容量上限** | 后端能吸收的写入速率，**与人数无关** |

- `limit_req_zone $bluewhale_report_global_key …` + `map $request_method $bluewhale_report_global_key { default ""; POST "bluewhale-report"; }`；
- `limit_req` **允许在同一 location 出现多次**（实测确认，非查文档推断）；
- 阈值：`REPORT_RATE=100r/s`（≈300 个客户端共用一个出口）、`REPORT_GLOBAL_RATE=300r/s`（≈6000 条日志/秒）。

**全局桶最容易写错的形态是"语法完全合法"的**：key 写成 `$binary_remote_addr` → 退化成第二个按 IP 桶，而 `nginx -t` 仍报 `test is successful`。→ 校验脚本为此加了 5 条检查（含"POST 映射到常量而非 `$binary_remote_addr`"、"两个 zone 的变量名不同"）。

另加了 `limit_req_status`/`limit_conn_status` 的显式 `429`（**默认是 503**）—— 0027 已写，本轮实测复核。

### 脚本工程：EBUSY 逼出的 `--emit`

`spawnSync` 在本沙箱**禁止 Node 创建进程（EBUSY）**，与备忘里 `spawn git`→EBUSY 同源。→ 给 `verify-nginx-config.mjs` 加：

- `--emit <目录>`：渲染出 `conf.d/` + `snippets/` + 可 `-c` 的 `nginx.conf`（唯一改写是 include 根 `/etc/nginx` → 产物目录），打印 `nginx -t` 命令，**由 shell 手跑**；
- `--nginx <可执行文件>`（或 `BW_NGINX_BIN`）：先用 `spawnSync(bin, ['-v'])` 探路径可用性，**把"启动不了"与"配置错"分开报**。

另外补了「自定义 map 变量未被误替换（被吃掉 = 限流静默失效）」这条检查 —— 与 `envsubst` 白名单那条是同一个失效模式的两端。

### 压限流的坑（新）

**压限流必须有活的后端。** 首次压测一个 429 都没出、全是 502：`error.log` 时间戳显示 15 个 POST 从 08:29:15 拖到 08:29:46 —— **后端没起时每次连接被拒耗时约 2 秒**，把请求间隔拉成 0.45 req/s，低于 2r/s 阈值自然不触发。

→ 起一个常驻极简上游（`upstream.mjs`，回 `{"code":0,...}`），单请求耗时从 2s 降到 **1.4ms**；再逐个 `netstat` 确认两端都 `LISTENING` 才压。**已写进 0028 与 `infra/nginx/README.md`。**

### `infra/nginx/README.md` §5 状态翻转

由「**未在真实 nginx 上验证过**」改写为「**已在 nginx 1.20.1 上验证过**」，附 8 行结果表 + 复现命令 + 「仍未验证的」三条。

但仍保留一条硬约束：**首次部署前仍必须先 `nginx -t` —— 那是"部署位置那棵树"的检查，与本次验的不是同一棵树**（`snippets/bluewhale-real-ip.conf` 的三态、`conf.d/` 的 include 路径都与部署位置有关）。

## ADR-0029 种子口令不得有默认值（本机）

承接 0027「发现但未处理」里那条，也是 0026→0027→0029 这条链上第一个**安全问题**（前两个是架构与容量问题）。

### 先核链路：0027 记错了两环

0027 记的是「`AuthProperties` 默认值 → `LoginRequest` 的 `@Schema(example)` → `openapi.json` → `schema.d.ts` → **登录页默认值** → 生产包」。逐环复核后：

- 登录页口令的初值是**空串**（`useState('')`），**不是** `@Schema` 给的；
- `@Schema(example)` 只落在 **JSDoc 注释**里，**不进产物**；
- **真正把它带进包的是登录页第 120-127 行把两个口令印在页面上**（`<code>Admin@12345</code>`），而那一页被打进 `platform-portal` 的包。

`grep -ro` 在 `dist/assets/index-CcyZqBqW.js` 命中 **1 处**。

⇒ **照 0027 记错的链路去修（只改 `@Schema`），口令仍在包里。** 这个纠正写进了 0029 第一节。

### "默认口令"的真正危险

不是"开发机看得到"，而是 `AuthProperties` 的两个 `password` **有默认值** ⇒ **任何环境**只要开种子且不覆盖口令就得到一个**口令公开可查的管理员**。而 `application-mysql.yml` 的说明**恰恰教人这么开**。

### 修法：「拒绝启动」是唯一不骗人的信号

另两种做法都会骗人：

- "跳过种子" → 安静地不种，而运维以为有一个（症状推迟到第一次登录）；
- "给默认口令" → 就是要消灭的那件事本身。

`DefaultAdminSeeder` 新增 `requirePassword(property, username, password)`，并把两个校验**提到所有落库之前**：

```java
// 先校验、再落库：两个口令都齐了才开始写，避免"管理员种下了、审计员报错退出"的半成品状态。
requirePassword(SEED_ADMIN_PROPERTY, seed.getUsername(), seed.getPassword());
if (auditor.isEnabled()) { requirePassword(SEED_AUDITOR_PROPERTY, …); }
```

开发口令的**真值来源收拢到 `application-h2.yml`** —— 全仓唯一一处。

`DefaultAdminSeederTest` 用「**依赖全传 null**」钉住"先校验、再落库"的顺序：顺序一旦反过来，用例会立刻 NPE —— 而那正是要防的半成品状态。

### 前端那条：`import.meta.env.DEV` 门控 + 构建后 grep 产物

登录页的开发提示包进 `import.meta.env.DEV ? (…) : null`。**验证方式是构建后 grep 产物，不是读代码判断**，且**查三条**（口令片段 / 提示正文 / 提示首句）—— 只查口令的话，"涂掉口令"与"整段摇掉"看起来一样。

修后：`index-nvSIZGeb.js` 对 `83287|用于对照按钮显隐|开发环境已种子两个账号` **全部零命中**。

### 凭据副本收敛：`scripts/lib/seed-credentials.mjs`（新）

`scripts/README.md` 早就写着「凭据走环境变量、**脚本里不出现任何密码**」，而 **4 个脚本**都硬编码了它 —— **这条约定曾经名不副实**。新增共享模块（`parsePasswords` 朴素逐行解析两个 `password`、`resolvePassword` 环境变量优先且**读不到就抛错**），4 个 e2e 脚本改为一行 import。

**没有引 YAML 库** —— 只为读两个字段不值得加依赖。

### 刻意没做（写进 0029「发现但未处理」）

1. **4 个子应用 dev 账号的惰性字面量**：`password: import.meta.env.VITE_DEV_PASSWORD ?? "Admin@12345"` 会**留在生产包里**（字面量替换），但 `allowDevAutoLogin` 为 `false` ⇒ **从不被使用**，比登录页那条轻。干净修法要动 `common-api` 这个被所有子应用依赖的共享包，不宜在长回合末尾改 —— **修法已写明**：`devAccount?: …` + 各调用点用 `import.meta.env.DEV ? {...} : undefined` 构造。

## ADR-0030 组织树、成员归属与数据范围求值（本机）

### 起点：两张表「表、实体、Mapper 全在，却零引用」

`bw_auth_organization` 与 `bw_auth_rel_org_user` 在仓里**只到 Mapper 为止** —— 没有 Service、没有 Controller、没有种子。**两张表在真实环境里恒为空**。

由此得出一个决定了切片边界的观察：**"只读的组织接口"没有价值** —— 表恒空 ⇒ 读出来永远是空列表。所以写入路径与成员归属必须与读取一起交付。这一点用 `AskUserQuestion` 让舰长定了两件事：**切片 = 后端全量 + 数据范围接线**（前端管理页留到下一轮）、**种子 = 种一棵最小组织树**。

### 本轮的核心交付

`DEPT` / `DEPT_AND_CHILD` 从"**永远算不出**"变成**可精确求值**。这是 `0025` 留下的最后一处"只存不用"。

| 层 | 内容 |
| --- | --- |
| 组织树 | CRUD + 树 + **移动**（`PUT /orgs/{id}/parent`）+ 两道删除守卫 |
| 成员归属 | 挂 / 撤 / 分页 / 反查 + **主岗**（每人至多一个、不静默搬动、时态参与求值） |
| 求值接线 | `DataScopeService.applyOrgScope`：有有效主岗 ⇒ `precise=true` + `visibleOrgIds` |
| 种子 | 总部 > 研发部 > 前端组；`admin` 挂总部、`auditor` 挂前端组（都不传 `isPrimaryPosition`） |

计数：权限 **23 → 27**、审计动作 **+7**、错误码 **+2**（`40410` / `40919`）、契约 **35→43 路径 / 55→67 接口 / 85→100 模型**、后端 **161 → 174 例**。

### 抓到的真缺陷：移动只写了派生列，没落 `parent_id`

`OrganizationService.updateColumns` 原本只写业务列，**不含 `parent_id`**。于是移动之后：

- `code_path` / `org_level` / `full_name` 已指向新父级 ⇒ **数据范围已经搬家**；
- `parent_id` 还在旧父级下 ⇒ **树接口按它拼树，节点显示在原地**。

**两处都不报错**，界面上看到的层级与真实的数据范围各说各话。同一个坑还影响 `create` 的"同码复活"分支（一个曾被删掉的编码被重建时，新父级同样落不下去）。

**抓它的断言**是端到端用例里的「移动后**原父级的 `hasChild` 应当归 0`」——`hasChild` 正是按 `parent_id` 数出来的，它留在了 `1`。

这也顺带说明了为什么必须用**显式 `set`** 而不是 `updateById`：复活时"从某个部门下"变成顶级需要写 `null`，而 `NOT_NULL` 字段策略写不了 `null`。

### 单元/契约测试：`OrganizationApiTest`（13 例）

沿用 `ResourceApiTest` 的两条既有做法：**不加 `@Transactional`**（最要紧的几条验证的正是"库里真正留下了什么"）、**口令从 `AuthProperties` 读**（ADR-0029）。本类自建的用户用一次性常量 `TEST_USER_PASSWORD`，与被保护的种子口令不是一回事。

用例覆盖：派生列与 `parentId` 一致 → 移动重写整棵子树（含**原父级 `hasChild` 归 0**）→ 改名重写子树 `fullName` → 成环 40913 → 修改路径拒绝 `parentId` 40001 → 标志位只收 0/1 → 删除两码分开（40913 / **40919**）→ **同码复活且复活出来是空部门** → 主岗不静默搬动 + 每人至多一个 → 重复绑定不堆行 + 40410 → **DEPT_AND_CHILD 真求值（含停用后退回算不出）** → 过期归属不计 → 编码形状/父级不存在 → 审计员 40301 / 未认证 40100。

**第一版跑出 4 个失败**，其中 1 个是真缺陷（`parent_id`），另 3 个是**我的测试写错了**：`OrganizationSaveRequest.orgCode` 是 `@NotBlank`，修改路径**要求把这个不被修改的字段回传**（与资源、角色同形状），少传被 DTO 挡成 `40000`。

## 1 `common-api`：组织域 11 操作 + 用户两个子资源

**先把契约形状逐个核实**（不凭记忆），核出四处容易写错的地方：

- **7 路径 / 11 操作**：`orgs`（page/create）、`orgs/tree`、`orgs/{id}`（detail/update/delete）、

- **组织域没有 `memberType`**（角色那边必须有）—— 这张关系表只装用户，不存在"两种成员同号不同表"。

`AccessUserApi` 补 `organizations(id)` 与 `dataScope(id)`，长注释写明 **`precise=false` 是"往窄兜底"不是错误**。

**踩坑**：`tsc` 报 `TS6196` 两个操作类型别名未使用 —— 改用 `NonNullable<DataOf<…>>` 消掉一个、

## 2 `platform-admin`：第六个标签页「组织」

新文件 `src/pages/Organizations/index.tsx`（**1237 行**），含组织树、编辑对话框、移动对话框、成员对话框。

### 三条设计决策（都写进了 `README.md` 的"设计取舍"）

1. **树提供结构与导航，详情提供表单初值。** 起因是本轮实证的一个事实：
   **`OrganizationTreeNode` 与 `OrganizationVO` 不是子集关系** —— 树节点有 `children`，
   **没有** `hasChild` / `orgType` / `managerId` / `description` / 三个联系方式；详情有 `hasChild`。
   后果很硬：**直接拿树节点填表单，会把那几列渲染成空、保存时以空值提交** ——
   "我只改了个名字"会顺手清掉组织类型、负责人、描述与联系方式，**且不报错**。因此 `openEdit` 必须先 `detail(id)` 回查。
2. **编辑态不渲染上级选择器。** 后端对"`parentId` 非空且与原值不同"返 `40001`（与用户组 `parentId` 的判断相反）。
   渲染一个能改的下拉 = 给一个必然报错的开关。`toBody(form, isEdit)` 在编辑路径上**干脆不传 `parentId`**（不传与传 `null` 同义）。
3. **「是否主岗」是三态而不是复选框。** 服务端对"不传"的定义是"没有别的主岗则自动设、已有主岗则保持不变"。
   压成二进制会让"不勾"读成"明确要求不要当主岗" —— 那恰好是最容易误伤数据范围的一种读法。
   实现是 `PrimaryChoice = '' | '1' | '0'`。

另外两条：**组织表单里没有派生列**（层级/路径/全称由服务端算，不接受入参）；
**移动是独立入口**（重写整棵子树 ⇒ 子树上每个人的范围同时变），对话框里把这件事明说，
候选列表用 `selfAndDescendantIds` 剔除自身与后代 —— 判据用树自身的 `children`，
**不按 `codePath` 前缀重算一遍**（那等于把服务端的求值口径在前端抄一份，两份一分叉就会回来"界面允许但后端拒绝"）。

### 用户页补两个反查（`#189`）

`UserOrgsDialog`（只读，附"写入口在组织页"的说明）+ `UserDataScopeDialog`：
`visibleOrgIds` 的 **`null` 与 `[]` 显示成两句不同的话** —— `null` 是"这一档不是按组织划定的"，
`[]` 是"按组织划定了，但一个也没有"。这两个语义压成同一句话，界面就在说谎。

`ALL` 档位下 `primaryOrgId` 与 `visibleOrgIds` **刻意都是 null**（`selfSufficient()` 直接返回、不进 `applyOrgScope`）；
**无角色 ⇒ `scope=null` 但 `precise=true`** 也不是失败（"没有任何生效角色携带数据范围，按仅本人处理"那一支）。

### 权限归属（写进 README 的对照表）

组织**树**归 `auth:org:read` / 个人**归属与数据范围**归 `auth:user:read`，**两者不互相蕴含**。
后果是**方向安全的**：只有 `org:read` 的人能改结构却看不到谁在哪个部门；只有 `user:read` 的人能反查个人归属却看不到树。
审计员因此表现为"组织页 403、用户页三个反查照常可用"。

**`40301` 的线上形态是 HTTP 200 + `code=40301`**（业务码），前端走 `BusinessError` 分支，
显示的是服务端文案「缺少权限：auth:org:read」—— **不会经过 `errors.ts` 里 403 那一条**，
而它比裸 403 更有用：指名缺哪一个权限码。

## 13:35–14:0x 角色页数据范围下拉：去掉「CUSTOM」假开关

## ADR-0033 开发凭据只在开发构建里构造（本机）

### 起点：`0029` 留的第 1 条是**一句没有验证过的判断**

原文写着"4 个子应用的 dev 自动登录账号……字符串仍在包里"。这句从没被证实过 ——
按本仓的处理方式（**先辨真伪**），本轮第一件事就是把它**量出来**。

量它的办法本身成了交付物：新增 `scripts/verify-bundle-secrets.mjs` ——
从 `scripts/lib/seed-credentials.mjs`（口令的**唯一真值来源**）读两个口令，去扫各应用的 `dist`。
**脚本里不写口令**，所以口令一改、检查跟着改，不会静默失效。

**第一次跑就推翻了原话的一半**：

| 产物目录 | 修复前 |
| --- | --- |
| `platform-admin/dist` | 干净 |
| `platform-audit-console/dist` | 干净 |
| `platform-log-console/dist` | **命中** 种子管理员口令 ×1 文件 |
| `platform-event-console/dist` | **命中** 种子管理员口令 ×1 文件 |
| `platform-environment/dist` / `platform-portal/dist` | 干净（前者没有会话，后者是 `0029` 修掉的） |

### 那两个"干净"是**恰好**，不是设计

`platform-admin` / `platform-audit-console` 的 `DEV_ACCOUNT` 是模块级常量，唯一引用点落在
`if (!import.meta.env.DEV) { …; return; }` **之后** ⇒ 生产构建下 `DEV` 被替换成 `false`、
`if (true) { …; return; }` ⇒ 其后整段不可达 ⇒ 常量无人引用 ⇒ 被摇掉。
**把 `return` 挪个位置，同一份代码立刻泄漏。** 两个控制台正因**没有**那句提前返回
（它们把判断做进了参数），对象作为实参留在调用点，于是被原样保留。
各自文件里那句"生产构建不会启用"的注释 —— **是给生产说的，打包器并没有听见。**

### 改法

1. `ConsoleAuthOptions` 删掉 `allowDevAutoLogin`，只留 `devAccount?: DevAccount` ——
   **账号的存在即开关**；"允许自动登录却没给账号"变成**表达不出来的状态**；
   顺带把 `ensureSession` 的两个分支收成一个。
2. 四处调用统一 `import.meta.env.DEV ? {…} : undefined`（`common-api` 的示例注释也改了）。
   口径从"生产不会用到它"（读代码推演）换成"**产物里没有它**"（机器可判定）——
   换成后者才谈得上固化成检查。
3. 新增 `scripts/verify-bundle-secrets.mjs`（三条设计：口令不写在脚本里／**只输出计数不输出命中串**
   —— 否则检查自己就把口令打进日志／退出码即结论）。
4. 后端 4 个测试不再抄口令（见下）。

`AuthApiTest`（内联在登录 JSON 里）、`PasswordHardeningApiTest`（`loginAsAdmin` 内联）、

## 子应用单跑 + 开发账号自动登录的真机验证（本机）

### 为什么做这个

上一轮（`0033`）**改了这条路径的形状**（`devAccount` 只在开发构建里构造），
但它是**全仓唯一没有任何脚本覆盖的运行方式** —— 所有 e2e 都从基座 :3000 进去。
手上只有单测 + 产物扫描，"浏览器里到底登录了没有"没人验过。

### 新增 `scripts/verify-standalone-dev-login.mjs`

- **它自己判定后端在不在**（探 `/api/health`，判据 `code===0`），按对应的一套期望断言：
  在跑 ⇒ 断言**自动登录成功**；没起 ⇒ 断言**优雅降级、不白屏**。两种状态下都能跑、结论都算数。
- **不直接带目标网址启动 Chrome，而是先停 `about:blank`**：
  等附加上调试器、装好错误监听（`Page.addScriptToEvaluateOnNewDocument` 注入
  `unhandledrejection` / `error` 收集器）**再导航**。带网址启动有一段竞态 ——
  初始加载期的异常发生在我们挂上之前，而本轮要看的恰好就是那段。
- 四个应用跑哪几个验哪几个（没在监听的记"跳过"），可选传截图目录。

### 抓到并修掉一个**真缺陷**

两个控制台写的是 `void consoleAuth.ensureSession().finally(() => render())` ——
`finally` 返回的新 Promise 被 `void` 丢掉，而 `channel.login` 失败时**会抛**。
实测（后端没起）两个控制台各抛一条：

```
unhandledrejection: HTTP 502 Bad Gateway
```

**改成与 `platform-admin` / `platform-audit-console` 一致的 `try/catch`**：失败也渲染
（没有会话只影响右栏），但记一条 error。修后**零脚本层报错**。
`ensureSession` 自己只覆盖了"没给 devAccount"那一种失败，登录请求失败是没人管的。

### 脚本自身踩的两个坑（都记进备忘）

1. **判据选成了"布局外壳"**：最初给管理面选的 `ready` 是 `admin-tabs`、审计台是 `audit-identity`
   —— 两者**无条件渲染**，于是后端没起时它们照样在，脚本报出
   "后端没起却出现了鉴权内容"这种**假问题**。真正由权限决定的是**里面装的东西**
   （`admin-tab-users` / `audit-list-panel`）。**写断言前先问"这个元素在没权限时会不会也渲染"。**
2. **进程不退出**：只 `chrome.kill()` 不够 —— WebSocket 长连接把事件循环挂住，
   症状是"结论已经打出来了、进程迟迟不结束"，在流水线里表现为**超时**而不是那行结论。
   收尾要 `ws.close()` + 兜底 `process.exit`。顺带：`ws` 要声明在 `try` **之外**（否则 `finally` 取不到；
   踩过 `ws is not defined`，它把一次成功的验证变成了失败退出）。

另外把**报错分两类**：脚本层（未捕获异常/未处理的拒绝）**任何模式都判失败**；
网络层（`Log.entryAdded` 的 `source==='network'`）在后端没起时**属于场景本身**、只计数 ——
不分开的话后端没起时那几条 502 会把脚本永远染红。

### 顺带订正一处文档与事实不符

脚本头里写的后端启动命令 `mvn -pl sts-app/sts-app-server -am spring-boot:run` **跑不起来**：
`spring-boot:run` 是 CLI goal、会落到 reactor 里每个模块上，父工程 `sts-parent`
没有 main class ⇒ `Unable to find a suitable main class`。正解两步：
`-am install -DskipTests` 装上游进本地仓，再 `-pl sts-app/sts-app-server spring-boot:run`。
`verify-menu-permissions.mjs` / `verify-portal-auth.mjs` 的头注释一起订正，
`scripts/README.md` 硬性约束里补了这一条。**本地仓是 `D:/repository/maven`（不是 `~/.m2`）。**

### 校验

- 就绪模式（后端在跑）：四个应用**全部通过** —— `bw.session` 都已落盘（含刷新令牌）、
  日志台右栏 / 事件台右栏 / 管理面六个模块标签（身份 `userId=1 · 角色 1 个 · 权限 45 项`）/

## ADR-0035 独立运行时入口必须等 preamble 装好（本机，计划外）

### 现象

单跑验证第一轮跑红两条：`platform-event-console` / `platform-audit-console` **首屏白屏**，控制台报

    @vitejs/plugin-react can't detect preamble. Something is wrong.

而且**刷新一次就好** —— 这种"重试即消失"最容易当成偶发。

### 误判与对照

第一反应是"下沉改坏了。**没有回滚，而是只重启一个 dev 服务、其余三个保持热**：
只有冷的那一个失败、且稳定复现 ⇒ **与代码无关**。
教训：对"看起来像回归"的现象，**先做冷热对照再动代码**，代价一分钟。

### 根因

`common-config/src/vite.js` 的 `qiankunDevPreamble()`：为了让 qiankun 能 `eval` 执行，
把 React preamble 从**模块脚本**改成了 **async IIFE** ⇒ 丢掉"模块脚本按文档顺序求值"这条规范保证
⇒ 入口的 `import('…/src/main.tsx')` 与 `import('/@react-refresh')` **抢跑**。
dev server 冷热是两种环境：首次被访问才做依赖预构建 ⇒ 冷启动时 `@react-refresh` 明显慢、抢输。
只在**独立运行**时暴露（跑在基座里时中间隔了几跳，`@react-refresh` 反而先到），
所以之前所有"从基座 :3000 进去"的 e2e 都没见过它。

### 改法

preamble 脚把 IIFE 的 Promise 落到 `window.__bwDevPreambleReady`；
入口脚包一层 `(window.__bwDevPreambleReady ?? Promise.resolve()).then(() => {…})`。
**只在真的改写了 preamble 时才动入口**（`let converted = false` 门控），
正则锚在带 `/src/main.tsx` 的那一段 `<script>` 上。改的是共享片段 ⇒ 四个应用一起受益。
**结论写进备忘**：改启动路径后 e2e 必须先重启 dev 再跑。

## 顺带：三个老 e2e 脚本的收尾（结论已打出、进程不结束）

`verify-menu-permissions.mjs` / `verify-portal-auth.mjs` / `verify-audit-pipeline.mjs`
只做了 `chrome.kill()`，CDP 的 WebSocket 长连接把事件循环挂住 ⇒
**结论已经打出来了、进程迟迟不结束**，在流水线里表现为**超时**而不是那行结论
（这次是先把它误判成"脚本卡住"才查出来的）。
补：`let ws = null` 声明到 `try` 之外、`ws = new WebSocket(…)`、`finally { ws?.close(); chrome.kill(); }`、
`main().catch(…).finally(() => setTimeout(() => process.exit(exitCode ?? 0), 500))`。
改写用一次性脚本、每处替换强制 `once()`（命中必须恰好一次）——
第一次锚点 `"  try {\n"` 命中了 2 次（`waitForDebugger` 里还有一个），
换成 `"  try {\n    await waitForDebugger();"` 才唯一。改后三个脚本**3~5 秒**自行退出、结论全过。

### 校验

- 单测：admin 29 / audit 11 全绿；**全仓前端 549 例全绿**（common-tools 178 / common-api 73 /
  environment 182 / event 18 / audit 11 / log 28 / admin 29 / portal 30）。
- 两个包 typecheck + ESLint + Stylelint 零错；**六个应用 build 全过**；
  全仓 `pnpm -r lint` / `pnpm -r typecheck` 全 Done。
- 产物自检：`verify-bundle-secrets.mjs` 6 个目录 / 18 个文件**零命中**
  （开发账号搬到模块级 `createConsoleAuth({…})` 后仍被摇掉）。
- 真机：**四个应用全冷启动**下 `verify-standalone-dev-login.mjs` 一次通过；
  后端停掉的**降级模式**也全过；`verify-micro-frontend.mjs`（挂载 / 全局状态下发 / 三维 / HMR /
  无浏览器报错 / 无 4xx）全过；环境台 `verify-scene-switching.mjs` 冷启动全过。
- **未被掩盖的既有状态**：`verify-micro-frontend.mjs` 第 2b 步仍报"热更新未生效"（`0012` 的已知限制），
