# server — 后端工作区

Maven 多模块 · Java 21 · Spring Boot 4.1。包名统一 `com.bluewhale.sts`。升级决策与破坏性变更清单见 `docs/decisions/0008`。

后端**按业务域切分，不按前端的两端切分** —— 管理端与用户端操作的是同一批业务对象、同一套状态机，按端切成两套等于把领域逻辑复制两份，改一条规则要改两处，两边还会逐渐跑偏。两端差异由接口面隔离。详见 `docs/decisions/0001`。

## 一、模块结构

**依赖方向只能自上而下**，禁止反向、禁止跨层跳跃：

```
sts-app  →  sts-server  →  sts-components  →  sts-common  →  sts-parent
业务应用     可部署服务      通用能力组件        技术底座        依赖管理
```

当前**已落地**的模块（未列出的层尚未创建，见下方说明）：

```
server/
├── pom.xml                        聚合根 —— 只列模块，不做依赖管理
├── sts-parent/                    父 POM —— 依赖版本统一治理（零代码）
├── sts-common/                    技术底座层
│   ├── sts-common-basic/              统一响应 · 错误码 · 业务异常
│   ├── sts-common-web/                全局异常处理 + CORS + Web 自动配置
│   └── sts-common-db/                 MyBatis-Plus 配置（分页 / 乐观锁 / 防全表更新）
├── sts-components/                通用能力组件层（ADR-0019 首次落地）
│   └── sts-components-audit/          @Audited 注解 + 审计目标上下文（只提供类型，不装配 Bean）
├── sts-server/                    服务层
│   ├── sts-server-log/                日志域服务（客户端技术日志上报与查询）
│   ├── sts-server-track/              行为事件域服务（埋点上报、查询、按事件名聚合）
│   ├── sts-server-auth/               权限域服务（身份 / 访问控制 / 认证 / 鉴权）
│   └── sts-server-audit/              审计域服务（拦截器自动产生、只读查询、按动作聚合）
└── sts-app/                       业务应用层
    └── sts-app-server/                唯一可启动进程（装配 + 健康检查 + 接口文档）
```

| 模块               | 打包 | 职责                                                                                                             | 依赖                                                                                                            |
| ------------------ | ---- | ---------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------- |
| `bluewhale-server` | pom  | 聚合根，一次构建产出全部模块                                                                                     | —                                                                                                               |
| `sts-parent`       | pom  | 依赖版本与全局插件配置，不含任何代码                                                                             | `spring-boot-starter-parent`                                                                                    |
| `sts-common-basic` | jar  | `R<T>` 统一响应、`ResultCode` 错误码、`BusinessException`                                                        | **零依赖**                                                                                                      |
| `sts-common-web`   | jar  | `GlobalExceptionHandler`、CORS 配置 + 自动配置                                                                   | `sts-common-basic`、Spring Web（provided）、springdoc 注解、Bean Validation                                     |
| `sts-common-db`    | jar  | MyBatis-Plus 拦截器（分页 / 乐观锁 / 防全表更新）+ 自动配置                                                      | `sts-common-basic`、MyBatis-Plus                                                                                |
| `sts-server-log`   | jar  | 客户端**技术日志**的上报 / 分页 / 详情 / 链路 / 聚合                                                             | `sts-common-web`、`sts-common-db`                                                                               |
| `sts-server-track` | jar  | 客户端**行为事件**的上报 / 分页 / 详情 / 按事件名聚合                                                            | `sts-common-web`、`sts-common-db`                                                                               |
| `sts-server-auth`  | jar  | **权限域**：租户 / 用户 / 组织 / 角色 / 用户组 / 资源，认证（登录 / 登出 / 刷新）与鉴权（`@RequiresPermission`） | `sts-common-web`、`sts-common-db`、`sts-components-audit`（标 `@Audited` 用）                                    |
| `sts-server-audit` | jar  | **审计域**：拦截器自动产生审计记录、只读查询、按动作聚合                                                          | `sts-components-audit`、`sts-server-auth`（取操作人）、`sts-common-web`、`sts-common-db`                         |
| `sts-app-server`   | jar  | 可执行应用：装配各域服务、健康检查、`application.yml`                                                            | `sts-server-log`、`sts-server-track`、`sts-server-auth`、`sts-server-audit`、springdoc UI、H2 + MySQL + 达梦驱动（runtime）、Flyway |

> **为什么需要 `sts-app` 这一层**：`sts-server-*` 是"可部署的服务能力"，但**不是进程** —— 它们不知道自己的端口、数据源，也不知道要暴露哪些接口文档。必须有一个应用层把这些装配成一个能 `java -jar` 跑起来的东西。这层**只做装配，不写业务逻辑**：一旦出现业务代码，就该下沉到 `sts-server` 或 `sts-components`。
>
> **`sts-components` 层在 ADR-0019 首次落地**（`sts-components-audit`）。它成立的前提是
> 「一个类型被**两个**域同时需要，而下沉它不引入业务语义」：`@Audited` 由权限域（标注解）
> 与审计域（读注解）共用，谁依赖谁都会成环。刻意**不带 `-starter` 后缀** ——
> 该模块不装配任何 Bean，名字里的后缀是个承诺，不能随便给。
> 仍未创建的：文件、消息这类通用能力。依旧遵循「**模块按需创建，不预置空壳**」。

`sts-common-basic` 刻意保持**零依赖**：它处在依赖链最底层，任何引入都会扩散到全仓。

> **依赖"按需声明"的三个坑**（都是编译期看不出来、只在运行时炸的类型）：
>
> | 现象                                                   | 原因                                                                   | 处理                                          |
> | ------------------------------------------------------ | ---------------------------------------------------------------------- | --------------------------------------------- |
> | Mapper 扫不到、`SqlSessionFactory` 不存在              | MyBatis-Plus 的 starter 坐标没跟着 Boot 大版本走                       | Boot 4 用 `mybatis-plus-spring-boot4-starter` |
> | `ClassNotFoundException: PaginationInnerInterceptor`   | 3.5.9 起分页 / 防全表更新拦截器拆到了独立坐标                          | 显式引 `mybatis-plus-jsqlparser`              |
> | mysql profile 启动报 `Unsupported Database: MySQL 8.0` | Flyway 10 起各数据库支持拆成独立模块，`flyway-core` 只内置 H2 / SQLite | 显式引 `flyway-mysql`                         |
>
> 共同规律：**starter 不再传递引入全部能力，谁用谁声明**。详见 `docs/decisions/0009` 第 4 条。
>
> 还有一类更彻底的情况：**依赖根本不存在**。达梦就是如此 —— Flyway 官方没有达梦模块，
> 引什么坐标都不管用。这类问题没有"补一条依赖"的解法，见第六节与 `docs/decisions/0010`。

## 二、统一响应与错误码

所有接口返回同一形状：

```json
{
  "code": 0,
  "message": "成功",
  "data": { "application": "bluewhale-server", "status": "UP" },
  "timestamp": 1759999999999
}
```

**业务失败仍返回 HTTP 200。** HTTP 状态码描述的是传输层是否送达；业务失败（余额不足、重复提交）在传输层是成功的。若混用状态码表达业务语义，网关、CDN、重试中间件会把业务失败当成传输故障去重试，反而制造重复扣款一类的故障。前端统一判断 `code === 0`。

> **响应体里没有 `success` 字段，这是刻意的。** `R.isSuccess()` 标了 `@JsonIgnore`：Jackson 会把 `isXxx()` 视作 getter，不标注就会自动序列化出一个 `success` 键。多余字段本身无害，但会诱导前端写出 `if (res.success)` 这种与 `code` 并存的第二套判断标准，两套标准迟早不一致。`HealthControllerTest` 里有断言钉死这一点。

错误码为 5 位，编码规则 **HTTP 状态码(3 位) + 业务细分(2 位)**：

| 错误码  | 含义               | 抛出方式                                  |
| ------- | ------------------ | ----------------------------------------- |
| `0`     | 成功               | —                                         |
| `40000` | 请求参数错误       | `R.fail(ResultCode.BAD_REQUEST)`          |
| `40100` | 未认证或登录已过期 | 认证过滤器                                |
| `40300` | 没有访问权限       | 鉴权拦截器                                |
| `40400` | 资源不存在         | `BusinessException(ResultCode.NOT_FOUND)` |
| `40500` | 请求方法不被支持   | 框架                                      |
| `40900` | 资源状态冲突       | 重复创建、并发修改                        |
| `42900` | 请求过于频繁       | **网关**（`infra/nginx/` 的 `error_page 429`）—— **后端代码里不产生它** |
| `50000` | 系统内部错误       | 兜底处理，**不透出细节**                  |

**域内细分码从 `xx01` 起。** 上表里每类的 `00` 号是"通用码"，被各域共用；
某个域要表达更精确的语义时，占用同一 HTTP 类别下的 `01` 起的空位。
权限域（`sts-server-auth`）目前用到的：

| 错误码  | 含义             | 错误码  | 含义                   |
| ------- | ---------------- | ------- | ---------------------- |
| `40001` | 请求参数不合法   | `40104` | 令牌无效               |
| `40101` | 用户名或密码错误 | `40105` | 令牌已过期             |
| `40102` | 账号已被锁定     | `40106` | 会话已失效，请重新登录 |
| `40103` | 账号已停用       | `40301` | 没有该操作权限         |
| `40401` | 用户不存在       | `40901` | 用户名已存在           |
| `40402` | 租户不存在       | `40904` | 租户编码已存在         |
| `40403` | 角色不存在       | `40912` | 资源标识已存在         |
| `40406` | 资源不存在       | `40915` | 资源已被角色引用       |
| `40002` | 引用的关联数据不存在 | `40913` | 父子关系成环           |
| `40407` | 该角色未持有此资源 | `40916` | 角色仍被成员持有       |
| `40408` | 该角色未授给此成员 | `40917` | 系统内置角色受保护     |
| `40409` | 组未包含此成员   | `40918` | 用户组仍包含成员       |
| `40919` | 组织仍包含成员   | `40920` | 引用的租户已停用       |
| `40921` | 自己所在的租户受保护 | `40302` | 该操作仅平台级可用     |

> **`40900` 段不再悬空**：此前没有 `DuplicateKeyException` 处理器，
> 任何唯一键冲突（并发下"先查后写"挡不住的那一次）都落进兜底、对外回 `50000`
> —— 责任方归错、监控算进可用性、前端当故障重试。现已由
> `GlobalExceptionHandler` 翻成 `409`。**它不是用来替代"软删复活原记录"那条正解的**，
> 而是并发下的第二道防线；精确原因应由业务代码**主动**判重返回域内码（如 `40912`）。
> 文案刻意不透露哪张表哪一列（同兜底处理器不透异常信息）。

> 这样分段的直接好处：`40101` 一眼看出是"认证问题、责任在调用方"，
> `40904` 是"唯一性冲突"，`50000` 才是"服务端故障"。
> 反面例子是参照实现 `SystemTerminator`：它把认证错误放在 `004xxx` 段，
> 其中 `004000` 与公共 `PARAM_ERROR` 撞码，同一串数字在两层含义间摇摆。

### 在业务代码里怎么用

```java
// 成功
return R.ok(data);
return R.ok();

// 业务拒绝 —— 抛异常，交给 GlobalExceptionHandler 统一翻译
throw new BusinessException(ResultCode.NOT_FOUND, "用户不存在");
throw new BusinessException(ResultCode.CONFLICT);   // 用枚举默认文案
```

**不要在 Controller 里手动 `try/catch` 再 `return R.fail(...)`** —— 那会把异常处理逻辑散到每个方法里，`GlobalExceptionHandler` 就没意义了。

日志级别是**有意区分**的：业务异常记 WARN（它是预期的拒绝，不该触发告警），未预期异常记 ERROR 并带完整堆栈。两者都用 ERROR 的话，告警会被正常业务拒绝淹没，最终没人再看告警。

## 三、模块内部如何组织

模块间按**业务域**切分，模块内按**特性（feature）**分包：

```
com.bluewhale.sts.log                    ← sts-server-log，包名用业务域（不带 server）
└── clientlog/                           ← 特性包
    ├── ClientLogController.java             接口层
    ├── ClientLogService.java                应用层
    ├── ClientLogMapper.java                 数据访问
    ├── ClientLogEntity.java / *VO.java      模型
    └── ...                                  约十个类，尚未到拆分阈值
```

**为什么不用 `controller/` `service/` `repository/` 作顶层分包**：改动一个功能要跨四个包来回跳；更要紧的是包之间没有任何边界——谁都可以从 `controller` 直接调 `repository` 绕过业务规则，编译器和评审都拦不住。按特性分包后，特性包本身就是天然的模块化候选点，将来拆服务只需整个包搬走。

单个特性超过约 10 个类时，再在其内部按 `domain` / `application` / `infrastructure` 细分。

### 日志域的几条硬规则

| 规则                                | 原因                                                                                                                                                                |
| ----------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **逐条校验，不整批拒绝**            | 一条畸形数据若能让整批 500 条全被拒，客户端日志会成片丢失，且丢的正是"出事那一刻最需要的那批"。信封级问题（`app` 为空、批次超限）才整体 400 —— 那是调用方写错了代码 |
| **超长截断而不是丢弃**              | 超长的通常是消息夹带整段响应体，丢弃等于丢掉"这里出过事"这个事实，截断至少保留开头                                                                                  |
| **级别解析不兜底成 `INFO`**         | 把非法值悄悄变成合法值，上游的拼写错误就永远暴露不出来。识别不了 → 该条计入 `rejected`                                                                              |
| **排序用 `serverTime` + `id` 双键** | 同一毫秒内的多条记录若只按时间排序，翻页时顺序不稳定，会出现"某条在第 1 页和第 2 页都出现"                                                                          |
| **`clientTime` 仅作参考**           | 客户端时钟不可信；排序、时间窗、统计一律用服务端接收时间                                                                                                            |

**技术日志与审计日志是两条管道。** 本模块处理的是技术日志（排查故障用：量大、短保留、可采样、可丢弃）。审计日志（谁在何时对哪个资源做了什么）走另一条管道，且**权威来源必须是后端拦截器** —— 这些事实前端根本不知道，客户端上报的内容也不可信。见 `docs/decisions/0004` 与 `docs/decisions/0019`。

**行为事件**（`sts-server-track`）：回答"用户做了什么"，用于漏斗与留存分析。它与技术日志的差别不是"换个名字"，而是**逐项相反**：事件**不可采样**（采样会毁掉漏斗）、契约**极稳定**（改名即历史数据断裂）、量级高一到两个数量级。因此它是独立模块、独立表、独立接口前缀（`/api/events/client`），只在传输通道那一层与日志共用实现。见 `docs/decisions/0011`。

**审计日志**（`sts-server-audit`）：三条管道里**唯一不由前端产生**的一条，回答"谁在什么时候对什么做了什么"。它此前长期停在"已设计未实现"，2026-10-12 落地，见 `docs/decisions/0019`。至此**三条管道全部落地**，且各自独立模块独立表 —— 这正是那句"内容不同 ⇒ 独立模块独立表、通道相同 ⇒ 复用"的检验结果。

### 日志域 / 事件域的鉴权与归属（ADR-0026）

> **这一节记录的是一处曾长期存在的静默泄漏。** 日志域（V1）与事件域（V2）建立时**权限域还不存在（V3）**，
> 此后没有回头补 —— 两个模块的 `src/main` 里 `RequiresPermission` **一次都没出现过**。
> 根因不是"忘了写"，而是 `AuthInterceptor` 的规则是**白名单反着写的**：
> **方法或类上没有 `@RequiresPermission` 就一律放行**（"未声明权限的接口 = 公开接口"）。
> 于是任何能发查询请求的人，读到的就是**全部租户**的日志与事件。修复前的实测：
> `GET /api/logs/client` 与 `/api/events/client` 返 `200 code:0`，而 `/api/audit/logs` 与 `/api/auth/users` 返 `40100`；
> **不带令牌上报一条，就能不带令牌把正文原样读回来。**

| 规则                                                                 | 原因                                                                                                                                                                                                    |
| -------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **上报公开、查询鉴权 —— 这是分类，不是遗漏**                          | 登录页出错时也必须能上报：未登录 ⇒ 无令牌 ⇒ 若要求鉴权则**最需要诊断的那批日志发不出来**。上报内容本来就整体不可信，加鉴权不会让它变可信。故 `POST /api/logs/client`、`POST /api/events/client` **刻意不加注解**，其余 7 个 `GET` 全部 `@RequiresPermission` |
| **新域前缀 `log:client` / `event:client`，登记在 `AuthPermissions.ALL`** | 该常量类是**全仓权限标识的唯一登记处**，不只是 `auth` 域的常量集合 —— 种子 `bw_auth_resource` 由它建出，凡经过 `@RequiresPermission` 的接口都必须在此登记，**没有第二个地方可放**。域前缀跟着**被访问的对象**走，不跟模块走。**与它并列的是 `AuthPublicEndpoints`**（**不参与权限判定**的端点唯一登记处，`decisions/0052`）—— 两者是同一张纸的两面：一个登记"谁要权限"，一个登记"谁不要"，且后者由 `PublicEndpointRegistryTest` 对着框架映射表**双向核对** |
| **三个读权限刻意不合并**                                             | `auth:audit:read`（合规追责）/ `log:client:read`（排障）/ `event:client:read`（产品运营）是**三种读者**；合成一个码的后果是**一次授权把三种数据一起给出去**，事后收窄只能改后台配置                                                       |
| **归属只取服务端会话**                                               | 写入用 `AuthContextHolder.currentTenantId()`（未认证返 `null`，上报必须照常入库）；读取用 `AuthContextHolder.require().getTenantId()`（能走到这里必然已认证；真未认证说明有人绕过 Web 层直接调服务，**抛错比返回全库数据正确**）。`bw_client_event.user_id` 是**上报方自己填的、可伪造**，**不是归属依据** |
| **租户条件恒定加上，不做成可关形式**                                 | 写 `eq(列, 值)` 而非 `eq(条件, 列, 值)`。可关的形式留的是"忘了传租户就查全量"的口子，失败方式是**多看到数据** —— 不报错、结果还更完整。这条与 `decisions/0022` 的"停用角色仍产生权限"同族：**开关存在，判定那一侧必须读它** |
| **聚合走的手写 SQL，参数必传、不给默认值**                           | `countByLevel` / `countByEventName` 显式加 `long tenantId` 并写进 `WHERE`。只改 wrapper 忘了它，症状是"**总数对、分布图是全库的**"                                                                              |
| **详情跨租户返 `404` 而非 `403`，且"不存在"与"不是你的"同码**         | `403` 等于**承认"这条记录存在"**。实现上先按主键查、再比对租户（而不是带租户条件去查），这样"存在但不给你看"在日志里可区分，事后能回溯越权尝试                                                              |
| **`tenant_id` 可空，NULL 语义 = "对任何租户都不可见"**               | 可空是必须的（登录前上报拿不到身份，`NOT NULL` 会让登录前上报直接失败）。**列表 / 聚合 / 详情三处一律不可见** —— 无法判断匿名日志属于哪个租户，展示给"当前租户"等于把**别的租户**的匿名日志一并展示出去，而登录页日志里可能带着用户输入的用户名，**宁可不显示、不可错显示** |
| **历史数据不回填**                                                   | 库里从未记录过归属，**任何回填值都是编造的，而编造的归属比查不到更危险**。日志是短保留期数据（默认时间窗 7 天），自然过期即可。真要保留是**部署决策**，用环境侧一次性脚本，**不要写进版本迁移**（写进来会让所有环境的"未知归属"被同一句 `UPDATE` 变成同一个租户的数据） |

> 本模块因此新增了对 `sts-server-auth` 的依赖（同 `sts-server-audit`）：**依赖权限域是语义上的必然** ——
> 要问"当前是谁"，就要用会话；方向是单向的，**权限域不依赖日志 / 事件域**。
> 前端的 401 是**漏接**而非缺实现：宿主在 `createMicroAppProps` 里**恒带 `auth`**，两个控制台只是没读。
> 见 `docs/decisions/0026`。

### 审计域的几条硬规则

| 规则                                                                             | 原因                                                                                                                                                                                    |
| -------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **没有写接口、没有写方法、没有 `deleted`、没有 `update_*`**                      | 不可篡改**不靠权限保护，靠结构上做不到**。`POST /api/audit/logs` 返回 `40500`；前端 SDK 的 `AuditApi` 同样只有三个读方法                                                               |
| **显式 `@Audited`，不自动拦所有非 GET**                                          | 自动拦会把登录 / 上报 / 健康检查全记进去，审计表被自己的上报灌满；而且 **HTTP 方法推不出"做了什么"**（`PUT` 既可能是改邮箱也可能是重置口令）                                          |
| **查询（`GET`）不记审计**                                                        | 审计记的是**变更**。要记"谁看了敏感数据"必须另起一条管道与另一张表（量级与保留期都不是一个数量级）                                                                                      |
| **审计拦截器 order 必须小于鉴权拦截器**（`WebInterceptorOrder.AUDIT = -100`）    | Spring 的 `HandlerExecutionChain` 只对**成功执行过 `preHandle`** 的拦截器回调 `afterCompletion`。排在鉴权之后 → 鉴权失败时审计永不执行 → **"越权尝试"这类最该留痕的记录静默丢失** |
| **`GlobalExceptionHandler` 每个 handler 都要 `ResponseOutcome.markFailure`**     | `afterCompletion` 收到的 `exception` **恒为 null**，而本仓"业务失败仍返回 HTTP 200" —— 两条加起来等于"失败看不出是失败"。漏调不报错，只让那一类失败被记成 `SUCCESS`                  |
| **写审计走 `REQUIRES_NEW`**                                                      | 业务事务回滚时审计不能跟着回滚 —— 而"操作被拒绝"恰恰最需要留痕。异常处理必须在**调用方**（self-invocation 会让 `@Transactional` 静默失效）                                            |
| **三套标识不可混用**                                                             | 资源 `auth:user`（`AuthResources`）≠ 权限码 `auth:user:create`（`AuthPermissions`）≠ 动作 `auth.user.create`（`AuthAuditActions`）。把资源填成权限码 → 按资源过滤永远查空且**不报错** |
| **只有服务端时间；匿名不产生审计**                                               | 审计不由客户端产生，故不存在双时间戳问题。匿名请求无操作人可归责，且公网扫描会灌满表；**已认证但无权限的必须记**（有明确操作人，且那正是最该留痕的一类）                              |
| **可见性由服务端决定，不由请求方决定**（ADR-0025）                              | 租户**无条件**强制为当前登录者；`operatorId` 只是"在可见范围内进一步收窄"，只有数据范围合并为 `ALL` 时才生效，否则被整体忽略。详情跨租户返回 **404 而非 403** —— 后者等于承认"这条记录存在"。此前两条查询连租户条件都没有，持 `audit:read` 者可读到别的租户的记录 |
| **`AuditRecorder` 写库失败只记 WARN，不重试、不外抛**                            | 接受"极少数记录会丢"：记审计失败不能连累业务响应                                                                                                                                        |

> **`sts-components-audit` 刻意不带 `-starter` 后缀** —— 它只提供 `@Audited` 注解与 `AuditContext`，
> **不装配任何 Bean**；真正装配拦截器的是审计域。名字里的后缀是个承诺。
>
> **一处已记录的同层依赖**：`sts-server-audit` → `sts-server-auth`（只读 `AuthContext` 与权限码，
> 不调用其服务）。与 `architecture/后端分层与依赖方向.md` 的"同层 ✗"不符，理由与触发条件见 `docs/decisions/0019`。

### 权限域的几条硬规则

`sts-server-auth` 是本仓第一个"从表到接口"完整闭环的服务，设计取舍见 `docs/decisions/0016`。

| 规则                                                               | 原因                                                                                                                                    |
| ------------------------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------- |
| **表前缀 `bw_auth_`，主键 `BIGINT` 自增**                          | 与 `bw_client_log` 同一形态；对外稳定标识交给各表的 `*_code` 业务编码                                                                   |
| **逻辑删除统一 `deleted`：0 正常 / 1 已删除**                      | 由 `@TableLogic` 承接，零配置。参照实现里不同表的 0/1 含义相反，是必须修掉的缺陷                                                        |
| **用户名在租户内唯一**（`uk(tenant_id, username)`），不是全库唯一  | 多租户下不同租户可以有同名账号                                                                                                          |
| **口令只存哈希，出参永不包含任何口令字段**                         | `UserVO` 手写逐字段映射，而非"把实体拷一遍"——后者会让实体新增字段自动泄露到响应里                                                       |
| **不区分"账号不存在"与"口令错误"**                                 | 都回 `40101`。区分开来等于提供一个账号枚举接口                                                                                          |
| **先验口令、再透露账号状态**                                       | 锁定 / 停用等提示只在口令正确后给出，否则同样构成信息泄露                                                                               |
| **认证（401）与授权（403）分开**                                   | 前端据此决定"跳登录页"还是"提示无权限"                                                                                                  |
| **刷新令牌只存摘要 + 轮换 + 重放检测**                             | 已作废的 jti 被再次使用即视为泄露，撤销该用户全部刷新令牌                                                                               |
| **口令有效期由策略决定，且只有一个写入方**（`decisions/0045`）     | `bluewhale.auth.password.expire-days` 默认 `0` = 不启用（不追溯存量、登录不重算寿命）。落库只在 `PasswordChanger#assignNewPassword`，建号 / 重置 / 自助改密三个入口都经过它。**登录与刷新两处都要检查** —— 只在登录查是不够的：刷新令牌轮换、每次续 7 天，一直别登出就**永不生效**。**失败的检查不得留副作用**（作废旧令牌排在全部校验之后），否则过期的用户反复刷新会把令牌烧掉 —— 那是"失败的请求留下的痕迹"，与"成功动作撤销会话"是两件事（`decisions/0046` 收窄了这里原本顺带举的"重置后自愈"）。判断**先看策略有没有开**：关掉就是谁也不过期，不靠清数据（`updateById` 静默跳过 null，"清"是个不会落库的动作）。过期的人**自己改不了密**（改密接口要会话）⇒ 文案指向管理员重置口令那条真路 |
| **凭据变更即撤销会话；作废令牌只有一处实现**（`decisions/0046`）   | 换口令（自助改密 / 管理员重置）撤销该账号**全部**刷新令牌，落点在 `PasswordChanger#change` 末尾 —— **不在调用方**：判据是"两个调用方取值不同的才是调用方的语义"，而撤销两边一致 ⇒ 放在调用方就是两份实现（本轮修掉的正是"一份写了、另一份漏了"，漏的那份是管理员重置：**换了一把锁、门还开着**）。`SessionRevoker` 是作废令牌的唯一实现（单个 / 全部两种粒度，`revoked` 与 `revokedAt` 一对一起写），`AuthService` 不再自己写这两列。撤销排在那次变更的**最后一步**（强度 / 防重用没过 ⇒ 会话一个都不动），且**重复撤销不推进撤销时刻**（撤销时刻只能被写一次）。**停用 / 锁定 / 删除刻意不撤销** —— 它们是**当前状态**，续期时读得到，靠校验不靠清理；锁定那条另有一层：触发它不需要任何凭据，顺带清会话就把"猜错 5 次口令"变成一次远程踢人 |
| **登出是两条路径，各一个语义**（`decisions/0047`）                 | `POST /api/auth/logout` 撤请求体里指明的**那一个**会话（请求体**必填** ⇒ 它不再需要任何身份）；`POST /api/auth/logout-all` 撤**当前用户**的全部会话（无请求体，`AuthContextHolder.require()` 定死作用域、不接受任何参数）。判据：**一个动作如果"省略它"会得到更重的后果，那它不是可省略的 —— 它该有名字**；此前"不传请求体"= 撤销全部，于是**危险动作成了省略的默认值**，而未认证时还会"什么都不做却返回成功"。`logout-all` **不需要权限码**（能登录就该能踢掉自己的会话；挂上权限码会让没被授权的用户永远清不掉自己名下的会话，而那正是他怀疑账号被人登着时唯一能自救的动作），**不记审计**（不改变任何凭据、对象只有操作者自己）但记一条 `log.info`。**撤销他人的会话不在这条接口里**，是另一条管理接口 |
| **建号按租户「默认角色」自动授予**（`decisions/0049`）             | `bw_auth_role.is_default` 从建表起就在、注释原文是"是否默认角色（**新用户自动授予**）"，写入 / 入口校验（只收 0/1）/ 契约 / VO / 种子全齐，**唯独"读它去授予"那一步没写** —— 本轮把它接上（同一件事在 `0022` 决策 11 里被写成"会被判定链路读取"，在 `RoleSaveRequest` 与 `api/README.md` 里被写成"只存不用"；**旧文不回改**，那句当时的前提是假的）。它是**租户级**的：查询 = `WHERE tenant_id = ? AND is_default = 1 AND status = 'ENABLED'`，所以"由租户决定"**不需要在租户表上再加开关**（`bw_auth_tenant.allow_register` / `allow_add` 就是两个反面教材：有列、有契约、有写入、有回显，**但没有任何逻辑读它、界面上也没有开关**）。**停用的默认角色自动退出默认集合** —— "默认角色"的语义是"新账号的起步配置"，停用的角色不该是任何人的起步配置；想暂时不给新账号角色应当**取消勾选**（停用会连带让所有已持有者一起失去权限）。**复用 `RoleMemberService.bind`**，不另写一套插入（upsert / 复活软删行 / 清同键冗余行只能有一份实现）；授予与建号**同一事务、异常照抛**（"建好了却没有起步角色"与"本来就没配"在界面上同形）。**不记审计**（那条路已有 `auth.user.create`，逐条记 `grant_member` 只会产出 N 条无处区分的记录）但记一条 `log.info`。`UserVO.defaultRoleNames` **只在建号响应里非空**，**空数组与 `null` 分指两件事**（`[]` = 这次没授出去任何东西、界面要据此提示下一步；`null` = 本条接口不表达这件事）。**改配置只影响之后新建的账号**，不追溯已建账号 |
| **口令强度只有一个来源**：`PasswordPolicy`（DTO 不再判 `min`）     | 两处都判会让"口令太短"返回两种错误码；提示语只能来自 `describe()`，配置改了它跟着改（`decisions/0020`）。`bluewhale.auth.password` 下的**所有**策略参数都从这一个类读 —— 强度 / 防重用范围 / 有效期（`decisions/0045`）                                  |
| **口令不得与当前或最近 N 条历史重复**（`40914`）                   | 历史存"被替换下来的旧口令"（append-only，**不继承 `BaseEntity`**），但校验时**当前值也要比** —— 否则"重置回原口令"会静默成功             |
| **设置口令只有一条实现**：`PasswordChanger`                        | 三件事（口令强度 → 防重用 → 写历史+裁剪）此前是 `UserService` 的私有方法 ⇒ 第二个入口出现时唯一可行的做法是复制粘贴，而三份复制品会在某次修改里只改到两份。建号只用得到第一件（`assertStrength` 单独公开），"设口令要同时更新哪几列"由 `assignNewPassword` 一处负责 —— 少写算法标识或更新时刻都不报错，只是静默失准（`decisions/0043`）。**撤销旧会话也挂在它身上**（`decisions/0046`）：换口令自带"清掉该账号全部刷新令牌"这个后果，所以下一个换口令的入口不写也不会漏 —— 这正是把它从调用方移进来的理由 |
| **自助改密必须验旧口令、且失败要计数**（`PUT /api/auth/password`） | 本接口不挂权限码（能登录就该能改自己的口令），所以旧口令是**唯一**能证明"本人"的手段 —— 不验的话一次访问令牌泄露就是一次账号接管。失败计数走 `LoginAttemptRecorder`，否则改密接口就成了绕过登录锁定去猜口令的后门。成功后**撤销该用户全部刷新令牌**（含当前会话）：改密的动机常常正是"怀疑口令泄露了"，留着别人的刷新令牌等于让改密变成一次无害的仪式（`decisions/0043`）。撤销由 `PasswordChanger#change` 执行，因此**管理员重置也适用**（`decisions/0046`） |
| **`mustChangePassword` 只标记、不拦截**                            | 管理员重置置 1、本人改密归 0，`MeVO` 与 `UserVO` 各暴露一份（前者供前端引导改密，后者让管理员能看到"他改了没有"）。服务端**不**因此拒绝登录 —— 那会形成死锁（进不去就没法改密），而"只发受限令牌"要为此引入一套令牌能力分级。它是给客户端的**引导事实**，不是强制的安全边界 |
| **口令变更状态必须随登录/刷新响应下发**                            | 前端基座走的是**登录 / 刷新**那条路 —— `GET /api/auth/me` 在前端只有一个调用点（"后台改了权限之后重新拉一次身份"），一条普通登录流程里根本不会走到它。只让 `MeVO` 返回它等于这一列**永远到不了用户面前**；刷新这条尤其不能少，否则用户按一次 F5 引导就没了。三个出口（`LoginVO` 覆盖登录与刷新、`MeVO`）取值同源，只在 `issueTokens` / `currentUser` 两处落一次（`decisions/0044`） |
| **登录锁定按指数退避**：第 n 次 `5 × 2^(n-1)` 分钟、封顶 24 小时   | 固定时长等于给攻击者一个恒定的重试预算（每 15 分钟来 5 次，成本不随次数上升）；`lock_level` 记"被锁过几次"，只有登录成功才清零          |
| **失败计数必须独立事务**（`LoginAttemptRecorder`，`REQUIRES_NEW`） | 登录失败抛 `BusinessException` 会回滚整个登录事务 —— 计数写在同一事务里就一起消失，**锁定永不生效**。这是 `decisions/0020` 修掉的一处静默缺陷 |
| **锁定状态必须出参可见**（`lockedUntil` / `lockReason` / `lockLevel`） | 只落库不暴露时，运维看到"锁定至明天"却不知道原因、也不知道是第几次，**无从判断退避在不在生效**                                           |
| **资源标识（权限码）创建后不可修改**                               | 改一个码等于让所有持有旧码的授权**静默失效** —— `rel_role_resource` 的行还在，却再也匹配不上任何 `@RequiresPermission`。要改走"新建 + 迁移"（`decisions/0021`） |
| **资源标识的形状由 DTO 注解承担**，与 `AuthTaxonomyTest` 同一正则   | 注解会进契约、前端能在提交前拦下；而 `AuthTaxonomyTest` 只看得见**常量**，看不见库里被手写进去的畸形行                                     |
| **删除资源有两道拒绝**：有子资源 `40913` / 已被角色引用 `40915`     | 资源是逻辑删除，删掉后判定 JOIN 自动排除它 ⇒ 若干角色**静默**少一项权限。与租户一致：不提供藏起来的级联                                    |
| **软删的行仍占着唯一标识 ⇒ 重建时复活原记录**                      | `uk_bw_auth_resource_code` 建在 `resource_code` **单列**上、不含 `deleted`，而 MP 的查询自动追加 `deleted = 0` 看不见它 → insert 撞键 → 落到兜底的 `40900`（`ADR-0024` 之前是 500，那时读作"50000 系统内部错误"）。**六个这样的列连同各自的答案见「唯一编码列与它们的软删语义」**（`decisions/0021` · `0056`） |
| **资源树对脏数据降级**：孤儿与成环按根返回，不丢弃也不报错         | 该表允许被直接写（`DefaultAdminSeeder` 即如此）；环会让对象图自指、序列化不到底。**看得到但层级不对，好过整棵树打不开**                    |

| **搜索的模糊匹配跟着等值一起区分大小写**（`decisions/0066`） | 搜索走的是后端 `LIKE '%kw%'`（七个入口：用户 / 用户组 / 租户 / 角色 / 资源 / 客户端日志，外加**只给 API 用**的组织分页接口；形状都是 `Query.keyword` + 一串 `LIKE` 条件用 `or()` 连起来（`0067` 之后那串条件由 `KeywordLike` 生成），如 `UserService#page`），**前端不做本地过滤**（但**不是"全都 trim 了"**：五个管理页提交时 trim、客户端日志页逐键上送**一次都不 trim**、组织页没有搜索框 —— 见 `decisions/0068`）。`LIKE` 的敏感性**同样由列排序规则决定** ⇒ `V8` 把它也改了。**实测**（两台引擎、同一段 SQL）：存 `admin` 时 `LIKE '%ADMIN%'` 在 `utf8mb4_0900_ai_ci` 上是 **1**、在 H2 与 `utf8mb4_0900_as_cs` 上是 **0** —— **改前两个 profile 在搜索上本来就是分歧的**，`V8` 把两边**对齐到"敏感"那一侧**（顺带结果，此前没人写过）。**决定：沿用列排序规则、跟着等值走**（它已经一致且零方言差异；反向做成不敏感要在这些入口显式 `LOWER()`、**h2 与 mysql 都得写**，等于故意再造一处"两方言必须人工同构"；而结果也不误导 —— `admin` 与 `Admin` 本就是两个账号）。**代价是用户可见的**：MySQL 上输入 `ADMIN` 不再搜到 `admin`。**加搜索框时不要在前端做本地过滤**（会造出第二套语义，前端没有守卫能发现）；**断言搜索匹配/不匹配的用例必须含"换个大小写搜不到"那一支**（只断"搜得到"的话，不敏感的实现也会绿），照跨 profile 的 `SearchMatchApiTest` 写 |
| **搜索关键词进 `LIKE` 之前必须转义，且转义符写在 SQL 里**（`decisions/0067`） | `keyword` 此前是**原样**拼进 `LIKE '%…%'` 的，而 MyBatis-Plus 的 `like()` 只做 `%+值+%`（`SqlUtils#concatLike` 的字节码里没有任何转义，`SqlLike` 也只有 `LEFT` / `RIGHT` / `DEFAULT`）⇒ **输 `%` 匹配全表、输 `_` 匹配任意单字符**。**实测**（绑定参数，复现 MP 的传参形态）：存 `abc` / `a%b` / `a_b` / `aXb` 时，现状输 `%` 得 **4**（全表）、输 `a_b` 得 **3**（`a%b`、`a_b`、`aXb` 全中）。**⚠️ 量这个不能用 SQL 字面量探针**：H2 的 `MODE=MySQL` 会把字面量里的 `\` 当转义符吃掉（`'a\%b'` 到 `LIKE` 时已经是 `'a%b'`），量到的是**解析器**而不是 `LIKE`。**决定：转义 `%` / `_` / 转义符自身，并把转义符写成 `ESCAPE '!'`** —— 收在 `sts-common-db` 的 `KeywordLike`（`pattern()` 出实参、`condition("列")` 出 `列 LIKE {0} ESCAPE '!'`），7 处搜索 / 15 个列条件全改用它。**转义符刻意不是反斜杠**：反斜杠是 `LIKE` 的**默认**转义符，靠它就等于又把"转义到底生不生效"交给数据库默认值代答 —— 实测 MySQL 开 `NO_BACKSLASH_ESCAPES` 后 `\%` **静默失效**（用户输自己完整的登录名反而搜不到、不报错），而 `ESCAPE '!'` 在 H2 / MySQL / MySQL+`NO_BACKSLASH_ESCAPES` 三格里全对（同 `0065` 的处置：把这件事写进 SQL，别依赖默认值）。**也刻意不"禁止这两个字符"**：`org_code` / `resource_code` / `username` 的形状里本来就允许下划线。`OrganizationService` 的两处 `likeRight(codePath, prefix)` **不在射程**：`code_path` 是"各级**主键** + 斜杠"（`#pathOf`，形如 `/1/5/`），只有数字与 `/`。**有机械守卫**（`scripts/verify-like-escaping.mjs`，零前置、进 `guards` job）：`src/main/java` 里**不许再有裸的 `like*`**（白名单只登记 `code_path` 那两处，**且逐条核对条数** —— 照 `0055`「只钉一支等于没钉」，实测"改掉两处里的一处"会红），带 `LIKE` 的 SQL 片段**同一行必须有 `ESCAPE`**。**断言"搜得到"的用例必须配一个只差一个字符的陪跑行**（只断"搜得到"的话，通配符泄漏的实现也会绿），照跨 profile 的 `SearchWildcardApiTest` 写 |
| **关键词的规范化（吃掉两端空白）只有一个真值来源**（`decisions/0068`） | 七个搜索入口此前分两种口径：组织 / 角色 / 用户组走各自**私有**的 `normalize`（`null` 进 `null` 出、全空白也出 `null`、否则 `trim()`），用户 / 租户 / 资源 / 客户端日志直传给 `KeywordLike.pattern()`（只判空）。两种口径对 `null` 与**只含空白**的处置一致，**唯一的分叉是两端带空白** ⇒ **同一条关键词在组织域搜得到、在用户域搜不到**（`SearchKeywordTrimApiTest` 两条同形断言，改前用户域**红** / 组织域**绿** —— 这就是"不一致"的现场证据）。**决定：规范化收进 `KeywordLike.pattern()`**（后端是权威边界 —— API 调用方与将来的别的客户端都不走前端那层），**调用方一律直传 `query.getKeyword()`，不要在 service 里再 trim 一遍**；吃掉**两端**、**不吃中间**（`LIKE '%…%'` 下前后空白不承载任何区分能力，只能造成"在某些页面上搜不到"；而 `a b` 里的空格是关键词的一部分，删掉就变成搜另一个词了）；`null` 与只含空白 = 不过滤（与改前两种口径都一致）。**"前端已经 trim 了"不能当契约用**：实测五个管理页在提交时 `trim()`、**客户端日志页一次都不 trim**（逐键上送、连提交中间态都没有）、**组织页根本没有搜索框**（刻意只有树视图）—— `0066` / `0067` 里"六个搜索框"那句不准确，以此处为准。前端在**提交 / 发请求时** trim，**不要在 `onChange` 里** trim（逐键上送的框会把用户刚敲的空格当场吃掉，值与光标都会跳）。**断言"两端空白被忽略"的用例要同时钉"只吃两端、不吃中间"**（只写前者的话，一个把空白全删掉的实现也会绿），照跨 profile 的 `SearchKeywordTrimApiTest` 写 |
| **精确匹配的过滤值（`eq`）进 SQL 之前也必须规范化**（`decisions/0069`） | 过滤值（`status` / `app` / `traceId` …）是 `eq` 精确匹配的，而各域写库前都过了一遍规范化 ⇒ **库里的值不会带两端空白** ⇒ `?status=%20ENABLED%20` **永远**匹配不到任何行（差异不承载区分能力）。取值分**三形态**：① **枚举归一**（角色 `status` / 资源 `resourceType` / 用户组与角色成员 `memberType`，走 `Xxx.parse`）—— **已健壮**，`parse` 内部就是 `equalsIgnoreCase(value.trim())` 且顺带归一大小写，**别把它换成 `trim`**（那是功能退化）；② **纯 trim**（组织 `status` / `orgType`、角色与用户组 `category`、资源 `parentCode`，走本域私有 `normalize`）—— 也健壮；③ **只判空**（用户 / 租户的 `status`，加上日志 / 事件 / 审计三域各 5 列：`hasText` 或 `!= null && !isBlank()` 之后**把原值**交给 `eq`）—— 两端带空白时一条也匹配不到，这是本轮统一掉的 **20 处**。**那处内部不一致**：三域的聚合统计走**手写 SQL**，判空是 Ognl 的 `<if test="app != null and app != ''">`，而同一请求的列表走 Java 的 `hasText()`（`isBlank`）—— 两者对 **`"   "`** 的判定**相反**（前者"给了值" ⇒ `AND app = '   '`、后者"没给" ⇒ 不过滤），症状是**同一个响应里「总数 3、各级别之和 0」**。**决定：真值来源收进 `FilterValue.text()`**（`sts-common-db` 的 `...common.db.query`，与 `KeywordLike` 并列）：`null` 进 `null` 出、否则 `trim()`、空则 `null`（= 不过滤）；20 处取值统一成"**先取局部变量、再判 `null`**"—— `eq(条件, 列, 值)` 的「值」是**无条件求值**的，写成 `query.getX().trim()` 空值时会当场 NPE（本仓已踩过多次）；**手写聚合 SQL 必须与 lambda wrapper 共用同一个局部变量**（`countByLevel` / `countByEventName` / `countByAction`），各算一遍的症状是"总数对、分布是全库的"，判空口径不同时更是"总数 3、各级别之和 0"；**`KeywordLike.pattern()` 内部也调它** —— "两端空白怎么处理"只有一个实现。`level` 那处的 `toLowerCase` **不下沉**（那是"该列存小写"的**列比较语义**，如资源域的 `method` 往反方向归一）。**`hasText` 不参与过滤条件**（它只服务条目校验与 `firstNonBlank`）。**有机械守卫**（`scripts/verify-filter-values.mjs`，零前置、进 `guards` job）：`src/main/java` 里 `.eq(...)` 的条件**不得**用 `hasText(...)` 或内联的 `query.getX().isBlank()`，三个手写聚合方法的实参**不得**是 `query.getXxx()`。**加过滤值时的写法**：`String x = FilterValue.text(query.getX());` 再 `.eq(x != null, Col::getX, x)`。**未答**：达梦未实测（历史上的另两条 —— 枚举归一、写入值 —— 已分别由 `0070` 与 `0071` 关掉） |
| **枚举列的过滤值归一成标准写法，自由文本的**不**归一**（`decisions/0070`） | **分界线是"这一列有没有一个可以用完的取值表"**，不是"名字看起来像不像枚举"。**枚举列**（全仓只有这五个列名： `status` / `resourceType` / `memberType` / `level` / `result`，其中 `status` 被四个域共用）走 **`FilterValue.enumValue(query.getX(), Xxx::parse, Xxx::wireName)`** —— 先吃两端空白，再 `parse` 认标准 写法（`enabled` → `ENABLED`），**认不得就按原样比**（**绝不退化成"不过滤"**：`?status=EANBLED` 拼错时若 静默返回全部，调用方以为自己筛过了，比报错危险得多）。**自由文本**（`app` / `traceId` / `namespace` / `sessionId` / `eventName` / `userId` / `deviceId` / 审计的 `action` / `resource` / `targetId` / `operatorName` / `orgType` / `category` / `parentCode`）走 `FilterValue.text(...)`，**沿用 `0065` 的 "区分大小写"、一个字都不归一**（换个大小写就是另一个字符串，归一它是篡改意图）。**`orgType` 是最容易走错 的一处**：名字像枚举，但写入时只 `normalize`（不校验取值）⇒ 取值集不存在 ⇒ 它是自由文本。**为什么归一 是"修正"而不是"篡改"**：`Status` 这一个枚举同时喂给用户 / 租户 / 组织 / 角色四个域的 `status` 列，各域 自己决定时 `?status=enabled` 在角色域搜得到、在另外三个搜不到（前端**四个管理页都没有 `status` 筛选框**， 界面上看不出区别）。**对枚举列再写一个私有 `normalizeXxxFilter` 是错的**（那正是 `0070` 消掉的四个实现）。 **新加枚举时补一个 `parse`**：大小写不敏感、认不得回 `null`，不兜底成某个默认值。**不让枚举类实现公共 接口**（`enumValue` 收两个方法引用，否则 `sts-common-db` 会变成各域枚举的共同依赖方向）。**有机械守卫** （`scripts/verify-filter-values.mjs` 规则 4）：五个枚举 getter **只能**作为 `FilterValue.enumValue(...)` 的 第一个实参出现；**给这五个 `Query` 加非过滤用途会让它报红 —— 那是提醒你更新白名单，不是让你忽略它**。 |
| **写入侧的过滤列也要过同一关**（`decisions/0071`） | 读取侧归一的那一半在这里补齐。**判据是"读侧会不会拿它做精确匹配"，不是"它看起来像不像编码"** —— 会，写入就必须过同一关；只归一读取侧是**空转**（库里存 `" myapp "`、读侧把 `?app=myapp` 规范成 `myapp` ⇒ 一条也匹配不到，归一反而制造假阴性）。**射程四组**：日志 `app` 与条目级 `namespace` / `traceId` / `sessionId`、事件 `app` 与条目级 `userId` / `deviceId` / `sessionId`（改前原样入库或只 `truncate`）、用户与租户两域 `status` 的 **`update` 路径**（`create` 走 `resolveStatus` 归一、`update` 原样入库 ⇒ 同一个字段两条路径两副面孔）。**`status` 那一组重一档：写入的值就是读者要看的那个值**（`AuthService` 判 `Status.ENABLED.wireName().equals(...)`）⇒ 传个小写的 `enabled` 会让**那个账号 / 整个租户登不进来**；租户域那条"不可停用自己所在租户"的自锁判据也按字面量比 ⇒ **启用被读成停用（`40921`）**。**写法**：`truncate(FilterValue.text(x), n)`（**先 trim 再截断**，反过来时一长串空白会把内容切光）；`status` 先 `FilterValue.text(request.getStatus()) != null`（不传 = 不改这一列）再交给本域 `resolveStatus`，**判据拿归一后的值比**。**`resolveXxx` 刻意不与 `enumValue` 合并**：读侧"认不得按原样比（空集）"与写侧"认不得就报错"是两种取向，合了迟早串味。**不给 DTO 加 `@Pattern`**（那会把"被归一"改成 400，而过滤侧认小写 ⇒ "能搜不能存"是更糟的不一致）。**不进射程的**：日志消息 / 路由 / 版本号 / IP 与名称 / 描述（不参与精确匹配）· **审计域的写入**（值取自 `@Audited` 注解与上下文，不由外部输入决定）。**有机械守卫**（`scripts/verify-filter-values.mjs` 规则 5）：`sts-server-log` / `sts-server-track` 里 `entity.set<App\|Namespace\|TraceId\|SessionId\|UserId\|DeviceId>(...)` 的实参必须含 `FilterValue`。**未答**：达梦未实测（该行原先还挂着 `email` / `phone` 那条，已由 `0072` 关掉） |
| **寻址列（`email` / `phone`）的判重口与写入口共用一个归一值**（`decisions/0072`） | 这两列的读侧不是过滤，是**判重**（`existsEmail` / `existsPhone` → 一次 `eq`）—— `0062` 已把"判重"与"过滤"归在**同一条判据**下，只是入口不同。它们此前住着**全仓最后一份"只判空、不 trim"的写入副本**（`UserService.blankToNull`，已删）。**两列的命运并不相同**：`phone` 上只有 `@Size(max=32)`（量长度）⇒ `" 13800138000 "` **一路进到服务层**，原样入库、判重拿带空白的字面量去比 ⇒ 库里已有 `13800138000` 时**判重通过**（NO PAD 的排序规则下两者不相等，`0065`）⇒ **同一个手机号能建出两个账号**；`email` 上有 `@Email`，而它**不 trim**（hibernate-validator `9.1.3.Final` 实测）⇒ 带两端空白的邮箱**在进服务层之前**就被判 40000，「格式不正确」—— 所以这一列改前改后**行为等价**，但**照样归一**（`@Email` 挡住空白是它校验格式的副产物、随时可被换掉；且同一件事不该有两种写法）。**决策：取一次 `FilterValue.text(...)` 存进局部变量，判重与 `entity.setXxx` 都用它** —— 只归一其中一侧不是"改了一半"，是**造出一种更隐蔽的不对称**（存 `13800138000`、比 `' 13800138000 '`）。`existsEmail` / `existsPhone` 因此不再自己判空白（入参已是归一值，`isBlank()` 那一支不可达），**归一刻意不放进它们内部**（那样两侧各 trim 一遍就又能分岔）。**不给 `phone` 加 `@Pattern`**（同 `0071`：那会把"被归一"改成 400）。至此"两端空白怎么处理"全仓**只剩一处实现**（`FilterValue.text`）。**存量值不订正**（本仓第一次回答"要不要 DML 迁移"）：无生产部署 · 边界不闭合（`0071` 的七个过滤列在更早窗口同样有脏值，按同一理由该一起修，那是跨 6 张表的独立一轮）· `TRIM(col) = ?` 会造出**第三种"相等"**（与 `0065` / `0066` 收口的口径冲突）。**有机械守卫**（`scripts/verify-filter-values.mjs` 规则 6）：`sts-server-auth` 里 `entity.set<Email\|Phone\|ContactEmail\|ContactPhone>(...)` 与 `existsEmail` / `existsPhone` 的实参，**含 `request.getXxx()` 且不含 `FilterValue` ⇒ 报红**（两侧都锚）。**未答**：达梦未实测 · ~~存量值未订正~~（**已由 `decisions/0073` 实测收口**：射程矩阵 21 列一次划完、唯一存量载体实测 0 脏行 ⇒ V9 不写）· 规则 6 看不到"先取局部变量、再直传原值" · 组织域的 `contact_email` / `contact_phone` 只有同形守卫、没有运行时断言 · `email` / `phone` 要不要归一大小写（本片把它钉住了：判重沿用 `0065` 的"区分大小写"） |

### 层级守卫（`40913`）的三支与断言矩阵

`HIERARCHY_CYCLE(40913)` 被五个域共用。**补它的断言要按"支"补，不按"域"补** ——
一个域里有三处 `throw`，只测了一处也叫"有断言"，而**漏一条分支与漏掉整个守卫，看起来一样绿**
（`decisions/0055` 就是从这个问法上找出的一格）。

| 域 | 自挂 | 挂到后代 | 删除守卫（仍有子节点） | 用例 |
| --- | --- | --- | --- | --- |
| 组织 `OrganizationService` | `:508` | `:514` | `:340` | `OrganizationApiTest` |
| 资源 `ResourceService` | `:189` | `:193` | `:231` | `ResourceApiTest` |
| 用户组 `UserGroupService` | `:429` | `:435` | `:230` | `UserGroupApiTest` |
| 角色 `RoleService` | `:455` | `:461` | `:254` | `RoleApiTest` |
| 租户 `TenantService` | — | — | `:119` | `TenantHierarchyApiTest` |

**租户一行只有一格是空位、不是缺口**：租户树没有"移动节点"这个动作，前两支没有对应代码
（与 `OrganizationService` 类注释里"与租户的差异"是同一件事）。

两条配套约定：

- **两支的文案断言要不同**（自挂说"自己"、挂到后代说"下级"）。这样"这条断言落在哪一支"
  在**正常运行下**就看得出来，不必靠扰动 —— 两条断言若都落在自挂分支上，后代那条会读到
  "自己"的文案而失败。
- **"删除守卫"那一支的用例要带反例**：删掉最后一个子节点之后，同一个父级必须立刻可删。
  少了这半段，一个"看到 `parentId` 非空就拒绝"的实现也能通过。

### 唯一编码列与它们的软删语义

DDL 里有**六个唯一编码列**，`uk_*` 一律**不含 `deleted`** ⇒ 软删的行仍然占着那个值；
而 MyBatis-Plus 给每条自动生成的查询都追加 `deleted = 0`，**常规判重看不见占位者**。
于是每个这样的列都必须自己回答一次："软删行还算不算占着"。**这张表是权威版本**（`decisions/0056`）——
代码注释里**不要数"第几处"**：那个数字此前停在"第四处（前三处：资源、角色、用户组）"，
而实际有六处；少掉的那两处，正是没人发现的那两处。

| 列 | 软删行还算不算占着 | 代码落点 | 用例 |
| --- | --- | --- | --- |
| `bw_auth_resource.resource_code` | **算** ⇒ 复活原行 | `ResourceMapper#selectAnyByCode` + `#restoreDeletedById` | `ResourceApiTest`「软删后重建同一标识」 |
| `bw_auth_role.(tenant_id, role_code)` | **算** ⇒ 复活原行（且清空授权与成员） | `RoleMapper#selectAnyByTenantAndCode` + `#restoreDeletedById` | `RoleApiTest`「软删过的编码可以复用」 |
| `bw_auth_user_group.(tenant_id, group_code)` | **算** ⇒ 复活原行（且清空成员与它持有的角色） | `UserGroupMapper#selectAnyByTenantAndCode` + `#restoreDeletedById` | `UserGroupApiTest`「软删后同码重建是复活原行」 |
| `bw_auth_organization.(tenant_id, org_code)` | **算** ⇒ 复活原行（且清空用户归属） | `OrganizationMapper#selectAnyByTenantAndCode` + `#restoreDeletedById` | `OrganizationApiTest`「同码软删重建」 |
| `bw_auth_tenant.tenant_code` | **算** ⇒ **拒绝**（`40904`） | `TenantMapper#selectAnyByCode` | `UniqueCodeReuseApiTest` |
| `bw_auth_user.(tenant_id, username)` | **算** ⇒ **拒绝**（`40901`） | `UserMapper#selectAnyByTenantAndUsername` | `UniqueCodeReuseApiTest` |

**前四行与后两行的分界不是偏好，是一条可以被检查的性质：复活是否安全，取决于那一行的删除守卫
有没有挡住活边。** 资源 / 角色 / 组织 / 用户组在删除时都拒绝了"仍被引用"（还有子节点 `40913`、
还有成员 `40915` / `40916` / `40918` / `40919`）⇒ 那条软删行必然是**没有活边的空壳**，
把它放回来不会让任何人多出一样东西。租户与用户不是这样：`TenantService#delete` 只拒绝
"仍有子租户"、**不拒绝"还有人"**；`UserService#delete` 只拒绝"删自己" ——
复活会把**一批人的登录与权限**一起放回来，而调用方以为自己只是新建了一个同名的东西。

两条配套约定：

- **"拒绝"那两处，两支给同一个码**（活行占着 / 软删行占着）。调用方要做的事完全一样（换一个值），
  与 `40920` / `40002` 那种"处置完全不同才分码"不是一回事；也**不**为软删那一支另写文案 ——
  它既不可操作，又把"软删"这个内部状态透给了调用方。用例断言的是**文案里点名了对象**
  （"租户编码" / "用户名"）：兜底那句"数据已存在或与已有记录冲突"也含"已存在"，
  只断言"已存在"就分不出这条断言落在哪一支。
- **没有唯一索引的列不许顺手一起挡**（`*_name` / email / phone）：索引不挡它们，
  库里本来就不认为它们唯一，软删之后自然等于释放 —— `UniqueCodeReuseApiTest` 有一条反例看着这件事。

**这个坑与"兜底码"是一对（下面这句是推断，不是实测）**：`40900` 那个处理器上线（`ADR-0024`）
之前，漏掉这一步的症状是 500 —— **显性故障，会有人去修**（资源 `0021`、角色 `0022`、
用户组 `0024` 三处都修在那个年代；组织 `0030` 在它之后，是照着前三处的形状补的）。
上线之后症状变成 `40900` —— **一个看起来完全正常的业务拒绝**，于是租户与用户两处
从头到尾没有一次"修这个坑"的射程覆盖到它们。换句话说：**兜底码让"缺失的判重"不再显形。**
它依然该有（并发下那一次拦截是真的，见 `DuplicateKeyAdviceTest`），
但不能拿它当"这一步做了"的证据。

哪些列是"开关"、谁在读它们。**这张表是权威版本**（`decisions/0054` 逐格核过并把它从 ADR 里迁了出来

> 会漏掉 wrapper 里的**方法引用** `Entity::getXxx`，而**判定链路的读取大量写在那里**
> （`getIsDefault()` 搜不到 `RoleMemberService` 里那句 `.eq(RoleEntity::getIsDefault, 1)`）。
> 同样不能靠列名、注释、邻接关系，**也不能抄上一条结论或上一份文档的背景** ——
> ADR 的背景写的是**决策前**的事实，而它会被后来的人当成现状读（`decisions/0054`）。

### `40002` 的每一处文案与它的读者

`PARAM_REFERENCE_MISSING(40002)` 的形状与别的业务码不同：**它是全仓唯一一个"一处判据、
多处 `throw`"的码**。每一处拦的都是同一件事（引用的东西不存在，或存在但放错了租户），
差别只在**文案点名了谁**。所以它值得的核对不是"按支拆"（每一处只有一支），
而是"每一处是否点名了正确的对象、是否都有断言"（`decisions/0057`）。

**计数刻意不写在节标题里**（`decisions/0039`：活文档不写会变的计数）。本节此前写的是"16 处"，
而 `0074` 新加的两处 —— `TenantService#resolveWriteTenant` 与
`OrganizationService#managerNameOf` —— **一次都没登记进来**，`0075` 逐个回溯源码才对齐。
要数就照着下面这张表数：**一行就是一个落点**。

**这张表是权威版本**（`〃` 表示"同上一个方法"）。

| 落点 | 文案点名 | 用例 |
| --- | --- | --- |
| `TenantService#requireReferencedTenant`（`#assertExists` / `#assertAcceptsNewData` 共用） | 租户 | `TenantReferenceApiTest` |

| `UserGroupService#bindMember` | 引用的用户 | `ReferenceMessageApiTest` |

**「读者分化」是 `0075` 加的一格，也是这一族第一次出现"同一个落点说两句话"。**
六处"引用的对象必须与容器同租户"的检查（`UserGroupService#assertSameTenant` 与
`#resolveParent`、`OrganizationService#resolveParent`、`OrganizationMemberService#requireSameTenantUser`、
`RoleService#resolveParent`、`RoleMemberService#assertSameTenant`）此前**各写一句自己的文案**，
而那句话对非平台级操作者是一个**先知**：他与"引用的 X 不存在"那一支的文案一比，
就知道"这个 id 确实是别家的一个真人"。现在这六处全部委托给
`TenantService#assertReferencedInSameTenant`，两句话由**它一处**生成：

- **平台级**（唯一能合法跨租户的人）拿到那句诊断原文 —— 他写错了租户与写错了主键，
  要去做的事完全不同（改租户归属 / 改 id）；
- **非平台级**拿到的是**与"引用的 X 不存在"逐字相同**的一句话（只差被带进文案的那个主键）。

判据是"**这位读者能不能对两种成因采取不同的行动**"，而不是"数据上是不是同一件事" ——
所以这不是"覆盖文案"的回潮：那一条管的是"同一个码在**同一类读者**面前说两件事"，
而这里两种读者的**处置能力不同**，本就不该被当成同一件事。`TenantIsolationApiTest`
第六节断的是"**两句话相等**"这条性质（不是某个字面量，所以措辞可以改而性质不许破），
另有一条对照断"平台级仍拿得到诊断、不许被一起收窄"。

**表中文案全部点名正确**，包括一处刻意的不对称：`ResourceService` 写的是父资源的
**编码**而不是主键（资源树的父子关系本来就以 `resource_code` 表达）。

两条配套约定：

- **断言要点到"哪个对象"，不能只点到"用户"两个字。** 同一个域里"引用的用户不存在"与
  "该用户与组织不属于同一租户"的文案**都含"用户"** ⇒ 只断两个字的话，两条支长得一模一样：
  换一支实现照样绿，而用例并不知道自己钉的是哪一支。既有那批断言断的是"租户"，
  钉的是"有没有点名放错租户"，与这条是分工、不是重复。
- **只断 `code` 的用例分不出"点在哪个对象上"。** 这个码**不携带**"是哪个引用错了"的信息，
  携带它的是文案。`OrganizationApiTest` 的父组织那条与 `RoleApiTest` 的授权资源那条
  此前只断言了 `40002`，两处的文案断言现由 `ReferenceMessageApiTest` 补齐，
  原用例保持不动（各钉一个维度）。

### `404xx` 的落点与它们的断言（十五处 + 跨租户一族 + 记录管道一族）

与 `40002` 恰好相反，这一族**一个码就是一个对象**（`40401` 用户 / `40402` 租户 / …），
所以"点名"这件事住在**枚举**里 —— 抛出点不写文案，也就写不出错的对象。由此两条规矩：

- **在抛出点覆盖文案 = 这个码在说两件事，没有例外。**（`0075` 之前这里写着"有一类覆盖
  是『同一个理由』，那类不算破坏这条规矩" —— **那条豁免是错的，已撤回**。）
  最早的一处是 `DataScopeService#resolve`（把"用户不存在"与"不属于当前租户"合成一句），
  `decisions/0074` 把它推广成**一族**：`TenantService#assertVisible(entityTenantId, code)`
  用 `code.getMessage() + "或不属于当前租户"` 统一生成文案。当时给的理由是
  "同一句话落在十几处落点上" —— 但**那句话与它要替的那句话不是同一句**：
  "东西真的不存在"那一支（`requireXxx` 里的 `entity == null`）说的仍是裸文案，
  于是同一个码在两条分支上给出**两句不同的话**，调用方比一下 `message` 就知道
  "这条记录确实存在，只是在别家" —— 而这正是覆盖文案原本要挡的那件事
  （`0025` 第 2 条）。现在**两条分支都用枚举里那句**：对看不见它的操作者而言它就不存在，
  所以只有一句话可说。要分处置就分码；要留成因就写进 `40002` 那句（见下面那节）。
  这条规矩由 `scripts/verify-notfound-messages.mjs` 机械守着；而"同一个 `requireXxx` 里
  交给 `assertVisible` 的码，必须与它自己那句'不存在'逐字相同"这一半由
  `scripts/verify-tenant-visibility.mjs` 守（`decisions/0076`）。
- **断言这一族断 `code` 即完整**（码就是对象）—— 与上面那节"只断 `code` 等于没核"
  **正好相反**。文案断言在这里另有用途：**证明同一个码的两条分支给的是同一句话**
  （`TenantIsolationApiTest` 第六节断的就是"两句话相等"，而不是"等于某个字面量"——
  于是措辞可以改，这条性质不许破）；一旦有人开始覆盖，它会先红。

**这张表是权威版本**（`decisions/0059` 补齐了此前没有断言的六处；`decisions/0074` 补了跨租户一族；
`〃` 表示"同上一个方法"）。

顺带记下公共码的一格：`ResultCode.NOT_FOUND(40400)` 的默认文案"资源不存在"**一次都没被用过** ——
三个读者（审计记录 / 客户端日志 / 客户端事件）全部自带文案，与上面那张表正好是两种相反的形态
（`40002` 的默认文案零使用是因为"每处都必须自己点名"，`40400` 的是因为"每个域都要说自己的对象"）。
它与 `AuthResultCode.RESOURCE_NOT_FOUND(40406)` 的文案**逐字相同**，靠码值区分
（前者是 REST 语义的"资源"，后者是 `bw_auth_resource`）。

**记录管道一族（`decisions/0077`）走的是另一格落点，与 `assertVisible` 不是一个东西。**
三条记录管道（审计 / 日志 / 事件）的读侧出口（`AuditLogService#detail`、
`ClientLogService#detail`、`ClientEventService#detail`）都调
`TenantService#assertRecordInCurrentTenant(recordTenantId, notFoundMessage)` —— 它**不接受任何**
"当前可见租户"参数（就取 `AuthContextHolder` 里的自己）、**没有"谁是平台级"这条分支可走**、
且`recordTenantId` 为 `null` 时**恒不可见**（未登录时产生的记录不属于任何租户，对**没有人**可见）。
两支（`null` / 不等于当前租户）**同码同句**，都抛公共 `ResultCode.NOT_FOUND(40400)`。

这与 `assertVisible` 是**两个 `null` 语义相反**的落点，别互相替换：
`bw_auth_resource.tenant_id IS NULL` = **平台级对象**（对所有人可见，`assertVisible` 直接通过）；
`bw_audit_log` / `bw_client_log` / `bw_client_event` 的 `NULL` = **不属于任何租户**。
把记录管道的出口接到 `assertVisible` 上 = 把未登录时的记录从"谁都看不见"翻成"平台级看得见"
—— 一次真的泄漏。分界是"**管理面 vs 观测面**"：`assertVisible` 的正当性来自**写侧能力**
（跨租户预配就是平台级的工作），而三条管道**没有写侧**。
"记录管道的出口必须过这一格"由 `scripts/verify-tenant-visibility.mjs` 的**规则 D** 机械守着
（它抛公共码，规则 A 那套"该表对应的 `404xx`"在这里无效）；落点**不写名字**，靠"方法体提到公共
`ResultCode.NOT_FOUND`"认出来，解析不出来就红。

### `401xx` / `403xx` 的落点与它们的断言

这一族的形状与上面两张都不同：问题不是"文案有没有点名"（`40002` 那种），也不是
"哪一处没断言"，而是**码本身有没有人抛**。把两个枚举（公共 `ResultCode` 与权限域
`AuthResultCode`）的 `401xx` / `403xx` 逐个回溯源码，结果是：**有落点的都断言了**，
而**七个码一次抛出点都没有**（`decisions/0060`）。

**这张表是权威版本**（`〃` 表示"同上一个方法"）。

| 码 | 落点 | 断言 |
| --- | --- | --- |
| `40100`（公共） | `AuthInterceptor#preHandle` | `AuthApiTest` · `AuditApiTest` · `DataScopeApiTest` · `OrganizationApiTest` · `ClientLogApiTest` |
| `40101` | `AuthService#login` × 3 · 〃 `#changePassword`（覆盖"当前口令不正确"） | `AuthApiTest` · `ChangePasswordApiTest` · `PasswordHardeningApiTest` · `SessionRevocationApiTest` · `TenantDisableApiTest` |
| `40102` | `AuthService#login` | `PasswordHardeningApiTest` |
| `40103` | `AuthService#login` | `SessionRevocationApiTest` |
| `40104` | `AuthService#refresh` × 3（其一覆盖"该令牌不是刷新令牌"）· `AuthContextHolder#require`（覆盖"当前请求未认证"） | `ChangePasswordApiTest` · `LogoutApiTest` |
| `40105` | **无** | — |
| `40106` | `AuthService#refresh` × 5 | `AuthApiTest` · `ChangePasswordApiTest` · `LogoutApiTest` · `PasswordExpiryApiTest` · `SessionRevocationApiTest` · `TenantDisableApiTest` |
| `40107`~`40110` | **无** | — |
| `40111` | `AuthService#login` · 〃 `#refresh` | `PasswordExpiryApiTest` |
| `40300`（公共） | **无** | — |
| `40301` | `AuthInterceptor#preHandle`（覆盖「`"缺少权限：" + required`」） | `AuthApiTest` · `RoleApiTest` · `OrganizationApiTest` · `ResourceApiTest` · `UserGroupApiTest` · `RoleMemberApiTest` · `DataScopeApiTest` · `AuditApiTest` |
| `40302` | `TenantService#assertCanCreateUnder`（非平台级建顶级租户） | `TenantIsolationApiTest` |
| `42900`（公共） | **无** | — |

七个零落点的码（`40105` · `40107`~`40110` · `40300` · `42900`）现在由
`scripts/verify-result-codes.mjs` 钉住：它们必须出现在那张脚本的 `UNUSED` 里并写明理由，
否则 CI 的 `guards` job 会红。三条值得单独说的：

- **"未认证"在实现里有两个码。** 入口（`AuthInterceptor`）抛公共码 `40100`，
  而 `AuthContextHolder#require()` 抛域码 `40104` —— 后者会从 `logout-all` / `me` /
  `changePassword` 这几条**公开端点自己拦**的路径上走到（登记在 `AuthPublicEndpoints`）。
  同一件事两个码，前端要认两个（现状：`platform-audit-console` 认 `40100`，
  `platform-admin` / 门户认 HTTP 401）。它**是有意的** —— `AuthService#logoutAll` 的注释
  点了 `40104` 的名、`LogoutApiTest` 有用例钉住 —— 但"要不要统一成一个"是产品决定，
  见 `decisions/0060` 的「未覆盖」。
- **`40104` 的那处覆盖正落在 `404xx` 那节的规矩上**：覆盖文案 = 这个码在说两件事 ——
  一处说"你给的令牌无效"，一处说"你没带令牌"。而后者已经有一个专门的码（`40100`）。
- **公共层的 `40300` 与 `42900` 一个读者都没有。** `40300` 被域码 `40301` 顶替
  （权限拒绝全走域码）；`42900` 是因为**限流落在 nginx 层**（`0028`），应用层不抛。
  两者都留作"公共层对外的语义"，当前没有任何代码会用到它们。

## 六、数据源与数据库迁移

数据源由 **profile** 决定，不是改文件：用哪个库是启动参数，显式出现在命令行与健康检查里。决策与踩坑清单见 `docs/decisions/0009`。

| profile          | 数据源                                  | 适用                | 数据                   | H2 控制台                                 |
| ---------------- | --------------------------------------- | ------------------- | ---------------------- | ----------------------------------------- |
| `h2`（**默认**） | `jdbc:h2:mem:bluewhale`（`MODE=MySQL`） | 开发、演示、CI 默认 | **进程内存，重启即失** | 开启 `/h2-console`（用户 `sa`，密码留空） |
| `mysql`          | `jdbc:mysql://127.0.0.1:3306/bluewhale` | 本地联调、**CI**    | 磁盘，重启后仍在       | 关闭                                      |
| `dameng`         | `jdbc:dm://127.0.0.1:5236`              | 信创环境            | 磁盘                   | 关闭                                      |

**默认必须是 h2** —— 它保证"clone 下来不装任何数据库就能跑"，`HealthControllerTest#defaultProfileMustBeH2`
里有断言钉住这一点（直接读 `application.yml`，与"本次运行的启动参数"无关）。

**但 h2 是开发便利，不是交付形态** —— `MODE=MySQL` 只是"语法尽量贴近"。
所以 CI 里有两个后端 job：`server` 跑默认的 h2，`server-mysql` 对**真实 MySQL** 跑同一套全量用例。
这条不是空开关：它第一次真跑就抓到 5 处**只会在换库时现形**的缺陷（其中 4 处的根因是
MySQL 默认的 `REPEATABLE_READ` 快照与"审计走独立事务"撞车）—— 见 `docs/decisions/0038`。

### 表结构怎么建：H2 / MySQL 走 Flyway，达梦走交付脚本

```
sts-server-log/src/main/resources/db/migration/
├── h2/V1__create_bw_client_log.sql       H2 方言
├── mysql/V1__create_bw_client_log.sql    MySQL 方言
└── dameng/V1__create_bw_client_log.sql   达梦方言（不由 Flyway 执行，见下）

sts-server-track/src/main/resources/db/migration/
├── h2/V2__create_bw_client_event.sql     H2 方言
├── mysql/V2__create_bw_client_event.sql  MySQL 方言
├── dameng/V2__create_bw_client_event.sql 达梦方言（不由 Flyway 执行，见下）
└── h2|mysql|dameng/V7__add_tenant_id_to_bw_client_event.sql   归属列 + (tenant_id, server_time) 索引

sts-server-auth/src/main/resources/db/migration/
├── h2/V3__create_bw_auth_tables.sql      身份 / 访问控制 / 会话共 12 张表
├── mysql/V3__create_bw_auth_tables.sql
├── dameng/V3__create_bw_auth_tables.sql
├── h2/V5__add_lock_level_and_password_history.sql     锁定层级列 + 口令历史表
├── mysql/V5__add_lock_level_and_password_history.sql
└── dameng/V5__add_lock_level_and_password_history.sql

sts-server-audit/src/main/resources/db/migration/
├── h2/V4__create_bw_audit_log.sql        审计流水表 + 5 个索引
├── mysql/V4__create_bw_audit_log.sql
└── dameng/V4__create_bw_audit_log.sql
```

> `sts-server-log` 除 `V1` 外另有 `h2|mysql|dameng/V6__add_tenant_id_to_bw_client_log.sql`（归属列 + 索引）。
> **`V6` 与 `V7` 必须分开两套号** —— 版本号全仓唯一，日志域与事件域各自都要加一列，不能都叫 `V6`。

> **版本号是"全仓唯一"，不是"每个模块各从 V1 开始"。**
> `spring.flyway.locations` 是全模块共享的 `classpath:db/migration/<vendor>`，
> 因此同一个 location 下出现两个 `V1` 会让 Flyway 在**启动阶段**直接失败：
> `Found more than one migration with version 1`。
> 事件表排到 `V2` 正是这个原因（日志域已占用 `V1`）。
> **新增建表脚本时取全仓当前最大号 + 1。** 详见 `docs/decisions/0009` 的「补充」章节。

- 迁移脚本由**领域模块自带**（谁拥有表结构谁写脚本），`spring.flyway.locations` 按 profile 指向对应厂商目录
- 各写各的**原生方言**，不追求一份通用 DDL —— 硬凑通用版只能取交集，MySQL 的列注释、存储引擎、字符集排序规则就全写不了
- 用 `flyway_schema_history` 表保证"只执行一次"，因此脚本里**不写** `IF NOT EXISTS`：那样会把"表已存在但结构不对"静默吞掉

```bash
# 新增表结构：追加脚本，不要改历史脚本
#   db/migration/<vendor>/V2__加个字段.sql
```

mysql profile 需要**先建好库**（Flyway 只建表、不建库）：

```sql
CREATE DATABASE bluewhale DEFAULT CHARACTER SET utf8mb4 COLLATE utf8mb4_0900_as_cs;
```

> 排序规则是 `_as_cs` 而不是 MySQL 默认的 `_ai_ci` —— 见上表「两个文本什么时候算相等」与
> `decisions/0065`。已存在的库不用重建，`V8__align_text_equality_collation.sql` 会把
> 13 张 `bw_auth_*` 表转过来。

**达梦没有 Flyway 支持**，该 profile 下 `flyway.enabled=false`，表结构走**交付脚本**：

```bash
BW_DB_PASSWORD=xxx bash scripts/init-dameng.sh     # 需要达梦客户端 disql 在 PATH 中
# 或由 DBA 直接执行 db/migration/dameng/V1__create_bw_client_log.sql
```

为什么不做自研 Flyway 扩展（约 300–400 行、全部绑定 Flyway 内部 API、升级即可能破损），
以及达梦在 DDL 上的方言差异清单，见 `docs/decisions/0010`。

> **迁移脚本一旦在真实环境执行过就不可修改。** `validate-on-migrate: true` 会因校验和不匹配而拒绝启动 —— 这是特性不是麻烦：迁移脚本是历史，改了历史就该新增一条，不是覆盖它。本地开发可以重建库绕过；有数据的环境必须追加新版本。

### 换到真实库后没有账号可登录

种子账号（`admin` / `auditor`）**只在 h2 profile 自动种**，这是有取舍的：

| profile            | 为什么这样定                                                                                                                     |
| ------------------ | -------------------------------------------------------------------------------------------------------------------------------- |
| `h2`               | 每次启动都是空库，**不自动种就一个账号都没有可登录** —— 而死锁在于"建账号的接口本身要求已登录"。种一套默认账号解开这个引导环     |
| `mysql` / `dameng` | 数据留得住，不需要每次补；而且**真实库不该被应用每次启动塞进一个固定口令的管理员**（默认口令写在 `AuthProperties` 里，等于公开） |

所以换库后要**显式种一次**，之后它就一直在了：

```bash
BW_DB_PASSWORD=<密码> java -jar sts-app/sts-app-server/target/sts-app-server-0.0.1-SNAPSHOT.jar \
    --spring.profiles.active=mysql \
    --bluewhale.auth.seed-admin.enabled=true --bluewhale.auth.seed-auditor.enabled=true
```

- 种子是**幂等**的（`ensure*` 语义：缺什么补什么、已存在就跳过），重复执行没有副作用
- `seed-auditor` **依赖** `seed-admin`：只读账号挂在 admin 种下的租户与资源上，少了 admin 它没有可挂的东西，开了也不生效
- 不想在任何库留固定口令的账号，就别开这两个开关 —— 用已有管理员账号调 `/api/auth/users`、`/api/auth/tenants` 建号

两个口令以 `AuthProperties.SeedAdmin` / `SeedAuditor` 的默认值为准，基座登录页的开发提示里也列了一份，**两处必须一致**。

### 三条必须先查的规矩

1. **新增会落库的字段前，先查一遍 MySQL 保留字。** `release`（发布版本号）是自然的领域命名，但 `RELEASE` 是 MySQL 8 的保留字，而 **H2 不认它** —— 同一个列名在 H2 上一切正常、在 MySQL 上 `ERROR 1064`。这是最难查的一类差异。
2. **别用 `@TableField` 把列名映射成另一个名字。** MyBatis-Plus 发现"列名与属性名不一致"会**自动补 `列名 AS 属性名` 的别名**，别名若撞了保留字照样报错。正确做法是让属性名与列名同构（`appRelease → app_release`，与 `traceId → trace_id` 一致），不产生别名。`ClientLogEntityMappingTest` 直接断言生成的 SQL 里不出现 `AS release`。
3. **新增字段也要查一遍达梦保留字 —— 两个库的结论不可互推。** `RELEASE` 是 MySQL 8 的保留字，达梦却完全不认它；反过来 `LEVEL` 是达梦的关键字（属非保留，可作列名），MySQL 也不管。查法：`SELECT KEYWORD FROM V$RESERVED_WORDS WHERE RESERVED='Y'`。`bw_client_log` 的 14 个列名已逐列核对过、无冲突，详见 `docs/decisions/0010`。审计表 `bw_audit_log` 的 16 个列名落地时也按同样口径核对过（`action` / `resource` / `result` 在 MySQL 8 **都不是**保留字）。

> 为什么这条要靠测试而不是靠跑用例？因为**默认跑在 H2 上，而 H2 不认这个保留字** —— 所有接口测试都会是绿的，直到换 MySQL 才炸。这类差异只能对生成物本身做断言。
