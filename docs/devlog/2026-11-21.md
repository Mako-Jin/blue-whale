## 三维王城 S4 接口层（第一批：契约 + starter + ERP 标杆 + 厅配置）

- **需求项**：把"每殿各吃一个异构接口、前端靠 dig 猜字段"改成"每服务一个 `/<前缀>/overview`"，
  先通一个标杆（户部 / ERP）再复制到其余 20 处。总纲 T4.1–T4.4、T4.6。
- **契约（T4.1）**：`docs/specs/overview-contract/README.md` + `overview.schema.json`。
  三个决定值得记：
  - **百分比只传比率**。S3 的 `formatPercent` 用"小于 1.5 就当比率"兜底，遇到真实的 0.8% 会显示成 80%；
    契约层定死 `0.82`，渲染层只乘一次 100，兜底逻辑不再有存在理由。
  - **三态 `live/stale/degraded`**。概览最坏的情况不是接口挂了（会白屏、会被发现），
    而是"牌上有数字、但数字是三天前的"。`stale` 强制带 `notes` 与上次时刻，前端必须标"陈旧"。
  - **降级也走同一形状**。404/500 由前端折成 `unreachable`，服务端降级也是一个 `OverviewSnapshot`，
    前端不必为失败写第二套解析。
- **后端 starter（T4.2）**：新增 `whale-sdk/whale-overview-sdk`（自动装配，注册进 `whale-sdk/pom.xml`）。
  - 接入成本＝实现 `OverviewProvider` + 配 `whale.overview.base-path`（示例 `/erp/overview`）。
    路径放配置而不是写死注解：服务一级前缀本来就不在 Java 里（REQ-ARCH-003 网关不剥前缀）。
  - **缓存键含租户** `service|nodeKey|tenantId`。少一段就是"A 租户的数发给 B 租户"，
    这类越权不报错、只表现为"数据看起来怪"。
  - **provider 在独立 daemon 线程池执行 + `Future.get(timeout)` + `cancel(true)`**：直接在请求线程跑
    provider，一旦里面有个没设超时的下游，会把 Tomcat 工作线程一起拖住；概览没有这个权力。
  - **失败不写缓存**：有上次成功快照 → 返回它并置 `stale`；没有 → `degraded` 空态。
    不缓存失败是为了让下一轮轮询自动重试，下游恢复最多晚一个周期。
  - **权限在控制器判定**（`UserContext.hasPermission`，与 `RequirePermissionInterceptor` 同口径，
    `super_admin` 放行），provider 拿不到请求头（它在别的线程）；块级裁剪用 `OverviewContext#hasPermission`。
  - **`overview.load{service,outcome}` 计数**：降级是静默失效高发区，必须有可告警的时序。
    Micrometer 挂在 `@ConditionalOnClass + @ConditionalOnBean` 的嵌套配置里，没有 actuator 的服务不受影响。

## 三维王城 S4 第二批：户部屏风页（列表 + 详情，T4.5）

- **需求项**：S4 的最后一块 —— 屏风里要能跑一张**真业务页**（筛选、翻页、看详情），
  并把上一批已下发但没人用的 `charts` / `links` 接上。总纲 T4.5。
- **为什么做成通用渲染器**：S5 有 9 殿 × 3 件套，每殿手写一张页，三周后就是 21 套各不相同的
  表格与分页逻辑。所以拆成两半：
  - `src/world/screenpage.ts`：取数 / 筛选 / 分页 / 详情 / 降级，一次做完；
  - `src/world/screenpages.ts`：按殿登记的配置（列口径、状态字典、详情字段、分录列）。
  接入第二张列表 = 加一条配置，渲染器不动。
- **数据不另造**：列表与详情直接复用 2D 后台的分页/详情接口
  （`/erp/scm/purchase-order/page`、`/erp/scm/purchase-order/{id}`），权限码复用
  `sys:erp:purchase:list`。**无新接口、无新权限点、无新迁移**。契约 §2.5 同步写明
  `links[].path` 就是这条列表接口（不搞"屏风专用第二套口径"）。
- **概览侧补齐**：`ErpOverviewProvider` 新增
  - `charts[0]`：营收/成本/利润柱状图 —— 三列都来自同一份 cockpit 快照，`null` 一律补 0
    （图表里的 `null` 会画成 NaN 柱，整张卡静默变白）；
  - `links[]`：采购订单入口，按 `ctx.hasPermission` 裁剪。没采购权限的人连"能点进去"都不该知道。
- **两条踩出来的硬约束**：
  1. **屏风没进入时，内部行/按钮一律不响应**。玩家"点一下屏风想进去"时，事件目标会落在表体行上，
     于是先弹详情、再被过场盖住——现场表现为"进殿后停在详情页"。现在由 `body.closest('.bws-screen').dataset.focus`
     判定，未进入只把点击让给外层 `screen.ts`。
  2. **屏风位置要按台基反算**。户部台基深 `(7+9)×0.95 = 15.2m`、顶面高 2.47m；按殿心偏移摆屏风会插进台基里，
     而 CSS3D 不做深度测试，看上去就是"浮在半空"。改成沿殿正面法线退到台基外的地面，并用
     `__bwwScreenOf` 校验：屏风底边投影 563px vs 地面 556px。
- **排版**：大屏 620px 高，KPI 单行 + 横向条形图（3 个值摊在 1100px 宽里用竖柱只剩发丝）+ 每页 6 行，
  刚好排满不用滚；详情态收起 KPI/图表/标签/工具栏，把整块屏让给详情与分录（分录区自己滚，整页不滚）。
- **验证**：`e2e/tools/world-screenpage-smoke.mjs` 35 项全绿：进屏风前后态、关键字筛选（20→1→20）、
  状态筛选（只剩已收货且回第 1 页）、4 页翻页与末页禁用、行点击详情（8 字段 + 12 行分录）、
  分录区滚动且整页不动、返回、Esc 退出、零控制台错误。
  回归 `world-screen-smoke/engage/ime/resize/hint`、`world-datahall-smoke`、`world-glyphs` 全通过；
  `world-city-smoke` 仍是 S1 扩容后的 3 项旧断言失败（传送门 9→13 等），与本阶段无关。
- **未做**：数枢殿那块写死数据的演示屏仍在（S5 统一按布局生成时替换）；真接口 HTTP 未验（本机 Nacos 未起）。

## S5 第一批（T5.1 数枢殿总控：聚合多服务 + 屏风页 + 厅配置）

**这一批在解决什么**：S4 打通了"一个服务 → 一个殿"，S5 要 9 个殿。总控是第一块，因为它必须先回答
"多服务怎么汇到一起"，否则后面 8 个殿各写一套汇总，就是 8 种口径。

- **宿主选 whale-monitor**：它是本工程唯一的无库采集型服务（只读 Nacos 与各服务只读接口），
  总控与它同构；新起服务要再占一档内存（VM 余量本就吃紧）。端点：
  `GET /monitor/overview`（概览）+ `/monitor/overview/halls[/{nodeKey}]`（屏风页的列表与详情）。
- **接入一殿 = 一行配置**：`whale.overview.aggregate.targets`。容器内直连容器名
  （`http://bw-erp:9001/erp/overview`），**不走网关** —— 网关挂了总控仍要能看到各殿真实状态。
- **身份透传**：转发 `X-User-Id / X-Tenant-Id / X-Permission-Codes`，各殿按自己的权限码裁剪；
  总控自身不设权限码（可见范围 = 你在各殿能看到的范围）。缺码的殿显示 `denied`（无凭据），
  与 `degraded`（没数）分开 —— "去要权限"和"去查服务"是两件事。
- **单殿失败隔离**：并行问询 + 单殿 2s 超时（SDK 5s），一座挂只让那一行变红；
  四张 KPI = 接入殿 / 通畅 / 陈旧 / 未通。
- **SDK 两个修补**：
  1. **缓存键补权限签名**（`tenant|permSignature`）。契约要求 provider 按权限做块级裁剪，
     同租户里权限不同的人本来就不是同一份快照 —— 原键只有 tenant，等于把有权限的人的数发给没权限的人。
     负向验证：签名去掉后 `shouldIsolatePermissions` 红。
  2. **`Overviews.formatValue/formatKpi`**：总控一行里混着金额/计数/百分比，一列只能一种排版，
     只能服务端先排版；规则与前端 `formatValue` 逐条对齐，`OverviewFormatTest` 6 例钉住。
- **屏风页**：S2 那块写死数据的演示屏换成真总控页（四列：殿 / 主指标 / 状态 / 说明）。
  分页与关键字/状态筛选**在服务端生效**（`current/size/keyword/state`），否则就是假分页。
- **顺手修掉 S2 遗留真 bug**：退出屏风后一块巨大纸面糊在镜头上且再也点不动。
  根因：three `CSS3DRenderer` 用 `WeakMap` 缓存上次写入的 `style.transform`，字符串没变就跳过写；
  屏风退出后矩阵与进入前一致 → 缓存命中 → 而 inline transform 已被清空，元素回到"无变换"。
  修法：还原时换一个新的 `CSS3DObject`（`Screen#reattach3d`）让缓存必然失效。
  三块屏风复测：退出后矩形 `16948×3202` → `268×138`。
- **验证**：`world-shushu-smoke` 31 项全绿（`page.route` 回与后端同形状的信封，并断言分页/筛选参数
  真的发出；末段把接口打 500，验"有旧值标陈旧 + 列表给人话与重试"）；后端聚合器 7 例 + SDK 33 例；
  checkstyle 0。回归：`world-screenpage-smoke` 35 项、`world-screen/engage/ime/resize/hint/occlusion/wheel`、
  `world-datahall-smoke`、`world-glyphs`、`world-quest` 全通过。
- **遗留**：`world-city-smoke` 3 项（S1 旧断言 传送门 9→13 等）；`world-guide` 1 项"中止后能正常走"
  （0.8m < 1.5m，已 `git stash` 在改动前基线复现同样结果）；真接口 HTTP 仍未验（Docker/Nacos 未起）。
- **e2e 维护**：`world-screen-ime` 与 `world-screenpage-smoke` 的选择器改为限定到具体屏风
  （`.bwsp-search` / `[data-screen-id=...]`）——城里现在同时挂着两块通用业务页，
  `.bws-input` 会同时命中搜索框与状态下拉框，strict mode 直接报错。

## S5 第二批（T5.2 枢密殿 / auth：概览 + 登录历史屏风页）

**这一批在验证什么**：T5.1 的总控只有户部一行，聚合链路等于只跑过一次样本。接入第二座殿
才能证明"加一行配置就能接一殿"不是特例，也才能看出并行问询、单殿超时、身份透传在异构服务上是否真的成立。

- **auth 概览** `GET /auth/overview`：四张 KPI（启用账号 / 在用会话 / 今日登录 / 今日失败）
  + 近 7 日成功/失败趋势 + 今日结果构成。权限码复用 `sys:login:history:list`。
- **统计下沉为端口** `AuthSecurityStatQuery`，租户**显式传参**。聚合总控时线程上挂的是调用者身份，
  靠 `TenantContext` 取租户会把别人的数算进来；显式传参让这种漏数在编译期就写不出来。
  一次聚合供 KPI 与趋势共用，一屏只打一遍库。
- **按天聚合条件列不套函数**：`login_time >= ? AND login_time < ?` 保住 `idx_login_history_time`；
  写成 `DATE(login_time) = ?` 索引直接失效。
- **告警两条只出一条**：次数（≥20）先判 CRITICAL，占比（≥30% 且样本 ≥5）补 WARNING。
  同时报两条，值班分不清"量大事"还是"比例事"，而处置动作是同一个。样本 <5 不谈占比
  ——1 失败 0 成功 = 100%，报了只会让人关告警。
- **屏风页** `/login-history/v1/page`：五列（账号/结果/方式/来源 IP/时间），结果中文徽标、失败标红；
  筛选只给 `result` —— 接口没有 `keyword`，就不给搜索框（给了就是"输入了没反应"）；
  详情 8 字段含失败原因/客户端/设备指纹。
- **新增 `datetime` 列口径**：到分钟。只到日期时同一天多条等于没给时间；不做时区换算
  （库里就是本地时间，前端再转会整体差 8 小时）。
- **总控接入**：`targets` 加 `shumi-hall`（`http://bw-auth:8081/auth/overview`），总控出现第二行真数据。
- **验证**：`world-shumi-smoke` 32 项全绿；auth provider 7 例 + 架构 8 例 + 总控 13 例；checkstyle 0；
  六项门禁 PASS。

## S5 第三批：度支殿（pay）

### 后端

- **`GET /pay/overview`**：四张 KPI（今日收款 / 今日建单 / 待支付 / 今日退款）+ 两张图
  （近 7 日收款趋势 line 金额、今日渠道构成 bar 金额）。权限码复用 2D 的 `sys:pay:list`，
  屏风页复用 `/pay/order/page` —— 无新接口、无新权限点。
- **退款不冲减收款**：收款是 `status IN ('PAID','REFUNDED')` 按 `pay_time` 落窗口的**毛额**，
  退款单独从 `pay_transaction`（`type='REFUND' AND status='SUCCESS'`）统计。净额会把
  "收 100 退 80"显示成 20，规模感全丢；值班要看的正是两个数各自的规模。
- **失败告警只数 `type='PAY'`**：退款失败混进来会稀释渠道故障信号，两者处置动作不同。
- **两条告警可并存**（与 T5.2 的"二选一"相反）：失败笔数 ≥5 → CRITICAL（看渠道）；
  待支付中超 24 小时未回调 ≥10 → WARNING（看回调）。不同根因就该都报。
- **统计端口** `PayOverviewStatQuery`：8 方法 / 4 record，租户显式传参，`invalidWindow()` 统一拦
  空租户与倒置窗口，空值折 0；渠道空白折 `UNKNOWN`（空类目会在柱图上长出一根无名柱）。
- **索引按查询形状补**：`V3__pay_overview_index.sql` + `init.sql` 三组幂等 `ADD INDEX`
  （`pay_order(tenant_id, pay_time)` / `pay_order(tenant_id, status, create_time)` /
  `pay_transaction(tenant_id, type, status, create_time)`）；时间条件列不套函数，保住索引。

## 三维王城 S5 第八批：通政殿（T5.8 / message）

### 后端

- `GET /message/overview`（`whale.overview.base-path`）：四张 KPI（今日投递 / 送达率 /
  积压未发 / 退信）+ 两张图（近 7 日投递 line、失败最多渠道 bar）。权限码复用
  `sys:message:record:list`，屏风页复用 `/message/v1/record/page` 与 `/{id}`，

- **不复用 2D 投递看板**（`/message/v1/record/dashboard`）：它把窗口内投递按

- **「积压未发」是本殿核心数**：状态仍停在 `PENDING / DISPATCHING` 且创建超过 10 分钟。
  不报错、不告警，接口返回成功而收件人什么也没收到——消息服务最典型的静默失效。
  10 分钟是异步补偿回收阈值（120 秒）的 5 倍余量。
- **告警两条根因不同**：积压 → `CRITICAL`（去看投递线程与补偿任务）；退信 → `WARNING`
  （地址失效，重试永远失败，只能改数据）。合并成一条会让人先重试一批不可能成功的投递。
- **小样本不谈比率**：近 24h 不足 20 条时，送达率跌破 90% 也不转黄灯（4 条坏 1 条 = 75%，
  报出来只是噪音）；但副标始终写"成功 X / 失败 Y"，避免"100% 其实只发了 1 条"。
- 端口 `MessageOverviewStatQuery`（5 方法 / 3 record）：租户显式传参、`invalidWindow()`、
  空值折 0、渠道空折「未知渠道」；窗口按 `sent_at` 卡（未发出的行 `sent_at` 为空，
  算进"今日投递"会偏大）。
- 索引 `V9__message_overview_index.sql` + `init.sql`：
  `msg_delivery(tenant_id, sent_at)` / `(tenant_id, status, sent_at)`、
  `msg_record(tenant_id, status, create_time)` / `(status, create_time)`，
  删被最左覆盖的 `idx_tenant_status`。**后两个不能互相替代**：补偿任务查"所有租户里卡住的
  PENDING"（`InterceptorIgnore(tenantLine)`）没有 `tenant_id`，带租户前缀的用不上；
  概览必须带租户，否则会把别家的积压算进来。

### 前端

- `MESSAGE_RECORD_PAGE` 五列（标题 / 业务类型 / 渠道 / 状态 / 创建）；**没有搜索框**——
  `MessageRecordQueryRequest` 只有 `bizType / bizId / status / channel`，没有关键字，
  配 `keywordParam` 也会被 Spring 静默忽略（与 T5.2 同一判据）。状态选项按"问题优先"排。
  详情配 `detailPath`，把各渠道投递明细 `deliveries` 渲染成分录表；正文 `content` 不进详情
  （TEXT 长度不受控，塞进 620px 屏风会把版面顶穿）。
- **详情分录必须用列级状态字典**：投递状态是另一套码，`READ` / `BOUNCED` 在消息状态里
  根本不存在；用页面级字典会原样显示英文且不报错。`DELIVERY_STATUS_STYLE` + 列级
  `statusMap` 覆盖（T5.6 加的能力，这是第二个真实用例）。

### 两条自测断言写错的教训

- 屏风页的 `formatKpiValue` 对 percent 输出 **`94.0%`**（一位小数），
  断言写成 `/^\d+%$/` 会误判成"没格式化"——正则要允许小数。
- **分录表只译文字、不打灯**（政事殿审批链、考功殿字段配置同此约定），
  断言 `td .bwsp-badge` 的 `tone` 恒为空。要验列级字典生效，看**文字**（`READ → 已读`）
  就够了：串用页面级字典时它会原样显示英文。

## 三维王城 S5 第九批：起居殿（T5.9 / audit，只读）

### 后端

- `whale-ops-audit` 是**单模块服务**（不像 message/form 是多模块），首次接入 overview SDK：
  pom 加 `whale-overview-sdk`、application.yml 加 `whale.overview.base-path: /audit/overview`。
- `AuditOverviewProvider`（`overview` 包）：4 KPI（今日审计 / 失败操作 / 留痕断流 / 归档陈旧）
  + 2 图（近 7 日审计 line、操作类型 Top5 bar）+ 2 告警。权限码复用 `sys:audit:log:list`。
- 核心是两张**静默失效牌**：留痕断流 = 最近一条审计距今多久（DURATION），
  归档陈旧 = 心跳 `audit.log.retention` 最后成功距今几天（与 `audit.job.stale.days` 同口径）。
  两者都不报错，是审计服务最典型的"该记的那段是空白"。告警 CRITICAL(断流)/WARNING(归档)可并存。
- 统计端口 `AuditOverviewStatQuery`（6 方法 / 2 record）+ Impl + 独立只读 Mapper
  （不污染公共 `AuditLogMapper`）。**租户显式传参**：provider 在独立线程池跑没有 TenantContext，
  SQL 必须自己带 `tenant_id`。复用既有 `idx_tenant_time`，无新迁移。
- 架构注意：audit 的 ArchUnit 只约束 mq/retention 包，overview/service 不受其分层规则限制，
  仍需带 `-am` 跑（5 例）。`-Dtest=AuditArchitectureTest` 配 `-am` 时要加
  `-Dsurefire.failIfNoSpecifiedTests=false`，否则上游模块"无匹配测试"报错。

## 三维王城 S5 第十批：城门楼地标（T5.10 / gateway，无入口）

### 定位

- 网关是**无状态代理**（路由 / 鉴权 / 限流），没有业务表，也没有 `/<服务>/overview` 可算。
  要做"网关健康"就得在全城唯一入口上多开一个业务端点并进白名单，而白名单与兜底路由
  每改一次都要重建镜像、重启入口——为一块地标多一颗暴露面，不划算。
  所以本批**不接 overview、不建屏风页**，只让门楼"被认出"。
