### 12.4 风险：定时任务没有分布式锁（P1，未修）

- 多副本部署时**每个副本都会执行**同一批定时任务，执行次数随副本数线性放大。
- 本次验证刻意让两个 CRM 实例同时在线（`bw-crm` 02:00 cron 未命中窗口，未产生重复），但 `CrmOrderSyncJob`（`0 * * * * ?` 每分钟）在双实例下会并发扫描同一批待推送订单——ERP 建单有幂等（按 `crm_order_no` 唯一）兜底，实测未产生重复单据，但会产生重复 RPC。
- 分析类任务靠业务幂等（快照 upsert、行动项 dedupKey）兜底，数据不会重复，只是多跑一遍。
- 建议（P1）：引入 ShedLock（Redis 或 DB provider）给有副作用的 job 加锁，或把定时任务收敛到单一调度实例（`scheduler.instance-enabled` 开关 + 只有主实例注册）。

## 十四、送达回执能力（P1 收口，2026-11-08 17:20–18:00）

### 14.1 为什么必须做

第十三节的缺口是**语义缺口**而不是配置缺口：`SENT` 只表示「已交给渠道」，业务方（CRM 营销）拿不到「已送达 / 已读 / 退信」。营销漏斗（发送 → 送达 → 阅读）到此为止，退信也无法回流去清洗联系人邮箱。

### 14.2 平台侧（whale-message）：V2 迁移 + 回执受理 + 回调 outbox

| 变更 | 说明 |
|---|---|
| `V2__delivery_receipt.sql` | `msg_record.callback_url`；`msg_delivery` 增 `delivered_at / read_at` 与 `(tenant, channel, provider_message_id)` 索引；新表 `msg_receipt`（回执流水，`(tenant, receipt_key)` 唯一）；新表 `msg_callback_task`（回调 outbox，`(tenant, receipt_id, delivery_id)` 唯一） |
| `DeliveryStatus` | 增 `DELIVERED / READ / BOUNCED`，并带 `progress` 阶梯与 `canAdvanceTo`：回执态**只许前进** |

### 14.5 联调暴露并修复的两个真实缺陷

1. **渠道编码两侧不一致**：消息服务站内信渠道是 `INAPP`/`IM`，CRM 只有 `INBOX`。回调首跑被 CRM 拒为 `41083 触达渠道非法：INAPP`，回执丢失。修：`SendChannel.fromMessageChannel` 做归一（`INAPP/IM → INBOX`）。
2. **回调把「业务失败」当成功**：业务方统一响应是「HTTP 200 + 业务码」，派发器原先只看 HTTP 状态，`code=41083` 被记成 `回执回调成功`，回执被静默丢弃。修：解析响应体 `code`，非 0 抛错走重试。实测复现：回调指向返回 `code=500` 的端点，日志 `回执回调失败，稍后重试: attempts=1, reason=业务方返回失败: code=500`。

### 14.7 仍未做

- **`@Scheduled` 无分布式锁**（全仓 21 处，含本次新增的回执派发器）：多副本会 N 倍执行。`@DistributedLock` 语义是「抢不到就抛/放行」，不适用于「抢不到就跳过」，需新增 `@ScheduledLock`（Redisson `tryLock(0, lease)` 失败直接 return）或引 ShedLock，建议单独立项逐个 job 加。
- 真实渠道回执：`mock=true` 下 EMAIL/SMS 不会产生真实 `providerMessageId`，回执上报可由供应商 webhook 或部署侧网关接入，本次未接真实供应商。
