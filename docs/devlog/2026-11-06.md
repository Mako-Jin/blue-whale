## Wave 5.80 M1B-5：ERP 物料/库存只读契约

### 起因

M1B 全景中 M1B-5 因 ERP 缺少内网只读物料/库存接口而待做。本轮先补 ERP 契约，再接入 PDM 客户端与降级，避免 ERP 故障阻断零件页。

### 落地内容

- **ERP 物料**：`ErpItemService#getByCode` + `GET /erp/internal/item/by-code?code=`；不存在时 `data=null`。
- **ERP 库存**：`StockRepository#listBalancesByItemCode`、`InventoryAppService#stockByItemCode` + `GET /erp/internal/stock/by-code?itemCode=`，按物料编码聚合各仓库数量并补仓库编码/名称，无余额返回 0 与空明细。
- **内网安全**：复用 `/erp/internal/**` 既有 internal-deny 与 `InternalTokenSupport`，未新增网关规则或权限码。
- **PDM 客户端**：`PdmIntErpClient#getItem/getStock` 解析物料与库存信封；PDM 回显优先 `erpItemCode`，未维护时回退零件编码。

- **前端**：零件库新增「ERP 库存」按钮，弹窗展示物料状态、库存合计与仓库明细；降级时顶部告警。

### 关键口径

- **导出复用 ACL 而不是另写 SQL**：列表与导出若各写一套条件，迟早出现「列表看不到、导出却有」的越权面。
- **5000 行截断而不是全量**：CSV 一次性拉全表会把内存与响应时间交给数据量决定；截断并显式标记，前端可提示用户加条件。
- **告警只认“错误变化”而不是每次失败**：同一失败每次重试都发一条，会把运维通知变成噪声，最后没人看。
- **接收人为空默认跳过**：未配置接收人时不应把同步失败升级为 500；告警是旁路，不是主流程的一部分。

## Step 2：商城服务 M0 落地（Wave 5.94，`whale-mall`）

### 起因

平台已具备 ERP/PDM/CRM/LMS/党政工会等域，但**交易侧空白**：没有商品中心、没有购物车与订单，任何"卖东西"的需求只能挂到具体业务服务里重写一遍。用户提出"搭建商城服务"，并确认两个前提：① **一套内核要兼容零售 / 经销订货 / 员工福利三种形态**；② **商品由商城自建商品中心**，不实时复用 ERP 商品与库存。

### 决策

- **不建三个服务、不建三套表**：三种形态的差异只有三处——渠道形态 `mall_channel.mode`（`RETAIL`/`B2B`/`WELFARE`）、结算方式 `settlement_type`（现金/积分）、价目类型 `mall_sku_price.price_type`（`RETAIL`/`B2B`/`POINTS`）。形态落在渠道上，同一套商品可被多个渠道复用。
- **价目解析策略写死在领域里**：`RETAIL→RETAIL`；`B2B→B2B 缺失回落 RETAIL`（经销客户没单独报价就按零售价，是常规做法）；`WELFARE→POINTS 缺失直接失败`（福利场景拿现金价结算是**错账**，不能当降级）。
- **商品中心自持**：不与 ERP 商品/库存双写。双写要先解决"谁是主数据"和冲突合并，M0 不做；ERP 库存对账列入 M1 备选。
- **支付不在本服务**：支付单归 `whale-pay`，商城只存 `payOrderId`；回调走内网 `POST /mall/internal/order/paid`，网关已把 `/mall/internal/**` 列入 internal-deny。

## Step 4：商城 M1 首切片——支付闭环与退款（Wave 5.95）

### 起因

M0 把订单停在「待支付」，钱的事没通：`whale-pay` 只有 MOCK 收单、无业务回调机制、退款是一次性全额且无退款单。本切片打通「下单 → 创建支付单 → 支付 → 回调推进 → 取消关单 → 整单退款」资金主链路，并把渠道适配器接口化。

### 决策

- **支付单由 mall 创建**：金额以订单应付为准，前端拿不到改金额的机会；按 `orderNo` 幂等（重复创建返回原单，不报错——业务方重试是正常路径）。
- **回调落任务表**：新表 `pay_notify_task`，支付/退款成功后**事务提交后异步首投**，失败按 30s×2^n 退避重试 6 次后置 `DEAD`，管理端可手工重试。回调丢了业务订单会永远停在待支付，这是资金链路最贵的一种丢。
- **状态机只加两条边**：`PAID → REFUNDING → REFUNDED`。REFUNDING 期间禁止发货、禁止再次退款（`canRefund` 只认 PAID），防并发双退；SHIPPED/COMPLETED 退款属售后域，下一切片做。
- **退款模型支持部分退款，入口只开整单**：`pay_refund` 有 `amount` 字段、`pay_order.refund_amount` 原子累计（单条 SQL 校验「剩余可退 ≥ 本次」），全额退完自动置 REFUNDED——但没有审批流的部分退款等于谁点谁退，业务入口留给售后切片。
- **渠道适配器 SPI 化**：`PayChannelAdapter`（pay/refund/queryStatus），`MockPayChannelAdapter` 内置；`PayChannelGateway` 退化为按渠道号路由。接真实渠道 = 新增实现类 + 配置一行，业务代码零改动。
- **回调地址格式 `<服务名>/<路径>`**：投递时经 Nacos 解析实例，与部署端口解耦；载荷带 `tenantId`，投递线程以 `X-Tenant-Id` 头还原租户上下文。

### 踩坑

1. **`MockPayChannelAdapter` 包名写错**（`com.bluewhale.common.exception` vs `core.exception`）→ 编译立刻暴露，改回。
2. **`PayChannelGateway` 去 Lombok 后残留 `@RequiredArgsConstructor`** → Checkstyle UnusedImports；改为显式构造器（需要建路由表，Lombok 表达不了）。
3. **`PayRefundServiceImpl` 多注入了 `PayNotifyTaskMapper`** → 改为直接用 `enqueue` 返回的任务 ID 调度首投，少一次查询。
