## whale-job 运维效率：任务批量操作与导入导出（扩展路线图第 7 项）

- **需求项**：批量启停/批量删除、跨环境搬运任务定义与依赖。设计见 `docs/job-batch-import-export.md`。
- **决策**：
  - 批量操作逐条复用单条服务方法（`changeStatus` / `delete`），单条失败只记明细、不整批回滚；
    整体加事务会让一条坏数据把整批回滚，与「批量治理」的使用预期相反。
  - 导出只含可移植字段，排除 `id` / `tenantId` / `failCount`：环境相关标识与运行态失败历史不可搬运。
  - 依赖边以 `{executorApp, jobCode, jobName}` 表达，跨环境 ID 必然不同，用 ID 导出等于不可用。
  - 导入匹配键：`jobCode` 非空用 `executorApp + jobCode`，否则用 `jobName`；冲突策略默认 SKIP，
    非法取值直接 400，避免拼写错误被静默当成 SKIP。
  - 导入的条目校验在服务层逐条执行 Jakarta Bean Validation，不在请求体上加 `@Valid`，
    否则一条坏数据会让整份文件被 400 拒绝。
  - 依赖在任务全部落库后按下游聚合，一次全量替换；新增任务因此可作为同文件内的依赖端点。
- **完成项**：
  - 新增 `POST /job/info/batch-status`、`POST /job/info/batch-delete`、
    `GET /job/info/export?jobGroup=`、`POST /job/info/import`；
  - 新增 `JobBatchService` / `JobBatchServiceImpl` 与 8 个 DTO/VO；
  - 权限与单条接口对齐（`sys:job:edit|delete|list|add`），写操作全部标 `@AuditLog`。
- **验证**：
  - 单测：`mvn -o test` → **137 项零失败**、BUILD SUCCESS、checkstyle 0 violation（新增 13 项）。
  - 起服实测（8082）：导出 TMP 分组 2 个任务 0 条边且不含 `id` / `failCount`；
    SKIP 导入 `skipped=2, dependencyCount=1`，`GET /job/info/{B}/dependencies` 回显上游 A；
    OVERWRITE 导入 `updated=2` 且 `remark` 已覆盖；非法策略返回 400；
    批量启停 `[A,B,999999]` → `successCount=2`、失败明细含 999999；
    批量删除两次 → 首次 `successCount=2`，再次全部「资源不存在」；测试任务已清理。
- **待做项**：管理端批量选择与导入文件上传交互。

## whale-job 告警增强：多通道配置化与恢复通知（扩展路线图第 8 项）

- **需求项**：失败告警同时支持多个 IM 通道；任务从连续失败恢复时补发一次「已恢复」信号。
  设计见 `docs/job-alert-channels-and-recovery.md`。
- **决策**：
  - `channels` 非空时完全替代 `webhook-url`，不做「两边都发」：避免切换通道后旧地址仍在收告警；
    `channels` 为空才回退为单个 `WEBHOOK`，既有部署零改动。
  - 内置 `WEBHOOK` / `DINGTALK` / `FEISHU` 三种载荷格式：钉钉 `msgtype`、飞书 `msg_type` 各自适配，
    通用通道字段保持不变。
  - 多通道串行推送、单通道失败继续下一个；`job_alert` 只写一条，`channel` 记录拼接后的通道名。
  - 恢复通知以「`fail_count` 条件清零影响行数 > 0」为触发条件，天然保证一次失败只对应一次恢复通知；
    恢复通知不受冷却限制，但人工重新启用任务（启用时已清零计数）不补发。
- **完成项**：
  - `JobProperties.Alert` 新增 `channels`（`type/url/enabled`）与 `recovery-enabled`；
  - `JobAlertNotifier` 新增 `notifyRecovered` 默认方法；
  - `WebhookJobAlertNotifier` 支持多通道、三种载荷、通道级失败隔离与恢复通知；
  - `JobScheduler#resetFailureCount` 改为返回是否清零，成功恢复时调用 `notifyRecovered`；
  - `application.yml` 增加多通道示例与 `recovery-enabled` 开关。
- **验证**：
  - 单测：`mvn -o test` → **142 项零失败**、BUILD SUCCESS、checkstyle 0 violation
    （新增多通道、恢复不受冷却、恢复开关、调度侧恢复触发共 5 项）。
  - 起服实测：本地 mock HTTP 服务（`/run` 首次 500、之后 200）配合 `webhook-url` 指向 mock `/alert`；
    手动执行两次后 `job_alert` 依次落 `ERROR` 与 `INFO` 两条且均为推送成功，
    mock 收到失败载荷（含 `errorMsg`）与恢复载荷（`message=任务执行已恢复`）；测试任务已清理，
    服务已恢复为无外发通道的默认配置。
- **待做项**：钉钉/飞书签名校验（当前按自定义机器人 URL 直发）；
  告警记录页增加通道筛选与恢复通知的前端标识。

## whale-job 管理端接入：拓扑 / 批量 / 导入导出 / 告警标识（C6）

- **需求项**：把后端已交付的第 5~8 项能力落到管理端 `whale-frontend/admin` 的定时任务页。
  设计见 [job-admin-console-frontend.md](../job-admin-console-frontend.md)。
- **决策**：
  - DAG 用自绘 SVG + 纯函数分层布局，不引入 ECharts / AntV / ReactFlow：
    仓库无现成图库，lockfile 也没有可复用条目，为几十个节点引入图库不划算；
    布局按最长路径分层、同层保持接口顺序，环上节点用迭代松弛封顶，异常数据也不会死循环。
  - 环检测只消费后端 `/job/graph/validate` 的结果并标红，不在前端重复实现算法。
  - `ProTable` 只新增可选 `rowSelection` 透传，选中集合由页面受控，翻页/刷新后保持；
    批量接口整体 200，失败提示只展示前 3 条原因，避免长列表刷屏。
  - 导出走 `downloadBlob`（401 静默续期一次）后另存附件，不把 JSON 渲染到页面；
    导入只在本地做 JSON 可解析与 `jobs` 数组检查，字段级校验全部交给服务端，避免两套规则漂移。
  - 告警 `channel` 按逗号拆成多个 Tag，`recovered` 显示「已恢复」；查询区按单通道模糊筛选。
- **完成项**：
  - 新增「依赖拓扑」页签（分组过滤、缩放、节点详情 Tooltip、环检测提示）；
  - 任务列表工具栏：批量启用/停用/删除、导出选中/导出全部、导入；
  - 新增导入弹窗（文件解析预览、SKIP/OVERWRITE、四类计数与失败明细）；
  - 告警记录页通道拆分、恢复标识与级别/通道筛选。
- **验证**：
  - `pnpm --filter @bluewhale/whale-ui build`（ProTable 新属性先出 d.ts）、
    `pnpm --filter whale-admin exec tsc -b`、`pnpm --filter whale-admin build` 全部通过；
