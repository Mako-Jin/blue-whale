## Step 4：商城售后单与部分退款（Wave 5.96）

### 起因

M1 首切片只做了整单退款，`payInternalClient.refund(payNo, totalAmount, reason)` 一次退完。它把三件事一起遮住了：

1. **退款请求不幂等**。支付侧 `refund(payNo, amount, reason)` 没有业务退款单号，每次调用生成新的 `pay_refund` 行。整单退款靠 `WHERE amount - refund_amount >= ?` 的额度兜底还能挡住重复（退完额度归零），但**部分退款下这个兜底失效**——订单 100 退 30，超时重试再退 30，累计 60 仍在额度内，多退 30 现金。而 `pay_refund` 上早就躺着 `uk_tenant_refund_no`，钥匙在手边没人用。
2. **退不了「一部分」**。买家只退一件时无路可走，只能整单退，商家白搭运费和已发商品。
3. **售后过程无处承载**。谁申请的、退哪几行、审核意见、退货物流，全靠 `mall_order.refund_amount` 一个数字表达。

### 决策

1. **先修幂等，再谈部分退款**。mall 生成售后单号作退款请求号传给支付侧，`pay_refund` 按 `uk_tenant_refund_no` 判重，已存在直接返回原单。命中但金额不同则拒绝——静默按原单返回会让调用方以为新金额也退了。
2. **整单退款降级为售后单的特例**（覆盖全部可退行 + 直接通过审核），不再有第二条退款路径。两条路径意味着两套额度计算、两套幂等、两处回调结单，迟早漏改一处。
3. **部分退款后订单保持原状态**，只累加 `refund_amount`；累计达 `total_amount` 才由 SQL 置 `REFUNDED`。不新增 `PARTIAL_REFUNDED`：多笔售后共存时订单状态不该反复跳，「已部分退款」是列表页展示问题（`0 < refund_amount < total_amount` 就能算），不该污染状态机。`REFUNDING` 语义收窄为「整单退款进行中，禁止发货」。
4. **行级额度用条件更新占用**（`WHERE quantity - refunded_quantity >= ?`），与支付侧原子累计同构。同一行被两张售后单并发申请时后到的直接失败，而不是两张都通过、退款时才发现退不出。
5. **驳回/撤销必须释放额度**。占了不还，商品被驳回一次就再也申请不了售后——这是最容易漏、后果最直接的一处。
6. **回调按售后单号定位**，支付侧把零售后号原样放在载荷 `refundNo` 里回传。查不到售后单时按「M1 在途退款单」兼容处理：用支付侧累计退款额推算增量只累计订单金额，**不抛错**——抛错会让投递方重试到死信，而老单子上线瞬间最容易出现。
7. **订单退款范围放宽到 PAID/SHIPPED/COMPLETED**。只放开已支付等于把退货全堵死（货发出去才发现问题是最常见的售后场景）。

### 落地内容

- **支付侧**：`PayInternalRefundRequest` 加 `refundNo`（幂等键，可空）；`PayRefundService.refundByNo` 加参数并前置判重，三参重载委托；`PayRefundServiceImpl.findReplayedRefund` 同号同金额返回原单、同号异金额抛错；兼容 `pay_refund` 并发同号（撞唯一键整笔回滚，调用方重试拿原单，「宁可失败不可多退」）。
- **数据模型**：`V4__mall_after_sale.sql` 新建 `mall_after_sale`（`uk_mall_after_sale_no`、类型/状态/金额/审核/退回物流号）与 `mall_after_sale_item`；`mall_order_item` 补 `refunded_quantity`/`refunded_amount`。
- **领域**：`MallAfterSale`（金额只由明细汇总、五态状态机、`markRefunded` 幂等）、`AfterSaleItem`、`AfterSaleStatus`、`AfterSaleType`；`OrderItem.refundableQuantity()`。

## Step 4（五服务分步计划）：ERP ↔ MES 打通

### 起因

ERP 生产订单只能下单、领料、完工，车间在 MES 里看不到任务；MES 已有接收工单入口和完工发件箱，但 ERP 没有回执端点，两边各记各的数。本批补「ERP 下达推送 → MES 报工/完工回传 → ERP 幂等入库 → 对账页兜底」的闭环。

### 落地内容

- **数据表**：`V16__mfg_mes.sql` 给 `erp_mfg_production_order` 追加 `mes_sync_status/mes_work_order_code/mes_synced_at/mes_last_error`，新建 `erp_mfg_mes_callback`（UK `tenant_id+source_event_id`）与 `erp_mfg_mes_progress`（UK `tenant_id+erp_order_no`）。
- **ERP 下发**：`release()` 发布 `ProductionOrderReleasedEvent`，`@TransactionalEventListener(AFTER_COMMIT)` 事务提交后推送 MES，成功 `PUSHED`、失败 `FAILED` 并记摘要，不污染下达事务。
- **ERP 回执**：`POST /erp/internal/production-order/{erpOrderNo}/completion|progress`；完工按 `delta = MES 累计完工 − ERP 已完工` 入库，`delta ≤ 0` 记 `DUPLICATE`，状态不允许/订单不存在记 `REJECTED`；入库用 `REQUIRES_NEW` 隔离；进度只写快照、不回写工序报工。
- **MES**：`MesTaskProgressServiceImpl` 报工后入发件箱 `WorkOrderProgress`（幂等键按「工单 + 报工/合格/完工 + 状态」），`MesOutboxDispatcher` 支持 `WorkOrderProgress` → `/progress`、`WorkOrderCompleted` → `/completion` 并携带 `tenantId`；新增 `GET /mes/internal/work-order/{erpOrderNo}` 进度查询（无工单 404）。
- **对账**：`/erp/mfg/mes/reconcile/page|{orderId}|push|pull|completion-apply`，差异标记 `ERP 已完工 − MES 累计完工`；权限 554–557、菜单 108（`migration-5.78-erp-mes.sql` 幂等）。
- **前端**：`MesReconcilePage` 筛选（关键字/日期/MES 状态/下发状态）、差异标记、详情抽屉（回调流水 + 任务）、重推/拉取/人工确认入库；`api/mfg.ts` 补类型与函数，`App.tsx` 注册菜单与路由。

## Step 5：商城计价重构——优惠券与运费（Wave 5.97）

### 起因

M0/M1 阶段订单只有一个 `total_amount`，语义是「商品行小计之和」。引入优惠与运费后，这个字段会被四拨人各按各的理解使用：

1. **支付单**把它当扣款金额（应该扣「应付」）；
2. **售后**把它当可退上限（应该按行「实付」退）；
3. **报表**把它当成交额（应该看商品总额，不含运费）；
4. **财务对账**把它当流水（应该与支付单一致，即应付）。

一个字段担四个语义，迟早有一处算错。同时商城还缺两个最基本的能力：下单不收运费（连「满 99 包邮」都没有），运营没有任何促销手段（只有原价卖）。售后刚做完、行级额度与分摊的落点还在手边，此时切这一刀最省。

### 决策

1. **`total_amount` 语义收窄为「应付」，另开三个字段**：`goods_amount`/`discount_amount`/`freight_amount`，`total = goods − discount + freight`。字段名与取值口径不变，支付单金额、退款额度、前端金额展示全部继续读它，**pay 侧一行不改**，也不需要迁移改值；无券无运费时 `goods = total`，老订单天然自洽。`goods_amount` 回填 `total_amount`（条件自带幂等）。
2. **优惠与运费必须分摊到行**：`mall_order_item` 增 `share_discount`/`share_freight`，行实付额 `netAmount = amount − share_discount + share_freight`。不分摊就只能「按原价退 + 事后手工扣优惠」，做不到也不可审计。
3. **分摊算法：前 n−1 行占比 `DOWN` 保留 2 位，末行吃尾差**。逐行 `HALF_UP` 时 `Σ 分摊 ≠ 优惠额` 是常态（33.33×3 = 99.99 ≠ 100），对账差几分钱永远查不出原因。末行吃尾差保证两个恒等式：`Σ share = 总额`、`Σ netAmount = total`。
4. **优惠封顶 `goods − 0.01`**：whale-pay 侧 `amount > 0` 是硬约束，全额券会把订单算成 0 元单，支付侧直接拒绝。
5. **售后可退基数从「快照价 × 数量」改为行实付额**：折扣订单按原价退等于把优惠折现送给买家。同一行分次退时末次直接取剩余，不再按比例算一遍——三次各四舍五入，合计常差一分。
6. **券模板与用户券分表，用户券落快照**（面额/门槛/折扣/渠道/有效期）：运营改券模板不能篡改已经发出去的承诺。核销与回退走 `WHERE status='UNUSED'/'USED'` 条件更新——一券两单必须让后到的那单失败，而不是两张单都核销成功；发放量用 `issued_qty < total_qty` 条件占用，并发重复领取靠 `uk_mall_coupon_user(tenant_id,coupon_id,user_id,claim_seq)` 挡。
7. **单券不叠加**，不做券 + 活动 + 会员价组合。券只做「全场 + 单渠道」，不做品类券/商品券/店铺券。
8. **运费三型**（`FREE`/`FIXED`/`THRESHOLD`），满额包邮的门槛分母取**用券前**商品总额，否则会出现「领了券反而多付运费」这种说不清的账。模板为空/停用/不存在一律 0 元——配置疏漏不该阻断下单。
9. **积分商城不参与优惠与运费**：`currencyType = POINTS` 时渠道保存强制清空 `freight_template_id`，带券下单直接 `COUPON_NOT_APPLICABLE`。积分场景用现金运费是错账，不是降级。

## Step 6：商城物流与履约——发货单、运单号与签收驱动完成（Wave 5.98）

### 起因

「发货」原本只是 `POST /mall/order/{id}/ship` 里的一次状态跳转加一次扣预占。它把四件事一起遮住了：

1. **不知道发的是什么**。没有承运商、没有运单号，买家问「到哪了」只能答「已发货」。
2. **不能拆包**。`OrderStatus.canShip()` 只认 `PAID`，第一次发货后订单变成 `SHIPPED`，**第二次发货直接被状态机拒绝**——一个订单三件货、仓库分两个包裹是常态。
3. **签收驱动不了完成**。物流显示已签收、订单还挂着 `SHIPPED`，超时自动完成更无从谈起。
4. **发货不可追溯**。谁发的、发了几件，只有一条 `mall_order_log`。

### 决策

1. **发货是独立单据**：`mall_shipment` + `mall_shipment_item`，订单与发货单 1:N。一张单对应**一个运单号**——运单号是唯一的物理资源，一单多号等于把唯一约束退化成备注。
2. **行上加 `shipped_quantity`**，与 `refunded_quantity` 同构：可发 = `quantity - shipped_quantity`，占用走条件更新，两笔单并发发同一行时后到的失败。
3. **订单状态由发货单驱动**：首次发货 `PAID→SHIPPED` 且**幂等不重写 `ship_time`**（否则拆包后订单发货时间变成最后一个包裹的时间）；全部发满且全部签收 → `COMPLETED`；全部作废 → 退回 `PAID`。
4. **发货单三态无草稿**：`SHIPPED`/`DELIVERED`/`CANCELLED`。草稿要另定「占没占数量、占没占运单号」的规则，而运单号一旦申请就已消耗。
5. **签收两条入口一段状态机**：内网 `POST /mall/internal/shipment/delivered` + 运营手工 `/delivered`，按发货单号幂等（重复回调不重写签收时间）。
6. **作废三件事一起做**：释放 `shipped_quantity`、回补 `reserved_qty`（`unship` 不动 `available_qty`——可售在下单预占时已扣，再加回去等于凭空多一件货）、若无有效发货单则订单退回 `PAID`。
7. **移除订单侧 `/ship`**：发货只留发货单一条路径。两条路径意味着两套可发数量校验、两套库存扣减，迟早漏改一处。

### 落地内容

- **数据模型**：`V6__mall_shipment.sql` 建 `mall_shipment`（`uk_mall_shipment_no`、`uk_mall_shipment_tracking(tenant_id,carrier_code,tracking_no)`）与 `mall_shipment_item`；`mall_order_item` 补 `shipped_quantity`（默认 0，**存量不回填**）。
