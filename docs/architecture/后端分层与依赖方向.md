# 后端分层与依赖方向

本文回答"模块该放哪层、能不能依赖"。规则本身见 `docs/decisions/0005`，这里只讲**怎么落地**。

---

## 一、五层结构

```
                       ┌─────────────────────────────────┐
   sts-app        →    │  业务应用 —— 面向前端可交付物    │
                       │  sts-app-portal / sts-app-admin │
                       └────────────────┬────────────────┘
                                        │
                       ┌────────────────▼────────────────┐
   sts-server     →    │  服务 —— 可独立部署的运行单元    │
                       │  sts-server-log / ...            │
                       └────────────────┬────────────────┘
                                        │
                       ┌────────────────▼────────────────┐
   sts-components →    │  通用能力组件 —— 跨服务复用      │
                       │  sts-components-audit / -file   │
                       └────────────────┬────────────────┘
                                        │
                       ┌────────────────▼────────────────┐
   sts-common     →    │  技术底座 —— 与业务无关          │
                       │  sts-common-basic / -web / -db  │
                       └────────────────┬────────────────┘
                                        │
                       ┌────────────────▼────────────────┐
   sts-parent     →    │  依赖管理 —— 不含代码            │
                       │  版本号唯一来源 · 全局插件配置   │
                       └─────────────────────────────────┘
```

**箭头的含义是"可以依赖下面，不能依赖上面"，且只能相邻依赖。**

---

## 二、依赖矩阵

| 依赖方 ↓ \ 被依赖 → | sts-parent | sts-common | sts-components | sts-server | sts-app |
|---|---|---|---|---|---|
| `sts-parent` | — | ✗ | ✗ | ✗ | ✗ |
| `sts-common` | ✓ | 同层 ✗ | ✗ | ✗ | ✗ |
| `sts-components` | ✓ | ✓ | 同层 ✗ | ✗ | ✗ |
| `sts-server` | ✓ | ✓ | ✓ | 同层 ✗ | ✗ |
| `sts-app` | ✓ | ✓ | ✓ | ✓ | 同层 ✗ |

> **"同层 ✗"**：同一层的模块之间不建立 Maven 依赖。需要互相调用的服务走 HTTP / 消息，而不是把对方的 jar 拖进自己的 classpath —— 后者会让两个服务在部署时被意外绑死（改一个必须重新发布另一个），微前端/微服务拆分就白做了。
>
> 若两个同层模块确实要共享代码，说明这段代码**放错层了**，应下沉到 `sts-components` 或 `sts-common`。

---

## 三、为什么分层要卡这么死

分层本身不产生价值，**能被构建系统强制执行的边界**才产生价值。

- 依赖方向写反 → `mvn` 直接报循环依赖，**编译期就失败**，不需要靠代码评审去发现。
- 跨层跳跃被禁止 → 防止 `sts-common` 变成"什么都能塞"的口袋。一旦它开始依赖上层，就会滚成一个谁都依赖、谁都不敢改的巨型模块，最终只能整体重写。

> 出现"我确实需要跨层用一下"的时候，正确动作是**把那个能力下沉到合适层次**，而不是在 POM 里加一行依赖。加一行是五分钟的事，偿还它需要几个月。

## 四、模块内部怎么分

模块间按**业务域**切；模块内部按**特性（feature）**分包。

```
com.bluewhale.sts.system          ← 模块：系统域
├── SystemApplication.java
├── health/                       ← 特性：健康检查
│   ├── HealthController.java
│   ├── HealthService.java
│   └── HealthVO.java
└── <下一个特性>/
```

对比"按技术层分包"（`controller/` `service/` `repository/` 各占一个顶层包）：

|  | 按技术层分 | 按特性分 |
|---|---|---|
| 改一个功能 | 跨 4 个包来回跳 | 集中在 1 个包内 |
| 包边界约束 | 无 —— 可从 controller 直连 repository | 特性包即边界 |
| 拆服务 | 需要把散落各处的类挑出来 | 整个包搬走即可 |
| 新人理解成本 | 要先建立全局地图 | 看目录名就知道系统有哪些能力 |

**结论：按特性分包。** 单个特性超过约 10 个类时，再在其内部按 `domain` / `application` / `infrastructure` 细分 —— 此时边界已由包名自然形成，不会退化成技术层分包。

## 五、与前端结构的对照

两端的**组织形式不同，但治理原则一一对应**：

| 关注点 | 前端 `web/` | 后端 `server/` |
|--------|-------------|----------------|
| 工作区 | pnpm workspace | Maven 多模块 |
| 聚合入口 | `pnpm-workspace.yaml` | `server/pom.xml` |
| 版本治理 | `catalog:` 段 | `sts-parent` 的 `dependencyManagement` |
| 公共层 | `packages/common-*` | `sts-common-*`、`sts-components-*` |
| 应用层 | `platform/*` | `sts-app-*` |
| 边界铁律 | `packages/*` 不得反向依赖 `platform/*` | 禁止反向依赖与跨层跳跃 |
| 空壳策略 | 按需建包，不预置 | 按需建模块，不预置 |
| 公共能力注入 | 显式 import | 自动配置（`AutoConfiguration.imports`） |

**刻意保持不同的一点**：前端按「端」切应用（用户端 / 管理端），后端**不按端切** —— 两端操作同一批业务对象、同一套状态机，按端切会让领域逻辑复制两份。详见 `docs/decisions/0001`。

|----|------|
