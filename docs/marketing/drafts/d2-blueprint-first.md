## 正文

上一篇的结尾，我说下一篇拆权限中心。

写完才发现顺序不对：图纸没铺开，就讲某一根柱子怎么浇，读者只能听个响。所以第二篇先交这张图——这栋楼有几层、按什么顺序浇、每种材料为什么选它。权限中心挪到第三篇，它跑不掉。

### 先说清这栋楼有几层

【此处插入四层架构图】

蓝鲸系统现在不是一个简单「项目」，是一片工地。四层架构，图里自下而上是依赖顺序：地基 → 底座承重墙 → 业务域 → 前端基座。

最底下是基础设施（第 1 层，地基）：MySQL、Redis、Nacos、RabbitMQ、Nginx，用一份 Docker Compose 编排，执行 `docker compose up -d` 即可一次性拉起，五个容器全部 healthy；MySQL 自动建出十余个 `bluewhale_*` 业务库。这一层追求的就是无聊、稳定，没有太多故事，负责打好底层地基。

往上一层是平台底座（第 2 层，承重墙）：网关、权限、文件、表单、工作流、定时任务、审计、告警、消息。这一层是整栋楼的承重墙，也是这套系统和一堆简单 CRUD 拼接项目最本质的区别。

底座只有一条铁则：业务域不重复造基础设施。OA 发起请假单，不需要自己实现登录鉴权、不需要手写审批流、不需要开发附件存储、不需要自己实现操作日志；直接调用 whale-workflow 启动流程，调用 whale-file 完成附件上传，方法上标记 `@AuditLog`，审计日志就由底座统一采集。一个新业务服务，真正需要开发的，只有自身业务表与业务规则。

再往上是业务域层（第 3 层）：ERP、MES、PDM、OA、CRM、项目管理、合同签章、LMS 培训考试、党政工会、商城、音乐、视频、城池场景、IoT 孪生……每一个都是独立服务、独立数据库、独立前端子应用，可以按需启用，不用即可关停。

最上面是前端基座（第 4 层，最上层）：一套 qiankun 主基座，挂载二十六个子应用。管理端、运维端、企业门户互相独立，各个业务应用互不干扰，共享同一套请求层、同一套主题、同一套权限组件。

后端采用 Maven 聚合工程，划分为：whale-parent（统一版本管控）、whale-common、whale-sdk、whale-services、whale-apps、whale-ops、whale-registry。前端基于 pnpm workspace + Turborepo，划分为：共享包、组件库、平台应用、独立 SPA。

这套分层不是前期设计好直接落地的。是迭代到中途，发现每新增一个业务，就要重复对接一遍权限、文件能力，才回过头重构收敛出来的。

### 十五个 Phase 不是十五件事，是一条依赖链

路线图 Phase 1–15，看着是十五个并列任务，本质是一条强依赖链：中间件 → 底座 → 前端基座 → 业务应用 → 交付部署 → 智能能力 → 平台深化 → 项目收线。

Phase 1，打通基础设施。这一步成就感最低，但决定后续所有故障区分是业务 Bug 还是环境问题。当初实机验证阶段踩过镜像源的坑，后续直接沉淀进环境变量模板。

Phase 2，打磨平台底座。也是整个系统投入时间最多的阶段：权限中心实现六层级模型（系统 → 菜单 → 接口 → 按钮 → 数据 → 属性，RBAC + ABAC 并存）；网关对接 Nacos 动态路由，实现限流、熔断、内网接口屏蔽、TraceId 链路追踪；表单从单纯 JSON 字段演进为三层元数据 + 版本化物理表；工作流从简单顺序审批迭代为状态机内核 + BPMN 2.0 双向解析。本阶段结束，二十八个模块可以完整全量回归构建。

Phase 3，完成前端基座。登录、路由守卫、多标签工作台、主题体系、子应用错误兜底。这一层如果缺失，后续二十六个子应用，每一个都要重复处理同类问题。

Phase 4，落地业务应用与运维能力。先把 ERP / MES / PDM / OA 四大主线跑通列表、表单、真实接口；再落地项目管理、电子签章合同中心、音乐平台、视频平台。前端全部移除 Mock 占位数据对接真实接口，同步补齐基座鉴权逻辑。

Phase 5，建设部署与 CI/CD。我给自己的验收标准不是「能够跑起来」，而是能够证明自己会坏掉。故意提交未使用变量、缺少 Javadoc 的代码，Backend CI、Frontend CI、Code Quality 三条流水线必须全部变红；代码回滚之后流水线再全部变绿。只有经历过变红再变绿的流水线才算真正门禁，从来不会失败的流水线只是装饰。

同批还落地三件关键工作：Maven Wrapper 入库保障构建可复现；Playwright 实现三条 E2E 自动化用例：登录权限渲染、表单建表填报、流程发起与会签；开发文档版本校验脚本，把文档版本与 POM 配置对账，注入虚假版本脚本直接非 0 退出。

至此系统实现自我构建、自我测试、自我缺陷校验。Phase 6 开始，核心命题从「能不能跑」转向「能不能查」。

Phase 6 与 7，构建系统内置知识 Agent。内嵌 Lucene 建立知识库，把代码、文档、DDL、依赖版本、Git 变更、运行时事实全部纳入索引，全仓约一千五百个文件切分为九千三百块文本块；具备可用大模型时启用 ReAct 自主编排，模型自主多次调用工具取证；对外暴露 MCP 只读接口，IDE 也可以查询系统信息，例如查询某个服务的端口。四十道黄金评测题，做到满分口径——答案可追溯，引用可以定位至具体文件与代码行，不是大模型主观自评。

Phase 8 到 13，批量落地全景业务域。城池场景 2D、CRM 客户商机、MES 七个业务上下文（七十张业务表，三百七十多个 Java 文件）、PDM 图文档、OA 协同、LMS 培训考试、党政工会。这里得到一个很现实的结论：MES 七十张表，最终没有拆分成多个微服务，而是单服务内部按业务上下文分包——拆分出新服务带来的跨网络调用、分布式事务成本，已经超过拆分带来的收益。

Phase 14，平台深化迭代。二十余个服务完成联调；全部接口实现路径版本化；自动生成 OpenAPI 契约与前端 TS 类型；网关路由治理，三十八条基础路由写入兜底配置文件，支持 Nacos 配置同 ID 覆盖；权限中心扩展 OAuth2.0、三方登录相关基座。

整个迭代周期，每一个 Phase 都要有外部可复现的验收标准，无法实机验证的不算完成。仓库 `docs/reviews` 存放两百一十一份检查报告，`docs/plans` 存放九十多份计划文档，约定只增不删。虽然看着繁杂，但所有过程均可追溯。

### 选材标准：三十年后还能修的东西

聊技术选型，重点不在于罗列用了什么，而在于，为什么放弃另外一些方案。

我的选材原则：优先选择长期维护、后续接手者可以维护修改的组件，不追逐当下热度。所谓「三十年后还能修」是一种比喻，核心诉求是避免强绑定小众、快速消亡的技术栈。

Spring Boot 4 + Java 21。选择 JDK 21 核心看重虚拟线程。业务系统大量 IO 等待，线程模型的影响，往往大于各种设计模式。

工作流，没有引入 Flowable、Camunda。这是被问最多的点，三点理由：

1. 这两套引擎表结构侵入性极强，国内审批特有的回退任意节点、比例会签、加签等能力，要么修改引擎底层表，要么外层再套一层适配；
2. 实际只需要 BPMN 2.0 做格式互通，并不需要它完整的运行时；
3. 引入重型引擎，出问题需要先吃透第三方内部实现，维护成本很高。

因此自研状态机内核，搭配轻量 BPMN 2.0 双向解析，支持导入导出标准 XML 用于外部系统互通，业务运行逻辑自主可控；设置两百节点上限、二十二个校验码；解析器加固，使用 JDK 原生 DOM，禁用 DOCTYPE、外部实体，限制文件体积。减少重型依赖，比减少业务代码更重要。

检索组件，没有引入 Elasticsearch。知识库仅近万个文本块，内嵌 Lucene，BM25 + KNN 向量 RRF 融合足够满足需求，重建索引十秒级（本机九到十三秒）。为这个规模单独运维 ES 集群，只是把运维成本换来了简历亮点。

限流熔断：不引入 Sentinel。限流采用 Redis 计数器，统一 429 返回报文；熔断早期自研，后续替换为 resilience4j 2.3.0，它已经有成熟实现，没必要重复造轮子。Sentinel 完整做过评估，产出结案报告，结论不引入。评估过但不用，也要留存文档，避免后续反复重新评估。

数据库：MySQL，目标兼容国产数据库。实话实说，当前只在 MySQL 完成完整验证；达梦、人大金仓、OpenGauss、OceanBase 适配属于 M2 准入目标，尚未完成全量兼容。行业常见的误区：把目标直接宣传为现状。

Redis + Redisson、RabbitMQ、MinIO：分别承担分布式锁与令牌黑名单（登出 Token 立即失效已经实机验证）；异步审计与业务事件，MQ→HTTP→本地三级降级，消息队列故障业务不能不可用；文件存储 SPI 插件化，本地文件、MinIO 切换仅改配置，业务代码零改动。

前端 React 19 + Vite + qiankun + Turborepo。二十六个子应用，是选择微前端的真实理由：否则任意子应用改动，都需要完整全量构建，开发效率会严重拖慢。没有选用 Next.js，后台系统不需要 SSR 带来的复杂度。

AI 模块独立 ai/ FastAPI。整套 AI 能力作为独立内网服务，仅暴露内网 8092 端口。刻意隔离：大模型相关框架迭代速度远快于业务代码，必须作为可整体替换外挂，不能耦合进业务微服务。

还有一条特殊选型约定：README 不硬编码版本号，全部指向 POM 作为事实源。文档写死版本号，一定会出现文档和代码版本漂移。配套版本对账脚本，胜过依赖人手工维护文档。

### 三次推翻重来

选型是静态纸面清单，真正痛苦的是动态取舍。项目里面有三次重要自我推翻。

第一次：表单引擎演进。最初方案直接用 JSON 字段存储表单数据，实现简单，但业务字段上百列的时候会彻底暴露短板。重构为主从分离 + 版本化物理表，发布表单动态生成物理数据表 `form_data_{code}_v{version}`，字段落地真实数据库列。后续又发现一张物理表只能绑定一张表单也不合理，迭代出三层元数据模型：表定义层管理真实列；表单视图层管控 UI 控件、布局；选项独立表存储；实现一张物理表可以被多张表单视图复用。关键概念解耦：存储类型 `data_type` 和控件类型 `widget_type` 分离。同一个 VARCHAR 数据库列，可以渲染文本框，也可以渲染下拉选择。

还踩过真实数据才会暴露的 Bug：早期修改表定义逻辑，整体逻辑删除全部列再重建，导致已有表单视图元数据全部悬空。修复方案：按照列编码就地合并，保留列主键。这类缺陷单测很难覆盖，只有真实业务数据运行才会暴露。

第二次：工作流引擎迭代。第一版仅支持简单顺序单待办，能用但是很脆弱，不支持并行、会签、回退。逐步叠加状态机内核统一流转逻辑；SpEL 受限条件表达式；并行网关、全票 / 任一 / 比例会签；转办、委派、回退至任意节点；增加流程定义版本快照，支持运行中实例迁移。版本快照是被现实倒逼出来的：修改流程定义，旧的在途实例不能直接跟着新版跑，实例必须锁定发起时刻对应的版本。

第三次：服务粒度重新判断。我最初固有认知，业务域就要拆分成多个微服务。做到 MES 阶段踩刹车。七十张业务表、七个业务上下文，如果拆为七个独立微服务，简单查询工单状态就需要多次跨服务调用，还要处理分布式事务。最终方案：单微服务，模块内部按照业务上下文分包。微服务拆分边界以「能否独立部署」为底线，不是拆的越细就越专业。过度拆分，只是给自己制造更多维护工作量。

### 现在站的位置

前面 Phase 不再逐条复述，聚焦当前所处 Phase 15，2026 Q4 收线蓝图，执行策略叫三线收敛：

- A 制造主攻：核心目标跑通完整制造业务链路。销售订单（鲸客）→ 生产订单（鲸造）→ 排产与报工 → 质检 → 入库（鲸营）→ 3D 看板（鲸城），看板展示真实业务数据。四条硬性验收口径：五个环节仅页面操作，不手写 SQL；订单每步状态变更完整留痕，记录操作人与时间；看板业务数据与数据库可对账校验，配套对账脚本；权限判定、订单列表分页、并发报工三组压测 P95 指标写入文档。
- B 协同做深：OA、CRM、项目、表单工作流底座，不新增大概念，聚焦补齐已有能力缝隙。
- C 空间做门面：IoT 孪生、城池可视化，服务制造主线的数据，不凭空生成业务数据。
- D 交易降为附属：商城模块不删除，但是优先级下调；什么都要做的系统，最后什么都做不完。

同时需要清偿技术债：文档门禁脚本强制落地、CI 实现 diff 增量构建、前端子应用鉴权遗留问题补齐。两项 M2 阶段前置条件：Nginx 真实网关环境验证 WebSocket 3D 联机；至少完成一套国产数据库，跑通权限中心加一个完整业务域。

回到第一篇提到的游戏化构想：依旧一行游戏化代码没有写。地基没有封顶，不急于做外壳装饰。

系统叫蓝鲸（BlueWhale），技术栈 Spring Boot 4 + React 19 + qiankun。想聊私有化部署或想看我踩过的坑，评论区或私信。下一篇，拆权限中心：它怎么从一个登录校验，长成角色成长体系的雏形。
