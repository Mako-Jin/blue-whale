## 正文

公众号第一篇文章，记录一个还在长出来、但已经长得很长的项目。

### 一、我到底在做一个什么东西

如果用一句话说：我在做一个把「公司」搬进代码里的系统，最终想让它变成一款「上班生活模拟器」——既能当企业级平台用，也能当游戏玩。

听起来有点疯。但这确实是我现在每天在做的事。

项目叫蓝鲸系统（BlueWhale Platform）。它起点是一个很正经的企业级全栈平台：Spring Boot 4 + React 19 + 微前端 qiankun + Docker，注册配置、权限中心、API 网关、工作流、表单引擎、文件存储、审计日志……一应俱全。

但它没有停在「又一个后台管理系统」。

因为在往里填功能的过程中，我逐渐意识到一件事：企业系统其实就是一个人上班生活的全部场景。你登录、你被分配任务、你审批、你请假、你报销、你参加培训、你投票、你看公告、你走流程、你被 KPI 追……这些不就是一个人的一天、一年、一辈子的切面吗？

所以我给它定了一个更大的目标：把游戏性与工作系统结合。系统里那套权限、流程、数据、看板，不只是工具，也可以变成玩法。

### 二、它现在长什么样（诚实版）

我不是来吹「已完成」的。这个项目还在进行中，而且我能很具体地说出它进行到哪一步。

打开我仓库里的 roadmap.md，你会看到一份长得夸张的路线图，分成了十几个 Phase。大致是这样的：

基础设施：Docker Compose 拉起 MySQL / Redis / Nacos / RabbitMQ / Nginx 五件套，全部 healthy；Nginx 的 HTTPS、HSTS、TLS 1.3、/api/** 经网关登录端到端打通。这部分是实机验证过的。

核心服务：权限中心（RBAC + ABAC 六层级模型、JWT 登录刷新注销、分布式令牌黑名单）、网关（动态路由、限流、熔断、内网接口屏蔽、TraceId 链路追踪）、公共组件、国际化 SDK……这些不是画饼，是有单测、有冒烟、有 devlog 的。

业务服务：工作流引擎做到了状态机 + BPMN 2.0 双向 + 条件表达式 + 并行会签 + 加签转办回退；表单引擎做到了动态表引擎（主从分离、版本化物理表、多租户）和拖拽式设计器；文件服务做了插件化对象存储（local + MinIO）；还有定时任务、审计、告警、监控、门户……

更往后的 Phase：ERP / MES / PDM / OA / CRM / 合同 / 音乐 / 视频 / 学习培训 / 党建工会……对，你没看错，它甚至长出了「音乐平台」和「视频平台」的模块。

我知道这看起来很夸张。所以我想强调一句：路线图上的每一个 [x]，背后都有对应的代码、单测、检查报告和 devlog。这个项目我最骄傲的不是功能多，而是它有一套能自我记录、自我验证的工程纪律——需求登记册、代码检查清单、每次变更产出 docs/reviews/ 报告、CI 代码质量门禁、文档唯一真相源校验脚本。

一个人做这么大的东西，靠的不是天赋，是让系统自己管住自己。

### 三、为什么想把它做成「游戏」

这是这篇文章最想聊的部分。

企业系统天然具备游戏化的骨架，只是大家平时不这么看它：

权限 = 角色与解锁。你是什么角色，能做什么事，本身就是一套成长体系。

流程 = 任务链与关卡。一个审批流就是一个多阶段任务，节点就是关卡。

工作流引擎 = 状态机。状态流转、条件分支、并行会签、回退重来——这不就是关卡设计吗？

看板与报表 = 计分板。完成率、通过率、覆盖率，本质就是分数。

表单设计器 = 玩家自己造关卡。拖拽、配置、发布，用户既是玩家也是设计师。

消息通知、待办、催办 = 每日任务与提醒。

所以「游戏性与工作系统结合」对我来说不是硬贴一层皮，而是把系统里本来就有的机制，显式地当成玩法来设计。一个人上班的种种场景——被派活、赶 deadline、走流程、跨部门协作、被催、复盘、晋升——都可以被建模成可玩的结构。

上面这些说出来像脑洞，那就说一个真落地了的。

论坛那一块已经有一套完整的等级，六级，叫鲸阶：初入鲸门、观澜、听潮、破浪、领航、鲸首。发帖给分，被人投花给分，被题金榜给 200 分，在 7 天金榜上拿第一给 1000 分。这几个分值是我一条条定的，定完就等于把话说死了：灌 40 篇水帖，才等于被人加精一次；灌 200 篇，才等于一次金榜第一。制度不在文件里，在权重里。

这也是为什么项目会长出音乐、视频、学习培训这些「不像企业系统」的模块。因为一个人的上班生活不只有工单和审批，还有午休时听的歌、公司培训、工会活动、党建学习、内部社区。要模拟「上班生活」，就得把生活的褶皱也装进去。

### 四、一个人做这么大的项目，图什么

说实话，图的是把「工程」当成「作品」。

大多数企业项目是交付物：需求来了，做完，交付，结束。但我想要的是一个能持续生长、能被自己玩、能记录自己成长的东西。所以我会写 devlog，会写检查报告，会在路线图里给每个 Wave 编号，会把「未做」「阻塞」「遗留」老老实实标出来。

这个项目现在还远没完成。路线图里还有一堆 [ ]，还有「实机待环境」「需人工复核」「试点复盘待环境」这样的诚实备注。但正是这些备注让我觉得它是活的——它知道自己缺什么，也知道下一步该去哪。

### 五、这个公众号打算写什么

既然开了号，我想把它当成这个项目的「外传」来写。计划大概几类：

项目进展记录：某个 Wave 做完了什么、踩了什么坑、怎么验证的。不吹，只记。

工程方法思考：一个人怎么用纪律管住一个巨型项目；文档、门禁、检查清单为什么比热情更可靠。

「游戏化企业系统」的设计脑洞：权限怎么变成角色成长、流程怎么变成关卡、看板怎么变成计分板。

技术细节拆解：工作流引擎、动态表单、BPMN 自研、向量检索 Agent 这些有意思的实现。

失败与反思：哪些设计推倒重来了，哪些「已完成」其实打了折。

如果你也在做类似的事——一个人扛一个大系统，或者想把正经软件做出点玩心——欢迎关注、留言、拍砖。

蓝鲸系统还在长。这篇文章是它的第一块鳞片。

下一篇预告：从一个「权限中心」讲起——为什么我把 RBAC 和 ABAC 做成了六层级，以及它怎么变成一套「角色成长体系」的雏形。

附：如果你好奇它现在到底有多少东西——后端是 Maven 多模块聚合工程（services / apps / ops / sdk / common），前端是 pnpm + Turborepo + qiankun 的微前端矩阵，基础设施全 Docker 化。具体端口和服务清单在 docs/service-catalog.md。这个号以后会慢慢拆给你看。

## 为什么加了鲸阶那一段

原文第三节全部是"企业系统天然具备游戏化的骨架"——六条映射，逻辑很顺，但**全是类比，没有一个已发生的例子**。而你在第五节恰恰把"游戏化"归类成"设计脑洞"，等于自己承认了这一点。

一篇开篇文章，如果通篇说"我要做一个游戏化的企业系统"，读者的判断是"想法不错，做不出来"。但只要有一处是真的在运行的，读法就全变了——从"构想"变成"已经在验证的构想"。

鲸阶是目前唯一符合这个条件的东西：等级名、阈值、分值、匿名不给经验，全都已经在代码里跑着（`ForumProperties`）。所以我把具体的分值放进去了，而且用了"灌 40 篇水帖 = 一次加精"这种算法，因为这是别人抄不走的一句话，也是你定规则时的真实心态。

如果这段你不喜欢，删掉不影响其余部分——第三节到"都可以被建模成可玩的结构"为止是自洽的。
