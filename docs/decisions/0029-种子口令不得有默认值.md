# 0029. 种子口令不得有默认值，开发口令不得进生产包

- **状态**：已采纳
- **日期**：2026-10-13
- **决策者**：舰长

## 背景

处理 `0027`「发现但未处理」第 1 条。动手前先把那条链路**重新核了一遍** ——
"口令进了生产包"这个结论是对的，但 `0027` **记错了中间两环**，而记错会直接导致修错地方。

### 一、链路重核：真正把它带进产物的是另一条路

`0027` 记的链路是：

```
AuthProperties(默认值) → LoginRequest 的 @Schema(example) → openapi.json → schema.d.ts
  → platform-portal 的登录页默认值（Login/index.tsx） → 生产构建产物
```

逐环实测：

| 环节 | `0027` 的说法 | 实测 |
| --- | --- | --- |
| `Login/index.tsx` 的"登录页默认值" | 口令成了登录页的默认值 | **错**。口令初值是**空串**（`useState('')`）；硬编码的只有 `tenantCode='default'` 与 `username='admin'`，都不是秘密 |
| `@Schema(example)` → 生成物 | 一路流进产物 | **半对**。它确实流进了 `openapi.json`（第 4028 行）与 `schema.d.ts`（第 1616 行），但落在 **JSDoc 注释**里 —— 注释不进产物 |
| 生产构建产物 | 已确认字符串在包里 | **对，但来源是另一条**：登录页把两个口令**印在页面上**（`<code>…</code>`），而那一页被打进 `platform-portal` 的包。`grep -ro` 在 `dist/assets/index-CcyZqBqW.js` 里命中 **1 处** |

**这个纠正有实际后果**：只修 `@Schema` **不会**让口令从生产包消失。
若照记错的链路去修，会得到一个"改了好几处、包里还在"的结果；
而如果不做"构建后 grep 产物"这一步，还会以为已经修好了。

### 二、真正的危险不是"开发机看得到"，而是"生产**静默地**得到一个口令公开可查的管理员"

`AuthProperties.SeedAdmin.password` / `SeedAuditor.password` 此前是**默认值**（写在本仓库里）。
这意味着：任何环境只要**打开种子开关**且**没有覆盖口令**，就得到一个口令公开可查的管理员。
而 `application-mysql.yml` 的说明**恰恰教人这么开**：

```bash
BW_DB_PASSWORD=<密码> java -jar sts-app-server.jar --spring.profiles.active=mysql \
  --bluewhale.auth.seed-admin.enabled=true --bluewhale.auth.seed-auditor.enabled=true
```

h2 下无害（每次启动都是空库）；mysql / dameng 下就是一条真实入口。
**它是"默认口令"这一类问题里最典型的一种：不是有人做错了什么，而是默认值替人做了决定。**

### 三、四处副本必然失步

同一个口令散在：`AuthProperties`（默认值）、4 个 `verify-*.mjs`、登录页提示、
两个控制台的 dev 自动登录。而 `scripts/README.md` 的硬性约束**明写**：

> **凭据走环境变量**：脚本里不出现任何密码（见 `docs/decisions/0003`）。

这条规矩已经名不副实很久了。而且它不只是"违反约定"—— 那是把一个**会变的值**复制了 4 份：
口令一改，四个脚本会一起静默失效（症状是"e2e 登录失败"，而不是"某处配置不一致"）。

## 决策

### 一、种子口令**没有默认值**；开了种子却不给口令 ⇒ **拒绝启动**

`AuthProperties` 的两个 `password` 字段清空；`DefaultAdminSeeder#requirePassword`
在**任何落库动作之前**校验，两个口令都齐了才开始写。

**为什么是启动失败**：另外两种做法都会骗人 ——

- "跳过种子"：安静地不种任何账号，而运维以为自己有一个。症状推迟到第一次登录才出现，
  那时现场已经离配置很远了；
- "给个默认口令"：就是要消灭的那件事本身。

启动失败是唯一不会骗人的信号，而且它把错误**定位到了那一行配置**。

**代价是明白的**：从"默认口令时代"升上来的部署会被挡在启动阶段，必须显式给一次口令。
这是有意的 —— 静默沿用旧默认口令比启动失败危险得多。

### 二、开发口令的真值来源收拢到 `application-h2.yml`

全仓唯一一处。其它地方**要么从它取，要么明确标注"必须与本文件一致"**：

- `scripts/lib/seed-credentials.mjs`（新增）从它读，4 个脚本不再各抄一份；
  支持 `BW_SEED_ADMIN_PASSWORD` / `BW_SEED_AUDITOR_PASSWORD` 覆盖
  （要指向另一套账号时用）；**读不到就抛错**，不安静地返回 undefined ——
  否则脚本会拿着空口令去登录，报一个与真正原因相隔很远的错；
- 登录页的开发提示是"必须与它一致"的第二处（前端读不到后端 yml，这是无法消除的重复，
  所以用注释把它标成"同一个值的两处"）。

h2 是开发 / 演示 profile，那两个口令**不是秘密**。它们的问题从来不是"被开发机看到"，
而是**曾被印在会被发布的东西上**。

### 三、`@Schema(example)` 不留口令

`LoginRequest.password` 去掉 `example`。理由与"它进不进产物"无关：
**契约是要发布出去的东西**，把真实口令写进示例等于印在公开文档上。
而且"口令"这个字段**没有有意义的示例** —— 能填进 `example` 的只可能是某个真实口令。

### 四、登录页的开发提示只在 dev 构建里存在

`import.meta.env.DEV` 门控。Vite 在生产构建里把它替换成字面量 `false`，
这段连同口令一起被摇掉。

**这是本切片唯一直接修掉"口令进生产包"的动作**，验证方式是**真的构建一次，再去 grep 产物**：

| 时机 | `platform-portal/dist/assets/index-*.js` |
| --- | --- |
| 修复前（`index-CcyZqBqW.js`） | 命中口令 **1 处** |
| 修复后（`index-nvSIZGeb.js`） | 口令片段 / 提示正文 / 提示首句 **全部零命中** |

三条都查，而不是只查口令：只查口令的话，"把口令涂掉"和"整段摇掉"看起来是一样的。

### 五、旧 ADR 不回改

按本仓惯例（`0027` 处理 `0026` 的未覆盖项时也是这么办的），**不回改 `0027` 正文**。
它那句记错的链路由本篇纠正。`docs/README.md` 的规则表新增一行承载它。

## 后果

**正面**

- "生产静默得到已知口令管理员"这条路径**在结构上被堵死**：没有默认值可继承。
- 开发口令从 4 份副本收敛到 1 份，`scripts/README.md` 的硬性约束**第一次真正成立**。
- 生产包里不再有开发口令（经过构建 + grep 验证，不是"应该没了"）。
- 公开契约里不再有口令示例。
- 新增 4 个单元测试钉住"拒绝启动"这条规矩，**并顺带钉住了"先校验、再落库"的顺序** ——
  测试里依赖全传 `null`：顺序一旦反过来（先种管理员、再校验审计员），用例会立刻 NPE。

**负面 / 代价**

- **h2 种子现在必须显式给口令**（在 `application-h2.yml` 里）。这是必要的：
  留一个"h2 专用默认值"就等于把默认值换个地方放而已。
- 登录页的开发提示**只在 dev 构建里出现**。生产构建下那一段是空的 ——
  对开发是"看不见提示"，对生产是"看不见提示"，两者看起来一样。
  这是刻意的：提示里的口令对生产没有任何用处。
- 登录页提示与 `application-h2.yml` 仍是**两处**（前端读不到后端 yml）。
  已用注释在两处互相标注；这是无法消除的重复，只能显式承认。

**后续约束**

- **任何"种子账号"都不得带默认口令。** 新增种子项时照 `requirePassword` 的模式办：
  先校验全部输入，再落库；缺输入就拒绝启动。
- 给脚本加新的种子依赖时，**从 `scripts/lib/seed-credentials.mjs` 取**，不要在脚本里抄口令。
- 前端任何"把开发凭据写出来"的地方都要 `import.meta.env.DEV` 门控，
  并且**验证方式是构建后 grep 产物**，不是读代码判断。

## 本决策未覆盖

- **自助改密接口**：仍是 `0020` 留下的那一项（防重用目前只在管理员重置路径上生效）。
  种子口令现在必须显式给，但**改口令**仍没有自助入口。
- **密钥级配置**（JWT 密钥等）的收口：本条只管口令，`0003` 对密钥那条的落地情况未复核。
- **`must_change_password` 的用法**：`ensureUser` 里写死 `0`，也就是说种子账号
  登录后不会被要求改密。开了种子的真实部署应当把它设上 —— 但那是种子语义的另一个决定。

## 发现但未处理

### 1. 4 个子应用的 dev 自动登录账号仍带着同一个口令

`platform-admin` / `platform-audit-console` / `platform-log-console` / `platform-event-console`
的 `src/auth/index.ts` 或 `src/console.ts` 里各有一处：

```ts
password: import.meta.env.VITE_DEV_PASSWORD ?? "Admin@12345"
```

**它比登录页那条轻**：`allowDevAutoLogin` 是 `import.meta.env.DEV`，生产构建下为 `false`，
所以这个账号**从不被使用** —— 是惰性的常量，不是被展示的凭据。但字符串仍在包里。

**为什么本轮不做**：干净的修法是让 `ConsoleAuthOptions.devAccount` 变成可选
（"凭据只在允许自动登录时有意义"），而那要动 `common-api` 这个被所有子应用依赖的共享包 ——
在一个长回合的末尾改共享包、再逐个复验消费者，风险大于收益。

**修法已经定好**：`devAccount?: …` + 各调用点用 `import.meta.env.DEV ? {...} : undefined` 构造。

### 2. 4 个后端测试仍写字面口令

`AuthApiTest` / `PasswordHardeningApiTest` / `AuditApiTest` / `ClientLogApiTest` 里
直接写着口令字面值，而同仓的 `RoleApiTest` / `UserGroupApiTest` / `DataScopeApiTest` /
`ResourceApiTest` 用的是 `properties.getSeedAdmin().getPassword()`。

**后者才是对的**：它让测试跟着配置走，口令再改时不会以"登录失败"的形式炸。
这是文档一致性，不是安全问题，留待顺手清理。

### 3. `0028`「发现但未处理」的两条仍在

非上报路径的 NAT 误伤（`/api/` 的按 IP 兜底）与多实例下的总量问题，都还没有处理。
