# 0058. 停用租户的效力与它的自锁边界：一句早已写下的判据，漏掉的第二个对象

- **状态**：已采纳
- **日期**：2026-10-14
- **决策者**：舰长

> 领的是 `0051`「未覆盖」第 1 条，而它当时被明确标成"**不修**，因为修它必须先回答下面那条"。
> 那一轮把两问写成必须一起决定的样子：**① 停用到底意味着"不许新登录"还是"现有会话也下线"；
> ② 后者成立时，谁来重新启用它（本仓没有"租户之外"的平台账号）。**
> 动手之前先去找这两问的答案，结果是：**第一问仓里已经答过了** —— `0046` 的「四」为
> "账号被停用"写下过这条判据，缺的只是同一条判据的**第二个对象**。
> 于是本轮没有新判据要定，只有两处落地，以及一个由此**才**成立的守卫。

## 背景

`0051` 未覆盖 1 的原文（实测、未处理）：

> **停用租户**对**已经在用的人**不生效 —— 一次性的探针实测：

| 停用之后 | 结果 |
| --- | --- |
| 重新登录 | `40101`（拒了） |
| 用停用前的刷新令牌**续期** | **`code: 0`（通了）** |
| 用停用前的访问令牌调 `/me` | **`code: 0`（通了）** |

> 根因在同一行代码里，而且**不对称就在那一行上**：**用户判了状态，租户只判了"非 null"。**

### 一、第一问已经答过 —— 答案就在 `0046`

`docs/decisions/0046` 的「四」逐条回答了"还有哪些状态变化该顺手撤一下会话"，
其中第一条正是本轮的形状：

> **账号被停用**：续期时读得到 `status`（`AuthService#refresh` 已经在拦），靠校验就够。
> 多撤一步的坏处很具体：管理员把状态改回启用，那个人**本可以不必重新登录**就回来（令牌还在）。

并给出那条可以被检查的性质：

> **撤销是主动清理，只用于无法从当前状态推出来的变化。**
> 换口令之后，旧刷新令牌看起来完全正常 —— 签名有效、`jti` 在库里、没有过期，
> **没有任何一列能说明"它属于上一任口令"**；所以只能撤。
> 而"停用 / 锁定 / 删除"都是**当前状态**，读的时候就知道，因此靠判断、不靠清理。

同一句话还写在 `SessionRevoker` 的类注释里（"那两件事是**当前状态**，每次校验时读得到，
靠判断而不是靠清理"），以及 `SessionRevocationApiTest` 的类注释里（"四例里有两例断言的是'没做'"）。

**所以租户这一格不是"判据不同"，是同一条判据的第二个对象没有落地。** 落地的那一格：

```java
// AuthService#refresh —— 本轮之后
if (tenant == null || user == null
        || !Status.ENABLED.wireName().equals(user.getStatus())
        || !Status.ENABLED.wireName().equals(tenant.getStatus())) {   // ← 这一行此前没有
    throw AuthResultCode.SESSION_INVALID.businessException();
}
```

三件事合起来让这个漏项不显形：`AuthTokenFilter` 是**无状态、不查库**的；访问令牌有
2 小时有效期；**刷新令牌是轮换的**（每次续出一个新的、有效期重新起算）。
⇒ **只要一个会话在被使用，它就永远续得下去，与租户的 `status` 无关。**

> **这一族的形状值得单独记一笔。** `0022`（停用角色）· `0024`（停用用户组）·
> `0045`（口令过期只在登录拦）都是"**状态列没有读者**"；`0056` 是"**看不见的占位者**"。
> 本片是第三种：**读者名单里少了一个** —— `bw_auth_tenant.status` 有读者（登录读了、
> `assertAcceptsNewData` 读了），只是**该读它的那条路没读**。
> 这种缺口比"零读者"更难发现：查"谁在读"能查到人，"零读者"一眼可见；
> 而"两个读者、少了第三个"要问的是"**还有哪条路会用到这个状态**"。

### 二、两处缺口是实测的（照 `0055` 立的规矩）

先写用例（`TenantDisableApiTest`）、跑**未改动的代码**，读数是四条：

| 用例 | 读数 |
| --- | --- |
| 停用后**续期** | `expected:<40106> but was:<0>` |
| 停用 → 重新启用 | `expected:<40106> but was:<0>` |
| 停用**自己所在**租户 | `expected:<40921> but was:<0>` |
| 删除**自己所在**租户 | `expected:<40921> but was:<0>` |

后两条是**新撞出来的**：`0051` 只写了"停用自己所在租户"这件事，
而**删除自己所在租户此前从未被任何文档提过** —— 它与停用是同一件事的另一半
（`@TableLogic` 让被删租户在应用层**等于不存在**，对登录的影响一模一样），
而 `TenantService#delete` 的守卫只查"仍有子租户"，不查"是不是自己"。

### 三、第二问也有答案 —— 而且"不清理"让这个答案更好看

**恢复入口 = 另一个租户里持有 `auth:tenant:update` 的账号。** 本仓权限是扁平的
（`auth:tenant:*` 没有租户内隔离，见 `0049` / `0050`），所以本仓的形态就是
**种子租户的管理员**（`DefaultAdminSeeder` 建的根租户那一个）。

"谁来重新启用"之所以在本轮**变得更容易回答**，正是因为决策 1 选了"靠判断、不靠清理"：

- 租户被停用期间，那个刷新令牌**没有被作废**（续期失败时不轮换，见 `0045` 决策 3）；
- 于是重新启用之后，**同一个刷新令牌立刻又能续期** —— 那个租户里所有人
  **不必重新登录**就回来了。

这是 `0046` 给的那条收益，在本片第一次有了用例（`shouldKeepSessionsAndResumeAfterTenantReEnabled`）。

**剩下的唯一真陷阱是"停用 / 删除自己所在的那个租户"**：操作者本人的续期会失败，
而重新登录会被拒（登录先拒 `status != ENABLED` 的租户）——
于是恢复只剩"另一个租户的管理员"，**根租户自己则只剩直接改库**。
这与 `40917` 拒绝停用系统内置角色的理由一字不差：

> 一次点击造成的后果需要连数据库才能撤销，**这种操作不该由一个 HTTP 接口提供**。

### 四、为什么这两处必须同一次落地

`0051` 当时把"停用自己所在租户"记成"**没那么急**"，给的理由是实测出来的：
停用之后既有会话照常续期 ⇒ **恢复入口还在**（拿着访问令牌就能把 `status` 改回来）。
那条理由正是本轮要拿掉的东西 —— 续期一判租户状态，退路就没了。
所以两条不是"顺带一起做"，而是**后者的前提被前者抽走了**。

## 决策

### 1. 续期与登录同判：租户状态并进 `refresh` 那一行

四个条件写在**同一行**、给**同一个码**（`40106` `SESSION_INVALID`）。
不分成四个码是刻意的：调用方能做的事完全一样（重新登录），
而"我为什么被请出去"不该在响应里被区分 —— 登录侧同样的理由让它把
"停用"与"不存在"都返 `40101`（见 `AuthResultCode.TENANT_DISABLED` 的注释）。

### 2. 不撤销任何令牌（靠判断、不靠清理）

`SessionRevoker` **不参与**这件事。若在这里顺手撤一遍，就会得到 `0046` 逐条论证过的那种坏处：
管理员把租户改回启用之后，那个人**本来可以不必重新登录**。
用例把这一条钉成**正断言**（`assertEquals(1L, aliveRefreshTokens(userId), "停用不该顺手清会话")`），
与 `SessionRevocationApiTest` 里"账号被停用 / 被锁定**不**撤销"是同一形状 ——
只钉"该撤的撤了"，下一次有人"顺手也撤一下"就没有东西会红。

### 3. 新增 `SELF_TENANT_PROTECTED(40921)`：不可停用 / 删除自己所在的租户

挂在 `TenantService#update`（把 `status` 写成非 `ENABLED` 时）与 `#delete` 上，
两处**同一个码**（后果相同、处置相同：去管理别的租户）。
判据是**身份与被操作对象的相等关系**，不是操作本身。

### 4. 守卫只拦"自己所在的那一个"

停用 / 删除**别的**租户照常 —— 那是管理动作，操作者站在门外、随时可以反向操作。
把守卫写成"谁都别停"会让这个能力形同虚设，所以**反例写在正题里**：
前两例停用的都是别的租户且期望成功（`code 0`）。

身份取自 `AuthContextHolder#currentTenantId()`，**不接受调用方传入**
（与 `AuthService#logoutAll` 那条"只能撤自己的"同一种写法）。
**没有身份上下文时不判**：这个守卫要挡的是"操作者把自己关在门外"，
没有身份就没有那个操作者（所有写路径都在 `@RequiresPermission` 之后，HTTP 上不存在这一支）。

### 5. 残留如实钉住，而不是顺手关掉

停用之后，**访问令牌在它的有效期内仍然可用**（`/me` 照常返回 `code: 0`）——
这是无状态认证过滤器的固有代价，与 `logout` / `changePassword` 接受的是同一量级
（撤销无状态令牌要引入黑名单存储，每个请求多查一次）。
用例把它写成一条**正断言**并附上理由：谁要是去动认证过滤器，这一条会先红，
他必须回头读这段（与 `0046` 决策 5、`0045` 的残留处理同一种做法）。

## 后果

- **停用这个动作对已经在用的人生效了**。对外可见的变化如实记：停用租户之后，
  该租户用户的**续期**请求从 `code: 0` 变成 `40106`；他们在访问令牌到期时被请回登录页
  （前端不需要新逻辑 —— `0045` 的"被请出去时的原因"机制已经覆盖这个码）。
- **恢复不必重新登录**：重新启用之后，手上那个刷新令牌立刻又能用（决策 2 + 三）。
- **自锁从"只剩改库"变成"HTTP 拒绝"**，且这条守卫**不限制正常的租户管理**。
- **代价（如实记）**：停用与"所有会话立即下线"之间有一个**访问令牌有效期**的窗口
  （默认 2 小时，决策 5 钉住）；`sessionRevoker` 一行未动，
  于是已停用租户的刷新令牌行会一直留到自身过期 —— "该租户被停用了多久"在库里有，
  但"因此失效了几个会话"没有痕迹（见未覆盖 4）。
- **契约零变化**：`openapi.json` 与 `schema.d.ts` 不动 —— 没有接口面变化，
  改动全在"同一个响应背后的会话状态"与新错误码上（错误码不进契约）。
- **一处此前只能靠推断的说法落地**：`server/README.md` 硬规则行里
  "**`bw_auth_tenant.status` 有两个读者**""要修得先定停用是否等于现有会话也下线"
  两处同时订正（后者是本轮回答的问题本身）。

## 未覆盖

- **`TenantService#update` 不过 `resolveStatus`**（与同一个类的 `create` 不同）：
  写进来的就是那个字面量，于是 `{"status":"disabled"}`（小写）或任何拼错的值
  **照样能落库**，而所有读者都在比 `"ENABLED"` ⇒ 一个拼错的状态值等价于"停用这个租户"。
  本轮的守卫因此把判据写成"**写入的值不是 `ENABLED`**"而不是"从 `ENABLED` 变成别的"，
  把它一并挡住了，但那是**顺手挡住**，不是处置。要不要让 `update` 也走 `resolveStatus`
  （宽容成 `ENABLED`，与 `create` 一致）或者反过来**拒绝非法值** —— 是另一条判据；
  `0051` 记过 `resolveStatus` 对租户的宽容是 `0009` 族的刻意差异，本轮**没有碰它**。
- **改存量数据仍不受 `40920` 约束**（`update` 不重新解析租户）：要挡得先回答
  "停用是**只读冻结**还是**整租户下线**"。本轮答的是后者（会话也下线），
  而"冻结存量数据"那一半没有答 —— 两者可以并存，但不是同一件事。
- **在停用的父租户下建子租户**（`TenantService#resolveParent` 只查存在性）——
  `0051` 未覆盖 2，本轮**仍未处理**。它的后果与停用租户不同
  （子租户的用户照常登录，不是"不可达数据"），所以不与本片同格。
- **停用租户时不留"因此失效了几个会话"的痕迹**：`revokeAll` 的返回值至今无人消费
  （`0046` 未覆盖 4）；本片又多了一处"本该有人消费它"的地方。
- **`auth:tenant:*` 是扁平的**：守卫只挡"自己所在"，挡不住"甲租户的管理员停掉乙租户"
  —— 那是 `0050` 未覆盖 1 的正题（平台级 vs 租户级管理台），本轮**没有碰它**。
- **粒度更细的会话管理仍缺**：管理侧"踢掉某个人的会话"（`0047` 未覆盖 1）与
  会话列表都还没有；本片给的是**整租户**粒度 —— 它能解决"这个租户别进了"，
  解决不了"这个租户里某个人别进了"。
- **同一形状的第三个对象没有被扫过**：本轮核的是 `bw_auth_tenant.status` 这一格。
  `0054` 那张表的口径是**列名模式**，而"**还有哪条路会用到这个状态**"这个问题
  对它口径之外的开关（`revoked` / `must_change_password`）以及非开关的状态列都没扫过
  —— 本片撞出的第三种形状（"读者名单里少了一个"）**目前仍靠逐个偶然撞见**。
