# 0071. 写入值的规范化

> 领 `0069`「未覆盖」4 与 `0070`「未覆盖」7，两处原文是同一句话：
> 「**写入值（`entity.setXxx`）仍然不统一**……`resolveStatus` 这类在部分域走（归一）、
> 部分域原样入库（`TenantService.update` 是已知的一处，见 `0058`）……
> 本轮把**过滤侧**收干净之后，这个不对称更显眼了 —— 但它是"写入"侧的事，未做。」
>
> 核完发现它不是"写入侧顺手补一下"，而是**前两篇留下的一处逻辑缺口**：
> `0069` 给 `FilterValue` 写的类注释里有一句"**各域写库前都过了一遍规范化，所以库里的值
> 不会带两端空白**"—— 那句话当时只对**一部分**列成立（上报进来的 `app` / `namespace` /
> `traceId` / `sessionId` 是原样入库的，只被截断）。而读取侧的归一在没有写入侧配合时
> **不是"宽容"，是空转**：库里存着 `" myapp "`，读侧把 `?app=myapp` 规范成 `myapp`，
> 结果是**一条也匹配不到** —— 归一反而制造了假阴性。
>
> 另一半更重：`status` 的两条 `update` 路径。写入的值不只是"能不能搜到"的问题，
> **它就是读者与判据要看的那个值**——`AuthService` 判的是
> `Status.ENABLED.wireName().equals(entity.getStatus())`。于是用户域写入一个小写的
> `"enabled"` 会让**那个账号登不进来**，租户域会让**一整个租户登不进来**。

## 背景

### 1 射程：四组写入点 + 五份副本

判据是**"读侧会不会拿它做精确匹配"**：会，写入就必须走同一关。
按这条判据把全仓的 `entity.setXxx` 过一遍，只有四组落在射程里。

| 域 | 列 | 读侧（过滤） | 写入侧（改前） |
| --- | --- | --- | --- |
| 日志 | `app` | `FilterValue.text` | **原样** `request.getApp()` |
| 日志 | `namespace` / `traceId` / `sessionId` | `FilterValue.text` | `truncate(...)`，**只截断不 trim** |
| 事件 | `app` | `FilterValue.text` | **原样** `request.getApp()` |
| 事件 | `userId` / `deviceId` / `sessionId` | `FilterValue.text` | `truncate(...)`，**只截断不 trim** |
| auth | 用户 `status`（`update`） | `FilterValue.enumValue` | **原样** `request.getStatus()` |
| auth | 租户 `status`（`update`） | `FilterValue.enumValue` | **原样** `request.getStatus()` |

**已经一致、本轮一个字都没动的**（列出来是为了说明"四组"不是"所有写入点"）：

- 日志 `level` / 事件 `eventName`（枚举列）—— 写入走 `ClientLogLevel.parse` + `wireName()`，
  读走 `enumValue`，同一份 `parse`；`eventName` 见下面「刻意不做」。
- auth 其余每一列 —— 组织 / 角色 / 资源 / 用户组四个域的写入都集中在各自的
  `applyCommon` / `applyTo` 里，`status` / `orgType` / `category` / `parentCode` /
  `description` 这一批**早就过了规范化**（`resolveStatus` 或本域私有的 `normalize()`）。
  用户 / 租户两域的 `status` 只在 `create` 上过（`update` 漏了），**这就是那处不对称**。
- 审计域**整个不在射程**：它的写入在 `AuditInterceptor` / `AuditRecorder` 里，
  值取自 `@Audited` 注解与上下文，**不由外部输入决定** —— 没有"客户端传了个带空格的"这条路。

另外顺手收掉了**五份私有 `normalize()`**（`OrganizationService` ·
`OrganizationMemberService` · `ResourceService` · `RoleService` · `UserGroupService`）。
它们与读取侧那五份是同一个东西：实现逐字相同（`null` 进 `null` 出、否则 `trim()`、
空则 `null`），`0069` 收读取侧时留下的这五个副本现在一并合掉。
`ResourceService.normalizeMethod`（`normalize` + 往大写归一）**保留** ——
后半句是该列的**比较语义**（资源域的 `method` 存大写，与日志域 `level` 存小写反向同源），
不是通用规范化。它内部改调 `FilterValue.text()`。

### 2 两种后果，两种严重度

**(a) 搜不到。** 上报 `app = " myapp "` ⇒ 库里存 `" myapp "` ⇒
`?app=myapp`（读侧 trim 成 `myapp`）一条也匹配不到。
`namespace` / `traceId` / `sessionId` / `userId` / `deviceId` 同理。
**这一类是"功能在，但那个记录查不出来"，没有更坏的后果。**

**(b) 不只是搜不到 —— 写入的值就是判据要看的值。** `status` 那两处集中在 `update` 路径上：

- **用户域**：`PUT /api/auth/users/{id}` 传 `status = "enabled"` ⇒ 库里存 `enabled` ⇒
  过滤 `?status=ENABLED` 搜不到（(a) 类），**而且** `AuthService` 里
  `!Status.ENABLED.wireName().equals(user.getStatus())` 为真 ⇒
  **这个账号登不进来**。一次"保存成功"把账号锁在了门外。
- **租户域**：同一件事重一档 —— `AuthService` 判租户状态的那一处同样按字面量比 ⇒
  **那个租户下的所有人登不进来**。
- **租户域还多一层**：`TenantService#update` 里那条"不可停用自己所在租户"的判据
  也是拿请求里的字面量比的（`!Status.ENABLED.wireName().equals(request.getStatus())`）⇒
  小写的 `"enabled"` 被判成"**我要停用自己所在的租户**" ⇒ 得到 `40921`。
  调用方唯一做错的事只是拼写用了小写，而系统回了一句"你不能停用自己"。
- **`create` 与 `update` 对同一个字段宽容度不同**：`create` 走 `resolveStatus`
  （认不得就落 `ENABLED`），`update` 原样入库。同一个 `Status` 枚举、同一个 DTO 字段，
  两条路径两副面孔。

`0058` 记过 `TenantService.update` 不过 `resolveStatus` 这件事，当时给的理由是
"判据要与'读者怎么读'保持一致"——**那个理由本身没错**（读者确实按字面量比），
但它只解释了判据的写法，没有回答"写进去的为什么可以是任意字面量"。
`0070` 之后过滤侧认小写了，两条口径正式分岔 —— 这就是必须收口的那一天。

### 3 前端看不见这个区别

与 `0070`「背景 3」同形：**这不是任何界面上可观察的行为**。
管理页提交 `status` 用的都是常量 `ENABLED` / `DISABLED`；上报的 `app` 来自构建配置。
差异只能从 **API 调用方一侧**撞到 —— 一个自己写脚本调接口的人、一个用别的语言的客户端、
一个从别处粘贴过来带了两个空格的值。所以它既不会被界面测试碰到，
也不会被"照着前端行为写的用例"碰到。

## 一 实测：九条同形断言

`WriteSideNormalizationApiTest`（九例，**跨 profile** —— 本仓第七处，
形状同 `TextEqualityApiTest` / `SearchMatchApiTest` / `SearchWildcardApiTest` /
`SearchKeywordTrimApiTest` / `FilterValueTrimApiTest` / `EnumFilterNormalizationApiTest`：
不 `@Transactional`、不按 profile 跳过）。不改代码跑一次 = **7 红 2 绿**：

| 用例 | 改前 | 改后 |
| --- | --- | --- |
| 日志：`app` 带两端空白上报，`?app=<干净值>` 搜得到 | 红（0 vs 1） | 绿 |
| 日志：条目级 `namespace` / `traceId` 带空白，过滤能搜到 | 红（0 vs 1） | 绿 |
| 事件：`app` 带两端空白上报，两种过滤值同一结果集 | 红（0 条） | 绿 |
| 事件：条目级 `userId` / `deviceId` / `sessionId` 同上 | 红（0 vs 1） | 绿 |
| 用户域：`update` 传 `enabled`，回显该是 `ENABLED` | 红（回显 `enabled`） | 绿 |
| 租户域：`update` 传 `enabled`写入的是 `ENABLED`，**且该租户下的人仍能登录** | 红（回显 `enabled`） | 绿 |
| 租户域：对自己所在租户传 `enabled`（**这是启用，不是停用**） | **红（40921）** | 绿 |
| 事件名带两端空白仍按【拒收并计数】处理（**回归钉**） | 绿 | 绿 |
| 标准写法（`ENABLED` / `DISABLED` / 不带空白）照旧（**回归钉**） | 绿 | 绿 |

第三条红（`40921`）是"启用被当成停用"的现场证据；第六条的"且仍能登录"是**后果**的证据
（读者的判据是字面量比较，库里躺着一个 `enabled` 时口令再对也进不来）；
最后两条是回归钉 —— 尤其"事件名仍被拒"那一条，它钉的是**本轮刻意不动**的另一半（见下）。

**一处要记的用例缺陷（全量跑才暴露）。** "标准值照旧"那条起初写成
`assertEquals(1, totalOf(?status=DISABLED))` —— 单独跑绿、**全量跑红**（库里是 2 条：
别的用例也会留下 `DISABLED` 的用户）。修法是带上 `keyword` 把断言锁在本次建的账号上。
与 `FilterValueTrimApiTest` 里那条"先确认基准非空"是同一个教训的两面：
**断言条数时必须带一个能圈定本次数据的锚**。

## 二 决策

1. **写入侧复用 `FilterValue.text()`，两个方向共用一份实现。**
   读侧与写侧处理的是同一件事（"两端空白不算内容"），分成两个方法只会让它们有机会分岔。
   代价是类名（`FilterValue`）窄了 —— 见下面「刻意不做」第 4 条。
2. **判据是"读侧会不会拿它做精确匹配"，不是"它看起来像不像编码"。**
   这条判据把射程切得干净：`app` / `namespace` / `traceId` / `sessionId` / `userId` /
   `deviceId` / `status` 进，"日志消息 / 路由 / 版本号 / IP"与"名称 / 描述"不进。
   它也是 `0069` / `0070` 那条判据**在另一个方向上的同一句话**。
3. **`status` 的两条 `update` 过 `resolveStatus`，判据拿归一后的值去比。**
   归一到标准写法之后，"小写的启用被当成停用"与"写进去一个让读者认不出的值"两条
   同时消失 —— 判据与读者看的是同一个值，而且它就是 `Status` 的真值。
   **外层判空保留**（不传 `status` 表示"不改这一列"，不是"改成 `ENABLED`"），
   只是判空的形态换成 `FilterValue.text(...) != null`。
4. **顺序：先 trim，再截断。** `truncate(FilterValue.text(x), 64)`，不能反过来 ——
   反过来时，一长串超长空白会把后面的内容整个切掉，结果是一个纯空白值。
5. **五份私有 `normalize()` 删掉、改调 `FilterValue.text()`。**
   与 `0070` 删掉四个 `normalizeXxxFilter` 同形：这些副本的**行为完全一致**，
   所以这是一个纯粹的"收敛到一处"，不改变任何现有行为。
6. **`resolveStatus` / `resolveResourceType` / … 那一批 `resolveXxx` 保留在各自域，
   不上收。** 它们与 `enumValue` **刻意不共用一个方法**：读取侧的原则是
   "认不得就**按原样比**（结果为空集，不假装成功）"，写入侧的原则是"认不得就**报错**"
   （或者像租户 / 用户那样兜底成 `ENABLED`）。把两件事合并成一个方法，
   迟早会有人把其中一侧的宽容度带过去。
7. **不给 `UserSaveRequest.status` / `TenantSaveRequest.status` 加 `@Pattern`。**
   加了当然能在入口挡住 `"enabled"`，但那是把它从"**被归一**"改成"**400**"——
   而过滤侧（`0070`）认小写。同一个值"能搜、不能存"是更糟的不一致。
   写入侧的选择是**归一**，不是拒绝。

## 三 落地

**后端**（12 个已跟踪文件 +1 个新用例）：

- `FilterValue` —— 类注释改写：第一句从"过滤值 → 进 SQL 之前"改成"**文本值的规范化：
  过滤值进 SQL 之前、写入值进库之前**"；并如实写下那句曾经不成立的话
  （"各域写库前都过了一遍规范化"只对一部分列成立，`0071` 补上之后才成为事实）。
  `text()` 的 javadoc 补上"写入侧 `null` 表示这个值是空的"。**方法签名一个字没改。**
- `UserService#update` —— `status` 过 `FilterValue.text` + `resolveStatus`。
- `TenantService#update` —— 同上，**判据改拿归一后的值比**，并改写那段"本方法不过
  `resolveStatus`（与 create 不同）"的注释（那句话现在不成立了）。
- `ClientLogService#report` —— `app` 过规范化；`namespace` / `traceId` / `sessionId`
  改成 `truncate(FilterValue.text(...), n)`；`message` / `route` / `appRelease` / `ip`
  **一个字没动**（理由写在方法里的注释上）。
- `ClientEventService#report` —— `app` / `userId` / `deviceId` / `sessionId` 同上；
  `eventId` / `eventName` / `route` / `appRelease` / `ip` 没动。
- 五份 `normalize()` 删除（`OrganizationService` · `OrganizationMemberService` ·
  `ResourceService` · `RoleService` · `UserGroupService`），13 个调用点改调
  `FilterValue.text()`；`ResourceService.normalizeMethod` 保留但内部改调它。
- **前端零改动**、**契约零改动**（没有改任何 DTO 注解或 `@Operation` 描述）。

**守卫**（`scripts/verify-filter-values.mjs` 加**规则 5**）：
上报侧（`sts-server-log` / `sts-server-track` 两个模块）里
`entity.set<App|Namespace|TraceId|SessionId|UserId|DeviceId>(...)` 的实参必须含 `FilterValue`。
判据是"从 `(` 起取到配对的 `)` 的实参文本"—— 于是多行调用
（`truncate(\n FilterValue.text(…), 64)`）也认得出来。
这一条与规则 4 是同一枚硬币的两面：前四条管"读的时候归一"，它管"写的时候也归一"。

**文档**：本篇 + `docs/README.md` §二/§四 + `server/README.md` 硬规则表 +
`scripts/README.md`。

## 扰动验位

- **用例**：改前 **7 红 2 绿** ⇒ 改后 **9 绿**（改动必要且充分）。
- **守卫规则 5** 扰两次都报红、行号指向那条语句：
  ① 日志域的 `entity.setApp(FilterValue.text(request.getApp()))` 改回
  `entity.setApp(request.getApp())` ⇒ 报 `ClientLogService:111`；
  ② 事件域的 `entity.setUserId(truncate(FilterValue.text(...), 64))` 改回
  `truncate(item.getUserId(), 64)` ⇒ 报 `ClientEventService:112`。还原 ⇒ 五条规则全绿。
- **规则 5 的射程边界也验了**：`AuditRecorder` 里那句
  `entity.setTraceId(record.traceId())` **不报红**（审计域不在 `REPORT_MODULES` 里，
  且审计的 `traceId` 不参与过滤）；两个上报域里的 `vo.setXxx(...)` 也不报红
  （读出来的值，锚点认的是接收者 `entity`）。
- 规则 1-4（`0069` / `0070` 遗留）本轮未动它们的锚点，仍全绿。

## 后果

**正面**

- **"读侧归一"这件事现在才真的成立。** 在此之前它是"看起来像宽容、实际制造假阴性"：
  库里带空白的值越多，读侧归一得越干净，那些记录越搜不到。
- **`status` 的那两条路不再能"保存成功但把账号/租户锁在门外"**，也不再会把
  一个启用请求读成停用请求。
- **`create` 与 `update` 对同一个字段宽容度一致了。**
- 全仓"两端空白怎么处理"只剩**一处实现**（`FilterValue.text`），
  读取侧与写入侧共 30 余处引用它。

**负面**

- **写入侧多了一次 `String.trim()`**（每条上报日志 / 事件一次，共 4~5 次）。
  与读取侧那次同源，代价可以忽略；换取的是"库里不会再有搜不到的值"。
- **`FilterValue` 这个名字现在窄于它的职责。** 代价用类注释消掉（见「刻意不做」4）。
- **规则 5 的白名单是硬编码的六个列名**，与规则 4 同一个代价。

**后续约束**

- 新加一个"会被 `?x=` 精确匹配"的列时，**写入侧也要过 `FilterValue`**，
  而不是只在 `buildWrapper` 里加一行 `.eq(...)`。规则 5 只能守住**已有的六个列名**
  （新列名锚不到，见 `0070`「未覆盖」2 的同一条结论）。
- 写 `truncate` 的场合先想顺序：`truncate(FilterValue.text(x), n)`，不是反过来。

## 「未覆盖」

1. **达梦未实测。** 本篇改动全在 Java 侧（`trim` 与 `resolveStatus`），不落到 SQL 上；
   但"写入侧归一之后库里不会再出现带空白的值"这件事只在 h2 与真实 MySQL 上验过
   （与 `0067`「未覆盖」1、`0069`「未覆盖」1、`0070`「未覆盖」1 同源）。
2. **用户 / 租户两域之外，`update` 路径还有没有别的"原样入库"？** 本篇按"读侧会拿它做
   精确匹配"这条判据扫了一遍，`status` 是唯一落在射程里的。但**判据之外**的列
   （名称 / 描述 / `username` / `tenantCode`）仍原样入库 —— 见「刻意不做」1，
   那是刻意的，不是遗漏。
3. **`email` / `phone` 的写入不 trim**（`UserService.blankToNull`：`null` 或纯空白转 `null`，
   否则**原值**）。它们的读侧是**判重**（`existsEmail` / `existsPhone`）而不是过滤，
   同源问题但入口不同 ⇒ 要改就得连判重入参一起改（只改一侧会让
   "存 `a@b.c`、判重比 `' a@b.c '`"这种新的不一致冒出来）。需要单独量一遍判重入口。
   **注意这一条与本篇的判据同源**：判重也是精确匹配。
4. **`hasText` 仍有 2 份副本**（日志 / 事件各一，服务于条目校验与 `firstNonBlank`
   与 `isValidEventName`）。它们**不参与过滤条件的拼装**，也不参与写入值的组装 ⇒
   与本届主题无关（承 `0069`「未覆盖」5）。
5. **规则 5 的白名单会陈旧**（承 `0070`「未覆盖」2）：六个列名是硬编码的，
   下一个域新加一个上报列时锚不到。做成"从 `*Query.java` 自动发现会被 `eq` 的列名"
   会引入误报（审计 / 鉴权域有一堆同名 setter 与过滤无关）⇒ 按 `0064` 不做。
6. **只有两个上报域有运行时断言**（日志 / 事件），审计域没有 ——
   审计域整体不在射程（写入不由外部输入决定），所以本轮的用例也没碰它
   （承 `0066`「未覆盖」2 · `0069`「未覆盖」6 · `0070`「未覆盖」5）。
7. **`?status=`（**空串**，而非纯空白）与不传的处理仍未单独断言**
   （承 `0069`「未覆盖」7 · `0070`「未覆盖」6）。
