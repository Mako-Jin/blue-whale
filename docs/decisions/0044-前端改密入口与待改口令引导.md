# 0044. 前端的改密入口与"待改口令"引导

- **状态**：已采纳
- **日期**：2026-10-13
- **决策者**：舰长

## 背景

`0043`「本决策未覆盖」第 1 条：

> **前端的改密页与"强制改密"引导**。本轮只做后端切片，接口可被 `curl` 完整验证。
> `MeVO.mustChangePassword` 已经就位，前端接上时**不需要再动后端**。

那句话只说对了一半。真去接的时候，有两处必须回到后端与契约 —— 而两处的理由都不是"顺手改改"。

### 一、`MeVO.mustChangePassword` 到不了前端

前端基座走的是**登录 / 刷新**那条路。`GET /api/auth/me` 在前端只有**一个**调用点
（`AuthChannel.reload()`），而它的用途是"后台改了权限之后重新拉一次身份"。
一条普通登录流程里没有任何一处会调它。

于是这一列在 `0043` 里刚刚从"零引用"变成"有一个读取方"，而那个读取方**根本不会被触发**：

- `POST /api/auth/login`（登录）—— 会走到
- `POST /api/auth/refresh`（刷新页面、401 恢复）—— 会走到
- `GET /api/auth/me`（`reload()`）—— **不会**

这是同一类缺陷的第三种出现形式：**字段齐全、写入方齐全、读取方写着，但走不到**。
它的前两种是 `0020` 的"失败计数被自己的异常回滚"（有 bug）与 `0043` 的
"`must_change_password` 零逻辑引用"（没有消费者）。这一次更隐蔽 —— 文档、注释、
契约字段全都在，缺的只是"调用链会不会经过它"。

刷新这条尤其不能少：不带着它，用户按一次 F5，引导就没了。

### 二、一条看着很像缺陷的推演，核到根上不成立

接前端时注意到一件事：`40101`（口令不匹配）按本仓"5 位 = HTTP 3 位 + 业务 2 位"
的规则，HTTP 状态就是 **401**；而 `common-tools/http` 的内核只按状态码判断
（`client.ts`）：

> 带着令牌发出 + 收到 401 + 未豁免自动恢复 ⇒ `onAuthLost()` ⇒ 清会话、跳登录页。

推演下去是一个很具体的坏结果：用户旧口令打错一个字 → 401 → 尝试刷新令牌 →
重试仍是 401 → 清会话、跳登录页。**界面上的表现正是"改密成功，请重新登录"** ——
用户于是拿着旧口令回登录页，而真正的原因（他打错了一个字）从未出现过。

链条上每一环都成立，**除了第一环的前提**。本仓有一条更强的约定：

> **业务失败一律返回 HTTP 200。** `GlobalExceptionHandler` 的每个处理器都返回
> `R.fail(...)`，并且专门用 `ResponseOutcome.markFailure` 留下成败标记，
> 让审计拦截器在"响应状态码看不出结果"的前提下仍能判断。

于是 `40101` 在传输层是 **200**，内核那一支根本不会命中。**那个缺陷不存在。**

#### 它是怎么差点被写进这份 ADR 的

第一次写 `common-api` 的用例时，替身里填的是 `status: 401`。测试于是绿了，
日志里出现 `kind=http`（而真实链路下是 `kind=business`）—— 一个"缺陷"就这样被造了出来，
连带着一段解释它的注释、一条 `skipAuthRetry` 的防护，以及这份 ADR 的初稿。

**用替身造出来的缺陷，测出来的一定是替身的属性。** 一个"只有在我的替身里才存在"的问题，
再讨论一小时也不会有结论 —— 因为它不在系统里。

#### 留下来的是判据，不是防护

- `changePassword` 走**默认**请求选项。代码里写明这条成立**依赖那条后端约定**，
  以及"若哪天改成按业务码回真实状态码，这里必须加 `skipAuthRetry`"。
- 用例改成照**真实响应形态**造（HTTP 200 + 业务码），并断言**会话仍在** ——
  这条断言现在真正盯的是那条约定：它一旦被改掉，这里会红。
- 一条判据进 `web/README.md` 的测试约定：**替身要照真实响应形态造。**

## 决策

### 1. 入口放在基座顶栏，与登出同一处

判据：**改密和登出都是会话级动作** —— 不依赖任何菜单码，只依赖"当前有会话"。

- **不能放进子应用。** 新账号可能一个菜单码都没有（`0031`），那时它进不去任何子应用。
  把改密入口放进子应用，等于让"被自己都进不去的口令锁在门外"从登录态换到门户态重演一遍。
- **只放基座是一致而非缺口。** 作为对照：`platform-admin` 单跑时连登出按钮都没有
  （会话级动作本来只有基座有）。子应用单跑是调试形态，不是产品形态。

### 2. `mustChangePassword` 走登录 / 刷新响应，`toSessionUser` 是唯一的转换点

- **后端**：`LoginVO` 也带这一列，取值在 `issueTokens` 里一行 —— 登录与刷新共用它。
  三个出口（`/login` `/refresh` `/me`）同源，都来自 `bw_auth_user.must_change_password` 一列。
- **前端**：`SessionUser.mustChangePassword: boolean`，**必填**。理由是它是**判定**字段
  （和 `roles` / `permissions` 同类），不是展示字段。判定字段留下"缺席"这个第三态，
  后面一定要有人为它猜一个默认值 —— 而无论猜"否"（该弹不弹，静默失效）还是猜"是"
  （对着没这回事的人弹窗）都是错的一方。
- **转换写成 `=== 1`，不是 `!== 0`。** 后者会让"字段缺席"被当成"要改密"，
  于是所有不带这个字段的响应都会让用户看到一次无事可做的引导。

### 3. 引导弹一次、可关闭、角标常驻 —— 仍然不是拦截

`0043` 决策 5 的两条理由在这里原样成立：直接拒绝登录会**死锁**，只发受限令牌要引入
令牌能力分级。所以它是一条**约定而非强制**。

一个关不掉的弹窗就是**假开关** —— 它声称"你必须改"，而客户端拿它没有任何办法。
因此：弹窗自动出现一次、随时可关；关掉之后**角标仍在**，因为"这个口令是别人代设的、
还没换过"这个事实并没有因为用户关掉了弹窗而改变。

### 4. 客户端只判一件事：两次新口令一致

其余规则（长度、字符类别、不得与旧口令相同、不得是最近用过的）**一律不在前端重写** ——
它们已经有唯一实现（服务端的 `PasswordChanger`），前端再写一份就是同一个规则的两处实现，
而 `0020` 决策 2 已经为此删掉过 DTO 上的 `@Size(min = 8)`。

"两次一致"是**只有客户端能判**的一条：服务端只收到一个新口令，它无从知道用户有没有
把新口令打错一遍。错误文案也由服务端给 —— 只有它知道缺哪几项。

### 5. 改密成功后本地会话当场结束，而这件事必须由通道做

服务端撤销的是**全部**刷新令牌（`0043` 决策 4）⇒ 本次会话已经无法续期。
`AuthChannel.changePassword` 因此在接口成功之后 `session.clear()`。

判据：**这不是界面的选择，而是服务端行为的必然结果。** 放在通道里，它就只有一个实现；
散在各个界面里，它就只是一句"记得清会话"。把它推迟到"访问令牌到期被踢出去"那一刻，
换来的只是一张查不出原因的故障单。

**代价与处置**：界面没有机会事后解释这件事（成功时会话已被清、页面正在去登录页的路上），
所以"会结束该账号在所有设备上的登录（含当前这个）"这句必须**前置**到按钮上方。
这也让"对话框没有成功态"成为正确设计而不是遗漏 —— 那时再 `setState` 只会写进一个
即将卸载的组件。

### 6. `changePassword(oldPassword, newPassword)` 用位置参数，不用对象

两个都是字符串。写成 `{ oldPassword: x, newPassword: y }` 时把两者写反，
**类型检查一声不响**，而症状是"用新口令去证明自己是本人" —— 一次必然失败、
且看起来像用户自己记错了口令。

### 7. 改密请求**不**豁免 401 自动恢复（这条是"不做"）

背景第二节推演出的那个坏结果不成立，因此**不加** `skipAuthRetry` ——
加它就是给一个不会发生的情况写防护，而它旁边那句注释还会是错的
（它得声称"这个 401 是业务判定"，可业务判定根本不产生 401）。

真正兜住这件事的是后端那条约定。前端在这里能做的是**把依赖写明**
（`createAuthApi` 里那一大段注释）并**留一条会随之变红的断言**（会话仍在），
而不是加一个看起来更安全的开关。

## 后果

**正面**

- `0043` 留下的"未覆盖第 1 条"补齐，`mustChangePassword` 这条小机制第一次
  **写入方 / 读取方 / 清除方 / 到达用户的路径**四段齐全。
- 改密入口不依赖任何菜单码，因此对"一个新账号都没有授权"的处境也成立。
- 一个真缺陷在接前端时暴露并被钉住：**"读取方走不到"**（背景第一节）。
  它比前两种形式都隐蔽 —— 文档、注释、契约字段全都在，缺的只是"调用链会不会经过它"。
- 一条疑似缺陷被核掉（背景第二节）。它没进代码，但留下了判据：
  **替身要照真实响应形态造。**

**负面 / 代价**

- `LoginVO` 与 `MeVO` 现在各有一份同名字段。这是**同一个事实的两个出口**，
  而不是两份状态（源头只有一列），但读契约的人需要知道为什么两处都有。
- 改完口令必须重新登录，且这次是**立刻**（`0043` 决策 4 的代价被前端提前兑现）。
  理由写在对话框上，而不是藏在代码里。

**它不是空转**（三层分开证明）

- `ChangePasswordApiTest` 新增一例：管理员重置后，「登录响应带 `mustChangePassword = 1`」
  且「刷新响应也带 1」，本人改密后同一个出口变 0 —— 钉住的正是"这一列到不到得了前端"。
- `common-api/tests/auth.test.ts`：`toSessionUser` 的三态（`1` → true、`0` → false、
  缺席 → false）；改密请求的路径与请求选项；**成功后会话被清**；
  **旧口令不对时（业务失败返 HTTP 200）会话仍在**。
- `ChangePasswordDialog.test.tsx`：两次不一致时**不发请求**；
  旧口令不对时显示服务端文案、**会话仍在**、按钮恢复可用；成功后**会话结束**且
  两个口令按位置传对；后果说明在做之前就可见。
- `BasicLayout.test.tsx`：**一个菜单码都没有时入口仍在**（这条就是决策 1 的判据本身）、
  待改密时自动弹一次并留角标、不需要改密时不弹不标、关掉后不再自动弹但角标还在、
  点入口能自己打开。

## 本决策未覆盖

- **"忘记口令"**。它需要一条不依赖登录态的凭证通道（邮件 / 短信），与本决策的
  "已验证本人"是两种不同的信任来源，不能复用这个接口（与 `0043` 同一条）。
- **`mustChangePassword = 1` 时的服务端强拦**。刻意不做（决策 3）。要知道它是一条约定：
  绕过前端的客户端可以在未改密的情况下继续调其它接口。若将来要强拦，前置条件是先有
  一条"不需要当前会话即可改密"的路径，否则会死锁。
- **子应用独立运行时的改密入口**。刻意不做：那些形态连登出都没有（决策 1）。
- **口令过期（`password_expires_at`）的引导**。后端已有 `40111`，前端同样需要一个入口 ——
  它与本决策的落点是同一个，但触发条件与文案不同，留给下一次。
