# 0011. 行为事件管道与前端埋点内核

- **状态**：已采纳
- **日期**：2026-10-10
- **决策者**：舰长

## 背景

舰长提出："在前端封装统一的事件机制，发布和订阅；用户有操作时都发布事件，
异步记录到服务端，之后计划接入大数据，测试阶段可使用普通数据库，用于分析用户行为。"

此时项目里已经有**两条**"前端产生 → 服务端落库"的管道：

1. **技术日志**（`sts-server-log` + `common-tools/logger` 的 `onRecord`）——
   排查故障，量大、可采样、可丢弃
2. **审计日志**（已设计未实现）——合规追溯，长保留期、不可改、**由后端拦截器产生**

现在要加第三条。因此第一个必须回答的问题不是"怎么做"，而是
**"它和已有的两条是什么关系"** —— 这决定了它是复用、扩展还是一套新东西。

## 决策

### 1. 行为事件是**第三条独立管道**，不挂在日志上

这一点在动手前先立住，因为它决定了后面全部结构。三者在四个维度上**逐项不同**：

| 维度       | 技术日志       | 审计日志         | 行为事件                         |
| ---------- | -------------- | ---------------- | -------------------------------- |
| 回答的问题 | 系统在干什么   | 谁对什么做了什么 | 用户做了什么                     |
| 契约稳定性 | 低，字段随意改 | 高               | **极高 —— 改名即历史数据断裂**   |
| 采样       | 可采样         | 不可             | **不可 —— 采样会毁掉漏斗与留存** |
| 权威来源   | 前端           | 后端拦截器       | 前端（行为）+ 服务端（接收时间） |
| 相对量级   | 中             | 低               | **高（日志的 10–100 倍）**       |

挂在日志管道上有三个具体后果，都不是理论风险：

- **采样策略打架** —— 日志要采样省量，事件一采样，转化率与留存率算出来全是错的
- **契约耦合** —— 日志字段随便改；事件字段改一下，历史数据就断层
- **量级互相拖死** —— 共用一张表、一个接口，事件洪峰会把日志查询一起拖垮

因此：**服务端另起 `sts-server-track` 模块，前端另起事件内核。**

### 2. 但**传输通道必须复用**，而且要先把它的位置摆正

复用与独立并不矛盾：事件与日志在"怎么送出去"上需求**逐条相同**
（批量、有界缓冲、指数退避、失败不抛异常），在"送什么"上完全不同。

动手时发现一个隐患：这套批量上报机制当时住在
`platform-log-console/src/reporter.ts` —— **在一个演示应用里**。
它的四条约束是通道本身的属性，与上报内容无关。若事件这边照着再写一份，
两份实现会立刻开始漂移（一份修了并发缺陷，另一份没修）。

于是先做了一步重构：

```
platform-log-console/src/reporter.ts   ← 曾经：完整实现
        ↓ 下沉
common-tools/src/report/BatchChannel   ← 现在：与业务无关的通用通道
        ↑ 薄封装
platform-log-console/src/reporter.ts   ← 现在：只告诉通道"日志的请求体长什么样"
```

同理下沉的还有一处：把任意值修剪成可序列化形态的 `sanitize`
（原先也只在日志演示页里），现在落在 `common-tools/src/json`，
日志与事件共用一份 —— 而它防的正是"一条脏数据让整批上报失败（499 条一起丢）"。

### 3. 前端形态：**语义化 `track()` + 内部总线**，不做通用事件总线

```
业务代码 ──track('order.submit', { orderId, amount })──▶ 追踪器
                                                          │
                            中间件管道（补齐上下文 / 屏蔽 / 脱敏）
                                                          │
                                          订阅者一：本地缓冲（页面左栏）
                                          订阅者二：批量上报通道
```

**为什么不做"万物皆事件"的全局总线：** 那样看起来更灵活，代价是没人能回答
"这个事件是谁发的、谁在听" —— 而埋点恰恰最需要回答这两个问题。
总线在这里是**埋点 SDK 的内部实现**，用来承载中间件与多订阅者；业务只认识 `track`。

中间件的顺序即语义：先**屏蔽**（最便宜，能省掉后面全部工作），再**脱敏**（改写 props），
最后交给订阅者。屏蔽与脱敏放在这里而不是散在各调用点的 `if` 里，是"一处生效"的意思。

### 4. 三个必须在第一版就定下来的边界

这三条现在不定，将来不是"改一下"而是"数据废掉重来"：

**① 事件名是永久契约。** 形态强制为小写点分至少两段（`order.submit`），
且**前后端用同一条正则**（后端的 `ClientEventService` 与前端 `EVENT_NAME_PATTERN`）——
两边各写一套的后果是"客户端放行、服务端逐条拒绝"，表现为
"接口返回成功但一条也没落库"。客户端的校验前移只是**提前暴露**，
不是替代服务端校验。

**② 双时间戳，各司其职。** `clientTime` 是客户端自报的（用户会改系统时间），
**不可信**，仅供展示与归因参考；`serverTime` 是服务端收到的那一刻，
是排序、分页、时间窗过滤的**唯一依据**。若拿 `clientTime` 排序，
一台时钟偏了的机器就能把它的全部事件插进别人的序列中间。

**③ `props` 结构版本按事件走。** `propsVersion` 是**按次传**的参数而不是全局配置 ——
版本属于"某个事件的结构"，不同事件在同一个版本号上没有任何共同含义。
缺省为 1 而不是留 NULL：列里全是 NULL 时，没人知道该从哪个数字开始递增。

### 5. 存储：少量维度列 + 一个 props JSON 列

```sql
bw_client_event(
  id, event_id, event_name, app, user_id, device_id, session_id, route,
  app_release, props_json, props_version, client_time, server_time, ip
)
```

**为什么不给每个事件类型建表：** 那会表爆炸 —— 每加一个埋点就要加一张表加一次迁移。
**为什么不把 props 全拆成列：** 事件属性是产品侧随手加的，
拆列意味着每次加属性都要改表结构，而表结构变更在本项目是有成本的（三套方言脚本）。

维度列只保留**会被拿来过滤和分组**的那几个，其余进 `props_json`。
将来接 ClickHouse / Doris 时，这个形状可以原样映射成"维度列 + Map/String 列"。

**`event_id` 刻意不建唯一索引。** 一次上报是一个多值 INSERT。若建唯一索引，
批内只要出现一条重复（客户端重试、网络重发都会造成），**整批插入就失败** ——
一条重复拖垮另外 499 条。两害相权：宁可在落库后按 `event_id` 去重（查询时 DISTINCT，
或异步补偿），也不能让一条重复毁掉整批。**唯一性的位置在消费侧，不在写入侧。**

### 6. 卸载兜底：埋点最大的数据损失来源

定时器还没到点，缓冲里那一批就随页面一起消失 —— 而"用户离开"往往正是最值得记录的行为。

两个必须绕开的坑，都写进了实现与注释：

- **不能用 `navigator.sendBeacon` 发 JSON** —— `application/json` 的 Blob 会触发 CORS 预检，
  而预检在卸载阶段不可能完成，请求被**静默丢弃**。
  改用 `fetch(..., { keepalive: true })`（同源下无此问题）。
  这也是演示页坚持走 vite 代理（同源）的原因之一。
- **keepalive 的请求体上限是 64KB**，超了整个请求被静默丢掉（不报错）。
  因此按体积裁剪，并**优先保住最近的那批** —— 越晚发生的事件越接近
  "用户为什么离开"这个问题的答案。

### 7. 大数据接入点：现在只留一个接口，不实现

本轮**不引 Kafka / ClickHouse**（与"按需创建、不预置空壳"一致）。
但有一件事必须现在做对，否则将来接不上：**把"落库"当作一个可替换的落点**。

当前实现是关系库；将来的实现是 Kafka → ClickHouse，业务代码零改动。
`BatchChannel` 已经把"怎么发"抽象出来了，服务端这一侧将来只需替换接收后的去向。

## 后果

**正面**

- 三条管道各司其职，采样策略、保留期、索引组合互不干扰
- 传输通道与脱敏逻辑各只有一份实现，日志与事件同时受益
- 埋点全程不抛异常：任何埋点故障都不会打断它所在的那段业务逻辑
- 契约链路照旧：`track()` → 上报 → `sts-server-track` → 落库 → 查询，
  前端类型全部由 OpenAPI 生成，零手写
- 演示页 `platform-event-console`（:3300）可完整观察链路，
  包括屏蔽与脱敏**在离开浏览器之前**发生

**负面 / 代价**

- 多了一个后端模块与一整套前端内核要维护
- 事件**不可采样**这一条是分析正确性的代价：它意味着事件量会真实存在，
  迟早要面对存储与查询成本（这是接大数据的原因，不是意外的负担）
- 服务端新增字段时要同时改三套方言脚本（h2 / mysql / dameng），
  漏一套的症状只在那一个库上出现

**后续约束**

- **新增落库字段前先查 MySQL 保留字**（`release` 那次是活教训，见 ADR-0009）
- **Flyway 迁移的版本号在整个后端唯一**（三分套脚本共用 location，见 ADR-0009 的补充）
- 事件名一旦上报过就不可改名；需要改结构时**加 `propsVersion`**，而不是改旧字段的含义
- 埋点代码不得抛异常、不得自我记录（否则一次故障会演变成客户端与服务端之间的雪崩）

## 尚未完成（明确列出，避免被当成已具备）

| 1   | **采样**                           | 事件采样必须"按会话整体采"，否则漏斗断裂。当前量级无压力，先不引入 |
| 2   | **服务端脱敏二次兜底**             | 当前只在客户端脱敏。服务端只做长度截断，不做字段级脱敏             |
| 3   | **事件注册表（含文档化）**         | 当前只有约定与演示页里的目录常量，尚未形成可校验的注册表           |

| 6   | **同意管理与可删除**               | 行为数据属个人信息，需要有同意记录与"按用户删除"的能力             |
