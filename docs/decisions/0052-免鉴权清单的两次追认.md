# 0052. 一份「安全评审清单」字段的两次追认 —— 而它不可能是那份清单

- **状态**：已采纳
- **日期**：2026-10-14
- **决策者**：舰长

## 背景

`0051` 核出 `bw_auth_tenant.status` 在全仓**只有一个读者**（登录），并把它归进
仓里早已有名字的那一族：**状态列没有读者**（`0022` 停用角色、`0024` 停用用户组）。
那一族此前都是**逐个偶然发现**的 —— 每次都是在追另一件事时撞上。

所以本轮先做一件不同的事：**把全部开关列一次扫完**，不再靠撞。

口径是 DDL 里带开关语义的列（`status` / `is_*` / `enabled` / `allow_*` / `deleted` /
`has_*` / `lock_*`），共 **27 个**（`deleted` 十一张表、`status` 四张表，其余零散）。

扫完的结论是：**绝大多数开关都有确定的读者**，而且大部分就写在判定链路的那两条 SQL 里：

| 开关列 | 读者 | 关掉之后 |
| --- | --- | --- |
| `bw_auth_resource.is_enabled` | `AuthorizationMapper` 的两条判定 SQL | 不再产生权限 |
| `bw_auth_role.status` | 同上 | 角色失效（成员关系还在，不再产出权限） |
| `bw_auth_user_group.is_enabled` | 同上 | 组不再传递角色 |
| `bw_auth_user.status` | `AuthService#login`（+ 续期） | 登不进来（既有会话见 `0051` 未覆盖 1） |
| `bw_auth_tenant.status` | `AuthService#login` | 同上（`0051`） |
| `bw_auth_organization.status` | `enabledSubtreeIds`（`DEPT_AND_CHILD` 求值）· `resolveParent` | 自己不再是范围目标、不许挂新下级 |
| `bw_auth_role.is_default` | `RoleMemberService#grantDefaultRolesTo` | 建号不再自动授予（`0049`） |
| `bw_auth_rel_org_user.is_primary_position` | `primaryOrganizationOf`（`DEPT` 求值） | 该条归属不参与"本部门" |
| `has_child`（租户 / 组织） | 删除守卫 | 仍可被删（守卫失效） |
| `deleted`（十一张表） | `BaseEntity` 上的 `@TableLogic` | 行在应用层等于不存在（`0051`） |
| `lock_level` / `lock_reason` | `AuthService#login` 的失败计数与锁定 | 不再锁定 |

> **⚠️ 上面这张表已由 `decisions/0054` 逐格核过，它不应再被当作权威版本。**
> `0053` 订正了 `has_child` 那一格，`0054` 又改掉五行、补上一列漏登记的
> （`tenant.status` 漏了 `assertAcceptsNewData`、`lock_*` 的主体写成了 `AuthService`
> 而实际是 `LoginAttemptRecorder`、`organization.status` / `role.status` /
> `is_primary_position` 各漏一处读者、`mfa_enabled` 整列没进表）。
> **订正后的权威版本在 `server/README.md` 的「权限域的开关列与它们的读者」** ——
> 本表按 `docs/README.md` §三 **逐字保留**（当时扫出来的是这样），此后只改那份活文档。
> 更要紧的是那句"下次不必再撞"：它自称的用途是**查询**，而 ADR 不能被更新 ——
> 一张只写得了一次的查询表，正是它自己批判过的"能给出相反结论的清单"。

**真正"零读取方"的只有四个**，其中三个早已有记录：

- `bw_auth_tenant.allow_register` / `allow_add` —— `0049` 的正题（"契约里的空位"）；
- `bw_auth_user_group.is_default` —— 与 `bw_auth_role.is_default` 同形，`0022` 族已记；
- **`bw_auth_resource.is_whitelist` 与 `is_deprecated` —— 从未被任何文档提过。**

本轮的正题就是最后这两个。**这一轮的价值有一半在于"扫完了"** ——
下次再问"这个开关有没有读者"，答案已经在这里，不必再撞一次。

### 一、同一张表上三个"只存不用"的字段，只有一个被诚实标注

`bw_auth_resource` 上有三个字段的实现事实**完全一样**：只在 `applyTo` 里写、
只在 `toVO` 里读出来给界面：

```java
entity.setIsWhitelist(flag(request.getIsWhitelist(), 0, "isWhitelist"));
entity.setIsDeprecated(flag(request.getIsDeprecated(), 0, "isDeprecated"));
```

但它们在契约里的自我描述是三种截然不同的态度：

| 字段 | `@Schema` 原文 | 事实 |
| --- | --- | --- |
| `resourceVersion` | "**当前只存不用**，版本治理尚未实现" | 属实 ✅ |
| `isWhitelist` | "**这是安全评审要看的一份清单**" | **不成立** ❌ |
| `isDeprecated` | （什么都没写） | 只存不用 ❌ |

也就是说：**唯一被标了"用途"的那个，用途不成立；另一个连标注都没有。**
这不是笔误 —— 是同一张表上的三条注释各自演化，没有一次被放在一起读过
（与 `0049` "同一件事的两句话写在两份文档里"、`0050` "三处注释追认一个缺口"同族）。

### 二、它**不可能是**那份清单 —— 三条证据

**证据 1：这份清单要回答的接口，在这张表里一行都没有。**

种子资源由 `AuthPermissions.ALL` 建出：

```java
// DefaultAdminSeeder#ensureResources
for (String code : AuthPermissions.ALL) { ... ensureResource(code, code, ResourceType.API, null, 0); }
```

而 `AuthPermissions.ALL` 是**权限码**的登记处 —— 只有走 `@RequiresPermission` 的接口才有码。
真正公开的接口（登录、刷新、健康检查、上报）**没有权限码**，因此在这个循环里根本走不到，
**在 `bw_auth_resource` 里一行都没有**。

**证据 2：于是这一列恒为 0，读起来却像"没有接口是公开的"。**

种子对每个资源都写 `setIsWhitelist(0)`，也没有别的地方会把它改成 1
（界面那条路见第四段）。于是一份"哪些接口不需要登录"的清单，给出的答案是
"一个都没有" —— 而实际有 9 个。**一份能给出相反结论的清单，比没有清单更危险**：
它会被当作评审依据。

**证据 3：真正的判定源是"反着写的白名单"，这一列没有可同步的对象。**

```java
// AuthInterceptor#preHandle
// 未声明权限的接口 = 公开接口（登录、健康检查等），直接放行
if (annotation == null) { return true; }
```

`0026` 已经把这条点成了"日志域 / 事件域当年完全公开"的**根因**。
既然规则是"没写注解 = 公开"，那么"哪些接口是公开的"就是一个**从注解推导出来的事实**，
不存在一份需要人工维护、可以与之并存的清单 —— 那份人工清单只会漂移。

### 三、实证：这件事不能靠读文本回答

实现本片时我先用文本匹配扫了一遍 Controller，**三次给出三个不同的答案**：

| 第几次 | 结果 |
| --- | --- |
| 第一次 | 把 `/api/auth/login` 归成"有注解" —— 上下文窗口里串到了上一个方法的注解 |
| 第二次 | 按方法块切分后，路由名被字符串解析吃掉了，连路径都是错的 |
| 第三次 | 手工按控制器数"映射数 vs 注解数"，`ResourceController` 多出的那一个注解其实是**类注释里提到过这个词** |

三次都不是"差不多"，是**在最重要的那个端点上给出完全相反的结论**。
结论：**"哪些接口是公开的"必须由框架自己的映射表回答** ——
注解与最终注册的路由之间隔着组合注解、类级 `@RequestMapping` 前缀、方法级路径拼接，
重写一遍就是造一个会漂移的副本。

### 四、界面上它是唯一一个"看起来是开关"的开关，而且它旁边的小字否认了它

资源页把 `isWhitelist` 摆成了一个下拉：

```
免鉴权  [ 否 / 是（白名单） ]
请求地址与免鉴权仅供评审参考，不参与运行时判定。
```

**控件在声明一种能力，紧邻的小字在否认它。** 而按第二段的证据，
这一列对**本表里存在的每一行**都只能诚实地填 0（有行的都是有权限码的接口 ⇒ 都不是公开接口），
也就是说那个"是（白名单）"的选项**只会被用来记下一句反话**。

这与本仓「不交付假开关」是同一个判据（`0018` 的 `origin`、`0022` 停用角色成假按钮）。
`0049` 对 `is_default` 的处理是"表单刻意不摆"，因为那个字段**能接上**；
`is_whitelist` **接不上**（判定源在注解上），所以"不摆"这条更适用。

## 决策

### 1. 新增 `AuthPublicEndpoints`：不参与权限判定的端点**唯一登记处**

九条：`GET /api/health` · 登录 / 刷新 / 登出 / 退出所有设备 · 当前用户 / 自助改密 ·
日志上报 · 事件上报。键的形状固定为 `方法 + 空格 + 路径`
（与框架映射表里的写法一致，含路径变量占位）。

沿用 `server/README.md` 里 `AuthPermissions.ALL` 的定位写法 ——
它是"权限标识的唯一登记处"，本类是"公开端点的唯一登记处"，两者是**同一张纸的两面**。

### 2. 新增守卫 `PublicEndpointRegistryTest`：每个 `/api` 端点**恰好二选一**

用 `RequestMappingHandlerMapping` 枚举全部 `/api/**` 端点，断言
「方法或类上有 `@RequiresPermission`」与「登记在 `AuthPublicEndpoints` 里」
**恰好二选一**（双向相等，漏登记与过期登记都会红）。

**守卫与被守的规则同源**：判定用的是 `AnnotatedElementUtils.findMergedAnnotation`，
与 `AuthInterceptor` 用的是**同一个方法**；枚举用的是**同一张**映射表。
副产物是一条断言"映射必须限定 HTTP 方法" —— 只写 `@RequestMapping` 的映射对所有方法可达，
登记键表达不了它，本仓目前没有（框架自带的 `/error` 不在 `/api` 下）。

**用三处扰动证明它不是空转**（照 `0040` 的做法）：

| 扰动 | 结果 |
| --- | --- |
| 登记一个不存在的端点 | 红，报 `已登记：[GET /api/auth/ghost]` |
| 摘掉一个真实登记的端点（`HEALTH`） | 红，报 `未登记：[GET /api/health]` |
| 摘掉一个受保护端点的注解（`TenantController` 的 `GET /api/auth/tenants`） | 红，报 `未登记：[GET /api/auth/tenants]` |

第三条就是**真正的失败模式本身**："新加端点忘了写注解 = 静默公开"，
现在它在构建期就红，并且**指名道姓**。

### 3. 登记**不等于**免登录，这条边界写进类注释

本表回答的是"拦截器判不判**权限码**"，不是"要不要**令牌**"。
`/api/auth/me`、`/api/auth/password`、`/api/auth/logout-all` 都在本表里，
但它们由服务层用 `AuthContextHolder.require()` 要求已认证 ——
**刻意不要权限码**（任何登录用户都应能看自己的信息、改自己的口令、踢掉自己的会话）。

不把这条写清楚，下一个人会拿这份登记表当"完全公开的接口清单"用，
那就是又造了一份会误导的清单（正是本轮在纠正的东西）。

### 4. 订正两处追认，并把"真清单在哪"指过去

- `ResourceEntity` 的类注释：删掉"把白名单放进资源表…以便查看与审计"那段
  （它从未成立），改成"本列是人工备注、不参与判定，也当不了那份清单 ——
  原因是公开接口在这里一行都没有"；
- `ResourceSaveRequest` / `ResourceVO` 的 `isWhitelist` 描述同样订正；
- `isDeprecated` 补上"当前只存不用"（与 `resourceVersion` 同款标注）。

### 5. 「免鉴权」从资源表单**撤下控件**，但**保留原样回传**

保留回传的理由是实打实的：资源更新是**全量覆盖**
（`update` 调 `applyTo`，缺省值落 0），不发这个字段就会被顺手抹掉。
所以它仍在表单状态里走一圈，只是没有可改它的控件。
这与 `isDeprecated` 现在的状态一致（它本来就没有控件）。

### 6. 不删列、不改契约结构，DDL 的列注释**不回改**

- 删列要走迁移、要破坏契约（`isWhitelist` 在 `ResourceSaveRequest` 与 `ResourceVO` 里都对外）；
  本轮的目的是**纠正它被追认的用途**，不是清理字段。
- 三方言 DDL 里那句 `COMMENT '是否免鉴权白名单：0 否 1 是'` **不改** ——
  它是已发布的迁移，改了会变 checksum。那句话本身只描述"这列叫什么"，
  不构成"它在判定"的断言，因此留着不算错；真正的错误断言在契约与实体注释里，已订正。

## 后果

**正面**

- **"忘了写注解 = 静默公开"从静默变成构建失败**，而这条正是 `0026` 点名的根因。
  此前它只活在文档里（`server/README.md` 有一处正面写过"白名单反着写的"），
  没有任何机器保证。
- 那份"安全评审要看的清单"**第一次真的存在**（`AuthPublicEndpoints`），
  且它由框架的映射表**核对**，而不是人工维护后静静漂移。
- 27 个开关列的读者**一次扫完并留档**（背景那张表）—— 这一族以后不必再靠撞。
- 定位到一处**方向最危险**的字段追认：它不只是没用，还会给出与事实相反的结论。

**负面 / 代价**

- **新增一个 `/api` 端点现在多一道必答题**：写注解，或登记为公开。
  这是**有意的摩擦** —— 它换掉的是"静默公开"。代价如实说：
  忘了登记的人会撞到一条他不熟悉的报错（报错文案里写了两条路，尽量一次说清）。
- 资源页少了一个可编辑字段。如实说：**没有任何代码、用例或文档依赖过"能改免鉴权"**
  （测试里零命中），而按证据二，它对存在的行只能填 0。
- 又多了一个需要与代码同步的登记处。它的防线是那条守卫 ——
  与 `AuthMenus` / `AuthPermissions` 的处境相同（那两处各有分类学测试）。

**后续约束**

- 新增 `/api` 端点时，`PublicEndpointRegistryTest` 是**必过项**，且它挂的是
  `sts-app-server` 的上下文（守卫要枚举真实映射，不能在纯单元测试里做）。
- 本守卫**只覆盖 `/api/**` 的 handler**：`AuditInterceptor` 与 `AuthInterceptor`
  的差异（前者按 `@Audited` 记录、后者按 `@RequiresPermission` 准入）不在射程内。

## 未覆盖

- **守卫把"静默公开"变成"显式公开"，但不判断"显式公开是否恰当"。**
  一个既没写注解、又没在服务层 `require()` 的新端点，现在会被要求登记 ——
  登记之后就没有东西再问"你确定它该完全公开吗"。
  这份登记表需要**人**在评审时读，这正是它作为"安全评审清单"的用法，
  而它现在至少是**准确且完整**的。
- **`allow_register` / `allow_add` 仍是空位**（`0049` 的正题）。
  本轮只是把它们**再确认**了一次（零读取方），没有处置。
- **`bw_auth_user_group.is_default` 仍只存不用**（`0022` 族），同上。
- **两列都还在契约里**，仍是 `Integer` 三态：删列要走迁移与破坏性契约变更，
  不在本片射程。
- **前端没有对应的守卫**：登记表在后端，前端的菜单码走 `AuthMenus` 那条链
  （它有自己的分类学测试），两者不是同一件事。
- **`has_child`（租户 / 组织）是冗余列**，只在写路径维护、只被删除守卫读。
  它能否与"真的查一次子节点"漂移，本轮**没有核** ——
  它是"开关列"扫描顺带浮出来的，但属于另一个判据（缓存一致性），不并入本片。
