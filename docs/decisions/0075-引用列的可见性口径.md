# 0075. 引用列的可见性口径：同一个码的每条分支说同一句话

- **状态**：已采纳
- **日期**：2026-10-16
- **决策者**：舰长

## 背景

`0074`「未覆盖」第 4 条把这件事原样挂着：

> **`manager_id` 之外还有没有别的跨租户引用列**：本片只核了组织那一处
> （`contact_*` 是自由文本，不引用实体）。角色 / 用户组 / 资源三域的引用列
> （`parent_id` / `resource_id`）都已有同租户或平台级校验，但这是一次手工核对，
> **没有守卫**。

本轮把那次手工核对做完，并在做它的过程中发现：**判定全都存在，缺的是"判定说出来的话"。**

### 一、侦察：把"引用列"一次划完

手法沿用 `0073` 的"矩阵一次划完"：**库里的"指向另一张表的 id 列" × "哪些读路径拿它去读 /
展示、却没有做可见性对账"**。三方言各 8 个迁移文件（共 24 个 DDL 文件）逐个过了一遍，
得到 **16 张表、16 个去重引用列**：

| 表 | 引用列 |
| --- | --- |
| `bw_auth_tenant` | `parent_id` |
| `bw_auth_user` / `bw_auth_role` / `bw_auth_organization` / `bw_auth_user_group` | `tenant_id`，以及后三者的 `parent_id` |
| `bw_auth_organization` | `manager_id` |
| `bw_auth_resource` | `tenant_id`（平台级、恒空） |
| `bw_auth_rel_role_member` | `role_id` · `member_id` · `tenant_id` |
| `bw_auth_rel_role_resource` | `role_id` · `resource_id` · `tenant_id` |
| `bw_auth_rel_role_resource_instance` | `role_id` · `resource_id` · `instance_id` · `tenant_id` |
| `bw_auth_rel_org_user` | `organization_id` · `user_id` · `tenant_id` |
| `bw_auth_rel_user_group_member` | `user_group_id` · `member_id` · `tenant_id` |
| `bw_auth_password_history` / `bw_auth_refresh_token` | `user_id` · `tenant_id` |
| `bw_auth_audit_log` | `operator_id` · `target_id` · `tenant_id` · `trace_id` |
| `bw_client_log` / `bw_client_event` | `session_id` / `device_id` / `event_id` / `user_id` / `trace_id` —— **全是 VARCHAR 客户端标识，不是外键** |

**判定层面：九处判定全部存在，没有安全缺口。** 逐条核过五类：

1. 以实体 id 为主语的入口（用户 / 角色 ×2 / 组织 / 用户组 / 租户共五个 `requireXxx`）
   全部经 `assertVisible`（`0074` 的落点）；
2. 以子资源为主语的入口（`RoleMemberService#rolesOfUser` · `OrganizationMemberService#listByUser` ·
   `DataScopeService#resolve`）各自取对象、各自过判定；
3. 容器引用成员 / 父级：`RoleMemberService#assertSameTenant` ·
   `OrganizationMemberService#requireSameTenantUser` · `UserGroupService#assertSameTenant` ·
   三个 `resolveParent`（角色 / 组织 / 用户组）· `TenantService#assertCanCreateUnder`；
4. 关系行（`rel_*` 表）承载的 `tenant_id` **一律从已校验的容器取**，不是从请求取；
5. 展示映射（`managerNameOf` / 用户名回填 / 组名回填）**全部由已过判定的行出发**。

顺带核出三件"没主人"的事，记进「未覆盖」：`bw_auth_rel_role_resource_instance`
整类未使用（零读路径）、`bw_auth_resource.tenant_id` 平台级恒空无读路径、
`bw_client_*` 的三个"引用列"根本不是外键。

### 二、侦察的另一半：判定在，但"说出来的话"把判定拆了

判定都在，**但它们说出去的话把"不可区分"这件事拆成了可区分**。三条，都属于文案层面：

**① 读侧覆盖文案分叉。** `0074` 决策 3 立 `TenantService#assertVisible` 时，用
`notFoundCode.getMessage() + "或不属于当前租户"` 生成文案，预期是"同一个码在所有这些落点
上给出同一句话"。**那个预期推错了方向**：覆盖之后，同一个码的**另一条分支** ——
`requireXxx` 里的 `entity == null`，也就是"东西真的不存在"—— 说的仍是**裸文案**。
于是同一个 `404xx` 给两句话：

```
GET /api/auth/users/999999999     → 40401「用户不存在」
GET /api/auth/users/<乙租户的 id>  → 40401「用户不存在或不属于当前租户」
```

非平台级读者比一下 `message` 就学到了"这条记录确实存在，只是在别家" ——
而"它存在"本身就是别人的信息（`0025` 第 2 条）。这正是 `0059` 第二节
「在抛出点覆盖文案 = 这个码在说两件事」要挡的事，**而这一族是那个码正在说两件事的地方**。
`DataScopeService#resolve`（`0059` 当时登记的唯一一处覆盖点）是同一个问题的源头。

**② 写侧同租户一致性的文案分叉。** 七处"引用的对象必须与容器同租户"的检查
（`RoleMemberService#assertSameTenant` · `OrganizationMemberService#requireSameTenantUser` ·
`UserGroupService#assertSameTenant` · 三个 `resolveParent` · `TenantService#assertCanCreateUnder`）
各自写了一句点名成因的话，而对非平台级读者，那句话与"引用的 X 不存在"是可区分的 ⇒
逐 id 试一遍就能**数出别家租户里有几个用户 / 组织 / 角色 / 用户组**。

**③ 文档与实现不一致。** `0074` 决策 5 写 `assertCanCreateUnder` 给的是
"`40402` + 与『租户不存在』**逐字相同**的文案"，实现给的是 `"租户不存在或不属于当前租户"`（带后缀）。
**决策的措辞本身就是最终想要的答案，偏离的是实现**。

**④（航程中新抓到的）负责人族连"码"都不同。** `OrganizationService#managerNameOf`：
`managerId` 指向**别家的真人** → `40002` + 点名成因；`managerId` **谁也不是** →
**静默返回 `null`、保存照常成功**。两支连结果都不同 —— 于是"收到 `40002`"这个事实本身
就等于"这个 id 是别家的一个真人"。**只统一文案是关不掉这个口子的。**

## 决策

### 1. `404xx` 的两条分支必须**同码、同句** —— 撤回 `0074` 的覆盖文案

同一个码的每一条分支都用**枚举里那句话**（`notFoundCode.businessException()`，不传实参）。
理由不是"该不该拆码"，而是**覆盖文案本身就违反它要守的那条理由**：

> 覆盖之后，"真的不存在"那一支说的仍是裸文案 ⇒ 两条分支说出两句不同的话 ⇒
> 调用方比一下 `message` 就知道"它存在，只是不在你这儿"。

**对看不见它的操作者而言它就是不存在，所以只有一句话可说。** 要分处置就分码；
要留成因就写进 `40002` 那句（下一条）。

### 2. 写侧同租户一致性：文案**随读者分化**，判据是"这位读者能不能对两种成因采取不同的行动"

新落点 `TenantService#assertReferencedInSameTenant(referrerTenantId, referencedTenantId,
label, id, diagnostic)`，六处调用点全部委托给它：

| 读者 | 拿到什么 | 为什么 |
| --- | --- | --- |
| **平台级**（唯一能合法跨租户的人） | `diagnostic` 那句**诊断原文** | 他写错了租户与写错了主键，要去做的事**完全不同**（改租户归属 / 改 id） |
| **非平台级** | **与"引用的 X 不存在"逐字相同**的一句 | 他不可能合法持有别家对象的 id（`0074` 决策 4 的原话：别家租户在系统里**就是不存在**，他连租户列表里都看不到它）⇒ 那一支对他只有一种成因 |

**"是不是两件事"看的是读者能不能分开处置，不是数据上是不是同一件事。**
所以这不是"覆盖文案"的回潮：那一条管的是"同一个码在**同一类读者**面前说两件事"，
而这里两种读者的**处置能力不同**，本就不该被当成同一件事。

它与 `assertVisible` 也**刻意分成两格**：那一格问"这个已存在的对象对当前操作者可见吗"
（不可见 → 该对象的 `404`）；这一格问"**我看得见的**这个对象，和我要把它挂上去的容器对得上吗"
（对不上 → `40002`）。`null` 视为不一致（三方言 `tenant_id` 是 `NOT NULL`，
`bw_auth_resource` 那一个除外，它不走这条路）。

### 3. 先"两支同码"，才谈得上"两支同话" —— 负责人族两支都改

`OrganizationService#managerNameOf` 的跨租户分支改走新落点；**"谁也不是"那一支从
静默成功改成 `40002` + `"引用的负责人不存在：" + managerId`**。两支因此同为 `40002`、
同为一句话（只差主键），非平台级读者再也分不出。

顺带订正的是 `0074` §7 在**同一个方法**上漏了一半的口径：它写"选择**拒绝**而不是静默当作
『没传』 —— 静默会让你以为设上了负责人，而那一列在界面上是空的"，而"谁也不是"那一支
**恰恰就是静默**：它把 `manager_name` 写成 `null`，却把 `manager_id` 原样留在行上，
树上渲染成 `#{42}` 加一个空名字 —— 一次**保存成功、数据却半更新**的写入。

**这条是有意接受的行为变化**：前端组织编辑表单会把 `managerId` 原样回传
（`Organizations/index.tsx`），而用户删除**不拦**"仍是某组织负责人"，所以
"删掉某人之后再改那个组织的任意一列"从静默通过变成 `40002`。这是对的 ——
那句文案是**真的**（那个负责人确实没了），而改法是清掉负责人一格；
继续静默会让 `manager_id` 一直悬空而没人知道。

### 4. 订正只写在新片里（`0074` 与 `0059` 的旧文一字不改）

`0074` 决策 3 / 决策 5 与 `0059` 第二节的原文按仓内规矩**保持原样**，本轮只在本文里订正：
`0074` 决策 3 的那半被本文撤回（已不是当前口径）、决策 5 的措辞是**对的**（改的是实现）、
`0059` 第二节登记的"全仓唯一一处覆盖文案"**当前位置已不是覆盖点**。

### 5. 给"撤回"这件事配一个机械守卫

撤回没有任何测试会拦：`404xx` 的既有断言（`NotFoundCodeApiTest` 断文案前缀、
`ReferenceMessageApiTest` 断 `40002` 的短语）都是"**含有**某个词"，
拦不住"想拦的那句话仍在"。所以新增 `scripts/verify-notfound-messages.mjs`，两条规则：

| # | 规则 | 它逮的是什么 |
| --- | --- | --- |
| A | 枚举里 `404xx` 的常量，凡是写成 `CONST.businessException(...)` 的，实参必须为空 | 一族共用一个码，补一句就是让这个码开始说两件事 |
| B | 任何 `businessException(...)` 的实参里不得出现 `.getMessage()` | 拿**另一个码**的文案来拼 —— `0074` 那一处正是这个形状 |

两条都是**语法级**事实（"调用点的实参为空" / "实参里有没有那个方法名"），
不需要理解语义，因此不误报（`0064`）。`404xx` 的名字也不是白名单 ——
它从 `AuthResultCode.java` 里**解析**出来，新加一个码自动纳入射程。
**两个方向都验过**（见「实测」）。

### 6. 刻意不做

- **不新增权限码、不改接口形状**：隔离与文案都不需要新的查询参数或 DTO 字段，
  契约**零变化**；
- **不动 `DataScope` 与业务查询的接线**（`0025` 遗留 + `0030` 第 10 条）；
- **不动资源域与菜单可见性**；
- **不动三条管道**（`bw_client_log` / `bw_client_event`）的可见性（`0025` 未覆盖）；
- **不把 `assertReferencedInSameTenant` 的五个参数收成入参对象**：参数多不是缺陷，
  语义清楚，而收成对象会让"label 与 diagnostic 必须点名同一个对象"这条约定更难核对。

## 实测

### 改前基线：精确出红

`TenantIsolationApiTest` 先长到 18 条（追加三条新用例），跑出 **18 跑 3 红 / 15 绿**，
红的正是那三条新用例，失败信息逐字印证三处缺陷：

| 用例 | 改前实测 |
| --- | --- |
| `invisibleEntityMessageIsIndistinguishable` | `expected: <用户不存在> but was: <用户不存在或不属于当前租户>` |
| `invisibleMemberReferenceMessageIsIndistinguishable` | `expected: <引用的用户不存在：#> but was: <该用户与角色不属于同一租户（#）—— …>` |
| `foreignTenantParentMessageMatchesAbsentTenant` | `expected: <租户不存在> but was: <租户不存在或不属于当前租户>` |
| `platformReaderKeepsTheDiagnosis`（**对照**） | **绿** —— 它守的是反方向（诊断不许被一起删掉），正确的实现下就应该绿 |

成员族与父级族**刻意分成两条用例**：它们走的是两处不同的实现，合在一条里的话前一行红了、
后一行就不再执行 —— 那正是 `0055`「只钉一支等于没钉」。
`masked()` 把文案里的主键换成 `#`（用 `\b` 而不是裸替换，否则 id 为 `1` 而文案里有 `100` 时会误伤），
于是"同形"这句判据可以写成**逐字相同**。

负责人族那一条（第 5 条新用例）写于第二轮，它在改前的形状由下面的扰动轮 5 / 7 直接测到。

### 七轮扰动：每条用例都打在对应那一处实现上

都是改完立刻跑、跑完立刻撤。

| 轮 | 扰动 | 结果 | 说明 |
| --- | --- | --- | --- |
| 1 | `assertVisible` 恢复覆盖文案 | **1 红** | 只有 `invisibleEntityMessageIsIndistinguishable` 红 —— 读侧一族 |
| 2 | `assertCanCreateUnder` 恢复覆盖文案 | **1 红** | 只有 `foreignTenantParentMessageMatchesAbsentTenant` 红 —— 租户域那一处 |
| 3 | `assertReferencedInSameTenant` 无条件给诊断 | **2 红** | 成员族 + 父级族；对照**绿**（诊断还在，正确） |
| 4 | `assertReferencedInSameTenant` 无条件给"不存在" | **1 红** | 只有对照红 —— **对照是有牙的** |
| 5 | `managerNameOf` 的"谁也不是"改回静默成功 | **1 红** | 只有负责人族红，失败点是 `$.code expected:<40002> but was:<0>` |
| 6 | `managerNameOf` 的诊断文案改回旧措辞 | **1 红** | 红的是**对照的第三条**（平台级那一支）—— 证明新加的对照断言有牙 |
| 7 | `managerNameOf` 绕开落点、手搓旧文案 | **2 红** | 负责人族 + 对照 —— 证明这一处确实走的是同一个落点 |

轮 1 / 2 与轮 3 / 4 是**成对**的：一轮拆"给多了"，一轮拆"给少了"，
这样才能证明那两条用例不是靠某一条间接约束"顺带"成立。

### 守卫的两个方向

- 规则 A：把 `DataScopeService#resolve` 改回
  `businessException("用户不存在或不属于当前租户")` ⇒ **红**，报 `DataScopeService:49:34`

  ⇒ **红**，报 `TenantService:227:28`。**这一条同时说明它逮得住它要防的那个写法**

### 全量回归

`mvn -o test`（server 全模块）：`sts-app-server` **246 条全绿**（本片 `240 → 246`，+6），

## 后果

**正面**

- `404xx` 这一族**两条分支说同一句话**，`"它存在"` 这条信息不再从文案漏出去 ——
  而且这条性质现在**有机器守着**（此前只有 `0059` 的一句话）；
- "不可区分"从**一处**（`0059` 时只有 `DataScopeService`）变成**一族**，
  再变成**两族**（读侧 404xx + 写侧 40002）；
- `0074`「未覆盖 4」的手工核对做完并被记录：**16 张表、16 个去重引用列、九处判定全在**，
  同时把它顺带抓到的三件"没主人"的事登记下来；
- 顺带修掉 `0074` 自己在 `managerNameOf` 上漏掉的一半（"谁也不是"那一支的静默），
  并把"半更新写入"（`manager_id` 悬空 + `manager_name` 为空）变成一个可操作的报错；
- `40002` 那张权威清单被订正：`0074` 新加的两处（`resolveWriteTenant`、`managerNameOf`）
  **一次都没登记**，本轮补进去，并给跨租户那六行加上「读者分化」这一格。

**负面 / 代价**

- **"读者分化"让 `40002` 的文案有了两个版本**。这是本文刻意加的（判据是读者能不能分开处置），
  但它确实打破了"一处落点一句话"的直觉 —— 代价是那张表多一列信息、断言要分工
  （`ReferenceMessageApiTest` 断平台级看到的具体短语、`TenantIsolationApiTest` 断非平台级
  看不出的那件事）。分工写进了两份 javadoc，但**读的人多一次跳跃**；
- **负责人族的行为变化**（决策 3）：一个悬空的 `managerId` 从"静默通过"变成 `40002`。
  它让"删人之后再改那个组织"多一次操作，换来的是那条悬空引用**必须被处理**
  （而不是静默地把 `manager_name` 清空、把 `manager_id` 留着）；
- **守卫只覆盖了一半**：「每个带 `tenant_id` 的表，其 `requireXxx` 必须调 `assertVisible`」
  这条**没写** —— 表名 → 类名不是无歧义的 token 形状，只能硬编码对照表（`0064` / `0067`）。
  写侧"每次同租户一致性检查有没有走同一个落点"同样锚不住。这两半仍是人工核对；
- `40002` 那张表**没有守卫**，而它已经漂过一次（见「正面」最后一条）。

**后续约束**

- 新增一处 `404xx` 的抛出点：**不传实参**。要分处置就分码；
- 新增一处"引用对象必须与容器同租户"的检查：**委托 `TenantService#assertReferencedInSameTenant`**，

## 未覆盖

- **"每个带 `tenant_id` 的表都要过 `assertVisible`"没有机械守卫**。这是 `0074`「未覆盖 4」
  想要的那条守卫，本文只补上了相邻的一半（`404xx` 的文案）。不写它的理由是机械可判定的
  形状不存在（表名 → 类名的映射有例外），只能硬编码清单 —— 那正是 `0067`
  「白名单要核对条数」说过的形状；**本轮实测证明这个缺口有代价**：
  `40002` 那张"权威清单"自己就漂过一次。
- **写侧同租户一致性的机械守卫**：手搓写法无穷（`.equals(tenantId)` / `Objects.equals` /
  先取局部变量再比 / 在 SQL 里 `eq(tenant_id)`），锚不住。本轮人工核了一遍。
- **`bw_auth_rel_role_resource_instance` 整类未使用**（表 + `RelRoleResourceInstanceMapper`，
  零读路径）。它是"资源实例级授权"的预留形态，删不删是产品问题；
- **`bw_auth_resource.tenant_id` 恒空**（资源是平台级目录）与 **`bw_client_*` 的
  `device_id` / `event_id` / `session_id` / `user_id` / `trace_id` 不是外键**（VARCHAR 客户端标识），
  两件事都只是登记，没有动作；
- **`40002` 的每一处文案没有逐处断言**：本文只给**新增与改动的**落点补了断言
  （`managerNameOf` 的两条支、六处委托之后**非平台级那一侧**的同形），
  表里其余各处不受本轮影响、因此**没动** —— 它们的断言状况见 `0057` 与
  `ReferenceMessageApiTest` 的 javadoc；
- **达梦未实测**（全仓同一条，`0073` 未覆盖 1）。
