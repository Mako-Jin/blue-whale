# 0054. 一张「下次不必再撞」的表，半数行要修 —— 逐格核过，并把它迁出 ADR

- **状态**：已采纳
- **日期**：2026-10-14
- **决策者**：舰长

## 背景

`0053` 的「未覆盖」里留了一条自己的推论：`0052` 收尾时声称那张对照表的价值有一半在
「**扫完了** —— 下次再问'这个开关有没有读者'，答案已经在这里，不必再撞一次」，
而同一个 `0052` 刚用一整节论证过「**哪些接口是公开的**不能靠读文本回答」
（三次源码扫描给出三个不同答案，最后只能去问框架的映射表），
却在它自己那张表里把 `has_child` 的读者**从邻接关系读了出来**（`0053` 订正了那一格）。
于是 `0053` 写下：那张表**值得逐格核一遍**，尤其"读者"一栏 ——
它是整张表里最容易由邻接关系推出来的一栏。

本轮就是做这件事。逐格核完的结论不是"有一格笔误"，而是：
**11 行里有 6 行要改，另有 1 列漏登记**；而两次错误来自**两条不同的捷径** ——
一次抄的是代码相邻，一次抄的是**上一条已经写下的结论**。

## 一、核法与结果

口径沿用 `0052` 自己写下的：DDL 里 `status` / `is_*` / `enabled` / `allow_*` /
`deleted` / `has_*` / `lock_*`。**判据只有一个**：逐列搜符号名，人工判断"这一处算不算读者"
（读者的意思是"读它来决定什么"；只把它搬进出参、搬进 `SET` 子句的不算）。

| 列 | `0052` 写的读者 | 核出来的事实 | 判定 |
| --- | --- | --- | --- |
| `bw_auth_resource.is_enabled` | `AuthorizationMapper` 的两条判定 SQL | 同，但**只在其中一条**（`r.is_enabled = 1`；另一条不 JOIN 资源表） | ✅（措辞偏松） |
| `bw_auth_role.status` | 同上 | 两条 SQL 各一处 ✅ **+ `RoleMemberService#grantDefaultRolesTo`**（挑默认角色时要求 `ENABLED`） | 漏一 |
| `bw_auth_user_group.is_enabled` | 同上 | 两条 SQL 各一处 | ✅ |
| `bw_auth_user.status` | `AuthService#login`（+ 续期） | 登录一处、续期一处 | ✅ |
| `bw_auth_tenant.status` | `AuthService#login` | 登录 **+ `TenantService#assertAcceptsNewData`** | ❌ 漏关键读者 |
| `bw_auth_organization.status` | `enabledSubtreeIds` · `resolveParent` | 两处都对，**另有 `OrganizationMemberService#primaryOrganizationOf`** | 漏一 |
| `bw_auth_role.is_default` | `RoleMemberService#grantDefaultRolesTo` | 同 | ✅ |
| `bw_auth_rel_org_user.is_primary_position` | `primaryOrganizationOf` | 同，**另有成员列表的 `primaryOnly` 过滤与写路径的"要删的是不是主岗"** | 漏二 |
| `has_child`（租户 / 组织） | 删除守卫 | **零判定读者**（`0053` 已订正） | ❌ 反了 |
| `deleted`（十一张表） | `BaseEntity` 上的 `@TableLogic` | 同 | ✅ |
| `lock_level` / `lock_reason` | `AuthService#login` 的失败计数与锁定 | **`LoginAttemptRecorder`** 才是它；`lock_reason` **零判定读者** | ❌ 主体错 |
| （**表里没有**）`bw_auth_user.mfa_enabled` | —— | **零判定读者** ⇒ 第六个"只存不用"的列 | 漏一列 |

**六行要改**（`has_child` 那行已由 `0053` 改掉，本轮又改五行），**加一列漏登记**。
「真正零读取方的只有四个」这句也顺带核了：按**列数**是**六个**
（`allow_register` / `allow_add` / `user_group.is_default` / `resource.is_whitelist` /
`resource.is_deprecated` / `user.mfa_enabled` —— 最后一个本轮才发现）。
顺带说：`0052` 那句"四个"连它自己列出的**三个并列项**都对不上，
而三个并列项其实是**五个列**。**在扫一遍之后写下的数，自己也要被数一遍。**

## 二、错得最重的两条，抄的不是同一个东西

### 1. `tenant.status`：抄的是上一条结论，而上一条结论已被它自己的决策作废

`0052` 在这一格写的读者是「`AuthService#login`」。事实上有**两个**：

```java
// AuthService#login —— 停用的租户登不进来（刻意与"口令错误"同码 40101）
if (tenant == null || !Status.ENABLED.wireName().equals(tenant.getStatus())) { … }

// TenantService#assertAcceptsNewData —— 停用的租户里不许再建数据
if (!Status.ENABLED.wireName().equals(tenant.getStatus())) { … }
```

第二个读者是 `0051` **自己的决策本体**（提交 `04582f5`，方法就写在 `TenantService` 里、
与 `assertExists` 相隔两行）。`0052` 却漏了它 —— 因为 `0051` 的**背景**里有一句
「`bw_auth_tenant.status` 在全仓**只有一个读者 = 登录**」，`0052` 把那句话抄了过来：

> **毛病出在把 ADR 的「背景」当成了「现状」。**
> 背景写的是**决策之前**的事实 —— `0051` 写下那句话时它是对的。
> 而 `0051` 的决策正是把读者从 1 个变成 2 个。整篇文档里没有一处说的是假话，
> 被抄出来的那一句却已经不成立了。

这与 `0053` 核出的那格是**同一个错误的两种形态**：那次抄的是**代码相邻**（列注释挨着
`delete`，于是"守卫读它"），这次抄的是**上一份文档的结论**。两次都绕过了那一句
唯一能回答问题的话 —— **去搜调用点**。

### 2. 这句话还活着，而且活在活文档里 —— 同一条规则自己否认自己

「只有一个读者」这句话不止在 `0051` 的正文里。`0051` 那一笔同时把它写进了
`server/README.md` 的权限域硬规则表，于是**同一条规则**读起来是这样：

> … 可用性 `assertAcceptsNewData`（存在 + `status = ENABLED`）**只放在 `create` 里** …
> **`bw_auth_tenant.status` 目前只有登录一个读者**：续期那条路不读它 …

前半句说 `assertAcceptsNewData` 读 `status`，后半句说只有登录读它。**自相矛盾，
而且是在同一次提交里写下的。**

- ADR 正文按仓里的规矩**不回改**（那句保留，作为"当时的事实"）；
- **活文档里的这句是错的，必须改** —— 活文档的职责就是承担现状。

## 三、第三条不是漏，是写错了主体（`lock_*`）

`0052` 把 `lock_level` / `lock_reason` 合成一格，读者写「`AuthService#login` 的失败计数与锁定」。
核对下来：

- **失败计数与锁定是 `LoginAttemptRecorder`**（独立事务，`REQUIRES_NEW`）：
  读旧 `lock_level`、写新 `lock_level`、写 `lockedUntil` / `lock_reason`；
  `AuthService` 只在**登录成功**时把 `lock_level` 清零。
- `lock_reason` **零判定读者** —— 它只被 `toVO` 搬进出参给运维看
  （`server/README.md` 的规则写得很清楚："只落库不暴露时，运维看到'锁定至明天'却不知道原因"）。

也就是说这一格里混着两个命运完全不同的列（一个真有读者、一个只存不用），
还被按在了错的方法上。**与第一格的问题同源：一格装多个对象，就没有一列被真正核过。**

## 四、剩下的三格：主要读者对，另有读者（不完整）

- `role.status` 漏了 `grantDefaultRolesTo`（挑默认角色时要求 `ENABLED`）——
  讽刺的是 `0052` 的**下一行**（`role.is_default`）引用的正是这个方法。
- `organization.status` 漏了 `OrganizationMemberService#primaryOrganizationOf`：
  "停用的组织不再能作为范围目标"这一条判定写在**两个**地方（`DEPT` 在 `primaryOrganizationOf`、
  `DEPT_AND_CHILD` 在 `enabledSubtreeIds`），`0052` 只写了后者 ——
  而前者的存在恰好写在 `enabledSubtreeIds` 的注释里（"调用方已确认过"），
  **又是从邻接关系读出来的**。
- `is_primary_position` 漏了成员列表的 `primaryOnly` 过滤与写路径里"要删的是不是主岗"的判断。

这三格不属于"要改"，属于"要不全"：主要读者都在，但如果有人照着它去问
"我只想改这一格的行为，会动到谁"，会漏掉一半答案。

## 五、漏掉的那一列：`mfa_enabled`

`bw_auth_user.mfa_enabled`（"是否启用多因子：0 否 1 是"）**在口径内**（含 `enabled`），
但表里没有它。它的全部读取点只有一处：

```java
// UserService#toVO
vo.setMfaEnabled(entity.getMfaEnabled());
```

**纯回显，零判定读者** —— 与 `resource.is_whitelist` / `is_deprecated` 是同一个处境，
只是它此前**没有被任何文档提过**（`docs/` 里只有契约字段与 `UserVO` 的字段清单提到这个属性，
没有一处讨论它有没有读者）。它使"只存不用"的**列**从五个变成**六个**。
MFA 本身是留白的（`AuthResultCode` 里 `MFA_*` 是零抛出点的码，
`0046` 记过），所以这一列与 `allow_register` / `allow_add` 同类：**契约里的空位**。

它的同族 `mfa_type`（多因子类型）连口径都没进，但读者数一样是零。

## 六、方法本身也有两个坑

### 1. `grep -rn "getXxx()"` 会漏掉整条判定链路

`0053` 把"怎么核"这条规矩连同命令一起写了下来：`grep -rn "getXxx()"`。
**那个写法是错的** —— 带括号只匹配**方法调用**，而 MyBatis-Plus 的 wrapper 用的是
**方法引用** `Entity::getXxx`，不带括号。本轮实证：

```java
// RoleMemberService#grantDefaultRolesTo —— role.is_default 的唯一判定读者
.eq(RoleEntity::getIsDefault, 1)
.eq(RoleEntity::getStatus, Status.ENABLED.wireName())
```

用 `getIsDefault()` 搜**搜不到它**；用 `getIsDefault` 才搜得到。
而"判定链路"的读取**大量**写在这种 wrapper 里 —— 也就是说带括号的搜法
**恰好会漏掉最要紧的那一类读者**。订正为：**搜符号名 `getXxx`（不带括号），
同时覆盖 `getXxx()` 与 `Entity::getXxx` 两种形式**。

### 2. 口径是"列名模式"，而模式之外还有开关

`status` / `is_*` / `enabled` / `allow_*` / `deleted` / `has_*` / `lock_*` 这七个模式
盖不住**无前缀的 0/1 列**：`bw_auth_refresh_token.revoked`、`bw_auth_user.must_change_password`
都是开关，一个都没进扫描。本轮顺手核了这两列（都不进表）：
`revoked` **有真读者**（`SessionRevoker` 与 `AuthService#refresh` 都判它）；
`must_change_password` 在**服务端一处判定也不读**，但它有**真实消费方 —— 客户端**
（拿它决定要不要弹引导改密，`0044`）—— 与 `is_whitelist` / `mfa_enabled` 那种"没有任何消费者"
不是一回事。所以 `0052` 那句"把全部开关列**一次扫完**"
只能按**当时写下的口径**读 —— 它是一个口径内完备的扫描，不是"全仓没有别的开关了"。

## 决策

1. **把这张表迁进活文档。** 它的自称用途是"下次不必再撞" —— 那是**活文档的职责**，
   而 `docs/README.md` §三 写着"不要删改原 ADR"。一张只写得了一次、
   写错了也不能更新的**查询表**，会长期停在错的状态；这恰恰是它自己批判过的
   "**一份能给出相反结论的清单比没有清单更危险**"。权威版本落在
   `server/README.md` 权限域硬规则表之后（标题「权限域的开关列与它们的读者」），
   订正只改那里。
2. **`0052` 那张原表逐字保留**，只在表下**加一行**指向新的权威版本与 `0054`。
   理由：`docs/README.md` §三 的措辞是"**决策被推翻时**不要删改原 ADR" ——
   本片不是推翻决策，是一张**读数表**里的事实订正；即便如此，仍**不删改原表**
   （保留"当时扫出来的是这样"），只加指向。**注释可以加，事实不覆盖。**
3. **订正活文档里那句错的**（`server/README.md`：`bw_auth_tenant.status` 的读者是
   **两个** —— 登录 + `assertAcceptsNewData`）。它同一条规则的前半句就在讲后者。
4. **订正"怎么核"这条规矩**：搜**符号名** `getXxx`，不搜 `getXxx()`。
   （`server/README.md` 与 `0053` 都只写了"用 `getXxx` 的调用点核"，本轮把
   "带括号会漏方法引用"写进去。）
5. **`mfa_enabled` 记进"只存不用"清单**（第六个列），**不处置** —— 它是 MFA 未实现的留白，
   与 `allow_register` / `allow_add` 同类，处置它要先有 MFA 这个功能。
6. **口径要连同它一起引述。** 以后说"开关列扫完了"，必须带上那七个模式；
   模式之外的 0/1 列（`revoked` / `must_change_password`）不在其中。

## 后果

**正面**

- 那张表第一次**被逐格核过**，并且从"写死在 ADR 里、改不动"变成"活在活文档里、可以改"。
  它以 `0052` 的名义存在了两轮，而**从来没有一列被真正核过**。
- 活文档里一句自相矛盾的话被修掉 —— 它不只是一句话：`0052` 那一格正是抄了它。
- "怎么核"这条规矩补上了最要紧的一半（漏方法引用 = 漏判定链路）。
- 两轮的教训现在可以并列看：`0053` 是"**邻接不是调用**"，本片是
  "**上一条结论也不是调用**"。两条捷径都省掉了那一次搜索。

**负面 / 代价**

- 多了一处需要与 DDL 同步的表（活文档里）。它的防线只有"下次有人来核" ——
  见「未覆盖」第一条。
- `0052` 的表下多了一行指向，读它的人要多跳一次。

**后续约束**

- 说"某列被谁读"，必须**搜符号名**（覆盖 `getXxx()` 与 `Entity::getXxx`），
  不能看列名、注释、邻接关系，也**不能抄上一条结论或上一份文档的背景**。
- 引用别人的文档当事实时，要先问一句：**那句话描述的是"那时"还是"现在"？**
  ADR 的背景写的是决策前的事实，而它会被后来的人当成现状读。

## 未覆盖

- **没有守卫能表达"读者一栏是错的"。** 能机械判定的只有**"漏列"那一半**
  （DDL 里匹配口径的列名，与表里出现的列名对一遍），而本轮 7 处改动里只有 1 处属于它。
  剩下 6 处错在**散文**上，判它要人回答"这算不算读者"。本轮**没有**做那个半覆盖的守卫 ——
  `0036` 拒绝的正是"只覆盖半件事的检查会让整件事显得被守住了"。是否值得加，留待单独一轮。
- **`0052` 的 6 条决策本身没有重新审。** 本轮只核那张**表**，没有重读它的决策与后果
  （`AuthPublicEndpoints` / `PublicEndpointRegistryTest` / 表单撤控件那几条不在射程内）。
- **`0051` 的正文不回改。** 那句"只有一个读者"留在背景里，作为当时的事实；
  指向由活文档与本片建立。**要注意读法**：它写的是决策前的状态（见决策 3）。
- **口径外的开关没有被系统扫。** `revoked`（已核：有真读者）· `must_change_password`
  （已核：服务端零判定读者、客户端是消费方）· `mfa_type`（已核：零读取方）·
  `rel_role_resource.effect`（已核：判定 SQL 的 `HAVING` 读它）—— 这四列只做了点核，
  没有逐个进表立档。
- **`mfa_type` 零读取方**，与 `mfa_enabled` 同族，同样不处置。
- **其余四个空位原样**：`allow_register` / `allow_add`（`0049` 正题）·
  `user_group.is_default`（`0022` 族）· `resource.is_whitelist` / `is_deprecated`（`0052` 正题）。
