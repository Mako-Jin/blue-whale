# 0021. 资源目录接口：权限码的登记约束与两处数据陷阱

- **状态**：已采纳
- **日期**：2026-10-12
- **决策者**：舰长

## 背景

`docs/decisions/0016` 把权限域立起来时，交付的是**认证 + 鉴权**这一条主线：12 张表、
8 条接口、`@RequiresPermission` 运行时判定、刷新令牌轮换与重放检测。那篇 ADR 的结尾把
**组织 / 角色 / 用户组 / 资源四类实体的管理接口**列为未覆盖项 —— 表、实体、Mapper 都已落地，
只缺 Controller 与 Service。

本决策交付其中之一：**资源目录**（`bw_auth_resource` 的增删改查 + 树）。

选它先做，是因为它是另外三条的**共同前置**：给角色授资源要先把资源登记出来；
而"菜单权限"要能落地，资源表里必须真的有 `MENU` / `PAGE` 类型的行
（现在种子数据把 `AuthPermissions.ALL` 一律建成了 `API`）。

但它的性质与另外三条不同，这才是本决策的主要由来：

**它维护的是"权限本身"。** 这个目录里的每一行都是一个权限码，被 `@RequiresPermission`
与 `bw_auth_rel_role_resource` 引用着 —— 于是这个 CRUD 接口的写操作能改变**其它接口**的
准入判定。用户 / 租户 / 组织的 CRUD 改的是数据，这里改的是判定依据。

在它之前，往 `bw_auth_resource` 加一条只有两条路：种子数据，或直接写 SQL。
而资源标识是长期契约、有严格形状（`域:资源:动作` 三段小写），**靠人肉记住格式并手写 SQL**
正是 `AuthTaxonomyTest` 想拦住的那类错误 —— 只不过那条测试只看得见代码里的常量，
看不见库里被手写进去的行。

## 决策

### 1. 资源标识（即权限码）创建后不可修改

与租户编码同一处理（`TenantService#update` 刻意不读 `request.getTenantCode()`），
但理由更强：改一个权限码等于让所有持有旧码的授权**静默失效** ——
`rel_role_resource` 里那些行还在，却再也匹配不上任何 `@RequiresPermission`。
界面上看不出任何变化，直到有人发现自己点不动某个按钮。

要改就只能"新建 + 迁移"，那是两步显式操作，每一步都有痕迹。

### 2. 标识的形状校验写在 DTO 注解上，与分类学测试共用同一形状

`ResourceSaveRequest.resourceCode` 上标
`@Pattern(regexp = "^[a-z][a-z0-9_]*:[a-z][a-z0-9_]*:[a-z][a-z0-9_]*$")`，
与 `AuthTaxonomyTest.PERMISSION_PATTERN` **同一个形状**。

写成注解而不是服务层 `if`，是因为注解会进 OpenAPI 契约：资源标识长什么样这件事
在**契约里可见**，前端能在提交前拦下一半错误。两处校验密度不同，依据是同一个正则。

这条守的是一个具体缺口：`AuthTaxonomyTest` 断言"每个权限码都能归到某个已声明的资源标识下"，
但它遍历的是 `AuthPermissions.ALL` 这个**常量集合**。若接口允许写进一个两段的
`auth:resource`（那其实是**资源标识**，不是权限码），这条保证在**存量数据**上就失效了，
而测试看不见库。

### 3. 删除的三道拒绝

| 拒绝 | 码 | 理由 |
| --- | --- | --- |
| 父资源不存在（建 / 改时） | `40002` | 引用完整性。用 `PARAM_REFERENCE_MISSING` 而不是 `RESOURCE_NOT_FOUND`：错的是入参里那个引用，不是被操作的这条记录 |
| 有子资源 | `40913` | 不提供藏起来的级联（与租户一致） |
| 已被角色引用 | `40915`（新增） | **本条目最要紧** |

第三条值得展开。资源是逻辑删除，删掉之后 `AuthorizationMapper` 的 JOIN 会自动把它排除 ——
于是一次 `DELETE` 会让若干角色**静默地**少掉一项权限。管理员的本意可能只是"清理一条不再用的
资源"，实际效果却是"某些人突然点不动某个按钮了"，而且没有任何界面会提示这件事发生过。

要求先显式撤销授权（那时能看到受影响的是哪些角色）再删资源，代价是两步操作，
换来每一步都可解释 —— 与租户"存在子租户时拒绝删除"是同一条原则：
**不提供藏起来的级联**。

`40915` 是新加的码（`RESOURCE_IN_USE`），因为现有 409xx 段位里没有能表达"被引用"的：
`40912` 是"标识已存在"（建的时候），`40913` 是层级问题，语义都不对。

### 4. 软删 + 单列唯一索引的冲突：**复活**原记录，而不是插入

这是本切片唯一一处**修掉了一个真实缺陷**的地方，也是它最值得记下来的原因。

`V3__create_bw_auth_tables.sql` 里：

```sql
CREATE UNIQUE INDEX uk_bw_auth_resource_code ON bw_auth_resource (resource_code);
```

关键在**不含 `deleted`**。而 `BaseEntity` 的 `deleted` 带 `@TableLogic`，
MyBatis-Plus 生成的每一条查询都会自动追加 `deleted = 0`。两者叠加的结果是：

```
删掉一个资源（软删）
  → 那一行仍然占着 resource_code
  → 再建同一个标识：selectCount 追加 deleted = 0，看不见它，判为"没重复"
  → insert → 撞唯一索引
  → GlobalExceptionHandler 里没有 DuplicateKeyException 的处理器
  → 落到兜底 50000「系统内部错误」
```

用户看到的是"系统内部错误"，真实原因只是"你删过它"。而且这个标识**永久不可复用**。

修法：建之前用一条手写 SQL 连软删行一起查（`ResourceMapper.selectAnyByCode`，
手写 SQL 不被 `@TableLogic` 改写），若查到的是软删行，就**复活它**
（`restoreDeletedById` + 正常 `updateById`）。

两个配套细节，都是踩过才知道的：

- `restoreDeletedById` 必须手写。`updateById` 会在 WHERE 上追加 `deleted = 0`，
  而目标行恰恰是 `deleted = 1` —— 永远匹配不到，且 MyBatis-Plus 对"影响 0 行"**不报错**。
- 复活路径还要在内存里 `entity.setDeleted(0)`。`updateById` 把非空字段写进 SET，
  留着 `1` 就会把刚恢复的那行当场再删一次（同样是静默 0 行）。

复活在语义上也更对：`create_time` 保留了这个标识**第一次**出现的时间，
而"删过又加回来"在审计里本就是两条记录（delete + create），历史是完整的。

### 5. 树接口：全量返回，孤儿与成环降级为平铺

- **不分页。** 资源目录的量级是"几十到几百条"（一个权限码一行，不是业务数据），
  全量查出的代价远低于在树上做递归 SQL；而树被截断了就不再是树。
- **两个必须兜住的数据形态**，都会导致整棵树打不开：
  - **孤儿节点**：`parent_code` 指向一个不存在或已被删除的标识 → **按根返回**。
    否则父资源一被删，整棵子树就从界面上静默消失，而它们还在库里、还在产生权限。
  - **成环**：`a→b→a` → 按根返回。环会让对象图自己指向自己，序列化时递归不到底。

两条都不是理论顾虑：**这张表允许被直接写**（`DefaultAdminSeeder` 就是经 Mapper 直接写表的），
所以不能假设数据是干净的。判定方式是"从候选父节点沿 `parent_code` 向上走，
若走回自己、或走不出环，就按根处理"，用 `seen` 集合保证终止。

原则是：**看得到但层级不对，好过整棵树打不开。**

写入侧另有一道成环校验（`update` 时父节点不能是自身或自身的下级，返 `40913`）——
两道是分工，不是重复：写入侧管"从接口进来的改动"，树接口管"库里已经是脏的"。

### 6. 资源是平台级的，不按租户隔离

`tenant_id` 一律留空（入参里没有这个字段），与种子数据一致。

这不是省事，是**不能单方面加**：`AuthorizationMapper` 那条判定 SQL 只按
`ro.tenant_id` 限定角色，**没有**按 `r.tenant_id` 限定资源。若这里开始写租户，
判定侧不加对应条件，就会出现"资源登记给了租户 A，租户 B 也能被授予"的**假隔离** ——
那比明说不隔离更危险。要做租户级资源，得连同判定 SQL 一起改，那是一个独立决定。

### 7. 出参加一个派生字段 `requestScoped`

由 `resourceType` 推得（`ResourceType.isRequestScoped()`），**不在保存入参里** ——
让调用方能传一份与之矛盾的 `requestScoped` 只会制造"两个真相"。

它的意义是把枚举里的判断摆到界面上：管理员登记一条 `MENU` 时应当能直接看到
"此权限不参与后端拦截"，而不是自己记住九个类型里哪两个才算。
这个信息在代码里是枚举的一个方法，在界面上一旦缺失，人就会凭假设行事 ——
以为"登记了权限就拦得住"。

## 后果

**正面**

- 权限配置从"改库"变成"调接口"。这是菜单权限、角色授权共同的前置。
- 资源标识的形状约束第一次同时覆盖了**常量**（`AuthTaxonomyTest`）与**存量数据**
  （DTO 上的注解 + 契约里的正则）。
- 修掉一处会产生 500 且让标识永久不可复用的缺陷（决策 4）。
- 树接口对脏数据降级而不是报错，且写入侧堵住成环 —— 两个方向都有守卫。

**负面 / 代价**

- 新增 4 个权限码（`auth:resource:*`）与 1 个动作码，管理员权限总数从 9 变 13。
  所有记录这个数的地方都要跟着改（e2e 断言、`scripts/README.md`、根 `README.md`、
  `common-tools/README.md`）—— 这属于**计数型文档的既有代价**，不是本决策引入的。
- `selectAnyByCode` 与 `restoreDeletedById` 是本域**仅有的两处绕开 `@TableLogic` 的 SQL**。
  它们是必要的，但也意味着"逻辑删除"这条约定在本域出现两个例外，需要注释守住。
- `update` 改父节点时会逐级向上查一次（树深 3~5 层）。比递归 CTE 简单，
  也不依赖三套库各不相同的递归语法，代价是层级极深时是 N 次查询。

**后续约束**

- **资源标识创建后不得提供修改入口。** 若将来确需变更，走"新建 + 迁移"，不要
  在 `ResourceSaveRequest` 上给 `resourceCode` 加"仅更新时生效"的分支。
- **删除资源前必须先确认没有角色引用它。** 40915 的文案里带上引用数，
  是为了让调用方能直接说出"影响了几个角色"。
- 新增的 `ResourceType` 取值必须同步 `ResourceSaveRequest` 的 `@Schema` 描述，
  否则管理员在界面上看不到合法取值。
- 前端 `common-api` 的 `AccessPermissions` **本轮刻意不加** `auth:resource:*`：
  该文件的规则是"只列前端真的用到的"，而资源管理页尚未落地。
  页面落地时一并补上。

## 本决策未覆盖

- **前端资源管理页**（`platform-admin` 的下一个页面）。判定数据与 6 条契约路径都已就绪。
- **角色 / 组织 / 用户组的管理接口**（ADR-0016 未覆盖项，同批剩下的三个）。
- **扫描 Controller 自动登记资源。** `request_url` / `request_method` 两列就是为它准备的，
  但目前**列结构表达不了现实**：`auth:user:read` 同时保护 `GET /api/auth/users` 与
  `GET /api/auth/users/{id}`，而这两列是单值的。自动登记前必须先解决这个一对多，
  否则要么漏登记、要么把同一权限码拆成多行（那份 `DISTINCT` 才勉强对得上，
  但"一个权限码一行"的模型就被破坏了）。
- **资源版本治理**：`resource_version` / `is_deprecated` 两列**只存不用**，
  登记与更新时会如实写入，但没有任何地方读它们。

## 发现但未处理（供后续决策）

1. **`AuthorizationMapper` 的注释与 SQL 不一致。** 注释写
   "`tenant_id` 同时参与角色与资源的限定 —— 防止跨租户的角色串用"，
   而 SQL 里只有 `ro.tenant_id = #{tenantId}`；`r.tenant_id` 与 `rr.tenant_id`
   都不参与过滤。当前资源全是平台级（`tenant_id` 为空），这个差异不会产生实际影响，
   但注释会让人以为租户隔离已经覆盖到资源侧。
   **本切片刻意没有改它** —— 授权 SQL 是安全判定本身，在一次 CRUD 切片里改它
   属于"顺手改了安全边界"，应当独立成一个决策并重新跑一遍越权用例。

2. **计数型文档会随权限数漂。** 管理员权限数（9 → 13）散布在 e2e 断言与四份 README 里，
   每次都靠人肉同步。本轮已把**能推导的那一处改成推导**：`AuthApiTest` 原来写死
   `permissions.length() == 9`，现在写 `AuthPermissions.ALL.size()` ——
   这条断言的本意是"管理员持有 ALL 里的全部权限"，写死数字会把它降级成"改代码时记得改测试"。
   剩下 `scripts/verify-admin-permissions.mjs` 仍写死 `13`：它是独立于 Java 源码运行的 `.mjs`，
   取不到那个常量。若要根治，得让它可以解析 `AuthPermissions.java`，或者由后端暴露一个
   "全部权限码"的公开端点 —— 后者更干净，但那是新接口，不在本切片内。
