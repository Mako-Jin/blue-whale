# 0063. 判重与唯一索引对账 —— "挡不挡重名"有了机械守卫

- **状态**：已采纳
- **日期**：2026-10-15
- **决策者**：舰长

> 领的是 `0062`「未覆盖」第 2 条：**"挡不挡重名"这个分类本身没有机械守卫** ——
> `0062` 那轮的手工对账（扫"判重实现 + `*_EXISTS` 抛出"，与三方言 DDL 的索引清单
> 对账，找"无索引却判重"的列）做了一次就完了，谁哪天把哪个名称判重"顺手"加回来，
> 没有任何东西会拦住他。
>
> 本轮把那次手工对账机械化成 `scripts/verify-unique-columns.mjs`（零前置，进 CI 的
> `guards` job），`0062` 删完之后该清单为空 ⇒ 守卫**首跑即全绿**，天然起步。

## 背景

`0062` 立的判据：**判一个列该不该挡重名，看它在语义上是否指认唯一对象，
不看它有没有唯一索引**。但判据是纸面的 —— `TENANT_NAME_EXISTS` 活了多久
没有人发现，就说明"人回溯源码对账"守不住这种事。

把全仓判重与 DDL 列成四格表：

|                | 库上有 UNIQUE            | 库上没有                 |
| -------------- | ------------------------ | ------------------------ |
| 服务层判重     | ✓ 数据约束级（双保险）   | 白名单（业务规则级唯一） |
| 服务层不判重   | ✓ 数据约束级兜底，合法   | ✓ 名称列，`0062` 的结论  |

只有"服务层判重 + 库上无索引 + 不在白名单"这一格要红。**右上格刻意不查**：
有 UNIQUE 却不判重（如 `bw_auth_refresh_token.jti`）是合法形态 —— 数据约束自己
会以 `40900` 兜底，服务层不用提前查。

## 决策

新守卫 `scripts/verify-unique-columns.mjs` 做四件事（全部零前置：只读
`src/main` 源码文本与三方言迁移脚本，不编译、不连网、不写文件）：

1. **每个被引用的 `*_EXISTS` 码都登记了它判的是哪一列**（脚本里的 `JUDGED` 表，
   当前 8 个码）。登记这个动作就是 `0062` 判据的落点 —— 新加判重的人必须先
   回答"这个列在语义上指认什么"；答不出"唯一对象"的，别写判重。
2. **登记的码仍然被引用**（腐烂检查，与 `verify-result-codes.mjs` 同口径）——
   若哪天有人走 `0062` 的路删掉某处判重，他会同时被提醒：删登记、把列挪进
   `NO_INDEX_ALLOWED` 写明理由。**一处决定，两处提醒**。
3. **三方言的唯一索引集合一致**。三份迁移脚本本该是同一次提交的拷贝（`0038`），
   此前谁改一份漏两份**没有任何东西会发现** —— 这是本守卫白捡的一条。
4. **每个判重列要么有 UNIQUE，要么在 `NO_INDEX_ALLOWED` 里写明理由**（当前
   `bw_auth_user.email` / `.phone` 两条 —— `0062` 三分里的"寻址"类，业务规则级
   唯一，有意接受并发漏网）。反向腐烂同样红：有人给 `email` 加了 UNIQUE，
   白名单理由就过期了。

锚定方式与 `0060` 的守卫同形：**语法级、逐字符可判、不依赖任何约定，因此不误报**。
它刻意不解析"先查后写"的具体写法（`selectCount` / `selectAny*` / exists helper
都行）—— 那是代码风格，不是要钉的事实。

## 后果

**正面**

- `0062` 的判据从纸面变成了 CI 必过项；"加回判重"或"改索引漏方言"都会红。
- 新增判重的成本里多了一步"登记"，而这一步正是逼人写下 `0062` 那个问题的答案。
- 三方言索引同构第一次有了机械守护。

**负面代价**

- `JUDGED` 与 `NO_INDEX_ALLOWED` 是**手工登记表**：码改名时要同步两处
  （枚举 + 本脚本），漏了会红 —— 但红即是提醒，这正是设计意图。
- 三方言一致性按**全集合**比对（不只判重列）。将来若某方言**合法地**需要
  不同的索引（现在没有这种情形），守卫会误红 —— 到时候再放宽口径，
  把"一致"收窄到判重列。

**后续约束**

- 新加判重：先在 `JUDGED` 登记码 → 列，再想清楚它属于 `0062` 三分的哪一类；
  属"寻址"类的，把列加进 `NO_INDEX_ALLOWED` 并写明理由。
- 删判重（`0062` 式）：删代码、删登记、（若该列仍被挡）挪白名单 —— 一次提交三步。

## 未覆盖

1. **"名字旁边必须有唯一标识"**（`0061` 未覆盖 3）仍是纸面规则 —— 可机械判定的
   方向：扫前端渲染 `*Name` 的位置，看同一展示单元有没有 `*Code` / `fullName`。
2. **别的"零理由"实现**（`0062` 未覆盖 3）：本守卫只对账"判重 × 唯一索引"这一类
   事实，全仓其它"零理由"的机制（只存不用的开关列等）不在射程内。
3. **"有 UNIQUE 却不判重"**刻意不查（右上格合法）；若某天想让"数据约束级"域
   强制双保险，那是新的决定，不是本守卫漏了。
