# 0004. 前端日志上报：采集与传输分层，新增 LogRecord 契约

- **状态**：已采纳
- **日期**：2026-10-09
- **决策者**：舰长

## 背景

前端日志打印在客户的浏览器里。**生产环境无法直接查看用户浏览器**，因此"日志打出来"只解决了一半问题——出了线上故障，那些日志等于不存在。

要回答的问题表面上是二选一："用事件机制，还是用异步 HTTP 直接调用？"

实际上这是两个不同层次的事，被混在了一起：

- **事件 / 输出通道**属于应用**内部**的分发解耦——日志怎么从调用点交出去；
- **HTTP** 只是众多出口中的**一种传输方式**。

同时，在评估自研 logger 时发现现有 `LogSink` 存在结构性局限：

```ts
type LogSink = (method: ConsoleMethod, args: unknown[]) => void;
```

它是**已渲染结果**的消费者，因此不适合做上报钩子：

1. **级别有损**：`LEVEL_CONSOLE_METHOD` 把 `info` / `success` 都映射为 `'log'`，`trace` / `debug` / `perf` 都映射为 `'debug'`。远端收到 `'log'` 无法区分 `info` 与 `success`。
2. **元数据被拍平**：命名空间、时间戳、上下文（如 traceId）全被拼进字符串，要拿结构化字段只能**反向解析自己的格式**——脆弱且不可维护。

## 决策

### 1. 采集与传输分层，不二选一

链路固定为四段，各段职责单一：

```
埋点（Logger） → 聚合（批量·采样·去重·脱敏·限流·断路） → 传输（sendBeacon / fetch） → 服务端
```

其中"事件机制"是**采集与分发**的形式，"HTTP"是**传输**的手段，二者是上下游关系，不存在替代关系。

### 2. 不允许"直接异步调用 HTTP"

`sendBeacon` / `fetch` 直接挂在日志调用点上是明确禁止的，四条理由：

| 问题 | 后果 |
| --- | --- |
| 页面关闭时 `fetch` 被取消 | **最需要的那条日志必然丢**——用户被搞崩后关页面，正是要排查的场景。可靠手段是 `navigator.sendBeacon()` |
| 写放大 | 日志量 = 用户数 × 会话时长 × 密度。不做批量 / 采样 / 限流，后端会被自己的客户端打挂 |
| 日志雪崩 | 上报失败 → 产生 error 日志 → 再次触发上报，形成递归。必须有断路，且**上报通道自身的异常必须静默吞掉** |
| 敏感信息外泄 | 前端日志最易带出 token / 手机号 / 用户输入。**脱敏必须在采集层完成**，不能依赖后端 |

### 3. 采样与限流是必选项，不是优化项

建议基线：`error` 全量、`warn` 采样、`info` / `debug` / `perf` 默认不上报（或极低采样），叠加用户级单位时间配额。

### 4. 新增 `LogRecord` 契约，作为采集层的对外接口

在 logger 中实体化"结构化记录"，新增 `onRecord` 钩子。**`LogSink` 保持不动**，两者分工写明：

| 通道 | 消费对象 | 用途 |
| --- | --- | --- |
| `LogSink` | **渲染后的样子**（含 `%c` 样式串） | 控制台输出、单元测试捕获、页面镜像 |
| `onRecord` | **结构化事实**（`LogRecord`） | 上报、落库、聚合 |

```ts
interface LogRecord {
  level: LogLevel;      // 级别保真：info 与 success 分得开
  namespace: string;
  timestamp: number;
  message: string;
  data: unknown[];      // 保持原始形态，对象不被 stringify
  context?: Record<string, unknown>;
  traceId?: string;     // 上报必需的关联维度
  sessionId?: string;
  route?: string;
  release?: string;
}
```

记录的派发点固定在**级别过滤之后、格式化之前**——与"过滤前置于格式化"的既有原则一致，被压制的日志不产生任何开销；即便渲染环节抛错，记录也已经交出去了。

**本期只实现采集契约，不实现传输与聚合**：后端尚不存在，没有可发送的目标。传输层随后端日志服务一起落地，届时只需实现一个 reporter，不必再改动 logger 核心。

### 5. 生产优先复用成熟方案

Sentry / 腾讯 RUM / 阿里 ARMS 等已具备完整链路。**自研的合理范围是"采集 + 事件契约"**（即本 ADR 的 `LogRecord`），传输通道可复用现有 APM。

### 6. traceId 跨端打通是最高优先级

前端生成 → HTTP header 透传 → 后端日志同 ID。这一步做通，两端日志才真正串得起来；不做，前后端日志是两座孤岛。

## 后果

**正面**

- 上报有了干净的接口，不需要反向解析自己格式化的字符串
- 级别与元数据在上报链路上无损耗
- 上报通道的异常被隔离在 `try/catch` 内，日志系统故障不会反噬业务
- 传输层可以后置实现，且不需要再动 logger 核心

**负面 / 代价**

- `LoggerConfig` 增加了 5 个字段（`onRecord` + 4 个上报元数据），配置面变宽
- 采集与传输分离意味着**必须显式实现聚合层**，不能靠"顺手发一下"蒙过去
- 采样策略需要按业务调整，多一处需要持续调优的参数

**后续约束**

- 任何上报实现**禁止**直接挂在日志调用点上，必须经由 `onRecord` 接入
- 上报通道内部抛出的异常必须被吞掉，不允许向外传播
- 新增上报维度（字段）时，先加进 `LogRecord` 与契约，再由两端消费
- 脱敏逻辑归属采集层，后端不承担前端日志的脱敏责任
