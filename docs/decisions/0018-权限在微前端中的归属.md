# 0018. 权限在微前端中的归属：会话在基座装配、实现在 packages、管理界面独立成子应用

- **状态**：已采纳
- **日期**：2026-10-12
- **决策者**：舰长

## 背景

后端权限域（`sts-server-auth`）已按 `docs/decisions/0016` 落地为**本仓第一个从表到接口的完整闭环**：
12 张表、8 条接口、`@RequiresPermission` + `AuthInterceptor` 的运行时鉴权入口、刷新令牌轮换与重放检测，
并在契约里占了 16 条路径中的一半。

**但前端的消费数是 0。** 基座（`platform-portal`）的「登录」按钮目前只是一个切换 `userId` 的调试开关
（`layouts/BasicLayout.tsx` 里明写「演示用」），`HostGlobalState` 只下发 `theme` / `locale` / `userId`
三个字段。也就是说：**认证链路后端已经付完了钱，前端一条接口都没调。**

落这一块之前必须先回答一个归属问题：**权限做进基座，还是独立成一个子应用由基座调度？**

这个问题被四条既有约束夹住，不能凭手感拍：

| 约束                                         | 出处                  | 对本决策的影响                                                      |
| -------------------------------------------- | --------------------- | ------------------------------------------------------------------- |
| 跨端只认 OpenAPI 契约，前端 SDK 禁手写       | 铁律②                 | 8 条 auth 接口必须经 `common-api` 接线，不能在基座里散写 `fetch`    |
| `packages/*` 不得反向依赖 `platform/*`       | 铁律④                 | 会话与权限的**实现**只能落在 `packages/`，基座是它的装配方          |
| `platform-user` 与 `platform-admin` 互不引用 | 铁律⑤                 | 权限能力若只写在基座组件里，两个子应用将来会各写一套                |
| 子应用必须保留独立运行分支                   | `docs/decisions/0012` | **登录逻辑写在基座里 ⇒ 子应用单跑时没有登录能力**，独立可调试性作废 |
| 客户端五条底线含「首屏零阻塞」               | `docs/decisions/0003` | 登录页属于首屏路径，不该是最贵的路径                                |

两条来自后端实现的事实，直接决定了前端的形状，必须先摆出来：

1. **权限不在令牌里。** `JwtCodec` 的载荷只有 `sub/uid/tid/uname/typ/jti/iss/aud/iat/exp`，
   `roles` 与 `permissions` 是 `LoginVO` / `MeVO` 的字段 —— 意味着**刷新页面后必须有一次「会话恢复」**
   （调 `/api/auth/me`），不能靠解析令牌拿到权限。
2. **刷新令牌是轮换 + 重放检测**（`docs/decisions/0016` 第 8 条）：已作废的 jti 再次出现即判定为泄露，
   撤销该用户**全部**刷新令牌。这意味着前端若发生**并发刷新**，第二个请求持的正是刚被轮换掉的旧令牌 ——
   后端会把正常时序误判成重放攻击，代价是把用户全部会话撤销。**刷新必须单飞（single-flight）。**

## 决策

### 1. 三件事分开归属，不做「基座 vs 子应用」的二选一

| 能力                                           | 性质                                                      | 归属                                        |
| ---------------------------------------------- | --------------------------------------------------------- | ------------------------------------------- |
| **会话**：登录、登出、令牌存取、刷新、会话恢复 | 跨应用的横切事实，与 `theme` / `locale` / `userId` 同性质 | **实现下沉 `packages/`，基座只做装配**      |
| **权限判定**：这个按钮 / 页面能不能看          | 全应用唯一的判定结果，多消费方                            | **基座算出来 → 全局状态下发，子应用只消费** |
| **权限管理**：组织 / 角色 / 用户组 / 资源 CRUD | 业务功能，体量大（对应 12 张表的管理界面）                | **独立子应用 `platform-admin`**             |

### 2. 会话实现落在 `packages/`，基座只做装配

- `common-api`：接 8 条 auth 契约（`satisfies keyof paths` 钉住路径常量，`LoginVO` / `MeVO` 用 `expectTypeOf` 钉住）
- `common-tools/http`：负责 `Authorization: Bearer <token>` 注入与 401 / 403 分流（ADR-0007 给鉴权钩子留的位置就在这里）
- 令牌存取与「会话提供方」抽象成一份可注入的实现，边界是：**它不 import qiankun、不 import 基座**
- **基座只做装配**：登录页、路由守卫、把会话结果下发。守卫必须在基座 —— 路由表在基座（由 `MICRO_APPS` 推导，ADR-0012 第 7 条）

这条的关键不是「放在哪个目录」，而是**同一份实现既能被基座驱动、也能被子应用单独驱动**：
子应用单跑（非 qiankun 环境）时，会话提供方从「基座下发的全局状态」换成「应用自身的 store」，
其余逻辑一行不改。

### 3. 权限判定单点计算，经既有的全局状态通道下发

- `HostGlobalState` 增加 `roles?: string[]` 与 `permissions?: string[]`，与 `MeVO` 的字段形状对齐；
  仍按既有约定用**可选的结构化类型**（`common-tools/micro/types.ts` 不 import 基座的 `GlobalState`）
- 计算只发生在基座：登录响应的 `LoginVO.permissions` → 直接采用；刷新页面 → `/api/auth/me` 恢复
- **子应用不得自行调用 `/api/auth/me`**：多一个调用点就多一处「只判了登录、忘了判权限」的可能
- 权限码形态与后端 `AuthPermissions` 完全一致：`域:资源:动作`（如 `auth:user:create`），
  **前端不得拼接或自造**（后端已把散写字面量的风险收成常量，前端再拼一次等于把风险搬回来）

### 4. 权限管理界面独立成 `platform-admin`

它是业务页面（表格、表单、树），体量大；基座要保持「壳薄」。基座一旦开始承载 CRUD 就会长成上帝应用 ——
而且基座代码**不受 qiankun 沙箱约束**，样式与依赖会与其他子应用混着长（ADR-0012 第 8 条已吃过样式串味的亏）。
它同时是按钮级权限最好的演示载体：同一个页面，有 `auth:user:create` 才出现「新建」按钮。

`platform-user` 仍按「按需再建，不空建」处理，不在本决策范围内。

### 5. 不开「认证子应用」

把登录做成子应用由基座调度，三条理由由轻到重：

1. **鸡生蛋**。进应用要先加载子应用才能登录，而加载子应用本身要走基座 ⇒ 未登录状态下先付一次
   远程加载 + qiankun 沙箱初始化，与 ADR-0003 的「首屏零阻塞」直接冲突。登录页是**首屏路径**，不该是最贵的路径。
2. **令牌会绕一圈回来**。令牌的持有者变成认证子应用，而消费方是所有其他子应用**和基座本身** ⇒
   仍然要「子应用 → 基座 → 再下发」，绕一层后回到决策 2。
3. **守卫逻辑会分裂两处**。「未登录不进子应用」是壳级判断（导航都不该出现），
   放子应用里就成了「基座要判断能不能加载那个负责判断的子应用」。

### 6. 令牌存储：access 放内存，refresh 持久化

- **access token 放内存**（不落盘）：它的载荷里已有 `uid` / `tid`，落盘只是白白扩大暴露面
- **refresh token 持久化**（`localStorage`）：换取「刷新页面后静默续期」的能力
- 接受这个权衡的理由是**后端的轮换与重放检测本就是为这条路设计的**：refresh 一旦泄露并被使用，
  旧令牌的再次出现即触发撤销该用户全部刷新令牌 —— 风险被兜住且有迹可循
- **httpOnly cookie 列为将来可选项，本次不做**：它需要后端改 `Set-Cookie`、并处理 CSRF 与跨源
  （现状是 `localhost:3000` ↔ `localhost:8080` 跨源），改动面远大于收益

### 7. 401 / 403 分流落在 http 内核，且刷新必须单飞

- **401 → 尝试刷新一次**；仍失败则清会话并通知基座跳登录页
- **403 → 业务「无权限」提示，不跳登录页**（ADR-0016 硬规则：认证与授权分开，
  前端据此决定是"跳登录"还是"提示无权限"）
- **刷新请求自身必须豁免自动刷新**：否则刷新失败 → 401 → 再刷新，形成死循环
- **并发 401 必须合并为一次刷新（single-flight）**。这不是性能优化，是**正确性要求**：
  轮换 + 重放检测下，并发的第二个刷新请求持的是刚被作废的旧令牌，后端会将其判定为重放攻击，
  撤销该用户全部刷新令牌 —— 一个前端的并发时序问题会升级成"全体会话被踢"
- 刷新成功后**重放原本挂起的请求**（每个请求各自重试一次，不递归）

### 8. 子应用独立运行时的会话来源

子应用单独跑（`:3200` / `:3300` / `:3400`）时没有基座下发，走**同一份 session 实现**，
只是把提供方换成应用自身的 store。开发期允许通过环境变量或本地写入的测试令牌起步，
但**不得在子应用里再实现一套登录页** —— 那会立刻长出第二份会话逻辑，正是本 ADR 要避免的事。

### 9. 子应用要发已鉴权请求：基座下发"认证能力"，不下发令牌值（第③段补充）

第③段（`platform-admin`）是第一个要发**已鉴权**请求的子应用，逼出了本决策没写到的最后一环：
令牌在基座的内存会话里，子应用怎么拿到？

把令牌值放进全局状态下发看起来最省事，但被两条硬约束否决：

1. **令牌值会陈旧。** 访问令牌是短效的，基座在后台静默刷新一次之后，
   子应用手里那份就成了作废的令牌，而它自己并不知道 —— 症状是"刚才还好好的，突然全部 401"。
   下发"取令牌"这个**动作**（函数）则永远取到最新的一份。
2. **刷新必须全应用只发生一次。** 第 7 条已经论证过并发刷新 = 全体被踢。
   子应用若各自实现刷新，等于把这个坑复制到每个子应用里。

因此 `HostProps` 增加**可选**的 `auth`（`common-tools/micro` 的 `HostAuthBridge`）：

```ts
type HostAuthBridge = {
  getAccessToken(): string | null; // 按需取，始终是基座手里的最新一份
  reauthenticate(): Promise<boolean>; // 请基座刷新一次；并发由基座合并
};
```

两个配套结论：

- **不提供"清空会话"**。会话失效是全局事实，清空只该有基座一个入口
  （基座对 `createAuthChannel` 刻意不传 `onAuthLost`，靠声明式守卫跳转）。
- **单飞必须在会话层再收一次。** `common-tools/http` 的去重是"按客户端"的，
  只能合并同一个客户端上的并发 401；基座自己的请求与若干子应用经桥委托过来的请求
  分属不同客户端，彼此看不见。因此 `AuthChannel.reauthenticate()` 自身也做合并 ——
  刷新是**会话级**动作，合并点落在会话层才算完整。

子应用侧则把两种来源归一成同样的两个动作（见 `platform-admin/src/auth/index.ts`）：
被基座加载用桥，独立运行自建会话（第 8 条），上层业务代码**完全不区分运行方式**。

## 后果

**正面**

- 会话与权限**只有一份实现**，基座、子应用、将来的 `platform-user` / `platform-admin` 共用
- 权限判定**单点计算、单点下发**，不存在「某个子应用只查了是否登录」的缺口
- 基座保持「壳薄」，与 ADR-0012 的定位一致
- 子应用的独立运行分支与独立可调试性保住
- 401 / 403 的语义只有一处解释，与后端 ADR-0016 的硬规则一一对应

**负面 / 代价**

- 基座要多一条守卫与两个全局状态字段（`roles` / `permissions`）
- 子应用必须处理**权限尚未就绪的中间态**：首帧拿不到权限集合时，既不能默认放行（漏权限），
  也不能默认隐藏到闪烁 —— 需要显式的「未就绪」状态，这是新增的、必须逐处考虑的复杂度
- refresh 持久化仍有 XSS 暴露面，由后端的轮换 + 重放检测兜底，属于**接受的风险**
- session 要多一层「提供方可替换」的抽象，比直接写死 `localStorage` 啰嗦

**后续约束**

- 前端不得自造、拼接权限码，只能引用与后端 `AuthPermissions` 一致的字面量
- 子应用不得自行调用 `/api/auth/me` 或任何认证接口
- 子应用不得自行刷新令牌、不得持有令牌副本：需要令牌一律经 `HostAuthBridge` 按需取，
  需要恢复一律委托 `reauthenticate()`（第 9 条）
- 所有需要令牌的请求必须经 `common-tools/http`，禁止绕过内核直接 `fetch`
- 刷新必须单飞；新增任何调用路径都不得绕过单飞合并（内核合并 + 通道合并，两层都要在）
- 新增子应用时，登录态与权限一律消费基座下发，不自建
- 需要同步的文档：`docs/decisions/0012`（全局状态字段表）· `docs/README.md` 对照表 ·
  `platform/platform-portal/README.md` · `packages/common-tools/README.md`（http / micro 章节）·
  `packages/common-api/README.md`

## 落地顺序

分三段，每段可独立交付、独立验证：

| 段             | 范围                                                                                                                                                                                                                                                                              | 验收方式                                                                                                 | 状态                        |
| -------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------- | --------------------------- |
| ① 契约与传输层 | `common-api` 接认证链路（登录 / 刷新 / 登出 / `me` 共 4 条路径）并组装 `createAuthChannel`；`common-tools/http` 令牌注入与 401 恢复、刷新单飞；`common-tools/session` 令牌存取                                                                                                    | 单测（含并发 401 合并、刷新失败清会话、403 不刷新）                                                      | **✅ 已完成**（2026-10-12） |
| ② 基座装配     | 登录页、路由守卫、`HostGlobalState` 增 `roles` / `permissions`、启动时 `restore()` 续期                                                                                                                                                                                           | 真浏览器脚本：未登录跳登录页、登录后可访问、刷新页面会话恢复、登出清干净                                 | **✅ 已完成**（2026-10-12） |
| ③ 子应用消费   | 新建 `platform-admin`（:3500）：用户 / 租户两页，操作入口按 `auth:user:*` / `auth:tenant:*` 显隐；`common-api` 接入权限域管理接口（users / tenants 共 5 条路径 11 个操作）；`HostProps.auth` 下发认证能力（第 9 条）；后端种子一个只读账号（`auditor`，仅两项读权限）作为对照身份 | 真浏览器脚本断言**两种身份**下的按钮差异 + 真实增删一次；后端接口测试断言审计员"读得到、写不了（40301）" | **✅ 已完成**（2026-10-12） |

**② 段落地时的三个实现要点：**

- **权限下发是模块级订阅**（`portal/src/micro/session-sync.ts`），不是布局组件里的 `useEffect`：
  登录页 `/login` 不渲染布局，写在布局里的话，恰恰在最需要广播「已登出」的时刻没有人在同步。
- **跳转只留一处**：守卫用声明式 `<Navigate>`；登出与 401 掉线只清会话。命令式跳转与
  声明式重定向并存会在 render 阶段打架，所以 `createAuthChannel` 的 `onAuthLost` 在基座里**刻意不传**。
- **守卫必须等恢复阶段结束再判「未登录」**：刷新页面时内存里没有令牌，
  直接按未登录处理的话，每次刷新都会掉一次登录。

**① 段落地时修正了两处本文档的原始描述：**

- 原写「接 8 条 auth 路径」。实际只接了**认证链路**所需的 4 条；权限域的**管理**接口（users / tenants /
  organization / role / usergroup / resource）随 `platform-admin` 在 ③ 段接 —— 按「不预置空壳」的既有约定，
  没有消费方的接口接线不提前做。
- 原写「令牌持久化与恢复（`/me`）」。实际 `restore()` 走的是**刷新令牌接口**：
  登录与刷新的返回体里**本身就带身份与权限集合**（`LoginVO` 有 `roles` / `permissions`），
  所以一次刷新即完成恢复，不必再调 `/me`。少一次请求，也少一个「有令牌但不知道是谁」的中间态。
  `/me` 保留给 `reload()`（权限被后台改动后重新拉取，且不轮换令牌）。

## 本决策未覆盖（后续切片）

- **httpOnly cookie 方案**：需要后端配合改 `Set-Cookie` 并处理 CSRF 与跨源
- **数据权限的前端呈现**：`data_scope` 的判定本身未做（见 ADR-0016 未覆盖项）
- **权限管理界面剩余的实体**：组织 / 角色 / 用户组 / 资源的 Controller 与 Service 尚未落地
  （ADR-0016 未覆盖项）。第 ③ 段已交付的是**后端已就绪**的 users / tenants 两张表的管理面，
  其余实体待后端补齐接口后按同样的写法接入 `platform-admin`（`common-api` 的 `access.ts`）
- **页面级权限**：导航入口与路由的按权限过滤（现在只做了按钮级；
  判定数据已经下发，加门只是基座侧的薄薄一层）
- **网关层令牌校验**：属部署面，与微前端生产部署一并考虑（ADR-0012 未完成项）
- **会话过期与多标签页同步**：多标签页登出 / 续期通过 `storage` 事件同步，暂不做
