# 0032. 日志链路查询的条数上限与稳定排序

- **状态**：已采纳
- **日期**：2026-10-13
- **决策者**：舰长

## 背景

`0026` 的「发现但未处理」第 3 条写着：

> **日志的 `listByTraceId` 在超大链路上没有条数上限**：一个 traceId 下的记录数
> 由客户端行为决定，当前直接 `selectList` 全量返回。

本轮核实时发现**它比那句话描述的更直接** —— `traceId` 不是"链路自然形成的规模"，
而是**上报方自己填的字符串**：

```java
// ClientLogService.report（改前，一直是这样）
entity.setTraceId(truncate(item.getTraceId(), 64));
```

上报接口 `POST /api/logs/client` 是**刻意公开**的（登录页出错时也要能上报，见 `0026`），
单批上限 500 条。于是"让某个 traceId 上攒下任意多条记录"是**两次正常请求**就能做到的事，
不需要任何异常行为。随后一次 `GET /api/logs/client/trace/{traceId}` 就把它们
全部拉进内存、全部序列化、全部写进一个响应体。

同一域里另外两个读接口都不是这样：

| 接口 | 条数上限 | 时间窗 |
| --- | --- | --- |
| `page`（分页查询） | `PageQuery.MAX_SIZE = 200` | 缺省最近 7 天 |
| `stats`（聚合统计） | ——（聚合没有行数问题） | 缺省最近 7 天 |
| `listByTraceId`（**改前**） | **无** | **无** |

所以这不是"有意的差异"，是**漏了一个**。

## 决策

### 1. 补上 7 天缺省时间窗，与同域另外两个接口一致

`DEFAULT_WINDOW_MILLIS` 已经存在（`page` / `stats` 都在用），直接复用。

链路的语义是"一次请求的完整链路"，它天然落在**秒级**；客户端批量上报的延迟
也只是秒到分钟级。7 天对它是极宽松的上界，不会把任何真实链路切掉。

### 2. 上限 200 条，用**分页插件**而不是手写 `LIMIT`

200 取自 `PageQuery.MAX_SIZE` —— "一次查询最多取回多少行"这件事在同一模块里
用同一个数，比另立一个数字更容易被记住。

**为什么不用 `.last("LIMIT 200")`**：本仓要跑 MySQL 与达梦两套方言（见 `0010`），
手写的 `LIMIT` 在达梦下未必成立，而 MyBatis-Plus 的分页插件会按**当前方言**
生成分页 SQL。`page()` 已经在用 `selectPage`，这里跟它保持一致，
就不必为"换个库跑"再排查一次。

`new Page<>(1L, TRACE_MAX_ROWS, false)` 的第三个参数关掉 count 查询 ——
本接口不需要总数，省掉一次 `count(*)`。

### 3. 它不是分页，是兜底

链路的读法是**要么整条读、要么不读** —— 翻页读同一条链路的第 4 页没有意义，
界面也不会提供"下一页"。所以这里**不加 `page` / `size` 参数**，超出上限即截断
（调用方拿到的是**最早**的 200 条，因为结果按时间升序）。

### 4. 次级排序键补 `id` —— 顺带修掉一个隐性缺陷

改前的排序只有一列：`orderByAsc(serverTime)`。而**同一批上报的记录，
`serverTime` 是同一个值**：

```java
// ClientLogService.report：serverTime 在循环**外**只算一次
long serverTime = System.currentTimeMillis();
for (ClientLogItem item : request.getLogs()) { ...; entity.setServerTime(serverTime); }
```

一批 20 条日志因此带着同一个 `serverTime`。只按它排序时，**批内顺序由数据库
任意决定** —— "链路的阅读顺序"会随执行计划、数据分布甚至版本变化而漂移，
而按发生顺序读一次请求，恰恰是这个接口存在的全部理由。

`id` 是自增主键，同一批内**等于插入顺序**，也就是上报时的原始顺序。补上它，
顺序才真的确定。（`buildWrapper` 里的分页查询早就因为同一个理由加了 `id` 次级键，
链路查询当时漏了。）

> 要说清楚的是：**这个缺陷测不出来**。现有测试断言 `$.data[0].message == "第一步"`，
> 在 H2 上即便不补 `id` 也一直是绿的（引擎碰巧按插入顺序返回）。
> 补 `id` 是把"碰巧对"变成"保证对"，理由由注释承载，而不是由某条断言证明。

## 后果

- 一次链路查询的响应体有界（≤ 200 条），不再有"一个响应打到几百 MB"的路径；
- 链路的时间范围有界（≤ 7 天），查到的不会是同名 `traceId` 的历史残留；
- 链路的**顺序变得确定**，不再依赖引擎行为；
- 契约有一处 `@Operation` 文案变化（描述里补上上限与时间窗），
  `docs/api/openapi.json` 随之重新导出；**结构不变**（无新路径、无新模型）。

**没有改变**：租户隔离仍由服务端强制加上（`0026` 的成果，本轮不动）；
`traceId` 仍由上报方自填且不做格式校验；上报仍然公开。

## 本决策未覆盖

`traceId` 的**格式与长度**仍然不做校验（只做 64 字符截断）。它是"由客户端生态
约定"的标识（HTTP 头、日志库、APM 各有各的生成方式），服务端收紧它只会让某些
客户端的链路断掉，收益接近于零 —— 真正的闸门是上面两条（条数 + 时间窗），
它们对任何格式都成立。
