# 0041. 契约生成物的同步守卫

- **状态**：已采纳
- **日期**：2026-10-13
- **决策者**：舰长

## 背景

`0040` 的「本决策未覆盖」第 2 条把这一步指明了：

> `web/packages/common-api/src/generated/schema.d.ts` 与 `openapi.json` 是否同步
> （生成物有没有跟上契约）没有守卫。`0006` 把生成物入库就是为了让它在 review 里显形，
> 机器兜底尚无。

本轮就是补上那半句。

### 它和 `0040` 守的不是同一段

`0040` 的 `verify-api-contract.mjs` 拿 `openapi.json` 去核对 **`docs/api/README.md`**，
守的是"文档与契约一致"。它读的两份都是入库文件 —— 于是**契约落后于代码时它看不见**
（两边一起旧、彼此自洽），这一条 `0040` 已在「未覆盖」第 1 条里如实写明。

本决策守的是另一段：

```
docs/api/openapi.json  ──openapi-typescript + prettier──▶  common-api/src/generated/schema.d.ts
     （入库）                                                        （入库）
```

两段都在版本库里，但**没有任何东西保证右边那半是由左边那份生成的**：
契约可以改、生成物不动，两份文件并存、各自"看起来都对"。

### 为什么这个错特别安静

契约变了而生成物没跟上时，**编译得过、用例也全绿** ——
前端消费的本来就是那份旧类型，前后自洽，没有任何一处会反对。

唯一能察觉它的场合是"有人打开 `schema.d.ts` 与 `openapi.json` 对着看"，
而那正是 `0039` 已经证伪过的办法（"最近一次改动顺手核过的地方就对，
没人再看第二眼的地方就漂"）。

`0006` 把生成物**入库**（而不是构建时生成）有意为之：让它在 review 里显形。
但"入库"只提供了**看得见的机会**，没提供**会被拦住的保证** —— 本轮补的是后半句。

## 决策

1. **在 CI 的 `web` job 里加一步：重跑一遍生成器，产物必须与入库版本逐字节相同。**

   ```sh
   pnpm --filter common-api gen:api
   git status --porcelain -- packages/common-api/src/generated   # 有输出即失败
   ```

   `gen:api` **只吃 `docs/api/openapi.json`**
   （`openapi-typescript <契约> -o <产物> && prettier --write <产物>`），
   不起后端、不连网 ⇒ 可以在流水线里随时重放。

2. **它不挂 `guards` job，尽管它同样"不需要服务"。** `guards` 的定义是**零前置条件**
   （不装依赖、不起服务），而这一步需要 `node_modules`（`openapi-typescript` + `prettier`）
   ⇒ 挂在已经装完依赖的 `web` job 里，紧跟"装依赖"之后：契约漂了应在十几秒内报出，
   而不是等 lint / 单测 / 构建全跑完。

3. **比字节，不比结构。** 备选做法是解析两份文件、比 schema 名字集合之类的**结构**差异 ——
   更宽容，但会漏掉字段级改动，而字段级改动恰恰是最常见的那种。
   敢比字节的理由是**上游是确定的**：`gen:api` 的输出实测连跑三次哈希一致
   （`a36a6824…`，且与入库版本相同），"上游不确定"正是比字节唯一会误伤的情形。
   再者，`gen:api` 末尾的 `prettier --write` 本来就是为这件事服务的 ——
   它在生成的那一刻就把格式归一，才让"逐字节相同"成为一个**可达**的判据；
   去掉它，`openapi-typescript` 的 4 空格 + 双引号与仓库的 2 空格 + 单引号之间
   会产生约 1800 行纯重排的 diff，"比字节"当场变成必然假红。

4. **失败信息要给出下一步动作**，而不只是"不一致"：打印 `--stat` 与那句
   `cd web && pnpm --filter common-api gen:api`。这一类失败的正确处置是**唯一的**
   （重跑生成器、把产物一起提交），不需要人再判断。

## 后果

**正面**

- `AGENTS.md` 硬性要求 5 的后半句（"改后端接口后必须跑 `gen:api`，并与代码同一次提交"）
  **第一次有了机器兜底**；此前它只写在文档里。
- 三段链路的**中间那一段**第一次被钉住：`0040` 守"契约 ↔ 文档"，本决策守"契约 ↔ 生成物"。
- 本机一条命令即可复现（**与 CI 同一套判据**）：

  ```bash
  cd web && pnpm --filter common-api gen:api
  git status --porcelain -- packages/common-api/src/generated   # 输出为空 = 同步
  ```

- **它不是空转**：三个负例逐个验过 ——

  | 扰动 | 结果 |
  | --- | --- |
  | 改了 `openapi.json` 而**忘了重生成** | 生成物跟上了新契约 ⇒ 与入库版本不同 ⇒ 红 |
  | `openapi.json` 不是合法 JSON（**生成器自己失败**） | `set -e` 拦在生成那一步 ⇒ 红（不会走到比对） |
  | **入库的生成物被删、生成器又把它造回来**（`git rm --cached` 后重跑） | 红 —— 但**最初那版写法会漏**（见下） |
  | 什么都不改 | 绿 |

  第三个是一条**实现时抓出来的真孔**：最初用的是 `git diff --quiet`，而 **`git diff` 看不见
  未跟踪文件** —— 把入库的生成物删掉、生成器原地重建它，`git diff` 一声不响、检查报绿。
  改成 `git status --porcelain -- <生成目录>` 才把这一类纳入；顺带把比对范围从"那一个文件"
  放宽到**整个生成目录**（那才是生成器声明的输出面）。

  > 附带一条被否掉的负例写法：**"直接改生成物"不是有效的负例** ——
  > `gen:api` 会把工作区里那份覆盖掉，比对时两边又是同一份，照旧报绿。
  > 负例必须落在**入库版本**这一侧（改契约、删文件），改工作区是改不动的。

**代价 / 负面**

- `web` job 多约十几秒。它排在"装依赖"之后，所以**依赖装不上时它也不会跑** ——
  那种情况下会先红在装依赖那一步，不是漏检。
- 它**只证明生成物忠于契约**，不证明契约忠于代码。后者仍是 `0040`「未覆盖」第 1 条
  （要构建并启动一次应用才能查）。
- 生成器或 Prettier **大版本升级时会一次性红**（输出格式变了，产物需要重新生成并入库）。
  这是要的：那种升级本来就该带着重新生成的产物一起提交。

**后续约束**

- 升级 `openapi-typescript` / `prettier` 时，**同一次提交**带上重新生成的 `schema.d.ts`。
- **不要**去掉 `gen:api` 末尾的 `prettier --write`（`common-api/README.md` §六 已写明）。

## 本决策未覆盖

1. `docs/api/openapi.json` 与**后端代码**是否一致 —— 即 `0040`「未覆盖」第 1 条，仍未覆盖：
   要查它得在流水线里构建并启动一次应用、重新导出、与入库的做 diff。

   （`0037` / `0039` / `0040` 均未表态）。
