# 0050. 租户存在性：一条有四个属主、却一个负责人都没有的规则

- **状态**：已采纳
- **日期**：2026-10-14
- **决策者**：舰长

## 背景

起点是 `0049` 的一条"未覆盖"：那份 ADR 的落点（按租户配默认角色）做完之后，
剩下那句"由**租户管理员**决定"在核的过程中被判定为**本仓还不存在的概念** ——
`auth:tenant:*` 没有租户内隔离，持权者能配所有租户。

顺着那条线去核"到底哪几处能跨租户"，没找到预想中的东西，找到了另一件：
**四个带 `tenant_id` 的域里，有一个域的租户校验是缺的，而另外三个域的注释把这个缺口
写成"有意不同"、追认了三次。**

### 一、四个域都带 `tenant_id`，而 DDL 里没有任何外键

`bw_auth_user` / `bw_auth_role` / `bw_auth_organization` / `bw_auth_user_group`
四个主表都有 `tenant_id BIGINT NOT NULL COMMENT '所属租户主键'`，
而 `V3__create_bw_auth_tables.sql` 里**零 `FOREIGN KEY`、零 `CONSTRAINT`**（实测）。
全仓唯一性靠唯一索引，完整性一律归应用层 —— 这是本仓的既定做法
（`0023` "多态表无外键 ⇒ 应用层保证存在性"是同一条）。

也就是说：**"建不出属于不存在租户的行"这件事，库里没有任何东西会替你挡住。**

### 二、"只取不校验"这句话写了三遍，从没被谁负责过

四个域各有一个同名的私有 `resolveTenantId`（语义都是"显式指定则用它，否则取当前登录者的租户"）。
其中三处的 javadoc 里都有一句形状相同的话：

| 文件 | 原文 |
| --- | --- |
| `RoleService` | "与 `UserService.resolveTenantId`（只取不校验）**有意不同**，理由是…" |
| `OrganizationService` | "与 `RoleService.resolveTenantId` 同一条（而与 `UserService` 的『只取不校验』**有意不同**）…" |
| `UserGroupService` | "与 `RoleService.resolveTenantId` 同一条（而那一条与 `UserService` 的『只取不校验』**有意不同**）…" |

三处**都只说了"不同"，没有一处写下"为什么可以不同"**。
并且全仓检索确认：`resolveTenantId` 与"只取不校验"在 `docs/` 下**零命中** ——
这条差异从未出现在任何决策记录里。

用户域那一份的实现是 `private static Long resolveTenantId(Long requested)`：
显式指定时**直接返回**，既不查存在性，也不查别的。`static` 本身是个线索 ——
它是四个副本里唯一不持有 `TenantMapper` 的那个，而"要不要校验"这件事的答案，
恰好就落在"有没有那个依赖"上。

**真实的错法不是笔误，是复制 + 追认。** 四次复制里有一次少了一步；
另外三份的注释把这个缺口解释成了设计，于是**下一个读代码的人会相信它**。
这比一处没写注释的疏漏更难发现：疏漏会在评审时被问，而"有意不同"是一个答案。

### 三、实测：这个缺口能造出什么

在修复前跑 `TenantReferenceApiTest`（把源码 stash 回旧版、用例不动）：

| 用例 | 旧代码 | 说明 |
| --- | --- | --- |
| 用户：指定不存在的租户建号 | **`code: 0`** | **账号被成功建出来了** |
| 用户：列表带不存在的租户 | **`code: 0`** | 返回空列表 |
| 角色 / 组织 / 用户组：同一个 40002 | 40002 | 三个域**本来就在校验** |
| 不传租户 → 落当前租户 | 通过 | 安全默认值没坏 |
| 显式指定一个存在的租户 | 通过 | 跨租户建号没坏 |

建出来的那个账号**永远登不进来**：登录先按 `tenantCode` 找租户，再按
`(tenant_id, username)` 找人 —— 一个不存在的 `tenant_id` 上没有任何 `tenantCode` 能映射到它。
它同时也**永久占着** `uk_bw_auth_user_tenant_username` 那个位置：
同租户内重名建号会被 `40903` 挡住，而挡住它的是一个谁也看不见、谁也删不掉的账号。

这正是 `RoleService` 注释里那句话说的东西 —— "静默不可达的数据，正是本仓尽量不让接口制造的东西"。
**一句话写在角色的注释里，而它描述的那个缺陷长在用户身上。**

### 四、影响面如实说

管理台**不传** `tenantId`：用户 / 角色 / 组织 / 用户组的建号与建表单一律不带这个字段
（`web/` 下 `tenantId` 只出现在 `MeVO` 映射、会话类型与审计演练面板的路径参数里）。
所以这个缺口**不是从界面上点得出来的**，它需要直接调接口 ——
但仍是一个"持有 `auth:user:create` 就能做、且做完全程无提示"的动作，
而 `admin` 持有全部权限。

### 五、顺着同一条线核出的另一处：文档与契约相反

要给四个域补"租户归属"这条约定时，去查 `docs/api/README.md` 的模型表，
发现 `UserGroupSaveRequest` 那一行写着：

> **没有 `tenantId`**（取当前登录者）

而契约里它**有** `tenantId`：

```
UserGroupSaveRequest -> ["groupCode","groupName","tenantId","parentId","category",
                         "isDefault","isEnabled","sortNo","description"]
```

同表里 `ResourceSaveRequest` 的"**没有 `tenantId`**（资源是平台级的）"是**对的**
（实测契约里确实没有）—— 也就是说这两句话长得一样、一句真一句假，
**而它们相邻 13 行、都被读过**。

这条属于同一族的第三种形态：不是"写了没调用"，也不是"注释追认缺口"，
而是**一句话在文档里被"顺口"复制到了它不成立的地方**。
它没有守卫 —— `verify-api-contract.mjs` 核的是**接口清单**
（路径 / 权限 / 计数），**不核字段级的散文**。

修法是把那半句改成事实（并把 `tenantId` 补进字段列表），
同时在权限域引言处**只写一条通用规则**，不逐个模型重复 —— 逐处重复正是它出错的路径。

## 决策

### 1. 存在性判定收进 `TenantService#assertExists`，给它一个属主

```java
@Transactional(readOnly = true)
public void assertExists(Long tenantId) {
    if (tenantMapper.selectById(tenantId) == null) {
        throw AuthResultCode.PARAM_REFERENCE_MISSING.businessException(
                "引用的租户不存在：" + tenantId);
    }
}
```

选 `TenantService` 而不是新建一个工具类：**"租户存不存在"本来就归租户域回答**，
而这个类此前只对"自己"负责（`requireTenant`），从没为"别人引用租户"提供过入口 ——
四个域于是各自伸手指向租户表。现在它们问 `TenantService`。

选**一个方法**而不是"合成一个 `resolve`"：四个域的"取当前登录者租户"那半段
（`AuthContextHolder.currentTenantId()` + `PARAM_INVALID`）语义完全一致，
但**它只有 5 行，且每处都要带一条领域专属的理由**（角色："永远不可能被授予给任何人"；
组织："永远算不出任何范围"；用户组："永远不可能产生权限"）。
把那些理由从各自的域里搬走，代价大于收益 —— 而**这次漂移的地方是"存在性判定"，
不是"取默认值"**，所以只把判定收口。是否连那半段也收，见"未覆盖"。

### 2. 四个域都调它，且**行为一致**

三处内联的检查改成 `tenantService.assertExists(requested)`，
用户域补上同样的一句。三个服务因此**不再注入 `TenantMapper`**（实测它们拿这个映射器
只干这一件事）—— 从"伸手查租户表"变成"问租户域"。

### 3. 与 `requireTenant` 分开，错误码不同且**刻意不合并**

- `requireTenant` 回答"**你要操作的那个**租户在哪" → `40402`（路径主语就是这个租户）；
- `assertExists` 回答"**你引用的那个**外键指向谁" → `40002`（主语是另一个资源，租户只是它的字段）。

合并成一个码，"我请求的租户不存在"与"我传的 `tenantId` 指向不存在的东西"
对调用方长得一模一样 —— 而这两种错要去的修复位置不同。

### 4. **只修存在性，不碰"能不能指定别家租户"**

后者是"授权"问题（指定一个**存在**的租户目前被允许，这是跨租户运营能力的来源），
它需要一个产品语义决定，见"未覆盖"。本轮不替它下结论，也不顺手把它关掉。

### 5. 用例断言的是"四个域给同一个答案"，不只是用户域

只测用户域的话，规则再被复制回去、再漂移一次，症状与这次一模一样。
所以 `TenantReferenceApiTest` 三个域各发一次请求、断言同一个码，
外加两条**正例**（不传 → 落当前租户；显式指定的**存在**租户被尊重）——
补校验最容易的错法是把"跨租户建号"一起挡掉。

### 6. 订正三处注释；旧文不回改

三处"有意不同"改成事实描述，并把领域专属的理由留在原地。
`docs/` 里没有旧文需要订正（这条差异从没进过文档）—— 本轮是**第一次**它被写进文档。

### 7. `docs/api/README.md`：订正一处假话，并把规则收成一条

`UserGroupSaveRequest` 那行的"**没有 `tenantId`**"改成事实（字段列表也补上它）；
权限域引言处新增**一条**「租户归属」通用规则（不传 → 落自己租户；显式传 → 必须存在，否则 `40002`），
并写明它与审计 / 日志域那套口径**刻意不同**。

**不逐个模型重复这条规则** —— 逐处重复正是它出错的那条路径（一处错、十三行外一处对）。

## 后果

**正面**

- `POST /api/auth/users` 不再能造出属于不存在租户的账号；
  `GET /api/auth/users?tenantId=<不存在>` 从"返回空列表"变成 `40002` ——
  空列表把一次输入错误伪装成了一个合法结果。
- "引用了不存在的外键 → 40002"这条规则**只有一个属主**，
  文案与错误码各一份。四个域此前是四份，其中一份漏了。
- 三个服务少了一个 Mapper 依赖。
- 一类缺陷的**成因**被记下来了：这次漂移不是笔误，是"复制 + 用注释追认"。
  这条比这次的具体修复更值得留 —— 它与 `0049` 那条"同一件事两句话写在两份文档里"
  是同一个家族：**信息写得足够多，但从没被放在一起读过。**
- `docs/api/README.md` 里那句与契约相反的话被订正，且"租户归属"从此**只有一条规则、
  写在一处**（权限域引言），不再逐个模型复述。

**负面 / 代价**

- 四个服务各多一个 `TenantService` 依赖，`assertExists` 在写路径上多一次 `SELECT`。
  （建号/建角色本来就是多语句事务，这一读不是主要开销。）
- `resolveTenantId` 仍是四份，仍有"再漂移一次"的空间 —— 只是**判定那一半**不再有。
- `UserService` 的 `resolveTenantId` 从 `static` 变成实例方法。

**后续约束**

- 新加一个带 `tenant_id` 的表时，**存在性校验问 `TenantService`**，不要再内联一份。
  这条写进了 `server/README.md` 的硬规则表。
- 本轮**只收口了判定**，没有收口"取默认值"那半段。若将来要合成一个 `TenantResolver`，
  必须同时决定那三条领域理由搬到哪里 —— 搬走它们才是这次没做的真正成本。

## 未覆盖

- **能不能在接口上指定"别的（存在的）租户"**：可以，且这是**授权**问题不是完整性问题。
  本轮的四个域里，读与写都接受客户端指定的 `tenantId`（不传则落自己租户）。
  要改成"只能操作自己租户"，得先回答**这是平台级管理台还是租户级管理台** ——
  现在两种都像：默认值像租户级，可覆盖像平台级。
  这正是 `0049` 未覆盖 1 的**正题**（"租户管理员"主体 + 租户内数据隔离），
  它需要的不是代码而是产品决定；决定之后再动。
- **审计域 / 日志域**：`0025` / `0026` 已经把这两处改成"租户恒定强制为当前登录者"，
  **不接受客户端传入**。本轮没有动它们，也没有把 auth 配置域往那个口径上靠 ——
  两套口径并存是当前的事实，而它们的差异有据（审计/日志是"读别人留下的记录"，
  auth 配置域是"管理自己的配置"）。
- **`bw_auth_tenant` 自身的接口**：租户的增删改**没有**租户归属概念
  （它操作的对象就是租户本身），因此不在本轮范围内。
- **取默认值那半段的四处复制**：本轮刻意留着，理由见决策 1 与后续约束。
- **软删租户**：`assertExists` 用 `selectById`，软删行同样能查到
  （`bw_auth_tenant` 是否有逻辑删除由框架配置决定，本轮未核）——
  即"引用的租户被软删之后，引用它的新数据仍能被建出来"。这一条本轮**没有验证**，
  也就不在此处断言它成立或不成立。
