# 0030. 组织树、成员归属与数据范围求值的接线：把 `DEPT` 档位从"永远算不出"变成"可精确求值"

- **状态**：已采纳
- **日期**：2026-10-13
- **决策者**：舰长

## 背景

`0025` 的「本决策未覆盖」里留着三句话，它们指向同一个缺口：

- **`DEPT` / `DEPT_AND_CHILD` 的精确求值**；
- **组织管理接口**（`bw_auth_organization` + `bw_auth_rel_org_user`）；
- 「不返回"可见组织 id 集合"这类看似更有用的字段」。

`bw_auth_organization` 与 `bw_auth_rel_org_user` 的**表、实体、Mapper 都已就绪，但全仓零引用** ——
没有 Service、没有 Controller、没有种子。两张表在真实环境里恒为空。

于是 `DEPT` 档位的处境是：枚举认得它、合并规则里有它、`precise` 如实报 `false`，
但它**永远算不出**。这正是本仓最不接受的东西 —— 一个看起来生效、实际不参与判定的开关。
而补它的前提是组织树本身有接口。

一个次要但决定切片边界的观察：**"只读的组织接口"没有价值**。表恒为空 ⇒ 读出来永远是空列表。
所以写入路径与成员归属必须与读取一起交付，否则交付的是一个"能查、查出空"的接口。

## 决策

### 1. 组织树用「物化路径」表达层级，三列派生字段一起维护

`org_level`（根为 `1`）、`code_path`（形如 `/1/5/`，**各级祖先主键加斜杠、不含自身**，根为 `/`）、
`full_name`（形如 `蓝鲸集团/研发部/前端组`）。

三者都是 `parent_id` 与各节点名称的**确定函数**，因此入参里**没有**这三个字段
（`OrganizationSaveRequest` 只接 `parentId` 与 `orgName` 等业务列）。

理由不是"少几个字段"，而是：`DEPT_AND_CHILD` 按 `code_path` 前缀匹配求子树。
让调用方传路径，就会出现"挂在这棵树下、路径却指向另一棵"的节点，
而那种节点的整棵子树会**静默地**算不进任何人的范围。

`manager_name` 同理不入参：只给 `manager_id`，姓名由服务端从用户表取 ——
给两份就必然出现两份不一致，而列表展示用姓名、详情用 id，不一致时两个界面会各说各话。

### 2. `code_path` 前缀匹配同时是"求值口径"与"重写边界"，这是有意的

`enabledSubtreeIds()` 用 `likeRight(code_path, rootPath + rootId + "/")` 求子树；
`rewriteSubtree()` 用同一个前缀定位要重写的后代。
两处共用一个事实是**刻意的**：若它们不一致，数据范围的边界就会与维护的边界脱节。

配套：子树重写**刻意不用一条 SQL**。三方言的字符串函数差别不小
（`SUBSTRING` / `SUBSTR` / 达梦的 `VARCHAR(n CHAR)` 会影响拼接），
而部门树是人手维护的量级（几十到几百个节点），逐行 update 更可读也更安全。

### 3. 移动节点是独立接口 + 独立审计动作，且修改路径**拒绝**层级变更

- 接口：`PUT /api/auth/orgs/{id}/parent`（传空 body = 提升为顶级）；
- 动作：`auth.org.move`。

理由：移动会重写整棵子树的三列，而 `DEPT_AND_CHILD` 按路径求值 ⇒
**子树上每个人的可见范围同时改变**，表面只是"换了个上级部门"。
混进一次普通字段更新里，事后追问"这个部门的可见范围为什么变了"就再也查不出来。

配套：`OrganizationSaveRequest.parentId` 在修改路径上**显式拒绝（`40001`）而不是静默忽略**，
只在"值非空且与原值不同"时拒绝；不传 / 传 `null` 都表示"这次不改层级"。
静默忽略的表现是"保存成功、层级没变"，调用方会以为改好了。

> **这与用户组 `parentId`（"接受但不产生权限"）的判断相反** ——
> 因为组织路径变了会真的改变数据范围。

### 4. 移动必须同时做完五件事，其中一件是本轮抓出来的缺陷

① 拒绝挂到自己或自己的后代下（`40913`，否则成一棵转不出来的环）；
② 重写自身与整棵子树的三列；③ 重算新父级的 `hasChild`；
④ 重算**原**父级的 `hasChild`；⑤ **`parent_id` 本身要落库**。

**⑤ 是一个真实缺陷，不是预防性措施。** `OrganizationService.updateColumns` 原本只写业务列，
不含 `parent_id`，于是移动之后留下的是一个**半更新状态**：

- `code_path` / `org_level` / `full_name` 已指向新父级 ⇒ **数据范围已经搬家**；
- `parent_id` 还在旧父级下 ⇒ **树接口按它拼树，节点显示在原地**。

两者都不报错。界面上看到的层级与真实的数据范围各说各话。

它不是推演出来的：端到端用例断言"移动后**原父级的 `hasChild` 应当归 `0`"，
而 `hasChild` 正是按 `parent_id` 数出来的 —— 它留在了 `1`。

同一个坑还影响**第二条路径**：`create` 的"同码复活"分支也调 `updateColumns`，
所以一个被删除的组织被重建时，它的新父级同样落不下去。
顺带说明为什么必须用显式 `set` 而不是 `updateById`：复活时"从某个部门下"变成顶级
需要写 `null`，而 `NOT_NULL` 字段策略写不了 `null`。

### 5. 主岗的三条硬规则

先记一个事实：`bw_auth_rel_org_user` **连 `(organization_id, user_id)` 唯一索引都没有**。
建表脚本只建了 `organization_id` 与 `user_id` 两个普通索引。
后果有两个：**同一人在同一组织下的重复归属不会撞键**；
**"每人至多一个主岗"完全靠服务层**，没有数据库约束兜底。

三条规则：

1. **每人每租户至多一个主岗。** `applyPrimaryPosition` 的写法是"先降级别处、再设置自己"，
   而不是"先查有没有、有就报错"—— 后者会让"把主岗从 A 搬到 B"这个再正常不过的动作需要两步，
   而中途失败会留下一个没有主岗的人。
   没有唯一约束，这条 update 就是全部保证；漏了它的症状是"一个人有两个主岗、
   能看到的数据比预期多"，**不报错**。
2. **不静默改主岗。** 不传 `isPrimaryPosition` 时：此人当前没有主岗 → 自动设为主岗；
   已有主岗 → **保持不变**。
   自动设第一条的理由是：没有主岗的人 `DEPT` 算不出范围、会被兜底成"仅本人"，
   而管理员刚把一个人挂进部门时期望看到的是"他在这个部门"。
   不搬已存在的主岗的理由是：那会**悄悄改变这个人的数据范围**，
   而他本人的部门归属看起来毫无变化。
3. **时态参与求值。** `effective_from` / `effective_to` 过期的归属不算数
   （与角色成员、用户组成员是同一条）。这是「判定侧静默缺陷」的同类：
   一段已经结束的归属在成员列表里看起来完全正常。

设主岗要求**先有归属**，否则返回 `40410` —— 主岗是那段归属的一个属性，
关系不存在时它无处安放，不该悄悄新建一条。

### 6. 成员挂在组织下（`/orgs/{id}/members`），不单开平级资源

与角色、用户组是同一条判断：归属是组织的**内部边**，没有"没有组织的组织归属"。
URL 本身就说明了"改的是哪个组织的成员"，同时天然带上归属校验。

与用户组那处有一处**形状上的差别**：路径里**没有 `memberType`**。
`bw_auth_rel_org_user` 只装用户，层级由 `parent_id` 表达 ——
没有多态列就不要在路径上假装有（多一个恒为 `USER` 的必填字段，只会让人猜它还能是什么）。

### 7. `DataScope.precise` 改名 `selfSufficient`，并新增 `needsOrgContext()`

旧名把两件事混成一件：**"这一档自足"**（一个说"整个租户"、一个说"只有我"）
与**"这一档最终能被精确求值"**。
后者是**合并阶段**才能回答的问题 —— 还要看运行时是否真有有效主岗 ——
不是枚举自己能回答的。

于是枚举上只留 `selfSufficient()`（只有 `ALL` 与 `SELF` 为 `true`），
另加 `needsOrgContext()`（`DEPT` 与 `DEPT_AND_CHILD`）。
`UserDataScopeVO` 的对外字段名仍是 `precise`，语义按第 8 条收窄。

### 8. `DEPT` 系列：有有效主岗才精确，否则往窄兜底（结论不变）

`DataScopeService.applyOrgScope`：

| 情形 | `precise` | 下发的字段 |
| ---- | --------- | ---------- |
| 主岗可解析且组织未停用 | `true` | `primaryOrgId` / `primaryOrgName` / `primaryOrgFullName` / `visibleOrgIds` |
| 没有归属 / 归属已过期 / 主岗组织已停用 | `false` | 带一句说明的 `note`，不返回组织集合 |

`visibleOrgIds` 的口径：`DEPT` 只有主岗那一个组织；`DEPT_AND_CHILD` 是**启用的**子树
（停用的后代被排除 —— 否则"停用这个部门"这个动作在它仍有下级时毫无效果，
而那正是调用方最可能期待的相反结果）。

**往窄兜底这一条一个字都没有改**（`0025` 第 7 条）：算不出就往"仅本人"收。
反过来的选择（算不出就当 `ALL`）会让"配了一个还没实现的范围"变成一次静默越权。

### 9. 同时把「可见组织 id 集合」返回出来 —— **推翻 `0025` 第 9 条**

`0025` 第 9 条明确写着"不返回这类看似更有用的字段"。
**触发条件到达了，因此推翻**，并把理由的变化记下来：

- 原先的理由：本期没有任何一处查询会消费它，返回一个恒为空的集合比不返回更糟 ——
  调用方会以为"这个人的可见组织就是空的"，而真实原因是"这个字段还没实现"；
- 现在的理由：组织树与成员归属落地后它**不再恒为空**，而它的消费方**就是反查接口本身**。
  那个接口的全部意义是回答"这个人的范围具体是哪些组织"，
  从审计面板点进来看到"本部门及下级（研发部 → 前端组）"才是可用的答案。

同时要如实说清它**还不是过滤条件的输入**（见第 10 条）：
`precise = true` 现在的含义是"这一档已经能被翻译成一组组织"，**不等于**"已经有查询按它过滤了"。

### 10. 审计可见性：**理由变了、结论没变**（刻意不做）

`currentRequestSelfOnly()` 仍然只有一处实现：
`return !resolveForCurrent().isAllData();` —— **只在 `ALL` 时返回 `false`**。

- **旧理由**："`DEPT` 算不出精确范围"；
- **新理由**：把 `DEPT` 接进审计过滤是一次**静默的放宽**，
  而 `bw_audit_log` **没有组织维度**，只能退化成 `operator_id IN (该部门的用户)`；
  审计表保留期很长 ⇒ 等于把历史上所有同部门人员都开放出去；
  而当前**没有任何一方要求**这件事。

这是一次**刻意的"不做"**，写在这里是为了防止后来者看到"`DEPT` 现在算得出了"
就顺手把它接上 —— 那会是一次没人评审过的权限放宽。

`0025` 的"详情跨租户 `404` 而不是 `403`"、"租户条件恒定加上"两条也一并保持。

### 11. 种子：种一棵最小组织树，并**复用服务而不是重抄派生规则**

`DefaultAdminSeeder` 种「总部 > 研发部 > 前端组」，并把 `admin` 挂在总部、
`auditor` 挂在前端组。

两个刻意的做法：

- `ensureOrg` 调 `OrganizationService.create`，**不自己拼 `orgLevel` / `codePath` / `fullName`** ——
  它们是派生列，抄第二份不会有任何测试盯着；
- `ensureMembership` 调 `bindMember` 且**不传 `isPrimaryPosition`** ⇒
  首次启动自然形成"admin 主岗在总部、auditor 主岗在前端组"，
  而重启**不会把运维改过的主岗改回来**（第 5 条第 2 点）。

### 12. 删除两道守卫，错误码分开；没有级联

- 仍有下级组织 → `40913`；
- 仍有成员归属 → `40919`（新码）。

两个原因不合并成一个码：处置完全不同（先删下级 / 先移成员），
合成一个只会让界面给出一句"删不掉"。

`40919` 与用户组相反的地方写在错误码注释里：**组织不持有角色**，故不予级联清除。
两条守卫对应两件"删掉之后没人会提示你"的事 ——
删一棵子树会连带影响所有后代；删一个有人挂着的部门会让一批人的 `DEPT` 档位**静默退回仅本人**。

**没有级联删除，也不提供"连人一起删"的选项**（与 `UserGroupService.delete` 同一条原则）。

### 13. `org_name` 不做唯一性校验

表上只有 `uk_bw_auth_org_tenant_code`。
不同上级下同名是合理的（两个分公司各有一个"综合部"），因此服务层不校验，
`AuthResultCode.ORG_NAME_EXISTS(40909)` 保持为**当前未使用的预留码**
（与 `ROLE_NAME_EXISTS` / `USER_GROUP_NAME_EXISTS` 同状态）。

### 14. 编码曾被软删组织占用时**复活原记录**

与资源、角色、用户组三处同一个坑、同一个修法：
唯一键 `uk_bw_auth_org_tenant_code` **不含 `deleted`** ⇒ 软删的行仍然占着这个编码，
而 MP 的每次查询自动追加 `deleted = 0` 看不见它 ⇒"判重通过 → insert → 撞键"。

修法是认出软删行并复活它。**复活出来的是空部门**：
`clearMembersOf` 一并清空该组织名下的用户归属。
不清的话，一个已被删除的部门名下的历史归属会在它被重建时突然复活，
那些人会静默重获一个自己都不知道的 `DEPT` 范围。

### 15. 权限码 4 个 / 审计动作 7 个 / 错误码 2 个

- **权限码**：`auth:org:read` / `create` / `update` / `delete`，登记进 `AuthPermissions.ALL`
  （全仓唯一登记处）。权限项总数 **23 → 27**；
- **资源标识**：`auth:org`（放在 `auth:user` 之后）—— 它是**数据权限的坐标系**；
- **审计动作**：`auth.org.create|update|delete|move|grant_member|revoke_member|set_primary_position`；
- **错误码**：`ORG_MEMBER_NOT_FOUND(40410)`、`ORG_IN_USE(40919)`。

权限码只分到"资源的增删改查"这一级：移动节点**没有**独立权限码（它复用 `org:update`），
但有自己的审计动作；成员与主岗同理共用一个权限码，而**设主岗**因为"直接改数据范围"
有独立动作。**权限管"能不能做"，动作管"做了什么"** —— 两者不是一回事。

## 后果

**正面**

- `DEPT` / `DEPT_AND_CHILD` 从"永远算不出"变成**可精确求值**，唯一出口是
  `GET /api/auth/users/{id}/data-scope`；`0025` 的最后一处"只存不用"被清掉；
- 两张恒空的表开始有数据，组织树有完整的管理面（后端）；
- 修掉一处**半更新状态**（`parent_id` 未落库），它同时影响移动与"同码复活"两条路径；
- 新增 13 条端到端用例（后端总用例 **161 → 174**），其中"原父级 `hasChild` 归 0"
  与"复活出来的是空部门"两条直接对应上面两个缺陷；
- 契约 **35 → 43 路径**、**55 → 67 接口**、**85 → 100 模型**（前端类型由
  `pnpm --filter common-api gen:api` 重生成，零手写）。

**负面 / 代价**

- **成员视图没有下沉。** 这是第三份同形的成员 VO（前两份是角色成员、用户组成员），
  但本轮的第三份恰好带来一个**不共有**的字段 —— `isPrimaryPosition`。
  真要下沉，公共部分应当由三个候选的交集定形，而"公共部分"此刻并不存在。
  `0024` 里"第三处成员关系出现时下沉"的触发条件因此只满足了一半，
  下调为**"第四个成员关系，或三者字段集第一次出现真包含关系"**。
  代价是 `OrgMemberVO` 与 `UserGroupMemberVO` 逐字近似，冗余是接受的。
- `OrganizationSaveRequest.orgCode` 在**修改路径**上仍是 `@NotBlank`
  （与资源、角色同形状）：调用方要把它原样带回来，少传会被 DTO 挡成 `40000`。
  这是既有约定，本轮没有改 —— 但它确实是一处"要求一个不被读的字段"。
- `precise` 的**对外字段名**保留、**枚举方法名**改了（`selfSufficient`），
  两者暂时不同名。这是有意的：契约字段改名会影响前端，而枚举方法是内部语义。
- 组织与数据范围之间多了一条**长链**：
  改主岗 / 移动节点 → 三个派生列 → `visibleOrgIds`。
  链上任何一环静默失效，表现都是"范围不对但不报错"。

**后续约束**

- **凡新增影响权限的开关，都要问一句"判定里读它了吗"**；
- 移动节点与设主岗必须保留为**独立接口 + 独立审计动作**，不得并入普通更新；
- 派生列（`org_level` / `code_path` / `full_name`）**永远由服务端维护**，
  不接受入参，新增写入路径时必须复用 `rewriteSubtree` / `updateDerivedColumns`；
- 往窄兜底的方向不得反转。

## 本决策未覆盖

- **前端管理页**（组织树 + 成员 + 主岗）。本轮只交付"后端全量 + 数据范围接线"，
  前端管理页留到下一轮 —— 现在起后端接口可被 `curl` 完整验证；
- **`CUSTOM` 的 `filter_json` 表达式解析**（`0025` 的遗留，仍然只存不用）；
- **把 `DEPT` 接进审计可见性** —— 刻意的"不做"，见第 10 条；
- **业务数据的数据权限**：本仓仍无业务数据表 ⇒ 过滤业务数据**无落点**（`0025` 的遗留）；
- **`org_type` / `relation_type` / `position_name` 是"存但不用"的描述性字段。**
  与用户组拒绝 `filter_json` 不矛盾：那些被拒绝是因为**看起来会改变行为**，
  而这三个是一句描述、界面也不承诺它会做什么。等真有地方按类型分叉
  （例如菜单可见粒度），`org_type` 才该被收窄成枚举；
- **`listByTraceId` 的条数上限**（上月遗留）。

## 发现但未处理（供后续决策）

1. **`bw_auth_rel_org_user` 没有 `(organization_id, user_id)` 唯一索引**，
   服务层的"先查后写"挡不住并发，残留的重复行会让一段已移除的历史归属复活。
   补索引要写新的迁移脚本（`0009` 禁改已执行脚本），且三方言各一份。
   在那之前，`revokeRedundantRows` 是缓解手段而不是修复。
2. **`OrganizationService.page` 的 `keyword` 会 `like` 三列**
   （`org_code` / `org_name` / `full_name`），其中两列没有前缀索引。
   部门树是人手维护量级，暂不构成问题；规模上来后要评估。
3. **组织树一次查全量、在内存里拼树，不做递归查询。**
   递归 CTE 在三方言里的写法差别不小（达梦要用 `CONNECT BY` 或 `WITH RECURSIVE`），
   不值得为几百行数据引入一个跨方言的语法分支。
   孤儿节点（父不在结果集里）会被当成根返回，而不是被过滤掉 ——
   把孤儿过滤掉等于让整棵子树在界面上凭空消失。
4. **`bw_auth_rel_org_user` 的时间窗只被"求值"读，没有被"展示"读。**
   成员列表带 `effectiveNow`，但它不区分"尚未生效"与"已过期"。
