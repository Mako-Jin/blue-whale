# 0043. 用户自助改密

- **状态**：已采纳
- **日期**：2026-10-13
- **决策者**：舰长

## 背景

`0020`「本切片未覆盖」第 1 条就是这件事：

> **用户自助改密接口**（含"强制改密"引导）。`must_change_password` 与 `password_expires_at`
> 两列已就位、登录时也已校验，但缺"改密页面 / 接口"这一段。

同一次回访还留下一条**后续约束**，它才是本决策真正要接住的东西：

> **任何"设置口令"的入口**（建号 / 重置 / 将来的自助改密）都必须依次经过
> `PasswordPolicy.violations(...)`、防重用检查、历史写入三件事。只做其中一件都是漏洞。

### 那条约束在写下的时候还不知道自己兑现不了

写下它的时候，三件事是 `UserService` 的**私有方法**。这意味着第二个入口出现时，
唯一可行的做法是复制粘贴 —— 而**三份复制出来的实现会在某一次修改里只改到其中两份**
（改的人当然会改自己正在写的那一个）。一条"必须都经过它"的约束，如果实现本身不可复用，
它就只是一句愿望。

本决策要接住的主要不是"新增一个接口"，而是**先让那条约束可兑现**。

### 顺带核出来的一处"文档与代码不符"

`0020` 说那两列"**登录时也已校验**"。实测只有一半：

| 列 | 实际 |
| --- | --- |
| `password_expires_at` | `AuthService#login` 确实校验了（第 109 行，`40111 PASSWORD_EXPIRED`） |
| `must_change_password` | **全仓零逻辑引用** —— 只在 `UserEntity` 声明与三方言 SQL 里出现 |

它和 `0020` 背景里那个"登录锁定从来没生效过"属于同一类：**字段齐全、注释齐全、什么都不发生**。
区别是这一次没有 bug，只是**没有消费者** —— 连置位的地方（管理员重置）都还没写。
一个既没有写入方、也没有读取方的列，在评审里看不出任何问题。

## 决策

### 1. 把三件事抽成 `PasswordChanger`（本决策最重的一处）

新增 `auth/authentication/PasswordChanger`，承载强度校验、防重用、历史留痕与裁剪。
`UserService`（管理员重置、建号）与 `AuthService`（自助改密）都只是它的调用方。

- **它替调用方落库**，因为它**已经在写库了**（历史那一条是 insert）。
  "写历史"与"写新口令"必须在同一次提交里发生，否则会出现"历史记了、口令没换"
  （下次改密会被一个从未用过的口令挡住）或"口令换了、历史没记"（防重用从这一轮起失效）。
  既然写库躲不掉，就让两者在同一处落下，调用方少一个可以忘的步骤。
- **`assignNewPassword` 单独公开**（只改内存、不落库）：建号走 insert、改密走 update，
  但"设口令要同时更新哪几列"只该有一个答案。少写算法标识会让 `PasswordHasher`
  无法判断该用哪套参数校验，少写更新时刻会让"口令多久没换"这类判断静默失准 ——
  两处都不会报错，这正是它们值得被收在一处的原因。
- **`assertStrength` 也公开**：建号只用到三件事里的第一件（那一刻没有被替换下来的口令、
  也没有可重用的对象）。把这一点摆成一个公开方法，而不是让建号自己再写一份长度与字符类别的判断 ——
  那正是 `0020` 决策 2 已经为此删掉过 DTO 上 `@Size(min = 8)` 的那种"同一个规则两处实现"。

**记历史必须在改字段之前。** `recordHistory` 读的是实体当前的 `passwordAlgorithm`：
先 `setPasswordAlgorithm(...)` 再记，历史里那条就会标着**新口令的算法**而存着旧口令的哈希 ——
与 `PasswordHasher` 的"算法随哈希存储"约定正好相反，且不报任何错。原实现（`UserService`）的顺序是对的，
已随重构原样保持。

### 2. 新接口 `PUT /api/auth/password`

请求体 `{ oldPassword, newPassword }`；**只要求已认证，不要求任何权限码**。

用 `PUT` 而不是 `POST`：口令是当前用户这个"资源"的一个属性，换掉它是幂等的整体替换
（重复提交同一个新口令，第二次被防重用挡下 `40914`，而不是又改一次）。
这与 `POST /api/auth/users/{id}/password` 不同 —— 那条是"发起一次重置"，每次尝试都是一次新操作。

新口令的形态由服务端策略判定（`40003`），DTO 上不写长度下限 —— 与 `0020` 决策 2 一致。

### 3. 旧口令必填 —— 它是本接口唯一能证明"操作者是本人"的手段

本接口不挂权限码（能登录就该能改自己的口令，否则用户会被一个自己都进不去的口令锁在门外），
所以**不能**像管理员重置那样靠 `auth:user:update` 把关。不验旧口令的后果很具体：
一次访问令牌泄露就等于一次账号接管 —— 攻击者进来改掉口令，主人随即被关在门外，
且连刷新令牌都被清空。

**旧口令错误沿用 `40101`**（凭据不对），只把文案换成"当前口令不正确"。
不新开错误码是因为这里是**同一件事**（口令不匹配）；前端本来就知道自己在调哪个接口，
多开一个码只会让"两个码表达同一件事"多一处。这与 `40408`/`40409`/`40410`
"不复用码值"的取舍并不矛盾 —— 那三处分属**三个不同的聚合**，而这里是同一件事。

**旧口令错误必须计数**（走 `LoginAttemptRecorder`）。它是一个**新的口令猜测入口**：
拿着令牌的人可以反复猜旧口令，猜中即可改密。不计数的话，"改密接口能绕过登录锁定去猜口令"
就成了一个现成的后门。代价是本人记错旧口令、连试几次也会被锁定 5 分钟 ——
与登录路径的后果一致；而"改密接口不受锁定约束"是更坏的一种不一致。

### 4. 成功后撤销**该用户全部**刷新令牌（含当前会话）

改密最常见的动机就是"我怀疑口令泄露了"。此时若留着别人已经换到手的刷新令牌，
他下一次刷新就会拿到一套全新的令牌对，改密便成了一次无害的仪式。

做不到"只撤销别人的"是因为**认不出当前用的是哪一个** —— 本请求带的是访问令牌，
里面没有刷新令牌的 jti。代价是改完密在访问令牌到期后需要重新登录，而那更像特征而不是缺陷：
重新登录一次，正好验证新口令确实能用。

**访问令牌仍有最长一个令牌有效期（默认 2 小时）的残留**，这是无状态访问令牌的固有代价，
与 `logout` 同源。但这里的自愈是确定的：攻击者即使握着访问令牌也**改不了密**（那需要旧口令），
且 2 小时后刷新失败、必然出局。

**撤销放在最后一步**：上面任何一步失败都不该动会话 —— 尤其"新口令不合规"时，
用户还需要用**当前这个会话**重新填一次。把它踢出去，等于让一次输错变成一次登出。

### 5. 把 `mustChangePassword` 接上 —— 只标记，不拦截

- **管理员重置**置 1（`0020` 原有行为，"下次登录必须改"）；
- **本人改密**清 0（改密这件事本人刚做完，不该再被要求改）；
- **`MeVO` 暴露它**，前端据此把用户引导到改密页。这是这一列第一个真正的读取方。

**服务端刻意不因此拦截登录。** 两条路都不通：直接拒绝登录会形成**死锁**（进不去就没法改密，
而改密接口本身要求已认证）；只发"受限令牌"要为此引入一套令牌能力分级 ——
为一个提示付出的是权限模型的复杂度。所以它是一条**约定**（`ui:` 那类"布局语义"的近亲）：
服务端给事实，客户端做引导。

**`UserVO` 也补上这一列**（顺带修掉 `0020` 自己那条判据没兑现的地方）：
"运营在界面上需要据此做决定的状态（锁没锁、锁几次、为什么锁）就必须进 `UserVO`" ——
管理员重置了某人的口令之后，"他改了没有"正是他最关心的下一件事。

## 后果

**正面**

- **`0020` 那条后续约束第一次可兑现**：第三个"设置口令"的入口（将来的忘记口令 / 强制过期改密）
  出现时，它只需注入 `PasswordChanger`，而不是去复制三个私有方法。
- 自助改密把"改口令"这件事从**管理员代劳**变成**用户可自助**，同时不牺牲前者的审计留痕。
- `mustChangePassword` 第一次有写入方、有读取方、也有清除方 —— 一个完整的小机制。
- **口令这条链路上四段都有机器兜底**：强度 / 防重用 / 历史由 `PasswordChanger` 一处实现，
  由 `PasswordChangerTest` 与 `ChangePasswordApiTest` 分别从"三件事本身"与"接线"两层钉住。

**负面 / 代价**

- 每次失败登录多一个短事务（`REQUIRES_NEW` 要新开连接）—— 与 `0020` 的代价同源，此处多一个入口。
- 改完密需要重新登录（访问令牌到期后）。这是决策 4 的直接代价。
- `/api/auth/me` 多一次主键查询（认证上下文里没有"账号状态"这类字段，只能回查）。

**它不是空转**（两层分开证明）

- `PasswordChangerTest` 六个用例覆盖三件事的顺序与原子性，以及**裁剪的边界**。
  其中"改回最初那个口令应当成功"这一条是**设计时最有用的一句**：只断言"历史条数 = 保留数"
  时，`keep` 次改密就已经让条数恰好等于保留数、**一次裁剪都没发生**，用例照样绿 ——
  而"最初那个已被挤出窗口"才真正证明窗口滑动过。
- `ChangePasswordApiTest` 七个用例覆盖接线：旧口令错 → `40101` **且失败计数真的落库**
  （与 `0020` 同一个理由：不加 `@Transactional` 才测得出"失败记录的存活"）、弱新口令 → `40003`
  且**旧口令仍可用**（一次输错不该变成一次登出）、复用 → `40914`、成功后旧口令作废 + 新口令可用
  + 旧刷新令牌 `40106`、`mustChangePassword` 被清 0、无令牌 → `40104`、**审计记了
  `auth.user.change_password`**（与 `auth.user.reset_password` 分开）。

**新增审计动作 `auth.user.change_password`，与 `auth.user.reset_password` 分开。**
登录 / 登出 / 刷新都不记审计，而这条记 —— 判据是**事后要不要问**而不是"接口重不重要"：
登录是高频动作，逐条记会把审计表灌满（那是应用日志与风控的活）；
凭据变更是低频、高重的事件，"这个口令什么时候被换掉的"一条记录就能定住整条安全时间线。

## 本决策未覆盖

- **前端的改密页与"强制改密"引导**。本轮只做后端切片，接口可被 `curl` 完整验证
  （与 `0030` 组织树那一批的处理方式一致）。`MeVO.mustChangePassword` 已经就位，
  前端接上时不需要再动后端。
- **"忘记口令"**。它需要一条不依赖登录态的凭证通道（邮件 / 短信），
  与本决策的"已验证本人"是两种不同的信任来源，不能复用本接口。
- **`mustChangePassword = 1` 时的服务端强拦**。刻意不做（决策 5 的两条理由），
  但要知道这是一条**约定而非强制**：一个绕过前端的客户端可以在未改密的情况下继续调其它接口。
  若将来需要强拦，前置条件是先有一条"不需要当前会话即可改密"的路径，否则会死锁。
- `0020` 未覆盖的其余项原样保留：**弱口令字典** · **验证码与 MFA 的实际校验** ·
  **口令过期策略的触发与引导** · **租户级差异化策略**。
