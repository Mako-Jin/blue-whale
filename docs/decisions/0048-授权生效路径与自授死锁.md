# 0048. 授权生效路径与"给自己授权"的闭合路径

- **状态**：已采纳
- **日期**：2026-10-14
- **决策者**：舰长

## 背景

`0031`「发现但未处理」第 2 条记着一句话：

> **审计员的菜单码写在种子常量里，不是"默认策略"** —— 新租户 / 新账号一概**没有**任何菜单码，
> 界面表现为"没有可进入的模块"。这是刻意的（默认不可见优于默认可见），
> 但意味着"新建一个可用账号"需要显式授权菜单，管理面目前只能逐条勾选。

那一句把后果写在**"谁来授权"**上。这一轮查的是**授权之后**—— 而那一侧有两个缺口，
一个在界面上，另一个在"闭合的路径"上。

### 一、两处空状态只说了"缺什么"

改前原文：

```tsx
// platform-portal/src/pages/Home/index.tsx
当前身份没有可进入的应用。请让管理员给这个账号授予对应的菜单码（ui:*:view）。

// platform-admin/src/App.tsx
当前身份没有可进入的模块（需要 ui:admin_*:view 之一的菜单码）。
```

两句都说对了缺哪个码，但**没说去哪补**，也**没说补完怎么让它生效**。
后一件更隐蔽，因为它不是"少写一句"—— 它涉及一条真实的链路：

权限集合的来路只有两条，**登录**与**刷新令牌**。`AuthService#issueTokens` 是两者共用的出口，
`LoginVO` 的类注释把这件事写明了（连 `mustChangePassword` 为什么也得跟着下发都解释了）；
`platform-portal/src/auth/index.ts` 里那句"权限不在访问令牌里（`JwtCodec` 的载荷只有用户与租户标识），
所以仅凭内存里的令牌无法知道我是谁、我有哪些权限"说的是同一件事。

于是"管理员授好了"与"你这里能看见了"之间隔着**一次会话更新**，
而当时的界面上**没有任何东西能让它提前发生**。用户能想到的两条路都很难受：
反复刷新页面（其实管用，但没人告诉他），或者重新登录一遍（代价更大，而他不知道更小的那条）。

### 二、让权限当场更新的那条路，代码在、没有人走

`AuthChannel.reload()` —— 声明就是为这件事写的：

> `/** 用现有访问令牌重新拉取身份与权限（后台改了权限之后刷新用） */`

实现在同文件的 `createAuthChannel` 里，三行：打 `/me`、`toSessionUser`、`session.updateUser`。
`session.updateUser` 内部会 `commit()`，于是订阅者（`usePermissions`）当场拿到新集合。

**它一个调用方都没有。** `grep -rn "\.reload(" --include=*.ts --include=*.tsx web/`
只命中声明与实现本身，真机脚本里也没有。

这和本仓近来反复核出的那一族是同源缺陷，但形状不同，值得单独记一次：

| 编号 | 形状 | 表现 |
| --- | --- | --- |
| `0045` | **零写入方** | `40111` 这个码从来不可能出现，因为没人写它 |
| `0046` | **位置错了** | "撤销"只写在两个调用方里的一个 |
| `0047` | **没有名字** | 能力在、分支在，但没有任何一处写着它的意图 |
| `0048` | **没有入口** | 有名字、有实现、有文档、有类型 —— **就是没人调** |

"没有入口"比前三种更难被测试发现：**它不是死代码**（类型检查不会报，它是个公开成员），
它只是**永远不会被执行**。一个能力既不能被界面引用、也不能被脚本点，于是它是否存在过
对外没有区别 —— 直到有人需要一个"让权限立刻生效"的动作，才会再去写一遍。

### 三、"给自己授权"是一条闭合路径

这一条比前两条硬，而且它不是本轮的缺口，是 `0031` 决策 1 的直接推论被推到尽头的样子：

> **菜单码是布局，读权限是安全边界。**

授菜单码的动作在「权限管理后台」里的「角色」页（资源授权 + 挂成员）。而**进「权限管理后台」
本身需要菜单码**（`ui:admin:view`）或其内部标签页的码（`ui:admin_*:view`）。
于是一个没有任何 `ui:admin_*` 的账号，**无论他持有多少读写权限**，都无法给自己补上菜单码 ——
他连那个标签页都渲染不出来。

```text
需要 ui:admin_role:view 才看得到「角色」标签页
        ↑                              |
        |                              ↓
   在「角色」标签页里给角色授菜单码 ←──┘    （闭合）
```

代价落在"首次可用性"上：它只能由**种子账号**或**库侧**提供（`0031` 决策里那句"审计员的菜单码
写在种子常量里"正是这个安排，`0029` 的种子开关是它的入口）。这不是要改的事 ——
要改的是**别让用户以为这是他自己能解决的事**，否则他会反复刷新、怀疑应用坏了，
而真正该做的是找一个已经持有 `ui:admin_*` 的人。

### 四、顺带核出的一处前端陷阱（与本轮改动直接相关）

JSX 会把**跨行的文本按空格拼起来**，而 prettier（`web/.prettierrc` 的 `printWidth: 100`）
会重排超宽的行。两者叠加的结果是：一句中文里会凭空多出一个空格。

这不是理论问题 —— 本轮的第一版就写出来了，prettier 把一行折成三行之后渲染成：

```text
只能由另一个 已持有 ui:admin_* 的账号来授 （在角色 页给该角色做…
```

`内部`、`来授 （`、`角色 页` 三处都是换行处被塞进去的空格。它不报错、测试也不会失败
（`textContent` 里仍然是那几个关键词），只有人眼能看出来 —— 而这恰好是本仓
"活文档与界面文案都按显示形态评审"那套习惯要拦住的东西。

## 决策

### 1. 「重新检查权限」放在基座顶栏，不放子应用

落点判据与 `0044` 的改密入口**完全相同**：它是会话级动作、**不依赖任何菜单码**，
而**最需要它的恰好是一个菜单码都没有的账号**。

放进子应用还有第二重问题，而且这一重是硬约束：子应用被基座加载时权限由基座下发，
且它**不得自调 `/api/auth/me`**（`0018` 第 3 条）。那时即便点了按钮、拿到了新数据，
子应用读的仍是基座下发的全局状态 —— **改了也不生效，是个假开关**。

### 2. 它是一个按钮，不是自动重取

自动重取要在每次渲染空状态时多发一次请求，而它多数时候得到的答案是"还是没有"，
却要用户为这一次往返等上一拍。这件事的发起者是用户（有人刚告诉他"授好了"），
反馈也该由他点出来才出现。

### 3. "没有变化"必须说出来

三种结果对应三种不同的下一步，所以分开表达：

| 结果 | 界面上那句话 | 用户该做什么 |
| --- | --- | --- |
| 有变化 | `权限已更新：新增 N 项`（或"移除 N 项"） | 什么都不用做，入口已经在了 |
| **没有变化** | `权限没有变化 —— 请确认管理员授的是当前这个账号` | 去找管理员核对**对象** |
| 失败 | 服务端给的原因 | 再点一次 |

第二种是这一条的重点。不说的话，界面毫无动静与"点了没生效"在用户眼里长得**一模一样**，
于是他会重复点、或者去走那条更贵的路（重新登录）—— 而真实原因往往是管理员授错了账号，
那件事只有这句话能指出来。

### 4. 一次失败不结束会话，按钮恢复可点

`reload()` 走的是已鉴权请求，失败可能是网络、超时、或服务端 5xx。
**一次查询失败不是"凭据已失效"的证据** —— 按 `0045` 定下的那条判据（只把服务端明确拒绝
当作会话失效的证据），这里只报错、保留会话、把按钮放回可点。
顺手也把 `:disabled` 的样式补上了：请求期间禁用它（防连点），
而原先 `&__action` 只有 `:hover`，禁用态看起来仍是个能点的按钮 —— 那看起来像坏了。

### 5. `reload()` 从此有且只有这一个调用方，它必须留在基座

那条"三行实现、零调用方"的能力，唯一合理的触发点就是这里。因此它**不向子应用开放** ——
不是"暂时不给"，而是**给了就必然错**（见决策 1 的第二重问题）。
`common-api/README.md` 里记下它的调用方，免得下一个人再次把它当成"没人用的东西"。

### 6. 两处空状态说满三件事

**缺什么 · 到哪补 · 补完怎么生效**，缺一件它就只是一句"你没有权限"：

```text
当前身份没有可进入的应用。菜单码（ui:*:view）决定入口出不出现。
它由管理员在「权限管理后台」里授：先到角色页给某个角色做「资源授权」。
勾上对应的菜单码之后，在同一个角色里把当前账号挂为成员。
授完回到本页，在顶栏点「重新检查权限」即可，不必重新登录。
若提示「权限没有变化」，请让管理员核对授的是不是当前这个账号。
```

路径写成「应用 → 标签页 → 动作」而不是接口路径：读这句话的人是一个刚登进来、
**看不到任何入口**的人，他能做的只有照着界面点。

### 7. 管理台的空状态要如实说出"自己授不了"

`platform-admin` 那句说的是**这件事为什么自己解决不了**（背景第三节的闭合路径）：
只能由**另一个**已持有 `ui:admin_*` 的账号来授。不说清这一点，用户只会反复刷新。

它的生效方式只说**"刷新本页"**，不说"回门户顶栏点重新检查权限" ——
本应用**可以独立运行**（`0018` 第 8 条），那时没有门户也没有顶栏；
而"刷新本页"在两种形态下都成立（独立运行时它自己走刷新接口，
被基座加载时由基座走刷新接口再把权限下发给它）。

### 8. 建号成功的那句通知要带上"下一步"

`已新建用户「x」。` 后面补上：它默认没有任何菜单码、到「角色」页授角色并挂为成员、
否则它登录后看不到任何入口。

不补的后果不是"少说一句"，而是**工作看起来已经完成**：管理员认为把人建出来就结束了，
直到那个人登录进来说"里面是空的"才回头查 —— 那时现场已经不在管理员手上了。
形状与同页的重置通知一致（`…该用户下次登录须改密`）：**动作 + 它的后果**。

### 9. 文案的每一行用 `<br />` 断开，且不超 printWidth

背景第四节那个空格，处置不是"写完记得看一眼"，而是让它在**结构上不可能发生**：
每行一句、行尾用 `<br />` 断（`<br />` 与其后的文本同处一行，因此不会被插入空格），
每行控制在 `printWidth` 之内 —— prettier 便不再重排这几行。

并各补一条**按整段断言**的用例（不是逐词），把渲染结果钉住：
一旦将来谁重排了这几行、多出一个空格，用例会红。逐词断言抓不到它，
因为关键词本身没被改动 —— 这正是这类缺陷能长期存活的原因。

## 后果

- 新账号被授权之后，**不必重新登录**：在顶栏点一下即可，且会明确告诉他成了还是没成。
- 两处空状态从"报账"变成"指路"：说清了在哪补、补完怎么办、以及（管理台那处）
  为什么自己补不了。
- 建号这条路上，"能用"与"建出来了"之间的那一步第一次被写在了**管理员做决定的地方**。
- `reload()` 从"存在但不可达"变成"有且只有一个调用方"，并被文档与用例同时钉住。
- 中文文案里的隐形空格有了结构性的解法与用例兜底；同一坑此前在 `Home` 的
  `home__desc` 那段（三行文本）里已经存在，只是没人注意到（多出的是两处
  标点后的空格，比"另一个 已持有"这种词间空格更不显眼，故本轮**不改旧文案**，
  只在新增文案上立规矩）。

## 未覆盖

1. **子应用内部的空状态没有自助路径。** 一个只持有 `ui:admin:view`（进得去管理台）
   但没有 `ui:admin_*:view`（看不到任何标签页）的账号，看到的是管理台的空状态，
   而那条路上只有"刷新本页"。要他不刷页面就更新，得让基座向子应用**再下发一次**权限 ——
   也就是一条宿主→子应用的推送通道，当前全局状态只有挂载时与变更时的下发，
   没有"请求重取"这个方向。
2. **多标签页不同步。** A 标签点了重新检查、权限变了，B 标签要等下一次刷新或请求才知道。
   与 `0047` 留的"多标签页不同步"是同一个问题在两个场景下的表现，应当一起解决。
3. **做了一张真机脚本能验的链路，但没进脚本。** "管理员授权 → 重查 → 入口出现"是本轮
   最该端到端验一次的东西，而九支 `scripts/verify-*.mjs` 里没有覆盖它。
   它需要一个真实授权动作（要管理权限与会话），因此不是纯界面脚本能独立跑完的 ——
   现有 `verify-menu-permissions.mjs` 是最接近的落点。
4. **`reload()` 的失败与 401 的关系没有单独验。** 现在依赖的是内核的既有行为
   （业务失败返 HTTP 200 故不会被当成令牌失效）。用例里 stub 的是业务失败那一路，
   真正的 HTTP 401 会触发刷新重试，那条路径本轮没有覆盖。
5. **"审计员"这个角色仍要靠种子。** 背景第三节的闭合路径意味着：一个租户若要重新开始，
   只能靠种子或库侧。要不要一条"引导期临时凭证"（类似 `0043` 讨论过的那类通道）
   仍未决 —— 它与"忘记口令"那条待办是同一类问题（都需要一条不依赖既有登录态的信任通道）。
