# 0006. 接口契约的生成与消费

- **状态**：已采纳
- **日期**：2026-10-09
- **决策者**：舰长

## 背景

ADR-0001 与 ADR-0005 定了「前后端分离、以 OpenAPI 作为跨端唯一真相源」，但没有回答落地层面的四个问题：

1. **契约文件从哪来？** 手写，还是从后端代码推导？
2. **生成物要不要入库？** 入库会带来 diff 噪声，不入库则前端构建必须先把后端跑起来。
3. **前端怎么消费？** 手写一套 SDK，还是从契约生成类型？
4. **契约漂移怎么被发现？** 后端把 `startTime` 从 `number` 改成 `string`，前端要到运行时才炸吗？

还有两个必须一并处理的现实约束：

- **生成器表达不了"任意值"。** 日志的 `data` / `context` 在后端是 `Object`，springdoc 只能推到 `{"type": "object"}`，而 `openapi-typescript` 会把这种"光秃秃的 object"渲染成 `Record<string, never>` —— 语义变成"一个不允许有任何字段的对象"，于是 `{ orderId: 'SO-2026-0001' }` 这种最普通的日志数据在**编译期**就被拒了。
- **契约导出需要应用真的能跑起来。** springdoc 的 `/v3/api-docs` 只在应用启动后才有内容，因此需要一个能自动等待、且端口不与开发服务冲突的导出脚本。

## 决策

### 1. 契约由代码生成，不手写

```
后端代码（注解）──springdoc──▶ /v3/api-docs ──scripts/export-openapi.sh──▶ docs/api/openapi.json
                                                                                    │
                                                       openapi-typescript ──────────┘
                                                                  ▼
                                              web/packages/common-api/src/generated/schema.d.ts
```

**没有一处字段名或类型是手写的。** 手写的只有两样东西：

- 后端 Controller 上的 `@Operation` / `@Schema` 注解（描述"这个接口是什么"）；
- 前端 `common-api` 里"哪个方法对应哪条路径"的接线（见第 3 条）。

手写 SDK 的问题不在于写字多，而在于**它是一份会过期的副本**：后端加个字段，前端那份不会自动多出来，唯一的表现是运行时 `undefined`。

### 2. 生成物入库

`docs/api/openapi.json` 与 `common-api/src/generated/schema.d.ts` 都提交进仓库。

**为什么入库**（而不是构建时生成）：

- 前端构建**不依赖后端是否可运行** —— CI 里不必为了编译前端而先起一个 Java 进程；
- 契约的每一次变化都会在 code review 里**显式出现为一个 diff**。契约变更影响面大，值得被人看一眼睛，而不是藏在流水线里。

代价是生成物的 diff 有噪声（行号、字段顺序）。接受这个代价，因为它换来的是"契约变更可见"。

### 3. `common-api` 只做装配，不做形状定义

| 层 | 是否认识业务接口 | 职责 |
|----|------------------|------|
| `common-tools/http` | **不认识** | 传输内核：怎么发、怎么翻译错误 |
| `common-api` | 认识，但只做接线 | 路径常量 + 契约类型 → 方法 |

路径常量用 `satisfies keyof paths` 约束：

```ts
const PATH_CLIENT_LOG = '/api/logs/client' satisfies keyof paths;
```

拼错路径 → **编译期报错**，而不是上线后一个 404。

### 4. 契约里"任意值"的缺口在 `common-api` 一次性修正

在 `common-api/src/types.ts` 定义 `JsonValue` / `JsonArray` / `JsonObject`，把契约中被误渲染为 `Record<string, never>` 的字段重新声明为真正的任意值：

```ts
type WithJsonPayload<T> = Omit<T, 'data' | 'context'> & {
  data?: JsonArray;
  context?: JsonObject;
};
```

这是全链路**唯一**需要人工介入类型的位置，且**只替换那两个字段**：`Omit` 之后其余字段仍完全来自契约。

> 不选"在后端把 `Object` 换成具体类型"：日志数据本来就是原样透传的，硬造一个 DTO 等于给"任意值"套一层假结构，反而更糟。

### 5. 用测试钉住契约的关键形状

`common-api/tests/log.test.ts` 里对易退化的字段做类型断言：

```ts
expectTypeOf<ClientLogQuery['startTime']>().toEqualTypeOf<number | undefined>();
```

springdoc 有过一次把 `Long` 静默推平为 `string` 的经历（查询参数位置带 `@Schema` 时以注解为准重建 schema，`type` 默认空串）。断言让这类退化在**测试阶段**失败，而不是在页面上显示成 `"1759999999999"`。

### 6. 后端注解的依赖只加在应用层

- `common` 层只依赖 `springdoc-openapi-starter-common`（提供 `@Schema` / `@Operation` 注解）；
- `springdoc-openapi-starter-webmvc-ui`（提供 `/v3/api-docs` 与 Swagger UI）**只加在 `sts-app-server`**。

注解是"描述"，端点与 UI 是"运行时设施"。技术底座层不该替业务应用决定要不要暴露接口文档。

### 7. 导出脚本使用固定端口、自动等待

`scripts/export-openapi.sh`：

- 默认端口 **18080**，刻意避开 8080（开发常用）与 3000/3200（前端）；
- 轮询 `/v3/api-docs` 直到就绪，而不是 `sleep 固定秒数`（慢机器上必然失败）；
- 拉到的 JSON 经 node 重新格式化后写入 `docs/api/openapi.json`，保证 diff 稳定。

## 后果

**正面**

- 契约不可能漂移：它没有第二份手写副本
- 前端构建与后端运行时解耦，CI 可分别独立跑
- 接口变更在 review 里可见，格式固定使 diff 可读
- 路径拼写错误从"上线后 404"提前到"编译不过"

**负面 / 代价**

- 改一个接口要跑两条命令（导出契约、生成类型），漏跑不会立刻报错，只能靠习惯与 review
- 生成物有 diff 噪声，评审时要学会跳过纯格式变化
- `openapi-typescript@7.13.0` 的 peer 约束是 `typescript@^5.x`，本项目用 6.0.3，`pnpm install` 会打一条 peer 警告。**功能正常**（生成结果已验证），但升级生成器时要重新确认
- 生成器对"任意值"的表达缺口需要人工补一次类型（第 4 条）

**后续约束**

- **后端改接口 → 必须重新导出契约并更新生成物，与代码同一次提交**
- 前端**禁止**绕开 `common-api` 手写裸请求，禁止手改 `src/generated/` 下的任何文件
- `common-api` 里除 `types.ts` 的 `JsonValue` 修正外，不得出现手写的字段类型
- 契约文件按域拆分（`openapi/` 目录多文件）暂不做，等接口数量真正变多再说
