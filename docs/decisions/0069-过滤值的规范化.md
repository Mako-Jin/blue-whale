# 0069. 过滤值的规范化

- **状态**：已采纳
- **日期**：2026-10-15
- **决策者**：舰长

> 领的是 `0068`「未覆盖」第 3 与第 4 条：**非关键词的过滤值仍然不 trim**
> （"射程约 20 处取值，未做"）与 **`normalize` 仍有 5 个副本**（"上收的对象应当是
> '所有过滤值的规范化'"）。
>
> 核完的结果：它也不是"两种风格"，而是**三种形态**，而且其中藏着一处
> **两条 SQL 路径判空口径相反**的真实缺陷 —— 同一个请求里会出现"总数 3、各级别之和 0"。
> 这比"某个页面搜不到"要硬：它是**同一个响应的两个字段自相矛盾**。

## 背景

### 1 射程：29 处字符串过滤值、三种形态

过滤值出自各域的 `Query` 对象，全部走 `eq`（**精确匹配**）。取值方式分三种：

| 形态 | 做法 | 域与列 | 处数 | 两端带空白 |
| --- | --- | --- | --- | --- |
| **枚举归一** | `Status.parse(raw)` 一类，认得就返回规范 `wireName` | 角色 `status` · 资源 `resourceType` · 用户组 / 角色成员 `memberType` | 4 | **已健壮** |
| **纯 trim** | 本域私有 `normalize()`（trim + 空串转 `null`） | 组织 `status`/`orgType` · 角色 `category` · 用户组 `category` · 资源 `parentCode` | 5 | **已健壮** |
| **只判空** | `hasText()` 或 `!= null && !isBlank()`，**原值**交给 `eq` | 用户 `status` · 租户 `status` · 日志 5 列 · 事件 5 列 · 审计 5 列 | **20** | **匹配不到** |

第一形态**已经是健壮的**，而且比 trim 更强 —— 它的 `parse` 内部写的是
`type.wire.equalsIgnoreCase(value.trim())`，**自带 trim**，还把大小写一并归一。
本轮**不动**它（把 `parse` 换成 `trim` 是功能退化）。

三形态对 `null` 与**只含空白**的处置一致（都退化成"不过滤"），
唯一的分叉在**两端带空白**时。

### 2 而那 20 处里还藏着一处"两条路径口径相反"

日志 / 事件 / 审计三域的**聚合统计**走手写 SQL，判空写在 SQL 里：

```
<if test="app != null and app != ''">   AND app = #{app}   </if>
```

而**同一个请求的列表**走 Java 的 `hasText()`（`isBlank`）。两者对 **`"   "`** 的判定**相反**：

| 输入 `app = "   "` | 列表（wrapper · `isBlank`） | 聚合（手写 SQL · `!= ''`） |
| --- | --- | --- |
| 判定 | "没给值" ⇒ **不拼条件** | "给了值" ⇒ `AND app = '   '` |
| 结果 | 本租户全部日志 | 0 行 |

⇒ 于是 `stats` 返回的 `total` 与 `levels` 加总**对不上**（实测：总数 3、各级别之和 0）。
本仓在那两处代码上写着"聚合 SQL 的租户条件必须与上面这句 wrapper 写到同一处语义"——
这次不一致的不是租户条件，而正是**它旁边那句判空**。

### 3 库里的值不会带两端空白

各域写库前都过了一遍规范化（`normalize` / `resolveStatus` / `parse`），
所以 `?status=%20ENABLED%20` **不是一个"想精确匹配带空格的"的意图** ——
它永远匹配不到任何行。这一处的差异**不承载任何区分能力**，只承载"在某些页面上搜不到"。

## 一 实测：六条同形断言

照本仓"先写能红的用例"的做法，先加 `FilterValueTrimApiTest`（6 例、跨 profile、
不 `@Transactional`），**不改代码**跑一次 —— 读数是 **4 红 2 绿**：

| 用例 | 改前 | 改后 |
| --- | --- | --- |
| 用户域：`"  ENABLED  "` 与 `ENABLED` 结果集相同 | **红**（2 条 vs 0 条） | 绿 |
| 组织域：同上（**对照组**） | 绿 | 绿 |
| 租户域：同上 | **红**（1 条 vs 0 条） | 绿 |
| 日志域：`"  <app>  "` 与 `<app>` 结果集相同 | **红**（1 条 vs 0 条） | 绿 |
| 日志域：**聚合的级别条数之和 = 总数**（空白 app） | **红**（总数 3、各级别之和 **0**） | 绿 |
| 纯空白 = 不过滤（三域同义） | 绿（**回归钉**） | 绿 |

两条红是"同一个 `status` 在组织域搜得到、在用户 / 租户域搜不到"；第三条红是
第 2 小节那处内部不一致的现场；而**同形的组织域那条是绿的** —— 这就是"口径不一致"的证据，
不必靠读代码推断。最后一条是**回归钉**：把判空下沉到公共实现时，最容易顺手弄坏的
就是"空白值"这一支。

第 5 条的断言值单独说明一下：它断的不是"命中几条"，而是**同一个响应内部自洽** ——
`total`（wrapper 算的）必须等于 `levels[*].levelCount` 之和（手写 SQL 算的）。
这个形状可以**原样复用**到任何"列表与聚合共用一组过滤值"的地方。

## 二 决策

1. **规范化的真值来源放在 `FilterValue.text()` 里，不放调用方。**
   与 `0068` 同一条理由：后端是权威边界，API 调用方、脚本、将来的别的客户端都不走
   前端那一层。而它本来就是"过滤值进 SQL 之前的预处理"的唯一入口。

2. **吃掉两端空白，空串与纯空白退化为 `null`（= 不过滤）。**
   与三形态改前的行为都一致（`null` 与纯空白本来就同义），不变。

3. **20 处取值统一成"先取局部变量、再拿它判 `null`"**：
   ```java
   String app = FilterValue.text(query.getApp());
   ...
   .eq(app != null, ClientLogEntity::getApp, app)
   ```
   不是风格选择：`eq(条件, 列, 值)` 的"值"是**无条件求值**的，写成
   `query.getApp().trim()` 会在值为 `null` 时当场 NPE（本仓已踩过多次）。

4. **手写 SQL 与 lambda wrapper 用同一个局部变量。**
   三处聚合（`countByLevel` / `countByEventName` / `countByAction`）与审计的
   `baseWrapper` 都改为接收**已经规范化过的**值 —— 一致性由"只有一个来源"保证，
   而不是由"两处各写一遍相同的判空"保证。

5. **枚举归一那 4 处不动。** `parse` 自带 trim 且顺带归一大小写，比 `trim` 更强；
   把它换掉是功能退化。"枚举型的过滤值要不要统一归一大小写"是**另一个维度**，见「未覆盖」。

6. **`KeywordLike.pattern()` 改为调用 `FilterValue.text()`。**
   规范化（只吃两端、不吃中间）只有一个实现；`KeywordLike` 只留 `LIKE` 特有的部分
   （转义 + 前后补 `%`）。`0068` 把规范化收进 `KeywordLike`，本轮把它**下沉**到
   更基础的 `FilterValue` —— 因为精确匹配的过滤值也要用它，而过滤值不该依赖
   "LIKE 那个类"。

**没有采用的两条路**：把规范化留给前端（`0068` 已经否过一次，理由不变）；
给每个域各写一遍判空（那正是这次要消掉的东西 —— 一处改了、另一处没改，
症状是"总数对、分布不对"，几乎不会被发现）。

## 三 落地

- **新增 `FilterValue`**（`sts-common-db` 的 `...common.db.query` 包，与 `KeywordLike` 并列）。
  `text(value)`：`null` 进 `null` 出，否则 `trim()`，空则 `null`。类注释写明与 `KeywordLike` 的分工。
- **`KeywordLike.pattern()`**：内部改调 `FilterValue.text()`；类注释里"关键词的规范化也在这里"
  改成"由 `FilterValue` 提供"。
- **20 处取值**：
  - `UserService` / `TenantService`：各 1 处（`status`）。
  - `ClientLogService`：`stats` 的 `app`（wrapper 与手写 SQL 共用）、`buildWrapper` 的 5 个值。
    `level` 那一处保留"该列存小写"的 `toLowerCase` —— 那是**该列的比较语义**
    （资源域的 `method` 往反方向的大写归一），不是通用规范化，不下沉。
  - `ClientEventService`：同上（`stats` 的 `app` + `buildWrapper` 的 5 个值）。
  - `AuditLogService`：`stats` 的 `resource`（要用三次，算一次传下去）+
    `buildWrapper` 的 5 个值；`baseWrapper` 改为接收规范化后的值。
- **`AuditLogService` 的私有 `hasText` 删掉**（它的唯一用途就是那 5 处过滤值）。
  **日志与事件两域的 `hasText` 保留** —— 它们还服务于条目校验与 `firstNonBlank`，
  那是"判空"这件事，与过滤值无关（见「未覆盖」）。
- **新增 `FilterValueTrimApiTest`**（6 例 · 跨 profile · 不 `@Transactional`）。
- **新增 `verify-filter-values.mjs`** 并接进 CI 的 `guards` job。

## 扰动验位

- **改代码前**跑那 6 例 ⇒ 4 红 2 绿（上表）——"没有规范化"这一侧的读数。
- **改代码后**跑 ⇒ 6 绿。
- 守卫三条规则各扰动一次（改回旧形态 ⇒ 必红，还原 ⇒ 必绿）：
  - 把 `UserService` 改回 `!= null && !isBlank()` ⇒ 规则 2 报红；
  - 把 `ClientLogService` 两处改回 `.eq(hasText(...), ...)` ⇒ 规则 1 报红（**两处都报**）；
  - 把 `countByAction` 的实参改回 `query.getResource()` ⇒ 规则 3 报红。
- **守卫自己的两个假绿也在扰动中发现并修掉**：
  - 规则 3 起初要求调用点前面有 `.`，而同类内调用写的是
    `selectCount(baseWrapper(...))` —— **一次都没命中**（改成 `\b` 才对）。
  - 同一条规则起初还把审计的 `baseWrapper` 纳入射程，结果**误报**：
    它的实参里有 `operatorId`（Long），调用点写的是
    `visibility.operatorFilter(query.getOperatorId())`，那是正当的。
    按 `0064` 的判据（会误报的守卫比没有更糟）把它移出射程。

## 后果

**正面**

- "精确匹配的过滤值进 SQL 之前长什么样"只剩一个真值来源：`FilterValue.text()`。
  新加一处过滤值时照抄"先取局部变量"，不需要再问"这个域要不要 trim"。
- **修掉一处真实缺陷**：日志 / 事件 / 审计的聚合与列表现在用**同一个变量**，
  `total` 与分布天然自洽（此前 `app = "   "` 时是"总数 3、各级别之和 0"）。
- `normalize` 的用途收窄到"写入值"（`entity.setXxx`）；过滤值不再需要它。

**负面 / 代价**

- **行为变化**：用户 / 租户 / 日志 / 事件 / 审计五域的过滤值，两端带空白的从
  "搜不到"变成"搜得到"。这是本次的目的，但它**是一次对外可见的行为变化** ——
  如果外部调用方此前依赖"我传 `" a "` 就只匹配含空格的"，那是不成立的假设
  （库里的值本来就不带空格）。
- 各域多了一行局部变量，`buildWrapper` 这类方法变长了几行。这是"值只求一次、
  且条件与值必然同源"的代价。
- 日志与事件两域**仍然各有一份 `hasText`**（服务于条目校验 / `firstNonBlank`），
  `0068` 说的"`normalize` 有 5 个副本"变成了"`hasText` 有 2 份副本"——
  副本数少了，但**没有归零**，见「未覆盖」。

**后续约束**

- 新加过滤值：`String x = FilterValue.text(query.getX());` 然后 `.eq(x != null, ...)`。
  **不要在 `eq` 的实参里现调 `.trim()`**（无条件求值，会 NPE）。
- 手写 SQL 与列表**共用同一个局部变量** —— 各算一遍就会出现"总数对、分布不对"。
- 改 `FilterValue.text()` 的规范化口径时，记得它同时服务 `KeywordLike.pattern()`。

## 「未覆盖」

1. **达梦未实测。** 本篇的改动全在 Java 侧（`trim` 与局部变量），不落到 SQL 上；
   但第 2 小节那处"手写 SQL 的判空"依赖 Ognl 与三方言的行为，而达梦上没验过
   （与 `0067`「未覆盖」1 同源）。
2. **枚举型的过滤值要不要统一归一大小写 —— 未定。** 角色 / 资源 / 用户组的
   `parse` 把 `enabled` 归一成 `ENABLED`，于是 `?status=enabled` 在角色域搜得到、
   在用户 / 租户 / 组织域搜不到。**大小写是另一个维度**（`0065` 已定"文本相等区分大小写"、
   `0066` 已定"`LIKE` 也跟排序规则走"），要动它得先回答"枚举的 wire name 算不算
   数据约束"—— 与"过滤值吃不吃空白"是两件事，本轮**刻意没顺带**。
3. **`trim()`（Java，只吃 `<= U+0020`）与 `isBlank()`（`Character.isWhitespace`）覆盖面不同。**
   与 `0068`「未覆盖」2 同源：本方法统一到 `trim()`，于是"只含全角空格"的过滤值
   从"不过滤"变成"搜一个全角空格"。这是待裁决的口径问题。
4. **写入值（`entity.setXxx`）仍然不统一。** `request.getStatus()` 这类在部分域走
   `resolveStatus`（归一）、部分域**原样入库**（`TenantService.update` 是已知的一处，
   见 `0058`）。**上游传进来一个带空格的枚举值就可能原样落库** —— 那是"写入"侧的事，
   与本篇的"过滤"侧不同源，未做。
5. **`hasText` 仍有 2 份副本**（日志 / 事件各一，服务于条目校验与 `firstNonBlank`）。
   它们是"通用判空小工具"的副本，不是过滤值的规范化 —— 上收它们属于"工具类整理"，
   与本篇主题不同，未做。
6. **只有三个域有运行时断言**（用户 / 组织 / 租户 + 日志）。事件与审计两域的
   过滤值共用同一实现、机械守卫也防了漏用，但没有各自的用例
   （与 `0066`「未覆盖」2、`0067`「未覆盖」2、`0068`「未覆盖」5 同源）。
7. **`?status=`（**空串**，而非纯空白）与不传的处理没有单独断言。** 两者在改前改后
   都同义（空串 → `null` → 不过滤），本类只覆盖了"纯空白"。低价值，未做。
