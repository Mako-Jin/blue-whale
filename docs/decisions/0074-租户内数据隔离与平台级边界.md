# 0074. 租户内数据隔离与「平台级」的边界：把「接口能不能指定别家租户」答成一条结构性判据

- **状态**：已采纳
- **日期**：2026-10-16
- **决策者**：舰长

## 背景

`0051` 的「未覆盖」最后一条把这件事原样挂着：

> **接口能不能指定别家（存在的、启用的）租户**：仍是 `0050` 未覆盖 1 的正题，
> 需要产品决定（平台级管理台 vs 租户级管理台）。本轮**没有碰**它。

`0049` / `0050` 的挂账是它的另一半：`DataScope` 没有接进 auth 域，而 `auth:tenant:*` 的
持码者"能改所有租户"。三句话指的是同一面墙：**auth 域有租户列，却没有租户边界。**

### 墙上的四个洞（读代码就能确认，不需要构造数据）

1. **四个业务域的 `resolveTenantId(requested)` 照单全收**：
   `requested != null` 时只调 `tenantService.assertExists(requested)`，**不验归属**。
   于是 `GET /api/auth/users?tenantId=乙` 列出乙租户的用户，
   `POST /api/auth/users` 带 `tenantId: 乙` 直接在乙租户里建号（角色 / 组织 / 用户组同形）。
2. **五处 `requireXxx(id)` 都是裸 `selectById`**（`requireUser` / `requireRole` ×2 /
   `requireGroup` / `requireTenant`）：把路径上的主键换成别家的，
   详情 / 修改 / 删除 / **重置口令**全部照做。
3. **租户域自己没有隔离**：任何持 `auth:tenant:*` 的账号列出、修改、停用、删除**所有**租户；
   `create` 也不限制父级 —— 任何人都能建**顶级租户**。
4. **两处以 `userId` 为主语的子资源自己取用户**：`RoleMemberService#rolesOfUser`（裸 `selectById`，
   会真的泄漏乙租户用户的角色来源）与 `OrganizationMemberService#listByUser`
   （按当前租户过滤，返回空 —— 安全但形态不一致）。

### 这不是"多看了几行"

`0025` 已经为审计域答过同一面墙的一半（"租户强制等于当前登录者"、"详情跨租户 `404`"），
但它只落在审计查询上。auth 域这四条合起来的效果是：

**一个持有 `auth:user:update` 的甲租户管理员，可以重置乙租户管理员的口令，然后以他的身份登录。**

租户是这套系统里唯一一条硬边界（`NEXUS` 的叙事就是"房间 = 租户、门禁 = 数据范围"），
而墙上的洞不是"权限码配错了"，是**判据不在**：权限码管"能不能做这件事"，
没有一处管"能对谁做"。

### 一个必须先回答的问题

要把边界立起来，绕不开"谁能跨租户"—— 而仓里其实已经答了一半，只是没被命名：

- `0058` 写"恢复入口只剩**另一个租户里持有 `auth:tenant:update` 的账号**（本仓的形态
  就是种子租户的管理员）"；
- `TenantDisableApiTest` 的两条前置**就是**用种子管理员跨租户建号；
- `resolveTenantId` 的 `requested` 分支从第一版起就存在，服务的就是"跨租户预配"。

也就是说：**"平台级"这件事在本仓是事实存在、只是没有名字、也没有边界。**
本片给它一个名字（判据），并把其余一切锁死。

## 决策

### 1. 「平台级」的判据是结构性的：**操作者所在租户是顶级租户**（`parent_id IS NULL`）

本仓的形态就是种子租户那一个（`DefaultAdminSeeder` 写的 `tenantLevel = 1` / `codePath = "/"`）。

**不新增权限码。** 层级位置是**可以从库里读出来的事实**，而一个"平台管理员"码会造出
两个都必须对上的开关（码 + 位置），它们不一致时的表现是"某个顶级租户的账号什么都不能管"——
一个没人会去查的静默状态。

**这个定义需要闭合**：否则"建一个顶级租户"就等于给自己升一级，而新升出来的那个账号
立刻获得全库可见性。闭合条件就是第 5 条的 `40302`（非平台级不能建顶级租户）。

**两个刻意的边界：**

- **所在租户查不到时不视为平台级** —— 判据在数据异常时必须能往**窄**走：
  一个指向不存在租户的会话（租户被删了）不该因此获得全库权限；
- **没有身份上下文时视为平台级** —— 与 `assertNotOwnTenant`（`40921` 的守卫）
  "没有身份就没有那个操作者"是**同一条先例**。无上下文的调用只出现在内部路径
  （种子引导 `DefaultAdminSeeder`、测试夹具），它们本来就要求显式传入租户；
  而 HTTP 上的每个写路径都在 `@RequiresPermission` 之后 —— 一定有上下文。
  若这里返回 `false`，种子会在启动时被自己的隔离挡住。

### 2. 读侧（列表 / 树）：租户条件**恒等于自己**，传入的 `tenantId` 被**忽略**

沿用 `0025` 第 1 / 3 条对审计查询立下的两条口径：租户条件是**无条件加上**的
（不是 `eq(条件, ...)` 那种可关的写法）；而一次越权尝试只该**安静地**返回调用方
自己有权看的那一份 —— "被忽略"与"筛出一个空结果"在调用方看来必须同形，
报 `403` 会把一次探测变成可观测的信号。

### 3. 详情 / 改 / 删 / 重置口令：跨租户一律返回**该对象的 `404`**

不是 `403`（`0025` 第 2 条）：`403` 等于向调用方承认"这条记录确实存在，只是不给你看"，
而"它存在"这件事本身就是别人的信息。

**这是 `0059` 那个家族里第二类覆盖文案的落点。** `0059` 当时登记的唯一一处是
`DataScopeService#resolve`（"用户不存在**或不属于当前租户**"，并注明"不能拆成两个码 ——
拆了就等于告诉调用方那个人存在，只是不在你这儿"）。本片把同一条判据推广到一族：
`TenantService#assertVisible(entityTenantId, notFoundCode)` 用
`notFoundCode.getMessage() + "或不属于当前租户"` 生成文案 ——
**因此同一个码在所有这些落点上给出的是同一句话**，"一处覆盖"变成"一族覆盖"这条变化
本身要记在 `0059` 名下，而不是当成新规矩。

### 4. 写侧（`create`）：带别家 `tenantId` **显式拒绝**，且与"租户不存在"**同码同文案**

`resolveWriteTenant` 与 `resolveQueryTenant` 刻意分成两个方法，因为同一个 `tenantId` 参数
在两条路上的语义不同：

| | query | create |
| --- | --- | --- |
| `tenantId` 的角色 | **过滤条件** | **归属声明** |
| 跨租户时 | 忽略（返回自己那一份） | 拒绝（`40002` + 与"引用的租户不存在"逐字相同的文案） |
| 反过来的后果 | 少看了几条 | 调用方以为建成的地方与实际不符，而他看不到任何异常 |

**同码之外还要同文案**：只同码而文案不同，等于换个地方泄漏。对非平台级操作者而言，
别家租户在系统里**就是不存在** —— 他连租户列表里都看不到它（第 5 条）。

### 5. 租户域自己也是一种资源

- 列表：非平台级只看得到**自己那一个**租户（恒定的 `eq(id, 自己)`）；
- 详情 / 修改 / 删除：跨租户 → `40402`（`assertVisible(id, TENANT_NOT_FOUND)` ——
  租户的"租户归属"就是它自己，所以传的是 `entity.getId()`）；
- `create`：非平台级**只能在自己的租户下建子租户**，两个分支两个码：
  - 不传 `parentId`（建顶级）→ **`40302`（新码）**。顶级租户不是"某个看不见的对象"，
    它是一个**能力**；这里也没有"那个东西存在"可言（它正要被创建）；
  - `parentId` 指向别家 → `40402` + 与"租户不存在"逐字相同的文案。

  层级权限判定**排在编码判重之前**：先判重的话，一个非平台级操作者能从
  "`40904` 编码已存在"与 `40302` 的差别里读出"这个编码被谁占着"。

### 6. 这条规则只有一个属主：`TenantService`

四个业务域的私有 `resolveTenantId` **全部删除**，租户解析连同隔离判定一起收到
`TenantService`（`resolveQueryTenant` / `resolveWriteTenant` / `assertVisible` /
`currentOperatorIsPlatform`）。这与 `0050` 把"租户存在性"从四个属主收到一处
（`assertExists`）是同一件事的下一步，而两个半片合成了一整条边界。

`assertExists` 与 `assertAcceptsNewData` 保持原位、语义不变；`resolveWriteTenant` /
`resolveQueryTenant` 的平台级分支**内部先过 `assertExists`**，顺序不可反：
不存在的租户应当给出"引用不存在"，而不是被当成一次越权。

> 用户域那一份的历史值得留一句：它曾是四个属主里**唯一漏掉存在性校验**的一个
> （`0050` 的主题），而本片删掉它时，它已经补上了那一格 —— 留下的是一段
> "同一条规则被写四遍、其中一遍写漏"的结构性记忆。

### 7. 顺带抓到的两处 —— 同一判据、同类缺口

- `RoleMemberService#rolesOfUser`：裸 `selectById` ⇒ 跨租户查别人的用户会真的列出
  他的角色来源（角色名 + 直授 / 经组）。它不经过 `UserService#requireUser`，
  所以加固 `requireUser` 覆盖不到它 —— 这正是"以 `userId` 为主语的子资源要各自过一遍"的原因；
- `OrganizationService#managerNameOf`：`manager_id` **没有任何判定读它**，
  所以跨租户传一个 id 的唯一后果是把别家用户的名字写进本租户组织的展示列。
  这里选择**拒绝**（`40002`）而不是静默当作"没传"——静默会让你以为设上了负责人，
  而那一列在界面上是空的。
- `OrganizationMemberService#listByUser`：原本按当前租户过滤、返回空列表（**安全形态**），
  改它是为了一致性 —— 同族入口对"不存在"与"不属于当前租户"必须给同一个答案。

### 8. 成员关系的一致性继续由既有校验承担，不重复加

`RoleMemberService#requireMember`（`assertSameTenant`）、
`OrganizationMemberService#requireSameTenantUser`、`UserGroupService#assertSameTenant`
已经在"成员与容器的租户必须相同"上做了判定。本片**不动它们**：
容器侧的可见性由 `requireRole` / `requireOrg` / `requireGroup` 挡在前，
成员侧的一致性由它们挡在后，两层合起来覆盖了"甲租户的角色不能授给乙租户的人"。

### 9. 刻意不做

- **`DataScope` 仍然不接业务查询**：本仓没有业务数据表（`0025` 的遗留），
  而把它接进审计域是一次**静默的权限放宽**（`0030` 第 10 条）—— 与"租户"这条轴无关，
  本片不碰；
- **接口形状一个都没改**：没有新增查询参数、没有改 DTO、没有加 `@Pattern`。
  隔离完全是服务端行为，契约因此**零变化**（前端不需要同步任何东西）；
- **资源域不动**：`auth:resource` 是**平台级**的目录（`tenant_id` 一律留空），
  它本来就没有租户维度，也不该有；
- **菜单 / 标签页可见性不动**（`0030` 未覆盖 5 的同一条边界）。

## 实测

新增 `TenantIsolationApiTest`（14 条，`@SpringBootTest` 端到端），
夹具刻意**都建在非顶级租户里**（A、B 都是种子租户的子租户）：种子账号是平台级，
用它做操作者**测不出任何隔离** —— 改前改后都是 `code: 0`。
每条用例的操作者是一个"自建租户里的、被授予了所需权限码的"账号，它的权限是真的
（不是靠 `@RequiresPermission` 拦出来的 `403`）。

| # | 用例 | 改前 | 改后 |
| --- | --- | --- | --- |
| 1 | 列表：`?tenantId=乙` → 拿到自己那一份、不含乙的用户 | **`code: 0` 且列着乙的人** | 只含自己 |
| 2 | 详情：查乙的用户 | **`code: 0`** | `40401` |
| 3 | 反查角色：查乙用户的角色来源 | **`code: 0`** | `40401` |
| 4 | 组织详情：查乙的组织 | **`code: 0`** | `40404` |
| 5 | 用户组详情：查乙的用户组 | **`code: 0`** | `40405` |
| 6 | 建号：带 `tenantId=乙` | **`code: 0`（真建出来了）** | `40002` |
| 7 | 改用户：改乙的用户 | **`code: 0`** | `40401` |
| 8 | 重置口令：重置乙用户的口令 | **`code: 0`** | `40401` |
| 9 | 删用户：删乙的用户 | **`code: 0`** | `40401` |
| 10 | 租户列表：非平台级 | **3 行（全库）** | 1 行（自己） |
| 11 | 租户详情 / 修改：够别家租户 | **`code: 0`** | `40402` |
| 12 | 建顶级租户 = 自升平台级 | **`code: 0`（真升上去了）** | `40302` |
| 13 | **对照**：平台级跨租户照旧 | `code: 0` | `code: 0` |
| 14 | **对照**：非平台级管自己租户照旧 | `code: 0` | `code: 0` |

**改前 12 红 / 2 绿（那 2 绿就是两条对照），改后 14 全绿。**

### 用例自身的两处缺陷（第一版 12 条时踩到的，记下来免得下次重踩）

1. **一条会改数据的用例污染了其他用例**：删用户那一版直接删的是共用目标，
   而改前那一下**真的把人删掉了**（逻辑删除）⇒ 之后 4 条查/改它的用例都因为
   "查不到"而**假绿**（`40401` 与预期值恰好相同）。修法是让那条用例**独占自己的靶子**。
2. **重置口令那一版给了种子口令** ⇒ 改前先撞 `40914`（口令防重用），
   把"跨租户"这件事盖掉。修法是用一个与已有口令不同的值。

两条都不是实现缺陷，是**断言不唯一的缺陷** —— 症状都是"红了，但红的原因不是本片要测的那个"。

## 验位（扰动）

同一批用例跑了两轮扰动，都是改完立刻跑、跑完立刻撤：

1. **同时拆掉四处读侧 / 层级判据**（`resolveQueryTenant` 恢复"照单全收"、
   `assertVisible` 直接返回、租户 `page` 去掉恒定条件、`assertCanCreateUnder` 整段取消）：
   **11 红 / 3 绿**。红的正是这四处对应的 11 条；绿的三条是两条**对照**加上第 6 条
   —— 第 6 条的判据是写侧那一处，这一轮没有拆它（所以这一轮它**应该**绿）；
2. **单独拆掉写侧的跨租户拒绝**（`resolveWriteTenant` 直接放行）：**1 红 / 13 绿**，
   红的只有第 6 条。

两轮合起来证明：**每条用例的判据都真的打在对应那一处实现上**，
而不是靠某一条间接约束"顺带"成立；而两条对照在两轮里都没红 ——
它们守的是反方向（不许过度收紧）。

## 后果

**正面**

- 租户这道墙**第一次有了服务端判据**，而且只有一处属主（`TenantService`）；
- `0050` 未覆盖 1 与 `0051` 未覆盖最后一条被**同一个决定**关掉（"能不能指定别家租户"
  的答案是"能 —— 但只有平台级能，其余一律锁死在自己租户内"）；
- `0049` 挂账的"`auth:tenant:*` 持码者能改所有租户"在租户域本身被收口；
- 覆盖五个域的 14 条端到端用例进入常态回归，且**有 2 条对照**守着"不许过度收紧"；
- 顺带修掉三处同类缺口（角色反查、组织负责人、组织归属反查），
  并把"以 `userId` / `orgId` 为主语的子资源要各自过一遍"写成了一条可复查的形态。

**负面 / 代价**

- **"平台级"是本片新命名的一个概念，而它只被两条用例间接钉住**（第 13 条与第 12 条）。
  判据本身（顶级租户）与它的闭合条件（不能建顶级租户）分别在两处，改动其中一处
  不会让另一处变红 —— 这是这条设计最脆弱的地方；
- 非平台级操作者的行为是"静默忽略"（读侧），也就是**他永远不知道自己的 `tenantId`
  参数被丢掉了**。这是 `0025` 既有的取舍（不把越权变成可观测信号）在更大面积上的应用，
  但它确实让"传错了参数"与"想越权"在调用方看来同形；
- **每个带 `tenantId` 的查询多一次租户查询**（判平台级要读自己租户的 `parentId`）。
  不带 `tenantId` 的路径零额外查询（`requested == null` 直接返回自己），
  同租户资源的 `assertVisible` 也零额外查询（先比租户 id，不等才去判平台级）；
- 前端**看不到任何变化**：非平台级管理员打开租户页只会看到一行。
  这对"平台级管理台 vs 租户级管理台"这个产品问题只是后端答案，
  界面要不要分两套（或者给平台级一个"管子租户"的入口）**没有落点**，见「未覆盖」。

**后续约束**

- 新增任何一个带 `tenant_id` 的域时，**三件事都要接**：
  查询走 `resolveQueryTenant`、新建走 `resolveWriteTenant`、`requireXxx` 走 `assertVisible`。
  漏掉第三条的症状是"列表干净、但详情能翻墙"；
- 凡新增"以某个 id 为主语的子资源入口"，都要问一句**它自己取的那个对象过可见性了吗**
  —— 本片有三处（`rolesOfUser` / `managerNameOf` / `listByUser`）正是漏在这里；
- `05` 的"不走既有入口的取数"（拼树、派生列回查）**不算缺口**，
  但每个新写法都要能回答"它是不是从已校验的对象出发的"。

## 未覆盖

- **平台级管理台的产品形态**：本片只给了后端语义。界面要不要区分两套管理台、
  平台级要不要一个"进入某租户"的入口，都没有落点（`0051` 提的"平台级管理台 vs
  租户级管理台"这个产品问题，本片答的是**它存在**，不是**它长什么样**）；
- **平台级操作者读别家租户的组织树**：`GET /api/auth/orgs/tree` 不接受 `tenantId`
  （它只看自己租户的森林），本片**没有给这个接口加参数** ——
  加了就是一次契约变化，而它属于上一条的产品决定；
- **平台级操作者查别家租户用户的 `data-scope`**：`DataScopeService#resolve` 的语义是
  "本租户内"（它自己带 `eq(tenantId)`），平台级也改不了这一点。这是既有的收敛，
  与本片同向，但"平台级该不该能查"没答；
- **`manager_id` 之外还有没有别的跨租户引用列**：本片只核了组织那一处
  （`contact_*` 是自由文本，不引用实体）。角色 / 用户组 / 资源三域的引用列
  （`parent_id` / `resource_id`）都已有同租户或平台级校验，但这是一次手工核对，
  没有守卫；
- **审计域之外的三条管道**（`bw_client_log` / `bw_client_event`）的可见性
  仍按"租户强制等于登录者"（`0025` 未覆盖），本片没有改它们的语义；
- **`40302` 的文案不被界面消费**：管理台不渲染"建顶级租户"这个动作，
  所以这个码在界面上不可达 —— 与 `40920` / `40921` 同样的处境；
- **达梦未实测**（全仓同一条，`0073` 未覆盖 1）。
