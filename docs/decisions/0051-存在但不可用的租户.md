# 0051. 「存在」不等于「可用」：引用的租户停用时，四个域照样把数据建出来

- **状态**：已采纳
- **日期**：2026-10-14
- **决策者**：舰长

## 背景

起点是 `0050` 收尾时留下的两条：

1. **一条明确标着"本轮没有验证"的**：`assertExists` 用 `selectById`，
   逻辑删除的行同样查得到，"引用的租户被软删之后，引用它的新数据仍能被建出来"
   —— 该 ADR 拒绝断言它成立或不成立（"由框架配置决定，本轮未核"）。
2. **一条明确标着"需要产品决定，不是代码"的**：接口能不能指定**别家存在的**租户。

第 2 条本轮同样不碰（它是授权问题，不是完整性问题）。
第 1 条能核，先去核它 —— 结果核出了**另一件同族的事**。

### 一、先核那条"未验证"：它本来就由 `@TableLogic` 覆盖

`bw_auth_tenant` 有 `deleted TINYINT NOT NULL DEFAULT 0 COMMENT '逻辑删除：0 正常 1 已删除'`
（三方言 DDL 都有），`TenantEntity` 继承的 `BaseEntity` 在 `deleted` 上标了 `@TableLogic`，
而全局配置里**没有**覆盖逻辑删除的默认值（`application.yml` 的 `mybatis-plus.global-config`
只有 `banner: false`）。

因此 `tenantMapper.selectById(id)` 生成的 SQL 自带 `deleted = 0` ——
**逻辑删除的租户在应用层就等于不存在**，走的就是 `0050` 修好的 `40002` 那一格，
不需要第二条判据。

实测（`TenantReferenceApiTest#shouldTreatDeletedTenantAsAbsent`：建租户 → `DELETE` 掉 → 往它里面建用户）
返 **`40002`**，绿。

这条值得单独钉住，理由是它的正确性**依赖一行离本域很远的注解**：
`@TableLogic` 在 `BaseEntity` 里、`@TableLogic` 的默认值与 DDL 的默认值（0 / 1）恰好一致、
全局配置恰好没被改过 —— 三者中任意一个变了，这个缺口就重新出现，
而它在四个域里的表现完全一样（都一样"静默放行"）。所以 `0050` 那格"未验证"关闭，
代价是一条用例。

### 二、顺着"可用"往下一格，撞见新的：租户**存在**、但**停用**

`bw_auth_tenant.status`（`ENABLED` / `DISABLED`）在全仓**只有一个读者 = 登录**：

```java
// AuthService#login
if (tenant == null || !Status.ENABLED.wireName().equals(tenant.getStatus())) {
    // 与"口令错误"同一个码：租户是否存在同样属于不该泄露的信息
    throw AuthResultCode.BAD_CREDENTIALS.businessException();
}
```

**登录先拒停用的租户，并且刻意返 `40101`（与"口令错误"同码）** ——
也就是说在登录侧，一个停用的租户与一个不存在的租户**被有意做成不可区分**。

（它也是**唯一**的读者：续期那条路不读它，见"未覆盖"第一条。
本轮只用到"新账号登不进来"这一半，那一半是成立的。）

而写侧不看这一列。`0050` 的 `assertExists` 只问"这个外键指得到东西吗"，
于是"租户存在但是停用"这一格**两头都放行**：

| 用例（修复前，源码 stash 回旧版、用例不动） | 旧代码 |
| --- | --- |
| 用户：指定一个**已停用**的租户建号 | **`code: 0`** |
| 角色 / 组织 / 用户组：同上 | **`code: 0`** |

**实测结果就是上面这张表**，四条全部 `code: 0` —— 数据被成功建出来了。

### 三、它的产物与 `0050` 修掉的那批是**同一个东西**

| | `0050`（租户不存在） | `0051`（租户停用） |
| --- | --- | --- |
| 新账号能不能登录 | 不能（`tenantCode` 映射不到任何租户） | 不能（登录先拒 `status != ENABLED`） |
| 能不能匹配上任何判定 | 不能 | 不能（判定两侧都限定 `tenant_id`，而那个租户没人进得来） |
| 占不占 `uk_bw_auth_user_tenant_username` | **占** | **占** |
| 建的人看没看到提示 | 没有 | 没有 |

差别只在**成因**：一个是"主键错"，一个是"状态错"。
`0050` 的背景里那句话在这里一字不差地成立 ——
"静默不可达的数据，正是本仓尽量不让接口制造的东西"。

### 四、仓里已经有同一条先例，而且租户是**更强**的那一档

`OrganizationService#resolveParent` 早就拒绝"挂到已停用的父组织下"：

> 父组织已被停用，不能在其下新增或移动到该节点：
> 停用的组织不再参与数据范围的路径求值，挂在它下面会得到一个算不出范围的分支

停用的组织只是**不参与范围求值**；停用的租户**连登录都进不去** ——
它下面的一切（用户、角色、组织、用户组）都没有任何消费者。
同一条规则，租户这一侧此前是空的。

### 五、为什么不能顺手塞进 `resolveTenantId`

四个域的 `resolveTenantId` **同时服务查询与新建**（每个域的两处调用点就是这两条路）：

| 域 | 查询调用点 | 新建调用点 |
| --- | --- | --- |
| `UserService` | `page`（`query.getTenantId()`） | `create`（`request.getTenantId()`） |
| `RoleService` | `page` | `create` |
| `OrganizationService` | `page` / `tree` | `create` |
| `UserGroupService` | `page` | `create` |

把状态判据塞进去，等于连"**查一个被停用的租户里现在有什么**"一起关掉 ——
而那恰恰是排查一个被停用的租户时最需要的信息。
所以这一格由调用方在 `create` 里**显式**问，位置本身就是这条边界的记录。

### 六、影响面如实说

`0050` 已经实测过：管理台的四个建表单一律**不传** `tenantId`（`web/` 下 `tenantId`
只出现在 `MeVO` 映射、会话类型与审计演练面板的路径参数里）。
所以这个缺口**不是从界面上点得出来的**，需要直接调接口 ——
与 `0050` 完全一样：是一个"持有 `auth:user:create` / `auth:role:create` 就能做、
且做完全程无提示"的动作，而 `admin` 持有全部权限。

## 决策

### 1. 新增 `TENANT_DISABLED(40920, "引用的租户已停用")`，与 `40002` 分成两格

两者是**同一个判据的两格**，但处置完全不同：

- `40002`（引用的租户不存在）→ "你传错了主键"；
- `40920`（引用的租户已停用）→ "你等它启用，或者换个租户"。

合并成一个码，调用方看不出该去改什么。这与 `0050` 决策 3 里
"`40402` 与 `40002` 刻意不合并"是同一条理由的延续 ——
只不过那一对区分的是"**我请求的**租户"与"**我引用的**租户"，
这一对区分的是引用对象的**两种不可用方式**。

放在 `409xx` 段（冲突）而不是 `400xx` / `404xx`：它说的是
"目标资源当前的状态不允许这个操作"，与 `40916` / `40918` / `40919`
（"仍被引用"）同一类 —— 都是**状态**问题而非**参数格式**问题。

### 2. 判据收进 `TenantService#assertAcceptsNewData`，与 `assertExists` 共用同一次查询

```java
@Transactional(readOnly = true)
public void assertAcceptsNewData(Long tenantId) {
    TenantEntity tenant = requireReferencedTenant(tenantId);
    if (!Status.ENABLED.wireName().equals(tenant.getStatus())) {
        throw AuthResultCode.TENANT_DISABLED.businessException(
                "引用的租户已停用，无法在其下新建数据：" + tenantId);
    }
}
```

`assertExists` 与它共用 `private requireReferencedTenant`（同一次查询、同一份文案）：
**分成两个方法不该让同一种输入出现两种答案** —— "租户不存在"这个输入在两个方法上
必须给出同样的码和同样的话，否则调用方按方法选码就成了新的坑。

**刻意分成两个方法而不是一个**：`assertExists` 回答"这个外键指得到东西吗"，
`assertAcceptsNewData` 回答"指到的东西现在能用吗"。只有**新建**路径需要后者。

选 `TenantService` 而不是新工具类，沿用 `0050` 决策 1 的理由 ——
这仍然是"租户的问题"，只是从第 1 格变成第 2 格；**属主不变**。

### 3. 只挂在四个域的 `create` 上，**不放进 `resolveTenantId`**

理由见背景第五节。这一条的代价是"四份调用"，收益是读侧不被误伤 ——
而四份调用**不会漂移**，因为它调用的是一个有名字有归属的方法
（`0050` 漂移的是"四份各自实现"，不是"四处调用同一个实现"）。
四份调用里任意一份漏掉，`TenantReferenceApiTest` 会先红（决策 5）。

### 4. 读侧**不挡**，并用一条用例把这条边界钉住

`shouldStillReadDataOfDisabledTenant`：停用之后按它的 `tenantId` 查列表仍返 `code: 0`。

这条不是"顺手测一下"，它是**这次改动的边界本身** ——
判据若被后来者"顺手"挪进 `resolveTenantId`，症状是平台侧连
"这个被停用的租户里有什么"都问不出来，而那条用例会先红。

### 5. 四个域断言**同一个码**，不只用户域

沿用 `0050` 决策 5：只测一个域的话，判据再被复制回各自域里、再漂移一次，
症状与这次一模一样。所以 `shouldRejectUserCreateInDisabledTenant` 与
`shouldRejectDisabledTenantInEveryOtherDomain` 一起钉住四个域。

### 6. 测试类承载两个 ADR，不新建文件

`TenantReferenceApiTest` 的题目本来就是"**引用的租户**"——
`0050` 是它的第 1 格（不存在），`0051` 是第 2 格（停用）。
分文件会让"这两格是同一个判据"这件事在文件层面就看不出来。

### 7. 顺带补 `server/README.md` 错误码表漏登记的 `40919`

那张表在 `0030` 新增 `40919`（组织仍包含成员）时没有跟着更新
（同批的 `40410` 也一直没在表里）。这不是本轮造成的缺口，但本轮要往同一张表里
加 `40920`，把 `40919` 一起补上比留一个"新码在表里、旧码不在"更不容易误读。

## 后果

**正面**

- 四个域不再能在一个**停用的租户**里造出没有任何消费者的数据；
  与 `0050` 合起来，"引用的租户必须可用"这条规则现在覆盖**两种**不可用方式，
  且**只有一个属主**（`TenantService`）。
- `0050` 那条"未验证"被关闭，且关闭方式是一条用例而不是一段推理 ——
  它依赖的 `@TableLogic` 在离本域很远的 `BaseEntity` 里，靠读代码是守不住的。
- **读侧不挡**这条边界第一次被写下来并有用例，而不是"碰巧没关掉"。
- 顺带核清了 `bw_auth_tenant.status` 在全仓**只有一个读者：登录**
  （连**续期**那条路都不读它 —— 见"未覆盖"第一条）。写侧此前完全不看它，
  这是本轮缺口的直接成因，也是"新增开关必问判定是否读它"那条家族规则的又一例 ——
  这次是"**状态列**没被写侧读"，而且它连读侧也没读全。

**负面 / 代价**

- 四个 `create` 各多一次租户查询（与 `0050` 那次是**同一次**：`assertExists`
  在 `resolveTenantId` 里已经查过一次，这里是第二次）。
  —— 可以合，但那要求把状态判据提前进 `resolveTenantId`，也就是把读一起关掉，
  不划算（背景第五节）。建号/建角色本来就是多语句事务，这一读不是主要开销。
- 停用租户从"能往里建数据"变成"不能"：如果有人用它做过"先冻结、再预置"的流程，
  这个流程现在被挡。如实说：**没有任何代码、文档或用例依赖过那个流程**，
  但这是本轮唯一一处**会让人少做成一件事**的改动。

**后续约束**

- 新加一个带 `tenant_id` 的表时，**新建路径**既要问 `assertExists`（在 `resolveTenantId` 里）
  也要问 `assertAcceptsNewData`（在 `create` 里）；漏掉后者会让这个缺口在新表上重开一次。
  这条写进了 `server/README.md` 的硬规则表。
- **改存量数据本轮不受此码约束**：`update` 路径不重新解析租户
  （四个域的 `tenantId` 本来就不可改，见 `docs/api/README.md`）。
  也就是说"停用一个租户之后，里面已有的行仍能被改名/停用/删除"。见"未覆盖"。

## 未覆盖

- **停用租户**对**已经在用的人**不生效 —— 也就是"停用"这个动作的效力比它看起来小（**本轮实测，未处理**）。
  本轮的判据（"新建时租户必须启用"）依据的是"停用租户里新造的账号登不进来"，
  这条是成立的；但**反过来那一半不成立**：停用一个租户**只挡新登录**。
  一次性的探针（用完即删，不入库）实测：

  | 停用之后 | 结果 |
  | --- | --- |
  | 重新登录 | `40101`（拒了） |
  | 用停用前的刷新令牌**续期** | **`code: 0`（通了）** |
  | 用停用前的访问令牌调 `/me` | **`code: 0`（通了）** |

  根因在同一行代码里，而且**不对称就在那一行上**：

  ```java
  // AuthService#refresh
  if (tenant == null || user == null || !Status.ENABLED.wireName().equals(user.getStatus())) {
  ```

  **用户判了状态，租户只判了"非 null"。** 而 `AuthTokenFilter` 是**无状态、不查库**的
  （"令牌自带 userId / tenantId，过滤器只做密码学校验"），访问令牌本身有 2 小时有效期；
  刷新令牌则是**轮换**的（每次续出一个新的、有效期重新起算）—— 这三件事合起来意味着：
  **只要一个会话在被使用，它就永远续得下去，与租户的 `status` 无关。**

  这是本仓那一族"**状态列没有读者**"的又一例（`0022` 停用角色成假按钮、
  `0024` 停用用户组一直在产生权限），只是这次没有读者的是**续期**那条路。
  它本轮**不修**，因为修它必须先回答下面那条 —— 两条是耦合的。
- **"停用自己所在租户"这件事，本轮先证伪了它没那么急（**与上一条耦合**）**。
  一度以为这是一个"一次点击把所有人锁在门外、恢复只能改库"的陷阱（与 `40917`
  保护的那件事同形）。实测之后**不成立**：停用之后既有会话照常续期，
  也就是说**恢复入口还在**（拿着令牌就能把 `status` 改回来）。
  但如果上一条被修（续期也判租户状态），这个陷阱就**立刻成立** ——
  那时"停用自己所在租户"= 所有会话在访问令牌到期后失效，而重新登录被拒 ⇒ 只能改库。
  所以两条必须一起决定，至少要回答：**① 停用到底意味着"不许新登录"还是"现有会话也下线"；
  ② 后者成立时，谁来重新启用它（本仓没有"租户之外"的平台账号）。**
  这一次轮的判据只依赖"新账号登不进来"，与这两个问题的答案无关，因此可以先行。
- **在停用的父租户下建子租户**：`TenantService#resolveParent` = `requireTenant`，
  只查存在性（`40402`），不查父租户的 `status`。
  形状与组织那一侧相同（`OrganizationService#resolveParent` 拒绝停用的父组织），
  **但后果不同**：停用的父租户不影响子租户的用户登录（登录只看**自己**那个租户的 `status`），
  所以子租户仍然完全可用 —— 这不是"造出不可达数据"，而是"树里有一个停用的中间层"。
  要不要挡是另一个判据，不与本轮同格。
- **改存量数据**（见"后续约束"）：停用租户里已有的行仍可被更新/删除。要挡的话，
  得先回答"停用一个租户到底是什么意思"：是"只读冻结"还是"整租户下线"。
- **接口能不能指定别家（存在的、启用的）租户**：仍是 `0050` 未覆盖 1 的正题，
  需要产品决定（平台级管理台 vs 租户级管理台）。本轮**没有碰**它。
- **`TENANT_DISABLED` 的文案不被界面消费**：管理台不传 `tenantId`，
  所以这个码在界面上不可达；`platform-admin` 的租户表单里也没有"停用"后的写入路径
  （停用是后端能力，界面只读回显 `status`）。契约与文档同步了，界面同步**没有落点**。
- **`Status.parse` 对租户的宽容**：`TenantService#resolveStatus` 把无法识别的值
  当成 `ENABLED`（与组织相反，组织是"状态非法就报错"）。本轮没有改它 ——
  它是 `0009` 族里已记录的刻意差异，与本轮判据无关。
