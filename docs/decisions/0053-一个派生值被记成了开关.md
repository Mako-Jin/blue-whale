# 0053. 一个派生值被记成了开关 —— 订正答案表里的一格，并统一两侧的重算口径

- **状态**：已采纳
- **日期**：2026-10-14
- **决策者**：舰长

## 背景

`0052` 收尾时把 `has_child`（租户 / 组织）标成"**本轮没有核**"，并把它归进另一类判据
（缓存一致性），留给下一轮。本轮核它。

开局就有点难堪：`0052` 刚刚用一整节论证**「哪些接口是公开的」不能靠读文本回答**
（三次源码扫描给出三个不同答案，最后只能去问框架的映射表），
而它自己那张"下次不必再撞"的答案表里，`has_child` 那一格正是**读出来的** ——
只不过那次读的不是文本，是**邻接关系**。

## 一、订正：两处都写着"被删除守卫读"，而守卫读的是别的东西

`0052` 里有两处这样说：

1. 背景那张对照表的这一行：

   ```
   | has_child（租户 / 组织） | 删除守卫 | 仍可被删（守卫失效） |
   ```

2. 「未覆盖」第 6 条：`has_child`（租户 / 组织）是冗余列，只在写路径维护、
   **只被删除守卫读**。

事实是两处 `delete` 的守卫都是**真查一次** `parent_id` 的计数，与这一列无关：

```java
// TenantService#delete
Long childCount = tenantMapper.selectCount(Wrappers.<TenantEntity>lambdaQuery()
        .eq(TenantEntity::getParentId, id));
if (childCount != null && childCount > 0) {
    throw AuthResultCode.HIERARCHY_CYCLE.businessException("该租户下仍有子租户，请先处理子租户");
}
```

```java
// OrganizationService#delete —— 同一句，另外多一道成员守卫（40919）
```

`git log -S "getHasChild"` 在 `TenantService` 上只命中**一笔**：建库那一笔
（`b76fed7`，认证域的第一个竖切）—— 而同一笔也正是引入 `eq(getParentId, id)` 的那一笔。
也就是说这个列**从第一天起就没有进过任何守卫**，"守卫失效"这个推演从来没有对应的事实。

改完之后，全仓 `getHasChild()` 的**读取点只剩三处**，没有一处在守卫里：
两个 `toVO`，加组织侧 `updateColumns` 里的一次原样回传。

## 二、那一格是怎么错的：把邻接关系当成了调用关系

`has_child` 的列注释（三方言 DDL 一致）写的是"是否有子节点：0 否 1 是"；
紧挨着它的方法体就是 `delete`，而 `delete` 里第一件业务动作就是数子节点。
于是"守卫读它"这句结论，是**从两件事挨着**推出来的。

这与 `0052` §三 是同一个错误的第二次发生，只是形态更隐蔽：那里错在"以为读源码能代替问框架"，
这里错在"以为代码相邻就是调用"。两处翻在同一个地方 ——
**"谁读了这一列"是一个只能由符号引用回答的问题**：

- 注释写的是"它是什么"，不是"谁在读它"；
- 相邻只说明它被放在这里，不说明它被调用；
- 而正确的做法**比错误的做法更便宜**：`grep -rn "getHasChild()"` 一次得到三行，全是出参装配。

还有一个更值得记的推论：**这一格写错了，不会有任何测试变红。**
守卫读不读这个列，两种实现给出**完全相同的可观察行为**（因为这个列始终与真值一致 ——
下一节那个例外是另一件事）。所以它只能靠核代码 + 本片记下来，**没有任何断言可以表达它**。

## 三、`has_child` 的真实状态：写者有、读者只有出参、消费者零

| 列 | 写者 | 读者 | 消费者 |
| --- | --- | --- | --- |
| `bw_auth_organization.has_child` | `create` 落 0 + `refreshHasChild`（建 / 移 / 删三处） | `toVO` | **无** —— 只有 `OrganizationApiTest` 与 `scripts/verify-admin-permissions.mjs` 的断言 |
| `bw_auth_tenant.has_child` | `create` 落 0 + `markParentHasChild`（只 0→1，见下节） | `toVO` | **无** |

所以它属于**「只存不用」**那一族，与 `resourceVersion` 同款（有读者、无消费者），
而**不是** `0052` 数出来的"零读取方"那四个。

但要如实说清它与那四个的差别：**它被真实计算过，也被真值校验过** ——
`0030` 用来抓出"`updateColumns` 漏写 `parent_id`"的那条断言，
抓的正是"移动后**原父级的 `hasChild` 应归 `0`**"。也就是说：
一个没有消费者的字段，曾经生产过一个真实缺陷的证据。

`0052` 那句"一个恒为 1 的展开箭头点开是空的"，描述的是一个**当前还画不出来**的箭头：
`web/**` 对这一列**零读取**（除注释与生成物 `schema.d.ts`）。

## 四、租户侧不只是没有读者 —— 它写的值本身会陈旧

`TenantService#markParentHasChild` 只做 0→1：

```java
if (parent == null || (parent.getHasChild() != null && parent.getHasChild() == 1)) {
    return;                       // 已经是 1 就直接返回
}
parent.setHasChild(1);
```

反向不重算。它给的理由写在 `OrganizationService` 的类注释里
（"与 `TenantService` 的三点差异"第 2 条）：**"租户树没有移动，层级极少变"**。

但**删除**在租户侧是存在的，而删除正是唯一能把这个值从 1 变 0 的动作 ——
**理由不覆盖它要解释的事实**。可复现的后果：建一个子租户、再把它删掉，
父级从此一直返回 `hasChild: 1`，出参对一个**不存在的**子节点说"是"。

`0052` 的结论是"**一份能给出相反结论的清单，比没有清单更危险**"。
这条从"清单"推广到单个字段同样成立 —— 它现在就在对外说一句假话，只是恰好没人听。

## 五、决策：统一到"与真值同源"，并补上缺的那条断言

### 1. 租户侧换成与组织侧同形的真重算

`markParentHasChild` → `refreshHasChild`：数一次 `parent_id`、无条件 `set`。

理由不是"顺手把两边弄一样"，而是：派生列一旦允许"只在某一个方向更新"，
它的正确性就变成一条**需要记住**的规矩；真重算把它还原成"这一列由什么算出来"这**一个事实**。
顺带删掉 `delete` 里那次多余的 `selectById(parent)` —— 旧签名要求传一个完整实体，
于是为了取父级还得先把它查出来。

### 2. `OrganizationService` 的"三点差异"改成两点

并把"`has_child` 为什么不再算差异"留一句在注释里（旧理由与事实不符）。
需要记住的差异少一件。

### 3. 补两条断言（新 `TenantHierarchyApiTest`）

- **有子租户时删父级 → `40913`。** 这条守卫**在租户域此前零用例**，
  而 `HIERARCHY_CYCLE` 在主代码里有 **13 处用法**（8 处"成环／自挂" + 5 处"删除守卫"）、
  在用例里此前一条都没碰到**租户**那一处；租户侧唯一被用过的那次是
  `TenantReferenceApiTest` 的夹具"删一个租户"，而那条路的期望是**成功**。

  顺带把"哪个域有断言"一次数清（**下一节会用到这张表**）：

  | 域 | 删除守卫（有子节点 → `40913`） | 用例 |
  | --- | --- | --- |
  | 组织 | `OrganizationService#delete` | ✓ `OrganizationApiTest`「有下级（40913）或有成员归属（40919）时拒绝删除」 |
  | 资源 | `ResourceService#delete` | ✓ `ResourceApiTest`「有子资源时拒绝删除（40913）」 |
  | 用户组 | `UserGroupService#delete` | ✓ `UserGroupApiTest`「删除守卫：仍有成员 40918；仍有子组 40913」 |
  | 角色 | `RoleService#delete` | **✗ 没有**（`RoleApiTest` 里 `40913` 零命中） |
  | 租户 | `TenantService#delete` | **✗ 此前没有** —— 本片补上 |

- **父级 `hasChild` 按真值重算：建两个子租户，删掉一个仍须为 1，删掉最后一个才归 0。**
  这条比"删完归零"强：一个"删除时把父级顺手置 0"的实现能通过只建一个子节点的用例，
  却会把"还有兄弟节点"说成没有。

**用扰动证明它不是空转**（照 `0040` 的做法）：把 `delete` 里那次重算摘掉
（等价于改动前的行为），第二条用例当场红，消息就是它自己的话：

```
删掉最后一个子租户之后，父级 hasChild 应为 0 ==> expected: <0> but was: <1>
```

如实记一句：**第一条用例在扰动下照常通过** —— 它钉的是守卫，而守卫从来不看这个列。
两条用例红的条件不同，正是它们各自钉住不同事实的证据。

## 六、不做的事

- **不删列、不从契约里摘字段。** 它是 `0030` 那条断言的载体：
  删掉它，"`parent_id` 漏写"这个真实缺陷就少一条能抓它的断言。
- **不顺手把它接进界面。** `0030` 已经留过这个口子（"要不要把 `hasChild` 也放进树节点，
  等有人真的需要在树上按它做判断时再说"）。本轮**不触碰界面** ——
  一个还没有人画的箭头不是本轮的判据。

## 后果

**正面**

- `0052` 那张"下次不必再撞"的表里，**已经发现有一格是错的**（本片订正了它；
  其余各格仍待逐格核，见未覆盖）；而"不靠读文本"这条规矩
  有了**第二个案例**，这次的案例在它**自己**身上。
- 租户树的父级 `hasChild` 不再对不存在的子节点说"是"（一条 API 层面可观察的错值）。
- 租户域那条 `40913` 守卫第一次有断言。
- 两侧口径同形 ⇒ `OrganizationService` 的类注释少一条差异；全仓 `getHasChild()`
  的读取点收敛到三处，且全在出参装配上。

**负面 / 代价**

- 租户建 / 删各多一次 `selectCount`；原先"父级已是 1 就直接返回"省下的那次写入也不再省。
  如实说：这是**为了少记一条规矩**付的查询 —— 而它换来的"规矩"是可验证的。
- 多一个测试类与两处需要与代码同步的断言。

**后续约束**

- **任何"某列被谁读"的说法，必须用 `getXxx` 的调用点核**（`grep -rn "getXxx()"`），
  不能用列名、注释或**邻接关系**核。这一条是本轮最贵的教训。
- `has_child` 与 `org_level` / `code_path` / `full_name` 同级：
  **派生列 —— 不入参、不参与判定、由 `parent_id` 真值算出。**

## 未覆盖

- **角色侧的 `40913` 整个没有断言**（本片顺带数出来的，见第五节那张表）：
  `RoleService` 既用它拦"有子角色"的删除，又用它拦"把角色挂到自己的下级下"，
  而 `RoleApiTest` 里 `40913` **零命中** —— 五个域里唯一一个两条形状都没钉住的。
  本片**没有处置**它，理由与 `0052` 对 `allow_register` / `allow_add` 的处理一样：
  它是撞上的、不在本片射程（角色树压根没有 `has_child` 这一列）。
  但要如实说清它与租户侧那条的差别 —— 租户那条**必须**在本片补，
  因为本片要订正的那个错误说法（"`has_child` 被删除守卫读"）指的正是它；
  角色那条与本片的判据无关，补它属于扩大射程。
- **界面仍未消费 `hasChild`**：展开箭头要不要按它画，`0030` 留的口子仍未动（本轮刻意不碰）。
- **同一事实有两份表示**：树接口给 `children`、详情与列表给 `hasChild`
  （`0030` 未覆盖里的同一条）。本轮没有合并。
- **`has_child` 与逻辑删除的关系只做了读注解确认**：子节点被逻辑删除后计数会把它排除
  （`@TableLogic` 让 `selectCount` 自带 `deleted = 0`），本轮靠读注解确认，
  没有专门用例钉住 —— 这与本片刚刚立下的规矩（"谁读这一列"要核调用点）属于同一类风险。
- **其他表的 `has_*` 列没有扩大扫描范围。**
- **`0052` 那张表的其余各格没有被逐格复核。** 本轮是"撞上了就核"，不是"逐格核"。
  按本轮的教训，那张表**值得逐格核一遍** —— 尤其"读者"一栏，
  它是整张表里最容易由邻接关系推出来的一栏。
