# 0064. 消歧手段的普查 —— "名字旁边必须有唯一标识"为什么仍然没有机械守卫

- **状态**：已采纳
- **日期**：2026-10-15
- **决策者**：舰长

> 领的是 `0061`「未覆盖」第 3 条，也是 `0063`「未覆盖」第 1 条：**"名字旁边必须有唯一标识"
> 是纸面规则** —— 新加一个展示名字的地方，漏了编码不会有任何东西变红。
> `0062`-2 已由 `0063` 那个守卫关闭，同一组里就剩这一处。
>
> 本轮先按 `0061` 那轮的同形扫法把**全部渲染位**扫了一遍（不再靠偶然撞见），
> 补掉查出的**两处缺口**；然后认真评估"能不能像 `0060` / `0063` 那样机械化" ——
> **结论是不能**，本轮把"为什么不能"连同**穷举清单**一起写下来。
> 这是一条**被否掉的守卫**：否掉它本身是决策，理由是可反对的。

## 背景

`0061` 立的规则：

> **层级的语义就是"同一个名字可以在不同上级下复用"。身份由编码承担，不由名字承担。**
> 消歧的职责落在"名字旁边有没有唯一标识"上，**不落在"禁止同名"上**。

`0061` 那轮是**人工**扫的，范围明确写着只覆盖"`platform-admin` 里 `roleName` / `groupName`
的字面出现位置"，**经变量间接渲染的名字不在射程内** —— 也就是说，那次扫出一个缺口
（用户页「角色来源」的来源用户组列）多少带点运气。本轮把它补成穷举。

## 一 普查：全部名字渲染位（穷举）

扫法：`web/platform/**/*.tsx` 里所有渲染 `*Name` 的 JSX 文本节点（不含 `className` /
`name=` / `placeholder` / `value=` / `data-testid` / `title=` 这些非展示位），
逐个看**同一个展示单元**里有没有唯一标识。共 **25 处**（其中两处是本轮新修的，已标出）：

| 位置 | 渲染的名字 | 同单元 / 邻列的标识 | 结论 |
| --- | --- | --- | --- |
| 用户页 · 用户列表「姓名」列 | `user.displayName` | 邻列「登录名」= `user.username` | ✓ |
| 用户页 · 组织归属「组织」列 | `org.orgName` | 同单元 `org.orgCode` | ✓ |
| 用户页 · 组织归属「全称」列 | `org.fullName` | 全路径自带消歧 | ✓ 出界 |
| 用户页 · 组织归属「岗位」列 | `org.positionName` | 自由文本，不指认对象 | ✓ 出界 |
| 用户页 · 数据范围「主岗组织」 | `primaryOrgFullName` | 同单元 `#{primaryOrgId}`；全路径自带消歧 | ✓ |
| 用户页 · 角色来源「角色」列 | `roleName` | 同单元 `roleCode` | ✓ |
| 用户页 · 角色来源「来源用户组」列 | `groupName` | 同单元 `groupCode`（`0061` 补） | ✓ |
| 资源页 · 资源列表「名称」列 | `resourceName` | 邻列 `resourceCode` | ✓ |
| 资源页 · 资源树节点 | `resourceName` | 同单元 `resourceCode` | ✓ |
| 资源页 · 上级资源下拉项 | `resourceName` | 同项 `resourceCode` | ✓ |
| 角色页 · 角色列表「名称」列 | `roleName` | 邻列 `roleCode` | ✓ |
| 角色页 · 成员抽屉「成员」列 | `memberName` | 同单元 `#{memberId}` | ✓ |
| 角色页 · 授权资源下拉项 | —（只渲染 `resourceCode`） | 标识本身 | ✓ |
| 组织页 · 组织树节点「名称」 | `orgName` | 同单元 `orgCode` | ✓ |
| 组织页 · 组织树节点「负责人」 | `managerName` | **原状无标识** | **✗ → 本修** |
| 组织页 · 上级组织下拉项 | `orgName` | 同项 `#{orgId}` | ✓ |
| 组织页 · 负责人下拉项 | `displayName` | 同项 `#{userId}` / `username` | ✓ |
| 组织页 · 成员抽屉「成员」列 | `memberName` | 同单元 `#{memberId}` | ✓ |

只是那个展示位**没渲染它**。

## 二 修：两处缺口

| 落点 | 原状 | 改动 |
| --- | --- | --- |
| `OrganizationTreeNode` | 只有 `managerName`（`OrganizationVO` 早有 `managerId`） | **加 `managerId`** + 契约链三步 |
| 组织树节点「负责人」 | `负责人 {managerName}` | `负责人 #{managerId} {managerName}` |
| 审计台流水「操作人」列 | `{operatorName}`（`AuditLogVO.operatorId` 早就有，详情在用） | `{operatorName} #{operatorId}` —— 与详情同形，**无需后端改动** |

两处都补了用例，并都做了**扰动验位**（去掉标识后用例变红）。

## 三 决策：这条规则**不机械化**，改为"穷举清单 + 纸面规则"

认真评估过能不能像 `0060` / `0063` 那样写一个零前置守卫。**不能**，理由是具体的：

**1. `0060` / `0063` 能成立，是因为它们锚定的东西是"无歧义的 token 形状"** ——
`*_EXISTS` 码的引用、`CREATE UNIQUE INDEX` 的列清单。正则扫到就是扫到，扫不到就是没有。

**2. "名字旁边有标识"是 JSX 树 + 展示语义的属性，不是 token 形状。** 实测三种口径都不行：

| 口径 | 结果 |
| --- | --- |
| "`*Name` 表达式的**同一行**还有别的可见内容 ⇒ 必须有标识" | 28 处命中里 **≥4 处误报**（表单 label、自由文本 `positionName`、演练文本模板串、`fullName` 全路径） |
| "`*Name` 表达式要有**同单元兄弟节点**里的标识" | 需要真解析 JSX 树；正则做不到，用正则会**假阴**（跨行兄弟节点扫不到） |
| "把 **所有** `*Name` 出现在 JSX 里的位置**登记**一遍" | 机械枚举出 **47 处**，其中过半是表单输入、`Dialog` 泛型 prop、label 等噪声 ⇒ 登记 47 条里 20+ 条是噪声，**维护成本 > 收益** |

**3. 一个守卫若会误报，它的下场是被 `// @ts-ignore` 掉。** `0063` 那篇写着它的价值前提是
"**语法级、逐字符可判、不依赖任何约定，因此不误报**" —— 这条规则给不了这个前提。
**强行机械化的守卫比没有守卫更糟**：它会训练人去忽略它。

⇒ **决策：保留纸面规则**，但把上面那张**穷举表**写进本篇 ——
"查有没有漏"从"扫一遍看"（无界）变成"对着这张表走一遍"（有界、可完成）。

## 四 怎么用这张表

新加一个**展示名字**的位置时：

1. 在 §一 的表里加一行，填上"同单元 / 邻列的标识"那一栏；
2. 填不出标识的，问两个问题：**这个名字指认一个对象吗**（不指认 ⇒ 出界，如自由文本
   `positionName`）、**它自己就带消歧信息吗**（带 ⇒ 出界，如 `fullName` 全路径）；
3. 两个都不是 ⇒ **漏了标识，补上**，并补用例。

**改名 / 删位置时同步删表行。** 表是纸面的，会腐烂 —— 但腐烂的形态是"表里有、
代码里没有"，人工一眼可见；而机械守卫若误报，腐烂的形态是"没人再看它"，
**更隐蔽**。这是本决策选纸面的第二层理由。

## 未覆盖

1. **表是手工维护的，会腐烂。** 没有东西保证"新加渲染位一定来登记" —— 这正是
   `0063`-2 那一类问题的原样复现。接受它：本仓还没有"前端渲染位"的机械枚举口径，
   造一个的成本（见 §三-2）高于它守住的东西。
2. **只扫了"名字"（`*Name`）。** 别的"指认对象的展示"（如只渲染了 id 却没渲染名字、
   或渲染了 `displayName` 却没渲染 `username`）不在射程内 —— 判据是同一句
   （"能不能区分两个不同对象"），但扫法不同。
3. **变量间接渲染的名字扫不到。** 名字先存进变量、再在别处渲染（如
   `const label = role.roleName`），本轮的正则口径看不见。已知、未堵。
4. **"邻列"是人工判断的。** 表里"邻列 `tenantCode`"这类结论靠人读表头 ↔ 单元格对应关系，
   不是机械判定的 —— 这是 §三 那个否掉的守卫的延续。
