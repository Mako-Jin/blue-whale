# 0068. 搜索关键词的规范化

- **状态**：已采纳
- **日期**：2026-10-15
- **决策者**：舰长

> 领的是 `0067`「未覆盖」第 3 条：**关键词的规范化各域不一致** ——
> "4 处 `normalize`（含 trim：组织 / 角色 / 用户组），3 处只判空不 trim（用户 /
> 租户 / 资源），日志另有 `hasText`。"
>
> 核完的结果：**它不是"两种风格"，而是一处会分叉的行为** —— 同一条关键词
> 在组织域搜得到、在用户域搜不到，两个域的同一条断言一个绿一个红（实测见下）。
> 更要紧的是那条用来给它开脱的话 —— "前端已经 trim 了" —— **在第七个入口上
> 当场不成立**：客户端日志那个搜索框一次都不 trim，而组织域根本没有搜索框。

## 背景

### 1 射程：7 处搜索、两种口径

`keyword` 出自 `Query` 对象，共 **7 处搜索、15 个列条件**。取值方式分两种：

| 域 | 列 | 取关键词的方式 |
| --- | --- | --- |
| 用户 | `username` · `display_name` · `email` | 原文（只判空） |
| 用户组 | `group_code` · `group_name` | `normalize`（trim + 空转 `null`） |
| 租户 | `tenant_code` · `tenant_name` | 原文（只判空） |
| 角色 | `role_code` · `role_name` | `normalize`（trim + 空转 `null`） |
| 资源 | `resource_code` · `resource_name` | 原文（只判空） |
| 组织 | `org_code` · `org_name` · `full_name` | `normalize`（trim + 空转 `null`） |
| 客户端日志 | `message` | 原文（只判空） |

两种口径对 `null` 与**只含空白**的处置一致（都退化成"不过滤"），
唯一的差别在**两端带空白**时。

`normalize` 是同一份实现（`null` 进 `null` 出、全空白也出 `null`、否则 `trim()`）
**在 5 个 service 里各复制了一份** —— 除了上面三个域，`ResourceService` 与
`OrganizationMemberService` 也各有一份，用于 `parentCode` / `category` / 成员等过滤值。

### 2 "前端已经 trim 了"在第七个入口上不成立

| 入口 | 有没有搜索框 | 前端 trim？ |
| --- | --- | --- |
| 用户 / 用户组 / 租户 / 角色 / 资源 | 有 | **有**（`keywordInput` 中间态，提交时 `setKeyword(keywordInput.trim())`） |
| 组织 | **没有** | —— |
| 客户端日志 | 有 | **没有**（逐键上送，`onChange` 直接改 filters，请求时原样带出） |

组织页没有搜索框是**刻意的**：它只有树视图，页面顶部写着理由（"再渲染一遍同样的行，
只能得到一份按关键字筛过的平铺列表 —— 而它恰好丢掉了唯一的有效信息（层级）"）。
契约里那个"按编码 / 名称 / 全称搜索"的分页接口是**给 API 调用方**用的，
前端没有调用它。

⇒ 所以 `0066` 里"前端只做 `.trim()`"那句，说的是"前端没有做本地过滤"
（这个结论仍然成立），但读成"这些入口都被前端 trim 过"就不对了；
`0067` 的"前端六个搜索框（… / 资源 / 组织）"也把组织算了进去。

## 一 实测：两条只差一个域的同形断言

照本仓"先写能红的用例"的做法，先加 `SearchKeywordTrimApiTest`（4 例、跨 profile、
不 `@Transactional`），**不改代码**跑一次 —— 读数是 **2 红 2 绿**：

| 用例 | 改前 | 改后 |
| --- | --- | --- |
| 用户域：`"  <词>  "` 应当搜得到 | **红**（命中 0 条） | 绿 |
| 组织域：同一条关键词同样该搜得到 | 绿 | 绿 |
| 纯空白关键词 = 不过滤（两域同义） | 绿 | 绿 |
| 只吃两端、不吃中间（`a b` 里的空格是它的一部分） | **红**（命中 0 条） | 绿 |

两条红都在用户域，而**同形的组织域那条是绿的** —— 这就是"各域口径不一致"的现场证据，
不需要再靠读代码推断。第 4 条那条红也是同一个根因（它的第一条断言同时依赖"两端被吃掉"）。

第 2 条在改前就是绿的，它的价值不在"改前红"，而在**它是对照组**：
把组织域也改成不 trim，它会红。第 3 条是**回归钉** —— 把规范化下沉到公共实现时，
最容易顺手弄坏的就是"空白关键词"这一支（变成"搜一个空格"）。

## 二 决策

1. **规范化的真值来源放在 `KeywordLike.pattern()` 里，不放调用方。**
   后端是权威边界：API 调用方、脚本、将来的别的客户端都不走前端那一层，
   "前端已经 trim 了"不能当契约用（第 2 节已经证明它在两个入口上不成立）。
   而 `pattern()` 本来就是"关键词进 SQL 之前的预处理"的唯一入口。

2. **吃掉两端空白，不吃中间。** 理由不是"顺手清一下"，而是**这一处的差异
   不承载任何区分能力**：`LIKE '%…%'` 是包含匹配，前后空白没法用来表达
   "我要找以空格开头的那条"，它只能造成"在某些页面上搜不到"。
   相反 `a b` 里的空格是关键词的一部分，删掉就变成搜另一个词了（用例 4 钉这一条）。

3. **`null` 与只含空白 = "没有这个过滤条件"**（返回 `null`，条件不拼进 SQL）——
   与两种口径改前的行为都一致，不变。

4. **7 处取值形态统一为 `pattern(query.getKeyword())`**：原本走 `normalize` 的
   三处删掉那层（`normalize` 本身保留，它还给 `status` / `category` / `orgType` 用）。

5. **前端日志页在发请求时 trim，不在 `onChange` 里 trim。**
   它是逐键上送的，输入过程中 trim 会把用户刚敲下的空格当场吃掉（值与光标都会跳）。
   这一条是"让请求本身就干净"、并与另外五个管理页对齐 —— 不是规范化的真值来源。

**没有采用的两条路**：把规范化留给前端（上面已否）；把两种口径都保留、
只写清楚"为什么有的 trim 有的不 trim"（写不出理由 —— 差异不承载区分能力，
它只是历史）：后者会让每一个新加搜索框的人重新掷一次骰子。

## 三 落地

- `KeywordLike.pattern()`：先 `trim()`，空则返回 `null`，再走原有的转义。
  类注释里加一节"关键词的规范化也在这里"，写明"调用方一律直传"。
- `OrganizationService` / `RoleService` / `UserGroupService`：删掉 `normalize(query.getKeyword())`
  那一层局部变量，改为直传；同时把"先取局部变量"那段长注释挪到它真正描述的
  `status` / `category` 那几行之前（它讲的是 `eq(条件, 列, 值)` 的实参无条件求值，
  与关键词无关 —— 留着会让人以为 `pattern(...)` 那行也在取局部变量）。
- 7 处 service 的注释统一成一句，并把 `decisions/0068` 挂上。
- 新增 `SearchKeywordTrimApiTest`（4 例 · 跨 profile · 不 `@Transactional`）。
- 前端 `platform-log-console`：新增 `cleanFilter()`，`level` / `namespace` / `keyword`
  三个过滤值在发请求前过一遍两端空白。

**注意 `level` / `namespace` 也一并 trim 了**，尽管它们不是关键词：它们与日志页的
搜索框在同一排、同一次改动里，留着不 trim 等于在同一屏里再制造一处"这个框吃空格、
那个框不吃"。它们在后端是**精确匹配**（`eq`）而不是 `LIKE`，
所以后端这一轮**没有**顺带把它们也规范化 —— 那是另一件事，见「未覆盖」。

## 扰动验位

- **改代码前**跑那 4 例 ⇒ 2 红 2 绿（上表）——"没有规范化"这一侧的读数。
- **改代码后**跑 ⇒ 4 绿。
- 改动的实质就是"在 `pattern()` 里加一个 `trim()`"，所以这两次读数合起来
  就是这次扰动验位：**去掉实现（= 改前）必红，加上实现（= 改后）必绿**。
- 另外两条是靠**结构**保证的，不靠这一次读数：把组织域也改成不 trim ⇒ 用例 2 红；
  把"空转 `null`"去掉（改成 `keyword.isBlank()` 之外还返回空串）⇒ 用例 3 红。

## 后果

**正面**

- "关键词长什么样"只剩一个真值来源：`KeywordLike.pattern()`。新加一个搜索框时，
  取值一律直传，不需要再问"这个域要不要 trim"。
- 第七个入口（客户端日志）此前**真的搜不到**两端带空白的词（从别处复制粘贴
  几乎必经这一手），现在两域行为一致。
- 组织 / 角色 / 用户组三处少了一层冗余的 `normalize`，"删掉它会不会改变行为"
  这个疑问随之消失（`normalize` 仍在，但只服务于别的过滤值）。

**负面 / 代价**

- **行为变化**：用户 / 租户 / 资源 / 客户端日志四个域，两端带空白的搜索从
  "搜不到"变成"搜得到"。这是本次的目的，但它**是一次对外可见的行为变化** ——
  如果外部调用方此前依赖"我传 `" a "` 就只匹配含空格的"，那是不成立的假设
  （`LIKE '%…%'` 下没法表达这个意图）。
- `trim()` 的口径与改前**不完全相同**：改前 `pattern()` 用的是 `isBlank()`
  （Unicode 空白，含全角空格 U+3000），改后是 `trim()`（只吃 `<= U+0020`）。
  于是"只含全角空格的关键词"在四个域上从"不过滤"变成"搜一个全角空格"。
  统一到 `trim()` 是为了与三处 `normalize` 一致（它们本来就是 `trim()`），
  见「未覆盖」。
- 前端多了一处 `cleanFilter()`。它不改变行为（后端也会吃掉），
  只是让请求参数干净、并与另外五个页面同形。

**后续约束**

- 新加搜索框：后端直传 `query.getKeyword()`，前端在提交 / 发请求时 trim，
  **不要在 service 里再 trim 一遍**（`KeywordLike` 已经做了）。
- 改 `KeywordLike.pattern()` 的规范化口径时，记得前端 JS 的 `.trim()` 与
  Java 的 `trim()` 覆盖面不同（见「未覆盖」第 2 条）。

## 「未覆盖」

1. **达梦未实测。** 本篇的改动是 Java 侧的 `trim()`，不落到 SQL 上，
   所以不像 `0067` 的 `ESCAPE` 那样需要三方言各验一遍；但"规范化之后的模式串
   在达梦上仍然按字面量比"这条依赖 `0067` 的结论，而 `0067` 的达梦验证本身还没做。
2. **`trim()`（Java）与 `.trim()`（JS）与 `isBlank()` 的覆盖面三者不同。**
   Java `trim()` 只吃 `<= U+0020`；JS `.trim()` 吃 WhiteSpace + LineTerminator
   （含 U+3000）；Java `isBlank()` 用 `Character.isWhitespace`。本轮统一到
   Java `trim()`（与三处既有的 `normalize` 一致）。若要把 Unicode 空白一起吃掉，
   得同时改 `normalize`、`pattern()` 与前端，**未做** —— 目前的影响面是
   "只含全角空格的关键词"，四个域的行为从"不过滤"变成"搜一个全角空格"。
3. **非关键词的过滤值仍然不 trim。** 各域的 `status` / `category` / `resourceType` /
   `parentCode` / `orgType`，以及日志域的 `app` / `level` / `namespace` / `traceId` /
   `sessionId`（走 `hasText()` 判空但把原值交给 `eq`）—— 它们在前端**已经**被 trim
   （日志域经本次新增的 `cleanFilter()`），但后端这一层没有：API 直接调用时
   `?status=%20ACTIVE%20` 匹配不到。**这是另一件事**（精确匹配字段的规范化），
   射程约 20 处取值，未做。
4. **`normalize` 仍有 5 个副本。** 它们是同一份实现（已逐个核对同形），
   服务于上面第 3 条里的那些过滤值。本轮没有把它们上收 —— 上收的对象应当是
   "所有过滤值的规范化"，那是第 3 条那件事的一部分。
5. **只有用户域与组织域有断言。** `KeywordLike` 目前没有单元测试 ——
   本仓 4 个 `sts-common-*` 模块都没有测试基建，为一个纯函数破例引入测试依赖
   不划算；语义由两个域的跨 profile 用例在真实路径上钉住。
   用户组 / 租户 / 角色 / 资源 / 客户端日志五处共用同一实现，但没有各自的用例
   （与 `0067`「未覆盖」2 同源）。
6. **`0066` / `0067` 里"前端六个搜索框"那句话不准确**（组织没有搜索框，
   日志是第七个入口）。两篇都是已定稿的 ADR，按本仓"ADR 不回改旧文"的约定
   不在原文里改；以此处为准。
