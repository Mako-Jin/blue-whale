# 0042. 契约与后端代码的同步守卫

- **状态**：已采纳
- **日期**：2026-10-13
- **决策者**：舰长

## 背景

`0040`「本决策未覆盖」第 1 条与 `0041`「本决策未覆盖」第 1 条指向的是同一件事：

> **契约本身是否跟上了代码**没有守卫。`openapi.json` 落后时两边读到的都是同一份旧文件。

至此契约这条链路上只剩这一段没有机器兜底：

```
后端代码（注解） ──springdoc──▶ docs/api/openapi.json ──openapi-typescript──▶ schema.d.ts
                    ↑ 本决策            ↑ 0040 守（对文档）        ↑ 0041 守
```

**缺了本段，`0041` 会守在一个可能已经过期的上游上。** `0041` 比对的**上游**就是
`openapi.json`：上游旧了，`gen:api` 照着旧契约生成，产物与旧契约一致 ⇒ `web` job 照样绿。
两段合起来才闭环。

### 它为什么值得做（而不是"反正流程写在文档里"）

`AGENTS.md` 硬性要求 5 早就写着"改后端接口后必须跑 `scripts/export-openapi.sh`"，
但**没有任何东西会检查**。而"契约落后于代码"是个**安静**的错：前端消费的就是那份旧类型，
编译得过、用例也全绿，前后自洽 —— 与 `0041` 记的是同一种安静。
唯一能察觉它的场合是有人把两份东西对着看，而那正是 `0039` 已经证伪过的办法。

### 动手之前必须先回答的问题：导出稳定吗？

"重新导出、与入库版本比"只有在**导出是确定的**前提下才成立；否则它是一条随机红，
而随机红比没有检查更坏（`0036` 决策 2）。

2026-10-13 本机实测（判据是 `sha256`）：

| 用例 | 结果 |
| --- | --- |
| 同一个 jar 连跑两次 | `d7dc9f0f…` / `d7dc9f0f…` —— 相同 |
| `mvn clean install` 重建后的 jar（jar 自身哈希 `8847fbe5…` → `9dfd63ff…`） | `d7dc9f0f…` —— 仍相同 |
| 入库版本（`docs/api/openapi.json`） | `d7dc9f0f…` —— 与上面几次全同 |

第二次跨的是**进程**，第三次跨的是**构建**（重新编译出的类文件、重新打的 jar）。
四次所得逐字节相同 ⇒ **可以比字节**。

（顺带得到一个**当次**的事实：入库的契约就是当前代码的真产物，此刻没有漂移。
按 `0039` 的判据这是个会变的值，所以它只说明"还没漂"。）

## 决策

1. **在 CI 的 `server` job 里加一步：重新导出契约，要求与入库版本逐字节相同。**

   ```bash
   bash scripts/export-openapi.sh                       # h2 内存库，不需要任何服务
   git status --porcelain -- docs/api/openapi.json      # 有输出即失败
   ```

2. **挂在 `server` job 的 `mvn verify` 之后，不新开 job。** 那一步已经产出可执行的 jar，
   而 `export-openapi.sh` 要的正是它 ⇒ 复用即可；新开一个 job 得再做一遍 Maven 构建
   （含依赖下载），换不来任何东西。也**不挂 `server-mysql`**：接口与数据源方言无关。

3. **用 `git status --porcelain` 而不是 `git diff`** —— 与 `0041` 同一套判据，
   读代码的人不必学第二套。（`0041` 那边是**必须**这么写，因为生成物可能未被跟踪；
   这里只是保持一致，代价为零。）

4. **失败信息给出唯一的下一步动作**，不让人再判断：`--stat`、diff 前 60 行，
   以及那两步（`bash scripts/export-openapi.sh` + `cd web && pnpm --filter common-api gen:api`）。

5. **导出失败（应用没起来 / 产物缺失 / JDK 不对）单独判、单独报**，不与"不一致"混成一条消息
   —— 两者的处置完全不同：一个要读日志，一个要重新导出。日志只在失败时全量打印，
   成功时只留前 6 行（标题 / 版本 / 接口数）。

## 后果

**正面**

- 契约链路**三段全部有机器兜底**：代码 → 契约（本决策，`server` job）·
  契约 → 文档（`0040`，`guards` job）· 契约 → 生成物（`0041`，`web` job）。
- **顺带多覆盖了一件事：打出来的 jar 真的能启动。** 此前 `mvn verify` 只证明"测试上下文能起"，
  而 `spring-boot:repackage` 产出的那个可执行 jar 能不能跑（`Main-Class` 写对没有、
  依赖有没有漏进 `WEB-INF/lib`）在 CI 里从没验过。这一步是第一次真跑它。
- 本机一条命令即可复现（**与 CI 同一套判据**）：

  ```bash
  bash scripts/export-openapi.sh
  git status --porcelain -- docs/api/openapi.json   # 输出为空 = 同步
  ```

- **它不是空转**，三个负例逐个验过：

  | 扰动 | 结果 |
  | --- | --- |
  | 把 `HealthController` 的 `@Operation(summary = …)` 改一个字、**不重新导出** | 红 —— 报出的 diff **只有那一行** |
  | jar 不存在（产物缺失） | 红 —— 脚本在第一步就报"请先执行 `cd server && mvn -DskipTests install`" |
  | 什么都不改 | 绿 |

  第一个用例同时证明了**导出确实反映代码变化** —— 这正是"检查不是空转"的定义。
  第三个用例是**在本机原样执行 CI 那段 `run` 块**跑出来的（把 YAML 里的脚本抠出来直接跑），
  不是"逻辑上应该没问题"。

**代价 / 负面**

- `server` job 多约 30 秒（起一次 h2 应用 + 导出）。它排在 `mvn verify` 之后，
  所以**构建或测试红了它就不会跑** —— 不是漏检，是那种情况下契约同步没有意义。
- 这一步让 `server` job 多了一个新依赖：**能启动应用、能用 18080 端口**。
  选默认 profile（h2 内存库）是因为它零外部依赖 —— `application.yml` 原文：
  "新人 / CI 不该被迫先装一个数据库"。脚本刻意用 18080 而不是 8080，理由见其头部注释
  （端口冲突会让它连上别人的服务、导出一份错误的契约，且不报错）。

- **⚠️ 残余风险：换 JDK 发行版理论上可能改键顺序。** 本机实测用的是
  **Oracle JDK 21.0.8**，CI 用 **temurin 21** —— 两者都是 HotSpot，
  `String.hashCode()` 有规范定义、javac 产出的类文件方法顺序也不依赖发行版，所以**预期一致**；
  但 `Class.getDeclaredMethods()` 的顺序在规范上**不保证**。
  若 CI 上出现"本机能过、CI 报不一致"、且 diff 全是**同一批键的换序**，那就是这个。
  处置是**把判据从"逐字节"降级为"解析后递归排序键再比"**，**不是关掉这一步**
  （关掉就回到了"没人看"）。
  **在 CI 上第一次真跑之前，这条风险没有被消除、只是被评估过 —— 如实记在此处。**

**后续约束**

- 改后端接口后按 `docs/api/README.md` §二 的三步走完、一次提交。本决策只是**兜底**，
  不是"可以忘了跑导出"的许可。
- 不要去掉 `export-openapi.sh` 末尾的格式化（`JSON.stringify(doc, null, 2)`）——
  它是"逐字节可达"的前提，与 `gen:api` 末尾的 `prettier --write` 是同一个理由（`0041`）。

## 本决策未覆盖

1. **接口在某个 profile 下才注册**（条件装配）时，契约会依赖导出时用的 profile。
   本仓目前没有这种接口，故按 h2 导出即全量；出现第一个时这条要重看。
2. `docs/api/README.md` §五「待补充」里那些**历史进度句**（`0040` 已记，与 ADR 同性质，
   记的是当次进度）。
3. 达梦（`0010`）与 MySQL（`0038`）下**接口本身**是否会变 —— 不查，因为接口与数据源无关
   （路径、查询参数、响应形状都不由 dialect 决定）。
4. `web/pnpm-workspace.yaml` 的 `elemental/*` 悬空 glob 仍待定
   （`0037` / `0039` / `0040` / `0041` 均未表态）。
