# 0022. 角色管理与角色资源授权：让授权可配置，外加判定侧的三处静默修正

- **状态**：已采纳
- **日期**：2026-10-12
- **决策者**：舰长

## 背景

`docs/decisions/0016` 立起权限域时，交付的是**认证 + 鉴权**主线；`0021` 补上了**资源目录**
（权限码的登记）。两篇之后仍然缺一环：**没有任何接口能把资源授给角色**。

后果不是"少一个 CRUD"这么轻：管理员那批权限全部来自 `DefaultAdminSeeder` 的硬编码，
也就是说**权限体系的形状是固定的** —— 想改一次授权，只能改种子或直接写 SQL。
`0021` 把"造权限码"变成了接口调用，但造出来的权限码**授不出去**，
于是它只能看、不能用。

本决策交付**角色管理**（`/api/auth/roles`）与**角色资源授权**（`/api/auth/roles/{id}/resources`），
并顺带修掉判定侧三处**静默缺陷** —— 它们此前不修也"看不出来"，而这一切片一旦把
`effect` / 时间窗 / 角色状态做成可点的配置，不修就等于交付三个假开关。

立项顺序的依据：资源目录 → 角色与授权 → （下一步）角色成员 / 用户组 / 组织。
前两步合起来，恰好覆盖"谁有哪些权限"这条链的**配置侧**。

## 决策

### 1. 授权挂在角色下，作为角色的子资源

`GET | POST /api/auth/roles/{id}/resources`、`DELETE .../resources/{resourceId}`。

不单开 `/api/auth/role-resources` 一类的平级资源。理由是**授权关系是角色的内部边**：
它没有脱离角色与资源独立存在的意义，也没有独立的生命周期 —— 不存在"没有角色的授权"。
挂在角色下，URL 本身说明了"改的是这个角色的授权集合"，同时天然带上归属校验。

**撤销的路径用 `resourceId`（资源主键）而不是 `grantId`（授权行主键）。**
后者会随 upsert 换行、随复活换 id，把它写进路径等于让调用方必须记住一行状态；
而资源主键让"授"与"撤"完全对称 —— 同一个 (角色, 资源) 二元组就是这条边的身份。
返回体里仍然给出 `grantId`，供需要精确定位的场合使用。

**没有"清空某角色全部授权"的接口。** 那种接口一次点击可能让一批人同时失去权限，
而审计里只有一条记录。逐个撤销让每一条都可解释 —— 与"不提供藏起来的级联"同源。

### 2. 授权是 upsert，并且清掉同键的其余行

按 (角色, 资源) 定位唯一一条有效行：存在则改它的字段，存在但已被撤销则**复活**它，
不存在才新建。三种做法里，另两种都会出问题：

- **直接插**：改效果（`ALLOW` → `DENY`）时会留下两条相反的行。判定按资源聚合、
  DENY 胜出，于是**旧的 `ALLOW` 还在生效状态**，而调用方以为自己改成了拒绝 ——
  实际效果是"这条授权忽然不生效了"，与预期正好相反。
- **先删后插**：`create_time` 每次刷新，"这条授权从什么时候开始"这段历史就丢了；
  而审计面板只记变更后的值，追溯不到。

**表上没有 `(role_id, resource_id)` 唯一索引**，服务层的"先查后写"挡不住并发。
这里刻意**不补这个索引**，理由是它会把并发提交变成 `DuplicateKeyException`，
而 `GlobalExceptionHandler` 当前没有对应处理器 → 兜底 `50000`。
与其用一个新迁移换来一条新的 500 路径，不如让**判定侧对重复行免疫**（见第 3 条）：
重复的 `ALLOW` 行只是让计数变大，`ALLOW` + `DENY` 并存则由 DENY 胜出。
服务层再加一道"写完之后清掉同键其余行"，让表里不会长期积累重复。
触发条件：补上 `DuplicateKeyException` → `409` 处理器之后，这个索引就该加。

### 3. `DENY` 的语义：按资源聚合，"一条命中即拒绝"

**这是本切片修掉的第一处静默缺陷，也是必须在本切片修的原因。**
`GrantEffect` 的注释与 `AuthorizationMapper` 的注释都写着"显式拒绝优先于允许"，
但原 SQL 的写法是在 JOIN 上过滤 `effect <> 'DENY'` —— 它排掉的是**那一行**，
不是那个资源。于是"角色 A 允许 + 角色 B 拒绝"时，A 那一行照样通过，资源仍然可用；
`DENY` 只在**同一个角色内**成立，而同一个角色的同一个资源上放两条相反规则毫无意义 ——
也就是说，**跨角色恰恰是 DENY 唯一的用途**，而它一直是失效的。

改法是以资源为单位聚合，用 `HAVING` 表达"这个资源上一条 DENY 都不能有"：

```sql
GROUP BY r.resource_code
HAVING SUM(CASE WHEN rr.effect = 'DENY' THEN 1 ELSE 0 END) = 0
```

用行数而非布尔值，是因为用户可能同时持有多个角色，"有没有 DENY"要跨这些角色一起看。
分组之后原有的 `DISTINCT` 也不再需要 —— 一个资源只会产出一行。

先把 `DENY` 修对、再暴露它的配置入口，顺序不能反：否则交付的是一个
"能配但配了没用"的开关，而它比没有这个功能更糟。

### 4. 停用的角色不再产生权限

**第二处静默缺陷。** `selectGrantedResourceCodes` 原本没有 `ro.status` 过滤，
而 `selectRoleCodes` 有 —— 两处不一致意味着"角色列表里查得到、权限却来自一个已停用的角色"。

在此之前"停用角色"不是一个能做的操作（没有角色管理接口），所以漏掉没有表现；
本切片之后它成了一个可点的按钮，**漏掉它就意味着点完之后权限照旧** ——
`AuthorizationMapper` 自己的注释里恰好写着一句判据："停用/删除不应只是界面上的假象"。

### 5. 时态授权进入判定，且时间作为入参而不是 `NOW()`

`effective_from / effective_to` 三张表都留了列（角色成员 / 角色资源 / 用户组成员），
但一直没进判定。本切片把它们加进 `effective_from IS NULL OR effective_from <= ?`
与 `effective_to IS NULL OR effective_to > ?`（半开区间 `[from, to)`）。

**语义价值**：到期自动失效**不需要定时任务去删数据** —— 定时任务一旦没跑，
权限就会静默地多留一天；时态过滤不会。

**时刻由调用方传入，不用 SQL 的 `NOW()`。** 判定在一个请求内可能被打多次
（多处 `@RequiresPermission`），各自取一次当前时间会让一个恰好跨过到期边界的请求
出现"角色查得到、权限查不到"。`PermissionChecker` 是请求级缓存，在那里取一次即可，
两次查询共用；出参的 `effectiveNow` 也复用同一套区间判断。
附带好处是三套数据库不必各自解释时间函数。

`effective_from / effective_to` 两端都为空的行不受影响，因此这条改动对存量数据
（种子数据全部为空）完全向后兼容。同理，第 3、4 条也向后兼容：种子角色均为
`ENABLED`，且没有任何一行 `DENY`。

### 6. 删除角色的三道拒绝，以及"授权一并撤销"

按检查顺序：

1. **系统内置角色不可删除**（`40917`）。
2. **有子角色不可删除**（`40913`）：不提供藏起来的级联，与租户 / 资源一致。
3. **有成员不可删除**（`40916`）：删角色会让**持有它的那些人**立刻少掉一批权限
   （判定 SQL 要求 `ro.deleted = 0`）。管理员的本意可能只是"清理一个不再用的角色"，
   实际效果却是"某些人突然点不动某个按钮了"，且没有任何界面会提示发生过。

**但角色自己的授权不构成拒绝理由，会被一并逻辑删除。** 这看起来与
"删资源时若有角色引用则拒绝"（`0021`）矛盾，其实是两条不同的规则，值得写清楚：

|              | 删资源被角色引用 ⇒ 拒绝                | 删角色有授权 ⇒ 一并撤销                    |
| ------------ | -------------------------------------- | ------------------------------------------ |
| 破坏的是谁   | **别的聚合**（角色的授权集合）         | 自己的**内部边**                           |
| 操作者视角   | 想清理一条资源，看不到谁在用它         | 正在看这个角色本身，它的权限就是它的部分   |

一并撤销还有一层安全考虑：**若留存，复活角色会让这批权限静默回来**。

### 7. 系统内置角色不可停用、不可改分类

`category = SYSTEM` 的角色由种子数据建立（`SUPER_ADMIN` / `AUDITOR`），是把系统管理起来的起点。
删掉或停用它会让**所有人**同时失去管理能力，而恢复手段只剩直接改库 ——
一次点击造成需要连数据库才能撤销的后果，不该由一个 HTTP 接口提供。

"不可改分类"看似多余，实为**堵住一条绕过**：若允许把 `category` 从 `SYSTEM` 改成 `CUSTOM`，
就可以先降级、再删除，两道保护会被一次 update 绕开。

### 8. 软删占用唯一编码 ⇒ 复活原记录，且复活出来的是空角色

与 `0021` 是同一个坑的变体：`uk_bw_auth_role_tenant_code` 建在
`(tenant_id, role_code)` 上、**不含 `deleted`**，而 MyBatis-Plus 给所有自动查询追加
`deleted = 0` —— 常规判重**看不见软删行**，判重通过后 insert 撞唯一键，
`DuplicateKeyException` 被兜底成 `50000`。于是"删掉角色、用同一个编码再建一个"
这个再正常不过的操作会得到"系统内部错误"。

正解同样是**复活那一行**（`selectAnyByTenantAndCode` + `restoreDeletedById`，
两个刻意绕过 `@TableLogic` 的手写 SQL），并在内存里把 `deleted` 置 0 ——
`updateById` 的 `WHERE` 也带 `deleted = 0`，对软删行影响 0 行且不报错。

**复活出来的一律是空角色**：`create` 在复活路径上会再清一次该角色名下的授权。
`delete` 已经清过一遍，这里再清是为了让"复活 = 没有权限"成为**无条件**成立的语义 ——
否则若某行角色是被直接改库删掉的（授权行还在），复活会静默恢复一批权限，
而调用方以为自己只是新建了一个同名的空角色。

### 9. `updateById` 的 `NOT_NULL` 策略清不掉字段 ⇒ 角色与授权一律显式 `set`

**第三处静默缺陷，而且是端到端测试逮出来的。** MyBatis-Plus 默认字段策略是 `NOT_NULL`：
`updateById(entity)` 只把**非空**字段拼进 `SET`，因此"把某个字段改回 null"这个操作
**根本发不出去** —— 影响 0 行、不报错、返回值正常，调用方拿到 200，库里那一列还是旧值。

在本类上有三处会因此变成假功能：

- `parentId` 改回 null（把角色从层级里摘出来）—— 传了 null，角色却还挂在原父角色下；
- `description` / `filterJson` / `category` 清空 —— 删掉描述点保存，刷新后描述又回来了；
- **授权行上的 `effectiveFrom / effectiveTo`** —— 把"临时代理"改回长期有效就是清掉时间窗，
  清不掉就意味着这条授权**永远停在过期状态**，表现为"我明明重新授了权，怎么还是没权限"。

第三处正是测试失败点：断言"恢复长期有效后权限应当回来"时拿到了 `40301`，
一路查到 SQL 才发现时间窗从未被清掉。修法是角色与授权都用
`update(new Entity(), lambdaUpdate().eq(...).set(...))` **逐列显式 set**。
传一个空实体而不是 `null`，是为了让 `updateFill` 有机会跑 ——
否则 `update_time / update_by` 会在这条 UPDATE 上停更，而"上次改于何时"正是审计要回答的问题。

### 10. 给角色授权共用 `auth:role:update`，不单设 `auth:role:grant`

依据是本仓已有的一条同类判断：重置口令共用 `auth:user:update`
（见 `AuthAuditActions.USER_RESET_PASSWORD` 的注释），理由是"能改这个对象的人
本来就能改它的全部方面"。角色的授权集合就是角色的一部分。

但这条与重置口令有一处**性质上的差别**，写下来备查：给自己持有的角色授权等于给自己提权。
因此触发条件是明确的 —— **当出现"只改角色资料、不许动权限"的诉求时**，就拆出
`auth:role:grant`（加一个常量 + 换注解，不影响数据）。在那之前不拆，
避免用权限码表达一个不存在的分工。

审计上则**必须分开**：`auth.role.grant` 与 `auth.role.revoke` 是两个独立动作标识，
虽然共用同一个权限码。事后追责时"谁给这个角色加了 `auth:role:delete`"必须能直接过滤出来，
而 `auth.role.update` 只记变更后的值，混在一起就只能靠比对前后快照。

### 11. 校验密度分层：有判定语义的严格，只存不用的宽松

- **严格**：`status` 走 `Status` 枚举、`dataScope` 走 `DataScope` 枚举、
  `isDefault` 只接受 `0/1`、`effectiveFrom < effectiveTo`。
  理由：这些值会被判定链路读取，写错不报错，只会静默改变行为。
- **宽松**：`category` / `inheritStrategy` / `filterJson` / `roleLevel` 只归一化、不加取值约束。
  它们当前既不参与判定、也没有消费方（角色继承与数据范围求值都还没做）。
  给它们编一套取值约束，等于提前定义一个还没有用例的契约 ——
  与 `resourceVersion` 的"只存不用"是同一种处理。

分界线的依据是"**写错了会不会有人受伤**"，而不是字段的重要性。

## 后果

- "谁有哪些权限"的配置侧闭环：资源（`0021`）→ 角色与授权（本决策）。
  此前改授权只能改库，现在是一次带审计的接口调用。
- 判定侧三处静默缺陷被修掉，且都有端到端测试兜住：
  `DENY` 跨角色、停用角色、时态区间。测试**走真实的 `@RequiresPermission`
  与真实接口**（`GET /api/auth/tenants`），而不是断言 `/me` 返回了一份列表 ——
  只有前者能证明判定真的变了。
- 权限码 13 → 17 项，错误码新增 `40407` / `40916` / `40917`。
  计数散落在 e2e 断言与四份 README，本切片已同步；再次提醒这是**会漂的一类文档**。
- 后端用例 109 → 120（新增 `RoleApiTest` 11 例），契约 34 → 42 个接口。

## 本决策未覆盖

- **角色成员关系**（`bw_auth_rel_role_member`：给用户 / 用户组授角色）的接口。
  判定侧已支持多态成员与时态区间，但**没有接口能写这两列** ——
  测试里是直接经 Mapper 插一行来验证判定链路的，那是测试的取巧，不是接口的一部分。
  这也是"时态在成员关系上生效"目前无法从接口验证的原因。
- **用户组 / 组织**的管理接口。
- **角色继承**：`parent_id` 与 `inherit_strategy` 只建层级、不产生任何权限传递。
- **数据范围求值**：`data_scope` / `filter_json` 只存不用；`RoleVO` 与 `RoleSaveRequest`
  的 `@Schema` 里逐字标了这一点。
- **实例级授权**：`bw_auth_rel_role_resource_instance` 表已就绪、零代码。
- 前端未接：`AccessPermissions` 刻意不含 `auth:role:*`（该文件规则是"只列前端真的用到的"）。
- **不做"扫描 Controller 自动登记资源"**，理由见 `0021`。

## 发现但未处理（供后续决策）

1. **`updateById` 的 `NOT_NULL` 策略是一个全仓性的坑，不止角色。**
   `TenantService.update` 同样直接 `setDescription(...)` + `updateById` ——
   把租户描述清空同样清不掉。本决策只修了权限域内新写的两处，
   **没有动 `TenantService` 与 `UserService`**：改它们的受影响面（既有测试、
   前端行为）不属于本切片的验证范围。触发条件：下一次需要"清空字段"的功能落在这两个服务上时。
2. **`ResourceService` 复用 `HIERARCHY_CYCLE(40913)` 表达"有子资源"**，
   文案是"层级关系不合法"；本切片的"有子角色"沿用了同一做法。语义上不精确 ——
   `40913` 应当专指成环，建议在真需要区分"有子节点"与"成环"时拆出 `40918`。
3. **`(role_id, resource_id)` 上没有唯一索引**，见第 2 条：正解存在，
   但前提是先有 `DuplicateKeyException` → `409` 的处理器。
4. **`GlobalExceptionHandler` 没有 `DuplicateKeyException` / `DataIntegrityViolationException`
   处理器**，一切唯一键冲突都会兜底成 `50000`。这条在 `0021` 就记过，
   本切片又踩到一次（角色编码），仍**未处理** —— 它值得单独一次很小但很值的改动。
5. **`AuthorizationMapper` 只按 `ro.tenant_id` 限定角色，不限定资源** ——
   与"资源是平台级的"（`0021` 第 6 条）一致，但注释与 SQL 的措辞容易被读成
   "两侧都限定了租户"。已记录未改：它是刻意的取舍，缺的是一句更清楚的注释。
