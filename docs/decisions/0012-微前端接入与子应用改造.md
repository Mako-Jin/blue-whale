# 0012 - 微前端接入：主应用挂载方式与子应用改造

- 状态：已采纳
- 日期：2026-10-10
- 关联：`0001-架构基线与技术选型`（qiankun 2.x 定选）、`0002-前端公共包与公共依赖治理`（catalog）

---

## 一、背景

ADR-0001 把 qiankun 2.x 定为微前端方案，`platform-portal` 的目录、路由、布局也早就建好了。但**接线一直没有真正发生**：

- `platform-portal` 里 `qiankun` 只写在 `package.json` 依赖中，全仓搜不到 `registerMicroApps` / `start` / `initGlobalState`；
- `platform-user`、`platform-admin` 两个规划中的子应用并不存在；
- 已有的 `platform-log-console`、`platform-event-console` 是**独立应用**：入口直接 `createRoot().render()`，没有导出 `bootstrap/mount/unmount`，也没有 `__POWERED_BY_QIANKUN__` 判断。

也就是说，主应用实际上只是一个普通 React SPA。要能调试微前端，必须做两件事：**改造主应用去挂载**，**改造子应用被挂载**。

在动手前必须定几件事：怎么挂、沙箱开不开、开发期与生产期的入口怎么区分、子应用要改到什么程度、样式隔离怎么办。这些决定都会长期约束后续每一个子应用，所以记在这里。

---

## 二、决策

### 1. 主应用用 `loadMicroApp`，不用 `registerMicroApps` + `start`

参考项目 `platform-terminator` 用的是后者：一个常驻的 `#sub-app-container`，靠 `activeRule` 匹配路由。那条路在这里有两个具体麻烦：

- 容器必须**在 `start()` 之前就存在于 DOM**，否则激活时找不到挂载点（典型表现是"路由切过去了但子应用不出现"）；
- 子应用的真实 DOM 落在全局容器里，而路由出口在另一个位置 —— 位置被拆成两处，排查时很难说清"到底谁在管这块区域"。

改成 `loadMicroApp` 后，**路由出口本身就是挂载点**：挂载与卸载直接对应 React 组件的挂载与清理，不存在竞态，位置也只有一处。代价是没有 qiankun 内置的 `prefetch`，需要时显式调 `prefetchApps` 即可。

实现落在 `src/micro/`：

| 文件                               | 职责                                                              |
| ---------------------------------- | ----------------------------------------------------------------- |
| `types.ts`                         | `MicroAppMeta`（注册信息）/ `GlobalState` / `MicroAppProps`       |
| `apps.ts`                          | 子应用注册表 `MICRO_APPS`、按名查找、按环境解析 entry             |
| `state.ts`                         | 全局状态：`initGlobalState` + **基座自己维护的本地副本**          |
| `loader.ts`                        | `mountMicroApp()`：组装 props、`loadMicroApp`、沙箱与资源过滤配置 |
| `index.ts`                         | 出口                                                              |
| `components/MicroAppContainer.tsx` | 挂载容器组件：加载态、失败兜底、卸载清理                          |

> 类型全部用 `type` 而非 `interface`。这不是风格偏好：qiankun 的泛型约束是
> `T extends Record<string, any>`，而 interface 不会获得隐式索引签名，直接编译不过。

### 2. 关闭 JS 沙箱（`sandbox: false`）

这不是图省事，是 Vite 子应用的必要选择：

子应用在开发期是一堆 **ESM 模块**，由浏览器原生 `import()` 加载。qiankun 的 JS 沙箱靠
`with(window)` 包住脚本来劫持全局变量，而**它包不住模块作用域** —— 沙箱开着也拦不到子应用模块里的全局访问，只会把 `document` / `history` / 定时器那部分补丁打上，白白增加出错面。

顺带说明一个被核实的细节（不是猜测）：qiankun 在加载时会先算出 `global`（开沙箱是 ProxySandbox，关沙箱就是 `window` 本身），把 `__POWERED_BY_QIANKUN__` 挂上去，再在执行脚本前 `window.proxy = global`。`vite-plugin-qiankun` 正是靠这两个全局桥接来交换生命周期，因此**关沙箱不会破坏子应用加载**。

同时必须排除 Vite HMR 客户端脚本，否则 qiankun 会改写它的加载地址，热更新悄悄失效：

```ts
excludeAssetFilter: (url) =>
  url.includes("react-refresh") || url.includes("@react-refresh");
```

### 3. 子应用接入用 `vite-plugin-qiankun`

qiankun 执行子应用脚本走 `import-html-entry`：把每个 `<script>` 的文本取出来用 `eval` 执行。Vite 开发期产出的是 **module script**，`eval` 出来的是普通脚本，根本执行不了。`vite-plugin-qiankun` 做两件事解决它：

1. 把 `<body>` 里的 `<script type="module">` 改写成动态 `import()`；
2. 在 `window` 上以应用名挂一个"等 qiankun 回调"的生命周期壳。

代价是这个包最后发布于 2023-07，peer 只写了 `vite: >=2`（无上界），属于事实上的停更状态。核过之后仍然采用，理由：它做的事**有明确边界且可验证**（只有 `transformIndexHtml` + 一个 dev 中间件），参考项目在 Vite 8 下也实际跑通；换掉它自己重写一遍成本更高且风险相同。若将来 Vite 大版本破坏它，替代路径是让子应用直接产出 UMD 单文件。

> 应用名是**隐式契约**：`vite-plugin-qiankun` 里的名字与基座 `MICRO_APPS` 里的 `name` 必须逐字一致，写错**不会有任何报错**，只会一直卡在"加载中"。因此两侧的配置里都写了相互指认的注释。

### 4. 子应用必须保留"独立运行"分支

```ts
if (!qiankunWindow.__POWERED_BY_QIANKUN__) {
  render();
}
```

这不是兜底代码，是**必须保留的开发方式**。子应用能单独 `pnpm dev` 打开时，改一行不用等基座起来。这一点在本轮尤其关键：被基座加载时 React 组件级热更新不生效（见「后果」），独立运行则完全正常。

### 5. 子应用 dev server 必须开 CORS，且锁死端口

| 配置                | 为什么必须                                                                                                                                                              |
| ------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `server.cors`       | 基座在另一个端口，要跨域拉子应用的 HTML 与脚本；不开的话基座连入口都拿不到                                                                                              |
| `server.origin`     | 决定 vite 重写资源地址（如 HMR 客户端）时用的前缀                                                                                                                       |
| `server.strictPort` | 端口写死在基座 entry 里。被占用时 vite 默认顺延到下一个端口，**基座仍去老端口拉** —— 结果是基座报加载失败、子应用这边一切正常，排查方向一开始就是错的。宁可启动直接失败 |

### 6. 全局状态下发：基座自己维护本地副本

qiankun 的 `initGlobalState` 只返回 `onGlobalStateChange` / `setGlobalState` / `offGlobalStateChange`，**没有 `getGlobalState`**。参考项目把 `actions.getGlobalState` 直接传给了子应用，而那是个 `undefined` —— 子应用一调用就抛错，且要到运行时才暴露。基座侧因此显式维护一份副本。

子应用侧不反向依赖基座（违反「应用之间禁止相互引用」），桥接逻辑下沉到 `common-tools/micro`：

- 只按**结构**描述基座下发的 props，不 `import` qiankun 的类型，本包「不依赖任何运行时第三方库」的约束不被破坏；
- `bindHost()` 把 props 挂到 `window.__MICRO_HOST__`，DevTools 里可直接看基座给了什么；
- 右下角渲染一个状态标记（`theme` / `userId`），让"全局状态真的到了子应用"这件事**看得见** —— 只靠 console 输出容易看漏。

### 7. 子应用路由由注册表推导

```tsx
...MICRO_APPS.map((app) => ({
  path: `${app.routePath.replace(/^\//, '')}/*`,
  element: <MicroAppContainer appName={app.name} />,
}))
```

新增子应用只改 `src/micro/apps.ts` 一处，不会出现"注册表里加了、路由忘了加"这种只在点击时才暴露的缺口。路径统一带 `/*`：子应用内部如何组织路由是它自己的事。

### 8. 样式隔离不指望框架

**没有**开 `experimentalStyleIsolation`。它依赖子应用把 `<style>` 写进入口 HTML，而 Vite 开发期是**由 JS 在运行时**把样式插进 `document.head` 的，且这段代码跑在真实 window 上、不经过沙箱代理，拦截规则根本不会命中。`strictStyleIsolation`（Shadow DOM）同理失效。

结论：**子应用的样式前缀必须自己保证不撞车**。当前两个控制台的 LESS 类名高度重叠（`.app` / `.btn` / `.panel` / `.pill` 等十余个），这是复制版式时留下的隐患 —— 见「后果」中的未完成项。

### 9. 开发期与生产期用不同 entry

```ts
export function resolveEntry(meta: MicroAppMeta): string {
  return isDev ? `//localhost:${meta.devPort}` : meta.prodEntry;
}
```

对应子应用侧 `base` 也必须分环境：**开发期保持 `/`**（`vite-plugin-qiankun` 靠 `base` 去定位 `/@vite/client`，加了前缀它会找不到，热更新静默失效），只有 `vite build` 才带上 `/log-console/` 这样的前缀。

### 10. 补掉 React Fast Refresh preamble 在 qiankun 下的执行错误

`@vitejs/plugin-react` 会往 `<head>` 塞一段内联模块脚本设置 Fast Refresh 的全局钩子：

```html
<script type="module">
  import { injectIntoGlobalHook } from "/@react-refresh"; …
</script>
```

`vite-plugin-qiankun` 只改写了 `<body>` 里的 module 脚本，**没管 `<head>` 里这段内联的**。于是 qiankun 用 `eval` 执行它时抛
`SyntaxError: Cannot use import statement outside a module`，`$RefreshReg$` / `$RefreshSig$` 也就装不上。

修法是把它也转成动态 `import()` 并去掉 `type="module"`，整体包进 async IIFE —— 语义不变，但变成普通脚本就能执行了。实现在 `common-config/src/vite.js` 的 `qiankunDevPreamble()`，**放在共享配置包而不是各子应用**：每个子应用都会遇到，散着写必然漂移。

## 三、后果

### 得到什么

- 主应用真正成为 qiankun 容器：按路由加载/卸载子应用，有加载态与失败兜底（提示端口与 CORS），切换路由时旧子应用干净卸载。
- 全局状态下发打通，并有可见的状态标记与 `window.__MICRO_HOST__` 两条排查通道。
- 子应用与独立运行时**共用同一份代码**，不存在"两套入口"的漂移。
- 子应用内 `/api` 请求在两种模式下都通：被基座加载时走基座页面的代理，独立运行时走自己的代理，代码里始终只写相对路径。
- 每个子应用新增的成本被压到很小：`main.tsx` 加生命周期、`vite.config.ts` 加两行插件与 CORS。

### 付出什么

- **`vite-plugin-qiankun` 是停更依赖**（2023-07 最后一个版本）。它做的事边界清晰，但升级 Vite 大版本时要重新验证。
- **多了一层隐式契约**：应用名在两侧必须一致，且写错不报错。已用注释与文档缓解，但没有编译期保障。
- **沙箱关闭**意味着子应用之间没有 JS 隔离。当前不影响（子应用只通过 props 与全局状态交互），但这是长期约束：子应用不得假设自己独占全局变量。
- **样式隔离没有兜底**，靠命名约定。

### 已知限制：被基座加载时，React 组件级热更新不生效

实测结论（真实浏览器 + CDP 验证，脚本见 `scripts/verify-micro-frontend.mjs`）：

| 场景                                  | 源码改动  | 样式改动 |
| ------------------------------------- | --------- | -------- |
| 子应用独立运行（`pnpm dev` 直接打开） | ✅ 生效   | ✅ 生效  |
| 子应用被基座加载                      | ❌ 不生效 | ✅ 生效  |

排除过的可能：Vite 的 HMR 投递链路是好的（模块更新确实从子应用端口拉取、客户端也打印了
`[vite] hot updated`）；也不是本 ADR 第 10 条那个 preamble 修复引起的 —— 做过 A/B 对照，**关掉修复后同样不生效**。根因尚未定位到具体环节。

**当前工作方式**：开发子应用时单独跑它（`:3200` / `:3300`），热更新完整可用；被基座加载的模式用于验证集成与端到端链路。这也是第 4 条"必须保留独立运行分支"的第二个理由。

### 明确未做

1. **`platform-user`** —— 规划中的业务子应用仍未创建。当前只登记"已能被加载"的应用，避免导航上多出点了就报错的入口。
   （`platform-admin` 已于 ADR-0018 第③段创建并注册，见 `0018-权限在微前端中的归属.md`。）
2. **子应用样式前缀去重** —— 两个控制台的 `.app` / `.btn` / `.panel` / `.pill` 等类名重叠。当前靠"同一时刻只挂载一个子应用"回避，真要在同一页面并存两个子应用就会串味。
3. **生产部署的静态目录** —— `prodEntry` 写的是 `/log-console/`、`/event-console/`，但还没有把子应用产物放到基座同域的部署流程。
4. **`platform-portal` 的 favicon** —— 页面会请求 `/favicon.ico` 得到 404（无实际影响，但控制台不干净）。
5. **鉴权与登录态** —— 基座的"登录"按钮只是调试开关，没有真实登录流程，`userId` 由按钮直接切换。
   **归属与落地顺序已由 `0018-权限在微前端中的归属.md` 定下**（会话实现在 `packages/`、基座只装配、
   权限经全局状态下发），并且**三段已全部落地**：调试开关已替换为真实会话（登录页 + 路由守卫 + 会话恢复），
   `HostGlobalState` 已下发 `roles` / `permissions`，权限管理界面落在 `platform-admin`。
   本条的"未做"状态自 2026-10-12 起**不再成立**，保留原文仅作演进记录。
6. **子应用的错误边界** —— 子应用内部渲染报错目前只会在控制台出现，基座不会感知。
