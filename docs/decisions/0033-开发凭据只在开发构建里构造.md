# 0033. 开发凭据只在开发构建里构造，并给产物加一道自检

- **状态**：已采纳
- **日期**：2026-10-13
- **决策者**：舰长

## 背景

`0029` 的「发现但未处理」留了两条：

> **1. 4 个子应用的 dev 自动登录账号仍带着同一个口令** …… 所以这个账号**从不被使用** ——
> 是惰性的常量，不是被展示的凭据。但字符串仍在包里。
>
> **2. 4 个后端测试仍写字面口令** …… 这是文档一致性，不是安全问题，留待顺手清理。

第 1 条是一句**未经验证的判断**（"字符串仍在包里"），而本仓对这类句子的处理方式是
**先辨真伪**。核实办法是新增一个自检脚本，从种子口令的**唯一真值来源**
（`scripts/lib/seed-credentials.mjs`，其背后是 `application-h2.yml`）读出口令，
去扫各个已构建的产物目录：

| 产物目录 | 核实结果（修复前） |
| --- | --- |
| `platform-admin/dist` | 干净 |
| `platform-audit-console/dist` | 干净 |
| `platform-log-console/dist` | **命中** 种子管理员口令 ×1 文件 |
| `platform-event-console/dist` | **命中** 种子管理员口令 ×1 文件 |
| `platform-environment/dist` | 干净（本应用没有会话，见 `0031`） |
| `platform-portal/dist` | 干净（`0029` 修掉的就是它） |

**所以那句话只说对了一半**：不是"4 个都残留"，而是**2 个真的残留**，另 2 个恰好没有。

### 那两个为什么恰好干净

它们的 `DEV_ACCOUNT` 是**模块级常量**，唯一的引用点在提前返回之后：

```ts
// platform-admin / platform-audit-console（改前）
if (!import.meta.env.DEV) { logger.error('…请改由基座加载'); return; }
logger.warn('独立运行：用开发账号自动登录', { username: DEV_ACCOUNT.username });
await channel.login(DEV_ACCOUNT);
```

生产构建下 `import.meta.env.DEV` 被替换成常量 `false`，于是这一句变成
`if (true) { …; return; }`，**其后整段不可达** ⇒ `DEV_ACCOUNT` 无人引用 ⇒ 被摇掉。

这是"**恰好没事**"，不是"设计成没事"：把 `return` 挪个位置（或者去掉这个提前返回），
同一份代码立刻就会泄漏。而两个控制台正因为**没有**那句提前返回 ——
它们把判断做进了参数 —— 对象作为实参一直挂在调用点上，于是被原样保留。

两个控制台的写法在各自文件里有注释解释"生产构建不会启用"。
**注释是给生产说的，打包器并没有听见。**

## 决策

### 1. `devAccount` 的存在，就是那个开关

`ConsoleAuthOptions` 删掉 `allowDevAutoLogin`，只留 `devAccount?: DevAccount`。

原先是"一个布尔开关 + 一份可能缺席的数据"，两者不一致时的行为需要靠约定
（"`false` 时账号不被使用"）；现在是**表达不出来的状态** ——
没有账号就等于不自动登录，没有第二种解释。

### 2. 凭据在**能被静态摇掉的位置**构造

四个子应用统一成同一句话：

```ts
devAccount: import.meta.env.DEV
  ? { tenantCode: …, username: …, password: … }
  : undefined,
```

生产构建下条件是常量假，整个对象字面量被摇掉。这与 `0029` 的"`import.meta.env.DEV` 门控"
是同一条要求，只是把**验证口径**换了：

| 口径 | 判断方式 |
| --- | --- |
| 改前："生产构建不会用到它" | 读代码、在脑子里推演 |
| 改后："产物里没有它" | **可以被机器判定** |

口径换成后者，才谈得上"固化成检查"。

### 3. 把"构建后 grep 产物"从一次性动作固化成脚本

`0029` 就要求"验证方式是构建后 grep 产物，不是读代码判断"，但那一次是**手工执行**的，
结果写进了文档。手工执行的检查会随下一次改动失效而无人知道 —— 门控写错、
调用点被复制、新的子应用又抄一份口令，都不会有任何信号。

新增 `scripts/verify-bundle-secrets.mjs`，扫 `web/platform` 下各应用的 `dist`，
命中即非零退出。三个设计点：

- **口令不写在脚本里**，从 `scripts/lib/seed-credentials.mjs` 取（这是 `0029` 的成果）。
  口令一旦在 `application-h2.yml` 里改掉，检查跟着改，**不会静默失效**；
- **只输出计数，不输出命中的口令串** —— 否则这个检查自己就把口令打进了日志；
- **退出码即结论**（干净 `0`、命中 `1`），可以直接进流水线。

### 4. 后端 4 个测试不再抄口令

`AuthApiTest` / `PasswordHardeningApiTest` / `AuditApiTest` / `ClientLogApiTest`
（"顺手清理"就是这一轮），改为 `properties.getSeedAdmin()` / `getSeedAuditor()` ——
与同仓的 `RoleApiTest` / `UserGroupApiTest` / `DataScopeApiTest` / `ResourceApiTest` 一致。

这不是安全问题（测试里的口令与配置里的是同一个值），是**文档一致性**：
口令是"会变的值"，抄一份之后就多了一处会与配置漂移的地方，
而漂移的表现是"登录失败"，不是"某处配置不一致"。

**它们内部各自造的临时账号口令不动**（`Nobody@12345` 之类）：那些是测试自己定的值，
不存在"与配置漂移"的问题。

## 后果

修复后重跑同一份检查：

| 产物目录 | 修复后 |
| --- | --- |
| 6 个目录 / 18 个文件 | **全部零命中** |

- 口令字面量不再出现在任何前端产物里，且这件事**由脚本保证**，不靠评审记忆；
- `devAccount` 缺席即"不自动登录"，独立部署的生产构建行为不变（连日志文案都没变）；
- 后端测试跟着配置走，口令再改时不会以"登录失败"的形式炸；
- `common-api` 测试 70 → 73 例（新增 3 例钉住新契约：不传账号不登录、传了才登录、
  有宿主桥时不建第二套会话）。

**没有改变**：宿主桥优先的判据、独立运行时的会话自建、`0026` 定下的接线分工
（`platform-admin` / `platform-audit-console` 各自那份 `src/auth/` 仍不下沉）。

## 本决策未覆盖

- **登录页的开发提示文案没有并入自检**。它已由 `0029` 修掉，但那段文案是会变的字符串 ——
  把它写进检查里，文案一改检查就永远"零命中"，是典型的**静默失效**。
  要并入就得让脚本先确认这个串在源码里还存在（自校验），本轮没做。
- **`scripts/verify-bundle-secrets.mjs` 不是密钥扫描器**：只查"已知的种子口令有没有被
  卷进前端产物"这一件事。令牌泄露、源码里的第三方 key 都不在射程内，
  那些需要另一类工具（本仓也没有引入）。
- `platform-admin` / `platform-audit-console` 的 `src/auth/` 仍未下沉到 `createConsoleAuth`
  —— `0026` 记录的既有技术债，本轮不动（下沉要连带改它们的测试与端到端脚本）。
- 密钥级配置（JWT 密钥等）外部化仍未复核（`0029` 已记）。

## 与 `0026` / `0029` 的关系

- **`0026` 正文里"`allowDevAutoLogin` 由调用方传 `import.meta.env.DEV`"这一句已被本条取代**
  （该字段不存在了）。按本仓惯例**不回改 `0026` 原文**，只在这里建立指向。
- 本条是 `0029`「发现但未处理」第 1、2 两条的**收尾**，并**修正了第 1 条的结论**
  （4 个中只有 2 个真的泄漏）。同样不回改 `0029` 原文。
- `0029` 的后续约束一句不变，只是"`import.meta.env.DEV` 门控"被具体化为
  "在能被静态摇掉的位置构造凭据"。
