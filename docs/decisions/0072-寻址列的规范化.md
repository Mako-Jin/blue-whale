# 0072. 寻址列的规范化

> 领 `0071`「未覆盖」3，原文：
> 「**`email` / `phone` 的写入不 trim**（`UserService.blankToNull`：`null` 或纯空白转 `null`，
> 否则**原值**）。它们的读侧是**判重**（`existsEmail` / `existsPhone`）而不是过滤，
> 同源问题但入口不同 ⇒ 要改就得连判重入参一起改（只改一侧会让
> "存 `a@b.c`、判重比 `' a@b.c '`"这种新的不一致冒出来）。**需要单独量一遍判重入口。**
> **注意这一条与本篇的判据同源**：判重也是精确匹配。」
>
> 领到之后先量了原文里没有数据的**两件事**，第二件把原文的"两列同形"推翻了：
>
> 1. **判重入口长什么样** —— 全仓只有 `UserService` 的两个私有方法（`existsEmail` /
>    `existsPhone`），底下都是一次 MyBatis-Plus 的 `eq`；`UserMapper` 里**没有任何**
>    按 `email` / `phone` 的查询。所以"判重入口"就这两处，射程有界。
> 2. **这两列的上游有没有别的守卫** —— `UserSaveRequest.email` 上有 `@Email`（⚠️ 它从
>    `sts-server-auth` 的**第一个提交** `b76fed7` 起就在），而 **`@Email` 不 trim**：
>    带两端空白的邮箱在**进服务层之前**就被判成"邮箱格式不正确"（`40000`）。
>    于是 `email` 那一半**根本没有可观测的缺陷**（改前改后行为完全一致），
>    而 `phone` 只有 `@Size(max = 32)`（量长度）⇒ 带空白的手机号**一路进到服务层**。
>
> 这一篇因此是**"一个真缺陷 + 一次等价变换"**，而不是原文预期的"两列同形、一起改"。
> 顺带把**全仓最后一份"只判空、不 trim"的写入副本**（`UserService.blankToNull`）删掉了。

## 背景

### 1 射程：两列 × 两个入口 × 两处判重

判据一字未改：**"读侧会不会拿它做精确匹配"**。这两列的读侧不是过滤，是**判重** ——
`0062` 早就把"判重"与"过滤"归在**同一条判据**下（"判重就是一次 `eq`"），只是入口不同。

| 列 | 读侧 | 写入侧（改前） |
| --- | --- | --- |
| `bw_auth_user.email` | `existsEmail` → `countBy(... eq(Email, value))` | `blankToNull(request.getEmail())` |
| `bw_auth_user.phone` | `existsPhone` → `countBy(... eq(Phone, value))` | `blankToNull(request.getPhone())` |
| `bw_auth_organization.contact_email` | —— （不判重） | `FilterValue.text(...)` —— **`0071` 已收口** |
| `bw_auth_organization.contact_phone` | —— （不判重） | `FilterValue.text(...)` —— **`0071` 已收口** |

两列 × 两个入口（`create` / `update`），判重点两个。**用户域这两列没有唯一索引**
（`0062`：寻址列的并发漏网是刻意接受的），所以判重就是唯一一道门。

### 2 两列的命运不同 —— `@Email` 顺手挡住了其中一列

一次性探针（直接跑 Bean Validation，不启 Spring 上下文；Hibernate Validator `9.1.3.Final`）：

| 入参 | `email`（`@Email` + `@Size(128)`） | `phone`（只有 `@Size(32)`） |
| --- | --- | --- |
| `a@b.c` | 通过 | —— |
| `' a@b.c '` | ✗ 邮箱格式不正确 | —— |
| `'a@b.c '` | ✗ 邮箱格式不正确 | —— |
| `' a@b.c'` | ✗ 邮箱格式不正确 | —— |
| `'   '` | ✗ 邮箱格式不正确 | 通过 |
| `''` | 通过 | 通过 |
| `a b@c.d` | ✗ 邮箱格式不正确 | —— |
| `null` | 通过 | 通过 |
| `' 13800138000 '` | —— | 通过 |

**`@Email` 与 `@NotBlank` 不同：它不先 trim。** 所以：

- **`phone`**：`" 13800138000 "` 通 DTO → `blankToNull` 判 `isBlank()` 为假 → **原样入库** →
  判重拿 `' 13800138000 '` 去 `eq`。库里存的是 `13800138000`（NO PAD 的排序规则下
  两者**不相等**，见 `0065`）⇒ **判重通过 ⇒ 同一个手机号建出两个账号**。
- **`email`**：带空白的值**根本到不了服务层**。能到服务层的只有 `null` / `""` / 干净值，
  而 `blankToNull` 与 `FilterValue.text` 在这三种输入上**逐个等价**（`null` 进 `null` 出、
  `""` 进 `null` 出、干净值进干净值出）。⇒ 这一列的改动是**等价变换**。

**但等价不等于不必改。** 理由有两条：① `@Email` 挡住空白是它**校验格式的副产物**，
不是为"归一"准备的机制 —— 哪天有人把它换成更宽松的写法（比如放开引号内的本地部分），
email 立刻变成第二个 `phone`，而那时**没有任何东西会提醒**；② 同一个 `UserService` 里
"寻址列的判重"只能有一种写法，留一列走 `blankToNull`、一列走 `FilterValue.text`
就是把 `0071` 刚消掉的"两种口径"重新种回去。

### 3 前端也看不见 —— 而且比 `0071` 更彻底

与 `0070`「背景 3」/ `0071`「背景 3」同形，但这里多一层：`Users` 页的表单**一处都不 trim**
（`submitForm` 里 `email: form.email || undefined` / `phone: form.phone || undefined`），
所以"带空白的手机号"确实能从界面上打出来 —— 只是**没有人会这么打**。
真正的入口是**自己写脚本调接口的人**：`POST /api/auth/users` 带 `"phone": " 13800138000 "`。
差异不会被任何界面测试碰到。

## 一 实测：八条同形断言

`AddressNormalizationApiTest`（八例，**跨 profile** —— 本仓第八处，形状同
`TextEqualityApiTest` / `SearchMatchApiTest` / `SearchWildcardApiTest` /
`SearchKeywordTrimApiTest` / `FilterValueTrimApiTest` / `EnumFilterNormalizationApiTest` /
`WriteSideNormalizationApiTest`：不 `@Transactional`、不按 profile 跳过）。
不改代码跑一次 = **5 红 3 绿**：

| 用例 | 改前 | 改后 |
| --- | --- | --- |
| 建号：`phone` 带两端空白 ⇒ 入库 / 回显该是干净值 | 红（回显 `"   11383913700   "`） | 绿 |
| 改号：`update` 传带空白 `phone` ⇒ 同上 | 红（回显带空白） | 绿 |
| 判重：库里是**干净值** ⇒ 拿**带空白**的同号建号该 `40903` | 红（`code: 0`，**建出来了**） | 绿 |
| 判重：库里是**带空白** ⇒ 拿**干净**的同号建号该 `40903` | 红（`code: 0`） | 绿 |
| 判重：`update` 把自己改成**别人那个号的带空白写法** ⇒ `40903` | 红（`code: 0`） | 绿 |
| 回归钉：纯空白的 `phone` 照旧等于「没有手机号」（三条：`"   "` / `""` / 不传） | 绿 | 绿 |
| 回归钉：判重沿用 `0065` 的文本相等关系 —— 大小写不同仍是两个值 | 绿 | 绿 |
| 前提钉：带两端空白的 `email` 在 DTO 层就被拒（`40000`） | 绿 | 绿 |

**中间两条是"两侧都要"的证据**：只归一写入侧（第三条会红）、或只归一判重侧（第四条会红），
任何"改一半"都会被其中一条逮住。第五条管 `excludeId`（"改自己的号不该与自己冲突"
是既有语义，本条要的是"排除自己之后仍要能比中别人"）。

**最后两条不是顺带一测**：第七条钉的是 `@Email` 这个**可撤销的前提**（本片对 email
只做等价变换、全靠它成立）；第八条钉的是归一**不该越界** —— `FilterValue.text` 只吃两端空白，
判重仍要跟着 `0065` 的排序规则走（若哪天有人给 `email` 也加一道"往小写归一"，这条先红）。

## 二 决策

1. **判重口与写入口共用同一个归一值。** 取一次 `FilterValue.text(...)`、存进一个局部变量，
   判重与 `entity.setXxx` 都用它。这是本片的**主决策** —— "只归一其中一侧"不是不完整，
   而是**造出一种比原来更隐蔽的不对称**（存 `13800138000`、比 `' 13800138000 '`）。
2. **`blankToNull` 删掉，`email` / `phone` 都改走 `FilterValue.text`。**
   至此"两端空白怎么处理"全仓**只剩一处实现**（`0071` 收掉了五份私有 `normalize()` 与
   一整套读取侧口径，本片收掉最后这份写入侧副本）。
   `blankToNull` 的"空串与纯空白退化为 `null`"正是 `FilterValue.text` 的既有语义
   ⇒ 这是一次**行为等价**的替换，不需要新的用例去保护那个语义（回归钉第六条顺手钉着）。
3. **`existsEmail` / `existsPhone` 不再自己判空白。** 入参已经是归一值，
   `isBlank()` 那一支永远不可达 ⇒ 判空只剩 `null` 一种形态（写成 `email != null && …`）。
   **归一刻意不放进这两个方法内部**：那样"判重侧"与"写入侧"会各自 trim 一遍，
   两处规矩就又能分岔了 —— 归一必须发生在调用方、且是**同一个变量**。
4. **不给 `phone` 加格式注解，也不动 `email` 的 `@Email`。**
   给 `phone` 加 `@Pattern` 当然能挡住带空白的值，但那是把它从"**被归一**"改成"**400**"——
   与 `0071` 决策 7 同一条理由（过滤侧认的是归一一侧，同一个值"能归一、却被拒"是更糟的不一致）。
   `@Email` 保持原样：它挡住 email 的空白是**副产物**，本片不依赖它（决策 2 照样归一
   email），只把它当成"这一列当前没有可观测缺陷"的解释。
5. **不做存量值订正**（本仓**第一次**需要回答"要不要写 DML 迁移"）。结论是**不写**，
   三条理由：
   - **本仓没有生产部署**（版本号仍是 `0.0.1-SNAPSHOT`）。违反不变量的存量行只能来自
     "本轮 / `0071` 之前的写入口"，而它们只活在本机与 CI 的开发库里 ——
     一条 `UPDATE` 修的是**开发机上那几行**，代价却是一片**永久留在迁移史里的 DML**。
   - **边界不闭合。** 若按"同一条不变量"订正，那 `0071` 的七个过滤列
     （`app` / `namespace` / `traceId` / `sessionId` / `userId` / `deviceId` / `status`）
     在更早的窗口里同样写过带空白的值 ⇒ 按同一理由也该订正 ⇒ 那是跨
     `bw_client_log` / `bw_client_event` / 四张带 `status` 的 `bw_auth_*` 表（共 6 张）
     的普查，属独立一轮。反过来说：**只订正"寻址"这四列**会让"哪几列要订正"的答案变成
     "最近两篇 ADR 碰过的列"，那是一个会随每篇 ADR 外扩的边界。
   - **它是本仓反复推后的一件事，不是新问题。** `0045`（口令有效期"**不追溯存量**"）、
     `0051`（"**改存量数据**"不受 `40920` 约束）、`0069` / `0071`（都只改写入侧、
     **没有订正已经写坏的行**）是同一件事的不同侧面 ⇒ 它值得**单独立一篇**，
     而那一篇的头一件事就是**把射程一次划完**。
   - **用 `TRIM()` 兜存量被否掉。** 在判重 SQL 里写 `TRIM(col) = ?` 能让旧行也算得中，
     但那会造出**第三种"相等"** —— `0065` 刚把"相等"收进排序规则（并让三方言一律 NO PAD），
     `0066` 又确认搜索沿用同一条关系；再在判重里塞一个 `TRIM`，同一个问题就有了三个答案。
     附带代价：索引失效。
6. **不新增错误码。** `40902`「邮箱已被占用」/ `40903`「手机号已被占用」照旧 ——
   本片改的是"什么时候才轮到抛它"，不是"抛出什么"。

## 三 落地

**后端**（4 个已跟踪文件 + 1 个新用例）：

- `UserService` —— `create` / `update` 各取一次归一值、判重与入库共用；
  `existsEmail` / `existsPhone` 去掉内层判空白；`blankToNull` 删除。
  `countBy` 与两条注释（"邮箱与手机号没有唯一索引 / 软删即释放"）**一字未动**。
- `FilterValue` —— 类注释：写明"两端空白只剩一处实现"是 `0071` + `0072` 两篇合起来的结果；
  并补一段"它**对会被精确匹配的值是全序的**：判重也是一次 `eq`，判重入参与入库值必须共用
  同一个 `text()` 结果"。**方法签名一个字没改。**
- **前端零改动、契约零改动**（没动任何 DTO 注解、没动 `@Operation` 描述、没动错误码）。

**守卫**（`scripts/verify-filter-values.mjs` 加**规则 6**）：

`sts-server-auth` 里 `entity.set<Email|Phone|ContactEmail|ContactPhone>(...)` 与
`existsEmail(...)` / `existsPhone(...)` 的实参，**含 `request.getXxx()` 且不含 `FilterValue` ⇒ 报红**。
两侧都锚（写入口 + 判重口），因为本片的主决策就是"两侧共用一个值"。
这个判据的特点是**它能打红改动前的写法**：`entity.setEmail(blankToNull(request.getEmail()))`
正好落在射程里，而组织域那种合法的内联写法
（`entity.setContactPhone(FilterValue.text(request.getContactPhone()))`）不会。

**文档**：本篇 + `docs/README.md` §二/§四 + `server/README.md` 硬规则表 +
`scripts/README.md`。

## 扰动验位

- **用例**：改前 **5 红 3 绿** ⇒ 改后 **8 绿**（改动必要且充分）。
- **守卫规则 6** 扰两次都报红、行号指向那条语句：
  ① 把 `create` 的写入侧改回**改动前的原句** `entity.setEmail(blankToNull(request.getEmail()))`
  ⇒ 报 `UserService:149`（写入口）—— 这一条同时证明"这个守卫能逮住本片修掉的那个 bug"；
  ② 把它改回 `existsEmail(tenantId, request.getEmail(), null)` ⇒ 报 `UserService:137`（判重口）。
  两处都只改一个、另一次复原，还原 ⇒ 六条规则全绿。
- **射程边界也验了**：`OrganizationService` 的两处 `FilterValue.text(request.getContactXxx())`
  **不报红**（实参含 `FilterValue`）；两处的 `vo.setContactXxx(entity.getContactXxx())`
  **不报红**（锚点认的是接收者 `entity`，`vo` 装的是从库里读出来的值）。
- 规则 1~5（`0069` / `0070` / `0071` 遗留）本轮未动锚点，仍全绿。

## 后果

**正面**

- **`phone` 上那个"同一个手机号两个账号"的口子关掉了**，两个方向都关：库里是干净值时
  拿带空白建号、库里是带空白时拿干净值建号，现在都返回 `40903`。
- **`create` 与 `update` 对同一个字段的宽容度一致**（两处共用同一次归一）。
- 全仓"两端空白怎么处理"**只剩一处实现**：`FilterValue.text`。
  类注释里那句从 `0069` 写到 `0071`、长期只对一部分列成立的话，到本片为止完全成立。
- 规律上，这是"**同一件事的入口不止一个**"这一族的又一例：`0071` 是"读侧归一了、写侧没归"，
  本片是"写侧归一了、**判重**侧没归"。三次（`0067` 关键词 / `0071` 写入值 / `0072` 判重）
  都是**同一个值从两个入口进系统**，而只改一个入口的结果都不是"没修好"，
  是**修出了一处新的不一致**。

**负面**

- **`blankToNull` 这个更像"取名"的方法名没了**：`FilterValue.text(request.getPhone())`
  读起来不如 `blankToNull(...)` 直白。代价用 `UserService` 里那段注释消掉。
- **规则 6 的白名单是四个列名 + 两个方法名**，与规则 4 / 5 同一个代价（新列名锚不到）。

**后续约束**

- **`email` / `phone` 上任何"再加工"（归一大小写、去内部空格、格式化手机号）
  都必须同时落在判重侧与写入侧** —— 它们是一个值、两个入口。
  规则 6 只挡"直传 `request` 原值"，**挡不住"只改一侧的再加工"**。
- 新增一个"会被精确匹配"的列时，先问一句：**它有几个入口？**（过滤 / 判重 / 排序 / 唯一索引）
  每个入口都必须过同一关。

## 「未覆盖」

1. **达梦未实测。** 本篇改动全在 Java 侧（`FilterValue.text` 与两处判重），不落到 SQL 上；
   但"归一之后库里不会再出现带空白的 `phone`"这件事只在 h2 与真实 MySQL 上验过
   （与 `0067`「未覆盖」1、`0069`「未覆盖」1、`0070`「未覆盖」1、`0071`「未覆盖」1 同源）。
2. **存量值未订正**（决策 5）。射程需要一次普查才能定：**"哪些列会被精确匹配"×
   "哪些历史窗口没有归一"**。已知会落进去的至少是 `0071` 的七个过滤列（6 张表）+
   "寻址列"四列（`bw_auth_user` 两列 + `bw_auth_organization` 两列，2 张表）；
   边界一旦按"同一条不变量"划，就该**一次划完**，
   不能再按"最近哪篇 ADR 碰过"划。列在这里而不是"刻意不做"，是因为它**不是决策、
   是没做**（且它是本仓第一次需要 DML 迁移的地方）。
3. **规则 6 看不到"先取局部变量、再直传原值"**（`String phone = request.getPhone();`）。
   判它要做数据流分析，与规则 1 的注释里那条"刻意不查"同源 ⇒ 按 `0064` 不做。
   射程外的那一种靠评审 + `AddressNormalizationApiTest` 钉着。
4. **组织域的 `contact_email` / `contact_phone` 没有运行时断言**：`0071` 把它们收进了
   `FilterValue.text`，本片只给它们补了"同形守卫"（规则 6 的射程含 `ContactEmail` /
   `ContactPhone`）。承 `0066`「未覆盖」2 · `0069`「未覆盖」6 · `0070`「未覆盖」5 ·
   `0071`「未覆盖」6 —— 同一个"只用例盖了三个域里的一个"的缺口。
5. **`email` / `phone` 要不要归一大小写**仍未答。本片把它**钉住**了（判重沿用 `0065` 的
   "区分大小写"），但"该不该"是另一回事：一个 `PROBE@BW.TEST` 与 `probe@bw.test`
   现在可以是两个账号。与 `0065`「未覆盖」同源。
6. **`?status=`（空串）与不传的处理仍未单独断言**
   （承 `0069`「未覆盖」7 · `0070`「未覆盖」6 · `0071`「未覆盖」7）。
7. **`username` / `tenantCode` 等标识列不 trim**：`username` 有 `@Pattern`（空白进不来）、
   `tenantCode` 不判重也不过滤 ⇒ 都不在射程。列在这里是说明"射程到 `email` / `phone` 为止"。
