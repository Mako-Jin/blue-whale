# 0003. 配置分域：三层配置与自研边界

- **状态**：已采纳
- **日期**：2026-10-09
- **决策者**：舰长

## 背景

规划后端时需要提供"配置服务"，且已知要兼容大量异构配置：既有客户端需要的（开关、超时、接口地址），也有服务端需要的（数据源、中间件、密钥）。

最容易走的弯路是**做一个万能配置服务**——一个接口、一张表、一套读写权限装下全部配置。这条路线的结局是确定的：它会退化成上帝对象，谁都能加字段、没人敢删字段，最终没人说得清某个字段还有没有用；更严重的是**把密钥和业务开关放在了同一个安全等级与同一个变更流程里**。

真正的问题不是"怎么存配置"，而是：

1. 配置应当按什么维度切分，才不至于互相污染？
2. 哪些层该自研、哪些层必须用成熟组件？
3. 客户端拿配置这件事，有哪些不可让步的底线？

## 决策

### 1. 配置按「作用域 + 敏感度」分三层，载体各不相同

| 层 | 内容 | 载体 | 归属 |
| --- | --- | --- | --- |
| **业务运行期配置** | 功能开关、灰度、主题、超时、接口地址 | **自研**，走 OpenAPI 契约下发 | 本项目 |
| **部署级配置** | 数据源、中间件地址、线程池、限流阈值 | **成熟组件**（Nacos / Apollo） | 运维 |
| **密钥级配置** | 数据库密码、第三方 Key、证书 | **Vault / KMS** | 安全 |

三层的**变更流程、安全等级、发布节奏完全不同**，因此不合并。

### 2. 自研范围只有「业务运行期配置」

理由：只有这一层具备业务语义、需要两端共享类型。下两层自研是纯浪费，而且密钥管理实现错一次就是安全事故。

**这一层现在不动手**，因为后端尚不存在，过早实现等于猜需求。本 ADR 只固化原则，实现随后端配置服务一起落地。

### 3. 客户端配置下发的五条底线

1. **首屏零阻塞**：配置未就绪时用**内置默认值**渲染，配置到达后应用。不允许首屏等配置接口。
2. **兜底默认值必须在客户端**：配置服务不可用时，应用仍须以内置默认值正常启动。这是可用性底线，不是优化项。
3. **版本化 + 缓存 + 变更通知**：不允许每次请求都拉配置，也不允许永不更新。用版本号 / ETag 配合短轮询。
4. **配置项有 schema 与类型**：前端消费配置必须类型安全，类型经 OpenAPI 契约生成（对齐根 `README.md` 铁律 2）。
5. **环境物理隔离**：dev / test / staging / prod 分开部署或分空间，不允许靠 key 前缀区分。

### 4. 命名与审计约束

- 配置键采用统一后缀风格，**同一个仓库内只允许一种写法**（如 `xxxEnabled`），禁止 `enableXxx` / `xxxSwitch` 并存。
- 配置变更必须留痕：**谁、何时、把哪个键从什么改成了什么**。没有审计就无法在事故后归因。
- 语义解释权归契约：同一份配置在两端的行为必须由契约定义，**不允许两端各自解释**。

## 后果

**正面**

- 密钥与业务开关分属不同安全等级，不会被同一条低门槛流程改到
- 自研面收敛到一层，维护成本最小
- 客户端配置的失败路径被显式设计（内置默认值兜底），而不是留给运气
- 后端搭配置服务时有明确边界，不会长成上帝对象

**负面 / 代价**

- 需要维护三套配置载体，运维心智成本高于"一个地方全放"
- 引入 Nacos / Apollo / Vault 等外部组件的部署与运维负担
- 客户端兜底默认值需要与远端配置**人工保持同步**，是一处需要纪律的地方

**后续约束**

- 新增任何配置项前，先判定它属于哪一层；分不清就说明切分有问题，先讨论再动手
- 业务运行期配置的所有键，进入 OpenAPI 契约后才允许被前端消费
- 密钥级配置**禁止**出现在代码仓库、普通配置中心、日志输出中
