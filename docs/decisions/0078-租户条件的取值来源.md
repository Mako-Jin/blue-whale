# 0078. 租户条件的取值来源：`0077` 说"静态看不出来"，而它看得出来

- **状态**：已采纳
- **日期**：2026-10-16
- **决策者**：舰长

## 背景

`0077`「未覆盖 2」挂着一条，原文是：

> **查询路径的租户条件从哪来**：规则 C 判的是"比较"、规则 D 判的是"按主键取实体"，
> 而 `page` / `stats` 那类查询走的是 `.eq(Entity::getTenantId, <某个变量>)` ——
> 变量是否来自落点，静态看不出来（要追局部变量赋值）。……
> **这是本片之后守卫最大的空白**。

同一句话也写在 `scripts/verify-tenant-visibility.mjs` 的「刻意不查的」里。
本片领它，射程是一句话：**写成 SQL 条件的那一刻，那个租户 id 是从哪儿取来的。**

### 那句话里对了一半

**"要追局部变量赋值"是对的，"静态看不出来"是错的。** `0076` 留下的判据在这里同样成立 ——
**问"这东西是什么"能，问"它叫什么"不能**。要问的是"这个租户 id 从哪来"，
而答案在源码里只有三个地方（第四种就是危险的那一种）：

| # | 来源 | 形状 |
| --- | --- | --- |
| 1 | **落点** | `TenantService#resolveQueryTenant` / `#resolveWriteTenant` / `#currentReadTenant` 的返回值 |
| 2 | **认证上下文** | `AuthContextHolder.require().getTenantId()`（以及会话对象上的 `getTenantId()`） |
| 3 | **实体自身** | `@TableName` 类型上的 `getTenantId()`；对象本身就是 `bw_auth_tenant` 时的 `getId()` |
| 4 | **请求绑定类型** | ❗`*Controller` 形参上绑定的那些 DTO —— **唯一危险的那一种** |

第四种危险的理由是 `0025` 第 2 条：**别家租户在系统里就是不存在**。
所以调用方指定的租户 id 只可能有两个下场 —— 查询时**被忽略**、写入时**被拒绝**，
而这两件事都只在落点里发生（`0074`）。**这就是本片要守的那一句。**

### 侦察：两种形状 × 四类来源（全仓普查）

租户条件在本仓只有两种写法，而**第二种此前没有任何文档提过**：

| 形状 | 处数 | 说明 |
| --- | --- | --- |
| `E1` `.eq(<X>::getTenantId, ARG)` | **23 处** | lambda wrapper 的条件 |
| `E2` SQL 文本里的 `#{tenantId}` | **17 处 / 11 个方法 / 8 个 Mapper** | `@Select` 10 个方法 · `@Insert` 1 个（`insertRecord` 的列清单） |

只守 `E1` 会漏掉**一半**的租户条件 —— 而"只守得住的形状"正是 `0077` 修过的那种不对称：
规则 D 之所以存在，正是因为规则 A 看不见三条记录管道。**这是本片的第一个决策理由。**

侦察的结论是**零缺口**：34 处来源全部合法。

| 来源 | 处数 | 位置举例 |
| --- | --- | --- |
| 落点 | 16 | `AuditLogService`（经 `Visibility`）· `ClientLogService` ×4 · `ClientEventService` ×3 · 四个 CRUD 域的 `page` / `tree` |
| 实体自身 | 12 | `OrganizationService#enabledSubtreeIds`（`root`）· `#rewriteSubtree`（`node`）· `OrganizationMemberService`（`org.getTenantId()` 透传）· `insertRecord`（唯一形参那个实体） |
| 认证上下文 | 2 | `DataScopeService#resolve` · `OrganizationMemberService#listByUser` |
| 落点 + 实体自身 / 上下文 | 4 | 三处形参在多个调用点上来源不同，逐点都合法 |

**零缺口不是"不用写守卫"的理由** —— `0074` / `0075` / `0076` 都是零缺口，
而它们各自留下了一份守卫。守卫管的是**下一次改动**，不是今天这一版源码。

### 侦察里同时撞见一条相邻的空白

`@Update("UPDATE bw_auth_rel_org_user SET deleted = 0 WHERE id = #{id}")` 这类
**"按主键改"的注解 SQL 完全没有租户条件**（`rel_*` 四个 Mapper 各一处）。
现状是安全的但**只是一次手工核对**：`restoreDeletedById` 的 `id` 来自
`selectAnyByOrgAndUser`（按组织 + 用户查，不是按主键），而且调用方已先确认过归属。

它是**规则 A / D 在写侧的镜像** —— 那里压根没有租户值可判，所以不属本片射程。
留在「未覆盖 1」（`0076` 未覆盖 5 的邻居）。

## 决策

### 1. 判据只有一条：来源不得是"请求绑定类型"上的租户

三类合法来源放行，第四类判红。**判断的对象不是"值对不对"，而是"它从哪来"** ——
这与 `0071` / `0072` 那两轮"值规范化"的口径不同：那一族问的是"这个值归一了吗"，
这一族问的是"这个值是谁给的"。两者的失败面也不同：前者造出匹配不上的假阴性，
后者造出**跨租户读到 / 写到别家数据**。

### 2. "请求绑定类型"从源码推导，零白名单

定义：**`*Controller` 里带注解的形参的声明类型**（实测 35 个，含 `*Query` / `*SaveRequest` /
`*BindRequest` 等，以及 `@PathVariable` 带来的 `Long` / `long` / `String`）。

- 取**注解**而不是取名字（`*Query` / `*Request`）：名字是人起的，没有形状（`0064`）；
  而"这个形参是不是从 HTTP 请求绑上来的"在源码里有唯一答案 —— 它带着注解。
- **构造器形参没有注解**，所以不会被收进来。这一条是踩出来的：不筛注解的话
  `AuditLogController(AuditLogService auditLogService)` 会把 `AuditLogService`
  也算成一个"请求绑定类型"，于是十几处正当写法当场变红（脚本第一版实测）。
- 附带的收益：`@PathVariable Long id` 带来的标量也在集合里。这是**特性不是噪声** ——
  `.eq(X::getTenantId, somePathVariable)` 与读 DTO 一样危险。

### 3. 两种形状一起守，且 E2 的判据落在**调用点**上

- SQL 文本里没有"从哪来"这件事，**只有调用点才有**；
- 例外是 `@Insert` 那种**唯一形参**的写法：`#{tenantId}` 从那个 bean 上读属性，
  没有调用点可看，判据就是**那个形参的类型是不是实体**；
- 两条形状共用同一个分类器，所以同一个变量同时喂给 `.eq` 与注解 SQL 时，
  **两处会一起红**（扰动轮 3 实测）。

### 4. 裸标识符按一跳追；追不到就红

链路三层，每层都只用源码里的字面量：

```text
裸标识符 t ──▶ 本方法内的局部初值 ──▶ 本方法形参 ──▶ 该形参的调用点实参
                    （单次赋值）        （位置对齐）    （接收者从字段声明读出来）
```

- **局部那一层**：`Long tenantId = <expr>;` —— 只有本方法、只取第一次赋值。
  取不到就落到下一层。
- **形参那一层**：先看**同文件里的自调用**（私有方法只可能这么被调），
  不是私有的话再看**本模块里带接收者的调用** —— 接收者的名字从
  "哪个类声明了这个类型的字段 / 参数"读出来，所以
  `organizationMemberService.primaryOrganizationOf(…)` 认得出，
  而与它同名的别的方法不会被当成本方法的调用点。
- **追不到就红**（`0076` 的自检要求）：既不是局部也不是形参 ⇒ 红；
  是形参但一个调用点都找不到 ⇒ 红；来源表达式认不出属于哪一类 ⇒ 红。

**声明与调用不靠名字区分。** 参数表那些 `(` 是**显式**收进 `declarationParens` 的
（成员的用"配平终点紧邻方法体"定位，注解 SQL 的用"声明里的第一个 `(`"定位）。
第一版靠"参数表后面跟不跟 `{`"来判 —— 在 **Mapper 接口**上失效：接口方法没有 `{`，
于是每一个声明都被读成了它自己的调用点。那条路的症状不是"少报"，是**报出来一屏废话**
（`?()` · 传了「SELECT gm.user_group_id FROM bw_…」），而这正是 `0064` 说的
"会误报的守卫比没有更糟"。

### 5. 落点改名只会变红，不会静默离开射程

分类器里写着 `resolveQueryTenant` 这些名字，所以改名会让那几处"认不出"从而**变红** ——
**报错方向是"多报"而不是"漏报"**。为了让那句红话说得清楚，另有一条自检确认三个落点名
还在 `TenantService` 里（改了名、或落点搬了家，都先红在自检上）。
这条与 `0077` 的"落点不写名字"**方向相反而目的相同**：那里靠"从声明里读"避免写名字，
这里靠"追不到就红"保证写了名字也不会静默失效。**两条路的共同点是失败方向朝红。**

### 6. 不写进 `verify-tenant-visibility.mjs`，另起一支脚本

`scripts/verify-tenant-scope-source.mjs`。三条理由：

1. **问的问题不同**：那支问"判定的落点在哪"（比较 / 按主键取实体），这支问"条件的取值从哪来"；
2. **射程的定义方式不同**：那支的射程是**模块推导**的（"接上了租户服务的模块"，`0076` / `0077`），
   因为这支的判据是"这个模块在用那套租户语义"；本支的射程是**自然射程** ——
   "凡出现租户条件的地方"（`.eq(::getTenantId)` 与 `#{tenantId}` 就是全部两类，
   全仓没有 `ne` / `in` / `like` / `orderBy` 上的租户条件）。两者不需要互相推导。
3. **需要的解析机制不同**：本支要"方法体 + 跨文件调用点"，那支要"DDL 三方言 + Mapper 泛型链"。

`0077` 把规则 D 并进那支脚本是对的（**它与规则 A 是同一个模型的镜像**）；
本支不是那一支的镜像，是**第三个问题**。三者的分工一句话：
**规则 C 管"比较"、规则 D 管"按主键取实体"、规则 E 管"条件的取值来源"。**

### 7. 刻意不做

- **不改任何生产代码。** 侦察结论是零缺口，而这一族的守卫**不需要改代码就能装上** ——
  这是 `0074` / `0075` / `0076` / `0077` 都没有做到的（那四片都动了行为）。
  本片是第一条**零行为变化**的守卫片，`git diff` 里没有 `.java`。
- **不查 `@Update … WHERE id = #{id}`**（未覆盖 1）：那里没有租户值可判，是另一个问题。
- **不查 `#{it.tenantId}`**：它出现在 `@Insert` 的列清单里，取的是待插入实体自己的租户 ——
  那是"这行数据归谁"（写侧落点 `resolveWriteTenant` 的事），与"条件从哪来"不是一件事。
  射程只认裸 `#{tenantId}`，所以它天然在外。
- **不给 `entity.setTenantId(...)` 加射程**：`0071` / `0074` 的那一半。
- **不把 `SFunction` 局部变量纳入射程**：把 `Entity::getTenantId` 先存进变量再传，
  落在形状之外（本仓零处）。与那支脚本"先取局部变量再比"是同一格代价（`0072` 规则 6）。

## 实测

### 侦察：射程与来源分布

```text
✓ 三个查询落点在租户服务里都还在（改了名不会静默离开射程，只会变红）
    resolveQueryTenant · resolveWriteTenant · currentReadTenant
✓ 射程非空（.eq 23 处 · SQL 里的 #{tenantId} 11 个方法 · 请求绑定类型 35 个）
✓ SQL 里的租户值只来自落点 / 认证上下文 / 实体自身
    34 处全部可推导 —— 读的是"请求绑定类型"上的租户才算越权
```

（`34 = 23 + 11`：`E1` 按处数、`E2` 按方法数 —— 后者的判据在一个方法的所有调用点上，
所以方法数与 `#{tenantId}` 的处数（17）不同。）

### 七轮扰动：每一轮都精确红，两个反例都不红

| 轮 | 扰动 | 结果 |
| --- | --- | --- |
| 1 | `UserService:69` 绕开落点、直取 `query.getTenantId()` | **只红 E1**，并指名请求绑定类型 `UserQuery` |
| 2 | `ClientLogService:167` 那个**调用点**换成 `query.getTenantId()` | **只红 E1**，并**指名调用点行号**（`167:29`）—— 形参的来源只在调用点上看得见 |
| 3 | `ClientLogService:256` 的来源换成认不出的 `tenantOf(query)` | **同时红 E1 与 E2 两处** —— 同一个变量既喂 `.eq` 又喂注解 SQL，两条形状口径一致 |
| 4 | `UserService:128` 的注解 SQL 调用点传 `request.getTenantId()` | **只红 E2**，并指名 `UserSaveRequest` |
| 5a | **反例**：把落点**内联**进 `.eq` 的实参（等价重构） | **全绿** —— 判据看的是来源，不是当前那行文本 |
| 5b | **反例**：先取局部变量再传（等价重构） | **全绿** —— 一跳解析真的在工作（不是靠"今天的源码刚好长这样"） |
| 6 | 落点改名（声明与调用点一起改） | **红**：自检 + 认不出 ⇒ 报错方向是**多报**而不是漏报 |

轮 5a / 5b 是本片最重要的两轮：那条被 `0077` 判定为"静态看不出来"的事，
如果守卫只是把今天的 34 行文本抄成了模式，这两个**语义等价、文本不同**的重构就会误报。
两轮全绿说明判据落在**来源**上。
轮 6 走的是另一头：改名**必须**响 —— 要么响在自检上，要么响在"认不出"上，不许静默。

### 全量回归与全套自检

`mvn -o -T 1C test` 全模块 **BUILD SUCCESS**，**52 个测试类 / 327 条 / 0 失败 0 跳过**
（与 `0077` 同基线 —— 本片没有动过一行 Java）。**十条**零前置自检全绿
（`0077` 是九条，本片 +1）。

## 后果

### 正面

- **`0077` 留下的"最大空白"关掉了。** 从那以后，"查询路径上的租户条件"不再靠一次
  人工核对，而有机器守着；两种形状一起守，所以不会出现"守住了 `.eq`、漏了注解 SQL"。
- **判据第一次落在"来源"而不是"写法"上。** 前几片的判据都是"某个调用在不在" /
  "某个码对不对"；这一片要回答"这个值是谁给的"，而它仍然做到了零白名单 ——
  靠的是把"谁给的"翻译成**类型问题**（`0076` 的判据第二次适用）。
- **`E2` 这一族的射程是普查出来的**：11 个方法 / 17 处 `#{tenantId}` 此前没有任何文档
  点名过（`scripts/README.md` 只提过三个手写聚合 SQL 的实参不许是 `query.getXxx()`，那是
  值规范化那一族的事，判的也不是"从哪来"）。
- **报错方向可预期**：追不到 ⇒ 红，认不出 ⇒ 红，落点改名 ⇒ 红。三处都是"多报"，
  所以这套守卫的失效模式是"有人来关掉它"，而不是"它安静地什么都没查"。

### 负面代价

- **新增一支 690 行的脚本与一个 CI 步骤**。它比前几支重的部分全在"一跳解析"上
  （方法体切片 + 跨文件调用点 + 声明/调用区分），而这部分是**必须**的：
  只看调用形状就等于把今天的 34 行文本抄成模式，轮 5a / 5b 会红。
- **形参的来源射程是同模块**。本仓 8 处形参来源全在同模块内，够用；
  一个跨模块的同名方法会同时被当成两处 ⇒ 代价是**误报**而不是漏报（可接受的方向）。
- **`typeOfIdent` 的兜底会扫整份文件**（本方法找不到声明时）。它是"多收"的一侧，
  影响的是"这句话该算请求绑定类型的吗"，只会让判红更容易、不会让判红更难。
- **`boundTypes` 这个名字比它实际宽**：它含 `@PathVariable` 带来的标量（`Long` / `String`）。
  这是有意的（见决策 2），但读代码的人容易以为它只收 DTO。

### 后续约束

- **新增一处租户条件（`.eq(::getTenantId)` 或 `#{tenantId}`），值只能来自那三类。**
  要给查询加"点名租户"的能力，先走 `0074` 未覆盖 1 那条产品决定 ——
  而**不是**在调用点把 `request.getTenantId()` 传下去。
- **`@Insert` 里 `#{tenantId}` 从唯一形参的实体上读**：把参数从实体改成散参时，
  要同时给它一个 `@Param("tenantId")`，否则守卫会红在"绑到谁身上认不出来"上。
- **改分类器里那三个落点名的拼写 = 改射程**。脚本头、自检与这一段都写了这句。
- **`E2` 的判据在调用点，所以"SQL 改对了、调用点没改"照样红** —— 这是有意的：
  值的来源不是 SQL 决定的。

## 未覆盖

1. **`@Update … WHERE id = #{id}` 这类"按主键改"的注解 SQL 完全没有租户条件**
   （`rel_*` 四个 Mapper 各一处）。它是规则 A / D 在**写侧**的镜像，而本片的射程
   是"条件的取值来源"（那里没有租户值）。今天的答案是"安全的，但是一次手工核对"：
   `restoreDeletedById` 的 `id` 来自 `selectAnyByOrgAndUser`（按组织 + 用户查，
   不是按主键），且调用方已先确认过归属。**要机器守它，判据得是"按主键改的出口
   必须能追到一次租户范围内的选取"** —— 那要调用图，且"追不到"与"追到了但人看漏了"
   不容易分开，留给下一片。
2. **达梦未实测**（全仓同一条，`0073` 未覆盖 1）。本片只读源码文本，与方言无关。
3. **`SFunction` 局部变量**：把 `Entity::getTenantId` 先存进变量再传，落在形状之外
   （本仓零处）。与那支脚本"先取局部变量再比"同一格 —— `0072` 规则 6 登记过的那类假阴。
4. **`.eq` 之外的条件形状**：`ne` / `in` / `like` / `orderBy` 上的租户条件全仓零处，
   所以射程只认 `eq`。将来有人写出 `.ne(UserEntity::getTenantId, x)` 它不在射程 ——
   但那种写法在本仓没有正当用途，一眼可见。**不预先把射程铺成"所有 wrapper 方法"**
   是因为那会把"哪些方法算条件"变成一个需要维护的名单（`0063` 的白名单要核对条数）。
5. **跨模块的调用点**：形参来源的搜索射程是同模块（见负面代价）。
6. **`#{it.tenantId}` 背后的写侧归属**：`resolveWriteTenant` 那一半由 `0074` 守着，
   本片没碰。
7. **`0025` 未覆盖 3 的"过滤条件那一类"**：审计的时间窗与 `resource` 过滤仍是纯查询参数、
   没有必传约束 —— 与本片的"来源"是两件事（那一件问"哪些条件必须有"）。
8. **`0077` 未覆盖 1 / 3~8**、`0076` 未覆盖 1~3 / 5~8、`0075` 未覆盖 1~6 等仍然挂着，
   本片没有推进（清单见各篇）。
