# 0067. 搜索关键词的转义

- **状态**：已采纳
- **日期**：2026-10-15
- **决策者**：舰长

> 领的是 `0066`「未覆盖」第 1 条：**`LIKE` 的通配符没有被转义** ——
> "`keyword` 是原样拼进 `LIKE '%…%'` 的，所以用户在搜索框里输入 `%` 或 `_`
> 会被当成**通配符**（输 `%` = 匹配一切）……本轮没有改 —— 它是一次独立决定，
> 且要先定'是转义、还是干脆禁止这两个字符'。"
>
> 核完的结果是：**要转义，但"怎么转义"这一步本身还有一次没被量过的分叉** ——
> 用 `LIKE` 的默认转义符（反斜杠）与**把转义符写进 SQL**，在一个很常见的
> MySQL 配置下**表现不同**，而且前者是**静默**失败。本篇把两者都量了。

## 背景

### 1 机制：MyBatis-Plus 不转义（字节码级）

`Wrappers.lambdaQuery().like(列, 值)` 的实参处理在
`com.baomidou.mybatisplus.core.toolkit.sql.SqlUtils#concatLike`，
3.5.17 的字节码就是三条分支拼 `"%" + 值` / `值 + "%"` / `"%" + 值 + "%"` ——
**没有任何一处转义**。`SqlLike` 这个枚举也只有 `LEFT` / `RIGHT` / `DEFAULT`
三个常量，没有"转义"这个概念；`likeValue` 只把值交给 `concatLike` 再绑成参数。

⇒ 所以"用户输的 `%` 会不会被当通配符"这件事，**此前由数据库的 `LIKE` 语义代答**，
而本仓在搜索这一层**从来没有决定过它**（与 `0065` 的"相等语义"、`0066` 的
"匹配敏感性"是同一类问题的第三次现身）。

### 2 射程：7 处搜索、15 个列条件

`keyword` 出自 `Query` 对象、由前端六个搜索框（用户 / 用户组 / 租户 / 角色 /
资源 / 组织）与日志控制台发来。全部落在两件事上：**把关键词前后补 `%` 再比**。

| 域 | 列 | 取关键词的方式 |
| --- | --- | --- |
| 用户 | `username` · `display_name` · `email` | 原文（只判空） |
| 用户组 | `group_code` · `group_name` | `normalize`（trim） |
| 租户 | `tenant_code` · `tenant_name` | 原文（只判空） |
| 角色 | `role_code` · `role_name` | `normalize`（trim） |
| 资源 | `resource_code` · `resource_name` | 原文（只判空） |
| 组织 | `org_code` · `org_name` · `full_name` | `normalize`（trim） |
| 客户端日志 | `message` | 原文（只判空） |

**另外两处 `likeRight` 不在射程**：`OrganizationService` 用
`likeRight(codePath, prefix)` 查子树，而那个 `code_path` 是
`pathOf()` 拼出来的 **"各级主键 + 斜杠"**（形如 `/1/5/`）——
里面只有数字与 `/`，用户手打的通配符进不来。

## 一 实测：先纠正一个**会骗人的**探针

第一版探针用的是 SQL 字面量（`c LIKE 'a\%b'`），结果 H2 上
"转义前的 `abc`"也命中了 —— 看着像"转义没生效"。真因是
**H2 的 `MODE=MySQL` 会把字符串字面量里的 `\` 当转义符吃掉**：
`'a\%b'` 到达 `LIKE` 时已经是 `'a%b'`。那次量到的是**解析器**的行为，不是 `LIKE` 的。

⇒ 换成 **`PreparedStatement` 的绑定参数**（MyBatis 正是这么传的），
两台引擎、同一段 SQL、四种候选方案：

| 探针（存 `abc` · `a%b` · `a_b` · `aXb`） | H2 2.4.240 | MySQL `_as_cs` | MySQL + `NO_BACKSLASH_ESCAPES` |
| --- | --- | --- | --- |
| 现状：输 `%` | **4（全表）** | **4（全表）** | **4（全表）** |
| 现状：输 `a_b` | **3**（`a%b`/`a_b`/`aXb` 全中） | **3** | **3** |
| 现状：输 `a_c` | **1**（命中的是 **`abc`**） | **1**（`abc`） | **1**（`abc`） |
| 方案甲：实参转义 `\%`（靠默认转义符） | 1（命中字面量 `%`）✓ | 1 ✓ | **0 —— 静默失效** |
| 方案乙：SQL 里 `LIKE ? ESCAPE '!'` + 实参转义 | 1 ✓ | 1 ✓ | **1 ✓** |

两句话：

1. **现状是缺陷，不是特性。** 输 `%` 列出全表、输 `a_b` 把 `a%b`/`aXb` 一起捞出来，
   而搜索框上写的是"按登录名 / 姓名 / 邮箱搜索"。"我要找含 `%` 的那条"
   （日志正文里的占位符、格式化串）是一个真实意图，不是一个没人知道的语法。
2. **"转义"这一步本身还有一次分叉，而且甲方案会静默骗人。**
   反斜杠是 `LIKE` 的**默认**转义符，靠它就等于把"转义到底生不生效"
   又交给数据库的默认值代答 —— MySQL 一旦把 `NO_BACKSLASH_ESCAPES` 打开
   （非默认，但 DBA 会开），`\%` 不再是转义序列，于是**用户输自己完整的
   登录名反而搜不到，并且不报错**。乙方案把转义符**写进 SQL**，在四格里全对。

**这一条是 `0065` 的教训的直接复用**：那一片的病因就是"三个方言各自默认值互不相同"，
处置是把它写进 DDL；这里同理 —— 把它写进 SQL。

## 二 决策

**转义 `%`、`_` 与转义符自身，并把转义符写成 `ESCAPE '!'`。**

- **不做"禁止这两个字符"**：`org_code` / `resource_code` / `username` 的形状里
  **本来就允许下划线**（`^[A-Za-z][A-Za-z0-9_]{0,63}$` 等），搜"我自己那个带下划线的编码"
  是正经用法。"禁止"会把一个合法输入判成错误。
- **不用反斜杠**：理由即上表 —— 它由数据库默认值代答，且失败是静默的。
  同理也不引第三方工具类：这件事的全部内容就是"一个转义 + 一句 `ESCAPE`"。
- **转义符选 `!`**：它在字符串字面量里不特殊（不受 `NO_BACKSLASH_ESCAPES` 之类影响），
  也不与 `%` / `_` 的语义纠缠。
- **收在一个类里**：`sts-common-db` 新增 `KeywordLike`
  （`pattern(keyword)` → 已转义的实参；`condition(column)` → `列 LIKE {0} ESCAPE '!'`），
  15 个条件全部改用它们，**不再有裸的 `like()`**。

## 三 落地

1. **`KeywordLike`**（`com.bluewhale.sts.common.db.query`，`sts-common-db` 模块）——
   `auth` 与 `log` 两个服务模块都依赖它。`condition()` 会断言列名的形状
   （`^[a-z][a-z0-9_]*$`）：它拼的是字符串、看着像能塞任何东西进去，
   而"绝不把外部输入拼进 SQL"这条约定在这里由一次**运行期就会炸**的检查兜着。
2. **7 个服务、15 个列条件**改成 `apply(condition("列"), pattern)`。
   `apply` 的 `{0}` 由 MyBatis-Plus 格式化成**绑定参数**（不是拼接）——
   日志里能看到 `username LIKE ? ESCAPE '!' OR display_name LIKE ? ESCAPE '!' …`。
   **各域原有的判空口径一个字没动**：4 处仍旧先 `normalize`（含 trim），
   3 处仍旧只判空（不 trim）—— 那是另一件事，不在本片射程（见「未覆盖」3）。
3. **机械守卫 `scripts/verify-like-escaping.mjs`**（零前置、进 `guards` job）：
   - `server/*/src/main/java` 里**没有裸的 `like*` 调用**，除非在 `ALLOWED` 登记过
     —— 登记的动作就是回答"这个实参是从哪来的"。
   - 带 `LIKE` 的 SQL 片段**同一行必须有 `ESCAPE`**。
   - **登记的条数要逐条对上**：这一条是照 `0055`「只钉一支等于没钉」加的 ——
     只登记"形态"的话，两处同名调用改掉一处、另一处还在，检查照样报绿
     （当次扰动实测过这个假绿）。
4. **`SearchWildcardApiTest`（4 例，跨 profile）** ——
   不 `@Transactional`、不按 profile 跳过，与 `TextEqualityApiTest` /
   `SearchMatchApiTest` 同形。
   - **每条断言都配一个只差一个字符的"陪跑行"**：正主姓名里是 `%` / `_` / `!`，
     陪跑里是 `x`。转义对了只命中一个；通了任意一种通配符就会命中两个。
     只断言"搜得到"的话，出事的那种实现**也会绿**（它的匹配集是超集）——
     `0066` 已经吃过一次这个形状的亏。
   - 第 3 例专门钉**转义符自身**：若漏了 `!`，`…a!b` 里的 `!b` 会被当成"转义后的 `b`"，
     一个字面量里带 `!` 的串就**再也搜不到它自己**。
   - 第 4 例是回归（不含通配符照常搜得到），确认转义没有把普通搜索弄坏。

**扰动验位（当次实测）**

- 把 `KeywordLike.pattern` 改回不转义 ⇒ 4 例里 **3 例变红**：
  `%` 与 `_` 两例 `expected: <1> but was: <2>`（陪跑行被一起捞出来）、
  `!` 那一例 `expected: <1> but was: <0>`（正主搜不到自己）；回归例仍绿。
- 守卫三个方向：加一处裸 `.like(` ⇒ 红；把 `condition()` 里的 `ESCAPE` 删掉 ⇒ 红；
  把两处 `likeRight(getCodePath)` 改掉一处 ⇒ **"裸调用"与"条数对不上"一次红两条**。

**真实 MySQL 上验过**：用干净实例（库按 `0065` 的 `utf8mb4_0900_as_cs` 建）跑
`-Dspring.profiles.active=mysql` 的三个跨 profile 类 ⇒ **13 例全绿**，
SQL 侧与 h2 同形。

## 后果

**正面**

- **"输 `%` 列出全表"没了**，七个搜索入口一起好 —— 而这是用户自己就能撞上的一类意外
  （`%` 在日志正文里到处都是）。
- 转义**不再依赖任何数据库默认值**：`ESCAPE` 写在 SQL 里，
  `NO_BACKSLASH_ESCAPES` 之类的服务端策略改不动它。
- 这条约定**有机械守卫**（锚定 `.like(` 这个方法名 —— 无歧义的 token 形状，
  不是 `0064` 那种要理解语义的判定），新加搜索时漏了会红，且**条数对账**挡住了"只钉一支"。
- 顺带留下一条坑的记录：**量 `LIKE` 不能用字面量探针**（H2 在 MySQL 模式下会吃掉
  `\`），必须用绑定参数 —— 否则量到的是解析器而不是 `LIKE`。

**负面 / 代价**

- **`apply` 在本仓是第一次用，且它要手写物理列名**：`.like(lambda)` 的编译期检查
  在这 15 个条件上换成了字符串。代价由两处兜着：`condition()` 的形状断言、
  以及守卫脚本（它扫的就是"还有没有裸 `like*`"）。
- **多了一个模块间的公共类**：`sts-common-db` 此前只有自动配置，
  现在多了一个"查询片段"工具。它放在那里是因为 `auth` 与 `log` 都依赖该模块、
  而搜索跨这两个模块 —— 就地复制两份会让"转义符是 `!`"这件事有两个真值来源。
- **搜索行为变了**：以前输 `%` 能得到"全表"这种（没人要的）结果，现在得到"含字面量 `%`"。
  方向是**更精确**。

**后续约束**

- **加一处搜索**：用 `KeywordLike.pattern` + `KeywordLike.condition`，
  **不要再写 `.like()`**；否则 `guards` job 会红（并告诉你该写什么）。
- **写"搜索能不能搜到"的用例**：照 `SearchWildcardApiTest` 的形状，
  **必须带一个只差一个字符的陪跑行**。只断"搜得到"的断言挡不住通配符泄漏。
- **改转义符**（`KeywordLike.ESCAPE`）：要同时看三件事 —— 它在字符串字面量里是否特殊、
  它是否被 `LIKE` 的模式语法占用、以及 `verify-like-escaping.mjs` 与 ADR 里的表格要同改。

## 未覆盖

1. **达梦未实测**（同 `0065` / `0066`）：达梦的 `LIKE` 是否支持 `ESCAPE` 子句、
   默认转义符是不是反斜杠，都没有实例可验。三方言里只有这一格是空的。
2. **只有用户域有运行时断言**。其余 6 处（用户组 / 租户 / 角色 / 资源 / 组织 / 日志）
   共用同一个 `KeywordLike`，且**漏用会被机械守卫挡住**；但"这六处的转义在库上真的生效"
   仍是**同一实现的推论**，不是各自的用例。`0066`「未覆盖」2 说的也是这六处。
3. **关键词的规范化在各域不一致，且本轮刻意没顺带统一**：4 处先 `trim`、3 处不 trim
   （前端都会 `trim` 后再发，所以这差异在界面上看不出来，但接口层是两套口径）。
   那是一次独立决定，不该混在"转义"里悄悄改掉。
4. **只解决了通配符**：`0066`「未覆盖」5 的"搜索的可观测性"（哪个关键词被搜了、搜空了）
   仍然没有；`0066`「未覆盖」2 / 4 也仍未关。
5. **`like` 家族里没被用到的那些**（`notLike` / `notLikeLeft` / `notLikeRight` /
   `likeLeft`）：当前一处都没有，守卫把它们的名字一并纳入了扫描，但**没有用例**
   —— 真要用时它们的实参同样是"用户输入"还是"服务端拼的"要先回答一遍。
6. **转义不影响索引**：`LIKE '%…%'` 前缀是通配符，本来就用不上索引；
   `ESCAPE` 不改变这一点（记在这里，免得被当成"转义会伤性能"）。
