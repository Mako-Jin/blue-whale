# 0007. 前端请求分层与错误模型

- **状态**：已采纳
- **日期**：2026-10-09
- **决策者**：舰长

## 背景

前端开始真的发请求了（日志上报、日志查询、健康检查），必须回答六个问题：

1. **请求能力放在哪？** 放进应用里、放进 `common-api`，还是独立成传输层？
2. **用 axios 还是 fetch？** 二者都能用，但会决定整个错误模型长什么样。
3. **失败怎么表达？** 如果只有一个 `Error`，调用方怎么区分"网络抖动该重试"和"业务拒绝重试一万次也一样"？
4. **重试谁来做？** 传输层自动重试，还是调用方决定？
5. **超时与取消怎么处理？** 两套中断机制并存时，总有一边忘了清定时器。
6. **统一响应 `R<T>` 在哪一层解开？** 每个调用点各写一遍，还是收口一次？

其中第 3、4 条是本决策的核心。既有项目里最常见的做法是"一个 `Error` + `message` 文案 + `if (err.message.includes('timeout'))`"，而文案是随时会被改掉的 —— 改一个字，判断就静默失效。

## 决策

### 1. 分两层：传输内核与契约装配

```
common-tools/http        传输内核 —— 刻意不认识任何业务接口
      ▲                  怎么发、怎么翻译错误、怎么解包
      │
common-api               契约装配 —— 只做接线
                         路径常量 + 契约类型 → 方法
```

| 层 | 认识业务接口 | 换一个接口要动它吗 | 改传输策略要动它吗 |
|----|--------------|--------------------|--------------------|
| `common-tools/http` | 否 | 不用 | 只动它 |
| `common-api` | 是，仅接线 | 只动它 | 不用 |

**为什么不让 `common-api` 自己实现请求**：那样"接口定义"和"怎么发请求"会焊死在一起，加一个鉴权头要改遍所有接口方法。

### 2. 基于 fetch 自建，不引入 axios

需要的能力只有：JSON 收发、超时、取消、统一解包、错误分类 —— 这些用 `fetch` + 约 250 行封装即可覆盖，且**没有额外运行时依赖**。

更要紧的是：axios 自带一套错误模型（`AxiosError`）与拦截器生态。引入它意味着项目里会同时存在"axios 的错误判断方式"和"我们的错误判断方式"，最终还是绕不开把两者归一到一套分类上 —— 那不如一开始就只有一套。

> 代价写清楚：自建就没有现成的拦截器/适配器生态，重试、缓存、并发去重都要自己写。目前只实现了确实需要的部分。

### 3. 错误分六类，判据是结构化字段而不是文案

```ts
type HttpErrorKind = 'business' | 'http' | 'network' | 'timeout' | 'abort' | 'parse';
```

| kind | 含义 | 典型反应 |
|------|------|----------|
| `business` | HTTP 200 但 `code !== 0`：请求完全正常，是业务规则拒绝了它 | 提示用户，改输入 |
| `http` | 状态码非 2xx：传输层 / 网关失败 | 5xx 与 429 可重试 |
| `network` | 请求没发出去或没收到响应 | 可重试 |
| `timeout` | 超过约定时间 | 先查是服务慢还是网络差 |
| `abort` | 调用方主动取消 | 静默忽略 |
| `parse` | 响应不是合法 JSON 或不符合统一响应结构 | 契约被破坏，要人看 |

`HttpError` 基类保留 `kind` / `status` / `code` / `traceId` 四个字段，**调用方按结构判断，永不匹配文案**。

### 4. `retryable` 由错误自己给出，但**内核不做自动重试**

`retryable` 的判据只有一条：**同样的请求再发一次，结果是否可能不同**。

- `network` / `timeout` → `true`
- `http` 且 `status >= 500` 或 `429` → `true`
- 其余（含全部 `business`）→ `false`

但**传输层绝不自动重试**。原因：**幂等边界是业务语义，不是传输层能拍脑袋决定的**。

- 日志上报的 `POST` 重试是安全的（重复落库可接受，且上报通道自带批量与退避）；
- 但"下单""支付"的 `POST` 重试就是重复扣款。

传输层无法从 `POST /orders` 这个路径推断出它是否幂等。因此内核只提供判据，**由调用方显式决定要不要重试**。日志上报通道（`LogReporter`）就是这么做的：失败批次放回缓冲、按指数退避重发、封顶 30s。

### 5. 统一响应在传输层一次性解开

三件事收口在 `createHttpClient` 里，而不是散落在每个调用点：

1. **解开 `R<T>`** —— 调用方拿到的直接是 `data`；
2. **`code !== 0` 抛异常** —— 用返回值表达失败必然有人漏判，而漏判的表现是"页面显示 undefined"，比抛异常难排查得多；
3. **超时与外部取消合并成一个 `AbortController`**。

`unwrap: false` 可关闭解包，用于契约之外的临时接口。

### 6. 超时先于取消分类

超时也是通过 `abort()` 实现的，两者抛出的都是 `AbortError`。因此 `toTransportError` 的判断顺序是：

```
timedOut ? TimeoutError : cause.name === 'AbortError' ? AbortError : NetworkError
```

若先按 `AbortError` 归类，超时会被报成"被主动取消"，排查时会去找"谁取消了这个请求"，而真正的原因（服务端太慢）被完全掩盖。

### 7. 链路标识由调用方提供，不自动生成

`HttpConfig.traceIdProvider` 返回非空值时自动注入 `X-Trace-Id`；同时从响应头回读 `x-trace-id`。

**为什么不在传输层自动生成一个**：那样每次调用都会是一个新 id，前端日志与后端日志永远串不起来 —— 而"能按一个 id 把一次请求的前后两端日志捞出来"正是这个字段存在的全部意义。因此 id 的生命周期必须由调用方掌握（真实项目里由业务请求的开始处生成并传递）。

### 8. 日志级别与 `silent` 开关

- `business` 失败记 **warn**，其余记 **error** —— 与后端 `GlobalExceptionHandler` 的策略一致：业务拒绝是预期行为，若也记 error，真正的故障告警会被正常业务拒绝淹没。
- `silent: true` 用于已知会失败、由调用方自行处理的探测类请求（如健康检查），避免每 10 秒往错误日志里写一条。

## 后果

**正面**

- 换接口不用碰传输层；改传输策略（鉴权、脱敏、重试）不用扫一遍接口定义
- 错误可按结构判断，文案改动不会让判断静默失效
- 统一解包 + 失败即抛，调用点没有"忘记判断"的机会
- 没有额外运行时依赖（`common-tools` 的依赖数保持为 0）

**负面 / 代价**

- 自建意味着重试、缓存、并发去重等要按需自己补，没有现成的生态可用
- 不自动重试 → 需要重试的调用点各自实现，存在重复实现的可能（目前只有 `LogReporter` 需要，暂不抽象）
- 六类错误比"一个 Error"要多写代码，也要求调用方真的按 `kind` 分支处理

**后续约束**

- 业务代码**不得**直接 `fetch`，一律经 `common-api` 的接口方法
- 调用方**不得**按错误 `message` 文案做判断，必须用 `kind` / `status` / `code`
- 需要重试时必须显式判断 `error.retryable` **并且**确认该操作幂等，两条都满足才重试
- 新增传输能力（鉴权、埋点、并发去重）加在 `createHttpClient` 的钩子上，不要在接口层里写
