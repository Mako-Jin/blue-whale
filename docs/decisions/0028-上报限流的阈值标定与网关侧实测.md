# 0028. 上报限流的阈值标定与网关侧实测（修正 0027 的两处）

- **状态**：已采纳
- **日期**：2026-10-13
- **决策者**：舰长

## 背景

`0027` 落地了网关层的上报限流。本决策由舰长的两个问题触发：

> 一、这个 nginx 只有一些配置，能使用吗？`D:\tools\installer\nginx` 有安装包，可以拷贝过来。
> 二、日志上报不应该限流吧？达到阈值就舍弃了？

两条都不是"再确认一下"，而是**能推翻结论的**：

- 问题一给出了本机就有的 nginx —— 而 `0027` 的结论里赫然写着"开发机既没有 nginx 也没有 docker"；
- 问题二质疑的是限流的**语义**（429 等于丢弃？）与**对象**（该不该限上报）。

按本仓的做法：先把能测的测掉，再回答。**测完发现 `0027` 有两处陈述不成立。**

### 一、实测推翻了 `0027` 的两处陈述

| `0027` 的说法 | 实测结果 |
| --- | --- |
| 「**没有跑过 `nginx -t`，也没有实际压出过一次 429**」（§后果·负面） | 跑过了，也压出来了 |
| 「`limit_req zone=xxx` 引用了不存在的 zone —— `nginx -t` **只在启动时**才发现」 | `nginx -t` **当场就报** `[emerg] zero size shared memory zone "xxx"` |

第二条的性质是**"把工具想象得比实际弱"**：nginx 的配置检查分两段（语法 → 语义），
zone 引用属语义段，`-t` 会走完。这条错误让 `scripts/verify-nginx-config.mjs` 的
价值被高估了一格 —— 它仍然有用（报得更早、直指缺哪个 zone、不需要装 nginx），
但**不是"只有它能挡"**。该脚本的头部表格已改正。

实测的做法与证据（**只读安装包**：拷到临时目录里跑，不动 `D:/tools/installer`、不装到系统）：

| 验的是什么 | 结果 |
| --- | --- |
| `nginx -t`（部署形态的那棵树） | **通过** |
| 15 个连续 POST，阈值压到 2r/s / burst 2 | `200 × 3 / 429 × 12`，响应体 `{"code":42900,"message":"请求过于频繁","data":null}` |
| **同一 URI** 的 15 个连续 GET | `200 × 15` |
| 等 2.2 秒后再打 5 个 POST | `200 × 3 / 429 × 2`（桶会回填） |
| 默认值下 450 个连续 POST | `200 × 216 / 429 × 234`，`error_log` 命中 `bluewhale_report_per_ip` |
| 只把**全局**阈值压到 2r/s（按 IP 放到 1000r/s） | 全部 429，`error_log` 命中 `bluewhale_report_global` |

中间那条"同一 URI 的连续 GET 全部 200"是关键：它把 `0027` 决策三（
"靠 `map $request_method` 把查询摘在配额之外"）从**依据 nginx 源码的推断**变成了**实测**。

> 踩过一次的坑，记在这里以免重犯：第一次压测一个 429 都没出来，原因是**后端没起** ——
> 请求全部 502，而**每次连接被拒耗时约 2 秒**，把 15 个请求的间隔拉成了 0.45 req/s，
> 低于阈值自然不触发。**压限流必须有一个活的后端**，否则测的是别的东西。

### 二、429 不等于丢弃 —— 这是问题二的直接答案

`common-tools` 的 `BatchChannel`（`web/packages/common-tools/src/report/index.ts`）：

| 项 | 默认值 | 位置 |
| --- | --- | --- |
| `batchSize` | 20 | `BATCH_DEFAULTS` |
| `flushIntervalMs` | 3000 | 同上 |
| `maxBuffer` | 500 | 同上 |
| `maxBackoffMs` | 30_000 | 同上 |

拿到非 2xx 时（`flush` 的 `catch` 分支）：

1. 把这一批**退回队首**（`buffer.unshift`）；
2. 退避时长 `min(flushIntervalMs × 2^失败次数, maxBackoffMs)`，**封顶 30 秒**；
3. 只有**放不下**的那部分才算丢（`state.dropped += batch.length - restored`）。

而缓冲溢出（`push` 分支）丢的是**最旧的**（`buffer.splice(0, overflow)`）。

于是完整语义是：

> **短暂超限 = 延迟；持续超限 = 丢最旧的一批。**

所以"达到阈值就舍弃了"**只在那一条链路的末端成立**，而且它还需要"客户端连续失败
到缓冲撑满 500 条"这个前提 —— 而客户端的退避同时又把它自己的请求速率降了下来，
两个机制是**互补**的：网关限流负责保护后端，客户端退避负责别把限流变成丢数据。

### 三、真正错的是**按 IP 的标定公式**，不是"该不该限"

`0027` 的 `.env.example` 写的是：

> 20r/s …… 客户端默认 20 条/批、3 秒一冲，**正常使用每 IP 每 3 秒才 1 个请求** ——
> 这个值几乎碰不到，只拦异常放大。

**"每 IP 每 3 秒才 1 个请求"把"1 个客户端 = 1 个 IP"当成了前提**，而它在本仓自己的
部署形态下不成立：企业 NAT、办公网出口、CDN 回源，都会让 N 个客户端共用一个源 IP。
真实速率是 `N / 3 r/s` —— 20r/s 对应**约 60 人**，一个稍大的办公网就能把它打满，
表现为"整片 429 而攻击者毫发无损"。

而它同时暴露了另一个洞：`0027` 的「本决策未覆盖」自己写着
「按 IP 的 `limit_req` 挡不住**很多来源各打一点**」——
按 IP 的桶被分布式灌注逐个打穿时，**没有任何一层在管总量**。

两件事是同一个病根：**把"隔离"和"容量"两件事压在了同一个阈值上。**
隔离要按"最大的那个来源"标定，容量要按"后端能吸收多少"标定，两者数量级不同、
标定依据不同，压在一起就只能是折中，而折中在两个方向上都会错。

## 决策

### 一、上报限流改成两层，两层有各自的标定公式

```nginx
# 按 IP：隔离 —— 按"最大的 NAT 出口"标定，不是按"一个客户端"
limit_req_zone  $bluewhale_report_key        zone=bluewhale_report_per_ip:10m  rate=${REPORT_RATE};
limit_conn_zone $bluewhale_report_key        zone=bluewhale_report_conn:10m;

# 全局：容量 —— 与来源无关，按后端能吸收的写入速率标定
limit_req_zone  $bluewhale_report_global_key zone=bluewhale_report_global:10m  rate=${REPORT_GLOBAL_RATE};
```

两个 zone 在两条上报 location 上**同时**挂载（`limit_req` 允许在同一 location 出现多次 ——
这一条是实测确认的，不是查文档推断的）。

| | 按 IP | 全局 |
| --- | --- | --- |
| 职责 | **隔离**：别让一个来源吃光全局预算 | **容量**：后端最多吸收多少 |
| 标定依据 | `N / 3` r/s（N = 最大 NAT 出口后的客户端数） | 后端**实测**能承受的写入速率 |
| 默认值 | `100r/s` / burst `200` / conn `40` | `300r/s` / burst `600` |
| 对应规模 | 约 300 个客户端共用一个出口 | 约 6000 条日志/秒（20 条/批） |

### 二、全局桶的 key 必须与来源无关

```nginx
map $request_method $bluewhale_report_global_key {
    default  "";
    POST     "bluewhale-report";     # ← 常量，不是 $binary_remote_addr
}
```

**写错的形态是"语法完全合法"的**：一旦 key 用 `$binary_remote_addr`，它就退化成
第二个按 IP 桶，全局上限不复存在，而 `nginx -t` 会说 `test is successful`。
`scripts/verify-nginx-config.mjs` 新增了一条检查专门挡这个。

### 三、`--emit`：把模板渲染成一棵可跑的树

`0027` 把"跑不了 `nginx -t`"当成了前提，于是只做了结构性校验。现在补上另一半：
脚本新增 `--emit <目录>`，把模板渲染成一棵与部署形态同构的树（`conf.d/`、`snippets/`、
一个可直接 `-c` 的主配置），顺带把 `nginx -t` 的命令打出来。

它**不只服务测试**：`--emit` 只替换已知的 `${变量}`，因此**不可能**把 nginx 自己的
`$remote_addr` / `$request_method` 吃掉 —— 而那个陷阱（手工 `envsubst` 漏白名单）
是这份配置里最容易踩、且踩了之后**配置依然"语法合法"**的一脚。它与
`scripts/verify-nginx-config.mjs` 现在共用同一套渲染逻辑。

另有 `--nginx <可执行文件>`（或 `BW_NGINX_BIN`）在渲染之后真跑一次 `nginx -t`。
**注意**：Node 的 `spawnSync` 在部分沙箱里被禁止创建进程（报 `EBUSY`），
那种环境下走 `--emit` + shell 里手跑 `nginx -t`，检查的是同一棵树。
本次验证走的正是这条路。

### 四、`0027` 的原文不回改

按本仓惯例（`0027` 处理 `0026` 的未覆盖项时也是这么办的），**不回改 `0027` 的正文**，
只在本篇与 `infra/nginx/README.md` 建立指向。`infra/nginx/README.md` 是**活文档**，
它的第五节的"未验证"结论已按本次实测改写。

## 后果

**正面**

- `0027` 的两处不实陈述被纠掉，且纠正是**可复现的**（README 里给了复现命令）。
- 限流的两个职责分离后，两个阈值各自可解释：一个按人数，一个按后端容量。
- `0027`「未覆盖」里"很多来源各打一点"那条**被部分覆盖**了 —— 分布式灌注打不穿总量桶。
- 同一 URI 上的"上报限流、查询不限流"从**推断**变成了**实测**。
- CI 里仍能跑（不带参数时不需要 nginx），需要时又能带上真 `nginx -t`。

**负面 / 代价**

- 配置多了一个 zone 与一个 `map`，读的人要理解"为什么是两个桶"。
- 默认值从 20r/s 放宽到 100r/s。**这是有意的**：总量职责移交全局桶之后，
  按 IP 的桶只需承担隔离，放宽它反而减少了 NAT 误伤；但"放宽"这件事必须与
  "全局桶真的生效"绑定才有意义 —— 所以本轮专门验了全局桶独立命中。
- `--emit` 产出的树里 include 根是**产物目录**而非 `/etc/nginx`，拷到部署位置时
  必须落在同名子目录下，否则两个 `include` 会失败。
- 阈值仍然只是**起点**：本轮验的是"能不能拦住"，不是"该定多少"。

**后续约束**

- 调整上报阈值时，**两个桶要一起想**：只动按 IP 的桶 = 改隔离；只动全局的桶 = 改容量。
  把总容量压小来"更安全"，会让正常流量也拿 429。
- 给上报域再加路径时，**两层桶都要挂**，`scripts/verify-nginx-config.mjs` 的
  `REPORT_PATHS` 清单与 location 要同步改（脚本里那份清单是写死的，不会自动发现新路径）。
- `scripts/verify-nginx-config.mjs` 的头部表格里，"`nginx -t` 能不能发现"那一列
  **必须是实测结论**，不是推断 —— 本轮已经因为推断错了一次。

## 本决策未覆盖

- **慢速攻击**：`limit_conn` 只限数量、不限时长，慢速连接仍能占住 worker。属 WAF / CDN 的活。
- **多实例下的总量**：全局桶也是**单机内存**的，多台 nginx 各自计数，
  实际总量 = 配置值 × 实例数。真要做全局配额得上 Redis 或网关产品。
- **阈值定得合不合适的实测**：本轮没有在真实负载下观察 `limiting requests` 的出现频率。
- **采样**：仍是 `0004` 第 3 条「采样与限流是必选项」里没做的那一半。

## 发现但未处理

- **非上报路径的 GET 也可能撞上 NAT 误伤**：`/api/` 的按 IP 兜底是 `100r/s`，
  它同样按 IP 计数。查询接口是人点出来的、频率低，暂时没改；但如果日志台出现
  "偶尔刷不出来"，**先去看 `error_log` 里有没有 `limiting requests`**，别先怀疑鉴权。
- **`0027`「发现但未处理」第 1 条（种子口令）已在同一轮处理** —— 见 `docs/decisions/0029`。
  那一篇同时纠正了 `0027` 记错的口令外泄链路。
