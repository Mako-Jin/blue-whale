# 0020. 口令与登录安全加固（对参照实现的二次取舍）

- **状态**：已采纳
- **日期**：2026-10-12
- **决策者**：舰长

## 背景

`0016-权限域服务设计与参照实现的取舍.md` 已经对参照实现 `SystemTerminator` 的
`sts-server-auth` 做过一轮取舍，但那一轮的重点是**结构**（DDD 五层不照搬、表名主键、
逻辑删除语义、自研 JWT 与 PBKDF2）。它记下的是"哪些**不**照搬"。

本决策是**第二次回访**，问题换成："那 515 个文件里，有没有**值得拿过来**的东西？"

### 回访的方法：先辨真伪，再谈借鉴

参照实现的构件数量远超本仓的权限域（约 515 : 69 个文件），但**数量不等于可用**。
逐一核对"有没有实现类、有没有调用方"之后，它的真实面貌是**大量构件停在设计阶段**：

| 构件 | 表面 | 实情 |
| --- | --- | --- |
| `PasswordPolicy`（值对象，含 `validate()`） | 完整 | **全仓没有一处调用它** —— 它被 `TenantConfigEntity` 持有，却从未接进登录或改密 |
| `PasswordHistoryEntity` + `PasswordHistoryPo` | 完整 | **没有对应的 Repository**，只有 `UserInfoAggregate` 引用过实体 |
| `InheritStrategyEnums`（NONE/FULL/INCREMENTAL/OVERRIDE） | 四值俱全 | 只是 `RoleInfoAggregate` 的一个字段，**没有任何继承逻辑** |
| `CaptchaService` | 是个服务 | **空接口**，一个方法都没有 |
| `LoginAttemptService` / `BlackWhiteListDomainService` | 有接口 | **没有实现类** |
| `AuthApplicationServiceImpl.authentication(...)` | 有方法 | **`return null`** —— 核心链路是空的（ADR-0016 已记） |

与此同时，它的 `AuthSecurityDomainServiceImpl`（312 行）**是真实现**：账户锁定、
验证码阈值、可信设备、黑白名单匹配都在里面。但它**从未被接进登录链路**——
唯一的调用点在被 `return null` 的那个方法里。

**而本仓的问题恰好相反**：链路是通的（登录 / 刷新 / 登出 / 鉴权 / 审计都在跑），
但**策略粗糙** —— 口令只校验长度，锁定是固定时长。

因此本决策的方向不是"抄功能"，而是：
**把参照实现里设计良好、却始终没接通的那些策略模型，接到本仓已经通了的链路上。**

### 核实时发现的一处真实缺陷

核对"锁定是否真的生效"时，发现本仓的登录失败锁定**从来没有生效过**：

```java
@Transactional
public LoginVO login(...) {
    ...
    if (!passwordHasher.matches(...)) {
        registerFailure(user, now);                              // 写 failed_attempts / locked_until
        throw AuthResultCode.BAD_CREDENTIALS.businessException(); // RuntimeException
    }
```

`BusinessException` 是 `RuntimeException`，`@Transactional` 默认对它回滚 ——
**失败计数连同这次回滚一起消失**。下次请求读到的仍是初值 0，
于是阈值永远达不到、账号永远不会被锁定；而且**连"账号已被锁定"那句 WARN 也到不了**
（它同样在阈值之后）。表象是：字段齐全、方法齐全、日志语句齐全，**什么都不会发生**。

这个缺陷**用带 `@Transactional` 的测试测不出来**：测试事务会把请求包进同一个事务里，
未提交的写在同一事务内可见，于是"根本没写进库"这件事被完全掩盖。
本决策的端到端测试因此**刻意不加 `@Transactional`**。

## 决策

### 1. 口令强度策略：借鉴意图，不借鉴"复杂度等级"

新增 `PasswordPolicy`（`auth/common/`，纯函数式），从 `AuthProperties.Password` 读取：
最小长度、是否要求大写 / 小写 / 数字 / 特殊字符、历史口令保留数。

与参照实现的两点不同：

- **不设"复杂度等级"这一层间接**。它的 `PasswordComplexityEnums`（LOW/MEDIUM/HIGH）把
  规则藏在枚举里："高"到底是要 12 位还是要特殊字符，得回查枚举；而"必须含特殊字符、
  但可以不要求大写"这类组合，等级根本表达不了，只能再加一级。
  直接配置"长度 + 需要哪几类字符"更精确，且与 `AuthProperties` 里其它策略参数同一形态。
- **返回全部未满足项，而不是 boolean**。`validate()` 返回 boolean 时，调用方只够回一句
  "口令不符合要求"，用户得反复试；逐条列出缺失项（"长度至少 8 位、至少一个大写字母"）
  才能给出可行指引。错误码 `40003` 的文案由 `describe()` 动态拼出，
  **配置改了提示跟着改**，不会出现"要求 12 位、提示写着 8 位"的错位。

默认值刻意保守：长度 8 + 大小写 + 数字，**不要求特殊字符**。
更严的规则是最容易让用户把口令写在便签上的那类要求，应由部署方按自己的合规基线打开。

### 2. 口令强度只在策略一处表达

`UserSaveRequest` 与 `PasswordResetRequest` 上的 `@Size(min = 8)` **删掉**，只留 `max`。

两处都写长度下限会导致：策略调到 12 时，8 位口令先通过 DTO、再被策略拒，
而且两次拒绝返回的是**两种不同错误码**，前端只能猜。
规则只能有一个来源 —— 现在它就是 `PasswordPolicy`。

### 3. 密码历史：防重用，按条数裁剪

新增 `bw_auth_password_history` 表（V5，三方言）、`PasswordHistoryEntity`、`PasswordHistoryMapper`。

- **历史里存"被替换下来的旧口令"**，不含当前口令；校验时**两者都看**。
  漏掉"当前口令"这一步的后果很具体：连续重置两次、第二次填回原口令会静默成功。
- **append-only，刻意不继承 `BaseEntity`**（`RefreshTokenEntity` 之后第二例）：
  没有"更新人"，也不该有逻辑删除 —— 删掉一条历史就等于抹掉"这个口令被用过"的事实，
  而那正是防重用检查赖以成立的依据。
- **裁剪按条数，不按时间**。参照实现给历史记了 `expiresAt`，
  但那样表的规模取决于"多久清一次"，与检查能覆盖的范围脱钩：
  长期不改密的账号会攒下无限多行，频繁改密的账号可能只剩两行。
  按条数裁剪（保留最近 N 条）时，表的规模直接等于"要防几次重用"这个量本身。
- 新口令先过强度策略（`40003`），再查重用（`40914`）。**两个码分开**：
  口令形态不合法与"口令合法但撞了"是两件事，前端据此给出的引导也不同。

### 4. 登录锁定改为指数退避

新增 `LoginLockPolicy`（同 `PasswordPolicy` 形态：从配置读、纯计算、可单测）。
第 n 次被锁定的时长 = `lock-duration × lock-growth-factor^(n-1)`，封顶 `max-lock-duration`。
默认 5 分钟 × 2，封顶 24 小时，即 5 / 10 / 20 / 40 / 80 … 分钟。

- **为什么不是固定时长**：固定时长对攻击者是一个**恒定的重试预算** ——
  每 15 分钟来 5 次，成本不随次数上升。退避让持续攻击的代价指数增长，
  而偶尔打错口令的合法用户第一次只需等 5 分钟。
- **`UserEntity` 只加一列 `lock_level`，不加新表**。登录失败状态本就落在用户行上
  （`failed_attempts` / `locked_until` / `lock_reason`），参照实现为它单开一张
  `LoginAttempt` 聚合（按 user+tenant），在本仓的单库模型下没有收益，
  只会把"判断是否锁定"从一次主键查询变成一次 JOIN。
- **两个计数各司其职**：`failed_attempts` 是"这一轮错了几次"（触发锁定后清零），
  `lock_level` 是"历史上被锁过几次"（只有登录成功才清零）。只留前者的话，
  "第几次被锁"无从表达，退避也就无从计算。
- 算法本身的三个边界由 `LoginLockPolicyTest` 用固定配置钉死：**翻倍**、
  **封顶**、**不溢出**（层级极大时 `Math.pow` 会溢出成 `Infinity`，
  若实现写成"先转 `long` 再与上限比较"会得到负数，那是"锁定到过去"，等于没锁）。
  参照实现这里的注释与代码也不一致（注释写 5/15/30/60/120/240/1440，代码算的是 `5 × 2^n`）。
- **锁定状态必须从接口看得见**：`lock_level` 与 `lock_reason` 都补进 `UserVO`。
  只落库不暴露时，运维在界面上看到"锁定至明天"，却既不知道原因、也不知道是第几次锁定 ——
  也就无从判断退避究竟在不在生效。

  这个缺口**单测抓不到**：用例从库里读 `lock_level` 断言通过，而接口响应里根本没有这个字段。
  它是跑**独立于测试的 HTTP 校验**（对运行中的应用直接打接口）时暴露的 ——
  落库断言证明的是"写进去了"，不证明"读得出来"。因此
  `PasswordHardeningApiTest` 补上一条**经 `GET /api/auth/users/{id}` 的断言**，
  "落库"与"可见"由两次断言分别钉住。

### 5. 失败计数必须跑在独立事务里（本次最重的一处修复）

新增 `LoginAttemptRecorder`，其 `recordFailure(...)` 标
`@Transactional(propagation = REQUIRES_NEW)`。

**为什么不能与登录共用事务**：登录失败会抛 `BusinessException`，它把整个登录事务标记回滚；
失败计数写在同一事务里就会一起消失（见「背景」）。这与 `AuditRecorder` 是**同一条理由的
两种表现**：**"因为这次操作失败而产生的记录"，恰恰不能跟着这次失败一起回滚** ——
审计要留住"越权尝试"，这里要留住"这次口令错了"。

两点实现细节：

- **拆成独立 Bean**，不在 `AuthService` 里加一个 `@Transactional` 方法：
  同类内部调用（self-invocation）不经过代理，注解会被静默忽略（与 `AuditRecorder` 同样的坑）。
- **按主键重新读用户**，不接收调用方传进来的实体：本方法在另一个事务里执行，
  调用方那个实体属于已被挂起的那个事务，它的 `failed_attempts` 可能已过期。
  重新读取拿到的是已提交的最新值 —— 这正是"连续失败"能够连续的前提。

调用方（`AuthService`）**吞掉**它抛出的异常：记不上失败次数只应导致"锁定暂时不生效"，
不该把"口令错误"这个正常结论变成 500，用户看到的仍应是 `40101`。

### 6. 端到端测试不加 `@Transactional`

`PasswordHardeningApiTest` 刻意不标 `@Transactional`，因为它验证的恰恰是
"失败请求回滚之后，什么仍然留下来了"。加上的话，未提交的写在同一事务内可见，
第 5 条那个缺陷会被完全掩盖 —— 测试全绿，而线上锁定永不触发。

代价是用例会真的写库（h2 内存库，随进程消失），因此用户名一律带时间戳后缀。

## 后果

**正面**

- **登录失败锁定第一次真正生效**。此前它是"代码完整、日志完整、没有任何效果"的状态。
- 锁定状态（是否锁定 / 第几次 / 为什么）在管理接口上可见，不再只是库里的三列。
- 退避让持续暴力破解的代价指数上升；合法用户第一次只需等 5 分钟。
- 口令有了强度门槛与防重用，且规则只有一个来源、一处实现、一条错误码。
- 三处策略（口令强度 / 锁定退避 / 防重用）都是无状态纯函数，
  可以脱离 Spring 与数据库直接断言边界，端到端只负责验证接线。

**负面 / 代价**

- 每次失败登录多一个短事务（`REQUIRES_NEW` 要新开连接）。
  与"计数被回滚掉"相比，这个代价是值得的。
- 收紧后的策略会让**新建或重置**时的弱口令被拒。**存量账号不受影响**
  （只在设口令时校验，不追溯、不强制重置），但"改回旧口令"这类习惯会被挡住 —— 那正是目的。
- 仍然**不判断弱口令字典**（`123456`、`password`）。那需要一份词表与额外的判定语义，
  不在本切片范围内；`PasswordPolicy` 只回答"长度够不够、字符类别缺哪几类"。
- 防重用目前**只在管理员重置路径上生效** —— 因为本仓还没有"用户自助改密"接口。
  新增那条路径时必须同样接入（见「后续约束」）。

**后续约束**

- **任何"设置口令"的入口**（建号 / 重置 / 将来的自助改密）都必须依次经过
  `PasswordPolicy.violations(...)`、`assertNotReused(...)`、`recordHistory(...)` 三件事。
  只做其中一件都是漏洞：漏了第一条等于没有强度门槛，漏了第二条等于可以改回旧口令，
  漏了第三条等于防重用只在这一轮有效。
- **任何"因为操作失败而要留下的记录"必须跑在独立事务里**（`REQUIRES_NEW`），
  且要拆成独立 Bean。这类记录目前有两处：`AuditRecorder`（越权尝试）与
  `LoginAttemptRecorder`（登录失败）。
- **append-only 的事实表不继承 `BaseEntity`**。例外清单：
  `RefreshTokenEntity`、`PasswordHistoryEntity`（以及审计域的 `AuditLogEntity`）。
- **新增表结构**必须追加 `db/migration/{h2,mysql,dameng}/V<n>__*.sql`，
  版本号取全仓当前最大号 + 1（权限域占 V3、审计域占 V4、本片占 V5），三方言都要写。
- 口令策略的提示语必须来自 `PasswordPolicy.describe()`，**不得在别处硬编码**。
- **带运营含义的新状态列，落库的同时必须暴露到出参**。`UserVO` 是逐字段手写映射的
  （刻意如此，见其类注释），所以新增实体字段**不会**自动出现在接口里 ——
  这是它挡泄露的代价。判断标准：运维在界面上需要据此做决定的状态（锁没锁、锁几次、
  为什么锁）就必须进 `UserVO`；纯内部计数则不必。
  `PasswordHardeningApiTest` 里"读库"与"读接口"两次断言应成对出现。

## 本切片未覆盖

- **用户自助改密接口**（含"强制改密"引导）。`must_change_password` 与 `password_expires_at`
  两列已就位、登录时也已校验，但缺"改密页面 / 接口"这一段。
- **弱口令字典**（常见口令、键盘序、与用户名相似度）。
- 验证码与多因子（MFA）的实际校验：`AuthResultCode` 里 `40107~40110` 已预留，
  参照实现对应的 `CaptchaService` 是空接口，无从借鉴。
- **口令过期策略的触发**：`PasswordPolicy` 未含"过期天数"，
  但 `AuthProperties.Password` 也没有这一项 —— 加它要连同"过期后如何引导改密"一起设计。
- **租户级的差异化策略**：参照实现把口令/锁定策略放在 `TenantConfig` 里（租户各一套）。
  本仓当前只有 `default` 一个租户，全局配置足够；等出现"不同租户不同合规基线"的
  真实需求时再下沉，那时它的形态由需求决定。

## 附：参照实现里**不**借鉴的部分

| 构件 | 不借鉴的理由 |
| --- | --- |
| DDD 五层模块结构 | ADR-0016 已决定按特性分包 |
| `BlackWhiteList`（IP/设备/客户端/用户） | 有真实现，但含两处 bug：`matchesRule` 里 `enabled == ENABLED` 时 `return false`（逻辑反了，启用中的规则反而不匹配）；CIDR 匹配用 `subnet.substring(0, prefixLen)` 做字符串截断，把"掩码长度"当成了"字符串长度"。需要独立的封禁需求时再从头写 |
| `InheritStrategyEnums`（角色继承） | 半空壳，无任何继承逻辑；角色继承本身是独立议题 |
| 23 个 `*Id` 值对象 + 12 个 primitive 值对象 | 本仓用 `Long` 主键 + 校验注解即可；引入一整套 ID 类型对当前规模是过度设计 |
| 多凭据登录抽象（password / mobile / remember-me 的 Provider 链） | 当前只有口令一种凭据；抽象要等第二种真实出现 |
| `LoginHistoryEntity`（登录历史） | 与审计管道职责重叠（"谁在何时登录过"），应作为一个独立议题与 `0019` 一起讨论，而不是顺手塞进权限域 |
| 租户级策略配置（`TenantConfig`） | 单租户阶段是过度设计，见「本切片未覆盖」 |
