# 0014. 多场景架构：清单落地方式与切换管线

- **状态**：已采纳
- **日期**：2026-10-10
- **决策者**：舰长

## 背景

`platform-environment`（ADR-0013）要承载多类环境场景：古建筑、原始丛林、现代写字楼、太空飞船，等等。随之而来两个问题：

1. **场景清单放在哪** —— 前端可配置、后端字典，还是管理端可维护？
2. 场景之间怎么切换，切换的代价是什么？

第 1 个问题最容易答错的方式，是把它当成"三选一"来答。

## 决策

### 1. 一个场景 = 「实现」+「元数据」，三选一只对元数据有意义

- **实现**（`scenes/*.ts`）：几何、材质、光照、动画，本质是 three.js 代码。
  **任何后端方案都下发不了它** —— 下发行可执行代码是安全红线。
  这意味着无论清单放哪，"新增一个场景"都要发前端版本。
- **元数据**（`SceneMeta`）：id、标题、描述、标签、排序、图标标识、主色、相机位姿、选项覆盖。
  纯数据、无行为，才是"前端配置 / 后端字典 / 管理端维护"三选一的真正对象。

### 2. 清单落地：前端注册表为底座，接口形状定成「后端可随时接管」

**当前选择前端注册表，不是妥协，有四条依据：**

1. **ADR-0003 已判定归属**：场景目录属于「业务运行期配置」层（自研、走 OpenAPI 契约）。
   问题不是"要不要后端"，而是"接不接既有通道"。而那份 ADR 同时写着
   "这一层现在不动手，过早实现等于猜需求"。
2. **ADR-0003 底线第 2 条让前端清单成为永久成果**："兜底默认值必须在客户端 ——
   配置服务不可用时，应用仍须以内置默认值正常启动"。将来接了后端，
   这份内置清单照样要在，只是从"唯一来源"降为"底板"。现在投入零浪费。
3. **本应用立身前提是「与任何应用无关、可独立运行」**（ADR-0013）。
   清单若强依赖后端，独立开 `:3400` 时选择器就是空的。
4. **此刻后端字典净收益为 0**：改场景内容仍要发版（代码在前端），
   只是把"改一处 TS"变成"改 TS + 改一条库记录"，**两地不同步的风险反而升高**
   —— 库里冒出一条前端没有实现的 id，用户选中就白屏。也违背"按需创建，不预建空壳"。

**升级路径（何时该换哪一档）：**

| 档位                         | 触发条件                                                    |
| ---------------------------- | ----------------------------------------------------------- |
| 前端注册表（现状）           | 场景数可控 · 仅 Web 端读取 · 改场景即改代码                 |
| 后端字典（接 ADR-0003 通道） | 按环境/租户区分可见场景 · 多端共用清单 · 运营改文案不跟发版 |
| 管理端可维护                 | 非开发人员维护 · 缩略图上传 · 角色控可见性 · 变更审计       |

### 3. 三条护栏：让升级不重写

- **护栏 A · 调用方只认函数，不认数据来源。** `loadSceneCatalog(): Promise<SceneCatalog>`
  从第一天起就是异步签名 —— 今天返回本地常量，明天内部换 HTTP，调用方一行不改。
  首屏走 `localSceneCatalog()`（同步内置清单，ADR-0003 底线第 1 条"首屏零阻塞"）。
  组件里**禁止**直接引用注册表内部。
- **护栏 B · 远端只能覆盖，不能发明。** `mergeCatalogOverrides()` 允许改标题/描述/标签、
  调排序、隐藏；**不允许**凭空造出前端没有实现的场景（认不出的 id 记入 `unknownIds`
  交上层告警）。可覆盖字段刻意限制在展示层 —— 相机位姿、背景色、环境光强度与实现
  强耦合，远端改不了实现就不该改取景。当前它没有生产调用方，提前写出来是因为
  它定义的是未来接线时的行为边界，等到接线才临时决定，几乎必然决定成
  "远端给什么就信什么"。
- **护栏 C · `id` 是跨端契约。** `SceneId` 是手写字面量联合，注册表用
  `Record<SceneId, SceneDefinition>` 承接 —— 漏实现一个场景、或注册了不存在的 id，
  都是**编译期**报错，而不是用户选中后白屏。

### 4. 选择器用卡片，不用下拉框

场景是**视觉选项**，"长什么样"是选择它的主要依据；下拉框恰好把这条信息藏起来。
卡片用「主色 → 场景背景色」的氛围色块 + 线框图标（`SceneMeta.icon` 只是**枚举**，
具体图形归组件渲染 —— 元数据保持纯数据，后端将来也只能选图标、不能塞图形）。

### 5. 切换 = 只换场景图，渲染器 / 画布 / 相机终身复用

`stage.loadScene(definition, options)` 内部只做三件事：释放旧场景图、构建新场景图、
把相机搬到新场景的取景位。**渲染器、画布、相机、相机控制器、PMREM 环境贴图全部复用。**

理由：重建它们不只是慢 —— 重建相机意味着要改 `OrbitControls.object` 并复位内部
球坐标状态；重建画布则撞上 ADR-0013 第 1 条硬规则（`forceContextLoss()` 后同一张
canvas 永久不可用）。

**旧场景先释放、新场景后构建，顺序不能反** —— 反过来峰值显存是两份场景之和。

### 6. 取景随场景走，不共用

每个 `SceneMeta` 必须自带：相机位姿、拉近/拉远范围、IBL 环境光强度、默认渲染选项覆盖。
构图差着数量级（古建筑要退到能看全屋顶，飞船要贴到能看清舷窗），共用一套取景
必然有场景取不对。**切场景同时重置渲染选项**：网格辅助线对广场铺装是参照、
对丛林和太空是干扰，沿用上一个场景的开关只会让人以为"这个场景的开关坏了"。

### 7. 散布必须走固定种子的伪随机

丛林里 14 棵树、写字楼灯柱、太空星点场都要"随机"分布，但**禁用 `Math.random()`**：
每次挂载画面都不同，既没法写断言，也没法复现用户截图里的那一帧。
统一用 `createPrng(seed)`（mulberry32），场景测试里有一条
"两次构建的位姿指纹逐字一致"的断言把这个约定钉住。

### 8. 释放是否干净，必须可断言

新增 `stage.diagnostics()`，暴露 three 维护的**当前在 GPU 上**的几何体/纹理计数。
`scripts/verify-scene-switching.mjs` 靠它断言：同一场景第二轮切回来时，
GPU 几何体数与第一轮一致（无累积）。看画面是看不出泄漏的 —— 泄漏要攒到
上下文上限才突然白屏。

**两个计数都要断言，不能只盯几何体。** 这句是吃过一次亏才补上的：切场景泄漏
阴影贴图时 `geometries` 全程纹丝不动，只有 `textures` 在涨（每次净增 2 张）——
一个只断几何体的验证脚本会一路绿灯地把泄漏放过去。凡是"释放"类的断言，
几何体与纹理是**两条独立的证据链**，缺一条就有一整类泄漏不设防。

### 9. 几何体共享：单位盒 + scale

一个场景里几十个方盒构件（墙、梁、楼板、舱段）全部复用**同一个单位 BoxGeometry**，
尺寸靠 `mesh.scale`。古建筑 127 次绘制调用只用了 6 份几何体。
共享几何体被重复 `dispose()` 是安全的（three 只发事件释放显存，数据仍在，可重新上传）。

## 后果

**正面**

- 新增场景 = 新建一个文件 + 加一个 id 字面量 + 注册一行，漏一步都是编译错误
- 切换是常数成本（不建新的 WebGL 上下文），实测两轮切换后 GPU 几何体数逐场景归位
- 未来接后端字典时，前端调用方零改动；改动的只有 `loadSceneCatalog()` 内部
- 场景画面的每一个细节都可复现、可断言

**负面 / 代价**

- 场景实现的自由度被接口（`SceneBuild`）约束：每个场景必须自己处理线框、网格开关
- `SceneId` 字面量与实现文件是一一对应的隐式契约，新增场景要动两处（有编译器兜底）
- 内置元数据与将来的远端配置需要人工保持同步（ADR-0003 已知代价）

### 验证方式

`node scripts/verify-scene-switching.mjs`（真实 Chrome + CDP）遍历五个场景两轮：
断言各场景渲染规模互不相同（证明确实换了场景图，不是只改标题）、三角面非零、
第二轮切回时 GPU 几何体数不增长、浏览器侧无报错。实测截图见 `docs/assets/0014/`：

| 截图                       | 内容                                              |
| -------------------------- | ------------------------------------------------- |
| `ancient-architecture.png` | 古建筑：广场铺装与殿宇，127 绘制调用仅 6 份几何体 |
| `primeval-jungle.png`      | 原始丛林：固定种子散布 14 棵树与雾                |
| `modern-office.png`        | 现代写字楼：玻璃幕墙格与灯柱                      |
| `spacecraft.png`           | 太空飞船：星点场（相机远裁剪面需给到 400）        |
| `baseline-lab.png`         | 渲染基线：默认参考场景                            |

## 明确未做

- **场景深化**：五个场景都是"可辨识的简化版"（全基础几何体、无外部资源），
  瓦垄、彩画、植被多样性、舱内细节等留给逐场景深化
- **远端清单**：`loadSceneCatalog` 尚无后端来源，接通时需同步后端契约与缓存策略
- **场景级参数运行时调整**（时间、天气、雾浓度滑杆）：等需求来了再进 `SceneMeta`
- **异步加载**（GLTF/HDRI、加载进度）：当前全部程序化生成，零网络依赖
