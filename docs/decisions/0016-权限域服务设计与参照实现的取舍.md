# 0016. 权限域服务（sts-server-auth）设计与对参照实现的取舍

- **状态**：已采纳
- **日期**：2026-10-11
- **决策者**：舰长

## 背景

平台地基需要五块能力：**权限、文件、定时任务、工作流、表单**。其中**权限是唯一的横切关注点** ——
文件、表单、工作流最终都要回答"这条数据谁能看、谁能改"。它属于"事后回填成本最高"的一类：
先做别的域再补权限，就要回头改表结构、改查询条件、改缓存键。

架构上的依赖顺序定为：**统一契约 → 权限 → 表单 → 工作流**，文件与定时任务作为旁支从第一段起并行插入。
本 ADR 只覆盖权限域这一块。

后端已有的参照实现是 `SystemTerminator` 的 `sts-server-auth`（515 个文件，DDD 五层）。
它在**结构**上值得参考，但**不宜照搬**：

- **核心链路是空的。** `AuthApplicationServiceImpl.authentication(...)` 直接 `return null`；
  `PasswordAuthenticationProvider.doAuthenticate(...)` 整段被注释；`Rsa384JwtTokenAdapter`
  三个方法均为空占位（即默认的 RS256 刷新令牌根本不可用）；没有登出、没有刷新接口。
- **没有任何运行时鉴权入口。** 全仓没有鉴权注解、AOP 或拦截器，RBAC 表建好了却没有任何一条接口被它保护过。
- **数据模型有硬伤。** `TenantInfoPo` 标 `auth_tbl_tenant_info` 而建表脚本建的是 `auth_tbl_tenant`；
  9 张表的 PO 没有对应建表脚本；`is_deleted` 语义在不同表里相反（有的 0 表示未删、有的 1 表示未删）；
  口令在 `user_info` 与 `rel_tenant_users` 两处冗余；`AuthErrorCodeEnums.USER_NOT_FOUND(004000)`
  与公共 `ResultEnums.PARAM_ERROR(004000)` 撞码。
- **约定与本仓不一致。** 它是 Spring Boot 3 / Jackson 2 / 字符串雪花 ID；本仓是 Boot 4 / Jackson 3 / 自增主键。

因此本决策要回答：**权限域在本仓怎么落地**，以及**参照实现里的哪些做法保留、哪些必须改**。

## 决策

### 1. 作为 `sts-server-auth` 落在服务层

层内依赖方向不变（`sts-app → sts-server → sts-common`），`sts-app-server` 装配它。
包名用业务域 `com.bluewhale.sts.auth`（不带 `server`），与 `com.bluewhale.sts.log` 一致。

参照实现的"五子模块分层"（interfaces / application / domain / infrastructure / starter）
**不照搬**：本仓模块内按**特性**分包（`tenant/`、`user/`、`organization/`、`role/`、`usergroup/`、
`resource/`、`relation/`、`authentication/`），单个特性超过约十个类时再在其内部分层。
理由见 `docs/decisions/0005` 第 5 条。

### 2. 表名 `bw_auth_` 前缀，主键 `BIGINT` 自增

- 表名统一 `bw_auth_<实体>`，与 `bw_client_log` / `bw_client_event` 同一形态。
- 主键用 `BIGINT AUTO_INCREMENT`（参照实现用字符串雪花 ID）。单库阶段自增更简单，
  且与已落地的两个域一致；对外稳定标识由各表的 `*_code` 业务编码承担。
  将来若确需分布式 ID，改的是生成策略而不是表结构。
- 审计字段全仓统一五列：`create_by / create_time / update_by / update_time / deleted`，
  时间一律 `BIGINT` 毫秒（不碰日期类型，绕开三套库的时区差异）。

### 3. 逻辑删除语义统一为 0=正常、1=已删除

由 MyBatis-Plus 的 `@TableLogic` 承接（默认值正是 0/1，零配置）。
参照实现里"不同表 0/1 含义相反"是要修掉的缺陷，不得复制。
`AuthEntityConventionTest` 里有一条断言钉死"逻辑删除字段必须叫 `deleted` 且带 `@TableLogic`"。

### 4. 用户归属单一租户，凭证只有一份

参照实现把口令同时冗余在 `user_info` 与 `rel_tenant_users`，两副本迟早不一致，
而"用哪个副本校验"本身就成了要考古的问题。本仓的模型是：
`bw_auth_user.tenant_id` 是普通列、`username` 在**租户内**唯一（`uk(tenant_id, username)`），
凭证落在用户行上。口令只存哈希（`password_hash` + `password_algorithm`），从不存明文。

若将来要支持"同一自然人跨租户、口令各租户独立"，再拆凭证表 ——
那时它的形态由真实需求决定，而不是提前设计。

### 5. 错误码沿用全仓规则，域内从 `xx01` 起

`5 位 = HTTP 状态码(3 位) + 业务细分(2 位)`（`docs/decisions/0005` 第 7 条）。
公共 `ResultCode` 只占用每类别的 `00` 号，因此域内编码**一律从 `01` 起**，
与公共码天然错开。这样"用户不存在"落在 `404xx`、"用户名重复"落在 `409xx`——
看到码就知道该归咎于调用方还是服务端，也从规则上消除了参照实现那样的撞码。

### 6. 不引入 Spring Security，也不引入 JWT 第三方库

- **认证**：`JwtCodec` 用 JDK 的 `HmacSHA512` + Base64URL + Jackson 3 实现 **HS512 JWT**。
  只支持对称密钥。刻意做了三件事：algorithm 锁定（拒绝 `alg=none` 与 alg 混淆）、
  恒定时间比较（`MessageDigest.isEqual`）、iss/aud/exp 三项全查。
  不实现 RS256 —— 参照实现里那个 RSA 适配器本就是空占位，与其照抄不如明确只支持 HS512，需要多方验签时再引入。
- **口令**：`PasswordHasher` 用 JDK 的 `PBKDF2WithHmacSHA256`。
  算法标识与迭代次数**随哈希一起存储**，因此调参不会让存量口令全部失效。
- **理由**：本仓的取向是"最小依赖"（`docs/decisions/0002` / `0003`）。单服务、对称密钥的场景
  用不到完整 JWT 库的一整套算法与序列化适配；而 jjwt 的 JSON 适配默认绑 Jackson 2，
  与本仓的 **Jackson 3**（Boot 4）正是已记录的一类共存隐雷。引入 Spring Security 则会带来
  一整套过滤器链与配置模型，与"只做 Bearer 解析 + RBAC 判定"两件事的诉求不成比例。

### 7. 鉴权入口收口到一处：`@RequiresPermission` + 拦截器

- 注解标在 Controller 类或方法上，`value` 是资源标识，多个之间为 AND。
- `AuthInterceptor`（`HandlerInterceptor`）在进入 Controller 前判定；异常交给已有的
  `GlobalExceptionHandler` 翻译 —— 不必再造一套错误响应。
- **未认证返回 401、无权限返回 403**，两者分开：前端据此决定是跳登录页还是提示无权限（前端的落地方式见 `0018-权限在微前端中的归属.md`）。
- 判定取数走 `AuthorizationMapper` 的一条多表 JOIN（用户 → 角色成员 → 角色 → 角色资源 → 资源），
  结果按请求缓存在 `AuthContext` 上，权限变更最多影响一个进行中的请求。

### 8. 刷新令牌：只存摘要，轮换 + 重放检测

- 库中只存 `token_hash`（SHA-256），泄露也不能直接使用。
- 每次刷新都作废旧令牌、换发新令牌；**已作废的 jti 被再次使用时**，
  视为令牌泄露，撤销该用户全部刷新令牌。
- 访问令牌无状态、不可撤销，靠短有效期（默认 2 小时）控制风险窗口。

### 9. 认证上下文只有一套

参照实现里 `common-web` 与 `common-domain` 各有一套 `UserInfoContext` / `TenantInfoContext`
（其中一套是空实现），同名不同义。本仓只保留 `AuthContext` + `AuthContextHolder`，
且强制由过滤器在 `finally` 中清理（Tomcat 线程复用，不清理会串号）。

### 10. 默认管理员种子数据默认关闭

建账号的接口本身要求已认证，存在引导死锁。`DefaultAdminSeeder` 解决这个问题，
但**默认关闭、只在 h2 开发 profile 打开**；生产环境必须由运维显式建号。

## 后果

**正面**

- 权限域成为五个域里第一个"从表到接口、从认证到鉴权"真正闭环的服务，
  其余域接入只需依赖 `sts-server-auth` 并在方法上标 `@RequiresPermission`。
- 错误码、逻辑删除、审计字段、表名前缀四条约定被测试钉死，参照实现里的几类硬伤在规则层面不可复发。
- 零新增第三方依赖，无 Jackson 2/3 共存风险。
- 端到端测试覆盖了登录、401、403、租户隔离、令牌轮换五条关键路径。

**负面 / 代价**

- HS512 为对称密钥：**所有能验签的服务都能签发令牌**。多服务场景需要改为 RS256，
  届时引入 nimbus-jose-jwt 之类的库更合适。
- PBKDF2 不抗 GPU 暴力破解，弱于 Argon2。作为内部平台的起点可接受，参数可调、存量无需迁移。
- 自研 JWT 编解码器终究是"自己实现安全原语"。已通过算法锁定 / 恒定时间比较 / 三项声明全查
  以及 7 条针对性测试把已知坑覆盖，但仍应把它当作需要复查的代码，而不是"写完就不用管"的库。
- 单个 `sts-server-auth` 模块内特性较多，将来拆服务时需要按特性包整包搬迁。

**后续约束**

- 新增权限资源时，标识必须加进 `AuthPermissions` 常量并在资源表登记，
  否则注解写了也不生效（两处都要有，缺一不可）。
  **注意区分三套标识**：权限码 `auth:user:create`（`AuthPermissions`）≠ 资源标识 `auth:user`
  （`AuthResources`）≠ 审计动作 `auth.user.create`（`AuthAuditActions`），形状相近、混用不报错 ——
  详见 `0019` 第 7 条与 `AuthTaxonomyTest`。
- 新增表结构必须追加 `db/migration/{h2,mysql,dameng}/V<n>__*.sql`，版本号取**全仓当前最大号 + 1**
  （权限域占 V3，审计域占 V4），三方言都要写。
- 新增实体必须继承 `BaseEntity`（除 `RefreshTokenEntity` 这类无审计语义的），
  且**不得用 `@TableField` 改列名**。
- **新增 / 修改写接口必须标 `@Audited`**（`action` 取 `AuthAuditActions`、`resource` 取
  `AuthResources`），查询接口不标。见 `0019-审计日志管道与后端自动产生.md`。

## 本切片未覆盖（后续切片）

- 组织 / 角色 / 用户组 / 资源的**管理接口**（表、实体、Mapper 已落地，仅缺 Controller / Service）。
- **数据权限判定**：`data_scope` 与 `rel_role_resource_instance` 的表与字段已就位，翻译成查询条件待做。
- **时态授权过滤**：`effective_from` / `effective_to` 列已留，判定未纳入。
- 验证码、短信登录、多因子（MFA）的实际校验。
- 网关层（`infra/nginx` 与网关空壳）的令牌校验与透传。
- ~~行为审计（谁在何时对哪个资源做了什么）~~ —— **已落地**（2026-10-12），
  但它**不属于权限域**：权限域只负责"标注解"（`@Audited`）与提供三套标识常量，
  记录与查询在 `sts-server-audit`，见 `docs/decisions/0019`。
