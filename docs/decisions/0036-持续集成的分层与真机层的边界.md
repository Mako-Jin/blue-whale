# 0036. 持续集成的分层，与"真机层不进流水线"的边界

- **状态**：已采纳
- **日期**：2026-10-13
- **决策者**：舰长

## 背景

到这个时间点，仓库里已经积了**一批只能靠人记得去跑的验证**：

| 已有的验证 | 规模 | 此前由谁执行 |
| --- | --- | --- |
| 前端单元测试 | 8 个包 / 549 例 | 人（改完自己跑） |
| 后端测试 | 180 例（本次实测；此前文档里记的 174 是旧数） | 人 |
| 前端构建 | 6 个应用 | 人（`vite build` 才会编译全部样式） |
| 产物自检（种子口令不得进包） | 6 个目录 / 18 个文件 | 人（**脚本存在，但是"想起来才跑"**） |
| 网关配置结构自检 | 1 个脚本 | 人 |
| 真机端到端验证 | 8 个脚本（浏览器 + 冷启动 dev server） | 人 |

而 `.github/workflows/` **不存在** —— 也就是说，上面任何一项都可能在某个提交里被跳过，
而且**不会有人知道**。这不是假设，同一轮里就有两条实证：

1. **`0035` 那轮修的三个 e2e 脚本"结论打完进程不结束"**（`finally` 里只 `chrome.kill()`，
   CDP 长连接把事件循环挂住）。在开发机上它的表现是"我多等一会儿"，**在流水线里表现为超时** ——
   这类缺陷**只有在流水线里才会以它真实的样子出现**。
2. **同一轮 `0035` 的 preamble 抢跑**：只在"**冷启动 + 真实浏览器**"下出现。
   这类缺陷**流水线也抓不到**（jsdom 里既没有 Vite 的 HTML 改写也没有真实求值顺序）。

这两件事恰好划出了本条的边界：**该自动化的自动化；抓不到的，不要假装抓到了。**

约束：仓库是**私有**仓库（Actions 额度有限，不做纯装饰的 job）；本次改动**无法在本机跑
GitHub Actions**（本机没有 `gh`，远端未认证 API 返回 404），因此验证方式是
"**把流水线里每一条命令在本机逐条跑一遍**"，而不是"写完就推"。

## 决策

### 1. 按"失败定位"分三个 job，而不是按技术栈分一件事

| job | 内容 | 前置 |
| --- | --- | --- |
| `web` | 装依赖 → ESLint → Stylelint → 类型检查 → 单测 → 构建 → **产物自检** | 无 |
| `server` | `mvn -B -ntp verify`（构建 + 测试，含 enforcer 的 JDK 门禁） | 无数据库 |
| `guards` | 网关配置结构自检 · **文档索引一致性** | 无 |

三个 job 互不阻塞：**哪个 job 红 = 哪一层出问题**，不需要读日志才知道是自己写错了还是环境不对。
这也是"不合并成一个 job"的全部理由 —— 合成一个，前一步失败会掩盖后面所有层的状态。

### 2. 真机层不进必过项（这是本条最要紧的一条）

`scripts/verify-*.mjs` 里那**九个**浏览器脚本（判据：脚本里有 Chrome / CDP 痕迹；权威清单是
`scripts/README.md` 的「前置条件」列）要**真实浏览器 + GPU + 冷启动的 dev server + 端口占用**。
把它们放进必过项，得到的不是"更强的 CI"，而是**随机红**：冷启动竞态、端口残留、
WebGL 在无头环境下的降级分支，都会以"测试失败"的样子出现，而它们**不是**代码缺陷。

> 随机红的流水线比没有流水线更坏：红久了就没人看了，于是它连"真的红"也传达不出去。
> 这与本仓反复出现的"假开关"是同一个错误 —— 交付一个**看起来在把关、实际不把关**的东西。

所以真机层继续由人跑，且**脚本本身要可靠**（非零退出即结论、结论打完必须退出、
浏览器侧报错必须让脚本失败 —— 这三条都在 `0031` / `0033` / `0035` 里逐条补过）。

### 3. 版本一律从仓库既有事实取，取不到的才手写

| 工具 | 来源 | 理由 |
| --- | --- | --- |
| pnpm | `web/package.json` 的 `packageManager` | 与开发机、与 `catalog:` 同一个事实源。两处都写就会漂，漂了 CI 就变成在测另一个版本 |
| JDK | `sts-parent/pom.xml` 的 `java.version` = 21 | 同源；enforcer 在构建期再兜一次 |
| Node | **在 workflow 里手写 `22`** | `engines.node` 写的是**下限**（`>=20`）。拿下限当 pin，runner 上会悄悄飘到某个未来的主版本 —— 升 Node 应当是一次显式改动，而不是一次自动升级 |

一处**必须注意**的实现细节：仓库根**没有** `package.json`（前端工作区在 `web/`），
而 `pnpm/action-setup` 的 `package_json_file` 默认是**仓库根**的 `package.json`，
所以必须显式写 `package_json_file: web/package.json`，否则它读不到 `packageManager`、
要么报错要么退化成"装最新版"。另外它**必须排在 `actions/setup-node` 之前**
——后者的 `cache: pnpm` 要求 `pnpm` 已经在 `PATH` 上。

### 4. 后端 job 不需要数据库服务

这是**已在仓库里的事实，不是新安排**：`application.yml` 的默认 profile 是 h2 内存库，
原文写着"零外部依赖，clone 下来 pnpm/mvn 一把就能跑起来"、"新人 / **CI** 不该被迫先装一个数据库"。
CI 直接用这个默认值，于是**顺带**多了一层验证：Flyway 迁移脚本对着一个空库跑了一遍 ——
迁移脚本不可执行这类错，在 CI 上会以"启动失败"的形式当场暴露。

### 5. 顺带把"改代码必须同改文档"里**能机械判定**的那部分钉住

`docs/README.md` §四 的文档索引是硬性要求（新增 ADR 必须登记），而**此前只靠人记得**。
新增 `scripts/verify-docs-index.mjs`（无前置条件，可进流水线）：

- ADR 索引**双向一致**：既查"有文件没登记"，也查"索引指向不存在的文件"；
- ADR 编号从 `0001` 连续递增（`§三` 写着"只增不改"）；
- §四 里引用的**其他文档路径**都真实存在。

**刻意不查** §二"改哪读哪"表里的路径：那里混着 `decisions/0012`（不带扩展名的简写）、
`sts-server-auth`（模块名）、`packages/*`（通配）。要一律判成路径就得写复杂的规则，
而**会误报的检查最终一定会被关掉** —— 关掉之后它什么也保护不了。

这个守卫**当场被负例证明过不是空转**：写完 ADR 后先跑一次，它在"每篇 ADR 都登记在索引里"
一项上报出 `0036-… .md` 未登记并非零退出，登记之后再跑才通过。

### 6. 流水线的入口只能是 `.github/workflows/`

`infra/README.md` 与 `CONTRIBUTING.md` §九 原本写着"一份部署 / CI 配置 → `infra/`"，
`infra/ci/` 也留着一个空的 `.gitkeep`。这条**做不到**：GitHub Actions 只从
`.github/workflows/` 读流水线，这是**平台的硬要求，不是我们的选择**。

因此：流水线定义落 `.github/workflows/ci.yml`；**删掉空占位的 `infra/ci/`**
（保留一个"永远不可能承载它声称的内容"的目录，是给人指错路）；两处文档订正为
"CI 入口在 `.github/workflows/`，`infra/` 放与平台无关的部署资产"。

## 本机逐条验证（2026-10-13）

GitHub Actions **不能在开发机上运行**（本机没有 `gh`；私有仓库的未认证 API 返回 404），
所以验证方式不是"跑一遍流水线"，而是：**把流水线里每一条命令在本机逐条跑一遍**，
外加对 workflow 自己做一次结构解析。下表就是实际结果：

| 检查 | 命令 | 结果 |
| --- | --- | --- |
| workflow 结构 | `js-yaml` 解析 + 自写断言（每步必须有 `uses` 或 `run`、`uses` 形如 `owner/repo@vN`、trigger / permissions） | 3 个 job / 17 个步骤，全部通过 |
| 前端装依赖 | `pnpm install --frozen-lockfile` | Done —— lockfile 与 `catalog:` 一致 |
| 前端静态 | `pnpm lint` · `pnpm stylelint` · `pnpm typecheck` | 10 / 9 / 10 个任务全成功 |
| 前端单测 | `pnpm test` | **549 例**全绿（8 个包） |
| 前端构建 | `pnpm build` | 8 个任务全成功 |
| 产物自检 | `node scripts/verify-bundle-secrets.mjs` | 6 个目录 / 18 个文件**全部干净** |
| 后端 | `JAVA_HOME=<jdk21> mvn -B -ntp verify` | **BUILD SUCCESS**，15 个模块，**180 例** 0 失败 |
| 网关自检 | `node scripts/verify-nginx-config.mjs` | 全部通过 |
| 文档索引（负例 → 正例） | `node scripts/verify-docs-index.mjs` | 登记前**报出 `0036` 未登记并退出 1**；登记后通过（36 篇） |

一个值得记下来的细节：`pnpm lint` / `pnpm test` 这些命令在本机是**真的通过 turbo 跑的**
（不是绕过 turbo 逐包直跑），所以 CI 与开发机用的是**同一条命令、同一套编排**
（`turbo.json` 的 `dependsOn: ["^build"]`）。这一点很重要 —— 否则 CI 会悄悄变成"另一套构建方式"，
本地绿、CI 红就成了常态。

## 后果

**正面**

- 上面那张表里前五行**第一次有了机器兜底**，不再依赖"想起来才跑"。
- 三层的分工让失败可定位；`--frozen-lockfile` 把"lockfile 漂移"从隐性变成显性。
- 后端迁移脚本每次 CI 都会对着空库真跑一遍。
- 文档索引（含 ADR 编号规则）有了守卫 —— 它是本仓最容易漏、代价最滞后的一步。

**负面 / 代价**

- **首次真跑未在本机验证过**（私有仓库 + 本机无 `gh`）。最可能红的几处已经预见：
  runner 上的 toolchain 版本差异、Maven 首次下载依赖、`--frozen-lockfile` 与 catalog 的
  一致性、以及 runner 默认 Node 与 `setup-node` 的先后顺序。
- 私有仓库的 Actions **消耗额度**；`concurrency` 取消了同分支的旧运行，但并没有省掉
  一次完整构建的成本。
- 前端测试与构建串在同一个 job 里：装依赖只做一次（省时），代价是 lint 失败会
  连带看不到测试结果 —— 分层"够用"，但**不是最优**，等它真的碍事再拆矩阵。

**后续约束**

- 改 `.github/workflows/` 里的命令时，**必须在本机把那条命令跑一遍**再推 ——
  CI 配置本身没有测试，它唯一的验证机会就是下一次推送。
- 加真机脚本**不要**顺手挂进必过项；要挂就先解决随机红（这正是当年把它们留在本机的原因）。
- 新增 ADR / 移动文档后，跑 `node scripts/verify-docs-index.mjs`（现在 CI 也会跑）。
- 版本升级（Node / pnpm / JDK）是**一次显式改动**：pnpm 改 `packageManager`、
  JDK 改 `pom.xml`、**Node 改 workflow**，三处各自唯一。

## 本决策未覆盖

- **真机层**（九个浏览器脚本）—— 见决策 2，这是刻意不做。
- **达梦 / MySQL profile**：CI 只跑默认的 h2。`0010` 的"未用真实实例验证"状态**没有改变**。
  > **后续（0038）**：MySQL 这一半已经被补上了 —— 新增 job `server-mysql` 对**真实 MySQL**
  > 跑全量用例。首次真跑就暴露出 5 处只会在换库时现形的缺陷。**达梦仍未变**（真实实例不可得）。
- **构建产物的缓存与复用**（turbo remote cache、actions/upload-artifact）—— 先跑通再加，
  顺序反了会把"缓存没命中"和"代码坏了"混成同一种红。
- **分支保护规则**（把这三个 job 设成必需检查）—— 那是仓库设置，不在版本库里。
- **镜像构建与推送**：`infra/docker/` 仍为空，CI 不做镜像。
- **`common-api#build` 的 turbo 告警**（既有、不是本轮引入）：`turbo.json` 给 `build` 声明了
  `outputs: ["dist/**"]`，而 `common-api` 的 build 不产出 `dist` ⇒ 每次都会打一行
  `no output files found for task common-api#build`。它不影响结果（任务本身是成功的），
  但会在 CI 日志里长期占一行噪声；改它属于另一件事（要先想清那个任务的产物到底是什么）。
- **文档索引守卫只覆盖 §四**：§二"改哪读哪"表里的路径仍无人查（理由见决策 5）。
