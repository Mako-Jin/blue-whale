# 0060. 登记了却没人抛的码 —— `401xx` / `403xx` 的落点，与一个只守"有没有落点"的守卫

> 起点是 `0059`「未覆盖」的第 3 条（`401xx` / `403xx` 没按"落点—断言"这个口径扫过）。
> 核完得到三个结论：**有落点的码断言都在**（与 `404xx` 那边的"六处零断言"不同）；
> **但有七个码一次抛出点都没有**，其中三个（`*_NAME_EXISTS`）正是 `0056` 未覆盖 4
> 那句"`*_name` 该不该唯一"的**具体形状**；以及 —— 把一个**只判"有没有落点"**的
> 机械守卫立了起来，它第一次运行就报出了那三个码。

## 背景

`0059` 扫 `404xx` 时用的口径是"逐个码回溯源码，数抛出点、核断言"，扫出来的是
**断言的空洞**（六处没有断言）。它留下三条未覆盖，第 3 条说别的段位没有按这个口径扫过。

本轮领的就是这一条，范围取 `401xx` / `403xx` —— 这两段的形状与 `404xx` 不同：
`404xx` 是"一个码就是一个对象"，而 `401xx` 是"一个码是一件事"（凭据错 / 锁定 / 停用 /
令牌无效 / 会话失效 / 验证码 / 口令过期），`403xx` 在本仓只有一件事（无权限）。
正因为如此，扫描的落点也不同：**不是"点名有没有错"，而是"这件事有没有人报"。**

## 一 全貌：有落点的都断言了，但七个码没有落点

把公共枚举 `ResultCode` 与权限域枚举 `AuthResultCode` 的 `401xx` / `403xx` 逐个回溯
`src/main`，得到这张表（权威版本在 `server/README.md`「`401xx` / `403xx` 的落点与它们的断言」）：

| 码 | 落点 | 断言 |
| --- | --- | --- |
| `40100`（公共） | `AuthInterceptor#preHandle` | 5 个用例类（各域权限用例都顺带覆盖） |
| `40101` | `AuthService#login` × 3 · `#changePassword`（覆盖文案） | 5 个用例类 |
| `40102` | `AuthService#login` | `PasswordHardeningApiTest` |
| `40103` | `AuthService#login` | `SessionRevocationApiTest` |
| `40104` | `AuthService#refresh` × 3（其一覆盖文案）· `AuthContextHolder#require`（覆盖文案） | `ChangePasswordApiTest` · `LogoutApiTest` |
| `40105` | **无** | — |
| `40106` | `AuthService#refresh` × 5 | 6 个用例类 |
| `40107`~`40110` | **无** | — |
| `40111` | `AuthService#login` · `#refresh` | `PasswordExpiryApiTest` |
| `40300`（公共） | **无** | — |
| `40301` | `AuthInterceptor#preHandle`（覆盖文案） | 8 个用例类 |
| `42900`（公共） | **无** | — |

与 `0059` 那边对比：**`404xx` 的问题是"有落点却没断言"（六处），这里的问题是"没有落点"（七处）。**
断言这一侧反而干净 —— 每个有落点的 `401xx` 码都至少有一个用例类钉着。

## 二 七个没有落点的码，分两类

"没有落点"不是一种东西，处置也完全不同。所以守卫把它们分开：

| 类别 | 码 | 为什么没有落点 |
| --- | --- | --- |
| **有意不用** | `40105` `TOKEN_EXPIRED` | "过期"在三处被有意合并（见下） |
| 〃 | `40300` `FORBIDDEN`（公共） | 权限拒绝全走域码 `40301`，公共层这一格没有读者 |
| 〃 | `42900` `TOO_MANY_REQUESTS`（公共） | 限流落在 **nginx 层**（`0028`），应用层不抛 |
| **登记了没实现** | `40107` / `40108` | 验证码功能未实现 |
| 〃 | `40109` / `40110` | 多因子未实现（`bw_auth_user.mfa_enabled` 也只回显） |
| 〃 | `40907` / `40909` / `40911` | 角色 / 组织 / 用户组的**名称唯一性**未实现 |

**`40105` 那一格值得单独说。** 它叫"令牌已过期"，而令牌过期是**必然会发生**的现实 ——
一个描述现实的码却没有抛出点，看起来像漏了。实际是**同一条语义被三处各自合并掉了**：

- **访问令牌**过期：`AuthTokenFilter` 只"翻译"不"拒绝"，过期与签名错误一起落进同一个
  `catch (JwtVerificationException)`，于是这次请求只是"匿名的"，最终由 `AuthInterceptor`
  抛公共码 `40100`（文案"未认证或登录已过期"—— 它自己就把两件事写在了一起）。
- **刷新令牌**过期：`AuthService#refresh` 先 `catch (JwtExpiredException)`，但抛的是
  `40106 SESSION_INVALID`（与"已撤销""租户停用"同码），理由是调用方能做的事完全一样。
- **登出**路径：过期按幂等成功处理（`logout` 的注释写了为什么）。

所以 `JwtExpiredException` 与 `JwtVerificationException` 这对**分层**（"上层能区分"）
是保留着的，只是**没有任何一层选择把"过期"透给调用方**。这是有意的，不是漏的 ——
但它此前没有被写下来过，只在代码里。本轮把它写进守卫的白名单（那条注释就是它的归属地）。

## 三 那个守卫：它守什么、不守什么

新增 `scripts/verify-result-codes.mjs`，接进 CI 的 `guards` job。

**它做什么**：读两个枚举里的全部常量，扫 `server/*/*/src/main/java` 对它们的引用；
没有引用的码**必须**在脚本的 `UNUSED` 表里写明理由（并区分 `intentional` / `pending`）。

**它守的是"有没有落点"，不是"有没有断言"。** 这两件事必须分清：

- 有落点却没断言 —— **在它射程之外**。断言的形式太多（`value(40101)`、
  `AuthResultCode.X.getCode()`、变量、`containsString`……），机械判会误报，
  而**会误报的检查终将被关掉**（`0036` 决策 5）。`0059` 那轮人工扫出的六处空缺，
  目前仍是唯一办法。
- 它守的是**前置条件**：一个连抛出点都没有的码，谈不上有断言。

**它与"全称句守卫"的区别** —— 这是它值、而 `0056` 那类不值的理由。`0056` 把
"给『全仓都……』加机械守卫"列进了**刻意不做**，因为全称句（"每个域都清了残留"）
要理解语义才能判。本脚本判的是另一件事：*某个标识符在源码里有没有被引用* ——
语法级、逐字符可判、不依赖任何约定，因此不误报。它挡住的是**只增不减的退化**：
码越加越多，没人记得哪个是活的。

**它当场抓到三个码**（第一次运行就报红 —— 那不是脚本写错了，是它第一次工作）：
`ROLE_NAME_EXISTS` / `ORG_NAME_EXISTS` / `USER_GROUP_NAME_EXISTS`。

## 四 顺带撞出的：三个 `*_NAME_EXISTS` 与一条旧待办

这三个码登记在枚举里，**没有任何地方抛**，而它们各自的兄弟 `*_CODE_EXISTS` 都有落点。
更关键的是**跨域不一致**：租户侧的 `TENANT_NAME_EXISTS` **有**落点
（`TenantService` 真的在校验租户名唯一）—— 于是"名称唯一"这件事在本仓是
**租户做了、角色 / 组织 / 用户组没做**。

`0056` 的未覆盖 4 是这么写的："`*_name` / email / phone 该不该唯一"。本轮把那个疑问
变成了**具体形状**：不是一个"要不要"的问题，而是**三个具体的码加三处缺失**，
且旁边就有一个已经做了的对照（租户）。

**本轮不动它** —— 它要的是产品决定（名称该不该唯一），不是实现。但它现在住进了守卫的
`pending` 清单：谁把名称唯一实现了，守卫会提醒他"这个码已经有落点了，把它从名单里删掉";
谁新加一个没人抛的码，守卫会拦住他。**这是 `pending` 这一类的全部意义。**

## 五 "未认证"在实现里有两个码

`40104 TOKEN_INVALID`（"令牌无效"）有四处落点，其中**一处在说另一件事**：

```java
// AuthContextHolder#require()
throw AuthResultCode.TOKEN_INVALID.businessException("当前请求未认证");
```

它说的不是"你给的令牌无效"，而是"**你没带令牌**"（或带了但没通过校验）。而入口
`AuthInterceptor` 对同一件事抛的是公共码 `40100 UNAUTHORIZED`。

- **它是有意的**：`AuthService#logoutAll` 的注释点名了"现在由 `require()` 明确拒绝（`40104`）"，
  `LogoutApiTest` 有一条用例钉住它（`shouldRejectAnonymousLogoutAll`）。
- **它落在 `404xx` 那节立的规矩上**：**在抛出点覆盖文案 = 这个码在说两件事。**
  `40104` 本义是"令牌坏了"，覆盖后同时表达"没带令牌"—— 而后者已经有专门的码。
- **代价是前端要认两个码**：现状 `platform-audit-console` 认 `40100`，
  `platform-admin` 与门户认 HTTP 401（`common-tools/http` 的刷新逻辑看的是传输层状态码）。
  **没有一处认 `40104`** —— 也就是说，`logout-all` 那条路径上的"未认证"在现有前端里
  落回通用提示。影响小（那条路径只有门户会走），但它是一个**两套码并存**的形状。

**本轮不改**：统一成一个码要动前端（三处判据）与两条用例，是产品决定。记为未覆盖。

## 七 它证明了守卫不是空转

| 扰动 | 期望 | 实测 |
| --- | --- | --- |
| 把 `RoleService` 的 `ROLE_CODE_EXISTS` 改名成 `ROLE_NAME_EXISTS` | 一次扰动同时触发两条：前者变零落点、后者有了落点（白名单腐烂） | **两条都报红**，且各自点名的正是对应的码 |
| 首次运行（未做任何扰动） | 报出三个未登记的码 | `40907` / `40909` / `40911` —— **天然负例** |

扰动后已还原（`git diff --exit-code` 确认 `RoleService.java` 与 HEAD 一致）。

## 决策

1. **"有没有落点"用机器守，"有没有断言"仍靠人工。** 前者是语法级事实、可精确判定；
   后者要理解断言形式，机械判会误报。**宁可少守一样，不要守出假红**（`0036` 决策 5）。
2. **白名单必须写理由，且要分两类。** `intentional`（有意不用，不该动）与
   `pending`（登记了没实现，是待办）处置完全不同 —— 混成一张表的话，
   后来者分不清"这个码能不能动"。
3. **守卫要报"白名单腐烂"。** 一个码重新有了落点、却还留在名单里，说明理由已经过期。
   不报的话，名单会慢慢变成一张"没人敢删"的表。
4. **不为了统一而统一。** `40104` 那处覆盖、`40300` 与 `42900` 的零读者，都先记为
   未覆盖而不是顺手改 —— 它们各自要的是产品决定，而"改一个码"会牵动前端与用例。
5. **"没有落点"也是要写下来的事实。** 七个码此前谁都说不清是漏了还是有意留着；
   现在每一个都在 `UNUSED` 里有理由与归类。

## 后果

**正面**

- "登记了却没人抛"从一个只能靠读代码偶然发现的问题，变成构建期可查的。
- `pending` 那四个（`*_NAME_EXISTS` 三个 + 验证码 / MFA 四个）从"可能漏了"变成
  **一份明确的清单**，且实现它们时会有提示来收尾。
- `40105` / `40300` / `42900` 的"为什么没有落点"第一次被写下来（此前只在代码里）。

**负面 / 边界**

- **它给的安全感只覆盖一半。** 有落点没断言的码它不报 —— 别把"守卫绿了"读成
  "错误码这一层没有问题了"。`0059` 那份人工扫描仍要定期重做。
- **它是文本匹配**：反射、字符串拼接出来的码、以及未来可能出现的新枚举都不在射程内。
  加新枚举要在脚本顶部的 `ENUMS` 里登记一行。
- **白名单是一处需要维护的东西**：理由过期、码改名、功能实现，都可能让它失真。
  "报白名单腐烂"那一条就是为了让它别烂掉。

## 未覆盖

1. **"未认证"要不要统一成一个码。** 现状入口 `40100`、内部 `40104`，且有意的。
   统一要动前端三处判据 + `LogoutApiTest` / `ChangePasswordApiTest` 两条用例，
   是产品决定。**先定"前端该按业务码还是传输层状态码判 401"** —— 这个问题不定，
   统一了也还是两套。
2. **`*_NAME_EXISTS` 三个码要不要实现。** 即"角色 / 组织 / 用户组的名称该不该唯一"。
   仓里有一个已做的对照（租户名），但"租户做了"不构成"别的也该做"的理由。
3. **断言仍靠人工。** `401xx` 这一侧恰好每个码都有用例，但那是历史累积的结果，
   不是守出来的；新增一个码时，守卫只保证它"有人抛"，不保证"有人钉"。
4. **前端读了哪些码没核过。** 这是另一条判据（跨端），本轮只看了后端 `src/main`。
   已知的三处判据不一致（`40100` / HTTP 401 / 无）就在眼前，但没有系统扫过。
5. **守卫的扫描面只有 `src/main`。** 测试里引用某个码**不算**落点（这是有意的），
   但反过来也意味着：一个只被测试引用的码，会被判成"没有落点"。
   当前没有这种码，将来若有（例如故意留一个"只给测试用"的码），要在白名单里说明。
