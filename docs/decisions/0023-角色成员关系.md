# 0023. 角色成员关系：把角色交出去，配置侧就此闭环

- **状态**：已采纳
- **日期**：2026-10-12
- **决策者**：舰长

## 背景

`0021` 交付了**资源目录**（造权限码），`0022` 交付了**角色与角色资源授权**
（把权限码授给角色）。两篇之后，RBAC 判定链的配置侧还差最后一环：
**没有接口能把角色授给任何人**。

这一环的缺席方式比前两环更隐蔽 —— 链路上它**是通的**：

- 表 `bw_auth_rel_role_member` 从 `V3` 就在，多态成员（USER / GROUP）与时态列都齐；
- `AuthorizationMapper` 的两条 SQL 都完整地读了它，连"用户 → 用户组 → 角色"的
  二级跳转都写好了；
- 判定能算出"某个人最终有哪些权限"，`/me` 也照常返回 `roles` 与 `permissions`。

缺的只是**写这两列的东西**。于是 admin 之所以有权限，是因为
`DefaultAdminSeeder.grantRole()` 直接插了一行；`RoleApiTest` 要验证判定链路时，
只能在测试里经 Mapper 插一行 —— 并且当时的注释诚实地写明"那是测试的取巧，
不是接口的一部分"。

后果是：`0021` 与 `0022` 造出来的角色与授权，**授不出去**。整个权限体系仍然只有
种子数据写死的那两个身份。

本决策交付**角色成员关系**（`/api/auth/roles/{id}/members`），
并顺带把两处"存在但不可配置 / 存在但不可达"的地方说清楚（见第 5、9 条）。

## 决策

### 1. 成员关系是角色的第二个子资源，与授权并列

```
GET    /api/auth/roles/{id}/members                        查成员（分页）
POST   /api/auth/roles/{id}/members                        授予成员
DELETE /api/auth/roles/{id}/members/{memberType}/{memberId} 解除成员关系
```

与 `/resources` 同一条理由：**成员关系是角色的内部边**。它没有脱离角色与成员
独立存在的意义，也没有独立的生命周期 —— 不存在"没有角色的成员关系"。
挂在角色下，URL 本身就说明了"改的是这个角色的成员集合"，同时天然带上归属校验。

**没有"清空某角色全部成员"的接口**，与 `0022` 不给"清空全部授权"同理：
一次点击可能让几百人同时失去权限，而审计里只有一条记录。

### 2. 撤销路径必须带 `memberType`，不能只用 `memberId`

这是本片与 `/resources` 唯一的形状差别：资源侧撤销用两段
（`{roleId}/resources/{resourceId}`），成员侧用三段。**两段在这里真的不够。**

`member_id` 是**多态列**，只在它自己所指向的那张表里有意义 ——
`bw_auth_user` 与 `bw_auth_user_group` 是两个独立的自增序列，
两个主键会撞号，而且撞号是常态而不是边界情况。若撤销只按 `memberId` 定位，
"撤销给了 ID=5 的用户"会**连带把"ID=5 的用户组"也撤掉**。

代价是很具体的：撤错了表现为**权限凭空消失**，没有报错、没有痕迹，
而用户只会说"我昨天还能点，今天不能了"。多写一段路径换来"不可能撤错对象"。

### 3. `memberType` 必填，刻意不给默认值

给 `USER` 当默认值是最"顺手"的做法，但它把一次明确的操作变得不明确：
调用方想授用户组、却漏了这个字段时，系统会拿 `memberId` 去用户表里找
一个**恰好同号的用户**并授给他 —— 一次真实存在的用户被静默提权，
而请求里没有任何一处写错过。

必填的代价只是调用方多写一个字段，收益是"授错对象"从**可能发生**变成**不可能表达**。
与 `0022` 第 2 节选择 `resourceId` 而不同时支持 `resourceId` / `resourceCode`
是同一条思路：形态上让歧义无法表达。

### 4. 成员必须存在（多态表刻意没有外键）

`USER` → 查用户表，`GROUP` → 查用户组表，不存在返 `40002`。

`MemberType` 的注释里写明这个取舍：**放弃外键**，换来"我为什么有这个权限"的追溯
只有一条路径（不必把两条链路拼起来看）。代价就是存在性只能由应用层保证 ——
本片正是那个"应用层"。

### 5. 成员必须与角色同租户，否则判定永远匹配不上

判定 SQL 的**两侧**都限定租户：`rm.tenant_id = ?` 与 `ro.tenant_id = ?`。
因此一段跨租户的成员关系**永远不可能生效** —— 它不会报错，只会安静地躺在库里：
列表里看得见、权限里没有。

这类"静默不可达的数据"是本仓尽量不让接口制造的东西，与
`RoleService.resolveParent` 校验"父角色必须同租户"是同一条。
文案也刻意点明租户而不是含糊地说"不存在"：`40002` 的默认文案是
"引用的关联数据不存在"，而这里数据**确实存在**，只是放错了租户 ——
只说"不存在"会让调用方去查主键有没有写错，方向完全跑偏。

### 6. 授予是 upsert，并清掉同键的其余行

与 `0022` 第 2 节**完全同一套**，因为两张表的形状一模一样：
`(role_id, member_type, member_id)` 上**没有唯一索引**（`V3` 里只有三个普通索引）。

- **直接插**：把"临时代理"改回长期有效时会留下同键的第二行，
  读表的人再也说不清这个人是什么时候被加进来的；
- **先删后插**：`create_time` 每次刷新，"这段关系从什么时候开始"就追溯不到了。

因此定位唯一一条有效行为目标：存在则改它的时间窗，存在但已被解除则**复活**它，
不存在才新建；写完之后清掉同键的其余行（并发下服务层的"先查后写"挡不住）。

时间窗的写入用**逐列显式 `set`**，不用 `updateById` ——
`0022` 第 9 条记的那个 `NOT_NULL` 字段策略缺陷在这里有同样的表现：
"把临时代理改回长期有效"就是清掉时间窗，清不掉就意味着这段成员关系
**永远停在过期状态**，表现为"我明明重新加进去了，怎么还是没权限"。
本片的端到端测试专门有一条断言盯住它（改回长期有效后权限必须回来）。

### 7. 成员列表分页，且不做按名搜索

**分页，而资源授权列表不分页 —— 这个差别是有意的。**
一个角色能授出的资源数被权限码总量封顶（当前 17 个，长期也就百量级），
一次取完是合理的；而成员是**多对多**的，"全员"这类角色的成员可能上万。

**不做关键字过滤**：成员名在**另一张表**里，而且随成员类型在两张表之间切换。
要按名字过滤就得先跨表解析出名字、再过滤 —— 那样 `total` 就不是数据库给的那个数了，
得先全量捞关系行才敢报总数，等于把分页的收益（不取全量）还回去。
按名字找一个人应当从**用户**列表那一侧进入（那里名字是本表的列，可以走索引）。
真的出现"在角色里按名字搜成员"的诉求时，正解是在关系表上冗余一份成员名，
而不是在这里做一次跨表后过滤。

### 8. 成员名分两次批量查，不用 JOIN，也不用 N+1

被授对象是多态的，一条 JOIN 得写成
`CASE WHEN member_type = 'USER' THEN u.display_name ELSE g.group_name END`
再挂两个 `LEFT JOIN` —— 一条 SQL 同时被两张表的方言细节影响，
而且 `bw_auth_user_group` 目前还没有任何接口，它的存在对这条查询是个不能失败的依赖。

改为"先取关系行（分页后的一页），再按类型分组各查一次 `IN`"：
总共 3 条查询、与成员数量无关，每一条都能单独看懂。

**成员已不存在时 `memberName` 返回 `null` 而不是报错或过滤掉**：
过滤掉会让"授过、但那个人已经被删了"这一段历史凭空消失，
而它恰恰是排查"为什么权限对不上"时要看的东西。

### 9. 不拒绝给"已停用的角色"或"已停用的用户"加成员

它们当前都不产生权限（判定要求 `ro.status = 'ENABLED'`，成员自身可用性由认证环节把关），
但"先配置、后启用"是合理的运维顺序：新员工的账号与角色一起建好、上线当天再启用，
比上线当天手忙脚乱地补配置安全得多。

与 `0022` 不拒绝给已停用资源授权是同一条判断。

`RoleMemberVO.effectiveNow` **只表达关系自身的时态**，刻意**不**把"角色停用"
和"成员停用"也压进这个布尔：一段成员关系是否真的在产生权限由**三个独立开关**
共同决定，压成一个值会让"到底哪个开关关着"变成不可见 ——
而那正是排查权限问题的第一个问题。成员列表回答"这个角色给了谁"，
"这个角色现在是不是停用"由 `GET /api/auth/roles/{id}` 回答（界面本来就会加载它）。

### 10. 复用 `auth:role:update` 权限码，但审计动作必须分开

读用 `auth:role:read`，写复用 `auth:role:update`，**不新增权限码**
（`AuthPermissions.ALL` 仍是 17 项）。理由与 `0022` 第 10 节一致：
目前只有一个身份持有它，拆出一个 `auth:role:member` 会是一个没人能"不同地持有"的权限码。

但这条路径与"给角色授资源"在**性质上不同**，必须写下来：

|                | 把资源授给角色                     | 把角色授给一个人（含自己）       |
| -------------- | ---------------------------------- | -------------------------------- |
| 受益条件       | 你得**已经持有那个角色**           | 受益者**当下就换了**             |
| 提权属性       | 条件式（先有角色）                 | **直接提权**                     |

也就是说，`auth:role:update` 现在包含一条**可以把自己加到 `SUPER_ADMIN`** 的路径。
这与 `auth:user:update` 含"重置任意账号口令"（包括管理员）是同一性质，
本仓已经接受过一次，因此本次同样不拆。

**触发条件是明确的**：当出现**第二个持有 `auth:role:update` 但不持有全部权限的角色**时，
就必须拆出 `auth:role:member`（加一个常量 + 换注解，不影响数据）。
在那之前不拆，避免用权限码表达一个不存在的分工。

审计上则**必须分开**，而且是本片比 `0022` 更强烈的一条：

- `auth.role.grant` —— 谁**扩大了这个角色的权限范围**；
- `auth.role.grant_member` —— **谁把某个人变成了这个角色**。

后者是更直接的一次提权。事后追责时"谁把 `SUPER_ADMIN` 授给了这个账号"必须能
一条过滤直接命中；让它藏在 `auth.role.grant` 里等于没记录。

### 11. 删除角色仍拒绝"有成员"，但复活角色时一并清空成员关系

`0022` 的第 6 条不变：**有成员时拒绝删除角色**（`40916`），
因为删角色会让持有它的那些人立刻少掉一批权限，而管理员的本意可能只是
"清理一个不再用的角色"。

本片补的是另一头：`create` 的复活分支此前只清授权，现在**也清成员关系**。
目的是让"**复活 = 一个没人持有、也没有权限的角色**"成为**无条件**成立的语义。

看起来多余 —— 有成员的角色根本删不掉，那软删的角色怎么会有有效成员行？
正因为它多余才要加：`delete` 的那道守卫属于**正常路径**，
而复活分支要防的恰恰是**非正常路径**（角色行被直接改库删掉、关系行还在）。
这一层保护的意义就是让语义不依赖"别的代码都写对了"。
`0022` 的第 8 条为授权写了同一句话，本片把成员也纳进去。

### 12. 成员关系上的时态首次进入验证范围

`effective_from / effective_to` 三张表都有，`0022` 只把**角色-资源**那一张
接进判定并验证。成员关系这一张虽然 SQL 里也过滤了，却**从来没有入口去产生它** ——
也就从来没被验证过。

本片的端到端测试盯住两处：

- **角色成员关系上的时态**：加成一段未来的区间 → 列表里 `effectiveNow=false`、
  判定当它不存在（`40301`）；改回长期有效 → 权限必须回来；
- **用户组成员关系上的时态**：判定里那段子查询同样有过滤，
  组-用户关系过期后权限必须消失。

第二处顺带把**组链路**（用户 → 用户组 → 角色 → 资源）第一次端到端跑通 ——
那段子查询写在那里很久了，此前没有任何东西走过它。

## 后果

- **配置侧闭环完成**：资源（`0021`）→ 角色与授权（`0022`）→ 成员（本决策）。
  这是第一次可以**只经接口**把一个账号配成管理员 —— 在此之前
  admin 的权限形状由 `DefaultAdminSeeder` 写死，改一次授权只能改库。
- **组链路首次被验证**。判定 SQL 里那段二级跳转从写下起就没走过。
- 权限码不变（17 项）；错误码新增 `40408`；审计动作新增 2 个
  （`auth.role.grant_member` / `auth.role.revoke_member`）。
- 契约 42 → 45 个接口；`RoleApiTest` 里那段"测试自己写库插成员关系"的注释
  不再必要，`RoleMemberApiTest` 走的是接口，**校验链也参与进来**
  （不存在的主键、跨租户的成员都会被挡掉），这是直接写库永远覆盖不到的。
- 仍然直接写库的地方只剩两处夹具：用户组与组-用户关系
  （`bw_auth_user_group` 与 `bw_auth_rel_user_group_member` 都还没有接口）。

## 本决策未覆盖

- **用户组 / 组织的管理接口**。`bw_auth_user_group` 有实体与仓储、没有服务与接口；
  `bw_auth_rel_user_group_member` 有实体与仓储、没有任何写入路径。
  本片用测试夹具验证组链路，那**是夹具不是接口**。
- **`/api/auth/users/{id}/roles`（反查"这个人为什么有权限"）**。
  这是排查权限问题时最常用的入口（"他的权限是从哪个角色来的、那个角色是谁给的"），
  而且它天然要跨越"直接授予"与"经用户组授予"两个来源。
  它与用户组管理是同一批的事，因此一起留给后续切片。
- **角色继承**：`parent_id` 与 `inherit_strategy` 只建层级、不产生任何权限传递。
- **数据范围求值**：`data_scope` / `filter_json` 只存不用。
- **实例级授权**：`bw_auth_rel_role_resource_instance` 表已就绪、零代码。
- 前端未接：`AccessPermissions` 刻意不含 `auth:role:*`（该文件规则是"只列前端真的用到的"）。

## 发现但未处理（供后续决策）

1. **嵌套用户组在判定里不生效，而注释声称支持。**
   `bw_auth_rel_user_group_member.member_type` 同样是多态列，
   `RelUserGroupMemberEntity` 与 `MemberType` 的注释都写着"组可以嵌套"，
   但判定 SQL 把 `gm.member_type` 钉成了 `'USER'` —— **只跳一层**。
   把"上海分部"放进"华东大区"、再把角色授给"华东大区"，上海分部的人
   **拿不到权限**，而成员列表里一切正常。
   已在 `AuthorizationMapper` 的类注释里写明（原文是断言"支持嵌套"，属于误导性注释）。
   **不在本片补**：真要做需要 `WITH RECURSIVE`，它在三套方言上的写法与版本要求
   都不一致，达梦在 Oracle 兼容模式下的支持程度未验证过；
   仓促加进去的风险是把"嵌套不生效"换成"某套库上整条判定失败" —— 后者严重得多，
   且不会在 h2 上暴露。触发条件：真的需要嵌套组时，且先在达梦实测。
   在那之前，**嵌套组这条路应当由用户组接口显式拒绝**，而不是默默接受。
2. **`auth:role:update` 现在包含一条直接提权路径**（把自己加到任意角色），
   见第 10 条。触发条件：出现第二个持有 `auth:role:update` 但不持有全部权限的角色。
3. **遗留的 `0022` 未处理项全部仍然成立**，本片没有推进它们：
   `DuplicateKeyException` → `409` 处理器（`40900` 段仍是空的）、
   `updateById` 的 `NOT_NULL` 策略在 `TenantService` / `UserService` 上未修、
   `40913` 被复用表达"有子节点"、
   `(role_id, resource_id)` 与 `(role_id, member_type, member_id)` 两处仍无唯一索引
   （后者的前提同样是先有 `DuplicateKeyException` 处理器）。
4. **多态表没有外键 ⇒ 成员被删后关系行会留下**，表现为列表里 `memberName` 为 `null`。
   本片选择"显示它"而不是"过滤它"（历史不该消失），但**没有提供清理入口**。
   触发条件：用户组接口落地时，需要在"删用户/删组"上做拒绝或级联的取舍。
