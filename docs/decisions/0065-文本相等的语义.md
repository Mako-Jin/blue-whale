# 0065. 文本相等的语义 —— 三个方言此前各答了一半，且没人发现

- **状态**：已采纳
- **日期**：2026-10-15
- **决策者**：舰长

> 领的是 `0062`「未覆盖」第 1 条：**`email` / `phone` 要不要从"业务规则级唯一"升成
> "数据约束级唯一"**（即加 `UNIQUE`）。
>
> 核完发现这个问法**缺一个前提** —— "唯一"是相对某个**相等关系**说的，而
> "两个文本什么时候算相等"在本仓**从来没被回答过**。于是它由三个方言各自的默认
> 排序规则代答，而三个默认值**互不相同**：MySQL 认 `A@b.com` = `a@b.com`，
> H2 不认。这不是纸面差异 —— 登录就是 `WHERE username = ?`，所以
> **同一个 `ADMIN` 在 MySQL 上能登进 `admin` 的账号，在 H2 上不能**。
>
> 顺带查出一件更凉的事：**`40902` / `40903` 这两处判重一条用例都没有**
> （`grep -rn "40902\|EMAIL_EXISTS" server/sts-app/` 零命中）。也就是说这一整块
> "判重"从来没有在任何一个 profile 上被跑过。

## 背景

### 1 那个问法缺的前提

`0062` 把列分成三类（标识 / 寻址 / 标签），判的是"要不要挡重名"。它答得没错，
但它默认了"重名"是可判定的 —— 而 `email = ?` 究竟匹配到什么，取决于
**列上的排序规则**，不取决于服务层。于是：

- 服务层那道 `selectCount` 的**强度**由我们决定（`0062` 说得清楚）；
- 服务层那道 `selectCount` 的**含义**由数据库决定 —— 而这里**一个字都没有**。

把 `email` 升成 `UNIQUE(tenant_id, email)` 会把这件事从"服务层的隐式默认"
搬进"DDL 里的一行 `COLLATE`"，**不会让它变成被决定过的事**。所以本片先答前提，
再回来答 `0062` 那个问题（答案见「决策」）。

### 2 实测：两台引擎，同一段 SQL

三个方言的 MySQL 与 H2 都是本机实跑（MySQL 8.0.26 干净实例，`--initialize-insecure`，
库按 `application-mysql.yml` 的建库语句建；H2 2.4.240 用本仓 h2 profile 的**原样 URL**
`jdbc:h2:mem:bluewhale;DB_CLOSE_DELAY=-1;MODE=MySQL;DATABASE_TO_LOWER=TRUE`）。
探针表建的是 `V3` 里 `bw_auth_user` 的形状（`username` 唯一索引 + `email` 普通索引）：

| 探针（已存 `a@b.com` / `admin`）      | H2 2.4.240 | MySQL `_ai_ci`（V3 现状） | MySQL `_as_cs` | MySQL `_bin` |
| ------------------------------------- | ---------- | ------------------------ | -------------- | ------------ |
| `email = 'A@B.COM'`                   | **0**      | **1**                    | **0**          | **0**        |
| `email = 'a@b.com '`（尾空格）        | **0**      | **0**                    | **0**          | **1**        |
| `email = 'á@b.com'`（重音）           | **0**      | **1**                    | **0**          | **0**        |
| `WHERE username = 'Admin'`            | **0**      | **1**                    | **0**          | **0**        |
| 唯一索引：已有 `admin` 再插 `Admin`   | **允许**   | **拒绝**（`ERROR 1062`） | **允许**       | **允许**     |
| 两行 `email = NULL`                   | 都建成     | 都建成                   | 都建成         | 都建成       |

三个可以直接读出来的结论：

1. **MySQL 与 H2 的方向相反，而且两处都反**：既在服务层判重上反（前三行），
   也在唯一索引上反（第五行）。所以这不是"某一层没对齐"，是**两套语义**。
2. **名字最像"二进制比较"的 `_bin` 反而错一格**（第 2 行）。`_bin` 是遗留排序规则，
   **PAD SPACE** ⇒ `'a@b.com ' = 'a@b.com'` 成立；而 H2 认为它们不同。
   `utf8mb4_0900_*` 系列是 **NO PAD**。**这一格是量出来的，不是从名字推的** ——
   如果按"二进制 = 最严格"去选，会得到一个"看起来对齐了、其实新引入一处分歧"的结果。
3. **H2 想改也改不动**：本仓 URL 里**没有** `IGNORECASE`，而 H2 2.x **已经不再支持
   这个设置** —— 当次实测把它加进 URL 后 `SELECT 'a' = 'A'` 仍返回 `FALSE`。
   H2 的原生替代品是 `VARCHAR_IGNORECASE` 类型（实测有效），但它做的是**反方向**
   的事（大小写不敏感）。

## 一 决策：相等是"区分大小写、也区分重音"的

**因为这是 H2 与达梦的实际行为，而 MySQL 是可以被改成它的那一侧。** 反方向
（把 H2 改成不敏感）技术上做不到 —— 见上面第 3 点，H2 2.x 没有可用的开关，
只能逐列换类型，而类型一换就直接改变了**存储语义的可塑性**（将来想回去又要换一遍）。

具体到 MySQL：`COLLATE` 从 `utf8mb4_0900_ai_ci` 改成 **`utf8mb4_0900_as_cs`**
（accent-sensitive + case-sensitive）。选它而不是 `_bin` 的理由就是上表第 2 行 ——
**`_as_cs` 是四格全对的唯一候选**。

### 为什么这个选择不需要额外辩护

- **它是"不动的那一侧"**：H2 与达梦零改动，改动集中在 MySQL 一份迁移里；
  如果选反方向，就得给 H2 逐列换类型（`VARCHAR_IGNORECASE`）而 H2 侧没有表级写法，
  等于把一条统一规则拆成 20 多处列级特例。
- **它让"两个看起来一样的登录名"不可能存在**：`admin` 与 `Admin` 是两个不同的值，
  一眼能看出不同，不存在"界面上一模一样、其实是两个账号"这种状态。
- **代价是明确的**：用户得记住自己注册时的大小写。这一点写进「后果」，
  并且由 `TextEqualityApiTest` 钉成断言（登录区分大小写），不是一句承诺。

## 二 落地：一个版本号，三份脚本，只有一份有语句

新增 **`V8__align_text_equality_collation.sql`**（版本号全仓唯一：V1 日志 / V2 事件 /
V3 权限建表 / V4 审计 / V5 口令加固 / V6 日志加列 / V7 事件加列，本片接 V8，见 `0009`）：

| 方言     | 内容                                                              | 为什么 |
| -------- | ----------------------------------------------------------------- | ------ |
| `mysql`  | 13 张 `bw_auth_*` 表逐张 `CONVERT TO CHARACTER SET utf8mb4 COLLATE utf8mb4_0900_as_cs` | V3 给每张表**显式**写了 `_ai_ci`，必须覆盖 |
| `h2`     | **空**（只有注释）                                                | H2 的默认值恰好就是目标值 |
| `dameng` | **空**（只有注释），且标了**未实测**                              | 预期默认是二进制比较，但本仓没有达梦实例 |

三点说明：

- **为什么不改 `V3`**：`0009` 写明"迁移脚本一旦在真实环境执行过就不可修改"
  （校验和不匹配会让启动直接失败）。所以 V3 / V5 里的表选项保持原样，本片在其后覆盖一层。
  —— 于是 `git log` 上会出现"V3 写 `_ai_ci`、V8 改成 `_as_cs`"，那是迁移的正常形态，
  不是矛盾。
- **为什么用整表 `CONVERT` 而不是逐列改 `COLLATE`**：它同时改**表默认值**与**已有列**，
  于是将来新增的列自动继承 `as_cs`，而不是悄悄退回库级默认。而且
  "一个库一个等价关系"比"哪几列特殊"容易守 —— 本域没有一处文本比较是**特意**
  要大小写不敏感的。
- **为什么 h2 / dameng 也放一个空文件**：`find` 一眼看过去三份脚本仍然一一对应
  （本仓的三方言目录就是按这条建的）。空文件里写的是"为什么这里没有语句"，
  顺带挡住"把 mysql 那条 `ALTER` 抄过来"这个反射 —— 抄过来 H2 会直接启动失败。

## 三 守卫：跨 profile 的断言，而不是新的 `verify-*.mjs`

新增 **`TextEqualityApiTest`**，7 例。它**刻意不 `@Transactional`、不按 profile 跳过**：
同一批断言在默认 h2（`server` job）与真实 MySQL（`server-mysql` job）上**各跑一遍**，
两个 profile 都绿才算数。

这是本仓**第一处跨 profile 的语义断言**，也是这条决定的真守卫。为什么不用
`scripts/verify-*.mjs`（`0060` / `0063` 那条路）：脚本能读的只有**文本**，而
"H2 的默认比较是敏感的"这件事**在 H2 的迁移脚本里没有任何字**（它就是"没写"）。
能机械化的守卫锚定的是"无歧义的 token 形状"（见 `0064` 的判据），
这里没有那种形状 —— 但**有一个比脚本更强的办法**：让两个引擎各跑一遍同一批断言。
两个 CI job 本来就存在（`0038` 建了 `server-mysql`），本片只是第一次把它当**语义对账器**用。

另外，断言写的是**行为**（"大小写不同的邮箱建得出来"），一个字的排序规则名字
（`_ai_ci` / `_as_cs` / PAD SPACE）都没提 —— 因为 H2 那侧无手段可写，只能按行为对账；
顺带也避免了"改个排序规则名字就绿"这种假通过。

**扰动验位（当次实测）**：把 h2 的 `username` / `email` 临时改成
`VARCHAR_IGNORECASE`（也就是把 H2 变成"大小写不敏感"）⇒ **7 例里 3 例变红**：
`shouldAllowEmailDifferingOnlyInCase`（期望 `0`，实得 `40902`）·
`shouldAllowUsernameDifferingOnlyInCase`（期望 `0`，实得 `40901`）·
`shouldNotAcceptALoginThatDiffersOnlyInCase`（期望 `40101`，实得 `0`）。
改回后 7 例全绿 ⇒ 用例对"相等语义"是敏感的，不是空转。

**题外但值得记一笔**：扰动前我按"改的是建号那一层"预期**两例**变红，实测是**三例** ——
登录那一例也跟着红了。这正是"扰动验位"要买的东西：**它顺带证明了那条断言真的连着
被改的那件事**，而不是一条"因为别的原因恰好通过"的用例。若当时按预期写文档，
就会把这一条漏记成"登录那例大概也连着吧"。

## 决策

- **相等是区分大小写、也区分重音的**（= H2 / 达梦的实际行为）。
  MySQL 的 `bw_auth_*` 全部转到 `utf8mb4_0900_as_cs`（新增 `V8`）；
  H2 / 达梦零改动，各自留一份说明为什么没有语句。
- **`email` / `phone` 仍然不加 `UNIQUE`**（`0062` 的结论不变）——
  但现在它有了**第二个**理由：下沉成数据约束级唯一，会把"相等关系"这件事
  从服务层的隐式默认搬进 DDL 的一行 `COLLATE`，**并不使它变成被决定过的事**。
  真正的落点是本片，不是那两条 `UNIQUE`。
- **新增 `TextEqualityApiTest`（7 例）**，同一个类在两个 profile 上各跑一遍；
  它同时补上了 `40902` / `40903` 此前**零覆盖**的空白。
- **`application-mysql.yml` 的建库语句**从 `utf8mb4_0900_ai_ci` 改成
  `utf8mb4_0900_as_cs`（新库起手就是目标值；已有库由 `V8` 覆盖）。
- **零接口形状改动**：不改任何列、不新增错误码、不动 OpenAPI 契约、不动前端。

## 后果

**正面**

- "两个文本什么时候算相等"第一次成为**被写下、并且被两个引擎各验一遍**的事。
- **登录、判重、唯一索引三处用的是同一个语义**了 —— 此前它们是三处各自的默认值。
- `40902` / `40903` 从零覆盖变成有覆盖，且覆盖在两个 profile 上。
- `0062`「未覆盖」1 关闭：那条"要不要下沉"的问法缺的前提被补上了，答案也随之稳固
  （不下沉，且理由从"寻址类留弹性"升级为"下沉也答不出这个问题"）。

**负面 / 代价**

- **这是一处产品可见行为的改变**：`ADMIN` 不再能登进 `admin` 的账号；
  MySQL 上此前"碰巧能"的同名/同邮箱现在会被当作两个不同的值。
  —— 注意**方向**：改的是 MySQL（此前不敏感的那一侧），H2 的行为**没有变**。
- **一处方言差异是"用不同手段达到同一语义"**，而不是同构的 DDL：
  mysql 用 `COLLATE`，h2/dameng 用"默认值即是"。读脚本的人会看到三份不同构的文件 ——
  这是 `0009` 分方言目录的应有形态，但确实比"三份拷贝"更难一眼确认。
- `CONVERT TO CHARACTER SET` 会**重建表**（13 张）。本仓是预发布、且 CI 每次
  空库从零迁移，代价可忽略；真实库首次升级会锁表，那是一次性的。
- **达梦侧的结论是推的，不是量的。**

**后续约束**

- **新加一张带文本等值语义的表（或列）时，不需要做任何事**：`V8` 已经把表默认值
  也换成了 `as_cs`，新列自动继承。**但如果新表是"另一个库"**，就要照 `V8` 再来一遍。
- **不要再给 H2 加 `IGNORECASE`**：2.x 已不支持，加了不报错、只是**静默无效**
  （当次实测 `SELECT 'a' = 'A'` 仍为 `FALSE`）—— 比报错更坏。
- **断言"两个文本相等/不等"的用例，不要只在默认 profile 上跑**：
  本片这类事实**只有跨 profile 才验得出来**。新增这类断言时照 `TextEqualityApiTest` 的形状写。
- **别用 `utf8mb4_bin` 表达"二进制比较"**：它是 PAD SPACE，与 H2 差一格（见上表第 2 行）。

## 未覆盖

1. **达梦侧未实测。** `dameng/V8` 里那句话是推的。首次上真实达梦实例时，
   请把本篇的探针表在达梦上重跑一遍，并把结论回填到那份文件与本节。
   （`0010` 说达梦是交付脚本、Flyway 关闭，所以它不会被 CI 碰到 —— 只能人工上机。）
2. **`0038` 的另一个方向没有守卫**：本片证明了"跨 profile 语义"这件事**可以**被验，
   但**哪些事实需要跨 profile 验**仍然靠人想起来。目前只有本片这一处这么写。
3. **前端侧的相等语义没查**：`platform-admin` 的用户页会不会按邮箱/手机号做
   本地过滤（`includes` / `filter`）——JS 的 `===` 与 `includes` 本来就是大小写敏感的，
   与后端现在的语义一致，但那是一句**巧合**，没有人核过，也没有守卫。
4. **`40902` / `40903` 的并发漏网仍然存在**（`0062` 的"寻址类"权衡）。
   本片没有动它，只是把它的**前提**补上了。
5. **`username` 的 `@Pattern` 只允许 ASCII 字母数字**，所以本次没有触及
   "Unicode 等价"（如 `Ａ` 全角 与 `A`）那一类相等问题 —— 它在 DTO 层就被挡掉了，
   但那意味着**将来放开登录名字符集时**要重答一次本片的问题。
