# 0026. 日志与事件的鉴权与租户隔离：两条管道的查询接口此前完全公开

- **状态**：已采纳
- **日期**：2026-10-12
- **决策者**：舰长

## 背景

`0025` 收尾时留了一句「发现但未处理」：**另外两条管道（日志、事件）的可见性是否与审计一致**。
本次核查的结论比预期严重，且不是推测 —— 用真实请求验证过：

```
# 修复前，不带任何令牌
GET  /api/logs/client        → HTTP 200 · {"code":0,...}
GET  /api/events/client      → HTTP 200 · {"code":0,...}
GET  /api/audit/logs         → {"code":40100}      ← 审计一直是要鉴权的
GET  /api/auth/users         → {"code":40100}
```

再进一步：不带令牌 `POST /api/logs/client` 上报一条，**不带令牌就能把正文原样读回来**
（`message: "cross-tenant-probe"`、`ip`、`context` 全都在）。

### 为什么它会是这样

`AuthInterceptor` 的规则是**白名单反着写的**：方法或类上**没有** `@RequiresPermission`
就一律放行（见该类注释「未声明权限的接口 = 公开接口，直接放行」）。
审计域的 Controller 三个方法都标了 `auth:audit:read`；而日志域与事件域
**一个都没标** —— 不是"标错了"，是这两条管道建立时权限域还不存在（日志 V1、事件 V2，
权限域 V3），此后一直没人回头补。

`AuthTokenFilter` 只负责"有令牌就翻译成上下文"，**从不拒绝**无令牌的请求。
所以"没加注解"的后果就是彻底的公开，而不是"降级为匿名可读部分字段"。

### 与审计域缺陷的性质差异

`0025` 修的审计问题是"表里有 `tenant_id`、查询忘了带"；这一次更彻底：
`bw_client_log` / `bw_client_event` **连 `tenant_id` 这一列都没有**，
两个模块的代码里**一次都没出现过 tenant**。也就是说这两个域在设计上就没有归属维度。

同时它还带来一个不显眼的坑：`bw_client_event.user_id` 由**上报方**填写。
看到"有用户了"，顺手写"按 `user_id` 过滤"看起来是对的 ——
但那个值可以随便填，伪造一个别人的 `user_id` 就能读到别人的行为记录。

## 决策

### 一、上报公开、查询要鉴权 —— 这是分类，不是遗漏

**上报保持公开**（`POST /api/logs/client`、`POST /api/events/client` 不加注解），理由：

- 登录页出错时也必须能上报。未登录 → 无令牌 → 若要求鉴权，**最需要诊断的那批日志
  恰好发不出来**；
- 上报内容本来就整体不可信（正文、上下文、`userId` 全部客户端提供），
  加鉴权并不能让它变可信，只会把它变得"发不出来"。

**查询必须鉴权**（新增权限码 `log:client:read` / `event:client:read`，
四个日志查询入口 + 三个事件查询入口全部标注）。理由：
读日志/事件等于读到别人的报错正文、上下文对象、IP 与操作序列 ——
"能上报"绝不蕴含"能读回"。

代价明确写在这里：**上报的归属不可信**，因此归属绝不能取自上报体。

### 二、权限码新增两个域前缀，并登记在同一个地方

`log:client:read`、`event:client:read`（资源标识 `log:client` / `event:client`），
加进 `AuthPermissions.ALL`。

- `AuthPermissions` / `AuthResources` 是**全仓权限标识的唯一登记处**，不只是 `auth` 域 ——
  种子数据（`bw_auth_resource`）由 `ALL` 建出来，凡经过 `@RequiresPermission` 的接口
  都必须在这里登记，没有第二个地方可放。域前缀跟着**被访问的对象**走，不跟着模块走。
- **不与 `auth:audit:read` 合并**：三条管道三种读者（合规追责 / 排障 / 产品分析），
  合成一个码的后果是一次授权把三种数据一起给出去，事后收窄只能改后台配置。
- `AuthTaxonomyTest` 会强制"每个权限码都能归到某个已声明的资源下"，
  所以新域必须同时登记资源标识，否则该断言直接失败 —— 这正是它的用处。

### 三、归属只取服务端会话，不取上报体的任何字段

写入时 `AuthContextHolder.currentTenantId()`，未认证为 `null`；
读取时 `AuthContextHolder.require().getTenantId()`。

- 写入用 `currentTenantId()` 而**不是** `require()`：上报是公开接口，
  未登录必须照常入库；
- 读取用 `require()` 而**不是** `currentTenantId()`：查询接口都已声明注解，
  走到这里必然已认证；真出现未认证，说明有人绕过 Web 层直接调服务，
  那时候**抛错比返回全库数据正确**。

### 四、租户条件恒定加上，不做成可关的形式

`eq(列, 值)` 写死，不用 `eq(条件, 列, 值)`。可关的形式留的是
"调用方忘了传租户就查全量"的口子，而它的失败方式是**多看到数据** ——
不报错、结果还更完整，只有跨租户比对时才看得出来。
这与 `0025` 的 `visibility()` 是同一条规则。

### 五、聚合走的手写 SQL 也要带租户，参数**必传**

`ClientLogMapper#countByLevel` / `ClientEventMapper#countByEventName` 各加一个
`long tenantId` 并写进 `WHERE`，**不给默认值、不做可选**。
只改 wrapper 忘了它，症状是"总数对、分布图是全库的" ——
返回的只是一个计数，几乎不会被察觉。同 `AuditLogMapper#countByAction`。

### 六、详情跨租户返 `404` 而非 `403`，且"不存在"与"不是你的"同码

与 `0025` 一致：`403` 等于向调用方承认"这条记录存在，只是不给你看"，
而"这个 id 上有没有记录"本身就是不该跨租户泄漏的信息。
实现上先按主键查、再比对租户（而不是带租户条件去查），
这样"存在但不给你看"在**日志里**可区分，事后能回溯越权尝试。

### 七、`tenant_id` 可空，NULL 的语义是"不属于任何租户，因此对任何租户都不可见"

- 可空是必须的：未登录上报拿不到身份，写成 `NOT NULL` 会让登录前上报直接失败；
- **NULL 记录一律不可见**（列表、聚合、详情三处都是）。这是刻意的取舍：
  无法判断一条匿名日志属于哪个租户，把它展示给"当前租户"就等于把**别的租户**的
  匿名日志一并展示出去 —— 而登录页日志里可能带着用户输入的用户名。
  宁可不显示，不可错显示；
- **不回填历史数据**：库里从来没有记录过归属，任何回填值都是编造的，
  而编造的归属比查不到更危险。因此升级后历史日志全部查不到 ——
  日志是短保留期数据（默认时间窗 7 天），自然过期即可。
  若某个部署确实要保留，那是**部署决策**（把历史行归给哪个租户），
  用环境侧一次性脚本做，**不要写进版本迁移**：写进来之后所有环境的
  "未知归属"都会被同一句 `UPDATE` 变成同一个租户的数据。

### 八、前端：宿主已下发认证能力，子应用只是没取

`platform-log-console` / `platform-event-console` 构造 API 客户端时没有传
`accessTokenProvider`，属于**漏接**（基座在 `createMicroAppProps` 里恒带 `auth`，
见 `platform-portal/src/micro/loader.ts`）。因此前端只需接上，不需要新增任何认证实现。

新增 `common-api` 的 `createConsoleAuth()`：统一决定"从哪取令牌"——
被基座加载用宿主桥，独立运行用自建会话（DEV 下用开发账号自动登录，生产构建只记错误不登录）。
它放在 `common-api` 而不是 `common-tools`，是因为需要 `createAuthChannel`，
放进 `common-tools` 会形成 `common-tools → common-api → common-tools` 的环。

`allowDevAutoLogin` 由**调用方**传 `import.meta.env.DEV`，本包不自己读环境变量 ——
一个与框架无关的契约包里不该出现 Vite 的全局变量，
而且"生产构建绝不自动登录"这件事应当留在调用点、在评审时一眼可见。

## 后果

- 修复前：任何能访问该服务的人可读**全部租户**的日志与事件（已验证，非推测）。
  修复后：四个日志入口与三个事件入口一律要求对应读权限，且只返回本租户数据。
- 管理员权限项 21 → **23**（`AuthPermissions.ALL` 自动授予 SUPER_ADMIN，
  `scripts/verify-admin-permissions.mjs` 的断言已同步）。`auditor` 仍为 3 项，
  因此审计员**读不到**日志与事件 —— 与它对用户组一律 40301 是同一类决定：
  权限按读者划分，不按"都是只读"合并。
- 后端测试 149 → **157** 例：`ClientLogApiTest` 9 → 13（补"未认证查询 401""上报仍公开"
  "匿名记录不可见""跨租户隔离"）、`ClientLogServiceTest` 6 → 8、
  `ClientEventServiceTest` 6 → 8。
- **这套测试此前全是绿的**，而接口是公开的 —— 因为它们全都是不带令牌发的请求。
  因此新用例刻意保留两种发法：查询一律带令牌，上报一律不带，并各有反例。
- 契约不变（无新接口、无新模型）；`@Operation` 描述有更新，`openapi.json` 已重导。
- 前端两个控制台从"能读到数据但不需要登录"变为"需要令牌"；
  独立运行时由 `consoleAuth.ensureSession()` 先备好会话再渲染。

## 本决策未覆盖

1. **`data_scope` 仍未参与日志/事件的查询**：本切片只做租户隔离（同租户内可见即全部可见）。
   若要按角色范围收窄（例如"运维只能看自己部门的日志"），需要把 `0025` 的
   `DataScopeService` 接进这两个域 —— 但日志/事件里没有组织归属字段，
   落点仍不清楚。
2. **组织接口仍未做**（`0025` 的遗留项）：它是 `DEPT` / `DEPT_AND_CHILD` 精确求值的前置。
3. **`platform-admin` / `platform-audit-console` 各自那份 `src/auth/` 未动**：
   `web/README.md` 写的下沉触发条件是"出现第三个管理型子应用"，
   日志台与事件台正是第三、第四个消费方。本次让新消费方一律用
   `createConsoleAuth`，但**没有**回头改那两个应用 ——
   下沉会连带改动它们的既有测试与 `scripts/verify-audit-pipeline.mjs`，
   属于独立的一次重构。这是**已知的、有意的**技术债。
4. **登录前上报的数据等于"写入后不可读"**：它是本切片刻意的取舍（见决策七）。
   若将来确实需要看登录页的诊断数据，正解是在**上报协议**里带上应用/租户标识
   并对该标识做校验（而不是把 NULL 记录放给某个租户），那是协议变更。

## 发现但未处理

1. **`bw_client_event.user_id` 是客户端可伪造字段**，本次只在实体与建表脚本的注释里
   写明"不是归属依据"，没有做校验 —— 因为校验它需要与权限域的用户表比对，
   而事件上报是公开接口、允许匿名，逐条比对会把上报通道拖慢。它是**产品分析维度**，
   不是身份凭证，保持现状并写明即可。
2. **`content-type` 之外的限流缺失**：两条上报通道公开且可写，
   当前只靠单批 500 条的上限兜底。公网部署前应考虑按 IP/应用限流。
3. **日志的 `listByTraceId` 在超大链路上没有条数上限**：一个 traceId 下的记录数
   由客户端行为决定，当前直接 `selectList` 全量返回。
