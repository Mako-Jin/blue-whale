# 0056. 唯一编码列的六份答案 —— 两处此前没有答案，而兜底码让这个缺口不显形

> 起点是 `0055` 「未覆盖」的第 1 条（**其他业务码也按"支"核一遍**，点了
> `40912` / `40915` / `40916` / `40918` / `40919`）。领到之后先去核那句话本身，
> 结论是它的**前提错了**：那五个码每一个都只在**一个域、一处** `throw`，
> 根本不存在"支"可拆；`40920` 更极端 —— 全仓只有一处 `throw`，四个域共用同一个属主。
> 真正"同一个坑被抄了很多遍"的是**另一种形状**：`00xx` 的唯一编码判重。
> 顺着它数下去，摸到本片真正的题目 —— **六个唯一编码列，四份写下了答案、两份没有**；
> 而缺的那两份此前**看不见**：兜底码 `40900` 把"撞唯一键"从一次显性故障（500）
> 变成了一个看起来完全正常的业务拒绝。

## 背景

DDL 里有六个唯一编码列，六个 `uk_*` **一律不含 `deleted`**（三方言一致）：

| # | 列 |
| --- | --- |
| 1 | `bw_auth_resource.resource_code` |
| 2 | `bw_auth_role.(tenant_id, role_code)` |
| 3 | `bw_auth_user_group.(tenant_id, group_code)` |
| 4 | `bw_auth_organization.(tenant_id, org_code)` |
| 5 | `bw_auth_tenant.tenant_code` |
| 6 | `bw_auth_user.(tenant_id, username)` |

而不含 `deleted` 的索引意味着**软删的行仍然占着那个值**；同时 MyBatis-Plus 给每条
自动生成的查询都追加 `deleted = 0`，**常规判重看不见占位者**。于是这六个列各自
必须显式回答一次："软删行还算不算占着"。

前四个域答了，而且答的是"算 ⇒ **复活原行**"（`ResourceMapper` / `RoleMapper` /
`UserGroupMapper` / `OrganizationMapper` 各有一对 `selectAnyBy*` + `restoreDeletedById`）。
后两处**没有答**：判重走 `selectCount`（看不见软删行）⇒ 判重通过 ⇒ `insert` 撞键 ⇒
`DuplicateKeyException` ⇒ 被 `GlobalExceptionHandler` 翻成兜底的
`40900`「数据已存在或与已有记录冲突」。

## 一、先核那句话：被"多处用"的不是那五个码

`0055` 的未覆盖把 `40912` / `40915` / `40916` / `40918` / `40919` 说成"一个码被几个域用"。
数量一下：

| 码 | 主代码里的 `throw` | 分布在 |
| --- | --- | --- |
| `40912` `RESOURCE_CODE_EXISTS` | 1 处 | 资源域 |
| `40915` `RESOURCE_IN_USE` | 1 处 | 资源域 |
| `40916` `ROLE_IN_USE` | 1 处 | 角色域 |
| `40918` `USER_GROUP_IN_USE` | 1 处 | 用户组域 |
| `40917` `SYSTEM_ROLE_PROTECTED` | 3 处 | 角色域（删除 / 停用 / 降级三条路，同一个判据的三种入口） |
| `40919` `ORG_IN_USE` | 1 处 | 组织域 |
| `40920` `TENANT_DISABLED` | **1 处** | 租户域（四个域**共用同一个属主** `TenantService#assertAcceptsNewData`） |

**这五个码没有"支"可拆** —— 一个码一处 `throw`，"按支核"没有射程。
（`40002` 例外，它有 16 处，但那 16 处是**同一支**在不同引用对象上的重复：
每一处拦的都是"引用的东西不存在"，差别只在文案点名了谁。它值得的核对是
"16 处文案是否都点名了正确的对象"，不是按支 —— 记进「未覆盖」。）

**真正该按"抄本"核的是另一个形状**：同一个坑在每个域各抄一遍、而抄本之间会漂移的那种。
本仓现成的例子就是上面那六个列 —— 而它此前已经被数过，只是数错了。

## 二、注释里数到了"第四处"，实际有六处

四个 Mapper 的类注释都写了"这是同一个坑的第几处"：

- `ResourceMapper`：两处"唯一"（没编号）
- `RoleMapper`：与资源"同一个"
- `UserGroupMapper`：**"第三处"**
- `OrganizationMapper`：**"第四处（前三处：资源、角色、用户组）"**

而实际是六处 —— **少掉的两处正是没人发现的那两处**。这不是笔误，是"用散文维护一份
可变的清单"这条做法本身的症状：清单写在四个不同的文件里，每加一处要手改四处，
而且**漏掉的那些恰恰不会让任何东西变红**（第 5、6 处根本没有对应的注释可改）。

⇒ 修法沿用 `0054`：**清单搬进活文档**（`server/README.md`「唯一编码列与它们的软删语义」），
代码注释里改成指向它，并显式写一句"**不要在这里数第几处**"。散文里的数字会漂，
指针不会。

## 三、两处缺口是实测出来的，不是推断出来的

`0055` 立过一条规矩：**涉及"最终可观察行为"（状态码 / 响应体）的结论必须实测或有用例。**
所以本片先写用例、跑一遍**未改动的代码**，用量例的失败输出当读数：

```
UniqueCodeReuseApiTest.shouldRejectReusingSoftDeletedTenantCode:109
    JSON path "$.code" expected:<40904> but was:<40900>
UniqueCodeReuseApiTest.shouldRejectReusingSoftDeletedUsername:137
    JSON path "$.code" expected:<40901> but was:<40900>
Tests run: 4, Failures: 2, Errors: 0, Skipped: 0
```

两条反例同批通过（下面第五节）—— 也就是说这两处**只错了"软删那一支"**，
"活行占着"那一支一直是好的。

## 四、语义怎么定：复活还是拒绝

`0055` 把这块记成"**修它要先定语义**（复活 / 明确拒绝），与停用租户同类，故只记不修"。
本片认为语义定得下来，判据是一条**可以被检查的性质**：

> **复活是否安全，取决于那一行的删除守卫有没有挡住活边。**

前四个域都满足：它们在 `delete` 上拒绝了"仍被引用"——资源有子资源 `40913` / 已被角色引用
`40915`，角色有子角色 `40913` / 有成员 `40916` / 系统内置 `40917`，组织有下级 `40913` /
有成员 `40919`，用户组有子组 `40913` / 有成员 `40918`。**这些守卫合起来保证了一件事：
一条软删行必然是个没有活边的空壳**，把它放回来不会让任何人多出一样东西
（而且四个域在复活时还会主动清掉残留边，让"复活 = 空壳"无条件成立）。

后两处**不满足**：

- **租户**：`TenantService#delete` 只拒绝"仍有子租户"，**不拒绝"还有人"**。
  一个已删租户名下可以有活着的用户，而 `AuthService#login` 先按租户编码找租户、
  找不到就按"凭证错误"处理 —— 那些人的登录现在正因为租户被删而失败。
  **复活会把这些人一起放回来**：一次"用回同一个编码"的建租户操作静默地撤销了一次删除，
  而删除的人看不到这件事发生。
- **用户**：`UserService#delete` 只拒绝"删自己"，**不动这个人的角色成员关系、组织归属、
  用户组成员关系**。那些边在账号被删期间是惰性的（判定 JOIN 要求 `u.deleted = 0`），
  复活会**同时把它们激活** —— 一次"用回同一个登录名"的建号操作静默地把一批权限还给了那个人。

⇒ **这两处选"拒绝"**，复用既有的域内码（`40904` / `40901`），不新增码、不新增文案分支。

**为什么两支给同一个码**：调用方要做的事完全一样（换一个值）。这与
`40920` / `40002` 那种"处置完全不同才分码"不是一回事（那一对的分码理由是
"你等它启用"与"你传错了主键"两种不同的下一步）。也**刻意不**为软删那一支另写一句文案：
它既不可操作，又把"软删"这个内部状态透给了调用方。

## 五、本轮改了什么

| 落点 | 改动 |
| --- | --- |
| `TenantMapper` | 新增 `selectAnyByCode`（手写 SQL，绕过 `@TableLogic`）；**不加** `restoreDeletedById` —— 那个方法在这里没有被授权使用的调用点 |
| `UserMapper` | 新增 `selectAnyByTenantAndUsername`（同上；`tenant_id` 必须限定，索引就是复合列） |
| `TenantService#create` | 判重改走 `selectAnyByCode`；`create` 上写明"为什么这里不复活" |
| `UserService#create` | 判重改走 `selectAnyByTenantAndUsername`；`existsUsername` 随之删除（它做不到这件事） |
| `UniqueCodeReuseApiTest` | 新增 4 条用例 |

用例设计上沿用 `0055` 的两条约定，并各有用处：

- **文案断言必须能区分"落在哪一支"**：兜底那句"数据已存在或与已有记录冲突"**也含"已存在"**，
  所以断言的是文案里**点名了对象**（"租户编码" / "用户名"）—— 只断言"已存在"的话，
  两条支的断言长得一样，这条用例就分不出自己是靠哪一支过的。
- **要带反例**，而且刻意带**两条**：
  1. **没有唯一索引的列不许顺手一起挡** —— 租户名称（`tenant_name` 上没有索引）
     软删之后**必须**可以复用。少了这条，一个"看见任何软删行就拒绝"的实现照样通过；
     而那种实现是错的：索引不挡这些列，库里本来就不认为它们唯一，软删本来就该释放它们。
  2. **删掉之后换一个新值照常能建** —— 拒绝的是**那个值**，不是这个动作。

## 六、顺带订正的失真说法（与第三节同一根因）

`40900` 那个处理器（`ADR-0024`）上线之后，"漏掉这一步会被兜底成 **500**"这句话
在 7 处主代码注释 + 3 处用例注释/用例名里还留着，且都是**现在时**。逐处订正为
"落到兜底的 `40900`（`ADR-0024` 之前是 500）"。

其中一处不是措辞问题，而是**一个被推翻的前提**：

> `DuplicateKeyAdviceTest` 的类注释写着："本仓所有'先查后判重'的创建路径都
> 已经把撞键的可能性挡住了 …… **没有任何一个 HTTP 请求能稳定地触发这条异常**"，
> 而这正是它"直接调 Mapper 而不是走 HTTP"的理由。
>
> **这句话在它被写下的那一天是假的。** 租户编码与用户登录名那两处当时判重看不见软删行，
> 一个普通的"删掉一个租户、再用同一个编码建一个"请求就能把它稳定地撞出来
> （第三节实测的那两条）。修复之后它才成为事实，并改由 `UniqueCodeReuseApiTest` 看着
> —— **那里钉的不是"本处理器可达"，恰恰是"它不该可达"**。
>
> 同一句话在 `server/README.md` 的那一行里也写着，一并订正。

**这是同一种错的第四次**（`0053` 抄**代码相邻** → `0054` 抄**上一条已写下的结论** →
`0055` 抄**自己那条正确的证据链推出的后果** → 本片：**一句话从"当时为真"变成"现在为假"，
而没有任何东西会因此变红**）。前三次的教训是"别抄捷径、去核调用点"；这一次不同：
**核了也没用** —— 它当时是对的。 ⇒ 由此补一条：

> **凡是"全仓都……/所有路径都……"这种全称句，必须指出它由什么保证；
> 没有守护的全称句，就是一句会过期的话。**

本片没有给这句话加守护（理由见第七节），但把它从"陈述事实"改成了
"陈述事实 + 指出谁在保证 + 它曾经不成立"。

## 七、不做的事

- **不给那四个复活域各再写一条用例。** 它们各自的回归点早就在
  （`ResourceApiTest` / `RoleApiTest` / `UserGroupApiTest` / `OrganizationApiTest`
  各有一条"软删后同码重建、主键不变"），再抄一遍只会让"改一处要改两处"。
  本片的新文件里只写清六列的矩阵并指向它们。
- **不做"六列全矩阵"的机械守卫。** 它需要解析三方言 DDL 里的 `CREATE UNIQUE INDEX`
  再与"有没有软删感知的读"对照 —— 而只有"漏列"这**一半**可机械判定（漏了列会被发现，
  但列在而代码没写对判不出来），与 `0054` 未覆盖第 1 条同形，照同一条理由不加。
  （**但列数变了要记得回来改活文档那张表** —— 下面「未覆盖」第 3 条点了名。）
- **不新增错误码、不新增文案分支**（理由见第四节）。
- **不改用户域 email / phone 的判重**：那两列没有唯一索引（理由见第五节）。
- **不动 `0055` 的正文**：ADR 按 `docs/README.md` §三 不能被更新；
  那句错前提只在本片里订正，并且订正写进 `server/README.md`（活文档）与那张表的注释。

## 后果

**正面**

- 六个唯一编码列第一次有了**一处**权威清单（活文档里的表），而不是散在四个 Mapper 注释里
  的一份会漂的计数。
- 租户编码与用户登录名的失败文案从兜底句恢复到域内码（`40904` / `40901`），
  并且**实测**确认（不是 500，也不是"回显库结构"）。
- 兜底码 `40900` 的那句"应用层没挡住"——即 `DuplicateKeyAdviceTest` 的前提——
  第一次真的成立，且由用例看着。
- 十处"会被兜底成 500"的失真说法被订正，其中一处是**被推翻的前提**，不是措辞。

**负面 / 代价**

- 让"删掉再用同名建回来"变得**不可能**（两个域）。这是决策的代价，不是缺陷：
  另一条路（复活）在这两个域会把访问权静默还回去。真正的解法是"先恢复那个已删对象
  （现在没有这个入口），或者换一个编码"，而不是让一次新建顺手完成一次撤销。
- 两个域**没有** `restoreDeletedById`：语义上的不整齐是刻意的，注释里写清了原因，
  免得后来者照另外四处的形状补一个不该有的方法。

**后续约束**

- **新增一张带 `deleted` 的表、或给现有表加唯一索引时，必须同时回答"软删行还算不算占着"**，
  并把它登记进 `server/README.md` 那张表。三张关系表的唯一索引是已经写在
  「未做」清单里的待办（`bw_auth_rel_role_member` / `rel_role_resource` / `rel_org_user`）——
  加索引会**新增**这样的列，别只加索引不回答。
- **代码注释里不要再数"第几处"**：清单在活文档。
- **凡"全仓都……/所有路径都……"的全称句，要指出它的保证者**（见第六节）。

## 未覆盖

1. **`40002` 的 16 处文案核对**：每一处是否点名了正确的引用对象、是否都有断言。
   它与本片同源（都是"同一个判据在多个地方各写一遍"），但形状不同（同一支、不同对象），
   本片只把它记下来。
2. **六列矩阵的机械守卫值不值**（见第七节）—— 只有"漏列"这一半可判定。
3. **加索引时会不会重犯**：三张关系表一旦加上唯一索引，就多了三个这样的列
   （见「后续约束」第一条）。这是本片最可能被"顺手"破坏的地方。
4. **`*_name` / email / phone 该不该有唯一索引**：现在它们靠服务层判重、库里不唯一，
   于是"软删即可复用"是行为的一部分。要不要收紧是产品决定，不是本片能定的。
5. **用户域 email / phone 的判重仍看不见软删行**（**故意的**，理由见第五节），
   但它与登录名的形状在代码上只差一行 —— 后来者容易"顺手统一"，故在此点名。
