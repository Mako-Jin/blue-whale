# 0079. 按主键写的租户条件：那一格的正当性此前只写在注释里

- **状态**：已采纳
- **日期**：2026-10-16
- **决策者**：舰长

## 背景

`0078`「未覆盖 1」挂着一条，原文是：

> **`@Update … WHERE id = #{id}` 这类"按主键改"的注解 SQL 完全没有租户条件**
> （`rel_*` 四个 Mapper 各一处）。它是规则 A / D 在**写侧**的镜像，而本片的射程
> 是"条件的取值来源"（那里没有租户值）。今天的答案是"安全的，但是一次手工核对"……
> **要机器守它，判据得是"按主键改的出口必须能追到一次租户范围内的选取"** ——
> 那要调用图，且"追不到"与"追到了但人看漏了"不容易分开，留给下一片。

本片领它。但**先把那句话里的计数订正了**。

### 订正：不是"`rel_*` 四个 Mapper 各一处"，是 8 处

`0078` 写那句时是顺手带过（它只在侦察 `E1` / `E2` 两种形状的路上撞见这族 SQL），
计数没有逐个数。本轮全仓普查 `@Update` / `@Delete` 里的注解写语句，实测是 **8 处**：

| 类 | 写法 |
| --- | --- |
| `organization/OrganizationMapper` | `@Update("UPDATE bw_auth_organization SET deleted = 0 WHERE id = #{id}")` |
| `role/RoleMapper` | `UPDATE bw_auth_role …` |
| `usergroup/UserGroupMapper` | `UPDATE bw_auth_user_group …` |
| `relation/RelOrgUserMapper` | `UPDATE bw_auth_rel_org_user …` |
| `relation/RelRoleMemberMapper` | `UPDATE bw_auth_rel_role_member …` |
| `relation/RelRoleResourceMapper` | `UPDATE bw_auth_rel_role_resource …` |
| `relation/RelUserGroupMemberMapper` | `UPDATE bw_auth_rel_user_group_member …` |
| `resource/ResourceMapper` | `UPDATE bw_auth_resource …` |

`0078` 漏掉的正是**四个域 Mapper**（组织 / 角色 / 用户组 + 资源）—— 它们与四个 `rel_*`
**共用同一个方法名 `restoreDeletedById`**，所以只按"看到 `rel_` 前缀"数，就会把
"四个域各一处"整批漏掉。**这是本片的第一个发现：按名字数会漏，按方法名数会漏，
只有按"SQL 文本 + 表名"数才不漏。**

### 8 处里有一处不该带租户条件

8 张表里 **7 张的 `tenant_id` 是 `NOT NULL`**（`bw_auth_organization` / `bw_auth_role` /
`bw_auth_user_group` / `bw_auth_rel_org_user` / `bw_auth_rel_role_member` /
`bw_auth_rel_role_resource` / `bw_auth_rel_user_group_member`），而
**`bw_auth_resource.tenant_id` 可空** —— 可空在这里不是"忘了约束"，它有确切含义：
**`NULL` = 平台级资源，对所有人可见**（`0074`；与 `0076` 排除 `bw_auth_resource`
是同一套推导）。

给定平台级资源补一个 `tenant_id = #{tenantId}`，**不是"更安全"，是改错语义** ——
它会把平台级资源整类排除在复活之外。所以这一处必须**推导排除**，而不是进白名单。

### 这一格的正当性此前只写在注释里

改前 7 处的 `javadoc` 都是同一句话的变体：

> 这个方法的代价（绕过逻辑删除保护）在调用点上被约束住：只在 `RoleService.create` 里、
> 且已确认该编码确实被一条逻辑删除的角色占着时调用。

**这句话是对的，而它不是一个约束。** 注释不被编译期检查、不参与任何 CI、也没有任何东西
会在有人**新加一个调用点**时亮起来；一旦有人在别处传一个不属于当前租户的 `id` 进来，
`WHERE id = #{id}` 照样命中，静默改掉别家那行。**这就是本片要守的那一格。**

`restoreDeletedById` 是**绕过 `@TableLogic` 的手写 SQL**：MyBatis-Plus 自己生成的 `updateById`
会带上 `deleted = 0`（于是对已删除的行影响 0 行），所以"复活"只能手写；而**手写就绕过了
`requireXxx` 那条链** —— 那条链上唯一的租户保证是 `assertVisible`（`0074`）。这是
规则 A / D 在**写侧**的镜像。

## 决策

### 1. 判据两条一起：`WHERE` 里有 `tenant_id = #{…}`，且那个名字是形参里有的 `@Param`

```text
射程内的一条注解写语句
  ├─ 表名从 SQL 文本的字面量读（UPDATE <表> SET）
  ├─ 可空性从建表脚本读 ⇒ tenant_id 可空 / 无此列 ⇒ 自动出局
  └─ 剩下两条一起判：
       ① WHERE 里出现 tenant_id = #{<名字>}
       ② 那个 <名字> 在本方法的形参表里有 @Param
```

**为什么少了第二条不行**：`@Update` 的注解 SQL 与 Java 形参是靠名字连接的，编译期一点
检查都没有。一处"SQL 改对了、形参改掉了"的改动（比如把 `@Param("tenantId")` 写成了
`@Param("tid")` 而 SQL 里还写着 `#{tenantId}`）**要到运行时才炸**（`BindingException`），
而那时它已经在别人的机器上跑。少了第二条，这个形状就是半个。

### 2. 射程由表的可空性推导，零白名单

`bw_auth_resource` 必须**被排除**，而且这条"被排除"要**被断言** —— 否则明天有人给它
顺手补个条件（看起来像加固），守卫会全绿，平台级资源整类复活不了。
所以另有一条自检专门确认它**在排除集里**（不是"没人提它"，是"它被推导出局"）。

这与规则 A 排除它同一套推导：**"这张表没有'租户内的行'这个前提"**，是表结构的性质，
不是某个人记得的事。

### 3. 刻意放弃 `0078` 建议的那条更严的判据

`0078` 建议的判据是"**按主键改的出口必须能追到一次租户范围内的选取**"。本片**不做**，
理由不是它不好，是它的**收益为零而代价明确**：

- 本仓 7 处调用点的租户**全在作用域内**：`tenantId`（落点返回值）·
  `org.getTenantId()` / `role.getTenantId()` / `group.getTenantId()`（实体自身）。
  追调用图能把每一处都追通，但**追通不等于"以后有人加了新调用点会被拦住"** ——
  拦住新调用点靠的是"调用点必须传一个租户"，而那件事**由形参强制**（决策 1 第②条）。
- "追不到"与"追到了但人看漏了"不容易分开（`0078` 的原话），这正是 `0064` 说的
  "会误报的守卫比没有更糟"的风险面。
- 换成"注解 SQL 自己带租户条件"以后，**判据只读 SQL 文本 + DDL，零前置、零调用图** ——
  它不依赖今天调用点长什么样，所以**新调用点、新方法、新域全都自动在射程内**。

一句话：**把"越权被调用点约束住"从注释里搬进 SQL 里**，比在调用图上做可达性分析
更短、更硬、更少例外。

### 4. 并进 `verify-tenant-visibility.mjs` 当规则 F，不另起脚本

`0078` 另起了一支脚本（`verify-tenant-scope-source.mjs`），因为那支问的是"条件的取值
从哪来"，与本支的模块推导射程、DDL 解析机制都不同。本片相反：**规则 F 与规则 A 是
同一个模型的镜像**（一个问"读侧按主键取实体过没过判定"、一个问"写侧按主键改的语句
自己带没带租户条件"），射程的推导方式、DDL 的读法、排除集的判据全都复用 ——
所以它是 `verify-tenant-visibility.mjs` 的**第六条规则**，不是第七支脚本。

四条守卫的分工一句话：
**规则 C 管"比较"、规则 D 管"按主键取实体"、规则 E 管"条件的取值来源"、
规则 F 管"写侧那条语句自己带没带租户条件"。**

### 5. 刻意不做

- **不改 `bw_auth_resource` 那一条**：它的 `tenant_id` 可空（见背景），加条件是改错语义。
- **不给 MyBatis-Plus 自动生成的写语句加射程**（`updateById` / `removeById` 等）：
  它们**不绕过** `@TableLogic`，租户保证在规则 A（"先 `requireXxx` 再改"）而不是规则 F。
  规则 F 只认**手写的**那几条 —— 手写才绕过。
- **不查 `@Insert`**：插入没有"按主键改"这回事，归属由写侧落点 `resolveWriteTenant` 管
  （`0074`），是另一问。
- **不查 `@Select`**：读侧的出口由规则 D 与规则 E 管，本片不重复。
- **不追调用图**（决策 3）。

## 实测

### 出红的那半步：只加形参、SQL 不动

先在 `RoleApiTest` 写新用例，**只把形参加上、SQL 里的 `WHERE` 保持原样**（一个真实的
"改了签名忘了改语句"的样子），用例红得精确：

```text
expected: <0> but was: <1>
  「别家租户的 id 不该匹配到任何行」
```

同时**既有 13 条用例全绿** —— 证明红的只是新钉的那一条，不是环境或夹具坏了。
补上 `AND tenant_id = #{tenantId}` 后转绿，日志里两行把方向钉死：

```text
id=13, tenant=2 ⇒ Updates: 0      # 别家（真实存在的另一个租户）的主键命中 0 行
id=13, tenant=1 ⇒ Updates: 1      # 本租户的主键照常复活
```

### 为什么这条用例只能直接经 Mapper 问

这条 SQL 的越权路径**没有 HTTP 入口** —— 唯一的调用者 `RoleService#create` 先经
`selectAnyByTenantAndCode(tenantId, code)` 取到那一行，`id` 从构造上就属于本租户。
所以**接口层面永远是绿的**，"SQL 层面挡不挡得住"只有绕过服务层才问得出来。
用例 javadoc 里写明了这一点，也写明"**两个方向都要断**"：只断"别家复活不了"，
一个"谁都别复活"的实现（条件恒假）也能通过 —— 而它会静默废掉"软删后复用编码"
这条已落地的能力。

### 五轮扰动：三条能精确红、两个反例都不红

| 轮 | 扰动 | 结果 |
| --- | --- | --- |
| 1 | 撤回 `RoleMapper` 的 `AND tenant_id = …` | 守卫**红**（指名 `RoleMapper.java:66:5`）**且**用例红 —— 代码 + 守卫双证据 |
| 2 | 撤回 `UserGroupMapper` 的条件 | 守卫**红**（指名 `UserGroupMapper.java:58:5`）、**用例全绿** |
| 3 | SQL 写 `#{tid}` 而形参仍叫 `tenantId` | 守卫**红**，指名"形参表里**没有**对应的 `@Param`"（判据②在工作） |
| 4a | **反例**：注解改成文本块 `"""` + 换行 + 小写 `update` | **全绿** —— 等价重构不误报 |
| 4b | **反例**：方法改名 `reviveById` + 调用点同改 | **全绿** —— 判据不读方法名（`0076` 判据） |

轮 1 与轮 2 是一对：**用例只覆盖 `RoleMapper` 一处，守卫覆盖全部 7 处** ——
轮 2 里"守卫红而用例绿"恰好证明**用例射程 ≠ 守卫射程**，两处各守一半；
若只有用例，`UserGroupMapper` 那处撤掉条件没有任何东西会响。
轮 4a / 4b 是 `0072` 规则 6 的另一半（**等价重构不许红**）：判据落在"这条 SQL 改的是
哪张表、带没带租户条件"上，而不是把今天 7 行文本抄成模式。

### 全量回归与全套自检

`mvn -o -T 1C test` 全模块 **BUILD SUCCESS**，**52 个测试类 / 328 条 / 0 失败 0 跳过**

## 后果

### 正面

- **`restoreDeletedById` 那一格的正当性从注释搬进了 SQL。** 从今往后，调用点唯一的义务是
  **把租户传对**，而这件事**由形参强制**（编译不过就传不下去）；"语句自己带没带条件"
  由规则 F 守。**新调用点、新方法、新域全自动在射程内** —— 不需要谁记得去更新一个名单。
- **规则 F 与规则 A 是同一个模型的两侧。** 读侧问"取到的实体过没过 `assertVisible`"、
  写侧问"改它的语句自己带没带租户条件"；两问共用 DDL 与推导，所以不会出现
  "守住了读写一侧、漏了另一侧"。
- **一条自检专门钉住"平台级资源必须被排除"**：`bw_auth_resource` 一旦被顺手"加固"，
  守卫会红在自检上，而不是静默把平台级资源整类挡掉。

### 负面代价

- **本片动了生产代码，且有行为变化**：7 处 `restoreDeletedById` 现在**必须**传租户，
  跨租户的主键从"能改"变成"影响 0 行"。本仓 7 处调用点全部传的是作用域内的租户，
  所以**正常路径零影响**；但这是一次**有意的行为收紧**，不是纯守卫片。
- **形参从一个变两个**：任何一个**新**调用点（本仓暂未出现）必须自己把租户传进去；
  忘了传会**编译不过**（这是特性 —— 失败方向朝"编译期"而不是运行时）。
- **规则 F 的射程是"全仓的注解写语句"**：`@Update` / `@Delete` 的 SQL 里只要出现
  `UPDATE <表> SET` 就会被读表名。将来若有人写出解析不出表名的写法，脚本会 **红在
  `writeUnresolved`**（防假阴）——那是**多报**方向，可接受，但要按提示补解析或补注释。

### 后续约束

- **新增一处"绕过 `@TableLogic` 的手写写语句"，就必须自己带租户条件**（表带
  `tenant_id NOT NULL` 的那些）。判据是"改的是不是带 `tenant_id NOT NULL` 的表"，
  不是方法名。
- **`bw_auth_resource`（和任何 `tenant_id` 可空的表）的复活语句刻意不带条件** ——
  这是平台级资源的语义，不是遗漏。改它之前先读 `0074`。
- **给 `restoreDeletedById` 加调用点，形参必须填对租户**（落点 / 实体自身）；
  编译器会挡住"忘了传"，不会挡住"传了别家的" —— 后者是规则 F 与用例管的事。

## 未覆盖

1. **`@Update` / `@Delete` 之外的"按非主键改"的注解 SQL**：本仓 `@Update` 全是
   `restoreDeletedById` 族，没有"按 `code` 改"这类。将来出现时规则 F 照样管
   （它判的是"带没带租户条件"，不关心主键不主键）—— 但**射程说明**目前写的是
   "按主键写的"，措辞可能要跟着改。
2. **MyBatis-Plus 自动生成的写语句**：`updateById` / `removeById` 等不在规则 F 射程
   （不绕过 `@TableLogic`），租户保证在规则 A。**两条规则之间的分界是"手写 vs 生成"**，
   不在本片机器化的范围内。
3. **`@Insert` 的归属**：由写侧落点 `resolveWriteTenant` 管（`0074`），本片没碰。
4. **达梦未实测**（全仓同一条，`0073` 未覆盖 1）。规则 F 只读源码文本与建表脚本，
   与方言无关。
5. **"传了别家的租户"这一类的运行时覆盖**：本片只给 `RoleMapper` 一处写了用例
   （用户组那处由扰动轮 2 验证了守卫会红）。其余 5 处没有各自的用例 —— 它们是**同一份
   形状**，用例的边际收益低；若将来某处调用点的租户来源变得不那么直接，再补。
6. **`0078` 未覆盖 3（`SFunction` 先存局部变量再传）**、`0078` 未覆盖 4~6、
   `0077` 未覆盖 1 / 3~8、`0076` / `0075` 等仍挂着，本片没有推进（清单见各篇）。
