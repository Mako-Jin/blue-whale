# 0077. 三条记录管道的读侧：一句从没说出口的口径，和它该住的那一格

- **状态**：已采纳
- **日期**：2026-10-16
- **决策者**：舰长

## 背景

`0074`「未覆盖」里挂着一条，本片把它领了：

> **审计域之外的三条管道**（`bw_client_log` / `bw_client_event`）的可见性
> 仍按"租户强制等于登录者"（`0025` 未覆盖），本片没有改它们的语义；

`0025`「本决策未覆盖」里也有同一条的另一半：

> **另外两条管道的可见性**：`bw_client_log` / `bw_client_event` 同样只有租户维度，
> 同样没有按数据范围过滤。它们的可见性规则要不要与审计一致，没有讨论。

所以这一轮的射程是一句话：**审计 / 日志 / 事件三条记录管道的读侧，要不要接 `0074`
刚立起来的"平台级"口径？**（`0076` 也把它记成「未覆盖 4」。）

### 侦察：三条管道 × 六个维度

| 维度 | 审计 `bw_audit_log` | 日志 `bw_client_log` | 事件 `bw_client_event` |
| --- | --- | --- | --- |
| `tenant_id` 可空 | 可空（三方言一致） | 可空（`V6` 加列） | 可空（`V7` 加列，与 `V6` 同形） |
| 租户从哪来 | `AuthContextHolder.require()` → 私有 `record Visibility(tenantId, currentUserId, selfOnly)` | 私有 `visibleTenantId()` | **与日志域逐字相同的**一份 `visibleTenantId()` |
| 过滤形态 | `.eq(Entity::getTenantId, tenantId)` **无条件** | 同 | 同 |
| 详情判定 | `Objects.equals(entity.getTenantId(), v.tenantId())` | `entity.getTenantId() == null \|\| .longValue() != tenantId` | **与日志域逐字相同** |
| 平台级出口 | 无 | 无 | 无 |
| 查询入参里有 `tenantId` 吗 | **没有** | **没有** | **没有** |

这张表里有两条发现是这一轮的支点。

**一、口径早就被钉住了，只是没人说出口。** 三条管道里，审计与日志各有一条隔离用例
（`AuditApiTest#shouldIsolateAuditLogsAcrossTenants`、
`ClientLogApiTest#shouldIsolateAcrossTenants`），它们**用的都是种子租户的管理员** ——
而种子租户是顶级租户（`tenantLevel = 1` / `codePath = "/"`），所以按
`TenantService#currentOperatorIsPlatform()` 的判据，**那两条用例的操作者一直是平台级**。
它们一直在断言"平台级也读不到"，只是从来没人在用例名、注释或文档里点破过。
而 `0074` 后来又给别的读路径开了平台级例外，于是"记录管道要不要照做"变成了一个
**没有任何东西在守、也没人回答过**的问题。

**二、事件域没有任何 API 级见证。** `0026` 给日志与事件两条管道都补了鉴权与租户隔离，
但只有日志域留下了用例（`ClientLogApiTest` 有 14 条）。事件域的 HTTP 面**一条都没有** ——
"它的隔离与日志域一模一样"这件事，一直只是"代码看起来一样"。

### 三个 `NULL`，两个相反的含义

| 表 | `tenant_id IS NULL` 的含义 | 读者 |
| --- | --- | --- |
| `bw_auth_resource` | **平台级对象**（所有租户共享的资源目录） | 所有人（`assertVisible` 遇到 `null` 直接通过） |
| `bw_audit_log` / `bw_client_log` / `bw_client_event` | **不属于任何租户**（未登录时产生的记录；见 `V6__add_tenant_id_to_bw_client_log.sql` 的列注释） | **没有人** |

这一条决定了本轮的形状：**三管道不能简单地把租户判定换成 `assertVisible`**。
接上去等于把未登录时产生的日志与审计行从"谁都看不见"翻成"平台级看得见" —— 那是一次真的泄漏。
两个 `null` 是两件事，所以是两个落点。

## 决策

### 1. "读侧可见租户"收成一格，落在 `TenantService`

三份私有实现（日志与事件那两份逐字相同）删除，`TenantService` 新增
`currentReadTenant()`。理由与 `0074` 删掉四个私有 `resolveTenantId` 是同一条：
**同一句话写得越散，改的时候越可能只改一半** —— 而半开的门（列表挡住了、详情没挡住）
看起来与关着的一样。这句话不是我加的，它原本就写在 `AuditLogService#visibility()` 的注释里，
理由却只用在一个类内部。

字段名也是判据的一部分：**`currentReadTenant()` 不接受任何参数**。

### 2. 不接平台级口径 —— 理由两条，都不在新片里

**(a) 接口形状里没有"点名租户"这一格，所以接不上。** `0074` 的读侧模型不是
"平台级看得见全部"，而是「**默认落在自己租户，只有显式点名才跨租户**」——
看 `resolveQueryTenant` 的正文：`requested == null` 时**对所有人都返回自己租户**，
平台级也只在自己点名时才越界。三个域的查询入参里从来没有 `tenantId`
（`AuditLogQuery` / `ClientLogQuery` / `ClientEventQuery` 都核过），
于是"平台级 + 记录管道"在形状上就没有可传的第二个值。
要开这个口子必须先给三个接口长出那一格 —— 那是**一次契约变化 + 产品决定**
（`0074` 未覆盖 1「平台级管理台的产品形态」，本片不答）。

**(b) 记录管道里不存在"合法的跨租户读者"。** `0074` 给平台级开例外的正当理由写在
`assertReferencedInSameTenant` 的注释里：**跨租户预配就是他的工作** ——
也就是说，那条例外是**写侧能力的投影**（`requireVisibleTenant` 的注释明写"详情 / 修改 / 删除
共用的取用"：看得见才改得动）。而三条管道的共同点恰恰是**没有写侧** ——
`AuditLogService` 的类注释第一句就是"**只有读方法，一个写方法都没有 —— 这是刻意的，
也是本域与另两条管道最根本的差别**"。一个只被观测的对象，没有"管理"这一面，
例外就失去了它所服务的那件事。

⇒ **分界是"管理面 vs 观测面"**：管理面的平台级例外服务于"他要不要对这个对象采取写动作"
（要 ⇒ 必须看得见），观测面没有这个动作。所以同一句"平台级"，在两处导向不同的结论，
而这两处并不矛盾 —— 它们回答的问题不同。

**这仍是一次"刻意不接"，不是"永久拒绝"**：复启条件写在「未覆盖 1」里。

### 3. 新落点的形状：`assertRecordInCurrentTenant(Long, String)`

- **`null` 恒不可见**（而不是恒可见）：与 `assertVisible` 唯一但决定性的一处差别；
- **没有平台级分支、没有读者分化**：`assertVisible` 对平台级放行、
  `assertReferencedInSameTenant` 按读者换文案，这一格两者都没有 ——
  因为它的读者里不存在合法的跨租户读者，所以两件事（"真的没有"与"不是你的"）
  对所有人都是同一句话（`0059` 第二节 / `0075`）；
- **抛公共码** `ResultCode.NOT_FOUND` 而不是 `AuthResultCode`：三个域本来就没有自己的枚举。
  这一点同时是守卫认出它的方式（见决策 5 的规则 D）——**改这个码会连带改掉射程**，
  所以我在源码注释里也写了这句。

### 4. 三处判定全部改走落点；查询路径的租户也只从落点取

`AuditLogService`（`Visibility` 里的租户 + `detail` 的租户那一半）、
`ClientLogService`（`page` / `detail` / `listByTraceId` / `stats`）、
`ClientEventService`（`page` / `detail` / `stats`）全部改掉。
`AuditLogService#Visibility` **保留** —— 它有 `currentUserId` / `selfOnly` 两格，
数据范围是审计特有的第二个维度，与租户那一维不是一回事。
每个域那句"不存在"提成常量，因为现在它有**两个**去处（"真的查不到"与"不属于你的租户"），
而两支必须逐字相同。

### 5. 守卫跟着扩：新增规则 D，规则 C 扩射程与形状

| # | 规则 | 怎么认 |
| --- | --- | --- |
| **D（新）** | 抛出**公共** `40400` 的方法（含调用同文件里那个构造器的）若按主键取实体 ⇒ 必须走记录管道的落点 | 这是规则 A 在三条记录管道上的**镜像**：它们没有自己的码，所以规则 A 从头到尾看不见它们 |
| C（放宽射程） | "接上了租户服务的模块"里不得手搓租户比较 | 判据从"出现过那两个落点名"改成"**模块里有 `TenantService` 类型的字段/参数并真的调了它**" —— 放宽之后三条管道才进得了射程 |
| C（扩形状） | 增加 `getTenantId().longValue() != x` 与 `x.getTenantId() == y` 两种 | 那正是三管道在本片之前的**原文写法**；**另一侧是 `null` 字面量的那一种被排除**（那是判空，不是"同一个租户吗"） |

**落点不写名字**：规则 D 找的是 `TenantService` 里"**方法体提到公共 `ResultCode.NOT_FOUND`**"
的那一个方法；解析不出来就红（否则规则 D 会退化成一条永远为真的空断言）。
这条自检与 `0076` 的"映射链完整"同源：**解析不出来必须红**。

### 6. 把口径说出口

- 三条管道的隔离用例现在**先证明操作者是平台级**（`GET /api/auth/tenants/{id}` 的
  `parentId` 为空），再断言"平台级也读不到"。没有这一步，那几条用例在操作者其实不是
  平台级时会照常全绿，而它们想守的那件事一刻都没被验证过；
- 事件域补齐 API 见证：新建 `ClientEventApiTest`（鉴权 / 匿名不可见 / 跨租户隔离 / 404）。

### 7. 刻意不做

- **不给三个接口加 `tenantId` 查询参数**（决策 2(a)）；
- **不把三管道接进 `DataScope`**（`0025` 未覆盖的另一半：日志与事件"没有按数据范围过滤"）——
  那是**另一个维度**（租户内再看多大范围），与本轮的"租户之间"正交。审计域有它是因为
  审计行**有操作人**这个维度；日志与事件的"人"是客户端可伪造的 `userId`，
  拿它做数据范围等于把越权判据交给上报方；
- **不合并 `assertVisible` 与 `assertRecordInCurrentTenant`**（决策 3）：两个 `null` 相反；
- **不动 `bw_auth_resource` 的 `requireResource`**：它的 `null` 是"平台级对象"，
  `assertVisible` 对它是空操作，这是 `0076` 已经从 DDL 推导出来的结论。

## 实测

### 侦察矩阵

182 个源文件 / 16 张实体表 / 3 条方言。守卫的射程从"7 处（auth 域）+ 排除 2 处"变成
"7 处 + 排除 2 处 + **记录管道出口 3 处**"，落点从声明里读出：

```text
  接上了租户服务的模块（规则 C 的射程）：sts-server-audit · sts-server-auth · sts-server-log · sts-server-track
  记录管道的落点（规则 D，从声明里读出）：assertRecordInCurrentTenant
✓ 记录管道的读侧出口都过了那一格落点
    3 处：AuditLogService#detail · ClientLogService#detail · ClientEventService#detail
```

### 七轮扰动：每一轮都精确红，反例不红

| 轮 | 扰动 | 结果 |
| --- | --- | --- |
| 1 | 落点加**平台级例外** | **3 条 API 用例红**（三域各一条隔离用例），失败点都是 `$.code expected:<40400> but was:<0>` —— 真的读到了别家记录 |
| 2 | 落点把 **`null` 当通过** | **2 条红**（日志 / 事件的"匿名行详情"），跨租户用例与整个审计域**全绿** |
| 3 | 审计 `detail` 恢复手搓 `Objects.equals`（**保留**落点调用） | **只红规则 C**（`AuditLogService.java:106:22`） |
| 4 | 去掉落点调用，改成**先取局部变量**再比 | **只红规则 D** —— 规则 C 看不见"先取局部变量再比"，而这正是脚本头「刻意不查的」登记过的那条限制 |
| 5 | 落点改抛权限域的码 | **守卫自检红并退出**："在租户服务里找不到'抛公共 40400'的那个方法" —— 规则 D 没有退化成空断言 |
| 6 | **反例**：加一句 `entity.getTenantId() == null` 判空 | **全绿**（退出码 0）—— 判空不是"比较两个租户"，不误报（`0064`） |
| 7 | 日志 `detail` 恢复成 **0077 之前的原文** `!=` 写法 | **只红规则 C 形状三**（`ClientLogService.java:203:53`）—— `0072` 规则 6 的判据：**能把改动前的写法打红** |

轮 1 与轮 2 刻意**成对**：一轮拆的是"平台级放行"，一轮拆的是"`null` 放行" ——
它们正是决策 2 与决策 3 各自的那句话，而两条的失败面完全不同（前者只打在跨租户用例上，
后者只打在匿名用例上）。这比"改一处红一片"更能说明两句话是两件事。
轮 6 是**反例**：一条守卫的价值有一半在"它不乱报"，所以反例与正例一样要做。

### 全量回归与全套自检

`mvn -o -T 1C test` 全模块 BUILD SUCCESS，**52 个测试类 / 327 条 / 0 失败 0 跳过**
（`0076` 是 51 类 / 322 条；本片 +1 类 / +5 条，其中 `ClientEventApiTest` 是新类，

## 后果

### 正面

- **一句从没人说出口的口径，现在住在签名里。** `currentReadTenant()` 没有参数、
  `assertRecordInCurrentTenant` 没有平台级分支 —— "平台级也读不到别家的记录"不再是
  三个域各自的实现细节，而是"要改也只能改这一处、且改不动接口形状就做不到"。
- **三份手搓变一格**，与 `0074` 收掉四个私有 `resolveTenantId` 是同一条。
- **守卫第一次能够进三条记录管道**。它们此前完全在规则 A 的射程之外（没有自己的 `404xx`），
  而"平台级也读不到"只由两条从没自述过身份的用例守着。
- **事件域有了 API 级见证**（此前 0 条），"它与日志域一样"第一次有了会被红掉的东西。
- `bw_auth_resource` 的 `null` 与三管道的 `null` 的区别，从"注释里的一句话"变成
  **两个签名上看得见的落点**。

### 负面代价

- **`AuditLogService` 多了一个构造依赖**，两个 `ClientXxxServiceTest` 也要跟着加 `@Mock`。
- **`detail` 里多了一次 ThreadLocal 读**（落点自己再取一次租户）。代价可忽略，
  但它是真实的：`AuditLogService#detail` 里现在有"取上下文"与"取租户"两步。
- **规则 C 的射程被放宽了**（"用过租户服务" > "用过那两个落点"）。今天它只多圈进两个模块，
  但语义上确实更宽 —— 放宽的理由写在脚本头，如果哪天出现一个"用租户服务、却该手搓比较"的
  正当例外，那就是 `0064` 又一次适用（**会误报的守卫比没有更糟**）。
- **规则 D 认落点的方式是"方法体里提到公共 `40400`"**。这是从声明推导（不写名字），
  但它把"落点抛哪个码"与"守卫认不认得它"绑在了一起：将来若有人把这个落点改成抛
  `AuthResultCode`，红的是守卫自检而不是用例 —— 这**是有意的**（宁可响得莫名其妙，也不要静默）。

### 后续约束

- **三管道的读侧口径只有一处可改**：`TenantService#currentReadTenant()`。
  想给它们开跨租户读，先改接口形状（决策 2(a)），再改这一格。
- **记录管道不允许用 `assertVisible`**：它的 `null` 语义相反。新增记录表时的第一个问题是
  "这条记录不属于任何租户时该给谁看"，而不是"用哪个现成方法"。
- **改动落点抛的码 = 改守卫的射程**。脚本头与落点的源码注释里都写了这句。

## 未覆盖

1. **平台级操作者读别家的记录**：本片答"不接"，并给了两条理由（接口形状 / 观测面无写侧）。
   要接，先答 `0074` 未覆盖 1 那个产品问题（平台级管理台长什么样），
   再给三个接口加"点名租户"那一格。**复启条件就是这两件**。
2. **查询路径的租户条件从哪来**：规则 C 判的是"比较"、规则 D 判的是"按主键取实体"，
   而 `page` / `stats` 那类查询走的是 `.eq(Entity::getTenantId, <某个变量>)` ——
   变量是否来自落点，静态看不出来（要追局部变量赋值）。
   `0077` 之后它只有一个来源，改动只需动一处；但"下次有人再手写一遍"没有机器拦着。
   **这是本片之后守卫最大的空白**，写在脚本的「刻意不查的」里。
3. **三管道不接 `DataScope`**（`0025` 未覆盖的另一半）：日志与事件是"没有按数据范围过滤"，
   本片只统一了**租户之间**的口径，租户内"能看多大范围"仍未讨论。
4. **手搓的其他形态**：`SQL` 里 `eq(tenant_id, …)`、`Objects.equals(a, b)` 两侧都是局部变量 ——
   与 `0075` / `0076` 同一格，仍要人工。
5. **`bw_client_log` / `bw_client_event` 的 `tenant_id` 语义没有守卫**：
   "`null` = 不属于任何租户 ⇒ 谁都不能看"这条不变式，今天由落点的实现保证，
   而三方言里那两列都是 `DEFAULT NULL`（不是 `NOT NULL`）—— 谁把它改成 `NOT NULL`，
   规则 B 会红（三方言一致），但"改成 NOT NULL 之后那批历史匿名行怎么办"没有答案。
6. **关系行 / 子资源的可见性**：`0076` 未覆盖 5（`rel_*` 的 `tenant_id` 恒等于容器租户）
   仍未接守卫。
7. **达梦未实测**（全仓同一条，`0073` 未覆盖 1）。
8. **`0025` 未覆盖 3 的"过滤条件那一类"**：审计的时间窗与 `resource` 过滤仍是纯查询参数、
   没有必传约束 —— 与本轮的"可见性那一类"是两件事，本片没动。
