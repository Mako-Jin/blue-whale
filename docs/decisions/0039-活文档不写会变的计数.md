# 0039. 活文档不写会变的计数（与 turbo 的产物声明订正）

- **状态**：已采纳
- **日期**：2026-10-13
- **决策者**：舰长

## 背景

起因是处置 `web/README.md` §七 那张表 —— 它的抬头写着"各项目均通过全部校验（逐包直跑）"，
下面是 6 行 × 8 列：类型检查 / ESLint / Stylelint / 单测 / 生产构建 / dev server。
本轮把它逐格核对了一遍，结果不是"数字旧了"，而是**它已经和同一份文档里的另一句话矛盾**。

### §七 那张表的实测对照

| 包                          | 表里写的用例数 | 本轮实测 | 差   |
| --------------------------- | -------------- | -------- | ---- |
| `platform-portal`           | 22             | **30**   | +8   |
| `common-tools`              | 169            | **178**  | +9   |
| `common-api`                | 55             | **73**   | +18  |
| `platform-log-console`      | 25             | **28**   | +3   |
| `platform-event-console`    | 12             | **18**   | +6   |
| `platform-environment`      | 182            | 182      | 0    |
| `platform-admin`            | 11             | **29**   | +18  |
| `platform-audit-console`    | 9              | **11**   | +2   |
| **逐包合计**                | **485**        | **549**  | +64  |

**485 是关键。** 同一份文档的别处（以及 `.github/workflows/ci.yml` 的头注释）写的是 **549** ——
也就是说：**总数被更新过、逐包表没有**，于是同一份文档里两个数字互相打脸，
而**没有任何机制会因此变红**。这类表不会有第二次机会被核对，谁也不会专门去数 `vitest` 的输出。

### 同样的病，全仓不止一处

顺势把活文档（README / AGENTS / CONTRIBUTING / workflow 注释）里的测试计数全扫了一遍：

| 位置                                                   | 原写           | 实测         | 状态       |
| ------------------------------------------------------ | -------------- | ------------ | ---------- |
| `server/README.md` 的构建命令注释                      | 当前 149 例    | **181**      | 已漂 **32** |
| `web/packages/common-tools/README.md` 的目录注释       | 178 例         | 178          | 恰好还对   |
| `web/packages/common-tools/README.md` 的测试说明       | `micro.test.ts` 共 13 条 | **14** | 漂 1 |
| `web/platform/platform-log-console/README.md` 的目录   | 25 例          | **28**       | 漂 3       |
| `web/platform/platform-environment/README.md` 的目录   | 181 例         | **182**      | 漂 1       |
| `web/README.md` §七 那张表                             | 见上表         | 见上表       | 5 处漂     |
| `docs/README.md` §四 的 `0036` 摘要行                  | 549 / 180      | 549 / **181** | 后端漂 1  |
| `.github/workflows/ci.yml` 头注释                      | 549 / 181      | 549 / 181    | 恰好还对   |

**规律是明显的**：凡是**最近一次改动时顺手核过**的地方就对（`ci.yml` 是 `0036` 那轮写的、
`common-tools` 的 178 是那轮加测试时写的），**没人再看第二眼的地方就漂**。这不是"谁不认真"，
是**这个办法本身不成立**：一个值如果没有地方能算出它、也没有门禁能查出它错了，它就一定会过期。

这与本仓已经反复记过的那类缺陷同源：

- `0037` 的"八个浏览器脚本"实为九个 —— 当时的处置是**指定唯一权威清单**（`scripts/README.md` 的「前置条件」列）；
- `0036` 决策 6 那个永远装不进内容的 `infra/ci/` 空占位；
- `0035` 记的"结论打完进程不结束 = 流水线超时"。

**都是"声称的状态与实际不符，且没有任何东西会因此失败"。**

## 决策

1. **活文档不写会变的计数。** 测试用例数、构建产物体积、"全部通过"这类状态，
   一律不写进 `README.md` / `AGENTS.md` / `CONTRIBUTING.md` / workflow 注释。
   **要数字就跑一遍**（`pnpm test` / `mvn verify`），**要看通过状态就看 CI**。

2. **ADR 是记录，可以带数字** —— 但必须写明是"当次实测"，且**不要求它以后还成立**。
   两类文档的分工：活文档回答"怎么约定"，ADR 回答"当时为什么这么定、当时的实测是什么"。
   所以 `0036` / `0038` 里那些数字**不回改**，它们是被时间钉住的快照。

3. **"通过状态"的权威源是 CI**（`0036` / `0037` / `0038`），不是任何文档。
   文档里再写一份，就是又造一个会漂的副本。

4. `web/README.md` §七 改为只记**静态配置事实**（每个包有没有某个脚本、dev 端口是多少）。
   这类值不随代码量变化，且恰好决定了"某个检查为什么没覆盖某个包"——比如
   `common-api` 没有 Stylelint、`common-config` 一个脚本都没有，所以 `pnpm stylelint`
   跑的是 9 个任务而不是 10 个（`turbo` **静默跳过**没有该脚本的包）。

5. **判据（写活文档时用这一条）**：**它会不会因为一次普通提交而变？**
   `六个应用`、`三套方言`、`:3600` 是结构事实 —— 改动它们是显式动作，写了不会悄悄过期；
   `149 例`、`465 kB`、`全部通过` 会随每次提交漂 —— 不写。

### 顺带订正：`test` 任务的 `outputs` 声明

`turbo.json` 给 `test` 声明了 `outputs: ["coverage/**"]`，而各包的 `test` 脚本是
`vitest run`（**不带 `--coverage`**）—— coverage 目录**根本不会出现**。

实测（`pnpm exec turbo run test --force`）：**一次打 8 行**
`WARNING no output files found for task <包>#test`，每包一行。

处置：改成 `"outputs": []`（承认它没有产物）。
**没有把 `--coverage` 加进 `test` 脚本** —— 那会让每次测试都多产一份没人消费的东西、
并拖慢流水线；覆盖率的 `provider` 在各包 `vite.config.ts` 里配着，真要就跑单包
（`pnpm --filter <包名> test --coverage`），那份产物不需要进缓存。

这与 `0037` 里 `common-api#build` 那条**是同一个错误**：**声明的产物与实际不符**。

## 后果

**正面**

- 少了一类"看文档以为知道、其实早就错了"的陷阱 —— 而且这类错误**不会自己暴露**。
- 每次 `pnpm test` 少 8 行噪声。噪声留着会训练人忽略输出，那是一种慢性失效。
- 数字的口径统一到"跑一遍"，不会再有人手工维护第二份。

**代价 / 负面**

- 文档里不再有"规模感"。改用"一整批""各包"这类量级词代替；真要数字就现场跑。
- §七 看起来变"空"了 —— 它换成了静态事实表，那类信息**不会过期**，但确实不如原来看起来"丰富"。
- 有读者可能觉得"连个数都不给"。§七 里留了一行说明**为什么删**，指向本文件。

**后续约束**

- 新增 README / 章节时**不写计数**；表达规模用量级词，或直接指向 CI。
- 写下任何"会变的量"之前先问：**它有没有权威源？** 若有（能从某个文件算出来），
  正确做法是**加一个零前置守卫**去核对，而不是靠人记得改（见"未覆盖"第 1 条）。

## 本决策未覆盖

1. **契约的路径 / 接口 / 模型计数**（`docs/api/README.md` 写 43 / 67 / 100）**属于另一类**：
   它们**有权威源**（`docs/api/openapi.json`），本轮实测**与文档一致**。可以像
   `verify-docs-index.mjs` 那样给它们加一个零前置守卫（读 JSON 算出来比对），
   但那是**独立一轮**，本决策不顺手做。
2. **文档里其他"会变的数"没有清零**，例如"六个应用""9 个任务""前后端各 15 / 8 个模块"这类。
   它们按决策 5 的判据是**结构事实**（增删是显式动作），与"用例数"不同类。
   **本轮只按"会不会因一次普通提交而变"划线**，没有追求"文档里一个数字都不许有"。
3. `web/README.md` §七 里那五段引用块（`vite build` 必须实际跑 / 产物 `base` 分环境 /
   三维画布不能由组件持有 / 切场景不换渲染器 / 相机跟随整体平移）**没有动** ——
   它们是不变量的记述、不是计数，且各自指向 `0012`~`0015`。
4. 顺带删掉了 §七 里那段"turbo 报 `os error 231`"的引用块 —— **它已经过时**
   （本轮 `turbo run test --force` / `turbo run build --force` 均正常，10 个任务全成功）。
   该段当时是把一次**本机进程创建限制**写成了"运行环境限制"，现在那个限制不在了，
   留着会误导人以为 `turbo` 编排放不动。
5. `web/pnpm-workspace.yaml` 里 `elemental/*` 那个指向不存在目录的 workspace glob
   **仍待定**（`0037` 的未覆盖项，本决策不表态）。
