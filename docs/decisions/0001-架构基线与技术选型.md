# 0001. 架构基线与技术选型

- **状态**：已采纳
- **日期**：2026-10-08
- **决策者**：舰长

## 背景

BlueWhale 是全新的大型全栈项目，开工前需要一次性把骨架定死——地基返工的成本远高于新建。

参考了两个既有项目作为结构范本：

- `platform-terminator` —— 纯前端 monorepo：pnpm workspace、`common-*` 公共包、按业务域分组、qiankun 微前端、React
- `SystemTerminator` —— 纯后端 Maven 多模块：`sts-*` 体系、包名 `com.yaocode.sts`

需要决策的问题：

1. 仓库如何划分？
2. 前后端放同一个工作区，还是分离？
3. 管理端与用户端在后端如何切分？
4. 技术栈选型？
5. Java 与 TypeScript 跨语言如何共享类型？

## 决策

### 1. 前后端分离为两个独立工作区

```
BlueWhale/
├── web/      前端工作区（pnpm workspace + Turborepo）
├── server/   后端工作区（Maven 多模块）
├── docs/     文档与契约        ┐
├── scripts/  跨端脚本          ├ 横向层，不属于任何一端
└── infra/    容器 / 网关 / CI / 部署 ┘
```

两端各自拥有构建体系，互不侵入，通过 HTTP + OpenAPI 契约对接。

**为什么不放同一个工作区**：pnpm 与 Maven 是两套完全不同的依赖与构建模型。混在一起会让 CI 配置、IDE 索引、依赖锁三方面同时变复杂，且任何一端升级工具链都会牵动另一端。

### 2. 前端按「端」切，后端按「业务域」切

- 前端按端拆成独立应用：`platform-portal`（容器）+ 用户端 + 管理端，各自构建、各自发布。
- 后端**不按端切分**，统一领域模型，两端差异由接口面隔离。

**理由**：管理端与用户端操作的是**同一批业务对象**——同一个订单实体、同一套状态机、同一个事务边界。后端按端切成两套 = 领域逻辑复制两份，改一个规则要改两处，两边还会逐渐跑偏。这是大型项目里最难偿还的债。

### 3. 技术栈

| 端 | 选型 |
|----|------|
| 前端 | React 19 + Vite 8 + TypeScript 6.0.3 + React Router 7 |
| 微前端 | qiankun 2.x |
| 前端工程 | pnpm workspace + Turborepo |
| 样式 | Less |
| 代码规范 | ESLint 10 + Prettier 3 + Stylelint 17 + commitlint + Husky + Vitest |
| 后端 | Java 21 + Spring Boot 3.3 + Spring Cloud 2023 |
| 数据访问 | MyBatis-Plus |
| 后端构建 | Maven 多模块（包名 `com.bluewhale.sts`） |
| 接口契约 | OpenAPI 3 |

### 4. 跨端共享走 OpenAPI 契约

Java 与 TypeScript 无法直接共享类型，因此以 `docs/api/openapi.json` 作为唯一真相源：

```
server/  ──生成──▶  docs/api/openapi.json  ──生成──▶  web/packages/common-api
（后端实现）           （唯一契约）                   （前端类型 + 请求客户端）
```

前端 SDK **禁止手写**，一律由契约生成。任何一方私自改字段，都会在下一次生成时暴露。

## 后果

**正面**

- 两端可并行开发，构建互不阻塞
- 契约自动生成，字段名不靠人肉同步，消除一大类低级事故
- 后端领域逻辑保持单一，业务规则改动只需改一处

**负面 / 代价**

- 需要维护契约生成链路（`scripts/`），比单体项目多一道工序
- 微前端引入 qiankun 后，本地同时拉起多个应用需要 Turborepo 协助编排
- TypeScript 被锁定在 6.0.3 —— 因 `typescript-eslint` 的 peer 约束（`<6.1.0`），无法使用 7.x

**后续约束**

- 六条铁律见根 `README.md`
- 规范工具链只维护一份，放在 `web/packages/common-config`
