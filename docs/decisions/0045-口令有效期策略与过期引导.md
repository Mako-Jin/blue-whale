# 0045. 口令有效期：一条从未生效的策略，与它的落点

- **状态**：已采纳
- **日期**：2026-10-13
- **决策者**：舰长

## 背景

`0044`「本决策未覆盖」第 3 条：

> **口令过期（`password_expires_at`）的引导**。后端已有 `40111`，前端同样需要一个入口 ——
> 它与本决策的落点是同一个，但触发条件与文案不同，留给下一次。

那句话里有两处前提。核对之后**两处都不成立**——这一轮的产出与其说是一个功能，
不如说是先把这两件事查清楚，再看剩下的是什么。

### 一、「后端已有 `40111`」——它是一条不可能出现的码

`AuthService#login` 里确实拦着它（那句 `if`），`AuthResultCode` 里有码、有文案，
`bw_auth_user` 有三方言建表语句、`UserEntity` 有字段声明。一处不缺。

缺的是**写入方**：`setPasswordExpiresAt` 全仓**零命中**。`PasswordChanger` 不写它、
管理员重置不写它、建号不写它、种子数据不写它，也没有任何配置会算出它。
这一列因此永远是 `NULL`，而 `user.getPasswordExpiresAt() != null && ...`
的**第一个条件恒为假**。

所以 `0043` 那句「`password_expires_at` 确实校验了」是对的、也是不够的：
**读的人在，写的人不在**，那条分支一次也不会走到。

这是同一类缺陷的**第三种形式**。前两种是 `0020` 的"失败计数被自己的异常回滚"（有 bug）
与 `0043` 的"`must_change_password` 零逻辑引用"（有消费者才有意义）。这一种最难发现，
因为**没有的东西看起来和有一模一样**：有 `if`、有文案、有数据库列、有文档描述，
连码表里的编号都接着排。它的前身（`0044` 查出的）是"有读取方、但那个读取方走不到" ——
两者的共同点都是：**读到这一段时看不出它不生效**。

（`AuthResultCode` 里 `TOKEN_EXPIRED` / `CAPTCHA_*` / `MFA_*` 也是零抛出点，
但它们与 `40111` 有一个区别：那些是**留白的码**，没有任何一处假装自己在工作。
留一个还没实现的码是记录设计词汇；写一个永远为假的条件是假装已实现。）

### 二、「落点是同一个」——也不成立

`0044` 的落点是**基座顶栏里的改密对话框**，它在会话之内。
而 `40111` 是**登录时**抛出的码：走到这里的人**没有被建立的会话**——他恰恰进不来。
一个够不到另一个，落点不可能是同一个。

再往里看一层，那句文案原本写的是「密码已过期，**请修改密码**」。
而 `PUT /api/auth/password` 要求 `AuthContextHolder.require()`（访问令牌），
所以这句话**描述的是一件用户做不到的事**。
指示越明确，找不到入口时越像自己的错 —— 这是比"没有提示"更坏的一种提示。

### 三、顺带核出：它原本可以在"一直别登出"下永不生效

过期只在 `login` 里检查。而刷新令牌是**轮换**的：每次续出一个新的、有效期重新起算
（默认 7 天）⇒ 只要用户至少每 7 天打开一次应用，他就**永远不必重新登录**，
`login` 里那条检查也就永远不会被执行。

它不是"残留一点时间"，是**永不生效**。而"永不生效"与背景一里那条"永远为假"
合起来意味着：`0043` / `0044` 里所有关于口令过期的描述，描述的都是一件没发生过的事。

## 决策

### 1. 保留硬拦，但把指示换成一条存在的路

过期就是不能登录、也不能续期。这与 `must_change_password` 的"放进来再引导"**不是同一条处置**，
而差别不是口味：

- `must_change_password` 是**管理员刚发下来的临时口令**。不放进来，用户就真的没有别的路
  （进不去 ⇒ 改不了密 ⇒ 死锁），所以只能让他先进来再引导。
- 口令过期是**口令已经不该再被接受**，而它有一条别的路：**管理员重置口令**
  （`platform-admin` 用户页的重置入口，重置后 `mustChangePassword = 1`，
  由 `0044` 的引导接管）。

判据可以写成一句：**硬拦只用在"还有别的路可走"的情形；没有别的路时，硬拦就是死锁。**

文案因此改成「口令已过期，请联系管理员重置口令」。这不是措辞问题 ——
原来那句指向一个不存在的入口，现在这句指向一个**真的能把人接回来**的动作，
而"真的"这件事有测试逐条证明（`PasswordExpiryApiTest#shouldSelfHealAfterAdminReset`：
重置 → 那条从未被烧掉的刷新令牌自己长回来 → 响应带上 `mustChangePassword = 1` →
新口令能登录）。

### 2. 过期检查必须覆盖**刷新**

见背景三。判据：**一条能被"保持登录"绕过的有效期策略，不是策略，是注释。**

拦在刷新这条路上的残留边界是访问令牌的有效期（默认 2 小时）：
最坏情况下到期的人还能用旧会话两小时，之后必须由管理员重置才能回来。
这与 `logout` / `changePassword` 接受的残留是同一个量级、同一条理由
（无状态访问令牌撤销不掉，只能靠它自己过期）。

### 3. 失败的检查不留副作用：作废旧令牌挪到**全部校验之后**

`refresh` 原本的顺序是"校验令牌 → **作废旧令牌** → 查人 → 发新令牌"。
校验移到作废之前，多了一层具体的收益：口令已过期的用户反复刷新只会反复得到 `40111`，
手上那个刷新令牌**不被烧掉** —— 于是管理员重置之后他不必重新登录就能恢复。

反过来（先作废再校验）会得到一个**没法自愈**的会话：令牌被烧掉、新令牌又没发出来。
这与 `changePassword` 注释里那句"上面任何一步失败都不该动会话"是同一条原则，
只是换了个地方：**一个失败的请求不该留下痕迹。**
用例里"同一个刷新令牌连刷两次都是 `40111`（而不是 `40106` 重放检测）"
与"库里未作废的令牌仍是 1 条"就是在钉它。

### 4. 有效期是策略；写入方只有一个

- 配置项 `bluewhale.auth.password.expire-days`（默认 **0 = 不启用**），
  与 `history-count` 同一形态、同一条原则：更严的规则由部署方按自己的合规基线显式打开，
  不由框架替它决定。
- 算术在 `PasswordPolicy#expiryOf`，**落库只在 `PasswordChanger#assignNewPassword` 一处**。
  建号 / 管理员重置 / 本人改密三个入口都经过它，于是"换了口令就该换寿命"没有第二处可忘。
  `shouldStampExpiryOnEveryPasswordEntry` 直接盯着这件事 —— 没有写入方的功能等于没有功能，
  而这正是本轮要修的病，不能在这里复发一次。
- **不追溯存量**：`NULL` 仍然是"永不过期"，打开开关不会让任何既有账号失效，
  他们只在下次改密时才拿到这个时刻（与 `history-count` 同一条）。
- **登录不重算寿命**。顺手推后是个很自然的写法，但它把有效期悄悄换成"多久没登录"。

### 5. 「关掉策略」靠判断先看策略，不靠清数据

这一条是被实现逼出来的，值得单独记。

`PasswordChanger` 一开始会在策略关闭时 `setPasswordExpiresAt(null)`，想把残留清干净。
**实测不落库**：MyBatis-Plus 的 `updateById` 默认跳过 `null` 字段（本仓未改这个全局策略），
于是那句代码是一句"代码清了、库里没清"的假动作 —— 而且它会让人相信残留已经清干净了。
即便能清，清残留也只覆盖"关掉策略之后又改过密的人"，其余人的旧时刻一直都在。

改成 `PasswordPolicy#isExpired` **先看策略有没有开**：关掉就是谁也不过期，
**配置一改完立刻对所有人生效、不需要动一行数据**。两条断言分别钉住两侧 ——
`PasswordExpiryDisabledTest`（库里放着过去的时刻，登录与续期仍照常）
与 `PasswordChangerTest`（策略没开时**不去动**那一列，谁要是补上那句 `set(null)` 就会红）。

### 6. 被请出去的时候，界面要说得清为什么

会话失效有两种来路，用户感受到的完全不同：自己点登出（他知道发生了什么），
或被服务端拒绝续期 —— 他正在做事，页面忽然回到登录页。**后一条路上没有任何用户动作**，
界面自己讲不出原因，而"为什么"只存在于服务端那句响应里。

`AuthChannel` 因此记下这一句（`consumeAuthNotice()`），登录页把它显示成一条与提交错误
**分开的**说明：`notice` 解释的是"你刚才为什么会掉出来"（先于本次操作存在），
`error` 说的是"这一次提交失败了"。合成一处，刚被踢出来的人会以为自己点错了什么。

三条判据：

- **只记服务端明确拒绝时的那句话**（业务失败）。传输层失败（断网、超时）
  不是"会话失效"的证据 —— 把它当原因，用户会以为必须重新登录，而可能只是后端此刻不可用。
- **文案原样用服务端的**。前端另写一套只会变成第二份会过期的说法，而且它是唯一被看到的那份。
- **启动时那次恢复失败不留原因**。用户还没进来过，没有"被中断"这回事；
  留着的话，隔一周打开应用会迎面看到一句昨天的原因 —— 话是对的，但它解释的是没发生过的事。

## 后果

- **`40111` 成为一条真的会出现的码**，且出现时有两条路可走（管理员入口 + 那句文案）。
  这句话现在有内容：`PasswordExpiryApiTest` 里五例覆盖登录被拒 / 续期被拒 / 不留副作用 / 自愈 / 写入方。
- **默认行为一行不变**：`expire-days = 0`，没有账号会过期，建号也不写那一列。
  打开它才会有人被挡在门外 —— 因此 `application.yml` 里那一行注释写明了前提：
  **打开之前先确认还有管理员能进来**。
- **"口令有效期"这件事第一次有了单一真值来源**：`PasswordPolicy` 是
  `bluewhale.auth.password` 下所有策略参数的唯一读取处（强度 / 防重用 / 有效期），
  `PasswordChanger` 是 `password_expires_at` 的唯一写入方。`AuthService` 两处检查引用同一个判断。
- **代价（如实记）**：`expire-days` 从 0 改成正数时，**库里已有到期时刻的账号会立刻按新策略生效** ——
  谁的口令比新 TTL 还老，谁就在那一刻失去登录能力。这与"不追溯"并不矛盾：
  不追溯说的是**不主动给存量账号写一个时刻**，而不是"忽略已经写下的时刻"。
  真要避免这种批量到期，正确的做法是**先设一个较大的天数、再逐次收紧**，
  而不是指望清库（见决策 5：清不掉）。
- 残留的到期时刻在策略关闭期间是**惰性**的（判断不看它），但它**留在库里**，
  并且会在策略重新打开时立刻生效。这是上面那条代价的另一面，刻意不掩盖。

## 未覆盖

- **「忘记口令」**。仍然需要"一条不依赖登录态的信任通道"（邮箱 / 短信 / 人工审批）。
  本轮没有碰它：过期与忘记是两种处境，前者的用户**知道自己的口令**，
  所以"找管理员重置"是一条可解释的路；后者连这一点都不成立。
- **租户级 / 角色级有效期**。当前是全局配置（与口令强度策略同一处）。
  多租户下这几乎一定要分化，但那时要回答"同一个用户属于多个租户按谁的算"——
  那是 `0016` 权限域的问题，不该顺手塞进这里。
- **过期前预警**（"还有 3 天过期"）。它需要把到期时刻下发给前端，
  而现在的响应里只有判定结果（过期 / 没过期）。做它等于多一个对外字段与一处文案，
  留给需要它的那一轮。
- **子应用独立运行时的处理**。与 `0044` 同样的理由：那些形态连登出都没有。
- **管理员重置口令不撤销刷新令牌**（本轮核出，未处置）。自助改密会撤销该账号**全部**
  刷新令牌（`0043` 决策，理由写在 `AuthService#changePassword`："改密最常见的动机就是
  我怀疑口令泄露了"），而管理员重置**只**改口令并置 `mustChangePassword = 1`
  （`UserService#resetPassword` 全文如此）。两者的动机是同一个，效力却不一致 ——
  一个已经换到手刷新令牌的攻击者，在管理员重置之后**仍然能续期**。
  它与本决策相邻但不同源（这条是"凭据变更该不该清会话"，本决策那句是"失败的检查不该有副作用"），
  故不当场混进来；它该由下一次动手解决，判据是"撤销会话的入口要不要只有一个"。
- **`40111` 的文案不在任何守卫射程内**。它写在 `AuthResultCode` 的枚举里，
  既不在 `openapi.json`（错误码不进契约），也不在 `verify-api-contract` 的核对范围内 ——
  改了这句话没有任何东西会红。这与 `0040`「未覆盖」里那条"契约与代码是否一致没有守卫"
  是同一类空白，只是这一处更小、也更不值得为它加机器。
