# 0073. 存量值的普查与 DML 迁移的定档

> 领 `0072`「未覆盖」2，原文：
> 「**存量值未订正**（决策 5）。射程需要一次普查才能定：**"哪些列会被精确匹配"×
> "哪些历史窗口没有归一"**。已知会落进去的至少是 `0071` 的七个过滤列（6 张表）+
> "寻址列"四列；边界一旦按"同一条不变量"划，就该**一次划完**，
> 不能再按"最近哪篇 ADR 碰过"划。」
>
> 领到之后把矩阵划完了、把唯一的存量载体实测了，结论是**没有一行可迁**：
> `0072` 决策 5 的三条理由 —— ①「无生产部署」**实测成立且加码**（全宇宙脏行数 = 0）；
> ②「边界不闭合」**被本篇矩阵关闭**（21 个判定列全部登记）—— 但关闭之后实测仍为 0，
> 结论不变；③「`TRIM(col)=?` 造第三种相等」只约束**判重 SQL 的永久使用**，
> 不约束一次性迁移，而如今它是**空集上的争议**。
> **V9 不写。** 本篇的交付物是一张**矩阵**与一份**体检 SQL**，不是一条 `UPDATE`。

## 背景

### 1 两个轴都是实测的

**轴一「哪些历史窗口没有归一」**——从 git 历史定，全部提交时刻：

| 事件 | 提交 | 时刻 |
| --- | --- | --- |
| 日志表创建（V1） | `e941b14` | 10-10 |
| 事件表创建（V2） | `260ca9e` | 10-10 |
| 认证域建表（V3） | `b76fed7` | 10-11 |
| **写入侧归一（`0071`）** | `a2bd429` | 10-15 19:08 |
| **寻址列判重归一（`0072`）** | `c8ef4cd` | 10-15 19:53 |

脏值窗口 = **表创建 → 写入侧归一**。读侧归一（`0069` 18:02 / `0070` 18:28）都落在
写入侧之前，不构成窗口。**全仓的脏值窗口统一关在 10-15 19:53**，
此后任何写入都过 `FilterValue`。

**轴二「哪些列会被精确匹配」**——判据仍是 `0071` 的那句"读侧会不会拿它做精确匹配"。
从代码反推（`eq` / `existsXxx` / `enumValue` / `KeywordLike` 全部调用点 +
写入侧 `setXxx`），得到 **21 个判定列**。

### 2 矩阵：21 个判定列 × 有没有真窗口

| 列 | 精确匹配入口 | 写入侧现状 | 真窗口？ |
| --- | --- | --- | --- |
| `bw_client_log.app` / `namespace` / `trace_id` / `session_id` | 读侧 `eq` + 聚合 SQL | `0071` 起过 `text()` | **有**（10-10 → 10-15） |
| `bw_client_event.app` / `user_id` / `device_id` / `session_id` | 读侧 `eq` | `0071` 起过 `text()` | **有**（同上） |
| `bw_auth_user.phone` | 判重 `eq` | `0072` 起过 `text()` | **有**（10-11 → 10-15） |
| `bw_auth_user` / `tenant` / `role` / `organization` 的 `status` | 读侧 `eq` + 登录/自锁的字面量比 | `0071` 起过 `text()+resolveStatus` | **有**（10-11 → 10-15） |
| `bw_auth_role.category` / `bw_auth_user_group.category` / `bw_auth_organization.org_type` / `bw_auth_resource.parent_code` | 读侧 `eq` | `0071` 起过 `text()` | **有**（10-11 → 10-15） |
| `bw_auth_user.email` | 判重 `eq` | `0072` 起（等价变换） | **无** —— `@Email` 从首提交起就在 DTO 层拒掉带空白值（`0072` 实测） |
| `bw_client_event.event_name` | 读侧 `eq` | **写侧自始有 `EVENT_NAME_PATTERN`**（小写点分、禁空白） | **无** |
| `bw_client_log.level` | 读侧 `enumValue` | 写侧自始 `parse → wireName`（wireName 本就是小写正形） | **无** |
| `bw_audit_log.result` | 读侧 `enumValue` | 写侧 `AuditResult.wireName()` 枚举生成 | **无** |
| `bw_audit_log.action` / `resource` / `operator_name` / `target_id` | 读侧 `eq` | `@Audited` 注解常量 / 会话上下文（源头是 `@Pattern` 校验过的 username）/ URL 路径段 | **无**（`target_id` 的理论窗口见「未覆盖」5） |
| `username` 与各 `*_code` | 判重 / 树查找 `eq` | `@Pattern` / `域:资源:动作` 编码自首提交起 | **无** |
| LIKE 列（`message` / 各名称列） | `KeywordLike` | —— | **不在射程** —— `LIKE '%abc%'` 对内容 `' abc '` 照样匹配，两端空白不造成漏检 |
| `contact_email` / `contact_phone`（组织） | —— 无精确匹配（`0072`-4） | `0071` 起过 `text()` | **不在射程** |

**结论：真窗口共 17 列**（日志 4 + 事件 4 + 认证域 9），**窗口已在 10-15 19:53 全部关闭**。
`0072` 决策 5 说的"边界不闭合"到此闭合 —— 答案不是"最近两篇 ADR 碰过的列"，
是从两个轴**一次划完**的清单。

### 3 唯一的存量载体，以及它的两个意外

脏行可能存在的载体逐一排除：CI 的 MySQL 每次对**新建库**跑迁移 ⇒ 永远 0；
h2 每次启动重建空库 ⇒ 永远 0；达梦从未部署。剩下的唯一载体是**本机开发 MySQL 的
`bluewhale` 库**（`application-mysql.yml` 指向的那个）。

实测它时撞出两个意外：

1. **窗口真实存在**：15 张 `.ibd` 的最后写入全部停在 **10-12 10:51~11:00** ——
   整库的数据全部产自"未归一窗口"之内，此后三天再没碰过。
   也就是说，**如果脏值存在，就该在这里**。
2. **这库的 Flyway 只跑到 V3**（V1 10-10 / V2 10-10 / V3 10-12）—— V4~V8
   从没在上面跑过。这意味着它的存量表仍是 V3 时代的 `utf8mb4_0900_ai_ci`
   （**不区分大小写**），⇒ **`level <> UPPER(level)` 这类枚举异形判定在这种库上
   永远为 0（假阴性）** —— 体检 SQL 不能用"与 `UPPER()` 相不等"的写法，
   要么 `DISTINCT` 全列人工核对，要么 `BINARY` 比对。这是本篇实测方法学上
   唯一的坑。

## 一 实测：21 项判定全部为 0

测量方式：`--skip-grant-tables --super-read-only` 起一个**免认证、拒绝一切写入**的
实例（连写权限都没有，物理上做不成 DML），逐列跑：

- **空白脏值**（17 列有窗口的 + 顺带全部自由列）：
  `CHAR_LENGTH(col) <> CHAR_LENGTH(TRIM(col))` —— **全部 0**；
- **枚举异形**（5 列，`_ai_ci` 下改用 `DISTINCT` 全列核对）：
  `level` 全是小写 wireName 正形、`status` 全是 `ENABLED`、`resource_type` 全是 `API`
  —— **全部正形**；
- 全库行数：`bw_client_log` 6 · `bw_client_event` 5 · `bw_auth_user` 3 ·
  `bw_auth_tenant` 1 · `bw_auth_role` 2 · `bw_auth_resource` 8 · 其余 0。

**存量脏行 = 0。** 窗口是真实的（意外 1），但窗口内没人写出过脏值 ——
上报端的取值都来自程序化探针，管理端的入参都是表单默认值。
`0072` 决策 5 的理由 ① 从"推断"变成"实测"。

## 二 决策

1. **不写 V9。** 三条理由的裁决见篇首引文：① 实测成立且加码 —— V9 的每条
   `UPDATE` 都命中 0 行，一条没有可观测收益的 DML 却要**永久留在迁移史里**；
   ② 边界已闭合，但闭合的产出是"确认没东西可迁"；③ 空集上无争议。
   `0072` 决策 5 从"理由未验的推后"升级为"**实测关闭**"。
2. **DML 迁移机制不另立。** Flyway 的 V 号脚本本来就是 SQL，"机制"已存在；
   本篇定下的是**启用它的条件**：将来若出现第二个存量载体（生产部署、
   长期使用的共享库），**先跑体检 SQL，非 0 才写 V9** —— 且届时射程以
   本篇矩阵为准（新列要重新按两个轴登记），写法用 `WHERE CHAR_LENGTH(col) <>
   CHAR_LENGTH(TRIM(col))` 的幂等 UPDATE（枚举列 `BINARY` 比对）。
3. **体检 SQL 收进本篇附录，不做成脚本、不进 CI。** CI 库每次新建必 0，
   跑了没有信息量；本机 dev 库也不是 CI 能碰的东西。这与 `0064`
   "宁留清单不留会误报的守卫"是同一取舍：它是一份 **runbook**，不是守卫。
4. **`0072` 决策 5 理由 ② 的关闭方式要如实记录**：不是"边界其实早闭合了"，
   而是**本篇把边界闭合了**（矩阵），闭合之后结论没变。
   "理由错、结论对"和"理由对、结论对"是两种不同的关闭，混着记会让后来者
   以为普查是无用功 —— 恰恰相反，没有这次普查，"0 脏行"就还是推断。

## 三 落地

**代码零改动、契约零改动、守卫零改动。** 交付物全部是文档：
本篇（矩阵 + 实测 + 附录体检 SQL）· `docs/README.md` §二/§四 ·
`server/README.md` 硬规则表（`0072` 行的「未答」栏关掉存量值那半）· 记忆收口。

## 验位

- 体检 SQL 重跑结果确定（0 就是 0，无随机性）；
- `verify-docs-index.mjs` 保证本篇登记进 §四不漏；
- 方法学的坑（`_ai_ci` 下 `UPPER` 判定恒绿）用意外 2 记录在案 ——
  它就是本篇的"扰动验位"：**同一个判定在两种排序规则下会给出两种答案，
  体检 SQL 必须写成与排序规则无关的形态**。

## 后果

**正面**

- 本仓**第一次正面回答了"要不要 DML 迁移"的完整流程**：划射程（矩阵）→
  测存量（体检）→ 定档（不写，给出复启条件）。下一次遇到同类问题
  （如真有生产部署），流程与判据都是现成的。
- `0071`/`0072` 留下的"已写坏的行还躺在库里"这句话，从**未验的担忧**
  变成**实测的清白**。
- 顺带发现并登记：**dev 库落后 V4~V8 三个迁移**（V4 审计表都不存在）。
  下次谁在这库上起 mysql profile，Flyway 会自动补跑，而 **V8 将第一次在
  "有存量数据的表"上做 collation 转换** —— 那是 Flyway 的正常行为，
  但值得在起库后看一眼它的输出。

**负面**

- 体检 SQL 靠人记得跑：没有守卫会在"出现第二个存量载体"时提醒任何人。
  判据写在本篇决策 2，唯一的保险是这一条登记本身。
- 矩阵是**快照不是活物**：新加一个精确匹配列，矩阵不会自己更新。
  它不进 CI 是刻意的（决策 3），代价是**复启时要重新对轴**。

## 「未覆盖」

1. **达梦未实测。** 本篇连 SQL 都没有落进代码，但"体检 SQL 在达梦方言下
   怎么跑"没验过（`CHAR_LENGTH` / `TRIM` / `BINARY` 的达梦等价物未核对）。
   与 `0067`/`0069`/`0070`/`0071`/`0072` 的同一条挂账同源。
2. **dev 库补跑 V4~V8 的结果未观察。** 库是舰长的、凭证不在仓里，
   本篇以只读方式测完即停。下次起库时 V8 对存量行的 collation 转换
   属于"第一次在有数据的表上执行"，留待届时。
3. **`0072`「未覆盖」5（email / phone 要不要归一大小写）原样挂着** ——
   本篇不碰等值语义。
4. **体检 SQL 覆盖的是"两端空白 + 枚举异形"两类脏值**，不是任意数据损坏
   （截断、编码错乱等不在射程 —— 它们不是"归一化窗口"的产物）。
5. **`bw_audit_log.target_id` 的理论窗口**：它取自 URL 路径段
   （`AuditContext.targetOf`），理论上可含编码空白；但没有读者证据表明
   可达（审计的写入者全是服务端注解拦截器），按 `0064` 不为理论路径立规矩。

## 附录：体检 SQL（runbook）

将来出现第二个存量载体时，先跑这个（**MySQL 8**；达梦需换方言）。
判定与排序规则无关（`CHAR_LENGTH` 数字符、`DISTINCT` 人工核对枚举形态），
对 `_ai_ci` 与 `_as_cs` 的库同样成立：

```sql
-- ① 空白脏值：17 个有窗口的列 + 顺带全部自由列
SELECT 'log.app' col, COUNT(*) dirty FROM bluewhale.bw_client_log
         WHERE CHAR_LENGTH(app) <> CHAR_LENGTH(TRIM(app))
UNION ALL SELECT 'log.namespace', COUNT(*) FROM bluewhale.bw_client_log
         WHERE CHAR_LENGTH(namespace) <> CHAR_LENGTH(TRIM(namespace))
UNION ALL SELECT 'log.trace_id', COUNT(*) FROM bluewhale.bw_client_log
         WHERE CHAR_LENGTH(trace_id) <> CHAR_LENGTH(TRIM(trace_id))
UNION ALL SELECT 'log.session_id', COUNT(*) FROM bluewhale.bw_client_log
         WHERE CHAR_LENGTH(session_id) <> CHAR_LENGTH(TRIM(session_id))
UNION ALL SELECT 'event.app', COUNT(*) FROM bluewhale.bw_client_event
         WHERE CHAR_LENGTH(app) <> CHAR_LENGTH(TRIM(app))
UNION ALL SELECT 'event.user_id', COUNT(*) FROM bluewhale.bw_client_event
         WHERE CHAR_LENGTH(user_id) <> CHAR_LENGTH(TRIM(user_id))
UNION ALL SELECT 'event.device_id', COUNT(*) FROM bluewhale.bw_client_event
         WHERE CHAR_LENGTH(device_id) <> CHAR_LENGTH(TRIM(device_id))
UNION ALL SELECT 'event.session_id', COUNT(*) FROM bluewhale.bw_client_event
         WHERE CHAR_LENGTH(session_id) <> CHAR_LENGTH(TRIM(session_id))
UNION ALL SELECT 'user.phone', COUNT(*) FROM bluewhale.bw_auth_user
         WHERE phone IS NOT NULL AND CHAR_LENGTH(phone) <> CHAR_LENGTH(TRIM(phone))
UNION ALL SELECT 'user.status', COUNT(*) FROM bluewhale.bw_auth_user
         WHERE status IS NOT NULL AND BINARY status <> BINARY UPPER(status)
UNION ALL SELECT 'tenant.status', COUNT(*) FROM bluewhale.bw_auth_tenant
         WHERE status IS NOT NULL AND BINARY status <> BINARY UPPER(status)
UNION ALL SELECT 'role.status', COUNT(*) FROM bluewhale.bw_auth_role
         WHERE status IS NOT NULL AND BINARY status <> BINARY UPPER(status)
UNION ALL SELECT 'org.status', COUNT(*) FROM bluewhale.bw_auth_organization
         WHERE status IS NOT NULL AND BINARY status <> BINARY UPPER(status)
UNION ALL SELECT 'role.category', COUNT(*) FROM bluewhale.bw_auth_role
         WHERE CHAR_LENGTH(category) <> CHAR_LENGTH(TRIM(category))
UNION ALL SELECT 'user_group.category', COUNT(*) FROM bluewhale.bw_auth_user_group
         WHERE CHAR_LENGTH(category) <> CHAR_LENGTH(TRIM(category))
UNION ALL SELECT 'org.org_type', COUNT(*) FROM bluewhale.bw_auth_organization
         WHERE CHAR_LENGTH(org_type) <> CHAR_LENGTH(TRIM(org_type))
UNION ALL SELECT 'resource.parent_code', COUNT(*) FROM bluewhale.bw_auth_resource
         WHERE CHAR_LENGTH(parent_code) <> CHAR_LENGTH(TRIM(parent_code));
-- ⚠️ 别用 `col <> UPPER(col)` 判枚举异形：在不区分大小写的排序规则（如未跑
--    V8 的旧库）下它永远相等 ⇒ 恒 0 的假阴性。枚举列一律 `BINARY` 比对，
--    或直接 `SELECT DISTINCT col` 人工核对形态。

-- ② 枚举形态核对（人工比对 wireName）
SELECT DISTINCT level FROM bluewhale.bw_client_log;          -- 应全为小写 wireName
SELECT DISTINCT status FROM bluewhale.bw_auth_user;          -- 应全为 ENABLED/DISABLED/LOCKED
SELECT DISTINCT status FROM bluewhale.bw_auth_tenant;
SELECT DISTINCT status FROM bluewhale.bw_auth_role;
SELECT DISTINCT status FROM bluewhale.bw_auth_organization;
SELECT DISTINCT resource_type FROM bluewhale.bw_auth_resource;
SELECT DISTINCT result   FROM bluewhale.bw_audit_log;        -- 该库需已跑 V4

-- ③ 全部为 0 ⇒ 不写迁移；任一非 0 ⇒ 按本篇矩阵射程写 V9（三方言同构、幂等 UPDATE）
```
