# 0059. 一个码就是一个对象 —— `404` 家族的点名住在码里，六处落点此前没有断言

> 起点是 `0057`「未覆盖」的第 3 条（`40407` / `40409` / `40410` 这些"找不到"的码
> 同样可能"点没点名"参差）。核完得到两个结论：**那句话的前提不成立** ——
> 这一族与 `40002` 结构相反，写不出错的对象；**但核出六处落点此前没有任何断言**，
> 其中包括**三个整族为零的码**（`40402` / `40404` / `40406`）。

## 背景

`0057` 核的是 `PARAM_REFERENCE_MISSING(40002)`：**一个码、十六处 `throw`**，
十六处拦的是同一件事、差别只在文案点名了谁，所以那一篇的核对是
"每一处是否点名了正确的对象、是否都有断言"。

它在末尾留下一个猜测而不是结论："**别的码的文案有没有同样的问题**"。
本片去核这个猜测。而核对的第一步不是逐处读文案，是先问一句
**"这些码与 `40002` 是不是同一种东西"** —— 答案决定了后面该核什么。

## 一、先核那句话：前提不成立

两个家族的结构正好相反：

| | `40002` | `404xx` |
| --- | --- | --- |
| 码与对象的关系 | **一个码覆盖十几个对象** | **一个码就是一个对象** |
| "是哪个对象"住在哪 | **抛出点的文案** | **枚举常量自己** |
| 抛出点会不会写错 | 十六处各写一句、各可能写错 | 不写文案，写不出错的对象 |
| 落点数 | 16 处 | 15 处 |
| 断言该断什么 | **文案**（码不携带对象） | **码**（码就是对象） |

所以 `0057` 那个猜测的落点**不存在**：`404xx` 家族没有"某一处忘了点名"这种失败模式，
因为它压根不在抛出点点名。本域十个码（`40401`~`40410`）的文案逐条核过 ——
**全部点名正确**，与代码实际查的那个对象一致。

两族之所以会长成这样，是因为它们回答的问题不同：`40002` 说的是"**你传的这个 id 有问题**"
（一种错），前半句是什么对象由调用方的入参决定，只能写在抛出点；`404xx` 说的是
"**你要找的那个东西不在**"，而"哪个东西"由接口自己的语义决定 —— 于是它变成一个码，
顺带把"前端该刷新哪个列表"也一起答了（`0048` 的那句话在这里有第二个用例）。

## 二、唯一一处覆盖文案，恰恰是这个码在说两件事

十五处落点里只有一处写了自定义文案：

```java
// DataScopeService#resolve
throw AuthResultCode.USER_NOT_FOUND.businessException("用户不存在或不属于当前租户");
```

放在 `40002` 的语境里看，这就是那十六处的同一种动作 —— "不存在"与"不属于当前租户"
是两种处境。由此推出一条**可检查的规矩**：

> **在抛出点覆盖文案 = 这个码在说两件事。**

拿它去验全仓的覆盖点，是成立的：`TOKEN_INVALID` 的"该令牌不是刷新令牌"、
`BAD_CREDENTIALS` 的"当前口令不正确"（改口令时与登录时是两件事）、
`SYSTEM_ROLE_PROTECTED` 的"不可停用 / 不可删除"（枚举默认文案把两件事用"或"连着）、
`HIERARCHY_CYCLE` 的三支（`0055` 的矩阵），都是同一个形状。

**这一处不能拆成两个码**：拆了就等于告诉调用方"那个人存在，只是不在你这儿"，
而反查接口恰恰不该回答这个问题。这与 `40002` 的选择**相反** —— 那边把它拆成两句文案
（"引用的用户不存在" / "该用户与组织不属于同一租户"），**因此把"那个人存在、
只是不在你这儿"说了出去**。两处的判据不同，而"**为什么这边可以泄漏、那边不可以**"
仓里**没有写下过任何一句话**；反倒是日志 / 事件那两个接口的 `@Operation` 描述里
把这条反泄漏理由写得很清楚（"不区分这两种情形，否则错误码本身就泄露了'这条记录存在'"）。
也就是说这条理由在本仓是**写给别的域、没有写给 `40002`**。记进未覆盖。

## 三、断言核对：十五处里六处空缺，三码整族为零

| 码 | 落点 | 此前 |
| --- | --- | --- |
| `40401` | `DataScopeService#resolve` | 有（`DataScopeApiTest`，两例） |
| `40401` | `RoleMemberService#rolesOfUser` | 有（`UserGroupApiTest`） |
| `40401` | **`UserService#requireUser`** | **没有** |
| `40402` | **`TenantService#requireTenant`** | **没有**（整族为零） |
| `40403` | `RoleService#requireRole` | 有（`RoleApiTest`：删完再查） |
| `40403` | **`RoleMemberService#requireRole`** | **没有** |
| `40404` | **`OrganizationService#requireOrg`** | **没有**（整族为零） |
| `40404` | **`OrganizationService#tree` 的 `rootId`** | **没有** |
| `40405` | `UserGroupService#requireGroup` | 有（`UserGroupApiTest`：删完再查） |
| `40406` | **`ResourceService#requireResource`** | **没有**（整族为零） |
| `40407` | `RoleService#revoke` | 有（`RoleApiTest`：再撤一次） |
| `40408` | `RoleMemberService#revoke` | 有（`RoleMemberApiTest`，两例） |
| `40409` | `UserGroupService#revokeMember` | 有（`UserGroupApiTest`：再移出一次） |
| `40410` | `OrganizationMemberService#revokeMember` | 有（`OrganizationApiTest`） |
| `40410` | 〃 `#setPrimaryPosition` | 有（同上） |

**九处有、六处没有。** 空着的那六处不是判断有分歧，而是**没有人在那种接口上写过
一条"查一个不存在的东西"**。同域的 `40403`（删完再查角色）与 `40405`（删完再查用户组）
都有人写过 —— 它们恰好落在了 `RoleApiTest` / `UserGroupApiTest` 里；
而 `40402` / `40404` / `40406` 这三条最典型的"删完再查"，一条都没写过。

**"删完再查"这条路径为什么值一条用例**：它问的是 `@TableLogic` 有没有真的接上
（行还在库里、只是每条查询都被补上了 `deleted = 0`）。它不成立时的症状不是报错，
而是"删掉的东西还能被查出来"——那条用例同时是软删机制的证据。

## 四、这一族该断什么，与 `40002` 相反

`0057` 的结论是"**只断 `code` 等于没核**"，因为 `40002` 的十六处共用一个码，
携带"是哪个引用错了"的只有文案。**这条规矩不能推广** —— 在 `404xx` 家族里
恰好反过来：

- **断 `code` 就是完整断言**（码就是对象）。
- **断文案不是"点名"，是证明这个码还只干一件事。** 一旦哪一处开始覆盖文案
  （= 第二节那条规矩被触发），那条文案断言会先红 —— 它是"这个码要拆了"的哨兵。

本片新增的用例两样都断，理由如上；`ReferenceMessageApiTest` 断的也是两样，
但两样在那边的**职责完全不同**。同一个写法在两个家族里含义相反，
这是本片最值得记下来的一点。

## 五、顺带核出的两件事

**一、公共码 `40400` 的默认文案"资源不存在"一次都没被用过。** 它的三个读者
（`AuditLogService` / `ClientLogService` / `ClientEventService`）**全部自带文案**，
与本表的十六处正好构成两种相反的形态：`40002` 的默认文案零使用是因为
"每处都必须自己点名"，`40400` 的默认文案零使用是因为"每个域都要说自己的对象"。
更值得记一笔的是它与 `AuthResultCode.RESOURCE_NOT_FOUND(40406)` 的文案**逐字相同**，
靠码值区分（一个是公共的"资源"（REST 语义），一个是权限域的"资源"（`bw_auth_resource`））。
换不换它那句话是文案决定，见未覆盖。

**二、同一个错码值被抄进了七个载体，其中三个是给消费者看的。**

核 `40407` / `40409` / `40410` 的时候顺手扫了 `40401` 在全仓的出现，摸到一件此前不知道的事：
**日志详情与事件详情这两个接口，在四处源码里说它们返回 `40401`，而实现返回的是 `40400`。**

| 载体 | 位置 | 谁会读到 |
| --- | --- | --- |
| 接口描述 | `ClientLogController#detail` 的 `@Operation` | 生成进契约与前端类型 |
| 接口描述 | `ClientEventController#detail` 的 `@Operation` | 同上 |
| 契约 | `docs/api/openapi.json`（两处） | 契约的消费者 |
| 前端类型 | `common-api/src/generated/schema.d.ts`（两处） | **前端** |
| 服务注释 | `ClientLogService#detail` | 读代码的人 |
| 服务注释 | `ClientEventService#detail` | 读代码的人 |
| 用例名 + 注释 | `ClientLogApiTest#shouldIsolateAcrossTenants` | 读用例的人 |

实现抛的一直是 `ResultCode.NOT_FOUND`（= `40400`），而且那条路径**有断言**
（`ClientLogApiTest` 断的就是 `40400`）—— 所以**断言是对的、错的是那几句描述**，
于是没有任何东西会红。前端照契约里的 `40401` 写一个分支，会落在一条**永远不成立的条件**上。

`40401` 是**权限域**"用户不存在"的码。那句话的**判据**（"不存在"与"不属于本租户"要合并，
否则错误码本身泄露记录的存在性）没有问题，错的是码值 —— 日志 / 审计 / 事件三个域
都没有自己的枚举，"这条记录不在"对它们是同一件事，用的是公共码。

**这是 `0053` / `0054` / `0056` 那一族的又一次出现，只是载体换成了接口描述。**
两种守卫都不会碰它：`0040` 的契约守卫**刻意不查散文**（"判不了对错"，写在它自己的未覆盖里），
而 `0041` / `0042` 守的是"生成物有没有跟上契约"—— 这次契约**忠实地**生成了一句错话，
逐字节一致，全绿。**四处源码已订正，契约与前端类型随之重新生成（同一次提交）。**

## 六、本轮改了什么

- **新增 `NotFoundCodeApiTest`（4 例）**，把六处空缺补齐：四个"实体不存在"的码各查一次 ·
  软删之后再查（租户 / 组织 / 资源）· 组织树的 `rootId` 不存在 · 给不存在的角色挂 / 摘成员。
  夹具自带，第二例靠"建一个真实体再真删掉"造场景。
- **`AuthResultCode` 的 `404xx` 段首**写下两条规矩（"覆盖文案 = 在说两件事" /
  "断 `code` 即完整、文案断言是哨兵"）—— 这是这一族**唯一**需要逐处判断的地方，
  所以它住在枚举里，而不是散在十五处。
- **新增活文档小节** `server/README.md`「`404xx` 的十五处落点与它们的断言」——
  十五行对照表（与 `0054` / `0056` / `0057` 同一条纪律：清单住活文档，注释里不复述）。
- **订正那七处错码值**（见第五节）：两个 `@Operation` 的描述、两处服务注释、
  一处用例名与注释，以及**随之重新生成的** `docs/api/openapi.json` 与
  `common-api/src/generated/schema.d.ts`（两者都入库、必须与代码同一次提交）。
- **`404xx` 的断言核对本身：生产行为零改动** —— 十个码的文案都对、十五处落的码都对，
  缺的只是断言。**这一片唯一的"修"是那七处描述**，它改的是文档、不是行为。

## 七、两次扰动验位

四例一次通过（与 `0057` 同一种结局），所以**"全绿"只证明断言与实现一致、
不证明断言能区分**，按仓内纪律补了两次扰动：

| 扰动 | 期望 | 实测 |
| --- | --- | --- |
| `OrganizationService#requireOrg` 覆盖文案为"组织已不存在" | 两处 `requireOrg` 用例变红、`tree` 那条仍绿 | 两红两绿，红的正是那两条 |
| `OrganizationService#tree` 的码换成 `40406` | 只有 `tree` 那条变红 | 一红三绿，红的正是那条 |

第一次扰动同时验了两件事：**文案断言有牙**，以及**两条 `40404` 的落点被分别钉住**
（把 `requireOrg` 动了、`tree` 那条不为所动）。第二次补上"改码会不会红"这一维。
两次都已还原。

## 决策

1. **六处空缺断言一次补齐**，写法沿用 `ReferenceMessageApiTest` 的自带夹具风格。
2. **断言同时断 `code` 与文案**，并在类注释里写清两样在这个家族里各自的作用。
3. **`AuthResultCode` 的 `404xx` 段首写下两条规矩**：覆盖文案 = 这个码在说两件事
   （覆盖前先问"是不是该拆码"）；这一族断 `code` 即完整、文案断言是"要拆了"的哨兵。
4. **活文档建表**「`404xx` 的十五处落点与它们的断言」，而不是在枚举里复述清单。
5. **订正那七处错码值，并重新生成契约与前端类型**（同一提交）——
   它已经进了契约，不改就是让前端照着一句错话写分支。
   **断言核对部分生产行为零改动**：不因为"顺手"去动那唯一一处的合并文案。

## 后果

- **正面**：`404xx` 的十五处落点第一次有了单点真相（活文档那张表）；
  `40402` / `40404` / `40406` 三个码从"零断言"变成"有断言"，
  且"删完再查"这条路径第一次被钉住（它同时是 `@TableLogic` 的证据）。
- **正面（方法）**：`0057` 那条"只断 `code` 等于没核"被限定到它成立的范围 ——
  一个家族的断言规矩不能靠类比搬到另一个家族，要先看**码携带了什么信息**。
- **正面（真缺陷）**：修掉一个**已经进了契约与前端类型**的错码值。
  本片其余部分都是"补断言"，只有这一处是"改错"。
- **负面**：第二例建真租户 / 组织 / 资源再删掉，比纯分支断言重（同 `0057` 的代价）。
- **负面**：契约与生成物因此各多两行 diff，且它们**必须与那四处源码同一次提交** ——
  分开提交会让 CI 的 `server` / `web` 两个 job 各红一次（`0042` / `0041`）。
- **后续约束**：**新增一处 `404xx` 的 `throw` 时，要同时回答两件事** ——
  码选对了吗（对象是不是它说的那个）、以及它在哪条用例里被钉住。
  要在抛出点覆盖文案之前，先回答"是不是该拆码"；不拆就把理由写在那处。

## 未覆盖

1. **`40400` 的默认文案"资源不存在"零使用、且与 `40406` 逐字相同**：
   它是公共枚举里的一句域无关的话，而三个读者全部自带文案 —— 要不要收得更中性
   （例如"目标资源不存在"），是文案决定。与 `0057` 未覆盖 4 同形。
2. **`40002` 分两句、`40401` 合一句，两处判据不同而 `40002` 那一边没写下理由**：
   分句泄漏了"那个人存在、只是不在你这儿"，合句没有。这个差别是有意的还是巧合，
   仓里没有答案。
3. **别的段位的码有没有同样的"断言空洞"**：本片只扫了 `404xx`。
   `401xx`（十个码）与 `403xx` 没按这个口径扫过；`409xx` 只在 `0055` 的矩阵里
   按"支"扫过一部分。
4. **公共枚举 `ResultCode` 里其余的码**：本片只看了 `40400`。
   `40000` / `40100` / `40300` / `40500` / `40900` / `42900` / `50000` 的读者与断言
   没有核过（其中 `40900` 的读者在 `0056` 里出现过，是兜底那一支）。
5. **"零断言的码"没有机械守卫**：可机械判定的是"枚举里有这个码、而测试里没有
   `value(<code>)`"，但断言也可能以 `AuthResultCode.X.getCode()` 的形式出现，
   那会误报 ⇒ 与 `0054` / `0056` / `0057` 的同类未覆盖同形。
6. **散文里的码值没有守卫**：本片订正的那七处，没有任何东西会拦住它再犯。
   `0040` 的契约守卫**刻意不查** `@Operation` 描述（"判不了对错"），
   而它这次恰恰是能查出问题的那条路 —— 前提是**描述里的码值格式统一**
   （同一个接口的 `responses` 里只有 `200`，业务码不进 responses，
   所以"描述里的码值在 responses 里存在吗"这种查法在本仓不成立）。
   要真做，得先定"描述里写业务码"的格式，属另一条判据。
