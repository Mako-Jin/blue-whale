# 0019. 审计日志管道：由后端拦截器产生、前端只读

- **状态**：已采纳
- **日期**：2026-10-12
- **决策者**：舰长

## 背景

`0004`（前端日志上报）与 `0011`（行为事件管道）在论证"三条并列管道"时，
都把**审计日志**写成"已设计、未实现"：它回答的是"谁在什么时候对什么做了什么"，
合规追溯用，全量、不可改、不可采样。两份 ADR 都明确它**由后端拦截器产生**，
是三条管道里唯一不由前端产生的一条。

于是很长一段时间里，仓库是这样一个状态：

- 契约里没有一条审计接口，只在 `ClientLogController` 的注释里写着"审计日志不走本接口"；
- 表、模块、拦截器、接口，一个都没有；
- 但**原料全在**：`AuthContext`（谁在操作）、`AuthInterceptor`（挂载点位）、
  `AuthAuditMetaObjectHandler`（`create_by` 自动填充这套机制）、
  `GlobalExceptionHandler`（统一出入口）。

也就是说，这一环缺的从来不是判断，而是**落地**。而它恰好是检验那句
"内容不同 ⇒ 独立模块独立表、通道相同 ⇒ 复用"的最好样本：审计与其他两条管道
**内容完全不同**（结构化事实 vs 自由文本 vs 行为埋点），因此必须独立。

动手前必须先回答四个问题，它们决定了后面所有结构：

1. **"不可篡改"怎么保证？** —— 加权限码？加签名？加只读账号？
2. **谁产生？** —— 每个 Controller 里手写一行 `auditService.record(...)`？还是拦截器？
3. **成败怎么判？** —— 本仓"业务失败仍返回 HTTP 200"，响应状态码上**看不出**结果。
4. **注解与域放哪？** —— 权限域要标它，审计域要读它，两者互相依赖会成环。

## 决策

### 1. 不可篡改不靠权限，靠"接口不存在"

加权限码只能挡住没权限的人；有权限的人（以及任何拿到数据库连接的人）照样能改。
审计的"不可改"因此落成一组**结构上做不到**的事实，而不是一组策略：

| 手段                              | 说明                                                       |
| --------------------------------- | ---------------------------------------------------------- |
| 不提供任何写接口                  | 只有三个 `GET`；`POST /api/audit/logs` 返回 `40500`        |
| `AuditLogService` 没有写方法      | 插入只走 `AuditRecorder`，绕过业务层                       |
| 实体不继承 `BaseEntity`           | 因此没有 `update_by` / `update_time` / `deleted` 这套东西  |
| 无逻辑删除                        | 表里没有 `deleted` 列，删除这件事不存在                    |
| 前端 SDK 没有写方法               | `common-api` 的 `AuditApi` 只有 `page` / `detail` / `stats` |

`40500` 是**刻意**让 `GlobalExceptionHandler` 单独处理的一类：
不接这一条时，"这个接口不接受 POST"会落到 `Exception.class` 兜底上，
对外变成"系统内部错误"，调用方会去查服务端日志 —— 而真正的原因是它用错了 HTTP 方法。
**把责任归错方，比不给错误码更浪费时间。**

### 2. 显式 `@Audited`，而不是"自动拦所有非 GET"

自动拦的诱惑很大（少写一行注解），但它会把登录、日志上报、健康检查、
行为事件上报全部记进去 —— 这些要么没有业务含义，要么本身就是高频写入，
审计表会被自己的上报请求灌满。而且 **HTTP 方法推不出"做了什么"**：
`PUT /api/auth/users/{id}` 既可能是改邮箱，也可能是重置口令，
两者在合规上完全不是一回事。所以动作标识必须由人显式给出：

```java
@Audited(action = AuthAuditActions.USER_CREATE, resource = AuthResources.USER)
```

**查询不标**（`GET` 不产生审计）。理由不是"查得多"，而是审计记的是**变更**：
读了什么不改变系统状态，把它一起记进来只会让真正要紧的写操作淹没在噪声里。
（若将来要"谁看了敏感数据"这类合规要求，那是一条**独立**的读取审计管道，
不该混进这张表 —— 它的量级与保留期都不是一个数量级。）

### 3. 注解下沉到 `sts-components`：该层首次落地

`@Audited` 同时被两个域用到 —— 权限域（`sts-server-auth` 标它）与审计域
（`sts-server-audit` 读它）。两个域互相依赖就成环了。

`docs/decisions/0005` 早已预留了 `sts-components` 层，并给了示例名
`sts-components-audit-starter`。本次落地时**刻意去掉了 `-starter` 后缀**
（实际 artifactId 是 `sts-components-audit`）：本模块**不装配任何 Bean**，
它只提供两个类型（注解 + 上下文工具）。带 `-starter` 会暗示"引了它就有审计能力"，
而真正装配拦截器的是审计域。名字里的后缀是个承诺，不能随便给。

`sts-components` 与 `sts-common` 的分界，沿用 `0005` 的说法：
**改了业务不受影响 ⇒ common；改了业务要跟着改 ⇒ components。**

### 4. 拦截器顺序：审计必须排在鉴权**之前**

这一条是踩过源码才敢写的。Spring 的 `HandlerExecutionChain.applyPreHandle`
会记录最后一个成功执行过的拦截器下标 `interceptorIndex`，
`triggerAfterCompletion` 从该下标**倒序**回调。于是：

> 鉴权失败时，`AuthInterceptor.preHandle` 抛异常并中断，
> **排在它后面的拦截器 `afterCompletion` 永远不会执行**。

若审计排在鉴权之后，"越权尝试"这一类**最该留痕**的记录会静默丢失，
而且丢得毫无痕迹。因此顺序被集中成常量（`sts-common-web` 的 `WebInterceptorOrder`）：

```
AUDIT = -100   <   AUTHORIZATION = -50   <   DEFAULT = 0
```

把数字收在常量类里而不是散在各处 `order = -100`，是因为这个顺序**有语义**，
且改错方向不会报错，只会让某一类记录消失。

### 5. 成败判定：加一条中立的 `ResponseOutcome` 通道

`afterCompletion` 收到的 `exception` 参数**恒为 null** —— 本次已核对
spring-webmvc 6.2.11 与 7.0.1 的 `DispatcherServlet.processDispatchResult`，
它调的就是 `triggerAfterCompletion(request, response, null)`。
异常早已被 `HandlerExceptionResolver` 处理完，走到这里只剩一个**成功的 200**。

而本仓的约定是"**业务失败仍返回 HTTP 200**"（`docs/decisions/0007`），
所以从响应上也补不回来。结果是：一次被业务规则拒绝的删除，会被如实记成 `SUCCESS`。

解法是在 `sts-common-web` 加一条**中立**通道：

```java
ResponseOutcome.markFailure(request, code, message);   // GlobalExceptionHandler 里每个 handler 都调
ResponseOutcome.failureOf(request);                    // 审计拦截器事后读走
```

关键在**放对位置**：它在 `sts-common-web`，因此**不认识审计域**，
不会让技术底座反向依赖业务模块。审计拦截器按三级判据取结果：

1. `exception != null` → FAILURE（未被 `Resolver` 接住的异常）
2. `ResponseOutcome.failureOf(request) != null` → FAILURE，并用它的业务码
3. `response.getStatus() >= 400` → FAILURE，折成 `状态码 × 100`

**漏调 `markFailure` 不会报错，只会让那一类失败被记成成功** —— 因此
`GlobalExceptionHandler` 的类注释里写明了"新增处理器时别忘了这一句"。

### 6. 写审计用 `REQUIRES_NEW`

`AuditRecorder.record(...)` 标 `@Transactional(propagation = REQUIRES_NEW)`。
业务事务回滚时审计**不能跟着回滚** —— 而"操作被拒绝/失败"恰恰最需要留痕，
正是那些要回滚的场景。事务传播开了新连接，因此业务回滚与审计落库互不影响。

异常处理刻意留在**调用方**（拦截器）：若把 try/catch 写在 `AuditRecorder` 内部方法里，
self-invocation 会让 `@Transactional` 静默失效（代理没被经过），
表现是"审计时有时无"，极难排查。

### 7. 三套标识必须分清：资源 ≠ 权限码 ≠ 动作

这是实现过程中**真的写错过**的一处：

| 类别     | 形状              | 例子                | 常量类              |
| -------- | ----------------- | ------------------- | ------------------- |
| 资源标识 | `域:资源`         | `auth:user`         | `AuthResources`     |
| 权限码   | `域:资源:动作`    | `auth:user:create`  | `AuthPermissions`   |
| 动作标识 | `域.资源.动作`    | `auth.user.create`  | `AuthAuditActions`  |

三者形状相近，混用的后果是**静默**的：把资源填成权限码，
存进去的是 `auth:user:create`，而"按资源过滤审计"查的是 `auth:user` ——
查不到任何东西，却不会报错。因此补了 `AuthTaxonomyTest` 把三者的形状与归属关系钉死。

### 8. 只记服务端时间；匿名不产生审计

审计**没有客户端时间戳**（日志与事件都有双时间戳）。原因很简单：它不由客户端产生，
所以不存在"客户端时间不可信"这个问题，也没有"两个时间该信哪个"的歧义。

**匿名请求不产生审计**：没有操作人，记下来也无法归责；更实际的是公网扫描会灌满表。
**已认证但无权限的请求必须记**：有明确操作人，而且那正是最需要留痕的一类。

### 9. 前端的形态：与另外两个控制台**刻意不同**

日志台与事件台都是左右分栏（客户端视角 / 服务端视角），因为"只看一边无法判断上报成没成"。
审计**没有"两边"**：没有任何路径让前端把记录送出去。

因此 `platform-audit-console`（`:3600`）做成自上而下的三块：
流水 → 按动作聚合 → 演练区。**形态跟着管道的产生方式走**，
"三个控制台长得统一"是次要的。

`common-api/src/audit.ts` 里 `AuditApi` **一个写方法都没有**，
`packages/common-api/tests/audit.test.ts` 用快照式断言把"只有三个读方法"钉住 ——
将来有人想加 `create`，测试会失败，逼他回答"审计记录该不该由前端补写"。

演练区（`DrillPanel`）的按钮**刻意不按权限显隐**：真实建一个租户、等审计记录出现、
再删掉它。用只读账号点下去会得到两条 `FAILURE` —— 而**那次拒绝同样留痕**，
这正是本区要展示的东西。若沿用权限管理台的"没权限就不渲染按钮"，
等于把最值得看的那类记录从演示里抹掉。

## 后果

**正面**

- 三条管道**全部落地**。"内容不同 ⇒ 独立模块独立表"这句话从判断变成了事实：
  `sts-server-log` / `sts-server-track` / `sts-server-audit` 三个域、三张表、三套契约。
- 审计的因果链变成可验证的：写接口一被调用，记录必出现（演练区当场证明），
  且**前端全程没有、也不能写审计表**。
- `sts-components` 层从"预留"变成"在用"，顺带把"何时才该建这一层"的判据写实了
  （被两个域同时需要、且下沉它不引入业务语义）。
- `WebInterceptorOrder` + `ResponseOutcome` 都是**通用**的：
  它们不认识审计，将来任何"需要事后判断请求结果"的组件都能复用。

**负面 / 代价**

- `GlobalExceptionHandler` 每个处理器都多了一句 `markFailure`。
  这是**约定型**的负担：漏了不报错，只让那一类失败被记成成功。
  接受的理由是替代方案（让审计去解析响应体、或让技术底座认识审计域）代价更大。
- 审计记录与业务响应之间**没有"先落库再返回"的强保证**（写在 `afterCompletion`）。
  因此演练区是"轮询等"而不是"断言立刻可见"，`AuditApiTest` 也按唯一条件过滤来断言。
- `platform-audit-console` 与 `platform-admin` 的 `auth/` 接线**逐字重复**了一份。
  六条铁律之⑤要求"复用下沉 `packages/`"，本次**有意没做**：
  那要同时改 `platform-admin` 的既有测试与端到端脚本，风险与"审计管道"无关。
  触发条件写在下一条。
- **`sts-server-audit` → `sts-server-auth` 是一次同层的 Maven 依赖偏离。**
  `architecture/后端分层与依赖方向.md` 的依赖矩阵写的是「同层 ✗」（同层模块之间不建
  Maven 依赖，要互相调用就走 HTTP / 消息）。本次偏离**是有意的，且范围是可枚举的**：
  审计域只从权限域读两样东西 —— 「当前操作人」（`AuthContext` / `AuthContextHolder`）
  与「权限码」（`@RequiresPermission` + `AuthPermissions.AUDIT_READ`）。
  两样都是**读权限域的词汇**，不是**调用权限域的服务**。
  按 `0005` 自己的分界（改了业务要跟着改 ⇒ components），正解是把这套词汇下沉；
  本次没做，因为那会连带改动权限域内部十余处引用，与"把审计管道做出来"是两件事，
  混在一起会让这次提交无法被单独审阅。触发条件见下条。

**后续约束**

- **新增写接口要标 `@Audited`**，并同时补 `AuthAuditActions`（动作）与
  `AuthResources`（资源）。只加注解不加常量是不允许的 —— 动作标识是**永久契约**。
- **查询接口不标**。要记"谁看了什么"必须另起一条管道与另一张表。
- **`GlobalExceptionHandler` 新增处理器必须调 `ResponseOutcome.markFailure`**。
- **拦截器顺序只能用 `WebInterceptorOrder` 的常量**，不得手写数字。
- **审计表不加入 `deleted` 列、不加 `update_*` 列**，也不提供任何写接口。
- **`sts-server-audit` 对 `sts-server-auth` 的用法只允许上面枚举的两样。**
  出现第三个用途（尤其是调用权限域的任何 Service）即视为越界，必须改为下沉词汇。
  更硬的触发条件：**第二个非权限域的服务需要 `@RequiresPermission` 时**，
  就把 `RequiresPermission` / `AuthContext`（连同 `AuthPermissions`）移到
  `sts-components` 下的认证词汇模块，届时本偏离自动消失。
- **`platform-*` 之间继续互不引用**；`platform-audit-console` 与 `platform-admin`
  的共享接线在**出现第三个管理型子应用时**下沉到 `packages/`。

## 落地顺序

1. `sts-components` / `sts-components-audit`：`@Audited` + `AuditContext`
2. `sts-common-web`：`WebInterceptorOrder`、`ResponseOutcome`、`GlobalExceptionHandler` 补标记
3. `sts-server-audit`：实体 / Mapper / Service / Controller / 拦截器 / 自动配置 + 三方言 `V4`
4. `sts-server-auth`：三套标识常量、给 6 个写方法标注解、`AUDIT_READ` 权限、审计员种子补权限
5. 测试：实体映射、拦截器（7 例）、审计 API（7 例）、标识分类学
6. 契约导出 → `common-api` 接 audit 域 → `platform-audit-console` → 端到端脚本

## 本决策未覆盖

明确没做、且已知要做的事：

- **采样**：审计全量，不做采样（与行为事件同理）。这条是约束不是待办。
- **脱敏**：服务端没有对 `targetId` / `errorMessage` 做二次脱敏。
- **保留期与归档**：表会一直长，没有分区、没有清理任务。
- **导出**：没有 CSV / 报表导出接口。
- **告警**：失败率突增没有触发任何通知。
- **读取审计**：只记变更，不记"谁看了敏感数据"。
- **达梦下的验证**：`V4` 的达梦脚本未在真实实例上跑过
  （`DESC` 索引与 `VARCHAR(n CHAR)` 沿用 `0010` 的结论，未复验）。
- **审计自身的失败**：`AuditRecorder` 写库失败只记一条 WARN，不重试、不外抛 ——
  接受"极少数记录会丢"，因为记审计失败不能连累业务响应。
