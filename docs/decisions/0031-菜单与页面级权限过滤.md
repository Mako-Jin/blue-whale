# 0031. 菜单与页面级权限过滤：把"导航栏上出现哪几个入口"变成可配置的事实

- **状态**：已采纳
- **日期**：2026-10-13
- **决策者**：舰长

## 背景

`0030` 的「发现但未处理」第 5 条留着一句话：**菜单级权限过滤** —— 基座导航零过滤。

它的现场表现是：审计员登进来，导航栏上有五个入口（含「日志控制台」「三维环境」），
点进去才吃 `40301`。这不是"少配了一条权限"，而是**导航栏在回答一个它答不了的问题**：

```java
// platform-portal/src/layouts/BasicLayout.tsx（改前）
{MICRO_APPS.map((app) => <NavLink .../>)}   // 整个数组渲染出来，没有过滤
```

而权限域里其实**早就为这件事留好了位置** —— `ResourceType` 里有 `MENU` 与 `PAGE`，
并且把这两类标成 `requestScoped = false`（不参与后端准入）。只是从来没有人建过这两种类型的资源行，
于是它们在库里恒为空。这与 `0030` 处理组织表的情形同源：**枚举认得它、规则里有它，但没有任何东西读它**。

要补的缺口因此是两步，而且**必须同做**：
① 登记菜单码与资源行（否则前端在等一个永远不会下发的权限）；
② 基座按它过滤导航（否则登记了也没人读）。

## 决策

### 1. `ui:` 是一个新权限域，它的性质与前所有域都不同

对应资源类型 `MENU` / `PAGE`。全文最重要的一句：

> **菜单码是布局，读权限是安全边界。**

它回答的是"导航栏上出现哪几个入口、应用内出现哪几个视图"，而**没有任何 `@RequiresPermission` 会写 `ui:*`**。
撤退一条菜单码只会让一个入口消失，**接口照样放行**。

因此菜单码**不是权限收窄工具**：想让某人看不见某个入口、又仍然允许他直接调接口，用菜单码；
想让他真的做不到某件事，只能动读写权限。反过来，**合并成一层**就会把"想让某人少看到一个入口"
升级成"真的收窄他的权限" —— 那是一次谁都察觉不到的静默越权收窄。

命名上也刻意与 URL **不同形**：资源标识是 `ui:admin` 这样的两段冒号串，
而它管的页面在 `/admin` —— 同形会诱使人去做字符串推导，而两者本来就允许不一致。

### 2. 两端各声明一份，靠同一串编码对齐，各由一个测试逐字钉住

菜单是**静态配置**，不是接口，因此**不进 OpenAPI**（跨端只认契约那条铁律管的是接口）。
于是跨语言互查没有低成本办法，只能：

- 后端 `AuthPermissions` 里的常量 + `AuthMenus`（新类，表达 `AuthPermissions` 表达不了的层级），
  由 `AuthMenuTaxonomyTest` 钉住；
- 前端 `common-api` 的 `menus.ts`（新文件），由 `menus.test.ts` 逐字钉住；
- 文档写明**改一个码要同时改两端**。

两端不一致的症状很难排查：后端改了、前端没改 ⇒ 前端在等一个永远不会下发的权限 ⇒
**那个入口永远不出现**，而所有人都会先去查"权限是不是没配"。

### 3. 菜单码必须登记进 `AuthPermissions.ALL`，且种子要分两途建资源行

`DefaultAdminSeeder.ensureResources()` 遍历 `AuthPermissions.ALL` 建种子资源行，
**它是种子数据的唯一来源**。因此漏登记的症状是"入口永远不出现"（不是"没有那一行"）。

建行分两途，因为两种资源形状不同：

| | 编码 | 父级 | 类型 | 名字 |
| --- | --- | --- | --- | --- |
| 接口资源 | 一码一行 | 无 | `API` | 编码本身 |
| 应用入口 | 一码一行 | 无 | `MENU` | 应用名 |
| 应用内视图 | 一码一行 | 应用码 | `PAGE` | 视图名 |

两者 `requestScoped` 都是 `false`，但**类型混了会让 `ResourceVO` 在后台显示一句反话**
（"此权限参与后端准入"）。页面码的 `parentCode` 写错则表现为资源树多一层嵌套。

新增测试特意**不断言"每个应用至少有一个页面"**：三维环境刻意没有页面级码（见第 7 条），
断言非空会把"刻意没有"与"漏写"判成同一件事。

### 4. 种子给两个内置角色补菜单授权，两份清单**分开写**

`AUDITOR_MENUS`（11 项）与 `AUDITOR_PERMISSIONS`（3 项）是两个常量，而不是合成一份。
理由：它们不是同类东西。合成一份会让后来的人把"撤销一条菜单码"误读成"收窄他的权限"，
而这两件事的后果完全不同（前者少一个入口，后者少做一件事）。

授权时两份清单汇合成一次 `grantResources`，但读的人能一眼看出一共有几项、各属哪一类。

### 5. 基座两步同做，且 `menuPermission` 做成**必填**字段

- 导航栏：`MICRO_APPS.filter((app) => permissions.includes(app.menuPermission))`；
- 路由层：`<RequireMenu permission={app.menuPermission}>` 包裹子应用路由，
  不通过则 `<Navigate to="/" replace state={{ denied: { path, permission } }} />`。

**只做第一条就是交付一个假开关**：导航栏看不见，地址栏照样进得去。
`RequireMenu` 嵌在 `RequireAuth` **之内** —— 两者问的不是同一件事
（前者"这个身份有没有这个入口"，后者"有没有身份"）。

`MicroAppMeta.menuPermission` 做成**必填**而非可选：可选字段会让漏填表现为
"**任何身份都看得见它**"，而那正好是这个改动要消灭的缺陷。必填会被编译器逼着回答"谁能看见它"。

`isMicroApp`（决定布局是否铺满）仍用**完整**的 `MICRO_APPS`：
它回答的是"这条路径属不属于某个子应用"（布局问题），不是"能不能进去" ——
没有菜单码的路径根本渲染不到那里，`RequireMenu` 已经把它重定向走了。

### 6. 概览页也要过滤，且被弹回时要指名说出缺哪一个码

概览（`/`）**不纳管权限**（任何已登录身份都看得到它，且它是被弹回时的落点），
但它列出的入口要过滤 —— 否则首页会成为整个应用里**唯一的"假开关集合"**：一堆点了就被弹回的卡片。

`RequireMenu` 重定向时带 `state.denied = { path, permission }`，概览读它并解释一句：

> 你没有进入 `/log-console` 的权限（需要 `ui:log_console:view`），已返回概览。

没有这段的话，敲一个没授权的地址表现为"什么都没发生"，而人只会怀疑应用坏了。
**骂人也要指名道姓。**

### 7. 三维环境**只有应用级码**，刻意不走页面级（推翻了动手前的设计）

动手前的计划是给它的五个场景各编一条页面级码。写到一半推翻，理由两笔：

1. 场景是**本地几何与材质**、不承载任何数据 ⇒ 关掉它保护不住任何东西 = **假开关**；
2. 它**当前没有、也不需要任何会话**（一个后端接口都不调）。引入认证链路后，
   "独立运行"那一支依赖后端可达 ⇒ 会**弄坏"后端没起时单跑看渲染效果"这个最常用的开发方式**。

它的应用级码 `ui:environment:view` 仍是真开关（导航栏上那个入口确实可以配）。
理由写在三处：`AuthResources` 的 `ui:` 段末尾、`AuthMenuTaxonomyTest`、
以及 `menus.ts` 里那段"刻意没有"的说明。

### 8. 应用内视图的拆分粒度跟着"能不能单独成立"走

- **日志台两栏**（演示 / 服务端查询）：它们的依赖本来就不同 ——
  左栏全在前端完成、不需要任何后端权限；右栏要读服务端库、能读到别人的报错正文。
- **详情抽屉跟着右栏走**：它展示的是服务端日志与链路，没有右栏就点不开它 ⇒
  单独给它一个码等于**造一个进不去的入口**。同理日志台不拆"链路"。
- **审计台三块**（流水 / 聚合 / 演练）：`DRILL` 与前两块性质不同（它会**写**），
  但它的按钮**刻意不做权限显隐** —— "越权尝试"本身就是要被记下来的事件。
  菜单码在这里只决定整块区域出不出现。
- **权限管理六个标签页**：顺序 = 授权链路的顺序（资源 → 角色 → 成员 / 用户组），
  「组织」排在最后，因为它回答的是另一个问题（"看得到哪些数据"而不是"能不能做这个动作"）。

**排序一致性是三处对齐的**：后端 `AuthMenus.ALL` 的声明顺序 = 前端 `menus.ts` 的顺序
= `App.tsx` 的 `TABS` 顺序 = 基座 `MICRO_APPS` 顺序。顺序不一致不会报错，
只会让"后台菜单目录"与"界面"看起来是两套东西 —— 真机脚本因此额外钉住了标签页顺序。

### 9. 权限 store 下沉到 `common-tools/micro`，并引入 `StandaloneIdentitySource`

`platform-admin` 与 `platform-audit-console` 各持有一份近似副本，当时是**有意留着的重复**
（`0026` 已记）。本轮要接五个子应用 ⇒ 再抄三份就是五份，触发条件（出现第三个消费方）到了。

下沉的是**与框架无关的那个内核**：

```ts
createPermissionStore(source: StandaloneIdentitySource): PermissionStore
```

`common-tools` 因此**不引 React**；"接到 `useSyncExternalStore`"那三行适配留在各子应用。

`StandaloneIdentitySource` 是新增的类型（`readStandaloneIdentity` / `onStandaloneIdentityChange`），
`ConsoleAuth` 现在实现它 —— 于是 `createPermissionStore(consoleAuth)` 一行接上。

**分支判据是"有没有宿主桥"而不是"有没有会话"**：用后者会把"还没登录"误判成"独立运行"，
进而自建第二套会话。这条同时出现在 `getAccessToken`、`readStandaloneIdentity`、
`getStandaloneSession` 三处。

`ready` 三态语义：`userId` 非空即表示权限集合**可信**（一个真的没有任何权限的已登录用户，`ready` 也是 `true`）。
`visibleViews()` 在未就绪时返回**空列表** —— "不确定"不等于"都可以看"。

### 10. 看不见的东西不发请求

三处：日志台右栏不可见时查询副作用**提前 return**（这时必然拿到 `40301`，白留一屏错误）、
上报副作用带上 `canReport`（一条看不见的管道仍在后台发请求，就是"假开关"那种味道）、
审计台的查询开关把菜单码一起算进去（`permission.ready && canRead && (showFlow || showStats || showDrill)`）。

新增的用例把这条钉成可断言的行为：`expect(mocks.page).not.toHaveBeenCalled()`。

### 11. 只剩一栏可见时收成单列

两个控制台都是固定两列 grid。过滤之后可能只剩一栏，而它会被按两栏比例挤在半边、
右边留一片空白 —— 看起来像"另一栏加载失败"。新增 `.layout--single` 修饰类。

日志台里 `--single` 与 `--with-drawer` 可能同时出现（只有右栏可见 + 抽屉打开），
那种组合是"内容 + 抽屉"两列，CSS 里单列一条 `.layout--single.layout--with-drawer` 规则。

## 发现但未处理

1. **`platform-user` 尚未创建** —— `MICRO_APPS` 里也不登记（注册一个加载不到的应用，
   只会在导航上多一个点了就报错的入口）。它的菜单码将来要在 `AppMenus` 与 `AuthMenus` 同时补。
2. **审计员的菜单码写在种子常量里，不是"默认策略"** —— 新租户 / 新账号一概**没有**任何菜单码，
   界面表现为"没有可进入的模块"。这是刻意的（默认不可见优于默认可见），
   但意味着"新建一个可用账号"需要显式授权菜单，管理面目前只能逐条勾选。
3. **概览页的卡片是过滤后的 `MICRO_APPS`，不是后端下发的菜单目录** ——
   菜单结构仍是两端各一份的静态配置。若将来出现"租户自定义菜单"，第 2 条那套"两端对齐"
   的假设会被推翻，届时必须改成后端下发结构，这个 ADR 的第 2 条要重写。
4. **`platform-environment` 独立运行不需要令牌**（它不调任何接口），
   因此它的菜单过滤只在**被基座加载**时有意义；单独跑时它是没有身份的，
   `usePermission` 一律为假。这一条目前不影响功能（它没有页面级码），
   但如果将来给它加了需要登录的功能，就要重新考虑第 7 条。
