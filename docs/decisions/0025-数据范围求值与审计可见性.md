# 0025. 数据范围求值与审计可见性：把 `data_scope` 接上第一个真实消费方，并修掉审计域的跨租户泄漏

- **状态**：已采纳
- **日期**：2026-10-12
- **决策者**：舰长

## 背景

`0022` / `0023` / `0024` 三份决策的「本决策未覆盖」里连续写着同一句话：
**`data_scope` / `filter_json` 只存不用**。一个角色可以配置"只能看本部门"，
配完之后系统行为毫无变化。这是本仓最不接受的一类东西 —— 一个看起来生效、
实际不参与任何判定的开关。

但"落地数据权限"要先回答一个更基础的问题：**过滤谁？**

把全仓的表列一遍（16 张）：`bw_auth_*` 14 张，加上 `bw_audit_log`、
`bw_client_log`、`bw_client_event`。**没有任何业务数据表** —— 订单、工单、设备、
工程都不在这里。这本身不是缺陷：本仓是一个**权限服务**（STS），
业务数据在别的系统里，靠这里下发的权限码与令牌做判定。

于是在当前仓里，"把 `data_scope` 翻译成 SQL 条件去过滤业务数据"这件事
**没有落点**。硬做的话只能造一个没人调用的求值引擎 —— 那是把"假开关"
换成"假的引擎"，性质一样。

与此同时，在摸审计域时发现了一个**真实缺陷**，而它恰好就是这个问题的第一个真实落点。

### 审计域：两条查询既没有租户条件，也没有范围判断

`AuditLogService` 的 `baseWrapper(resource, operatorId)` 只做两件事：
按请求方传入的 `resource` 与 `operatorId` 过滤。`AuditLogQuery` 里**没有 `tenantId`**，
Service 里也从不注入当前租户。后果：

1. 持 `auth:audit:read` 的账号，**把 `operatorId` 换成别人（或者干脆不传）**
   就能读到**其他租户**的审计记录 —— 而审计表的每一行都写着
   "谁、什么时候、做了什么事"，它是最不该跨租户可见的一张表；
2. **"看谁的记录"完全由请求方决定**。`operatorId` 长得像一个过滤条件，
   实际起的作用是"选一个主体"。

这两个问题在单租户的 e2e 里完全看不出来 —— 那套脚本只有一个租户，
所有断言都落在同一个租户内。

## 决策

### 1. 审计可见性由服务端决定，不由请求方决定

`AuditLogService` 新增 `visibility()`，三条查询路径（分页 / 详情 / 聚合）共用它。
规则只有两条，方向都是**收窄**：

- **租户强制等于当前登录者的租户**。这一条不是 `eq(条件, ...)` 那种可关的写法，
  而是无条件的 —— 审计记录没有"平台级"的概念，把它写成可选的，
  等于给"忘记传租户"留一个静默全量查询的口子；
- **操作者**：只有数据范围合并为 `ALL` 时才可由请求方指定，否则强制等于当前登录者。

配套：`AuditLogMapper.countByAction` 加**必传**的 `tenantId`。
它只差一个 `WHERE` 就能从"本租户的动作分布"变成"全库的动作分布"，
而因为它返回的只是计数，越权了几乎不会被察觉。

### 2. 详情跨租户返回 `404`，不是 `403`

`detail(id)` 原来直接 `selectById` 就返回。现在校验
`entity.tenantId == 当前租户`（以及 SELF 档下 `operatorId == 自己`），不满足则 404。

用 404 而不是 403：**403 等于向调用方承认"这条记录确实存在，只是不给你看"**。
而对审计记录来说，连"存在"这件事本身都不该跨租户泄漏。
这条与 `0021` 里"重建同码撞唯一键时复活原记录"是同一类思路：
**不该让别人能从错误码里读出信息**。

### 3. `operatorId` 降级为"在可见范围内进一步收窄"

SELF 档下，请求方传进来的 `operatorId` 被**整体忽略**，查询强制落在自己身上；
而不是"与当前用户不相等就报错"。

后者会把一次越权尝试变成一个**可观测的 403**，而它本该安静地返回调用方
自己有权看的那一份。"被忽略"与"筛出一个空结果"在调用方看来必须是同一件事的
两种说法，实现选的是前者（`Visibility.operatorFilter`）。

### 4. 合并规则：取最宽

一个人可能同时持有多个角色，各带各的 `data_scope`。合成的结果取**最宽**的那一档 ——
权限是并集，范围也是：授一个更宽的角色的效果，不该被另一个更窄的角色抵消。
写反的后果（取最窄）表现很隐蔽：**"给他加了个新角色，他反而看得更少了"**，
而所有单角色用例都会通过。

`DataScope` 枚举为此新增 `rank()`。五档的序：

```
ALL(5) > DEPT_AND_CHILD(4) > DEPT(3) > CUSTOM(2) > SELF(1)
```

数值本身没有含义，只有大小关系有。`CUSTOM` 的位置是刻意的**任意** ——
一个自定义条件可能比"本部门"宽也可能更窄，它与其他档位无法比较。
把它放在组织范围与 `SELF` 之间，是因为它至少是一个**显式配置的条件**，
而 `SELF` 是"什么都没配"时的安全默认，显式配置应当赢过默认。

### 5. `selectRoleCodes` 升级为 `selectEffectiveRoles`，而不是新增第三条 SQL

数据范围与角色编码来自**同一组角色**，也就共用同一套生效判定
（角色未删未停用、成员关系未删、两层时态都落在区间内）。
另开一条只有一列不同的查询，就要把那串六七行的条件写第二遍 ——
而两遍一旦漂移，症状是"角色查得到、数据范围查不到"，两边各自的测试都通过，
合起来才不对。

顺带的一个好处：返回类型从 `List<String>` 变成 `RoleScopeView`，
让"这个数据范围是从哪个角色来的"成为一个可以直接回答的问题。

### 6. "已配置"与"已生效"必须分开：`precise` 标记

`UserDataScopeVO` 里有一个 `precise` 字段，含义是**这一档能不能被精确求值**：

| 档位                         | `precise` | 为什么                                              |
| ---------------------------- | --------- | --------------------------------------------------- |
| `ALL` / `SELF`               | `true`    | 自足：一个说"整个租户"，一个说"只有我"              |
| `DEPT` / `DEPT_AND_CHILD`    | `false`   | 需要"谁的部门是哪个"—— 组织归属表已有、接口未落地   |
| `CUSTOM`                     | `false`   | 需要解析 `filter_json` 的表达式                     |

**没有这个标记，"配了 `DEPT` 但还算不出来"与"就是 `ALL`"长得一模一样。**
这正是 `0022` 里 `requestScoped` 那处教训的同一类问题：派生字段要么显式说出来，
要么就会被人当成它不存在。

### 7. 算不出的档位往**窄**兜底，不往宽

`currentRequestSelfOnly()` 的实现是 `!resolveForCurrent().isAllData()` ——
**只有 `ALL` 返回 `false`**，取非 `ALL` 的全部档位（含 `DEPT` 系列与 `CUSTOM`）
都返回 `true`（收窄到本人）。

理由：反过来的选择（算不出就当 `ALL`）会让"配了一个还没实现的范围"
变成一次**静默的越权** —— 用户以为自己配的是"本部门"，实际拿到的是"全租户"，
而这两种结果在界面上都不会报错。收窄则最坏只是"少看了几条"，
是可解释、可修正的。

同理，**没有任何档位时返回 `scope == null` 而不是 `ALL`**：
"没配数据范围"与"配了全部数据"是两件事。

### 8. 求值器复用判定链，不自己写一套"什么算生效"

`DataScopeService` 取有效角色走的是 `AuthorizationMapper.selectEffectiveRoles`，
与"有哪些权限码"是同一套过滤。若数据范围用另一套定义，会出现
"有权限但范围变了"这种无法解释的组合。

因此也继承了 `0022` 修的几处缺陷：**停用的角色不贡献数据范围**。
这条有专门的用例 —— 若漏掉，症状是"停用角色只停掉了权限、没停掉范围"，
而**看得见全部数据却做不了操作**，恰恰是比"能操作但看不到"更危险的那一半。

### 9. 不返回"可见组织 id 集合"这类看似更有用的字段

本期没有任何一处查询会消费它。返回一个恒为空的集合，比不返回更糟 ——
调用方会以为"这个人的可见组织就是空的"，而真实原因是"这个字段还没实现"。
等组织归属落地、真有查询要按它过滤时再加，那时它有确切的语义。

### 10. 反查接口归 `auth:user:read`，与角色反查同

`GET /api/auth/users/{id}/data-scope` 读的是"某个用户"的信息，
与 `/{id}/roles`（`0024`）同类，因此同样归 `auth:user:read`、
同样不标 `@Audited`（它是查询）。

于是**审计员也看得见它，但对用户组管理一律 `40301`** ——
这条差异在测试里被刻意保留，说明这两个决定是分开做的。

## 后果

- **接口 +1**：`GET /api/auth/users/{id}/data-scope`（34 → 35 路径，54 → 55 接口）；
- `data_scope` 从"只存不用"变成**有真实消费方**（审计查询），并且这个消费方
  是安全方向的（越权读数据，而不是显示错误）；
- **审计域的跨租户泄漏被修掉**，且修复方式是可测的（造一条别的租户的记录，
  验证列表 / 聚合 / 详情三条路径都挡住）；
- `DataScope` 枚举从"只落地字段"变成"有合并语义与精确性标记"，
  后续要给 `DEPT` 系列补求值时，入口已经在这里，不必再问一遍"合并规则是什么"。

## 本决策未覆盖

- **业务数据的数据权限**。本仓没有业务数据表，`data_scope` 的价值最终要在
  业务系统里兑现。本决策只交付了"求值 + 下发"，没有交付"过滤业务数据" ——
  后者需要一个有业务数据的仓。
- **`DEPT` / `DEPT_AND_CHILD` 的精确求值**。需要组织管理接口先落地
  （`bw_auth_organization` 已有 `code_path` 列，正是为子树查询预留的）。
- **`CUSTOM` 的 `filter_json` 表达式解析**。格式、求值时机、注入风险都未讨论。
- **组织管理接口**（`bw_auth_organization` + `bw_auth_rel_org_user`）。
  表、实体、Mapper 都已就绪，缺 Service 与 Controller。
- **动态用户组求值**（`filterJson` / `orgScopeJson`），见 `0024` 第 2 条。
- **另外两条管道的可见性**：`bw_client_log` / `bw_client_event` 同样只有租户维度，
  同样没有按数据范围过滤。它们的可见性规则要不要与审计一致，没有讨论。

## 发现但未处理（供后续决策）

1. **`bw_auth_rel_org_user` 是第三处成员关系**，但它的形状与前两处**不一样**：
   `rel_role_member` 与 `rel_user_group_member` 都是多态表（`member_type`），
   而它是专用的两列（`organization_id` + `user_id`），还带
   `is_primary_position` / `position_name` / `relation_type`。
   它的语义也更接近"归属"而非"授予"（一个人必须有部门，而角色可以一个都没有）。
   因此 `0024` 里"第三处成员关系出现时把三份成员 VO 下沉"的触发条件
   **只满足了一半** —— 下沉的目标形状需要重新想，不能照搬。
2. **组织表已就绪但零接口**：`bw_auth_organization` 有 `code_path` / `has_child` /
   `org_level` / `manager_id`（+ 冗余的 `manager_name`），
   `OrganizationMapper` 只有继承来的 CRUD。补它是 `DEPT` 系列的前置。
3. **审计的时间窗与 `resource` 过滤仍是纯查询参数**，没有"必传"约束。
   本期只处理了"可见性"这一类参数，没有动"过滤条件"那一类 ——
   两者的区别是：前者决定**能看到什么**，后者只决定**看到的那部分里挑哪些**。
