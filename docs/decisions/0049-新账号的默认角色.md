# 0049. 新账号的默认角色：激活 `bw_auth_role.is_default`

- **状态**：已采纳
- **日期**：2026-10-14
- **决策者**：舰长

## 背景

这一轮的起点是一个提案：**"针对不同的租户添加配置开关，由租户管理员决定需不需要默认角色。"**
它要解决的是 `0031` 那句"新账号一概没有菜单码"的下游后果 —— 新账号登进去一片空。

方向是对的：`0048` 里我提过一个陷阱（"共享的默认角色会让'收回某人的入口'变成改共享角色，
影响所有人"），而"每个租户各配各的"正好化解它 —— 角色本来就带 `tenant_id`，
两个租户各标各的，互不牵连。

但动手前核了几件事，其中三件**改变了落点**。

### 一、租户级配置开关这个模式已经存在 —— 而且它是空的

`bw_auth_tenant` 上早就有两列（`V3__create_bw_auth_tables.sql`）：

```sql
allow_register TINYINT DEFAULT 0 COMMENT '是否允许自助注册：0 否 1 是',
allow_add      TINYINT DEFAULT 0 COMMENT '是否允许下级创建租户：0 否 1 是',
```

逐层核对：

| 层面 | `allow_register` / `allow_add` |
| --- | --- |
| 数据库列（三方言） | 在 |
| 契约 + 生成类型 | 在 |
| 后端写入 / 回显 | 在（`TenantService.create/update` 写它，`toVO` 回显它） |
| **有任何逻辑读它** | **全仓零调用** —— `getAllowRegister()` / `getAllowAdd()` 无人调 |
| **界面上有开关** | **不在** —— 租户表单只有"租户编码 / 名称 / 描述"三个字段 |
| 它描述的那个动作是否存在 | `allow_register` 描述的动作**不存在**：auth 域没有注册端点，`grep -rni register` 在 main 代码里只命中它自己 |

也就是说：**生产者（界面）与消费者（判定逻辑）两头都空，只剩中间那截管道。**
这是那一族缺陷里的又一种形状，而且比前几种更彻底 ——
`0045` 是"写了没调用"，`0046` 是"位置错了"，`0047` 是"没有名字"，`0048` 是"没有入口"，
这一种是**契约里的空位**。它连"假开关"都算不上（假开关至少有个能被点的东西）。

### 二、`bw_auth_role.is_default` 不是空位，是半成品 —— 而且它有档案

准备动 `default_role_id` 时发现角色表上已经有一列：

```sql
is_default TINYINT DEFAULT 0 COMMENT '是否默认角色（新用户自动授予）：0 否 1 是',
```

它的状态与 `allow_register` **完全不同**：

| 层面 | `bw_auth_role.is_default` |
| --- | --- |
| 数据库列（三方言） | 在，注释明写"**新用户自动授予**" |
| 后端写入 | 在（`RoleService` 的 `flag(...)` 归一化 + 更新同步） |
| 入口校验 | 在，且**有专门用例**：只接受 0/1（`RoleApiTest` 里那条"`isDefault=7` 这类值放行不会报错，只会静默改变语义 —— 必须在入口挡住"） |
| 契约 / VO / 种子 | 都在（种子写 `setIsDefault(0)`） |
| **那个行为本身** | **`getIsDefault()` 全仓零消费** —— 没有任何一处读它去授予角色 |
| 界面 | 不在，而且是**有档案的刻意留白**（见下） |

`bw_auth_user_group.is_default`（注释"是否默认用户组"）是同样的形态。

**"刻意不摆"这件事本身是有记录的。** `platform-admin/src/pages/Roles/index.tsx` 的表单边界
注释原文把它列在"不进表单"那一类里：

```
 *   <li><b>继承策略</b>（inheritStrategy）、<b>默认角色</b>（isDefault）、
 *       filterJson 一律不进表单：只存不用的字段不给它配的样子，
 *       否则管理员配完以为生效、排查时才发现从来没被读过。
```

理由是对的（"配了不生效" 比 "看不见" 更坏），只是它描述的是**当时**的状态。

### 三、同一件事，两句相反的话，写在两份文档里

`0022` 决策 11 的原文：

> - **严格**：`status` 走 `Status` 枚举、`dataScope` 走 `DataScope` 枚举、
>   `isDefault` 只接受 `0/1`、`effectiveFrom < effectiveTo`。
>   **理由：这些值会被判定链路读取**，写错不报错，只会静默改变行为。

而同一时间，`RoleSaveRequest` 的 `@Schema` 与 `docs/api/README.md` 都标着"**当前只存不用**"。

**两句相反的话，隔 98 行写在两份文档里，各自被读过，但从没被放在一起读过。**
按 `0022` 自己的判据（"有判定语义的字段严格校验"），`isDefault` 当时**不该**被严格校验 ——
它没有读取方，属于"宽松接受"那一类。它之所以被列进去了，是**顺带**：
它和 `status` / `dataScope` 都是开关形状，就被一起归了类。

这不是笔误，是一种更常见的错法：**按形状归类，而不是按判据归类** ——
而形状相同的两个字段，语义可能一个已经落地、另一个还是空的。

### 四、"由租户管理员决定"在本仓要翻译成什么

租户是真的，而且是**树形**的（`parent_id` / `tenant_level` / `code_path` / `has_child` / `status`），
用户 / 角色 / 组织 / 各关系表都带 `tenant_id`。但**"租户管理员"不是一个已存在的概念**：
种子只有两个角色（`admin` 带 `data_scope=ALL`、`auditor`），权限是扁平的 `auth:tenant:*`，
而数据范围的求值 + 下发虽已完成，`docs/api/README.md` 明写它的消费方只有一个：**审计查询**。

于是"由租户管理员决定"落到今天的代码上，实际是"由持有 `auth:tenant:update` 的人配 ——
而那个人能改**所有**租户，没有租户内隔离"。这条要如实写在文档里，不能让它读起来像已经隔离了。

## 决策

### 1. 承载字段用 `bw_auth_role.is_default`，而不是新加 `tenant.default_role_id`

它就是**为这件事造的**：字段注释原文"新用户自动授予"。新加一个字段的代价是仓库里
同时存在两个都说"新用户自动授予"的字段且语义打架 —— 而排查这类问题时，
"到底哪个在生效"会是最先被问、又最难答的一句。

顺带也解决了粒度的差别：`is_default` 天然支持**一个租户多个默认角色**
（多个"起步配置"），而租户上一个 `default_role_id` 只能有一个。

### 2. "由租户决定"靠 `tenant_id` 自然成立，不新增配置项

默认角色的查询是 `WHERE tenant_id = ? AND is_default = 1 AND status = 'ENABLED'`。
每个租户各标各的角色 —— **不需要在租户表上再加一个开关**，
"这个租户有没有默认角色"就是"这个租户有没有 `is_default = 1` 且启用中的角色"。
一个字段同时表达"开没开"与"开的是哪个"，没有两个字段不同步的余地。

### 3. 停用的默认角色自动退出默认集合

查询限定 `status = 'ENABLED'`，两个理由：停用的角色本就不产生权限（判定要求 `ro.status = 'ENABLED'`），
挂上只留下一条"不产生效果的关系行"；更要紧的是**"默认角色"的语义是"新账号的起步配置"，
一个被停用的角色不该是任何人的起步配置**。

这同时给了租户一种"暂时不给新账号任何角色"的表达方式 —— 但**更该用"取消勾选"来做**：
停用会连带让所有已持有该角色的人一起失去权限，副作用比它看起来大得多。这条写进了表单提示。

### 4. 复用 `RoleMemberService.bind`，不另写一套插入

"把角色授给一个人"只能有一份实现。`bind` 承担着 upsert、复活软删行、清同键冗余行三件事；
新用户确实不可能撞上那三种情况 —— 但**这个保证依赖于调用方，而 `bind` 自己持有它**。
复制一份出来，就会在将来某次改动里分头漂移。

注入方向是 `UserService → RoleMemberService`（`RoleMemberService` 只依赖 4 个 Mapper，
不依赖 `UserService`，所以不成环）。

### 5. 授予与建号在同一个事务里，失败不吞

建号成功而授予失败会留下一个"看起来建好了、却没有起步角色"的账号 ——
而它与"这个租户本来就没配默认角色"在界面上**完全同形**。因此异常照常抛出，整笔回滚。

### 6. 不记审计，但记一条 `log.info`

判据沿用"事后要不要问"：建号这条路上已有 `auth.user.create`，逐条记
`auth.role.grant_member` 会产生 N 条"同一个人、同一秒、同一个对象"的记录，
而它们在审计面板上无处区分。但审计只回答得了"谁建了这个号"，
答不了"它一出生就带着哪些角色" —— 那一句留在日志里。

### 7. 接口如实返回"授了哪些"

`UserVO` 加 `defaultRoleNames`（**仅 `POST /api/auth/users` 这一个响应里非空**：
授出的角色名，按角色主键升序；**空数组**表示该租户没有启用中的默认角色）。
其余三条路（列表 / 详情 / 更新）返回 `null`。

它是**那次动作的结果**，不是用户的属性。"出生时带着什么角色"只在建号那一刻有意义，
此后角色可被改无数次；属性视角的问题由 `GET /api/auth/users/{id}/roles` 回答（还带"经组获得"的来路）。

**没有它，`0048` 刚补的那句建号通知会变成假话** —— 它写着"该账号默认没有任何菜单码"，
在配了默认角色的租户里这句是错的，而且会把管理员指去重复做一件已经做完的事。
管理台的通知按它分岔。

### 8. 空数组与 `null` 分开，是有意的

两者表达的是不同的事：`[]` = "这次没授出去任何东西"（该提示下一步），
`null` = "这条接口不表达这件事"。混成一个 `null`，那句通知就失去了判据。

### 9. 角色表单把它摆出来 —— 顺序是"先实现、后摆"

`0048` 立过一条："表单只摆出**配了真的会生效**的字段"。所以这一列不是被"放开"的，
而是**先补上了消费方，那条界线自己把它纳了进来**。
反过来做（先摆出来、后实现），它就是下一条 `CUSTOM` —— 而 `CUSTOM` 至今还挂在
数据范围下拉的历史值里，是个现成的反例。

同时订正 `RoleSaveRequest` 与 `RoleVO` 两处 `@Schema` 的"当前只存不用"（改成事实）。
**`0022` 决策 11 的原文不回改** —— 那句话当时是错的（前提为假），
现在恰好成立；改旧文会让"当时为什么这么写"这段信息消失。

### 10. `allow_register` / `allow_add` 留着，只在这里记一笔

三个选项（清掉 / 留着 / 清 `allow_register` 补 `allow_add`）里选了最保守的一个。
代价是契约里继续有两个没人读的字段 —— 但它们现在**有档案了**：
这份 ADR 就是"为什么留着"的答案，而在此之前，下一个读契约的人仍会以为它们生效。

（`allow_add` 描述的"限制下级创建租户"是**可以真实现**的，补它不需要新字段。
`allow_register` 描述的动作则根本不存在 —— 要让它成真，得先有"忘记口令"那条不依赖登录态的
信任通道，见 `0048` 未覆盖。）

## 后果

**正面**

- `bw_auth_role.is_default` 从"半成品"变成真开关：**它有消费方了**，
  且这个消费方正是它注释里写的那件事。
- `0031` 决策 2 的下游后果有了一个不推翻它自己的解法：默认仍是"默认不可见"
  （不配就是没有），要"默认可见"的租户自己去标 —— **由租户决定，而不是由代码决定**。
- `0048` 那句建号通知不再会变成假话。
- 新账号的"起步配置"从"建号 + 另外一步授权"变成一次建号。

**负面 / 代价**

- 建号这条路上多了一次角色查询与 N 次关系写入，且**全部落在同一个事务里**：
  建号变慢了，而且默认角色配错时会连建号一起失败（这是决策 5 换来的：宁可失败可见）。
- 契约里 `UserVO.defaultRoleNames` 是个"只在一处有值"的字段。
  它会让读契约的人先困惑一下 —— 判据写在字段注释里，但注解挽不回第一眼。
- `allow_register` / `allow_add` 继续空着。

**后续约束**

- 新建的自动授予**只影响之后**新建的账号，不追溯已建账号。
  "改配置会改到谁"这条边界必须能被验证 —— 有用例钉住。
- 想"取消默认角色"必须**显式传 `isDefault: 0`**。契约里它是非必填的 `Integer`，
  后端按"字段是否为 `null`"决定要不要 `SET` 这一列 ⇒ 传 `undefined`（= 不带这个键）
  在更新语义里是"不改这一列"，会让取消**静默失效**。前端表单有一处注释与一条用例钉住它。
- 角色表单里多行提示文案的**每一行都要有东西隔开**（`<br />`）。
  JSX 会把同一段文本里的换行折成一个空格，prettier 还会按 `printWidth` 重新折行 ——
  `0048` 踩过一次，这一轮又踩了一次（第一版渲染出"只存不用， 是"）。

## 未覆盖

- **"租户管理员"与租户内数据隔离**：本轮的"由租户决定"实际由持有 `auth:tenant:update`
  的人执行，而该权限**没有租户内隔离**（持有者能配所有租户）。要做真隔离，
  得先新建一个 `SYSTEM` 分类的租户管理员角色、并把 `DataScope` 接进 auth 域自身的查询
  （目前只有审计查询消费它），还要先回答一条语义问题："租户内能不能改自己的租户配置"。
- **自助注册**（`allow_register` 描述的动作）：不存在。
- **`allow_add` 的真实现**：存在但没做。
- **默认角色对已建账号的追溯**：不做（与"角色"-"成员"关系一致，改配置只影响之后）。
- **"该租户没配默认角色"与"配了的都已停用"在响应里分不出**：两者都返回空数组。
  管理台的通知因此把两种原因都写出来，而不是替用户认定一个 ——
  认定的那个会让他去错的地方找。要分开，得再给响应一个字段。
- **`bw_auth_user_group.is_default`（"是否默认用户组"）仍是只存不用**：
  与角色那一列同形，本轮没有动它。它的消费方应当是"新建用户自动进哪些组"，
  而那与"自动获得角色"是两件事（经组获得的角色会多一层时态，见 `UserRoleVO`）。
- **"新账号能用"是两段拼起来的**：默认角色本身不带任何资源授权，
  "建号后能看到什么"仍取决于该角色被授了哪些资源。本轮只保证前一段 ——
  配了默认角色但那个角色一个菜单码都没授，新账号照样看不到入口，
  而这时"默认角色配了、为什么还是空的"会比没配时更难排查。
