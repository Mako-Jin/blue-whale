# 0066. 搜索的匹配语义 —— 一个从没被决定过、而被 `V8` 顺手改掉的关系

- **状态**：已采纳
- **日期**：2026-10-15
- **决策者**：舰长

> 领的是 `0065`「未覆盖」第 3 条：**前端侧的相等语义没查** ——
> "`platform-admin` 的用户页会不会按邮箱 / 手机号做本地过滤（`includes` / `filter`）？
> JS 的 `===` 与 `includes` 本来就是大小写敏感的，与后端现在的语义一致，
> 但那是一句**巧合**，没有人核过，也没有守卫。"
>
> 核完发现**那句话的前提不成立**：前端**一处本地过滤都没有**。全仓
> `toLowerCase` / `toUpperCase` / `localeCompare` 一共只出现 11 次（含用例），
> 非测试的只有两处 —— HTTP 请求头的**大小写无关查找**与日志标题的**显示**大写；
> 对 `email` / `phone` 的**比较是零处**。六个搜索框（用户 / 用户组 / 租户 /
> 角色 / 资源 / 组织）全都把 `keyword` **发给后端**，前端只做 `.trim()`。
>
> 但顺着"那到底是谁在比"查下去，撞出一个 `0065` 没料到的口子：
> **搜索走的是 `LIKE '%kw%'`，而 `LIKE` 的敏感性同样跟着列排序规则走** ——
> 于是 `V8` **顺手把搜索也改了**（MySQL 上从"不敏感"变成"敏感"），
> 而"搜索该不该区分大小写"这件事，本仓**从来没有决定过**。

## 背景

### 1 前端：零本地过滤（实测，不是"没找到"）

这是一次**否证**，证据要写足，否则下一个人还得再查一遍：

| 扫的东西 | 结果 | 说明 |
| -------- | ---- | ---- |
| `toLowerCase` / `toUpperCase` / `localeCompare`（全仓，含用例） | **11 处** | 非测试的 2 处：`common-tools/http/client.ts:57`（HTTP **头名**的大小写无关查找）、`common-tools/logger/logger.ts:264`（日志标题**显示**用大写）；其余在用例里 |
| 对 `email` / `phone` 的**比较**（`===` / `==` / `.includes`） | **0 处** | 它们只被"回显"与"提交"，从不参与判断 |
| 前端 `.filter` / `.includes` / `.startsWith` / `.indexOf` 的落点 | 全部是权限码、className 拼接、树节点 id、按键码（`Arrow`）、URL 前缀 | 没有一处是对**用户记录**的文本筛选 |
| 页面对 `keyword` 的处理 | **只有 `.trim()`** | 然后原样放进请求参数 |

于是 `0065` 担心的那个"巧合"**根本不成立** —— 不是因为巧合成立了，
而是因为 **JS 的比较根本没有参与**。前端是纯"透传 + 渲染"。

顺带更正一处表述：`0065`「未覆盖」3 写的是"前端侧的相等语义没查"，
准确的写法是 **"前端没有相等语义可查"**。旧文按本仓惯例不回改，以本篇为准。

### 2 真正的暴露面在后端：`LIKE`

六个搜索入口（用户 / 用户组 / 租户 / 角色 / 资源 / 组织）都走同一形状：
`Query` 里一个 `keyword`，Service 里一串 `like(列, keyword)` 用 `or()` 连起来。
唯一一处用户侧的实例如 `UserService#page`：

```java
.and(query.getKeyword() != null && !query.getKeyword().isBlank(), w -> w
        .like(UserEntity::getUsername, query.getKeyword())
        .or().like(UserEntity::getDisplayName, query.getKeyword())
        .or().like(UserEntity::getEmail, query.getKeyword()))
```

`LIKE` 是**模糊匹配**，不是等值 —— 但**它的敏感性同样由列排序规则决定**。
所以 `V8`（把 13 张表转成 `utf8mb4_0900_as_cs`）不可能只改等值面而放过它。

## 一 实测：`LIKE` 跟着列排序规则走（两台引擎、同一段 SQL）

探针表按 `V3` 里 `bw_auth_user` 的形状建，存一行 `username = 'admin'`、
`email = 'Admin@Example.com'`：

| 探针                                | H2 2.4.240 | MySQL `_ai_ci`（**改前**） | MySQL `_as_cs`（**改后**） | `_bin` |
| ----------------------------------- | ---------- | -------------------------- | -------------------------- | ------ |
| `username LIKE '%ADMIN%'`           | **0**      | **1**                      | **0**                      | 0      |
| `username LIKE '%admin%'`           | 1          | 1                          | 1                          | 1      |
| `email LIKE '%ADMIN@%'`             | **0**      | **1**                      | **0**                      | 0      |
| `email LIKE '%Admin@%'`             | 1          | 1                          | 1                          | 1      |

两句话：

1. **改前两个 profile 在搜索上是分歧的**（MySQL 不敏感 / H2 敏感）——
   这比"等值面分歧"更早、更容易被人碰到：搜索框是每天在用的东西。
2. **`V8` 把两边对齐了，而且对齐的是"敏感"那一侧。** 这是那次改动的
   **顺带结果**：`V8` 的设计意图是等值面（登录、判重、唯一索引），
   搜索是被同一张排序规则带过去的。它没有被写进 `0065`，也没有任何用例。

## 二 决策：搜索与等值共用同一条关系

**就让它跟着走 —— 搜索也区分大小写。** 三条理由：

- **它已经是一致状态，且零方言差异。** `V8` 之后 h2 / mysql 在搜索上给同一答案；
  反过来（把搜索做成不敏感）要在六个入口上显式写 `LOWER()`，而且 **h2 与 mysql 都得写** ——
  那是**故意**再造一处"两方言必须人工保持同构"的语义，与本仓对 `0038` 的用法背道而驰。
- **结果不误导。** `0065` 之后 `admin` 与 `Admin` 是**两个不同的账号**，
  搜 `ADMIN` 找到的是**名叫 `ADMIN` 的那个**。搜索给的是"字面命中"的记录，
  没有撒谎；它只是不替用户扩大匹配。
- **搜索的六个入口里有四个半搜的是"编码/标识"**（`resource_code` 是
  `域:资源:动作` 三段、`*_code`、登录名），**大小写本来就是它们的一部分**；
  姓名与中文则根本无大小写可言。跟着列走是唯一一条同时覆盖两类的规则。

**代价是明确的**：MySQL 上此前"输入 `ADMIN` 也能搜到 `admin`"这种便利没有了。
写进「后果」，并由 `SearchMatchApiTest` 钉成断言 —— 不是一句承诺。

## 三 守卫：`SearchMatchApiTest`（跨 profile）

新增 `SearchMatchApiTest`，2 例，与 `TextEqualityApiTest` 同形：
**不 `@Transactional`、不按 profile 跳过** ⇒ 同一批断言在 h2（`server` job）
与真实 MySQL（`server-mysql` job）上各跑一遍。本仓**第二处**跨 profile 的语义断言。

- `shouldSearchCaseSensitively`：建一个大小写混写的号（登录名与邮箱共用同一段前缀）
  ⇒ 原样搜得到、`toLowerCase()` 搜不到（断 `total == 0`）。
- `shouldNotFindTheSeedAdminUnderADifferentCase`：**直接拿种子账号**（两个 profile 都种）——
  `admin` 搜得到、`ADMIN` 搜不到。这一例是"用户真的会去搜的那个串"，也最直观。

**为什么"搜不到"那一支才是关键**：只断言"大小写一致时搜得到"的话，
一个**不敏感**的库也会绿（它的匹配集是超集）。要分开两种语义，
必须把**"换个大小写就搜不到"**写出来 —— 那是两种语义**唯一**不同的那一格。

**扰动验位（当次实测）**：把 h2 的 `username` / `email` 临时改成
`VARCHAR_IGNORECASE`（把 H2 变成"搜索不敏感"）⇒ 两例**双双变红**
（都是 `expected: <0> but was: <1>`）；改回后 2 例全绿。

## 决策

- **搜索沿用列排序规则 —— 跟着等值一起区分大小写。** 不改任何代码：
  这是 `V8` 之后已经成立的语义，本篇是把它**从"顺带"变成"决定过"**。
- **`0065`「未覆盖」3 关闭**，且结论是**否证**：前端没有相等语义可查
  （零本地过滤），暴露面在后端 `LIKE`，由本篇接手。
- **新增 `SearchMatchApiTest`（2 例）**，跨 profile 跑，钉住这条语义。
- **零接口形状改动**：不动列、不动错误码、不动 OpenAPI 契约、不动前端。

## 后果

**正面**

- "搜索框怎么比"第一次成为**被写下、并且被两个引擎各验一遍**的事。
- 一处**此前没人发现的 profile 分歧**被 `V8` 顺带消掉，现在有了断言守着，
  不会再漂回去。
- `0065` 那条未覆盖的**真结论**（前端零本地过滤）被记下来了 ——
  下一个人不必再扫一遍 `toLowerCase`。

**负面 / 代价**

- **MySQL 上搜索变严格了**：输入 `ADMIN` 搜不到 `admin`。
  用户可能把它读成"这个账号不存在" —— 而**它确实存在，只是字面不同**。
  这是本轮唯一一处用户可见的行为变化，方向是"更严格"。
- **搜索与等值同源，将来想放宽就要成对改**：见「未覆盖」第 1 条。

**后续约束**

- **加一处搜索框时不需要做任何事**：`keyword` 照原样发给后端即可，
  语义由列排序规则统一决定（不要在前端做本地过滤 —— 那会制造第二套语义，
  而前端没有任何守卫会发现它）。
- **断言"搜索匹配/不匹配"的用例，照 `SearchMatchApiTest` 的形状写**：
  必须含"换个大小写搜不到"那一支，否则不敏感的实现也能绿。

## 未覆盖

1. **`LIKE` 的通配符没有被转义。** `keyword` 是原样拼进 `LIKE '%…%'` 的，
   所以用户在搜索框里输入 `%` 或 `_` 会被当成**通配符**（输 `%` = 匹配一切）。
   机制是确定的（MyBatis-Plus 的 `like` 不转义实参），但**本轮没有改** ——
   它是一次独立决定，且要先定"是转义、还是干脆禁止这两个字符"。
2. **只有用户域有断言**，其余五处（用户组 / 租户 / 角色 / 资源 / 组织）
   的搜索语义仍是"因为用同一张排序规则所以相同"的**推断**，没有各自的用例。
3. **达梦未实测**（同 `0065`）：达梦的 `LIKE` 是否与它的等值面一样是二进制比较，
   没有实例可验。
4. **前端"不做本地过滤"没有守卫。** 它是一条纸面约定 —— 而按 `0064` 的判据，
   要机械化它得解析 JSX 树（判断某个渲染位有没有挂 `filter`），属"会误报"那一类，
   故**刻意不加守卫**，只在此登记。
5. **搜索的可观测性没定**：现在无法回答"哪个关键词被搜了、搜空了"。
