# 0024. 用户组管理与成员关系归属：配置侧的最后一块，连带修掉判定侧第五处静默缺陷

- **状态**：已采纳
- **日期**：2026-10-12
- **决策者**：舰长

## 背景

`0023` 交付角色成员关系后，RBAC 判定链的配置侧只剩两个缺口，
而且它在 `0023` 的「本决策未覆盖」里被点名留下：

- **用户组没有任何管理接口**。`bw_auth_user_group` 有实体与仓储、没有服务与接口；
  `bw_auth_rel_user_group_member` 有实体与仓储、没有任何写入路径。
  `0023` 用测试夹具验证了组链路（用户 → 用户组 → 角色 → 资源），
  但那**是夹具不是接口** —— 这一段关系至今无法由任何人经界面配置。
- **没有反查接口**。`GET /api/auth/users/{id}/roles`（"这个人的权限是从哪个角色来的"）
  是排查权限问题时最常用的入口，它天然要跨越"直接授予"与"经用户组授予"两个来源。

本决策把这两件一起交付。组与反查是同一批的事：反查的一条来源就是用户组，
把组的管理接口与它拆开做，反查那一侧就只能永远返回"经组"的来源为零。

实现过程中又逮到判定侧的**第五处静默缺陷**（见第 4 条），一并修掉。

## 决策

### 1. 用户组的八个路径，成员子资源挂在组下

```
GET    /api/auth/user-groups                                      查用户组（分页）
GET    /api/auth/user-groups/{id}                                 查用户组详情
POST   /api/auth/user-groups                                      新增用户组
PUT    /api/auth/user-groups/{id}                                 修改用户组
DELETE /api/auth/user-groups/{id}                                 删除用户组
GET    /api/auth/user-groups/{id}/members                         查组成员（分页）
POST   /api/auth/user-groups/{id}/members                         把用户加进组
DELETE /api/auth/user-groups/{id}/members/{memberType}/{memberId} 把用户移出组
```

与角色的两条关系边（`/roles/{id}/resources` 与 `/roles/{id}/members`）是**完全同一条判断**：
成员关系是用户组的内部边，没有脱离组独立存在的意义，也没有独立生命周期
（不存在"没有用户组的成员"）。挂在组下，URL 本身就说明了"改的是哪个组的成员"，
同时天然带上归属校验 —— `{id}` 是必经的一环。

撤销路径同样带 `memberType`（三段），理由与 `0023` 第 2 节逐字相同：
`member_id` 是多态列，用户与用户组是两个独立的自增序列、会撞号，
只用 `memberId` 会**移错对象**，而"移错了"表现为权限凭空消失。

### 2. 用户组是"静态组"：`DYNAMIC` 与动态成员规则显式拒绝

`UserGroupEntity` 有 `category`（`STATIC` / `DYNAMIC`）、`filterJson`、`orgScopeJson` 三列，
都是动态组的输入。但动态成员规则的**求值没有实现**，接受它们会得到一个
"永远算不出成员"的组 —— 一个看起来建好了、实际不产生任何东西的壳。

因此：

- `category` 在服务层被**收窄成 `STATIC`**，传 `DYNAMIC` 报 `40001`（文案说明"动态组求值未实现"）；
- `filterJson` / `orgScopeJson` **连入参都不接受**，也不在出参里。

后者比前者更值得写下来：接受一个**没人读的字段**，最坏的后果不是"白存了一列"，
而是调用方**以为它生效了** —— 配置完动态规则、成员却永远是空的，
排查方向会完全跑偏到"规则写错了没有"。看不见的字段不会误导人，看得见的空壳会。

### 3. 组嵌套显式拒绝 `GROUP` 成员（`40001`）

`bw_auth_rel_user_group_member.member_type` 同样是多态列，注释也写着"组可以嵌套"，
但**判定 SQL 把 `gm.member_type` 钉成了 `'USER'` —— 只跳一层**（`0023`「发现但未处理」第 1 条）。

接受 `GROUP` 成员会产生一条**"成员列表里看得见、判定里完全不参与"**的关系。
这正是本仓最不接受的东西：一个假开关。因此 `bindMember` 对 `memberType != USER`
直接报 `40001`，文案点名"判定只跳一层"，而不是默默接受。

补嵌套需要 `WITH RECURSIVE`，它在 h2 / mysql / 达梦三套方言上的写法与版本要求都不一致，
达梦在 Oracle 兼容模式下对递归 CTE 的支持程度**未验证过**。
仓促加进去的风险是把"嵌套不生效"换成"某套库上整条判定失败" —— 后者严重得多，
且不会在 h2 上暴露。触发条件与 `0023` 相同：真的需要嵌套组、且先在达梦实测。

`MemberType` 的类注释用一张表钉死了**两张多态表对取值的支持程度不一样**
（`rel_role_member`: USER ✓ / GROUP ✓；`rel_user_group_member`: USER ✓ / GROUP ✗），
让下一个读代码的人不必再推一遍。

### 4. 判定侧第五处静默缺陷：停用用户组一直在产生权限

`bw_auth_user_group.is_enabled` 这一列从建库起就在，`UserGroupEntity` 也一直带着它，
接口也能改它 —— 但 `AuthorizationMapper` 的两条子查询**从不连 `bw_auth_user_group`**，
它是纯粹摆设。于是"停用"这个按钮按下去**什么都不发生**。

如果把本切片只做成"把用户组接口发出去"，交付出去的 `isEnabled` 就是**第五个假开关**。
因此本片把它接进判定：子查询连表检查 `ug.deleted = 0` 与 `ug.is_enabled`。

它与 `0022` 修掉的"停用角色不产生权限"是**同一类**：配置侧有开关、判定侧不读。
至此判定侧累计修掉五处静默缺陷（`0022` 三处：DENY 跨角色、停用角色、时态过滤；
本片一处：停用用户组；另一处是 `0023` 首次验证的组链路时态过滤）。

**由此提炼一条规则**：凡新增一个会影响权限的开关（状态位、时态列、归属字段），
都要同时问一句"**判定里读它了吗**"。问不出答案的开关，就不该出现在接口上。

### 5. 反查接口与判定 SQL 分开实现，不合并

反查 `GET /api/auth/users/{id}/roles` 返回**一组无序语义的行**，每行是一个"来源"：

- `source = DIRECT` —— 用户直接持有的角色（一条边）；
- `source = GROUP` —— 用户经某个用户组持有的角色（两条边：组-用户 + 角色-组）。

它与判定 SQL **必须分开**，理由不是"省一次改动"，而是**两者演进方向相反**：

|          | 判定 SQL                                   | 反查                                        |
| -------- | ------------------------------------------ | ------------------------------------------- |
| 目标     | "此刻**有效**的权限码集合"                 | "配置里**有哪些**路径"                      |
| 处理     | 聚合、去重、过掉停用/过期                  | 不过滤、逐条、带来源                        |
| 演进     | 越来越**严**（每修一处静默缺陷就多一层过滤） | 越来越**宽**（要显示所有形态，包括无效的） |

硬把两者合并，反查会退化成 `GET /api/auth/me` 的副本 —— 而它存在的意义恰恰是
回答"为什么**没有**权限"。

**反查刻意不过滤状态与时态**：一行"角色已停用 / 组已停用 / 授权已过期"正是答案本身。
唯一真正过滤掉的是"用户根本不在那个组里"（`gm.id IS NOT NULL`）——
那不是"配置了但无效"，而是**这条关系不存在**。

### 6. 反查带两组时态字段

经组授予实际是**两条边**（`rel_role_member` 一条、`rel_user_group_member` 一条），
各有自己的生效区间。因此 `effectiveFrom/To`（角色-成员那条边）与
`groupMemberEffectiveFrom/To`（组-成员那条边）**分开返回**。

`source = DIRECT` 时第二组为 `null` —— 那条边**不存在**，而不是"长期有效"。
把"不存在"与"长期有效"压成同一个 `null` 会让前端无法区分，
所以 `groupMemberEffectiveNow` 只在经组时有值。

SQL 里 `LEFT JOIN bw_auth_rel_user_group_member` 的 **ON 里带 `rm.member_type = 'GROUP'`**：
让组成员表只对"组类型的关系行"参与连接，用户直授行自然得 `NULL`。
写在 `ON` 而不是 `WHERE` —— 写进 `WHERE` 会整行滤掉超时的直授行，那是内连接语义。

### 7. 反查的权限归属是 `auth:user:read`，不是 `auth:user_group:read`

反查读的是**某个用户**的信息（"这个人有哪些角色"），与"用户列表 / 用户详情"同类，
因此归 `auth:user:read`。它虽然跨越用户组，但用户组只是**来源之一**，
不能因为它连了组就把权限归到组上。

这条有一个可观察后果，测试刻意保留：**审计员（`auditor`）持有 `auth:user:read`**，
因此它可以直接调用反查（`code=0`），但对用户组的增删改查一律 `40301`。
"反查属于用户读、不是用户组读"是一个**分开做的决定**，不是顺带的。

### 8. 用户组的第三处"软删行占着唯一索引"

`uk_bw_auth_user_group_tenant_code` 建在 `(tenant_id, group_code)` 上、**不含 `deleted`**，
与资源表（`0021`）、角色表（`0022`）是同一个坑的第三处：
MP 查询自动追加 `deleted = 0`、看不见软删行 → 判重通过 → insert 撞键。

正解同样是**复活原记录**，且复活出来一定是**空组**：清成员（`clearMembersOf`）+
清该组自己持有的角色授权（`clearRoleGrantsOf`）。目的是让
"**复活 = 没人、也没权限**"成为**无条件**成立的语义 —— 与 `0023` 第 11 条同一条理由：
`delete` 的守卫属于正常路径，复活分支要防的是**非正常路径**（行被直接改库删掉、关系行还在）。

`clearRoleGrantsOf` 的 `member_type = 'GROUP'` 条件**不能省**：
用户与组是两个独立自增序列、会撞号，省掉会把"恰好同号的用户"的角色也删掉。

### 9. 删除用户组的两道拒绝，以及一次"不拒绝"

- **有成员** → `40918`（用户组仍包含成员，请先移除成员）：删组会让组里所有人
  静默少一批权限，而管理员的本意可能只是"清理一个不再用的组"；
- **有子组** → `40913`（层级关系不合法）：与资源、角色同一条。

**但组自己持有的角色授权不构成拒绝理由，会被一并撤销** ——
与 `RoleService.delete` 完全同构：成员已清空后那些授权不再影响任何人，
而且它们属于这个组**自己的配置**（是聚合的内部边）。留存它们会让"复活"静默带回权限。

### 10. `DuplicateKeyException` → `409`（填上一直空着的 `40900` 段）

`40900` 这一段从错误码表建起就是空的：所有唯一键冲突都落进兜底处理器，
对外回 `50000`「系统内部错误」。这有三个具体问题：

1. **责任方归错**。冲突是"调用方提交了已存在的数据"，属 4xx；报成 5xx
   会让监控把它算进可用性、让前端当成故障去重试（而重试永远不会成功）。
2. **它不是用来替代"复活原记录"那条正解的**，而是**并发下的第二道防线**：
   服务层的"先查后写"挡不住两个请求同时通过判重。
3. **文案刻意不透露哪张表哪一列**（同兜底处理器不透异常信息）。
   精确原因应由业务代码**主动**判重返回域内码（如 `40912` 资源标识已存在），
   落到这里说明"业务代码没预料到这次冲突"。

**`spring-tx` 必须是 `compile` 而不是 `provided`**：异常处理器类在启动时被反射扫描
（`@ExceptionHandler` 的方法签名需要解析），`provided` 不传递依赖会让
依赖本模块的服务模块在启动时 `NoClassDefFoundError`，而它与那行业务代码毫无关系、
极难定位。

配套的 `DuplicateKeyAdviceTest` 钉住两件通常被想当然的事：

1. 直接撞唯一键抛出来的**确实是 Spring 的 `DuplicateKeyException`** ——
   这依赖 MyBatis-Spring 的异常翻译链按**数据库方言匹配错误码**（H2 23505 / MySQL 1062），
   换库 / 换连接池 / 改翻译链都可能让它变成裸 `PersistenceException`，
   那时处理器**永远匹配不上**、症状与修之前一模一样；
2. 处理器把冲突翻成 `409`。

**为什么这个测试直接调 Mapper 而不走 HTTP**：本仓所有"先查后判重"的创建路径
都已挡住撞键的可能性（撞上就走复活那一支），**没有任何 HTTP 请求能稳定触发这条异常**。
正因为不可达，才更需要单独测出来 —— 否则它就是一段没人跑过的代码。

### 11. 路径写 `user-groups`（连字符）、权限码写 `auth:user_group:*`（下划线）

这是全仓**唯一一处两处不同形**，刻意记下。
三套标识的字符集由 `AuthTaxonomyTest` 钉死为 `[a-z][a-z0-9_]*`：
URL 给人看，标识给程序与后台配置用。标识放宽字符集会让"拿标识当键"的地方
（缓存 key、正则、日志字段、前缀匹配）处处需要转义 —— 因此标识只允许下划线。

### 12. 权限码 17 → 21，错误码 +2，审计动作 +5

- 权限码新增 4 项 `auth:user_group:{read,create,update,delete}`（`AuthPermissions.ALL` 17 → 21）。
  **成员关系复用 `auth:user_group:update`**，与角色侧同构（不新增 `auth:user_group:member`）。
- 错误码新增 `40409`（用户组未包含此成员，对应角色侧的 `40408`）
  与 `40918`（用户组仍包含成员，对应角色侧的 `40916`）。
- 审计动作新增 5 个：`auth.user_group.{create,update,delete,grant_member,revoke_member}`。
  其中 **`grant_member` 是本域第二条间接提权路径**（把用户加进已被授予角色的组），
  与 `auth.role.grant_member` 同性质 —— 必须独立成标识，不能藏在 `update` 里。

### 13. 组成员关系与角色成员关系形状对齐，但不共用 VO

两者字段几乎一样，但**取值域不同**（角色成员允许 `USER` / `GROUP`，
组成员当前只允许 `USER`）、名字解析来源不同。共用一个 VO 会让
"组成员能不能是组"这个**当前不允许**的取值域渗进角色侧。
下沉的触发条件是**第三个成员关系出现**（组织-用户是下一个候选），
在那之前各自持有自己的 VO。

## 后果

- **配置侧彻底闭环**。`0023` 里"最后两处直接写库的夹具"（用户组与组-用户关系）消失，
  `RoleMemberApiTest` 改为全程走接口。这是第一次"用户 → 用户组 → 角色 → 资源"
  整条链可以**只经接口**配出来。
- **反查首次提供"为什么有权限"的入口**，且它与判定方向相反、刻意不过滤无效配置。
- **判定侧累计修掉五处静默缺陷**，并提炼出"新增开关必问判定是否读它"这条规则。
- 契约 45 → **54 个接口**（34 条路径 / 83 个模型）；权限域 26 → **41 条**。
- `40900` 段终于有处理器；全量测试 129 → **140 例**。

## 本决策未覆盖

- **组织管理接口**（`bw_auth_org` / `bw_auth_rel_org_user`）。
  与用户组同形、同样"表与实体已就绪、无接口"，是下一个自然候选。
- **给三张关系表加唯一索引**（`(role_id, resource_id)` /
  `(role_id, member_type, member_id)` / `(user_group_id, member_type, member_id)`）。
  有了 `409` 兜底才**终于"有资格"加**（否则并发撞键会落到 `50000`），
  但那是独立的一次决定：加索引要同时处理"复活原记录"与"清同键其余行"的既有逻辑。
- **动态组求值**（`filterJson` / `orgScopeJson`），见第 2 条。
- **菜单权限的两步**：资源表里还没有 `MENU` / `PAGE` 类型的行
  （种子把 `ALL` 全建成了 `API`）；基座导航也没按权限过滤（`BasicLayout` 直接遍历 `MICRO_APPS`）。
- **前端接线**：`platform-admin` 尚未接资源 / 角色 / 成员 / 用户组四个管理页；
  `AccessPermissions` 也因此刻意不含 `auth:resource:*` / `auth:role:*` / `auth:user_group:*`。
- **`updateById` 的 `NOT_NULL` 策略**在 `TenantService` / `UserService` 上仍未修
  （`0022` 第 9 条记录的遗留项）。
- **数据权限求值**（`data_scope` / `filter_json` 只存不用）—— 最大的一块，建议单独立 ADR。

## 发现但未处理（供后续决策）

1. **菜单权限仍差两步**（见「未覆盖」）。
   `0021` 让权限码可经界面登记，但资源类型只有 `API`，基座导航也没接权限集合 ——
   也就是说"给某人配了菜单权限"目前**看不到任何界面效果**。
2. **`AuthorizationMapper` 的注释与 SQL 不一致**：类注释说"多态成员按类型过滤"，
   但 `AuthorizationMapper` 只按 `ro.tenant_id` 过滤用户组那一侧。
   已经记录，未改（改动它属于"数据权限"，超出本片）。
3. **`40913` 被复用表达"有子节点"**（用户组与资源、角色同病）：
   文案是"层级关系不合法"，语义不精确，等真需要区分时再拆码。
4. **多态表没有外键 ⇒ 成员被删后关系行会留下**（`0023` 遗留第 4 条）。
   本片给用户组加了删除守卫（有成员拒绝），但**用户被删时组成员关系仍会留下孤儿行**，
   表现为反查里那一行的 `groupName` 有值、成员名却是悬空的。
   触发条件：真出现"删用户后必须清干净组关系"的合规要求时，在 `UserService.delete` 上做级联或拒绝。
