# 0076. 按主键取实体的路径：把"手工核对过"换成"机器守着"

- **状态**：已采纳
- **日期**：2026-10-16
- **决策者**：舰长

## 背景

`0074`「未覆盖」第 4 条要的是**一条守卫**：

> **`manager_id` 之外还有没有别的跨租户引用列**：……角色 / 用户组 / 资源三域的引用列
> （`parent_id` / `resource_id`）都已有同租户或平台级校验，但这是一次手工核对，
> **没有守卫**。

`0075` 把那句"没有守卫"接着写进了 `scripts/verify-notfound-messages.mjs` 的「刻意不查的」，
并且给了理由：

> ……但**表名 → 类名不是无歧义的 token 形状**（`bw_auth_user` → `UserService#requireUser`、
> `bw_auth_organization` → `requireOrg`、`bw_auth_user_group` → `requireGroup`……），
> 只能硬编码一张对照表 —— 那正是 `0067` 说过的形状：**白名单要核对条数**，漏一个就假绿。

**那段论证推错了方向，本轮把它证伪。** 需要的从来不是"表名 → 方法名"（那个映射确实不存在，
`requireUser` / `requireOrg` / `requireGroup` 三种命名并存），而是"**这个 `selectById` 取的是
哪张表的行**"—— 这个问题在源码里有唯一答案，因为链路全是**声明里的字面量**：

```text
    字段名 ──(private final XxxMapper xxxMapper;)──▶ Mapper 接口
           ──(extends BaseMapper<XxxEntity>)─────▶ 实体
           ──(@TableName("bw_xxx"))──────────────▶ 表名
           ──(建表 / 加列脚本)────────────────────▶ tenant_id 可空吗
```

四环都是逐字写的，没有一环需要猜。之所以 `0075` 会得出"只能硬编码"，是因为它去找的是
**方法名**（那是人起的名字，本来就无形状），而答案在**类型**上（那是编译器认的东西）。

这件事本身有一个已付过的代价：`0075` 发现 `server/README.md` 里那张自称权威的 `40002`
文案清单**自己漂过一次** —— `0074` 新加的两处一次都没登记进来。清单会漂，因为没东西拦着它漂。

## 决策

### 1. 射程的判据是**三条同时成立**，全部可机读

同一个方法体内：

1. 有一次 `XxxMapper.selectById(...)` 调用；
2. 该 Mapper 的实体表在 DDL 里是 `tenant_id NOT NULL`；
3. 抛出**这张表对应的那一个** `404xx`（`bw_auth_user` → `USER_NOT_FOUND`，
   即表名去掉 `bw_`/`auth_` 前缀、大写、加 `_NOT_FOUND`）。

⇒ 该方法体**必须**调 `assertVisible(`。

判据的读法：① 是"按主键取一行"，③ 是"取不到就报**这个对象**找不到" —— 两件同时成立时，
这个方法就是**这个对象的读侧出口**，它必须顺手回答"这位操作者看得见它吗"。
少了那一句，跨租户的 id 会得到一个**安静但错误**的答案：它说"这个对象不属于你"，
而按 `0025` 第 2 条，正确的答案是**"它不存在"**。

### 2. 例外不列白名单，**从 DDL 推导**

规则只对"表带 `tenant_id NOT NULL`"生效，于是两处天然出局，**没有一行对照表**：

| 表 | 为什么出局 | 从哪读出来 |
| --- | --- | --- |
| `bw_auth_resource` | `tenant_id` **可空**（平台级资源恒为 `NULL`）—— 对它的实体调 `assertVisible` 是**空操作**（那条判定遇到 `null` 直接返回） | 三方言建表脚本 |
| `bw_auth_tenant` | **根本没有 `tenant_id` 列** —— 它是租户本身，"租户归属"就是它自己，可见性由 `TenantService#requireVisibleTenant` 单独说 | 三方言建表脚本 |

这两条理由都写进脚本的输出里，而不是写进脚本的代码里。**天数是推导出来的**，
哪天门数变了，输出会变 —— 这正是 `0067`「白名单要核对条数」想要的那种性质：
不用核对，因为没有白名单可核对。

### 3. "同一个对象"是射程的一部分 —— 由实测逼出来的第三条

第一版判据只有"同方法内 `selectById` + 有 `404xx`"，它在
`OrganizationMemberService#setPrimaryPosition` 上报了**误报**：

```java
OrganizationEntity org = organizationService.requireOrg(orgId);   // 这里判过了
List<RelOrgUserEntity> active = activeRows(orgId, userId);
if (active.isEmpty()) {
    throw AuthResultCode.ORG_MEMBER_NOT_FOUND.businessException(); // 40410：说的是**归属**
}
...
return toMemberVO(target, userMapper.selectById(userId));          // 取的是**用户**
```

它取用户、抛的是归属的 `40410` —— **那个 404 的理由不覆盖这次取数**，所以它不在射程。
⇒ 加上"③ 抛的码必须是**这张表对应的那一个**"。加上之后矩阵从"8 处判定 / 1 处缺 + 1 处误报"
变成"7 处判定 / 0 处缺 + 2 处推导排除"，**零误报零缺口**。

**这一处不判的理由写进了源码注释**（不是只写在 ADR 里）：脚本会把它的位置印在输出里，
读的人从输出能直接落到答案上。它走不到跨租户，依据是**关系行的不变式**而不是查询条件 ——
`active` 非空蕴含"存在一条 `(orgId, userId)` 的归属行"，而归属行的租户由 `bindMember`
写成 `org.getTenantId()`、且引用的人先过 `requireSameTenantUser` ⇒ 归属行的租户
**恒等于容器的租户**。所以"能取到 `active`"这个前提本身就蕴含"`userId` 与本组织同租户"。

### 4. 三方言的 `tenant_id` 存在性与可空性必须一致

它是规则 1 的判据，所以它自己得无歧义。而这件事**没有别的东西能拦**：
**dameng 是唯一没被 CI 真跑过的方言**（`ci.yml` 只有 h2 与真 MySQL 两个后端 job）。
h2 与 mysql 一旦分裂，测试会红；dameng 与那两条分裂，**没有任何测试会红**。

只在 `tenant_id` 上对账，不做"三方言 DDL 全等"：类型名本来就不同
（`BIGINT` / `BIGINT IDENTITY` / `NUMBER`），全等会误报，而**会误报的守卫比没有更糟**（`0064`）。

### 5. "不得手搓同租户比较"的射程是**模块推导**的，不是全仓

`0075`「未覆盖 2」把"写侧同租户一致性有没有走同一个落点"记成**锚不住**（手搓写法无穷）。
本轮发现其中**一种形状**可以锚：`getTenantId()` 参与相等比较
（`x.getTenantId().equals(y)` / `Objects.equals(x.getTenantId(), y)`）。

但这条规则**不是全仓成立**的。第一版全仓扫描立刻在审计域报出一处 ——
`AuditLogService#detail`：

```java
if (!Objects.equals(entity.getTenantId(), visibility.tenantId())
        || (visibility.selfOnly()
                && !Objects.equals(entity.getOperatorId(), visibility.currentUserId()))) {
    throw notFound();
}
```

**那一处是正当的**：审计域有自己的 `Visibility` 模型，它**故意不接受** `tenant_id` 为 `null`
（未登录时产生的审计行不该对任何人可见），而 `assertVisible` 把 `null` 视为
"无需判定、直接通过"。两个模型说的是两件事。

⇒ 射程改成**推导**：**模块内出现过 `assertVisible(` 或 `assertReferencedInSameTenant(`
的调用，就算采用了统一落点**，规则只在那样的模块里生效。理由："手搓是第四个口径"这句话
只在一个租户模型下才成立；采用落点的模块里，租户语义已经被 `0074` 决策 4 定死了
（**别家租户在系统里就是不存在**），没有第二句话可说。

实测：全仓只有 `sts-server-auth` 一个模块采用落点，且它里面**零处**手搓。

### 6. 订正 `0075` 写在脚本里的那段论证（`0075` 的正文一字不改）

`scripts/verify-notfound-messages.mjs` 的「刻意不查的」第一条整段改写 ——
它现在说"那条守卫**已经**有了，见 `verify-tenant-visibility.mjs`"，而不是"写不了"。
`0075` 的 ADR 正文保持原样：**ADR 记录的是当时的判断，不回改**；
被证伪的判断由新片订正，这与 `0075` 订正 `0074` 时改 `AuthResultCode` 注释、
而不动 `0074` 正文是同一个做法。

### 7. 刻意不做

- **不把"该不该做同租户判定"机械化**。规则 5 只覆盖"已经在比、却绕开落点"的写法，
  而且只覆盖 `getTenantId()` 直接参与比较的形状；先 `Long t = x.getTenantId()` 再比，
  它看不到。判"该不该判"要理解语义。
- **不改审计 / 日志 / 事件三域去接 `0074` 的平台级口径**。它们是**另一个可见性模型**，
  接不接是一个产品问题（`0074` 未覆盖 2 / 3），不是本轮能顺手改的。
- **不删 `bw_auth_rel_role_resource_instance`**（整表 + Mapper 零读路径，`0075` 登记过）。
- **不改任何行为**。射程内 7 处本来就都对 —— 本轮加的是守卫，不是修复。

## 实测

### 侦察矩阵（先量清，再决定）

按"花括号深度切方法体"把 182 个源文件里的 **26 个 `selectById` 调用点**逐个归位：

- **射程 7 处**：`UserService#requireUser` · `OrganizationService#requireOrg` ·
  `RoleService#requireRole` · `RoleMemberService#requireRole` · `RoleMemberService#rolesOfUser` ·
  `OrganizationMemberService#listByUser` · `UserGroupService#requireGroup`；
- **推导排除 2 处**：`ResourceService#requireResource`（表可空）· `TenantService#requireTenant`（表无此列）；
- **另有 1 处印出来供人核对**：`OrganizationMemberService#setPrimaryPosition`（决策 3）；
- 其余 16 处没有 `404xx`，本就不是"取实体就报找不到"的形状。

**射程内零缺口** —— 所以本片不改任何行为。

### 七轮扰动：每条规则都能精确红，且不多红

| 轮 | 扰动 | 结果 |
| --- | --- | --- |
| 1 | 拆掉 `UserService#requireUser` 的 `assertVisible` | **只红 A**，位置到 `UserService.java:252:45` |
| 2 | `OrganizationService#requireOrg` 的 `assertVisible` 改成传 `USER_NOT_FOUND` | **只红 A2** |
| 3 | dameng 的 `bw_auth_organization.tenant_id` 改成可空 | **只红 B**，并指名 `dameng=NULL h2=NOT NULL mysql=NOT NULL` |
| 4 | 在 auth 域手搓 `group.getTenantId().equals(user.getTenantId())` | **只红 C**，一处（两条形状命中同一行，按行去重） |
| 5 | **新增**一个读侧出口 `requireRoleForRecon` 却忘了判定 | **只红 A**，射程 **7 → 8** |
| 6 | 把 `UserGroupEntity` 的 `@TableName` 改成不存在的 `bw_auth_user_groups` | **只红自检** —— 这正是防**假阴**：不报红的话，`bw_auth_user_group` 的判定会从射程里静默消失 |
| 7 | 把 `bw_auth_resource.tenant_id` **三方言**都改成 `NOT NULL` | **只红 A**，射程 **7 → 8**、排除 **2 → 1**，抓出 `ResourceService#requireResource` |

轮 5 与轮 7 是这片的重点：它们证明**射程是推导的**，不是把今天的 7 个名字抄进脚本 ——
新加一个出口会进射程，表的口径一变射程也跟着变。轮 6 证明**解析不出表名时会红**，
而不是安静地少查一处。

扰动逐轮做完立刻撤回，`git diff --stat` 为空后才继续。

### 全量回归与全套自检

- 全模块 `mvn -o -T 1C test`：**BUILD SUCCESS**，**51 个测试类 / 322 条 / 0 失败 0 跳过**。
  其中 `sts-app-server` 仍是 `0075` 记下的 **246 条** —— 本片不改行为，所以这个数字**不动就是对的**
  （`322` 是全模块；`246` 只是那一个模块）；
- 零前置自检从 **8 条变 9 条**，全部绿。

## 后果

### 正面

- `0074`「未覆盖 4」要的那条守卫**补上了**，而且不是靠一张会过期的名单 ——
  下个域新增一张带 `tenant_id NOT NULL` 的表、写一个忘了判定的 `requireXxx`，
  它会红（轮 5 验过）。
- `0075` 那段"只能硬编码"的论证被订正 —— 一个被写下的错误结论，比一个没写的结论更危险。
- 顺带得到两条**没有别的东西能拦**的性质：dameng 的 `tenant_id` 口径（规则 B）、
  auth 域不再出现第四个租户口径（规则 C）。
- 审计域那处"看着像缺口、其实不是"的实现被**读过并留了档**，
  而不是被一条误报的守卫逼着改坏（`0064`）。

### 负面代价

- 脚本依赖**四种源码/DDL 写法的稳定性**：`private final XxxMapper xxxMapper;`、
  `extends BaseMapper<XxxEntity>`、`@TableName("…")`、以及建表脚本里 `tenant_id` 那一行的形状。
  任何一处换了写法，**自检会红**（不是静默少查）—— 红的时候要先判断是"写法变了"
  还是"真的少了"。
- 规则 C 的射程是模块推导的，语义上"一个模块算不算采用落点"取决于它有没有那句调用 ——
  这比一个写死的目录更诚实地反映了本仓的现状，但也意味着审计域**今天不在射程**。

### 后续约束

- **新增一张带 `tenant_id NOT NULL` 的表**，它的读侧出口要么调 `assertVisible`，
  要么在 DDL 上说明为什么这一列可空（平台级）。
- **别把 `assertVisible` 写在"另一个对象"的 `404xx` 方法里** —— 它不会被本守卫拦住，
  但那种写法读起来就是错的。
- 采用落点的模块里，**手搓租户比较会红**；要写第四个口径，先改 `Visibility` 那种模型
  并说清它与 `0074` 的关系。

## 未覆盖

1. **"该不该做同租户判定"本身**。守卫只管"已经决定要判、却绕开落点或判错"，不管"这里该不该判"。
   判它要理解语义 —— 例如 `setPrimaryPosition` 那处就是靠关系行的不变式推理出来的。
2. **手搓的其他形态**：先取局部变量再比（`Long t = x.getTenantId(); … t.equals(y)`）、
   在 SQL 里 `eq(tenant_id, …)` 与判定互不覆盖、`!=` 的引用比较。规则 C 只覆盖
   `getTenantId()` 直接参与 `equals` 的两种写法。
3. **写侧（`40002` 那一族）仍然只有 `0075` 的手工口径**：七个落点现在都走
   `assertReferencedInSameTenant`，但"新加一处该不该走它"没有守卫。
4. **审计 / 日志 / 事件三域的可见性模型**没接 `0074` 的平台级口径 ——
   本轮只把它读清并留档（`0074` 未覆盖 2 / 3）。
5. **关系行 `rel_*` 的 `tenant_id` 恒等于容器租户**这条不变式没有守卫，
   只有四个写入点的代码可以读（本轮核过都成立）。
6. **`bw_auth_rel_role_resource_instance` 整表 + Mapper 零读路径**（`0075` 登记，仍挂着）。
7. **达梦仍未实测** —— 规则 B 只保证"DDL 的写法一致"，不保证它能跑。
8. **枚举常量改名带来的射程漂移**：规则 A 的判据两侧都不读枚举，所以**同时**改枚举常量名与
   它的全部源码引用（保持可编译）会让那一处静默离开射程。没做成检查的理由是"这张表被
   `selectById` 取过、却没有抛出它对应的那个码"**本来就有正当情形**（决策 3 那一处），
   判它得理解语义；而真会发生的改名是跨文件整体重命名，那种会撞上"**射程为空 ⇒ 红**"——
   兜底就是那一条。
