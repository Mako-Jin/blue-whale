# 0005. 后端模块划分与依赖约束

- **状态**：已采纳
- **日期**：2026-10-09
- **决策者**：舰长

## 背景

ADR-0001 定了「前后端分离、后端按业务域切」，但没有回答后端内部的具体问题：

1. 模块分成哪几层？层与层之间的依赖方向是什么？
2. Maven 坐标怎么组织？`groupId` 要不要按层分级？
3. 一个新模块里，代码按什么维度分包？
4. 公共能力（统一响应、异常处理）如何被各服务复用，又不制造隐式耦合？

参考项目 `SystemTerminator` 的 `sts-*` 体系整体方向是对的，但有两处不宜照搬：

- **预置了大量尚无内容的模块。** `file` / `flow` / `scheduler` 各自带 5~7 个子模块，其中多数是空壳。空模块会让首次构建变慢、IDE 索引变重，而且"这里以后要放什么"的意图，半年后没人记得——最后往往被填进不相干的东西。
- **父级靠本地仓库解析。** 部分模块的 `<relativePath/>` 为空，必须严格按顺序 `mvn install` 才能构建，换台机器极易踩坑。

## 决策

### 1. 五层单向依赖

```
sts-app   →   sts-server   →   sts-components   →   sts-common   →   sts-parent
业务应用       可部署服务        通用能力组件          技术底座         依赖管理
```

依赖**只能自上而下**：禁止反向依赖，禁止跨层跳跃（例如 `sts-app` 不得直接依赖 `sts-common`）。

**为什么禁止跨层跳跃**：跨层一旦开口，`sts-common` 就会在不知不觉中被当作"什么都能放"的口袋，最终变成一个谁都依赖、谁都不敢改的巨型模块。跳跃需求出现时，正确做法是把该能力下沉到合适层次，而不是直接在 POM 里加一行。

### 2. groupId 按层分级

| 层 | groupId | artifactId 示例 |
|----|---------|-----------------|
| 根 | `com.bluewhale.sts` | `sts-parent` |
| 技术底座 | `com.bluewhale.sts.common` | `sts-common-web` |
| 通用能力 | `com.bluewhale.sts.components.<域>` | `sts-components-audit-starter` |
| 服务 | `com.bluewhale.sts.server` | `sts-server-system` |
| 业务应用 | `com.bluewhale.sts.app` | `sts-app-portal` |

分级的 `groupId` 让构建日志和依赖树里的模块归属一目了然，代价是每个中间层聚合 POM 都要显式写 `<relativePath>`。

包名与 `groupId` 对齐，**唯一例外是服务模块**：包名用业务域而非构建层，即 `com.bluewhale.sts.system`（不是 `com.bluewhale.sts.server.system`）。包名描述的是"代码属于哪个业务域"，构建分层是工程视角，不该污染源码命名。

### 3. 版本号只出现一次

- 所有子模块**不写 `<version>`**，一律从 `sts-parent` 继承。
- 自制模块之间的互相引用，在 `sts-parent` 的 `dependencyManagement` 里用 `${project.version}` 统一收口。

这样升级版本号只需改 `sts-parent` 的一行。

### 4. 模块按需创建，不预置空壳

与前端 `packages/` 的约定一致：**先问"这个模块现在有没有内容"**，没有就不建。

规划中的 `sts-components-*`、`sts-app-*` 在有真实业务落地时再创建，届时不改动任何已有模块的坐标。

### 5. 模块间按业务域切，模块内按特性切

- **模块间**：按业务域划分（`sts-server-system`、未来的 `sts-server-log` 等），一个模块对应一个可独立演进的业务边界。
- **模块内**：按**特性（feature）**分包，而非按技术层分包。

```
com.bluewhale.sts.system
├── SystemApplication.java
└── health/                      ← 特性包
    ├── HealthController.java        接口层
    ├── HealthService.java           应用层
    └── HealthVO.java                出参模型
```

**为什么不用 `controller/` `service/` `repository/` 作为顶层分包**：那种切法下，改动一个功能要跨四个包来回跳；更要紧的是包之间没有任何边界——任何人都可以从 `controller` 直接调 `repository` 绕过业务规则，而编译器和评审都拦不住。按特性分包后，特性包自身就是天然的模块化候选点，将来要拆服务只需整个包搬走。

单个特性超过约 10 个类时，再在其内部按 `domain` / `application` / `infrastructure` 细分，此时边界已由包名自然形成。

### 6. 公共能力通过自动配置生效，不靠扩大组件扫描

`sts-common-web` 用 `META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports` 登记自动配置类，业务模块依赖即生效。

**不采用 `scanBasePackages = "com.bluewhale.sts"` 的方案**：那会让依赖关系从代码里消失——读源码看不出 `sts-common-web` 究竟贡献了什么，一个包重命名就能静默失效。自动配置把契约写在明面上，是否生效可直接从条件装配报告（`--debug`）读出。

### 7. 统一响应契约：业务结果只由 `code` 表达

所有接口返回 `R<T>`：`{ code, message, data, timestamp }`。

- `code` 为 5 位：**HTTP 状态码(3 位) + 业务细分(2 位)**，如 `40400`。看到码即知是客户端问题还是服务端问题，不必回查文档。
- **业务失败仍返回 HTTP 200。** HTTP 状态码描述的是传输层是否送达；业务失败（余额不足、重复提交）在传输层是成功的。混用状态码表达业务语义，会让网关、CDN、重试中间件把业务失败当作传输故障重试，反而制造重复扣款一类的故障。
- 传输层失败（401/403/404/5xx）仍由框架按标准返回，不套此包装。

### 8. 业务异常不采集调用栈

`BusinessException` 构造时 `writableStackTrace = false`。业务异常在正常运营中高频出现（用户反复提交非法表单），采集栈没有价值却让日志体积与 CPU 开销成倍上升。需要排查时再用构造参数打开。

## 当前落地状态

按"模块按需创建"原则，S1 阶段只建立**已有实际内容**的模块：

```
server/
├── pom.xml                       聚合根
├── sts-parent/                   依赖管理（零代码）
├── sts-common/
│   ├── sts-common-basic/         统一响应 R · 错误码 · 业务异常
│   └── sts-common-web/           全局异常处理 + 自动配置
└── sts-server/
    └── sts-server-system/        系统域服务（健康检查）
```

`sts-components/` 与 `sts-app/` **尚未创建** —— 等出现第一个真正需要复用的能力组件、第一个业务应用时再建。

## 后果

**正面**

- 依赖方向由构建系统强制：跨层或反向依赖会直接编译失败，不靠人自觉
- 版本号单点维护，升级只需改一行
- 新模块的落位有明确规则，无需每次都讨论"这该放哪层"
- 特性分包使模块边界天然存在，为将来的服务拆分留好了接缝

**负面 / 代价**

- 分层越多，中间层的聚合 POM 越多；本项目的取舍是**只在有内容时才补**，因此短期内层数不全
- 特性分包下，跨特性的公共部分需要主动提炼，否则容易在多个特性包内重复
- 统一响应把业务错误压到 HTTP 200，**监控系统无法靠状态码统计业务失败率**，必须改为解析响应体中的 `code`（已在 `docs/architecture/` 记录该约束）

**后续约束**

- 新增模块必须同步 `server/README.md` 的模块表与根 `README.md` 的结构图
- 服务模块拆分粒度以"能否独立部署"为准，避免为分层而分层
