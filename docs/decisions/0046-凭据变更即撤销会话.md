# 0046. 凭据变更即撤销会话：一个放在了调用方的动作，与它漏掉的那一半

- **状态**：已采纳
- **日期**：2026-10-13
- **决策者**：舰长

## 背景

`0045`「未覆盖」里记着一条（本轮核出、未处置）：

> **管理员重置口令不撤销刷新令牌**（本轮核出，未处置）。自助改密会撤销该账号**全部**
> 刷新令牌（`0043` 决策，理由写在 `AuthService#changePassword`："改密最常见的动机就是
> 我怀疑口令泄露了"），而管理员重置**只**改口令并置 `mustChangePassword = 1`
> （`UserService#resetPassword` 全文如此）。两者的动机是同一个，效力却不一致 ——
> 一个已经换到手刷新令牌的攻击者，在管理员重置之后**仍然能续期**。……
> 它该由下一次动手解决，判据是"撤销会话的入口要不要只有一个"。

那一句里的判据要拆成两问。第一问（要不要只有一个）答案明显；**第二问才是这一轮的内容** ——
它为什么不只一个，以及"补一句"为什么不是答案。

### 一、「补一句」能当场对齐，但它依赖的正是造成缺口的那件事

最省事的做法是给 `UserService#resetPassword` 末尾补一句撤销。它当天就能让两处一致，
但前提是**记得**。而"记得"恰恰是这条缺口产生的原因：换口令有两个入口，
撤销只写在其中一个里 —— 写自助改密的那个人顺手写了，因为当时他正在改那一段；
另一个入口没人动，也就没人想起。

这与 `PasswordChanger` 之所以被拆出来的理由完全同源（它的类头写着：
"复制粘贴出来的三份'都对'，会在将来某一次修改里只改到其中两份"）。
所以补法必须让**下一个入口也没法忘**，而不是让这一处今天看起来对。

### 二、真正要回答的是：它为什么在调用方

`PasswordChanger` 的类头已经有一节「调用方负责的部分（本类刻意不做）」，列着三条：
验旧口令、`mustChangePassword` 的取值、解锁与清零失败次数。这三条有个共同点，
而类头**还没有把它说出来**：

- 管理员重置**不知道也不该知道**旧口令，自助改密**必须**验旧口令；
- 管理员重置要置 `mustChangePassword = 1`，自助改密要置 `0`；
- 管理员重置要顺带解锁，自助改密本就是登录状态、不必处理。

**它们在两个调用方那里取值不同。** 而"清掉旧会话"在两个调用方那里取值
**完全一样**：都撤、撤的都是全部。于是一条判据浮出来：

> **两个调用方取值不同的，才是调用方的语义；取值一致的，就不该由调用方决定。**

取值一致的规则放在调用方，等于同一件事有两份实现 —— 而这里已经把代价演了一遍：
一份写了、另一份漏了。**它不该被修在调用方，它该被移到那个动作本身。**

### 三、漏掉的那一半，偏偏是更该做的那一半

管理员重置不是"顺手换个口令"，它是**运维介入**：`UserController` 把它的审计动作与
"改资料"分开（`auth.user.reset_password` / `auth.user.update`），理由写在类注释里 ——
"前者是运维介入他人账号的动作，事后追责时与'改过资料'是完全不同的问题"。

它发生的一刻，管理员刚刚**认定这个账号出了问题**：口令泄露、账号被顶掉、或者本人进不来。
而那一刻恰恰没有任何会话被清掉。攻击者拿着已经换到手的刷新令牌继续续期 ——
**换了一把锁，门还开着**。重置是这套系统里唯一一个"认定出了问题却不清会话"的动作。

### 四、顺带要回答的：还有哪些状态变化该"顺手撤一下"

统一之后紧接着就是这个问题，而答案大多是不该 —— 理由是同一条：

- **账号被停用**：续期时读得到 `status`（`AuthService#refresh` 已经在拦），靠校验就够。
  多撤一步的坏处很具体：管理员把状态改回启用，那个人**本可以不必重新登录**就回来
  （令牌还在），撤销把这件本来不必发生的事变成了必须发生。
- **账号被锁定**：它拦的是**新的登录尝试**，而它已经拦住了（口令正确也进不来，
  `PasswordHardeningApiTest` 钉着）。触发条件是"有人猜错了几次口令"，
  而这件事**不需要任何凭据就能由第三方制造**：若锁定同时清会话，
  一次 5 次的错误猜测就升级成"把正在工作的人踢下线"，成了一个免费的 DoS。
- **账号被删除**：续期时 `user == null`，同样是校验读到的。

于是判据有了第二半：

> **撤销是主动清理，只用于无法从当前状态推出来的变化。**
> 换口令之后，旧刷新令牌看起来完全正常 —— 签名有效、jti 在库里、没有过期，
> **没有任何一列能说明"它属于上一任口令"**；所以只能撤。
> 而"停用 / 锁定 / 删除"都是**当前状态**，读的时候就知道，因此靠判断、不靠清理。

## 决策

### 1. 撤销会话移进换口令这个动作本身

`PasswordChanger#change` 末尾调用 `SessionRevoker#revokeAll`。
`UserService#resetPassword` 与 `AuthService#changePassword` 各自都不再写撤销 ——
后者原本那一句被删除（它会变成第二次撤销），前者从来没写过。

这条的效果不是"两处一致了"，而是**换口令这件事从此自带这个后果**：
下一个新增的入口（忘记口令、批量重置、导入账号）不写也算数。

### 2. 作废令牌的两个字段由一处写

新增 `SessionRevoker`，两种粒度（`revoke` 单个 / `revokeAll` 该用户全部）都在那里——
"作废"要同时写 `revoked` 与 `revokedAt` 两列，与 `PasswordChanger` 管的
"哈希 / 算法标识 / 更新时刻"三列是同一个形状的问题：**成对的东西由一处落，
而不是由每个调用方记得落**。少写 `revokedAt` 不会报错，只是"作废于何时"无从判断 ——
而会话时间线里唯一有用的那一段，正是"它是何时被掐掉的"。

`AuthService` 的私有 `revokeAllForUser` 随之删除，登出与重放检测改用同一个实现。

### 3. 撤销排在那次变更的最后一步

`change` 里它排在强度校验、防重用、历史写入、`updateById` 之后。
这与 `0045` 决策 3 把"作废旧令牌"挪到全部校验之后是同一条：
**一个失败的请求不该留下痕迹。** 具体收益：管理员填了一个不合规的新口令时，
库里的会话一个都不动 —— 不存在"口令没换成、人却被踢出来了"。
`SessionRevocationApiTest#shouldNotRevokeSessionsWhenResetIsRejected` 钉的就是它。

### 4. 重复撤销不推进撤销时刻

`SessionRevoker#revoke` 对**已作废**的令牌直接返回 0，不改写 `revokedAt`。
今天三处调用各自都挡着，但那是三处各挡一次；挡在实现里才不会有第四处忘了挡 ——
重复撤销的后果是"这个会话是什么时候被掐的"变成随调用次数漂移的值。

### 5. 不撤销的三处是刻意的，并有用例钉住

见背景四。`SessionRevocationApiTest` 里有两例断言"**没**撤销"
（停用、锁定），第三处（删除）由 `refresh` 的 `user == null` 分支承担。
只钉"该撤的撤了"是不够的：那样下一次有人"顺手也撤一下"就没有东西会红，
而锁定那条被顺手撤掉的代价是一个免费的 DoS。

### 6. 与 `0045` 决策 3 的关系：它的收益被收窄，主张不变

`0045` 决策 3 在解释"为什么作废旧令牌排在全部校验之后"时举了一条收益：
口令已过期的用户反复刷新只会反复得到 `40111`，手上那个刷新令牌**不会被烧掉** ——
"于是管理员重置之后他不必重新登录就能恢复"。本轮之后**后半句不再成立**：
重置会撤销全部会话。恢复的路从"自愈"变成"用新临时口令重新登录"。

这不是推翻那条决策。它主张的事（失败的请求不留副作用）一字未动，
并由 `PasswordExpiryApiTest#shouldRejectRefreshWithExpiredPassword`
（同一个令牌连刷两次都是 `40111` 而不是 `40106`、未作废的令牌仍是 1 条）继续钉着。
被收窄的是它**顺带举的那个例子** —— 那里把两件事读成了一件：

- **失败没烧掉令牌**：这是"不留痕迹"，属于那条决策；
- **成功动作烧掉令牌**：这是"凭据换了，旧会话失去依据"，属于本篇。

而且新那条路并不亏：重置之后"旧令牌还能用"本身就可疑 ——
管理员刚认定这个账号出了问题，那个会话凭什么自动回来？
新口令必须由管理员交付给本人，**这个交付动作正是**"谁现在有资格进来"的答案。

## 后果

- **一处效力不一致消失**：自助改密与管理员重置现在同等效力，撤销由同一个实现执行。
- **`UserService#resetPassword` 的净改动是 0 行代码**（只多了注释）。
  这正是本轮想要的修法形状：缺的不是一行，是一个位置。
- **对外可见的变化（如实记）**：管理员重置口令之后，该账号在**所有设备上**的会话立刻失效，
  用户需要拿新口令重新登录一次。前端不需要新逻辑：那次刷新得到 `40106`，
  由 `0045` 的"被请出去时的原因"机制在登录页说明，文案是服务端那句"会话已失效，请重新登录"。
- **代价**：重置之后用户手上那个刷新令牌不再可用，`0045` 记录的那条便利没了（见决策 6）。
- **契约零变化**：`openapi.json` 与 `schema.d.ts` 不动 —— 无接口面变化，
  改动全在"同一个响应背后的会话状态"里，而契约描述不到那里。

## 未覆盖

- **多因子（MFA）的绑定与解绑**也是凭据变更，该走同一条路，
  但 `MFA_*` 目前是留白的码（`AuthResultCode` 里没有任何抛出点），没有可接的对象。
- **改用户名、改绑邮箱 / 手机**同样是身份凭据。前者当前不允许修改（`UserService#update`
  刻意把它排除在外），后者要等口令找回通道建立 —— 两条都该各自回答一次
  "要不要清会话"，而不是照着这里套。
- **「退出所有设备」没有独立入口**（只有登出不传刷新令牌时才是全部撤销）。
  有了它，`SessionRevoker` 就是它的实现 —— 但那条接口还需要一个权限码与一句文案，
  且要回答"撤销别人所有会话"的授权边界，不该顺手塞进这里。
- **`revokeAll` 的返回值目前无人消费**。它是为"这一次到底踢掉了几个会话"准备的，
  也许某天该进审计（"重置口令时同时清掉了 3 个会话"）。现在刻意不记：
  审计表不该多出一列只被写、不被看的数据。
- **`0045` 里那句"不必重新登录就能恢复"仍留在原文中**。按仓内约定不回改旧 ADR，
  指向由本篇（决策 6）与 `docs/README.md` 的索引行建立 —— 读旧文的人要能走到这里。
