# 0070. 枚举型过滤值的归一

- **状态**：已采纳
- **日期**：2026-10-15
- **决策者**：舰长

> 领的是 `0069`「未覆盖」第 2 条：**枚举型的过滤值要不要统一归一大小写**。原文写的是
> "要动它得先回答'枚举的 wire name 算不算数据约束'……本轮**刻意没顺带**"。
>
> 核完的结论：它不是一个"要不要"的口径问题，而是**同一条参数在四个域有两副面孔** ——
> 同一个 `Status` 枚举同时喂给角色 / 用户 / 租户 / 组织四个域的 `status` 列，
> 于是 `?status=enabled` 在其中一个域搜得到、在另外三个搜不到。前端的下拉框两处长得
> 一模一样，**没有人能从界面上看出区别**。这跟 `0069` 是同一类东西：差异不承载任何
> 区分能力，只承载"在某个页面上搜不到"。

## 背景

### 1 射程：五个 getter、九个调用点

"枚举列"指的是**列里存的是一个封闭取值集的字面量**。全仓的过滤参数里属于这一类的只有五个：

| getter | 枚举 | 列 | 域 |
| --- | --- | --- | --- |
| `query.getStatus()` | `Status` | `status` | 用户 · 租户 · 组织 · 角色（**同一个枚举四家共用**） |
| `query.getResourceType()` | `ResourceType` | `resource_type` | 资源 |
| `query.getMemberType()` | `MemberType` | `member_type` | 角色成员 · 用户组成员 |
| `query.getLevel()` | `ClientLogLevel` | `level` | 日志 |
| `query.getResult()` | `AuditResult` | `result` | 审计 |

九个调用点、八个服务。**关键在 `status` 那一行**：它是九个里唯一被四个域共用的，
所以"各域自己决定"这件事在这里不是风格问题，而是**同一个枚举有四种答案**。

### 2 改前的两副（其实是三副）面孔

| 做法 | 域 | 处数 | `?status=enabled` |
| --- | --- | --- | --- |
| 走本域私有的 `normalizeXxxFilter` → `parse` → `wireName` | 角色 `status` · 资源 `resourceType` · 角色成员 `memberType` · 用户组成员 `memberType` | 4 | **搜得到** |
| `FilterValue.text` + 手写 `toLowerCase(Locale.ROOT)` | 日志 `level`（该列存小写） | 1 | 搜得到（方向固定朝小写） |
| `FilterValue.text` + 直接 `eq` | 用户 `status` · 租户 `status` · 组织 `status` · 审计 `result` | 4 | **搜不到** |

`toLowerCase` 那一处看着像"宽容"，其实只是"该列存小写"这一步的落点 ——
它把大写输入压成小写，但没有一个"取值表"可认（`clientLogLevel.wireName()` 恰好就是小写，
所以"归一成标准写法"与"转小写"在这里同结果，纯属巧合）。

**同一件事在三个域是三个答案**：角色认，日志认（但只朝一个方向），用户不认。

### 3 前端看不见这个区别

前端只有三处真正的筛选控件（资源类型 / 成员类型 / 日志级别，都是 `<select>`，
选项值是后端给的标准写法）；用户 / 租户 / 组织 / 角色四个管理页**根本没有 `status` 筛选框**。
也就是说：这四个域上的大小写口径差异**不是任何界面上可观察的行为**，
只能从 API 调用方那一侧撞到 —— 而 API 调用方（脚本、将来的别的前端、外部集成）
没有理由知道"这个域宽容、那个域不宽容"。

## 一 实测：九条同形断言

照本仓"先写能红的用例"的做法，先加 `EnumFilterNormalizationApiTest`
（9 例 · **跨 profile** · 不 `@Transactional`），**不改代码**跑一次 —— 读数是 **4 红 5 绿**：

| 用例 | 改前 | 改后 |
| --- | --- | --- |
| 用户域：`status=enabled` 与 `status=ENABLED` 同一结果集 | **红**（3 条 vs 0 条） | 绿 |
| 租户域：同上 | **红**（1 条 vs 0 条） | 绿 |
| 组织域：同上 | **红**（4 条 vs 0 条） | 绿 |
| 审计域：`result=success` 与 `result=SUCCESS` 同一结果集 | **红**（1 条 vs 0 条） | 绿 |
| 角色域：`status` 同上（**对照组**） | 绿 | 绿 |
| 资源域：`resourceType=menu` 同上（**对照组**） | 绿 | 绿 |
| 角色成员：`memberType=user` 同上（**对照组**） | 绿 | 绿 |
| 日志域：`level=INFO` 与 `level=info` 同一结果集（**对照组**） | 绿 | 绿 |
| 认不得的值仍按原样比（结果为空）、纯空白仍 = 不过滤（**回归钉**） | 绿 | 绿 |

四条红正是"同一个枚举的三副面孔"；四条绿是**对照组**（已经宽容的一方），
它们的作用是证明"红的那几条不是因为'枚举过滤天然做不到'"——同一条断言在隔壁域是绿的。

**注意一处容易误读的地方**：组织域的 `status` 在 `0069` 的表里是**绿**（对照组，
量的是"两端空白"），在本篇里是**红**（量的是"大小写"）。同一个用例形状、两个 ADR
里结论相反，因为量的是**两个不同维度** —— 组织域当年 `trim` 了、但没有归一大小写。
`0069` 与本篇合起来才是"这一列到底宽容到什么程度"的完整答案。

最后一条是**回归钉**：归一化最容易踩坏的一支是把 `parse` 失败当成"没给条件"——
那样 `?status=EANBLED`（拼错）会**静默返回全部**，调用方以为自己筛过了。这比报错危险得多，
所以它必须有一个自己的断言（不只是注释里写一句）。

## 二 决策

1. **规范化的入口收敛到 `FilterValue.enumValue(raw, parser, wire)`**：
   先 `FilterValue.text()`（吃两端空白、空则 `null`），再 `parser.apply()`；
   认得就返回 `wire.apply(parsed)`（标准写法），**认不得就返回已 trim 的原值**。

2. **认不得时按原样比，不退化成"不过滤"。**
   这是本篇最重要的一条。`?status=EANBLED` 若变成"不过滤"，调用方拿到**全部**记录
   却以为自己筛过了 —— 与"结果为空"差着一整个数量级。原样比的结果是空集：
   既没有假装成功，也没有把查询拦下来（过滤条件不该让查询失败，这一点与 `0067`/`0068`
   定下的"关键词宽容"是同一条取向）。

3. **分界线是"这一列有没有一个可以用完的取值表"**，不是"这个字段看起来像不像枚举"。

   - **有** ⇒ 换个大小写不是另一个对象，归一它是**修正写法**。
   - **没有** ⇒ 换个大小写就是另一个字符串，归一它是**篡改意图**。

   于是 `orgType` / `category` / `parentCode` / `app` / `traceId` / `namespace` / `sessionId` /
   审计的 `action` / `resource` / `targetId` / `operatorName` **一个字都不动**，
   继续走 `FilterValue.text()`。**自由文本沿用 `0065` 定下的"区分大小写"** ——
   本篇没有推翻它，只是把"枚举"从"自由文本"里分出来。
   （`orgType` 是这条线上一处容易走错的：它的名字像枚举，但**写入时不校验取值**
   —— `OrganizationService` 里是 `normalize(request.getOrgType())`，纯 trim。取值集不存在，
   就不能归一。）

4. **不让枚举类实现一个公共接口来省掉那两个参数。**
   `enumValue` 收两个方法引用（`Xxx::parse` / `Xxx::wireName`）。做成接口（比如
   `WireNamed`）会更短，但会把 `sts-common-db` 变成**各域枚举的共同依赖方向** ——
   而这里需要的只是"调用方告诉我怎么解析"。两个方法引用就把依赖留在了调用方那一侧。

5. **五个枚举的 `parse` 一律"大小写不敏感 + 认不得回 `null`"，缺的补上。**
   `Status` / `ResourceType` / `MemberType` / `ClientLogLevel` 本来就是这个形状；
   审计的 `AuditResult` **此前没有 `parse`**（`result` 列此前只写不查），本轮补一个 ——
   与另外四个同一取舍：不兜底成 `SUCCESS`，让拼写错误暴露出来。

6. **日志域的 `level` 从"`text` + `toLowerCase(Locale.ROOT)`"换成 `enumValue`。**
   行为等价（`ClientLogLevel.wireName()` 就是小写），但"朝哪个方向归一"由枚举自己回答，
   不再是一行手写的大小写转换。`0069` 记的那句"`level` 的 `toLowerCase` 不下沉"因此
   **不再是特例** —— 它现在就是 `enumValue` 的一个普通调用点。

**没有采用的两条路**：把自由文本也归一到小写（那正是 `0065` 否掉的，会让 `Trace-…` 与
`trace-…` 变成同一个过滤条件）；把 `parse` 失败当成"不过滤"（见决策 2）。

## 三 落地

- **`FilterValue` 加 `enumValue(...)`**，类注释新增「两类过滤值，两个入口」一节，
  写明分界线的判据（"有没有一个可以用完的取值表"）与"认不得按原样比"的理由。
- **`AuditResult` 加 `parse(...)`**（大小写不敏感、认不得回 `null`）。
- **九个调用点**：
  - 用户 / 租户 / 组织 / 角色 `status` → `enumValue(query.getStatus(), Status::parse, Status::wireName)`；
  - 资源 `resourceType` · 角色成员与用户组成员 `memberType` → 同形；
  - 日志 `level` → `enumValue(query.getLevel(), ClientLogLevel::parse, ClientLogLevel::wireName)`；
  - 审计 `result` → `enumValue(query.getResult(), AuditResult::parse, AuditResult::wireName)`。
- **删掉四个私有方法**（`RoleService.normalizeStatusFilter` ·
  `ResourceService.normalizeTypeFilter` · `UserGroupService.normalizeMemberTypeFilter` ·
  `RoleMemberService.normalizeMemberTypeFilter`）—— 它们就是"各域自己决定"的载体，
  三份同形实现（`memberType` 那份还重复了两次）。归一现在只有一个入口。
- **各域的私有 `normalize()` / `resolveStatus()` 保留** —— 它们**现在只服务写入侧**
  （`entity.setXxx(request.getXxx())`），与过滤侧不同源，本轮不碰（见「未覆盖」7）。
- **新增 `EnumFilterNormalizationApiTest`**（9 例 · 跨 profile · 不 `@Transactional`）。
- **`scripts/verify-filter-values.mjs` 加规则 4**：五个枚举 getter **只能**作为
  `FilterValue.enumValue(...)` 的第一个实参出现，出现别处即红。

## 扰动验位

- **改代码前**跑那 9 例 ⇒ 4 红 5 绿（上表）——"各域自己决定"这一侧的读数。
- **改代码后**跑 ⇒ 9 绿（改动必要且充分）。
- **守卫规则 4 扰动两次**（改动 ⇒ 必红，还原 ⇒ 必绿）：
  - 把租户域改回 `FilterValue.text(query.getStatus())` ⇒ 报红，行号指向那一条语句；
  - 再改成**完全绕开**（`.eq(..., query.getStatus())`，一处 `FilterValue` 都不经）⇒ 同样报红。
- 另外三条规则（`0069` 遗留）本轮未动代码，仍全绿；规则 4 与它们互不干扰。

## 后果

**正面**

- `Status` 这一个枚举在四个域终于**只有一副面孔**：`?status=enabled` 到处都搜得到。
  这是本篇的主要目的，也是"四个域共用一个枚举"本该有的样子。
- "归一"从 4 份私有实现收成 1 个方法调用；`memberType` 那两份重复实现随之消失。
- 新增一类过滤值的成本变成一条规则（`enumValue` + 两个方法引用），
  不再需要"照抄隔壁域那个 `normalize` 再改改"。

**负面 / 代价**

- **枚举列与自由文本的过滤口径从此不同**：前者不区分大小写，后者区分（`0065`）。
  这不是矛盾（两类值的性质不同），但它是一个**必须记住的不对称**，
  否则将来会有人"顺手统一"其中一半。守卫规则 4 只钉枚举那一侧，
  自由文本那一侧**刻意没有守卫**（见「未覆盖」4）。
- **行为变化、对外可见**：`?result=success`、`?status=enabled` 这类请求从"空结果"
  变成"有结果"。如果外部调用方此前把这个空结果当成了某种语义，那是不成立的假设。
- 认不得的值仍按原样比 ⇒ `?status=NOT_A_STATUS` **仍然是空集**而不是 400。
  这是刻意的（过滤条件不该让查询失败），但意味着**拼错不会被报错提醒** ——
  只能靠"结果为空"自己发现。这一条有用例钉住。

**后续约束**

- 新加**枚举列**的过滤值：`String x = FilterValue.enumValue(query.getX(), Xxx::parse, Xxx::wireName);`
  然后 `.eq(x != null, ...)`。**不要**为它再写一个私有 `normalizeXxxFilter`。
- 新加**自由文本**的过滤值：走 `FilterValue.text()`，**不要**顺手 `enumValue`
  （那会把 `Trace-…` 与 `trace-…` 变成同一个条件）。
- 新加**枚举**时补一个 `parse`：大小写不敏感、认不得回 `null`，不兜底成某个默认值。
- 五个 getter 名（`getStatus` / `getResourceType` / `getMemberType` / `getLevel` / `getResult`）
  是守卫规则 4 的白名单。**给这五个 Query 加非过滤用途**会让规则 4 报红 ——
  那是提醒你去更新白名单，不是让你忽略它。

## 「未覆盖」

1. **达梦未实测。** 本篇改动全在 Java 侧（`parse` 与 `wireName`），不落到 SQL 上；
   但"排序规则决定比较语义"这件事在三方言上不同（`0065`），而"归一之后不再依赖它"
   只在 h2 与真实 MySQL 上验过（与 `0067`「未覆盖」1、`0069`「未覆盖」1 同源）。
2. **规则 4 的白名单是"当前这五个 getter 名"。** 下一个域新加一个枚举列、用了新 getter 名时，
   没有 token 能锚定它 —— 只能靠"枚举列的过滤值走 `enumValue`"这条纸面规则。
   （与 `0064` 的结论一致：能机械化的是"锚定无歧义 token 形状"，锚定不到就别硬做。）
3. **`AuditResult.parse` 只在过滤侧用。** 写入侧仍直接落 `name()`（即枚举名），
   两边现在恰好一致，但**不是同一条通道**保证的 —— 与「未覆盖」7 同源。
4. **剩下的十四个自由文本过滤值仍区分大小写**：`app` / `namespace` / `traceId` / `sessionId` /
   `eventName` / `userId` / `deviceId`（日志与事件）· `action` / `resource` / `targetId` /
   `operatorName`（审计）· `orgType` / `category` / `parentCode`（auth）。
   **这是 `0065` 的决定，不是遗漏**，但"这十四个里有没有其实该算枚举的"没有逐一核过。
5. **用户组的 `memberType` 没有自己的用例**（角色成员那处有，作对照组）。
   两处走的是同一个 `MemberType` + 同一个 `enumValue`，靠"同一实现 + 守卫覆盖"，
   没有各自的运行时断言（与 `0066`「未覆盖」2、`0069`「未覆盖」6 同源）。
6. **`?status=`（**空串**，而非纯空白）与不传的处理仍未单独断言**（承 `0069`「未覆盖」7）。
7. **写入值（`entity.setXxx`）仍然不统一**（承 `0069`「未覆盖」4）。
   `resolveStatus` / `resolveResourceType` / `resolveDataScope` / `resolveEffect` /
   `resolveCategory` 各域一份，且 `TenantService.update` 原样入库（见 `0058`）。
   本轮把**过滤侧**的枚举归一收干净之后，这个不对称更显眼了 —— 但它是"写入"侧的事，未做。
