# 0002. 前端公共包与公共依赖治理

- **状态**：已采纳
- **日期**：2026-10-09
- **决策者**：舰长

## 背景

前端工作区开始沉淀公共代码时，遇到一个容易混淆的问题：**"公共依赖"到底指什么？**

它是两件不同的事，混在一起就会两头都做错：

1. **第三方依赖的版本**想统一管——避免同一个库在不同子项目里锁到不同版本，升级时漏改。
2. **自研的公共代码**想复用——日志、请求封装、工具函数、设计令牌。

同时，`platform-terminator/packages/common-tools` 里的 logger 已经积累了实际使用经验，需要评估是否照搬、以及照搬哪些部分。

需要决策的问题：

1. 要不要建一个包专门"存放公共依赖"？
2. 公共依赖的版本怎么统一？
3. logger 是照搬、还是重写？

## 决策

### 1. 不建"存放依赖的包"，用 pnpm catalog 管版本

公共依赖的**版本**统一写在 `web/pnpm-workspace.yaml` 的 `catalog:` 段，各 `package.json` 一律写 `"catalog:"`：

```yaml
catalog:
  react: ^19.3.0
  typescript: ^6.0.3
```

```json
{ "devDependencies": { "typescript": "catalog:" } }
```

**为什么不用包来放依赖**：那会产生幽灵依赖（ghost dependency）——某个库可以被引用到，却没有出现在引用方的 `package.json` 里。后果是运行时解析不到、IDE 提示不出来、换包管理器即崩。catalog 只统一版本号，**依赖归属关系仍然留在各自的 `package.json`**，两者兼得。

### 2. 公共代码按能力建包，`packages/common-*`

当前建了 `common-tools`（日志 + 环境探测），`common-config` 已有。其余（`common-theme`、`common-components`、`common-api`）按需再建，不预置空架子。

### 3. logger 重写而非照搬

保留参考实现的**组织形式**（`common-*` 包、`src/<能力>/` 分层、工厂 + 实例），但**实现重写**。

参考实现中确认存在的问题（详见 `packages/common-tools/README.md` 的修复清单，共 16 项）中，影响最大的四条：

1. 所有级别都走 `console.log` → DevTools 级别筛选失效、错误日志拿不到堆栈定位；
2. `timestampFormat` 的分支被整段注释掉 → 配置形同虚设；
3. 主题是浅合并 → 局部覆盖色板会产出 `undefined` 色值；
4. 只用 `%c` 渲染 → 在 Node / CI 里打印出一堆 `%c color:#...` 噪音。

## 后果

**正面**

- 依赖版本单一来源，升级只改一行
- 无幽灵依赖，依赖归属显式
- 日志在浏览器与终端表现一致（`css` / `ansi` / `plain` 三态自适应）
- 日志可通过 sink 被测试捕获、被页面镜像、上报远端

**负面 / 代价**

- 必须遵守纪律：新增依赖先写进 catalog，否则 CI 与本地版本会漂移
- 公共包不做内部转译，由消费方的 Vite 直接处理 TS 源码——换非 Vite 工具链时需要重新评估
- 一个包同时承载 logger 与 env 两个能力，包体有意保持精简；后续新增能力应另开包而非堆进 `common-tools`

**后续约束**

- 新增公共代码：优先判断"是否只服务于一个应用"，是则不建包
- 新增第三方依赖：先加到 `web/pnpm-workspace.yaml` 的 `catalog:`
- `packages/*` 不得反向依赖 `platform/*`（根 `README.md` 铁律 4）
