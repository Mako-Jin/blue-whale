# 0038. 真实 MySQL 进流水线（h2 之外的方言必须机器必跑）

- **状态**：已采纳
- **日期**：2026-10-13
- **决策者**：舰长

## 背景

`0036` 立 CI 骨架时，后端只有一个 job，跑的是**默认 profile（h2 内存库）**。
当时的理由抄自 `application.yml` 自己的注释：「新人 / **CI** 不该被迫先装一个数据库」。

**那条理由对默认路径成立，但它被顺带当成了"MySQL 不必进 CI"。** 两者不是一回事：

| 事实 | 后果 |
| --- | --- |
| `db/migration/mysql` 那 7 个迁移脚本，只有**人**在本机手动跑过（`2026-10-12` 那轮还发现"V3 从没在 MySQL 上跑过"） | 迁移脚本的可执行性**没有**任何机器保证 —— 改坏了要等某个人想起来在本机跑一次才知道 |
| 全套用例**从没在 h2 以外的库上执行过** | 所有"只在 h2 成立"的假设都沉在水下，没人知道有多少 |

第二行是本质问题。h2 是**开发便利**（`MODE=MySQL` 只是"语法尽量贴近"），它不是交付形态；
而"全套用例只在一个库上跑过"意味着：**这一层的绿灯证明力比它看起来小得多。**

本轮把"MySQL 进 CI"当独立一轮做，第一步就是**先在本机复现 CI 的形态**，再决定 job 长什么样。
方法：不碰舰长那个已有 11 个库的本机实例（root 口令按约定由舰长现场提供、不落任何文件），
而是用 `mysqld --initialize-insecure` 另起一个**全新空实例**（独立数据目录、端口 3307）——
这正是 `services: mysql` 的形态：**空库 + 无口令 root**。

### 首次真跑的结果：5 处红（4 失败 + 1 错误）

**全部集中在两处，且根因都是"测试自己的假设"，产品代码一行没改。**

**① `AuditApiTest`：4 例（3 失败 + 1 错误），根因只有一个 —— 事务隔离级别。**

症状是一致的：审计记录**写进去了却查不到**（`$.data.total` 期望 1、实际 0），
且**没有任何报错**。定位靠三条互相独立的实证：

- 日志里 `insertRecord` 全部 `Updates: 1`，**没有任何 SQL 异常**（不是"没写进去"）；
- 失败用例的查询条件与已提交的行逐字段对得上（`action` / `target_id` / `server_time` 窗口全中）；
- **决定性实验**：把连接默认隔离级别降到 `READ_COMMITTED` 再跑 → **9 例全绿**。

机制：审计落库走的是独立的 `REQUIRES_NEW` 事务（`AuditRecorder`，这是**要保的特性** ——
业务失败要能回滚，审计不能跟着回滚）。而测试自己开着 `@Transactional`，**并且在此之前已经读过数据**。
在 MySQL 默认的 `REPEATABLE_READ` 下，那个读就把快照定住了，之后**别的事务**提交的行永远看不见。
**H2 的默认隔离级别恰好是 `READ_COMMITTED`**，所以这个坑在只跑 H2 时完全不存在 ——
它是一条**只有换库才可能现形**的缺陷。

**② `HealthControllerTest`：1 例。**

`$.data.profile` 断言写死 `"h2"`。这条断言的**意图**没问题（钉住"clone 下来不装数据库就能跑"
这个承诺），**机制错了**：它断的是"本次运行的启动参数"，于是 `-Dspring.profiles.active=mysql`
一跑就红，而红的原因与它要守的承诺毫无关系。

## 决策

### 1. 新增 job `server-mysql`，对**真实 MySQL** 跑全量用例

`services: mysql:8.0`（与开发机同主版本），命令与 `server` job **逐字相同**（`mvn -B -ntp verify`），
只多一个 `-Dspring.profiles.active=mysql`：

- **不覆盖数据源 URL**：服务发布到 3306，恰好就是 `application-mysql.yml` 里写死的地址
  ⇒ 本机能跑通的那条命令，在 runner 上是同一条（`0036` 的"命令先在本机跑一遍"才成立）。
- **不注入凭据**：profile 的默认值本来就要 root + 空口令（`${BW_DB_USERNAME:root}` / `${BW_DB_PASSWORD:}`），
  与 `MYSQL_ALLOW_EMPTY_PASSWORD: 'yes'` 正好对上 ⇒ 这个 job 里**没有 secrets 要配**。
- `MYSQL_ROOT_HOST: '%'` **必须有**：连接从宿主机经 docker 网关进来，源 IP 不是 `localhost`，
  否则报 `Access denied for user 'root'@'172.17.0.1'`。
- 与 `server` job **分开**而不是合成一个：合成后前一步失败会掩盖后一步，而这两个 job
  回答的是两个不同的问题（"默认路径还好吗" / "真实库上还好吗"）。同 `0036` 的分 job 原则。

### 2. 修测试的**假设**，不修产品代码

- **隔离级别**：给 `AuditApiTest` 显式写 `@Transactional(isolation = Isolation.READ_COMMITTED)`
  ——**把测试的假设写下来**。**否决**的替代方案：把 mysql profile 的数据源隔离级别改成
  `READ_COMMITTED`。那等于**为了测试去改产品的隔离级别**，而产品没有任何理由偏离 MySQL 默认值。
- **健康检查**：把两件事拆成两条断言，各自配一个**机制匹配意图**的写法 ——
  "接口报的 profile 与本次真正生效的一致"（读 `Environment`）／"默认 profile 是 h2"
  （**直接读 `application.yml`**，与 `DatasourceDialectTest` 同一套做法：配置改了要跟着红，
  而不是在测试里另抄一份默认值）。

### 3. 给这个 job 加一条**防假绿**自检

少了 `-Dspring.profiles.active=mysql`，默认 profile 就是 h2 ⇒ 用例照样全绿，
而这个 job 一个字节的 MySQL 都没验证到。所以构建完**查日志里的实证**，不查"配置看起来对不对"：

- `Database: jdbc:mysql`（真的连了 MySQL）
- `已启用默认管理员种子数据`（`-D...seed-*` 真到位了）
- `Successfully applied`（Flyway 真对空库执行了迁移）

三条都拿真实日志正/负例验过（见下）。

### 4. 种子开关的处置：不动 `0029` 的取舍，只在 CI 里显式打开

mysql profile **默认不开**种子（真实库的账号该由运维建，而不是应用每次启动补一个固定口令的
管理员 —— 即 `0029` 的结论）。但下面这批用例要靠一个能登录的账号，h2 下那个账号是种子给的，
所以 CI 里用 `-Dbluewhale.auth.seed-admin.enabled=true` 等四项**显式**打开并给出口令。

口令与 `application-h2.yml` 里的**是同一对**（本仓唯一的真值来源，`scripts/lib/seed-credentials.mjs`
就是从那里读的）。它们是开发/演示口令、不是秘密；`0029` 真正要禁的是"**生产包**里带固定口令"，
不适用于 CI 的一次性库。此后若要把它们当密钥管，改成 secrets 即可，命令本身不用动。

## 本机逐条验证（2026-10-13）

| 项目 | 结果 |
| --- | --- |
| 全新空实例（`--initialize-insecure` / 3307 / root 无口令 / `bluewhale` 空库） | 起来了；**这就是 CI 的形态** |
| 迁移从零执行 | `V1..V7` 全部成功，`Successfully applied 7 migrations … now at version v7`（0.83s），17 张表 |
| 种子在 MySQL 上 | 生效：2 个账号、45 条资源 |
| 修复前（全量，MySQL） | 107 例 → **4 失败 + 1 错误** |
| 修复后（全量，MySQL） | 107 例 → **0 失败 / 0 错误** |
| 修复后（全量，h2 默认） | 107 例 → **0 失败 / 0 错误** |
| 后端用例总数 | **180 → 181**（新增"默认 profile 必须是 h2"一条） |
| 防假绿自检 | 正例（MySQL 日志）放行；**负例（h2 日志）被拦住** —— 证明它不是空转 |
| workflow 结构自检 | 4 job / 22 步全通过（每步有 `uses` 或 `run`、`uses` 形如 `owner/repo@vN`） |
| 表名大小写 | 18 张表 + 16 个 `@TableName` **全小写** ⇒ 已排除"Windows 上 `lower_case_table_names=1`、Linux 上是 `0`"这条本地探针**测不出**的差异 |

**未验证（如实记下）**：`services:` 那一段**只能由 runner 跑**，本机没有 docker ⇒
镜像行为、服务健康检查、`MYSQL_ROOT_HOST` 是否足够，都还没有第一次真跑的证据。
最可能红的两处：镜像初始化与健康检查的时序、以及上面那条 `Access denied`。

## 后果

**正面**

- "MySQL 迁移脚本能不能执行"从**人记得**变成**机器必跑**；顺带每次都对**空库**从零迁移一遍
  （这正是 `flyway_schema_history` 校验和机制最怕的那种漂移的探测面）。
- 用例第一次真的在**真实库**上跑：`REPEATABLE_READ` 那一类"只在换库时现形"的问题
  从此有归口。首次跑就抓到 5 处 —— **它不是空开关**。
- 两个 job 的失败语义清晰：`server` 红 = 默认路径坏了；`server-mysql` 红 = 真实库上坏了。

**负面 / 代价**

- **后端构建时间大致翻倍**（两个 job 各跑一次 Maven，缓存共用）。
- 多一处**会变的值**：CI 里那对口令与 `application-h2.yml` 是两份副本。可接受的理由是
  **漂移的影响是良性的** —— 用例从 `AuthProperties` 读口令（`0029` 的后续约束），
  两边不一致也只会种出另一个口令、测试照样过。**已否决**的替代方案是在 CI 里用
  `node scripts/lib/seed-credentials.mjs` 取口令：它要为此给 `server` 侧引入 Node 环境，
  而收益只是消掉两个演示口令的副本。
- 真实 MySQL 带来**新的不确定性来源**（镜像版本、初始化时序）。这与"真机层不进必过项"不冲突：
  MySQL 是**流水的常规依赖**，而不是需要 GPU / 真实浏览器的真机层。

**后续约束**

- **改迁移脚本后，`server-mysql` 必须绿** —— 它是这条链路上唯一会真的执行 `db/migration/mysql` 的地方。
- **新增任何"只在某个 profile 成立"的断言前，先问它在另一个 profile 下还成立吗**（本轮的 5 处红全部源自这一类）。
- 若日后 h2 也换成 `REPEATABLE_READ`（或换别的更贴近生产的库），**`AuditApiTest` 的显式
  `READ_COMMITTED` 会再次显示出它的作用** —— 那里已经写下了为什么。

## 本决策未覆盖

- **达梦（DM8）仍然只有"配置文件与 URL 识别"层面的验证**（`DatasourceDialectTest`），
  真实实例不可得 ⇒ 它继续留在 `0010` 的"未验证清单"里。**本决策不改变它。**
- 没有做路径过滤（改了后端才跑后端 job）—— 与既有两个 job 保持一致，先不做优化。
- 没有上分支保护必需检查（属仓库设置，不在版本库里，见 `0036`）。
