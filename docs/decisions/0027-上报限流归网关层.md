# 0027. 上报限流归网关层：应用层不做限流，且不能按 `X-Forwarded-For` 限

- **状态**：已采纳
- **日期**：2026-10-13
- **决策者**：舰长

## 背景

`0026` 收尾时留了一句「发现但未处理」第 2 条：

> **`content-type` 之外的限流缺失**：两条上报通道公开且可写，当前只靠单批 500 条的上限兜底。
> 公网部署前应考虑按 IP/应用限流。

本次据此动手。但**动手前的侦察推翻了"把限流写进 `server/`"这个默认思路**。

### 一、现状：服务端一条限流也没有

在 `server/` 下逐个搜 `RateLimit` / `Bucket` / `TokenBucket` / `Throttle` / `Semaphore` /
`Quota` / `maxRequestSize` / `concurrent` —— **全部零命中**。也没有 bucket4j / resilience4j /
guava / caffeine 任何可作为基础的依赖（`sts-parent` 的 `dependencyManagement` 里没有，
15 个 `pom.xml` 里都没有）。

唯一的体量闸门是 Bean Validation 的**单批 500 条**
（`ClientLogReportRequest:54` / `ClientEventReportRequest:55`），
`server.tomcat.*` 一个字都没配过（`application.yml` 的 `server:` 块只有端口与编码）。

还有一个**从未存在过的组件**：`ResultCode.TOO_MANY_REQUESTS(42900)` 早在枚举里，
`server/README.md` 的错误码表把它归给"限流组件" —— 而那个组件在本仓不存在。

### 二、三条既有约定同时指向"不该写在应用里"

| 出处 | 原文 |
| --- | --- |
| `infra/README.md` 约定 4 | 「**网关是统一入口。** 鉴权、限流、跨域在 `nginx/` 或后端网关层解决，**不要散落在各应用里**」 |
| `docs/decisions/0003` | 「**限流阈值**」归**部署级配置** → 成熟组件（Nacos / Apollo）→ **运维** |
| 后端 **5 处**注释 | `X-Forwarded-For` 可被伪造，**不可作为鉴权或风控依据** |

### 三、最后一条才是决定性的，但它被误读了

那 5 处注释（`ClientLogController:106`、`ClientEventController:95`、`AuthController:67`、
`AuditInterceptor:197` 等）说的是"应用层不能用它"。

**成立的原因不是"IP 不可信"，而是"应用无法判断自己前面有几跳、该信哪几跳"。**
一个部署在直连公网的进程与一个部署在两层 CDN 之后的进程，读到的
`X-Forwarded-For` 含义完全不同，而应用无从区分 —— 于是最保守的做法只能是"一概不信"。

**nginx 知道答案，因为它自己就是那个代理。** `set_real_ip_from` 一旦配好，
`$binary_remote_addr` 就从"最后一跳的地址"变成真实客户端 IP。

结论：**限流不是"不该做"，而是只有在这一层才可能做对。**
在应用层按 IP 限流，会是伪造一个请求头即可绕过的**假开关** ——
比不做更坏，因为它看起来像有防护。

## 决策

### 一、限流归网关层，应用层不做

落在 `infra/nginx/`（该目录此前只有 `.gitkeep`）。**不新增任何限流依赖、不写任何限流代码。**

这意味着后端与前端**零改动**：没有新接口、没有新权限码、没有新错误码、契约不变
（`42900` 早就备着，只是"来源"列写错了，见 `server/README.md`）。

### 二、真实 IP 必须在网关层先做对，且分三态

`snippets/bluewhale-real-ip.conf` **默认全注释**，并在文件里写清三态：

| 状态 | 判据 | 不这么做的后果 |
| --- | --- | --- |
| **必须打开** | nginx 前方还有 LB / CDN | 所有客户端共用一个 IP → 限流退化成"全局一个桶" → **人一多就整片 429**，真攻击者毫发无损 |
| **绝不能打开** | nginx 就是边缘 | 用**可伪造的** `X-Forwarded-For` 覆盖真实 IP → **伪造一下即绕过** |
| **打开时逐个网段** | `set_real_ip_from` 只写自己那台代理 | 写 `0.0.0.0/0` 等于信任所有人 |

这一段是整个决策里**唯一配错也不会报错的地方**，两种错方向的表现都极难当场看出。
因此校验脚本专门有一条检查它的启用状态与网段宽度。

### 三、两条通道靠**请求方法**区分

上报 `POST /api/logs/client` 与查询 `GET /api/logs/client` 是**同一个 URI**。
用 `map $request_method` 把非 POST 的 key 置空：

```nginx
map $request_method $bluewhale_report_key {
    default  "";
    POST     $binary_remote_addr;
}
```

依据是 nginx 自己的处理逻辑 —— `limit_req` 与 `limit_conn` 都是
`if (key.len == 0) { return NGX_DECLINED; }`，**空 key 的请求不计入**。

不这样做的后果：查询接口会被上报通道的配额挤掉。那是个**已鉴权**的接口，
被误限比不限更糟 —— 表现为"日志台偶尔刷不出来"，而没人会想到是上报配额干的。

### 四、429 的形态

先明确一件事：**nginx 的 `limit_req_status` / `limit_conn_status` 默认值是 `503`，不是 `429`。**
所以下面这两行不是装饰，没有它们 `error_page 429` 永远不会被触发，而且超限会以
"服务不可用"的形态出现（与真实的宕机混在同一个告警通道里）：

```nginx
limit_req_status   429;
limit_conn_status  429;
```

然后是响应体：`error_page 429 = @bluewhale_too_many_requests;` → 命名 location → JSON：

```json
{"code":42900,"message":"请求过于频繁","data":null}
```

- 与后端的错误码表对齐（同一个 `42900`），让人一眼能对回 `ResultCode`。
- **刻意不带 `timestamp`**：nginx 拿不到 epoch 毫秒（`$msec` 是秒 + 三位小数），
  而一个"格式对、数值错"的 `timestamp` 比没有更坏 —— 与本仓「宁可不显示，不可错显示」一致。
- 前端**不需要任何改动**，这一点是核查过的：`common-tools/http` 的 `readBody()`
  对非 JSON 响应体原样返回（`client.ts:72-77`），429 走 **HTTP 状态码**分类，
  且 `errors.ts` 里 `retryable` 对 429 为 `true` —— 上报通道随即指数退避，正是想要的行为。

### 五、阈值全部走变量模板

`REPORT_RATE` / `REPORT_BURST` / `REPORT_CONN` / `API_*` / `MAX_BODY_SIZE` /
`BACKEND_UPSTREAM` 等 11 个变量放 `infra/nginx/.env.example`，不入库
（`infra/README.md` 约定 1）。理由即 `0003`：限流阈值是**部署级配置**，不同环境的合理值不同。

### 六、体量闸门补在网关

`client_max_body_size`。条数上限（500）由后端管，**字节数**上限此前**没有任何一层管**
（后端从未配过 `server.tomcat.*`）。一批 500 条到底多大，只有这一层说了算。

### 七、补一个不依赖 nginx 的结构性校验

`scripts/verify-nginx-config.mjs`。开发机既无 nginx 也无 docker（两命令均 command not found），
`nginx -t` 跑不了；但 `nginx -t` 也**查不到**下面这几类错，而它们都能让配置"通过语法检查但行为是错的"：

| 这类错 | `nginx -t` | 本脚本 |
| --- | --- | --- |
| `limit_req zone=xxx` 引用了不存在的 zone（zone 名拼错） | 只在启动时 | ✅ |
| 模板变量漏在 `.env.example` 之外（渲染后是空值） | ❌ | ✅ |
| envsubst 白名单漏了，把 nginx 自己的 `$request_method` 替换掉 | ❌ | ✅ |
| 上报路径没挂上限流 / `map` 丢了 | ❌ | ✅ |
| 真实 IP 网段被配成 `0.0.0.0/0` | ❌ | ✅ |

脚本用两个负例验证过不是空转：(a) 把 `bluewhale_report_per_ip` 改成 `bluewhale_report_typo`
→ 命中"每个被引用的 zone 都已定义"；(b) 把 `set_real_ip_from` 改成 `0.0.0.0/0`
→ 命中"没有把可信网段写成 0.0.0.0/0"。

> 顺带一提：脚本**第一次跑就抓到两个问题** —— 一个是模板注释里字面写的占位符示意（误报，
> 已把残留检查收紧到"变量形状"），一个是脚本自身只扫了模板、没扫 `include` 进来的 snippet
> （`$host` / `$remote_addr` / `$scheme` 住在 `bluewhale-proxy.conf` 里，导致假警报）。
> 两个都改掉了 —— 记在这里是因为"检查器自己不空转"这件事需要有证据。

## 后果

**正面**

- 后端与前端**零改动**：没有新依赖、没有新接口、没有新权限码、契约不变、测试数不变。
- 限流落在唯一能让"真实客户端 IP"成立的地方，因此它是**真的**，不是假开关。
- 阈值是部署级参数，改阈值不用重新构建、不用改代码。
- 补上了一个从未存在过的组件在文档里的错位（`42900` 的"来源"列）。
- 有一个可在 CI 里跑、不需要 nginx 的结构性校验。

**负面 / 代价**

- **这份配置没有在真实 nginx 上验证过。** 开发机既无 nginx 也无 docker，
  因此**没跑过 `nginx -t`，也没实际压出过一次 429**。已做的是结构性校验 + 逐条人工复核。
  首次部署前必须先 `nginx -t`。与 `0010` 达梦那条同一处置：**如实标注，不假装已验证**。
- **应用变成"没有 nginx 就没有防护"**：本地直连 `:8080`、或有人绕过网关直连后端时，**
  上限只剩单批 500 条**。这是"不散落在应用里"的必然代价，接受它。
- **限流是按 IP 的**：NAT / 企业出口 / 移动网络下，大量真实用户共用一个 IP。
  阈值定得保守会误伤，定得宽松则防护有限。`.env.example` 的默认值刻意给得宽
  （上报 20r/s，而客户端默认 3 秒才 1 个请求），**宁可拦不住异常放大，也不误伤正常用户**。
- nginx 成为一个**新的运行依赖**：本地开发不需要它，但任何非直连部署都需要。

**后续约束**

- 任何"给某个接口加限流"的需求，**先改 `infra/nginx/`，不要改 `server/`**。
  真要突破这一条（比如需要按租户配额），必须新写一篇 ADR 说明为什么网关层做不到。
- 若启用 `set_real_ip_from`，**必须同时写对网段**；`scripts/verify-nginx-config.mjs` 会挡 `0.0.0.0/0`。
- 给两个上报域**再加路径**时（比如将来有 `log:server`），要同时更新
  `bluewhale.conf.template` 的 location 与 `scripts/verify-nginx-config.mjs` 的路径清单 ——
  脚本里那份清单是**写死的两行**，它不会自动发现新路径。
- `42900` **由网关产生，不由后端产生**：后端代码里不应出现 `ResultCode.TOO_MANY_REQUESTS`
  的抛出处（除非将来真的在应用层做限流）。

## 本决策未覆盖

- **分布式灌注与慢速攻击**：按 IP 的 `limit_req` 挡不住"很多来源各打一点"，
  也挡不住慢速连接耗尽（`limit_conn` 只限数量，不限时长）。这两类属 WAF / CDN 的活。
- **采样**：`0004` 第 3 条写的是「**采样与限流是必选项**」，本次只做了限流。
  采样仍未做（`0011` 的「尚未完成」第 1 条也记着"事件采样必须按会话整体采，否则漏斗断裂"）。
- **限流与"上报尽力而为"的调优**：被 429 的批次由客户端退回队首、指数退避，
  超出 `maxBuffer` 的丢最旧。这条链路是通的，但**没有在真实压力下调过参**。
- **应用层完全不设防**：如上所述，这是有意的代价。
- **网关的高可用 / 多实例**：`limit_req_zone` 是**单机内存**的，多台 nginx 各自计数 ——
  实际上限会是"配置值 × 实例数"。要做全局配额得上 Redis 或网关产品，未覆盖。

## 发现但未处理

### 1. 开发用种子口令被编译进了生产前端包，且与 `scripts/README.md` 的硬性约束矛盾

`AuthProperties.java:158` 里 `password = "Admin@12345"`（h2 种子管理员口令）是**默认值**，
它经 `LoginRequest.java:28` 的 `@Schema(example = "Admin@12345")` 一路流进：

```
AuthProperties(默认值)
  → LoginRequest 的 @Schema(example)         ← 注释即"对外示例"
  → docs/api/openapi.json
  → common-api 的 schema.d.ts                ← 生成物入库
  → platform-portal 的登录页默认值（Login/index.tsx）
  → 生产构建产物 dist/assets/index-*.js      ← 已确认字符串在包里
```

同时 `scripts/README.md` 的「脚本的硬性约束」写着
「**凭据走环境变量**：脚本里不出现任何密码（见 `docs/decisions/0003`）」，
而 **4 个脚本**（`verify-admin-permissions` / `verify-audit-pipeline` /
`verify-micro-frontend` / `verify-portal-auth`）**都硬编码了它**，另有两个控制台的
`src/auth` 与 `src/console.ts` 也带（独立运行的 dev 账号）。

**为什么这不是"无所谓"**：`AuthProperties` 的那个值是**默认值**而不是"仅测试用"——
任何环境只要**开启种子**（`--bluewhale.auth.seed-admin.enabled=true`，
`application-mysql.yml` 的说明里就是这么教的）且没有覆盖口令，就会得到一个
**口令公开可查的管理员账号**。h2 下无所谓（每次启动空库），mysql / dameng 下不是。

**为什么本轮不处理**：它跨"后端默认值 / `@Schema` 示例 / 生成物 / 脚本约定"四处，
是一个独立的切片，塞进限流这一刀只会两边都做不干净。**已列为下一轮候选。**
