## 1. 背景与问题

场景导航需要同时回答两个诉求：

- **生产力**：用户每天通过「城池/空间」进入 OA / ERP / CRM / 知识库，要求**打开快、低配可用、可键盘操作**；
- **可视化**：管理层希望有 3D 城池作为统一入口与展示面。

如果直接把 3D 作为 MVP 前置，会引入三类不可控成本：WebGL 兼容与显卡差异、3D 资源体积与首屏预算、素材版权与许可证。任一不满足就会阻塞整个场景服务上线。

## 2. 决策

**2D 为唯一必选呈现，3D 为可选增强（M3）**；3D 未满足解冻条件前不进入编码。

### 2.1 目标行为

1. 导航、入口跳转、可见性过滤、发布/下线全部在 2D 下闭环，不依赖 3D。
2. 3D 仅消费同一份 `sc_scene` / `sc_scene_node` / `sc_node_binding` / `sc_layout_version` 数据，**不新增业务语义、不另建表**。
3. 满足任一降级条件即回退 2D：无 WebGL、低配设备、首屏超预算、FPS 持续低于阈值。降级由前端判定，服务端只下发 `threeDEnabled` 与预算参数（`GET /scene/meta`）。
4. 3D 解冻需同时满足 F-09 四条件（见 [frozen-optional-modules.md](../frozen-optional-modules.md)），包括素材来源与许可证登记。

### 2.2 实施要点

- 服务端职责止于「布局数据 + 发布快照 + 入口权限码」，**渲染引擎不在服务端**；
- 发布校验硬卡口（≤200 节点 / 深度 ≤5 / 无环 / ≥1 启用入口 / URL 白名单）对 2D/3D 共用；
- 3D 坐标字段 `coordinate_z` 在 M1 已预留，M3 启用时不需要改表；
- 前端 3D 能力收敛在共享渲染层（`whale-common-three`），不散落在业务应用。

### 2.3 备选方案与取舍

| 方案 | 结论 | 理由 |
|---|---|---|
| A. 3D 作为 MVP 必选 | 否决 | 兼容/预算/版权三重风险前置，会阻塞导航主链路 |
| **B. 2D 必选 + 3D 可选增强** | **采纳** | 2D 可独立交付并验收；3D 失败不影响主流程 |
| C. 完全不做 3D | 暂不采纳 | 可视化诉求真实存在，保留 M3 可选路径成本低 |

## 3. 影响与风险

| # | 风险 | 缓解 |
|---|---|---|
| R1 | 3D 性能不达标 | 预算卡口 + FPS<30 降级 + 资源上限；默认 2D |
| R2 | 3D 素材版权/许可证缺失 | 素材登记与许可证复核，未授权不上线（F-09 条件之一） |
| R3 | 2D/3D 数据双写漂移 | 单一数据模型，3D 只读同一布局快照 |
| R4 | 降级判定不可观测 | `GET /scene/meta` 暴露 `threeDEnabled`；前端降级原因上报日志 |

## 4. 结论与后续

- 决策结论：**2D 优先，3D 可选**；M1/M2 已按此交付。
- 后续任务：8.5（M3 3D）保持**未启动**，仅在 F-09 解冻后按独立波次立项。
- 重审条件：F-09 解冻、出现必须 3D 才能承载的业务需求、或 2D 交互被证明无法满足导航诉求。
