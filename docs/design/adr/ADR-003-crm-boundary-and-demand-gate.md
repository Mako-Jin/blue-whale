## 1. 背景与问题

CRM 是本平台最后补齐的业务域之一。开建前存在三个必须先回答的问题：

1. **是否需要建**：如果没有真实客户/商机需求，只保留外部 CRM 入口即可，避免凭空造域；
2. **客户主数据归谁**：ERP 已有客户表（`erp_customer`，用于财务与订单），CRM 若再建一套，极易出现双主数据；
3. **边界在哪**：合同、审批、消息、附件、库存、应收分别属于其他服务，CRM 不能顺手全做。

若不在编码前定稿，域模型会随实现漂移，返工成本远高于一次门禁评审。

## 2. 决策

### 2.1 需求门禁（机制）

- 任何 CRM 业务编码前必须通过门禁评审，并在 `requirements/register.md` 登记 REQ 编号与验收标准；
- 服务内以配置 `whale.crm.demand-gate-passed`（默认 `true`）作为**唯一开关**：置 `false` 时服务回退为「仅 `/crm/meta` 的维护态」，业务端点不生效；
- 门禁结论、范围与不做的内容写入 `crm-service.md` §1，变更须同步更新。

### 2.2 客户主数据归属

**CRM 拥有客户主数据**（`crm_customer` 为唯一客户聚合根）；ERP 只拥有供应商，**不拥有客户主数据**；
合同域「相对方」只保存 `crmCustomerId` 快照，不回写、不复制客户档案。

### 2.3 职责边界

| CRM 拥有 | CRM 不拥有（下游/上游） |
|---|---|
| 客户、联系人、跟进、公海 | 供应商主数据（ERP / 未来 SRM） |
| 线索、商机、销售阶段、报价版本 | 合同正文与签署（`whale-contract`） |
| 合同台账投影、回款计划、商务订单、开票申请、售后工单与 SLA、营销与分析 | 审批（`whale-workflow`）、消息投递（`whale-message`）、附件字节（`whale-file`） |
| 客户编码规则与数据权限范围 | 库存、发货、应收应付记账（ERP） |

- `whale-crm → auth` 为**遵奉者**：身份与权限码只来自网关注入，不另造身份源；
- `whale-crm` 与 `whale-erp` **不共享主数据表**；跨域只走内网 REST 或事件（如 `CRM-SO-{orderNo}` 幂等下发订单、退换货下发 ERP 销售退货）；
- 所有跨服务调用走 `/**/internal/**` + `X-Internal-Token`，对外 403。

### 2.4 备选方案与取舍

| 方案 | 结论 | 理由 |
|---|---|---|
| A. 不建 CRM，仅外链第三方 | 否决 | 用户已提供 6 大模块 29 子模块的真实全景需求 |
| B. 客户主数据放 ERP，CRM 只读 | 否决 | 客户归属、公海、跟进、商机是 CRM 的聚合行为，放 ERP 会把销售域塞进财务域 |
| **C. CRM 拥有客户，ERP 拥有供应商，合同存快照** | **采纳** | 单一主数据归属清晰；跨域只引用 ID 与快照，避免双写 |
| D. 无门禁直接开工 | 否决 | 域边界未定会导致 M3–M6 反复返工（R5） |

## 3. 影响与风险

| # | 风险 | 缓解 |
|---|---|---|
| R1 | 客户主数据与 ERP 重复 | 明确 CRM 唯一归属；ERP 侧客户仅作财务往来对象，禁止反向同步为 CRM 客户 |
| R2 | 合同相对方与 CRM 客户漂移 | 合同只存 `crmCustomerId` 快照；客户合并时执行跨上下文引用重写（M1 已实现） |
| R3 | 门禁开关被误关导致业务静默不可用 | 开关状态在 `GET /crm/meta` 暴露；运维监控启动日志；变更需走发布流程 |
| R4 | 新服务增加 CI/部署矩阵成本 | 复用 Dockerfile 模板与镜像矩阵，按需启用 |
| R5 | 权限/菜单编号冲突 | 使用预留段（337–354）与已登记号段，迁移脚本幂等 |

## 4. 结论与后续

- 决策结论：**门禁通过（2026-11-04），CRM 拥有客户主数据，边界如上**；M0–M6 已按此交付。
- 后续任务：新增 CRM 能力前先核对本 ADR 边界；若需改动客户主数据归属，必须新开 ADR 取代本文。
- 重审条件：ERP 或 SRM 提出客户/供应商合并建模、合同域要求回写客户档案、或门禁开关机制被证明不可运维。
