| # | 问题 | 结论 |

## 1. 三方边界

```
前端（底图 SDK：腾讯 GL JS / 高德 JS API）
      │  只拿「坐标 + 标准地址」，不拿 Key
      ▼
whale-map（8100，/map/**）
      │  坐标口径、供应商选择、配额、缓存、打点数据都在这里
      ▼
腾讯位置服务 / 高德开放平台（HTTP，服务端 Key）
```

- **前端**：画底图、画点、画线。切供应商只换 SDK，接口不变。
- **whale-map**：唯一的 Key 持有者。任何「坐标从哪来」的疑问都在这层能查到答案。
- **供应商**：只被当能力提供方，不承担业务语义。

**明确非目标**：轨迹回放、实时定位推送、路径导航 GUI、瓦片代理、离线地图。这些要么是另一个产品，要么会违反「仅 443 对外」的网络边界。

## 2. 坐标系口径（这是最容易错的地方）

### 2.1 约定

| 环节 | 坐标系 | 说明 |
|---|---|---|
| 落库（`map_location.lng/lat`） | **WGS84** | GPS 原始值、国际标准、无损可逆 |
| 对外响应 / 前端展示 | **GCJ-02** | 腾讯、高德、天地图都在用 |
| 百度接口边界 | BD-09 | 只在适配器内部出现，不出现在任何表、任何响应里 |
| Provider SPI 契约 | **WGS84** | 适配器负责把自家坐标转进来、把结果转出去 |

### 2.2 为什么这样定

- **存储放 WGS84**：GCJ-02 是加偏结果，反算只能迭代逼近（本服务用 5 次迭代，误差压到 1e-9 度）。如果存 GCJ-02，每次读出来做距离计算都要先反算一次，误差层层累积，而且「同一个点」在不同路径下会算出不同坐标。
- **展示放 GCJ-02**：国内底图都是 GCJ-02，输出 WGS84 会整整偏 300–500 米——用户看到点在马路对面。
- **转换只在出入口各一次**：链路中间（缓存、打点、附近查询）一律用 WGS84，绝不来回倒手。

### 2.3 一个必须记住的陷阱

`GeoDistance.meters(a, b)` 会**自动把 b 转到 a 的坐标系**再算。这是为了防止「跨供应商结果直接相减」，但也意味着：**用它度量「加偏前后偏移量」会得到 0**（两点被统一后重合）。单测里已就此写了注释，避免后来者把它当 bug 改掉。

## 3. 供应商 SPI、能力路由与降级

### 3.1 契约

```java
public interface MapProvider {
    String name();
    boolean supports(MapCapability capability);
    boolean configured();              // Key 与基址齐全
    GeocodeResult geocode(GeocodeQuery query);
    RegeoResult regeo(RegeoQuery query);
    PoiPage searchPoi(PoiQuery query);
    RouteResult route(RouteQuery query);
}
```

- 入参出参**一律 WGS84**，适配器在边界换算。
- 失败抛 `BizException`，**不返回 null**：null 会让「供应商挂了」与「查无此地」混为一谈。

### 3.2 路由

```yaml
whale:
  map:
    default-provider: tencent
    capability-routing:
      GEOCODE: tencent
      REGEO: tencent
      POI: tencent
      ROUTE: amap          # 高德路径规划作为首选
      DISTANCE: local      # 本地球面计算，不消耗任何配额
    fallback: [amap]
```

候选链 = 能力路由 → 默认供应商 → 降级链，去重后逐个尝试，过滤掉「不支持该能力」与「未配置 Key」的。

### 3.3 降级 ≠ 重试

主供应商失败**立刻换下一家**，不在同一家重试。理由：对「Key 失效」「配额用尽」这类确定性失败，重试只是让用户多等一个超时周期；对网络抖动，换一家比再等一次更快出结果。

### 3.4 配额

- 落库按 `(tenant_id, provider, usage_date)` 唯一。
- 准入是一条**原子条件更新**：`WHERE used_count < limit_count`。先查后改在并发下会一起通过检查，超出的那几次正好是「以为还有额度」的时刻。
- 计数表不可用时**放行**并告警：把统计功能升级成单点故障，代价远大于多打几次接口。
- 每次调用**先占配额再外呼**，宁可浪费几次，不可超用（供应商超限会直接拒绝服务）。

## 4. 数据表（`bluewhale_map`，3 张）

| 表 | 作用 | 关键设计 |
|---|---|---|
| `map_location` | 业务对象打点 | 唯一键 `(tenant_id, biz_type, biz_id)`；`biz_id` 用字符串兼容各类主键；经纬度 `DECIMAL(10,7)/(9,7)`（约 1 厘米，比较精确）；`geohash VARCHAR(12)` + 普通索引 |
| `map_geocode_cache` | 地址解析缓存 | 唯一键 `(tenant_id, provider, query_type, cache_key)`；`cache_key` 是查询串 SHA-256（等长，超长地址不会撑爆索引）；TTL 默认 90 天 |
| `map_quota_usage` | 供应商日配额 | 唯一键 `(tenant_id, provider, usage_date)`；`limit_count = 0` 表示不限 |

### 为什么这三张表都没有 `deleted` 列

它们都不是业务单据，而是**状态**：一个对象当前在哪、某个地址上次解析成什么、今天用了多少配额。状态表的正确语义是覆盖写与物理删除。

挂上逻辑删除会立刻撞上一个具体问题：`map_location` 的唯一键是 `(tenant_id, biz_type, biz_id)`，删掉一个对象的打点后再打一次，逻辑删除的旧行还占着键，插入直接失败。把 `deleted` 编进唯一键也救不了——`deleted` 只有 0/1 两个值，删两次照样撞。

### 为什么 M0 不建 `map_region`

原方案 §3.6 里有它（行政区 + 围栏，`ST_Contains` + POLYGON）。本轮不建，理由是口径没定：围栏多边形通常来自 GCJ-02 底图，而点位存的是 WGS84，直接 `ST_Contains` 会有 300–500 米偏差。**先把「围栏坐标系与点的坐标系必须同源」这条定下来，再建表**，否则建出来的是一张看着能用、判定结果悄悄错的表。围栏（P1）与打卡范围一并放 M1。

## 5. 接口（9 个）

| 方法 | 路径 | 权限 | 说明 |
|---|---|---|---|
| POST | `/map/geocode` | `sys:map:geo:query` | 地址 → 坐标（带缓存，响应含 `cached`） |
| POST | `/map/regeo` | 同上 | 坐标 → 地址 |
| GET | `/map/poi/search` | 同上 | POI 检索（`keyword`/`city`/`page`/`size`） |
| POST | `/map/route` | 同上 | 驾车/步行/骑行 |
| POST | `/map/distance` | 同上 | 批量直线距离（本地计算，不耗配额，结果按下标对齐） |
| PUT | `/map/location/{bizType}/{bizId}` | `sys:map:location:manage` | 打点（幂等覆盖；给坐标或给地址二选一） |
| GET | `/map/location/{bizType}/{bizId}` | `sys:map:location:query` | 查询打点（未打点返回 `null`） |
| POST | `/map/location/{bizType}/{bizId}/remove` | `sys:map:location:manage` | 取消打点（物理删除） |
| GET | `/map/location/nearby` | `sys:map:location:query` | 附近查询（`lng`/`lat`/`radiusMeters`/`limit`） |
| GET | `/map/provider/health` | `sys:map:provider:view` | 供应商状态与今日配额余量 |

响应中的坐标**一律带 `coordType`**。不是冗余：下游存下来时总要知道这串数字属于哪个坐标系。

## 7. 验收

1. `PUT /map/location/CRM_CONTACT/1001` 只传 `address` → 返回 `source=GEOCODE`、`adcode` 已回填；再调一次只传 `lng/lat` → 同一条记录被更新（不新增）。
2. 同一地址连续 `POST /map/geocode` 两次 → 第二次 `cached=true`，且 `map_geocode_cache.hit_count` 递增。
3. 把 `TENCENT_MAP_KEY` 置空、保留高德 Key → `GEOCODE` 自动由高德出结果，响应 `provider=amap`。
4. 把某供应商 `quota-per-day` 调成 1 → 第二次调用跳过它，`/map/provider/health` 显示 `remaining=0`。
5. `GET /map/location/nearby?lng=116.404&lat=39.915&radiusMeters=500` → 只返回半径内点位，按距离升序。
6. 跨供应商场景：先用高德解析、再用腾讯解析同一地址 → 两点距离 < 50 米（说明坐标系已统一；若差 300 米以上，说明漏了一次转换）。

## 9. 待确认

1. **Key 归属与计费**：腾讯/高德 Key 由谁申请、算哪个成本中心？两家都有免费额度，但企业 Key 需要实名。
2. **前端底图策略**：前端展示用哪家底图（腾讯 GL 还是高德 JS）？服务端的 `displayCoord` 已固定 GCJ-02，所以两家都能用，但底图 SDK 需要单独的前端 Key（带 Referer 白名单）。
3. **配额上限**：当前默认 10000/天/供应商。若日活过万，地址解析会先撞上限——届时优先扩缓存命中率，不是直接加配额。
4. **合规**：批量点位含个人信息，轨迹与打卡数据不得对外发布。M0 未做轨迹，M1 做围栏时需要同步过一遍合规。
