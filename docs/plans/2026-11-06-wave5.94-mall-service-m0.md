# Wave 5.94 商城服务（whale-mall）M0 计划

> 日期：2026-11-06　状态：**已批准（用户「可以兼容吗」→ 一套内核兼容三种商城形态）**
> 依据：`docs/architecture.md`（服务边界与 REQ-ARCH-003 自持前缀）、`docs/naming-conventions.md` §三/§八、`whale-pay`（支付出口）、`whale-file`（素材字节）
> 目标：M0 打通「建商品 → 上架 → 加购 → 下单 → 取消/支付 → 发货 → 完成」主干，跑通一个真实可演示的闭环。

---

## 一、结论：一套内核兼容三种商城形态

商城不是一个「页面」，而是三件不同的事共用了同一套商品与订单。因此**不建三个服务、也不做三套表**，而是把差异收敛到两个可替换的策略上：

| 维度 | 零售（RETAIL） | 经销订货（B2B） | 员工福利（WELFARE） |
|---|---|---|---|
| 买家身份 | 平台用户 | 平台用户（代表客户） | 员工（平台用户） |
| 价格来源 | `RETAIL` 价目 | `B2B` 价目，缺失回落 `RETAIL` | `POINTS` 价目，缺失**直接失败** |
| 结算方式 | 在线支付 | 在线支付 / 账期（M1） | 福利积分扣减（M1） |
| 币种口径 | CASH（元） | CASH（元） | POINTS（积分） |
| 履约 | 快递发货 | 发货 / 自提 | 发放 / 自提 |

落地为三张「配置面」而非三份代码：`mall_channel.mode`（形态）、`mall_channel.settlement_type`（结算）、`mall_sku_price.price_type`（价目）。**新增第四种形态只需要加枚举值 + 一条价格解析规则，不改表结构。**

为什么不按形态拆服务：三者 80% 的表是同构的（商品、SKU、库存、购物车、订单、明细），拆开就是三份同构代码同步演进，最终分叉成三个互不兼容的「商城」。真正的差异只有「这一单多少钱、怎么收」，这恰好是策略层能吸收的。

## 二、服务边界

**做**：商品中心（类目 / SPU / SKU / 多价目 / 可售库存）、商城渠道、购物车、订单（含下单试算、幂等、库存预占与释放、状态流转）、订单发货与完成。

**不做（明确交接）**：

| 能力 | 归属 | 本服务的动作 |
|---|---|---|
| 支付下单、对账、退款 | `whale-pay` | 只落 `pay_no` 与支付时间；回调走 `/mall/internal/order/paid` |
| 图片与详情附件字节 | `whale-file` | 只存 `file_id` / URL 引用 |
| 订单通知（下单成功、发货） | `whale-message` | 只记通知意图，M1 接 |
| 客户档案与等级 | `whale-crm` | M0 不读；买家统一为平台用户，`customer_id` 列预留 |
| 商品主数据与实物库存 | `whale-erp` | 商城**自建商品中心**（用户 2026-11-06 定）；ERP 对账在 M2 以「库存差异表」形式做，不做实时双向同步 |

## 三、数据模型（V2，9 张表）

| 表 | 语义 | 关键约束与理由 |
|---|---|---|
| `mall_category` | 类目树 | `(tenant, parent_id, category_name)` 唯一。**同级不允许重名**——跨级同名是常态（「配件/电池」与「耗材/电池」），用全路径唯一会把正常业务挡在门外 |
| `mall_spu` | 商品 | `(tenant, spu_code)` 唯一；`status` = DRAFT / ON_SALE / OFF_SALE |
| `mall_sku` | 规格 | `(tenant, sku_code)` 全局唯一（**不是 spu 内唯一**）：拣货、对账、售后都按 SKU 编码单点定位，允许两个 SPU 撞码等于埋雷 |
| `mall_sku_price` | 价目 | `(tenant, sku_id, price_type)` 唯一，三种 `price_type` 各一行；**不用一列多字段**（`retail_price`/`b2b_price`/`points_price`），否则加一种价目就要改表 + 改所有 DTO |
| `mall_sku_stock` | 可售库存 | 一 SKU 一行；`available_qty` 可售、`reserved_qty` 已预占。**扣减用条件更新**（`WHERE available_qty >= ?`），不先查后改 |
| `mall_channel` | 商城渠道 | `(tenant, channel_code)` 唯一；`mode` + `settlement_type` + `currency_type` |
| `mall_cart_item` | 购物车 | `(tenant, channel_id, user_id, sku_id)` 唯一——重复加购走「数量累加」而不是插第二行 |
| `mall_order` | 订单 | `(tenant, order_no)` 唯一；`(tenant, user_id, idempotency_key)` 唯一（幂等键落库，不靠 Redis） |
| `mall_order_item` | 订单明细 | 落**商品快照**（名称/规格/图/单价），商品改名改价不影响历史订单 |
| `mall_order_log` | 状态流水 | 只追加；谁在什么时候把单子从什么状态改到什么状态 |

金额口径：

- 现金单 `DECIMAL(12,2)`，积分单同样 `DECIMAL(12,2)` 但**校验为整数**（0.5 积分没有业务含义，允许它只会让对账时出现无法解释的小数）。
- 币种由渠道 `currency_type` 决定，订单落快照 → 后续渠道改配置不影响历史单。
- 全程 `BigDecimal`，禁止 `double`；比较用 `compareTo`，不用 `equals`（`1.0` 与 `1.00` 不等）。

## 四、订单状态机

```
PENDING_PAYMENT ──pay──> PAID ──ship──> SHIPPED ──complete──> COMPLETED
       │
       └──cancel──> CANCELLED
```

**只允许这四条边**，其余一律 `ORDER_STATE_CONFLICT`：

- `PAID` 不能取消：钱已收，取消等于退款，退款是 M1 的独立流程（要有审批与流水），塞进取消里会让「取消」这个动作有时退钱有时不退。
- `SHIPPED` 不能取消：货在路上；逆向走售后。
- 支付回调幂等：已 `PAID` 再回调直接返回成功（**不报错**），否则支付方重试会打出成片的失败告警。

## 六、关键判断（容易做错的点）

1. **下单必须一次事务内完成「扣库存 + 建单 + 清购物车」**，且扣库存放在最前：后扣会出现「单已建、库存没了」的半成品单；先扣失败则直接结束，没有补偿。
2. **幂等键落唯一索引，不落 Redis**：Redis 过期后重复提交照样建单，而唯一索引永远有效。冲突时返回已存在订单（200），不返回 409 —— 用户双击不该看到错误。
3. **购物车价格不落库**：加购只存 SKU 与数量，价格在下单试算时实时解析。落价会出现「加购时 9.9，结算还是 9.9」而商品早调价的口径漏洞。
4. **订单明细必须存快照**：商品名/规格/图/单价全部复制一份。只存 `sku_id` 的话，商品下架删除后订单详情就只剩一串数字。
5. **B2B 价缺失回落零售价，福利价缺失直接失败**：前者是常见商业规则（未签约客户按零售价），后者是事故（把 99 元当 99 分积分卖出去）。
6. **库存扣减用条件更新**，`affected == 0` 即库存不足。先 `select` 再 `update` 在并发下必然超卖，而且超卖不会报错——只会发不出货。
7. **取消释放预占，发货才扣预占**：`available` 在下单时就减掉（防超卖），`reserved` 记「已卖未发」。发货只减 `reserved`，再减 `available` 会把库存扣两次。
8. **不建「商品可售范围」表**：M0 所有上架商品对渠道全可见。建范围表但没维护界面，结果是「建了渠道但商品全不显示」，比不做更糟。
