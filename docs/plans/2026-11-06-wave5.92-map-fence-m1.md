## 1. 为什么现在做，先解决什么

M0 留下了围栏没做，理由是「口径没定」：围栏多边形通常从 GCJ-02 底图画出来，而点位存 WGS84，
直接 `ST_Contains` 会偏 300–500 米。**这个口径必须有人拍板，否则它会一直挂在待办里**。

本轮把它定死并落成代码：

| 环节 | 坐标系 | 转换点 |
|---|---|---|
| 前端绘制 / 提交 | GCJ-02（或声明任意坐标系） | 服务端入口转一次 |
| 落库 `map_fence` | **WGS84**，与 `map_location` 同源 | — |
| 判定运算 | WGS84 | — |
| 返回前端 | GCJ-02 | 服务端出口转一次 |

一条铁律：**围栏与点位同源，转换只在出入口各一次**。中间任何一环再转一次，结果就会偏 300 米，
而且数据看起来完全正常。

## 2. 为什么不用 MySQL 空间函数

`ST_Contains` 在 MySQL 里默认按「度」在笛卡尔平面上算：

- 经度 1 度在北京约 85 公里、在赤道约 111 公里 → 同一段经度差在南北方表示的距离不同，围栏被拉伸；
- 换 SRID 4326 能改善，但要求所有数据严格同源，而 **SRID 写错不报错**，只会让判定悄悄偏几百米；
- 「离边界还有多远」在 SQL 里更难表达，而打卡场景恰恰需要它（提示「还差 30 米」）。

所以改为三段式：

1. **bbox 粗筛（SQL）**：`min_lat <= ? AND max_lat >= ? AND min_lng <= ? AND max_lng >= ?`，走索引；
2. **局部等距投影（应用层）**：以**查询点**为原点，`x = Δlng × cos(lat₀) × 111319.49`、`y = Δlat × 111319.49`；
3. **射线法（PNPOLY）+ 点到线段距离**：判定内外，并给出到最近边的距离。

以查询点为原点而非围栏质心：查询点投影后恒为 `(0,0)`，它自身不引入误差，判定只承受顶点投影误差。
几公里范围内该误差小于千分之一，稠密打卡场景（100 米级）完全够用。

## 3. 表设计

`map_fence`（`V2__fence.sql`）：

| 字段组 | 说明 |
|---|---|
| `fence_type` | `CIRCLE` / `POLYGON` |
| `center_lng` / `center_lat` / `radius_meters` | 圆 |
| `points` | 多边形顶点 JSON `[[lng,lat],...]`，首尾不闭合 |
| `min_lng` / `max_lng` / `min_lat` / `max_lat` | 外接矩形，粗筛用 |
| `biz_type` / `biz_id` | 归属：空=通用，只有 type=只绑类型，两者都有=绑对象 |
| `enabled` | 停用不参与判定 |
| `deleted` | **逻辑删除** |

**与 V1 三张表相反，本表有 `deleted`**：V1 的三张是「状态」（对象在哪、地址解析成什么、今天用了几次），
覆盖写与物理删除才是正确语义；围栏是「配置单据」，打卡记录与配送单会长期引用它，删掉后仍需指回一个
能解释的名字，误删也要能恢复。因为**允许同名围栏并存**，本表不建唯一键，逻辑删除也就不会引发撞键。

**顶点上限 200**：再多说明有人在拿行政区边界当打卡范围，判定会变慢且没有业务意义。
**单租户上限 500 个**：超过说明围栏被当数据表在用。

## 4. 接口（6 个）

| 方法 | 路径 | 权限 | 说明 |
|---|---|---|---|
| POST | `/map/fence` | `sys:map:fence:manage` | 保存（`id` 空则新建，否则覆盖） |
| GET | `/map/fence/page` | `sys:map:fence:query` | 分页 |
| GET | `/map/fence/{id}` | `sys:map:fence:query` | 详情 |
| POST | `/map/fence/{id}/remove` | `sys:map:fence:manage` | 逻辑删除 |
| POST | `/map/fence/{id}/contains` | `sys:map:fence:query` | 已知围栏问一点 |
| POST | `/map/fence/match` | `sys:map:fence:query` | 已知一点问全部（打卡用） |

两个判定接口刻意分开：打卡是「用户到了某个位置，找出命中的考勤组」（`match`），
配送是「这个地址在不在配送范围内」（`contains`）。合成一个会让调用方每次都要传一个可能为空的 `fenceId`。

`match` 只返回 `inside=true` 的围栏，按 `distanceMeters` **降序**——越靠中心越前，打卡时「最稳的那一圈」排第一条。
**空数组表示不在任何范围内，不是错误**，调用方不要当异常处理。

`distanceMeters` 有符号：内正外负。`contains` 返回 `-30` 就是「超出 30 米」。

## 5. 三个容易踩的坑

### 5.1 bbox 跨 180 度经线会让围栏被静默跳过

跨线围栏顶点一半在 179.x、一半在 -179.x。按 min/max 写成 `179 → -179`，SQL 条件
`min_lng <= ? AND max_lng >= ?` 永远为假——不报错、不命中，排查时只能看到「围栏明明存在却不生效」。

写入时识别跨线（`maxLng - minLng > 180` 或越界），把 bbox 放成 `-180`/`180`。
**粗筛宽松可以接受，漏判不行。**

### 5.2 GeoJSON 式闭合顶点会产生一条零长度边

前端传 `[[a],[b],[c],[d],[a]]` 时，末点与首点重合。射线法遇到零长度边会算错交叉次数。
写入与判定两侧都做去重（`dropClosingVertex`），双保险。

### 5.3 圆形围栏的 bbox 要留余量

半径换算成度再换算回米有浮点误差，bbox 卡到刚好等于半径会让边缘点被粗筛掉。
按 1.05 倍外扩。

## 6. 验收

1. 画一个 200 米圆，`POST /map/fence/{id}/contains` 传圆心 → `inside=true`、`distanceMeters≈200`。
2. 传原点外 130 米 → `inside=false`、`distanceMeters≈-30`。
3. 存一条跨 180 度经线的多边形 → `SELECT min_lng, max_lng FROM map_fence` 得到 `-180 / 180`
   （若得到 `179 / -179`，粗筛会把这条围栏永久跳过）。
4. 存一个 L 形围栏 → 凹口内的点 `inside=false`，长边内的点 `inside=true`。
5. `POST /map/fence/match` 传 `bizType=OA_ATTEND&bizId=12` → 只返回该考勤组围栏与通用围栏，
   别的考勤组的围栏不出现。
6. 删掉围栏后 `GET /map/fence/{id}` → 404 语义（`44030`），但 `SELECT * FROM map_fence WHERE id=?` 仍能看到该行。

## 7. 非目标

| 不做 | 理由 |
|---|---|
| 行政区边界判定 | 需要行政区多边形数据（另采），且行政区是「面数据」不是「打卡范围」，放 M2 |
| 围栏内点位统计/热力 | 属报表，需要聚合查询与缓存，不属于地图服务 |
| 打卡结果落库 | 属考勤业务（`whale-oa`），地图只回答「在不在范围内」，不替业务下结论 |
| 前端围栏编辑器 | 与 M1-1 共享包一起做（需要前端底图 Key） |
| 轨迹与围栏的进出事件 | 轨迹本身是 M1 外内容，事件流需要 MQ |
