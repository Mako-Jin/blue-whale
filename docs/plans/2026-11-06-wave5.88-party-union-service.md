## 1. 决策变更：从「并入 OA」改为「独立起服务」

### 1.1 变更内容

| 项 | Wave 5.87 原决策 | 本稿决策 |
|---|---|---|
| 部署形态 | 并入 `whale-oa`，作为 `com.bluewhale.oa` 下的 `party` / `union` 两个子包 | **独立应用 `whale-party`** |
| 库 | `bluewhale_oa` 内建 `oa_party_*` / `oa_union_*` | **独立库 `bluewhale_party`**，前缀 `pty_` |
| 端口 | 复用 9004 | **9009** |
| 前端 | 复用 8103 `whale-oa` 加两组菜单 | **独立子应用 8116 / base `/party`** |
| 权限 | `sys:oa:party:*` / `sys:oa:union:*`（1950–1999，登记为 OA 扩展段） | **`sys:party:*` / `sys:union:*`**（号段仍为 1950–1999，**归属改为本服务自有段**） |
| 迁移脚本 | OA `V7` / `V8` | `whale-party` 自有 `V1` 起编号 |
| 发布节奏 | 跟随 OA 波次 | 独立发布，不受 OA M2/M5 进度约束 |

**号段不重排**：1950–1999 与菜单 470–489 原就登记给党政工会，只是当时挂在 OA 名下、编码带 `sys:oa:` 前缀。改独立服务后**号段沿用、前缀改 `sys:party:` / `sys:union:`**，避免牵动已发布的权限迁移。代价是权限码前缀与登记表里的「OA 扩展段」措辞需要同步改写（见 §9）。

### 1.2 为什么可以独立（原「并入 OA」的三条理由如何替代）

Wave 5.87 §1 里否决新建 `whale-party` 的理由有三条。逐条给出替代方案：

| 原理由 | 独立后的处理 | 评价 |
|---|---|---|
| 党建内容发布可复用 OA 公告 + 网盘 + 文件 | **不再复用 OA 公告**，自建 `pty_content`（附件仍归 `whale-file`）。党建内容要「先审后发」，OA 公告没有审核态、且发布即进全员时间线；把未审内容塞进公告表等于绕开审核 | 原理由站不住：这是两种不同的发布语义，共用一张表迟早要在查询里到处加「这条是党建的吗」 |
| 组织生活 / 慰问 / 福利走 OA 审批底座（Workflow） | 直接调 `whale-workflow` 的通用流程接口，**不读 `oa_approval_config`**。审批底座本来就是 workflow 服务；OA 的 `oa_approval_*` 是它自己的业务表 | 原理由高估了复用度：真正被复用只有 workflow 服务本身，与 OA 无关 |
| 党员 / 会员台账是「行政人事」的自然延伸 | 改为**复用 ERP 员工只读契约** `GET /erp/internal/employee/directory`（M5 已建，含 `orgCode`），只读同步快照，做法与 LMS 一致 | 独立后反而更干净：党工只需要「谁在职、属于哪个组织」，不需要 OA 的审批上下文 |

### 1.3 代价（必须承认）

1. **运维面 +1**：多一个服务进程、一个库、一个前端子应用。启动脚本、监控、告警、数据库备份都要加一份。
2. **员工快照重复**：`whale-lms` 的 `lr_member_snapshot` 与 `whale-party` 的 `pty_member_snapshot` 会各存一份在职员工。**不做共享库、不做跨库读**——两个域各自同步、各自容错，一方 ERP 拉取失败不影响另一方。
3. **跨服务一跳**：审批与通知从「OA 本地调用」变成「HTTP 内网调用」，多一跳网络与一套超时降级策略。
4. **组织架构口径**：`orgCode` 来自 ERP 契约。若 ERP 组织调整（部门合并），支部归属需人工复核——**不做自动跟随**（支部是党组织单元，不是行政部门的镜像，自动跟随会把支部并错）。
5. **前端包体**：新增一个子应用，基座需多注册一项。

## 3. 上下文分区

```
com.bluewhale.party
├── branch    支部台账（编码取号/名称/上级支部/层级/书记/成立日期/启停）
├── member    党员台账（组织关系转入转出/入党日期/党龄/党费基数/预备转正）
├── activity  三会一课与主题党日（计划/完成/归档 + 逐人签到明细 `pty_activity_signin`）
├── fee       党费标准档位与月度收缴（档位左闭右开 / 应收生成 / 实收登记 / 免缴留痕）
├── content   党建内容与先审后发（草稿→待审→发布→下线/退回）
├── union     工会（会员/慰问帮扶/福利发放/活动报名/职代会提案）
├── integration  ERP 员工只读、whale-file 附件、whale-message 通知、workflow 审批
├── common    PartyActor / PartyErrorCode / PartyPermissions
└── config    PartyProperties
```

**为什么 `member` 与 `union` 分开**：党员与工会会员是两套台账，同一个人可能只是其中之一，党费基数和会费标准也不同。合在一张 `pty_member` 里会出现大量「党员但非会员」的 NULL 列。

**为什么 `fee` 独立于 `member`**：党费基数挂在党员身上，但**每月应收/实收是一条条流水**，且存在减免、补缴、跨月调整。基数变了不能改历史流水。

## 5. 关键规则

1. **先审后发**：`content` 的状态机是单向的（草稿→待审→发布→下线），**发布态的任何修改都退回待审**，不允许「编辑即生效」。理由：党建内容对外代表组织口径，改了没人看就等于没有审核。
2. **支部编码取号**：走 `pty_sequence` 编号流水表（`SELECT ... FOR UPDATE` 加锁自增 + 唯一键兜底重试），**不用 `MAX()` 也不用 `COUNT`**——`MAX()` 在删除过末号后会回退发出重复编号，`COUNT` 更是连中间空洞都补不上；两者还要解析全部历史编码格式，规则一改就错。流水表还能表达「按年重置」（`seq_date = yyyy`），这是靠解析编码做不到的。
3. **上级支部不成环**：保存时沿父链上溯，遇到自己即拒绝；深度上限 10 层。
4. **党员离职不删档**：转出/离职只改状态并记转出日期，历史参会与党费保留——组织关系转出不是「这个人没入过党」。
5. **党费流水不可改**：应收生成后只能登记实收或新增减免记录，**不覆盖原应收**；补缴另起一条并标注所属月份。
6. **敏感字段最小化**：党员台账存身份证号时**只存后四位 + 哈希**（用于去重），完整号码不入库；手机号按需展示时脱敏。导出默认不含身份证与手机号。
7. **员工快照只读**：`pty_member_snapshot` 由 ERP 契约单向同步，**party 侧不回写 ERP**；同步失败保留旧快照并告警，不清表。
8. **审批降级**：workflow 不可达时，慰问/福利申请**保存为草稿**并提示稍后提交，不丢数据也不假装成功。

## 6. 与既有服务的关系

| 能力 | 归属 | 交互方式 |
|---|---|---|
| 员工/组织主数据 | `whale-erp` | 内网只读 `GET /erp/internal/employee/directory`（含 `orgCode`），单向同步快照 |
| 附件与封面 | `whale-file` | 只存 `fileId` 引用，不存字节、不转码 |
| 通知（转正/催缴/活动/提案） | `whale-message` | 内网 `POST /message/internal/send`，幂等键去重 |
| 慰问/福利审批 | `whale-workflow` | 通用流程发起与回查；**不读 `oa_approval_config`** |
| 统一身份与权限 | `whale-service-auth` | 网关注入 `X-User-Id` / `X-Roles` / `X-Permission-Codes`，本服务不解析 JWT |
| OA | `whale-oa` | **无依赖**。差旅/请假等行政流程留在 OA，党工不反向调用 |
| LMS | `whale-lms` | **无依赖**。党员学习时长如后续要看，走 LMS 公开接口而不是读它的库 |
