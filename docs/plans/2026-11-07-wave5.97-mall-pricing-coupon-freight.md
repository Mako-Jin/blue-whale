# Wave 5.97：商城计价重构——优惠券与运费

> 状态：**已实施**（2026-11-07；whale-mall 单测 180 / 覆盖率行 50.5%·分支 46.3% / ArchUnit 7 上下文 / 前端 tsc+build+lint 全绿）
> 前置：Wave 5.95 M1 支付闭环（`24da861`）、Wave 5.96 售后单与部分退款（`a807b4f1`）
> 口径：先落「金额构成 + 分摊」，再落运费与券；单券不叠加；积分商城不参与

## 1. 为什么现在必须做

订单金额现在只有一个 `total_amount`，语义是「商品行小计之和」。一旦引入优惠与运费，这个字段会被四拨人各按各的理解使用：

- 支付单拿它当扣款金额（应该扣「应付」）
- 售后拿它当可退上限（应该按「实付」退）
- 报表拿它当成交额（应该看「商品总额」，不含运费）
- 财务对账拿它当流水（应该与支付单一致，即「应付」）

**一个字段担四个语义，迟早有一处算错。**而这一刀越晚切，存量订单越多、退款分摊越难补。售后刚做完，行级额度与分摊的落点还在手边，此时做分摊最省。

同时补齐商城闭环里最后两个缺口：

- **运费**：现在下单不收到任何运费，「满 99 包邮」这类最基本的能力都没有。
- **优惠**：运营没有任何促销手段，商城只有原价卖。

## 2. 关键判断（9 条）

### 判断 1：`total_amount` 语义收窄为「应付金额」，另开三个字段

```
goods_amount    商品总额 = Σ 行 amount
discount_amount 优惠金额（券）
freight_amount  运费
total_amount    应付金额 = goods_count - discount + freight
```

`total_amount` 保持字段名不变、含义改为应付：支付单金额、退款额度、前端金额展示全部继续读它，**不改 pay 侧一行代码**，也不需要数据迁移改值。无券无运费时 `goods = total`，旧订单天然自洽。

迁移脚本里 `goods_amount` 回填 `total_amount`，`discount_amount`/`freight_amount` 默认 0。报表若要看成交额，从此读 `goods_amount` 而不是 `total_amount`。

### 判断 2：优惠与运费必须分摊到行

`mall_order_item` 增 `share_discount` / `share_freight`，行实付额 `= amount - share_discount + share_freight`。

不分摊的话，「退这一件该退多少钱」永远算不出来：订单 100 元用 20 元券，退其中一件 50 元的商品，该退 40 还是 50？分摊之后答案唯一，且天然可审计（分摊明细就在行上）。

分摊算法：按行 `amount` 占 `goods_amount` 的比例，`HALF_UP` 保留 2 位，**最后一行吃尾差**。逐行四舍五入后总额常常差 0.01，让最后一行兜底是最简单且不会为负的做法。

### 判断 3：售后可退上限从 `amount` 改为「行实付额」

`occupyRefundQuota` 的约束从 `amount - refunded_amount >= ?` 改为 `(amount - share_discount + share_freight) - refunded_amount >= ?`。

这是判断 2 的直接后果。不改的话，一张 8 折券的订单按原价退，**商家倒贴 20% 现金**——这是本切片唯一会直接造成资金损失的漏点，必须在同一批里改掉。

### 判断 4：积分商城不参与运费与优惠券

`currencyType == POINTS` 时：`freight_amount = 0`、拒绝任何 `couponId`。

积分体系下的「满 100 元减 10 元」和「运费 12 元」都不可解释——福利商城的运费要么是 0，要么是「扣 N 积分包邮」，那是另一套模型。硬套只会产出「积分订单欠商家 12 元运费」这种谁也不敢处理的脏数据。拒绝比兼容便宜。

### 判断 5：券模板与用户券分两张表，用户券落快照

- `mall_coupon`：模板（运营建）。面额、门槛、有效期、发行量、适用渠道。
- `mall_coupon_user`：用户领到的券实例。**面额/门槛/到期时间全部落快照**。

理由：运营把「满 100 减 50」改成「满 100 减 5」时，已经领出去的券不能跟着变——那是发出去的承诺。只存 `coupon_id` 再关联查模板，等于让模板修改篡改历史承诺。

### 判断 6：券核销用条件更新，取消与整单退款必须回退

```sql
UPDATE mall_coupon_user
   SET status = 'USED', order_no = #{orderNo}, used_time = NOW()
 WHERE id = #{id} AND status = 'UNUSED'
```

影响 0 行 = 券已被并发占用 → 抛错，不静默成功（否则一券多用）。

**回退**：订单取消、整单退款（覆盖全部可退行）后置回 `UNUSED` 并清 `order_no`。不回退的话，券被一次取消吞掉，客服只能手工补——和上一波「驳回不释放额度」是同一类错误。

**部分退款不回退**：券已经部分消耗，且优惠已经分摊到行上随着部分退款按比例退掉了。

### 判断 7：运费模板挂渠道，不挂商品

`mall_channel.freight_template_id` 可空（空 = 不收运费）。模板三选一：

| 计费方式 | 含义 |
|---|---|
| `FREE` | 全免 |
| `FIXED` | 固定运费（`base_amount`） |
| `THRESHOLD` | 满 `free_threshold` 包邮，否则收 `base_amount` |

不做按件数/按重量/多模板累加：那需要商品级运费模板 + 叠加计算 + 首重续重规则，是独立一波的量。渠道级已经能覆盖「零售满 99 包邮、B2B 固定 30 元」这两个最常见的场景。

**门槛判定的分母是 `goods_amount`（含优惠前）**：用券后金额跌破包邮线就收运费，会让「领了 20 元券反而多付 12 元运费」，这是最容易被投诉的交互。

### 判断 8：单券、不叠加、折扣券必须封顶

一次下单只能用一张券。叠加规则（券 + 活动 + 会员价 + 积分抵扣）会引入优先级、互斥矩阵、试错回滚，是完整的促销引擎。

折扣券必须有 `max_discount_amount`（封顶）。不封顶的 8 折券在 10 万元订单上算出 2 万元优惠，运营只能事后追认。同时优惠不能把应付打到 0 以下：`discount = min(计算值, goods_amount - 0.01)`，保证支付单金额始终 > 0（whale-pay 侧 `amount > 0` 是硬约束）。

### 判断 9：可用券在试算阶段算，下单阶段重算

`preview` 返回可用券列表（含不可用原因），用户选券后再次 `preview` 带 `couponId` 看实付。`create` 时**不信任前端传来的金额**，按 `couponId` 重新校验门槛、归属、状态并重算分摊。

前后端各算一遍看似浪费，但只信前端等于把优惠额度开放给浏览器；只信后端不给实时反馈等于每次下单失败才知道券不能用。折中是「前端试算只为展示，金额以 order 返回为准」。

## 3. 数据模型

### 3.1 新增表

```sql
-- 运费模板
mall_freight_template(
  id, tenant_id, template_name,
  charge_type      VARCHAR(16),   -- FREE / FIXED / THRESHOLD
  base_amount      DECIMAL(12,2) DEFAULT 0.00,
  free_threshold   DECIMAL(12,2) DEFAULT NULL,
  status           VARCHAR(16) DEFAULT 'ACTIVE',
  remark, create_time, update_time, deleted
)  -- uk_mall_freight_name(tenant_id, template_name)

-- 优惠券模板
mall_coupon(
  id, tenant_id, coupon_code, coupon_name,
  coupon_type      VARCHAR(16),   -- FULL_REDUCTION 满减 / DISCOUNT 折扣
  threshold_amount DECIMAL(12,2) DEFAULT 0.00,   -- 使用门槛
  face_amount      DECIMAL(12,2) DEFAULT 0.00,   -- 满减面额
  discount_rate    DECIMAL(5,4)  DEFAULT NULL,   -- 0.8500 = 85 折
  max_discount_amount DECIMAL(12,2) DEFAULT NULL,-- 折扣封顶
  channel_id       BIGINT DEFAULT NULL,          -- NULL = 全场通用
  total_qty        INT DEFAULT 0,                -- 发行量，0 = 不限
  issued_qty       INT DEFAULT 0,
  per_user_limit   INT DEFAULT 1,
  valid_from, valid_to DATETIME,
  status           VARCHAR(16) DEFAULT 'ACTIVE',
  remark, create_time, update_time, deleted
)  -- uk_mall_coupon_code(tenant_id, coupon_code)

-- 用户券
mall_coupon_user(
  id, tenant_id, coupon_id, user_id,
  coupon_code, coupon_name, coupon_type,          -- 快照
  threshold_amount, face_amount,                  -- 快照
  discount_rate, max_discount_amount,             -- 快照
  channel_id,                                     -- 快照
  valid_from, valid_to,                           -- 快照
  status           VARCHAR(16) DEFAULT 'UNUSED',  -- UNUSED / USED / EXPIRED
  order_no         VARCHAR(32) DEFAULT NULL,
  used_time        DATETIME DEFAULT NULL,
  create_time, update_time, deleted
)  -- uk_mall_coupon_user(tenant_id, coupon_id, user_id) 每人每券一条（per_user_limit=1 的简化）
   -- idx_mall_coupon_user_status(tenant_id, user_id, status, valid_to)
```

## 6. 下单计价时长

```
preview(couponId)
  ├─ 解析渠道 → currencyType
  ├─ 行小计 Σ = goods_amount
  ├─ POINTS？→ freight=0，忽略 couponId
  ├─ 运费：模板(FREE|FIXED|THRESHOLD) 按 goods_amount 判门槛
  ├─ 券：归属/状态/渠道/门槛校验 → discount
  │     折扣券 discount = min(goods × (1-rate), max_discount)
  │     兜底 discount = min(discount, goods - 0.01)
  ├─ 分摊：share_discount / share_freight 按行比例，末行吃尾差
  └─ total = goods - discount + freight

create(couponId)
  ├─ 同 preview 全流程重算（不信前端金额）
  ├─ 券核销：条件更新 UNUSED→USED，0 行即失败
  ├─ 落库：订单 + 行(含分摊) + 券快照
  └─ 失败回滚时券的核销一并回滚（同事务）

cancel / applyFullRefund
  └─ 券回退 USED→UNUSED（同事务）
```

## 10. 实施结果（2026-11-07）

九步全部落地，与计划的偏差只有四处，均已记录：

1. **`releaseIssuedQty` 预留后删除**。领取失败靠事务整体回滚已经够用，多留一个回补方法等于给「发行量」开了第二写入点。接口、实现、Mapper 三处一并删掉。
2. **`preview` 与 `create` 共用一段组装计价**，没有各写一份。试算 80、下单 82 这类问题一旦发生就无法复现。
3. **新增菜单 500–502**（售后单 / 优惠券 / 运费模板）。计划只提了权限号段；5.96 落售后权限时漏了 `sys_menu`，子应用顶栏能进但平台侧边栏看不到，本轮一并补登。
4. **`MallChannel.validate()` 抽出 `deriveCurrency()`**。加「积分商城清空运费绑定」后圈复杂度到 16，Checkstyle 门禁拦下。

实测口径：单测 **180 项**（新增 56，计划估 36）、覆盖率行 **50.5%** / 分支 **46.3%**（计划要求不低于上一波 48.8% / 44.2%）、`-Pcoverage-gate verify` BUILD SUCCESS、Checkstyle 0、ArchUnit 4/4（`CONTEXTS` 7 个）、前端 tsc + vite build（2099 模块）+ eslint 0、`check-doc-consistency` PASS。

计划外但顺手做掉的：

- 订单详情行表格加「实付」列（含分摊优惠/运费明细），售后弹窗补「本次退款」列——否则买家看不出为什么折扣订单退的钱比原价少。
- 前端售后预估金额算法同步改为行实付额（原先是 `unitPrice × quantity`，折扣订单会多估）。

第 9 节「明确不做」清单本轮**全部未做**，无一项被悄悄带入。
