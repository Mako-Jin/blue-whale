# Wave 5.96：商城售后单与部分退款

> 状态：**已实施**（2026-11-07；whale-mall 124 单测 / whale-pay 43 单测全绿，两服务覆盖率门禁通过）
> 前置：Wave 5.95 M1 首切片（支付闭环 + 整单退款）已提交 `24da861`
> 口径确认：带审核环节 / 仅退款 + 退货退款 / 部分退款后订单保持 PAID 累加金额
>
> **实施差异**（与下文原计划的偏差，均以实际落地为准）：
> 1. 错误码改用 **45050–45055**（原计划 45041 起，与类注释「45050 起留给售后」冲突）。
> 2. 接口实际 **7 个新增**（买家 4 + 运营 3），另 `POST /mall/order/{id}/refund` 保留但内部改走售后单；计划里列的 `/mall/internal/order/refunded` 未新增，沿用 M1 已存在的回调端点。
> 3. `pay_refund` 表结构确实未改，但 **DTO 改了**：`PayInternalRefundRequest` 加 `refundNo`，`PayRefundService.refundByNo` 加参数并前置判重——这是原计划判断 1 的落地形式。
> 4. 新增 `AFTER_SALE_INVALID`(45055) 与 `AFTER_SALE_APPLY`(2215) 权限，运营侧权限顺延为 2216 / 2217。

## 1. 为什么这一刀必须切在这里

M1 只做了整单退款，`payInternalClient.refund(payNo, totalAmount, reason)` 一次退完。它掩盖了三件事：

1. **退款请求不幂等**。pay 侧 `refund(payNo, amount, reason)` 没有业务退款单号，每次调用生成新 `pay_refund` 行。
   整单退款靠 `WHERE amount - refund_amount >= ?` 的额度兜底还能挡住重复（退完额度就归零），
   但部分退款下这个兜底失效：订单 100 退 30，超时重试再退 30 累计 60 仍在额度内，**多退 30 现金**。
2. **退不了「一部分」**。买家只退一件商品时无路可走，只能整单退，商家损失运费与已发商品。
3. **售后过程无处承载**。谁申请的、退哪几行、审核意见、退货物流，全靠 `mall_order.refund_amount` 一个数字表达。

## 2. 关键判断（9 条）

### 判断 1：先修幂等，再谈部分退款
`pay_refund` 已有 `uk_tenant_refund_no(tenant_id, refund_no)`，幂等的钥匙早就在手边，只是没人用。
**mall 生成退款请求号（复用售后单号）→ 传给 pay → pay 按退款单号判重，已存在直接返回原单。**
这是本切片第一个提交，独立可验证，不依赖售后单落地。

### 判断 2：整单退款降级为售后单的特例，不再走独立代码路径
`POST /mall/order/{id}/refund` 保留（管理端一键退），内部改为「生成一条覆盖全部可退行的售后单并直接置 APPROVED」。
好处：退款只有一条实现路径，行级额度占用、幂等、回调全部复用。代价：多一次插入，可忽略。

### 判断 3：部分退款后订单保持 PAID，只累加 `refund_amount`
不新增 `PARTIAL_REFUNDED`。理由：订单状态表达的是**整单资金状态**，多笔售后共存时它不该反复跳；
「已部分退款」是列表页的展示问题，用 `refund_amount > 0 && < total_amount` 就能算出来，不该污染状态机。
`REFUNDING` 保留，语义收窄为「整单退款进行中，禁止发货」。

### 判断 4：行级退款额度用条件更新占用，与 pay 侧的原子累计同构
```sql
UPDATE mall_order_item
   SET refunded_quantity = refunded_quantity + #{qty},
       refunded_amount   = refunded_amount   + #{amt}
 WHERE id = #{itemId} AND quantity - refunded_quantity >= #{qty}
```
影响 0 行 = 该商品可退数量不足 → 抛错回滚整张售后单。这样同一行被两张售后单并发申请时，后到的那张直接失败，
而不是两张都通过、退款时才发现超额。

### 判断 5：售后单状态机五态，不含 REFUNDING
`CREATED 待审核 → APPROVED 审核通过（退款执行中） → REFUNDED 已退款`，旁支 `REJECTED 已驳回` / `CANCELLED 已撤销`。
APPROVED 就是「已发起退款、等回调」，不需要再多一个中间态——退款的真实进度由 `pay_refund.status` 表达，
售后单再加一层 REFUNDING 只会让两个状态机对不齐。

### 判断 6：订单转 REFUNDED 由累计金额判定，不由售后单状态判定
回调到达时：
- 售后单 → REFUNDED
- 订单 `refund_amount` 原子累加；累加后 `>= total_amount` 才置 `REFUNDED`，否则订单回到 `PAID`
- 曾置 `REFUNDING` 的订单（整单退）在回调后转 `REFUNDED`

这样「三笔部分退款各 30、最后一笔 40」和「一笔整单退款 100」的结果完全一致。

### 判断 7：仅退款 / 退货退款只差一个 `type` 字段，不拆两张表
两者流程同构（申请 → 审核 → 退款），差异只在审核时的检查项：退货退款需要退回物流单号才能完成，
后续接 WMS 入库也只对 `RETURN_REFUND` 生效。用 `type` 区分，本切片不实现物流单号（留字段）。

### 判断 8：回调命令必须带售后单号，否则定位不到要结哪张单
现有 `OrderRefundedCommand` 只有 `orderNo/payNo/refundNo/refundAmount`。
`refundNo` 是 pay 侧生成的，mall 发起时并不知道。改造为 mall 发起时把售后单号作为退款请求号传下去，
pay 原样回传，回调按 `afterSaleNo` 定位。**`refundNo` 保留作为 pay 侧流水号，仅用于日志追溯。**

### 判断 9：买家接口不设权限码，靠订单归属校验
`POST /mall/after-sale` 由买家调用，权限模型里没有「买家」这个角色粒度，
沿用现有买家接口的做法（`actor.requireUserId()` + 校验订单 `userId == actor.userId`），不加权限码。
管理端 `list` / `audit` 各加一个权限码（2215、2216）。

## 3. 数据模型

### 3.1 新增 `mall_after_sale`（售后单）
| 字段 | 类型 | 说明 |
|---|---|---|
| `after_sale_no` | VARCHAR(64) | 售后单号，`AS + yyyyMMddHHmmss + 4位随机`，租户内唯一 |
| `order_id` / `order_no` | BIGINT / VARCHAR(64) | 关联订单 |
| `type` | VARCHAR(16) | `REFUND_ONLY` 仅退款 / `RETURN_REFUND` 退货退款 |
| `status` | VARCHAR(16) | `CREATED` / `APPROVED` / `REFUNDED` / `REJECTED` / `CANCELLED` |
| `refund_amount` | DECIMAL(12,2) | 本次申请退款金额（= 行金额之和，服务端计算，前端传不了） |
| `reason` | VARCHAR(255) | 售后原因（字典：不想要了/质量问题/发错货/少件…） |
| `description` | VARCHAR(500) | 问题描述 |
| `images` | VARCHAR(1000) | 凭证图片，逗号分隔 |
| `audit_user_id` / `audit_user_name` / `audit_time` / `audit_remark` | | 审核信息 |
| `refund_no` | VARCHAR(64) | pay 侧退款流水号（回调回填，仅追溯） |
| `refund_time` | DATETIME | 退款完成时间 |
| `return_logistics_no` | VARCHAR(64) | 退回物流单号（本切片只留字段不校验） |

索引：`uk_tenant_after_sale_no`、`idx_order(tenant_id, order_id)`、`idx_status(tenant_id, status)`。

### 3.2 新增 `mall_after_sale_item`（售后行）
`after_sale_id` / `order_item_id` / `sku_id` / `spu_name` / `sku_code` / `unit_price` / `quantity` / `amount`
（商品信息快照，与 `mall_order_item` 同理由：商品改名或删除后售后单要能独立看懂）。

### 3.3 `mall_order_item` 加列
`refunded_quantity INT NOT NULL DEFAULT 0`、`refunded_amount DECIMAL(12,2) NOT NULL DEFAULT 0`。

### 3.4 `pay_refund` 无需改结构
`amount` 本就是「本次退款金额」，`uk_tenant_refund_no` 已存在。只改写入时用调用方传入的退款单号。

## 5. 时序

### 5.1 部分退款（买家申请 → 运营审核）
```
买家            mall                      pay                  渠道
 |--申请售后----->|                        |                     |
 |               |--占用行额度(条件更新)    |                     |
 |               |--insert 售后单 CREATED  |                     |
 |<--受理--------|                        |                     |
 |               |                        |                     |
运营            |                        |                     |
 |--审核通过----->|                        |                     |
 |               |--APPROVED              |                     |
 |               |--refund(afterSaleNo)--->|                     |
 |               |                        |--pay_refund 判重    |
 |               |                        |--applyRefund 原子累计|
 |               |                        |--渠道退款----------->|
 |               |                        |<--成功--------------|
 |               |<--通知任务 REFUNDED------|                     |
 |               |--结售后单+累计订单退款额  |                     |
```

### 5.2 关键分支
- 行额度不足 → 申请时直接失败（409/45041），不进审核队列
- 审核通过时订单剩余可退金额不足 → 拒绝通过（防订单被别的售后单先退光）
- 回调重复 → 售后单已 REFUNDED 幂等返回
- 订单累计达 `total_amount` → 订单 REFUNDED；否则回 `PAID`

## 6. 错误码与权限

> 实施备注：原计划用 45041–45045，与 `MallErrorCode` 类注释已约定的「45050 起留给售后」冲突，落地改用 45050–45055。

| 码 | 常量 | 含义 |
|---|---|---|
| 45050 | `AFTER_SALE_NOT_FOUND` | 售后单不存在（或订单中不存在该商品行） |
| 45051 | `AFTER_SALE_STATUS_INVALID` | 当前状态不允许该操作 |
| 45052 | `AFTER_SALE_QUANTITY_EXCEEDED` | 可退数量不足 |
| 45053 | `AFTER_SALE_AMOUNT_EXCEEDED` | 可退金额不足 |
| 45054 | `AFTER_SALE_NOT_OWNER` | 非本人订单 / 售后单 |
| 45055 | `AFTER_SALE_INVALID` | 申请参数非法（明细为空、同一行重复、数量非正、类型无法识别） |

权限（`migration-5.96-mall-aftersale.sql`）：
- 2215 `sys:mall:aftersale:apply` — 买家申请/查看/撤销自己的售后（全员口径，同 `CART_MANAGE`）
- 2216 `sys:mall:aftersale:list` — 售后全量列表（运营）
- 2217 `sys:mall:aftersale:audit` — 审核通过 / 驳回（运营）

菜单：售后单页面挂在子应用 8119 侧边栏，按 2215 显示；`sys_menu` 侧暂未登记（子应用路由已可用，登记留到菜单统一梳理时补）。

## 9. 明确不做

- 退货物流单号校验、WMS 退货入库回写
- 换货（需联动库存重新出库）
- 部分退款按运费/优惠分摊（当前订单无运费与优惠，全额即商品行之和）
- 售后超时自动关闭、买家举证图片上传（只存 URL 字符串，走文件服务后续接）
- 退款到余额/积分（只走原路退回）
