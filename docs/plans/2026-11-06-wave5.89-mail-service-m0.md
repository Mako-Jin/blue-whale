## 1. 为什么必须独立成服务

用户 2026-11-06 明确：**`whale-message` 是消息管控，不是邮箱**。两者混淆会导致
「一个域两个主人」——模板与投递记录归消息中心，邮件内容归邮箱，边界一旦糊掉，
后续任何一方改表都会打断另一方。

| 维度 | `whale-message`（消息管控） | `whale-mail`（邮箱域） |
|---|---|---|
| 所有权 | 模板、渠道路由、幂等键、投递记录 | 邮箱账号、文件夹、邮件索引、附件、草稿 |
| 数据 | `msg_template` / `msg_record` / `msg_delivery` | `mail_account` / `mail_folder` / `mail_message` / `mail_attachment` / `mail_draft` |
| 语义 | 「把一条已渲染的消息送到某个渠道」 | 「一个邮箱里有什么，用户怎么读写」 |
| 关系 | 可把 EMAIL 当通道输出，但**不存邮件** | 不关心渠道编排，只关心邮箱本身 |
| 共享 | 无共享表；如需通知「收到新邮件」，由 `whale-mail` 调 `/message/internal/send` 单向发出 | 同左 |

**不做的事**：`whale-mail` 不实现模板渲染、不做站内公告、不发短信。

## 2. 与 MTA 的分工

`whale-mail` **不是**邮件服务器，它是邮箱业务服务。协议侧交给 Mailcow
（Postfix + Dovecot + Rspamd + Webmail）：

```
浏览器 → qiankun 前端 → /mail/** → whale-mail:8099
                                      ├─ MySQL bluewhale_mail（索引与业务态）
                                      ├─ Redis（预留：未读缓存/限流）
                                      ├─ IMAP 993 → Dovecot（收信）
                                      └─ SMTP 587/465 → Postfix（发信）
```

Mailcow 不提供邮件内容 REST API（只有域名/邮箱管理 API），所以自研 UI 必须走 IMAP，
并在本地建索引用于分页、检索与业务关联。这也是本服务存在的技术理由。

## 3. 数据模型（V1 基线 5 表）

| 表 | 用途 | 关键约束 |
|---|---|---|
| `mail_account` | 平台用户 ↔ 邮箱地址 ↔ 协议端点 | `uk (tenant_id, email)`；凭据只存 `secret_ref` |
| `mail_folder` | 系统 + 自定义文件夹 | `uk (tenant_id, account_id, imap_name)`；**UID 位点按文件夹维护** |
| `mail_message` | 邮件索引（元数据 + 正文缓存） | `uk (tenant_id, account_id, folder_id, uid)` |
| `mail_attachment` | 附件引用 | 二进制在 `whale-file`，本表只存 `file_id` |
| `mail_draft` | 草稿 | 草稿无 IMAP UID，独立成表 |
| `mail_delivery_report` | 退信回执 | 一行 = 一个收件人 + 一条 DSN 结果；唯一键 `(tenant, account, notify_message, recipient)` 保证重复同步幂等 |

## 5. 四个关键设计决策

**① 正文惰性回源，不在同步阶段拉。**
同步只取 header（主题/发件人/大小/标记），打开详情发现正文为空时才连一次 IMAP 并回填。
后果：首同步流量从「整箱邮件」降到「几百条 header」，MySQL 也不会被正文撑爆。
回源失败不抛 500，只返回空正文并记 warn——一封畸形邮件不该拖垮整个详情页。

**② 已发送副本的 UID 取负数。**
自己发出的邮件会在 IMAP 的 Sent 文件夹再次出现。本地副本用负 UID 占位（服务器 UID 恒正），
同步时再按 `Message-ID` 去重，既保证「刚发完立刻能在已发送看到」，又不会两边重复。

**③ 密码永不入库。**
`mail_account.secret_ref` 只存配置键名（Nacos key 或环境变量名），运行时由
`Environment` 解析。解析不到就快速报错，不做「空密码继续连」的降级——否则表现为
难排查的认证超时。

**④ UID 位点挂在文件夹上，不是账号上。**
同一账号的 INBOX 与 Sent 的 UID 空间彼此独立，共用位点会互相覆盖。检测到
`UIDVALIDITY` 变化时重置位点并告警（M0 不自动清库，避免与逻辑删除的唯一键冲突）。

## 11. 前端 M0-FE（`frontend/platform-apps/whale-mail`，已完成）

端口 **8117**、vite base `/mail`、qiankun 微应用名 `whale-mail`。

| 页面 | 路由 | 内容 |
|---|---|---|
| 邮箱 | `/mail` | 三栏：文件夹（含未读角标、同步按钮）/ 邮件列表（搜索、分页、未读加粗、星标与附件标记）/ 阅读区 |
| 账号设置 | `/mail/account` | 账号列表、绑定 / 编辑 / 解绑、单账号同步 |

对话框：写信、回复、编辑草稿（同一 `ComposeModal`，靠 `draft` / `replyTo` 区分入口）。

### 三个必须守住的安全口径

1. **邮件 HTML 一律在 `sandbox` iframe 内渲染**，不用 `dangerouslySetInnerHTML`。
   基座与子应用同源，一封带 `<img onerror>` 的邮件若注入主文档就能直接读到平台 token。
   `sandbox` 不授 `allow-scripts` / `allow-same-origin`，脚本无法执行、也读不到父页 DOM。
   iframe 内再叠一层 `Content-Security-Policy: default-src 'none'`。
2. **远程图片默认屏蔽**。图片 URL 带唯一参数即可当「已读回执」用，泄露收件人阅读行为；
   用户点「显示图片」才放开 `img-src`。
3. **不接受邮箱密码输入**。表单只收「凭据引用」键名（如 `mail.credential.zhangsan`），
   真实值由部署侧注入。页面收密码会经过浏览器、后端日志与数据库三处，轮换即需改库。

### 两个数据源问题

- **草稿箱双来源**：本机草稿在 `mail_draft`（写信框保存），服务器草稿是被同步回来的 `DRAFT` 文件夹邮件。
  M0 没有 IMAP APPEND，本机草稿不会推到服务器，因此草稿箱给「本机草稿 / 服务器」两个页签，
  默认本机——否则用户看不到自己刚存的草稿。
- **列表与详情分离**：列表接口不返回正文，正文按需回源。前端必须接受「首次打开详情会慢一拍」，
  不能因为列表里有 `preview` 就当成正文展示。

### 上下文保持

文件夹与选中邮件写进 query string（`?folder=INBOX&id=12`）。
qiankun 在基座切换标签页时会卸载子应用，只用组件内 state 会导致「切走再回来回到收件箱第一页」。

### 平台接线

`qiankun/apps.ts` 增 `whale-mail`（8117）、`routes.tsx` 增 `mail/*`、
`router/menu.ts` 增「邮箱」入口（权限 `sys:mail:message:list`，与 `migration-5.89-mail.sql` 的菜单 490 一致〔原拟 481 与 5.88 工会段撞号，2026-11-06 代码审查修正〕）、
`MainLayout` 图标、`.env.example` 增 `VITE_SUBAPP_ENTRY_MAIL`、CI 前端镜像矩阵增 `whale-mail`（`namespace: frontend`，
避免与同名后端镜像冲突）、`docs/service-catalog.md` 前端表第 22 行与端口表 8117。

**验证**：`tsc --noEmit` 0 错误、`eslint --max-warnings 0` 0 告警、`vite build` 成功（1.25 MB / gzip 396 KB）。
未实机联调——本机无 MySQL 与 IMAP 服务。

## 12. M1 附件（收发双向，已完成）

### 数据流

```
收信：IMAP 部件字节 → MailFileClient.upload → whale-file 返回 fileId → mail_attachment 落一行
发信：/file/upload 先传（前端）→ /mail/send 带 fileId → MailFileClient.download 取流 → MIME mixed
下载：GET /mail/attachment/{id}/download → 归属校验 → 反代 whale-file 内容接口
```

### 三个关键决策

1. **附件按需登记，同步不下载**。同步阶段只拉 header；用户首次打开详情时才连 IMAP 取附件并写文件服务。
   若在同步时拉全部附件，首同步的流量与存储会随邮件量线性上涨，而且大多数附件永远不会被打开。
2. **超限不丢弃、只降级**。超过 25MB（单文件）或 50MB（单封合计）的附件不入库字节，但仍写一行元信息
   （`file_id` 为空）。下载时明确提示「超出容量上限，未缓存内容」——用户看到名字下不动，
   比「列表里根本没有这个附件」更可解释。
3. **下载必须走本服务代理**，不能把 `whale-file` 的下载地址直接给前端。附件归属按
   「附件 → 邮件 → 账号 → 当前用户」判定，裸 `fileId` 一旦暴露就能被其他用户直接拉取。
   前端也因此不能用 `<a href>`，必须取 blob 后本地保存——新窗口导航不带 `Authorization`。

### 发信的 MIME 结构

- 无附件：保持 `text/plain` / `text/html` / `multipart/alternative` 三种简单结构。
  一律套 `multipart/mixed` 会让部分客户端把「只有一个 text 部件」显示成带空附件的邮件。
- 有附件：外层 `multipart/mixed` = 正文部件（可能是 `alternative`）+ 每个附件一个部件（`Content-Disposition: attachment`）。

| 文件 | 说明 |
|---|---|
| `client/MailFileClient.java` | 内网文件客户端：multipart 上传、内容下载，自带内网令牌与租户头 |
| `support/FetchedAttachment.java` | IMAP 附件快照（`content` 为 null 表示超限跳过） |
| `support/MailImapSupport#fetchAttachments` | 按 UID 递归收集部件，带 MIME 深度与单文件上限 |

- `ComposeModal`：`Upload` 选择文件后立即上传换 `fileId`，发送时随请求带上；草稿明确提示不保存附件。

### 三个判断（不是配置细节，而是方向选择）

1. **出站 25 走中继，不硬刚工单**。云厂商封出站 25 是惯例；即使工单批了，还要自己养 IP 信誉。
   走中继把「IP 预热」这件不可压缩的事外包出去，代价是退信归因变难。
   注意中继商必须已在本侧验证发件域，否则会重写 `From`。
2. **DMARC 从 `p=none` 起步**。直接 `p=reject` 会把现有转发链路上的正常邮件全部打回，
   这类事故要等 DNS 缓存过期（最长 48 小时）才恢复。
3. **DKIM 公钥超 255 字符必须拆分**。多数 DNS 服务商静默保存失败，表现为
   「Mailcow 显示已签名，收件方 `dkim=fail`」——最难查的一类假象。

### 自检脚本的两个实现细节

- 输出不用 `Format-Table`：CJK 字符按 1 字符计宽、终端按 2 列渲染，表格必然错位，改为逐行着色输出。
- 脚本文件必须带 **UTF-8 BOM**。Windows PowerShell 5.1 对无 BOM 的 UTF-8 按系统 ANSI 解码，
  中文字符串的字节被误判成 `{` `}` `"` 等结构字符，直接导致语法解析失败
  （本次实测：无 BOM 报 8 处「意外的标记」，加 BOM 后 `PARSE_OK`）。

## 14. M2 建用户自动开邮箱（已完成）

### 链路

```
whale-auth UserAppService.create（事务内）
  └─ publish UserDomainEvent(CREATED)
       └─ MailProvisionListener（@TransactionalEventListener AFTER_COMMIT）
            └─ mailProvisionExecutor 线程池（core 1 / queue 500 / AbortPolicy）
                 └─ POST http://whale-mail:8099/mail/internal/provision
                      └─ MailProvisionServiceImpl
                           查重 → 生成地址与口令 → Mailcow add/mailbox → 落 mail_account + 系统文件夹
```

### 五个关键决策

1. **不改 `UserAppService`，挂领域事件**。应用层不该知道「邮箱」这件事；开通是基础设施侧的可选副作用。
   代价是新用户信息要从事件 ID 反查，但换来「邮件服务宕机不影响建用户」。
2. **AFTER_COMMIT + 异步**。用户没落库就开邮箱会留下孤儿邮箱；同步调用则让建用户接口的响应时间
   绑到 Mailcow 的健康度上（一次 TLS 握手就可能 3 秒）。
3. **不抛异常、不回滚用户**。漏开邮箱是功能缺失，建不出用户是事故。失败只记 ERROR 日志，
   带 `userId`，便于补开。
4. **Mailcow 调用不在事务内**。一次 HTTP 最长 10 秒，包在事务里会白占数据库连接。
   只有「写账号 + 建系统文件夹」两步进短事务（`TransactionTemplate`），两者必须原子——
   有账号没文件夹会导致列表页空白。
5. **落库失败回删 Mailcow 邮箱**。否则 Mailcow 里留下无人认领的地址，下次代开永远撞
   「地址已存在」，且没人知道该删哪个。

### 口令为什么要落库（与前几轮口径的补充）

V1 的设计是 `secret_ref` 只存配置键名，密码由部署侧注入。这条对**外部托管邮箱**仍然成立。
但代开邮箱的口令是平台自己生成的，服务端必须读回来登录 IMAP，因此新增 `secret_cipher`
存 `ENC(...)` 密文：

- 密钥复用 `WHALE_CONFIG_ENC_KEY`（`whale-config-crypto` 的 Jasypt 约定），不引入第二套密钥体系
- 密钥缺失时**直接失败**，不降级明文——否则口令会进备份包
- 解析优先级：`secret_ref` 有值走配置；否则 `secret_cipher` 解密；都空则报错

### 三个不做（都有明确理由）

- **不强制首次登录改密**（`force_pw_update=0`）：平台要用该口令连 IMAP，员工一改密文即失效、同步全断
- **不返回初始口令**：解密只发生在服务端连 IMAP 那一刻，返回给调用方只是换个地方存明文
- **不自动改已存在邮箱的口令**：Mailcow 有、平台无记录的地址可能是别人在用的邮箱，
  自动重置等于把人锁在门外，返回 `CONFLICT` 交人工判断
