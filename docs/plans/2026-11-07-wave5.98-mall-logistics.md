# Wave 5.98：商城物流与履约——发货单、运单号与签收驱动完成

> 状态：已实施（2026-11-07）
> 前置：Wave 5.97 计价重构（`d4a1dbff`）
> 口径：发货成为独立单据、支持拆包分批；签收驱动订单完成；不做轨迹明细与电子面单

## 1. 为什么现在必须做

现在「发货」只是 `POST /mall/order/{id}/ship` 里的一次状态跳转：

```java
order.ship(LocalDateTime.now());
for (OrderItem item : order.getItems()) {
    skuStockRepository.ship(item.getSkuId(), item.getQuantity());
}
```

它把四件事一起遮住了：

1. **不知道发的是什么**。没有承运商、没有运单号，买家问「我的货到哪了」只能回一句「已发货」。
2. **不能拆包**。`OrderStatus.canShip()` 只认 `PAID`，第一次发货后订单变成 `SHIPPED`，**第二次发货直接被状态机拒绝**——一个订单买了三件、仓库分两个包裹是常态，现在只能一次全发或拆成两个订单。
3. **签收驱动不了完成**。`COMPLETED` 只能由买家点「确认收货」或运营手工点，物流显示已签收但订单还挂着 `SHIPPED`，超时自动完成更无从下手。
4. **发货不可追溯**。谁发的、什么时候发的、发了几件，只有一条 `mall_order_log`。

这一刀必须切在计价之后：金额与分摊已经稳定，行上多了 `share_discount`/`share_freight`，此时给行再加一个「已发数量」不会与金额口径打架。

## 2. 关键判断（8 条）

### 判断 1：发货是独立单据，不是订单上的一个状态位

`mall_shipment`（一批货一张单）+ `mall_shipment_item`（发哪几行、各多少）。订单与发货单 **1:N**。

一张发货单对应**一个运单号**——现实里运单号是唯一的物理资源，一个包裹一个号。把两个包裹塞进一张单，就等于允许「一单多号」，那 `tracking_no` 从唯一约束退化成备注。

### 判断 2：行上加 `shipped_quantity`，与 `refunded_quantity` 同构

```
可发数量 = quantity - shipped_quantity
```

占用走条件更新 `WHERE quantity - shipped_quantity >= ?`，与退款额度完全一样的写法。好处是并发下两笔发货单同时发同一行时，后到的直接失败，而不是两边都显示成功、出库时才发现只够一份。

### 判断 3：订单状态由发货单驱动，`ship()` 幂等放宽

- **首次发货** → 订单 `PAID → SHIPPED`，`ship_time` 只写第一次
- **再次发货**（同订单第二张单）→ 订单已是 `SHIPPED`，`ship()` **不抛错、不改时间**
- **全部行发满且全部发货单签收** → 订单 `SHIPPED → COMPLETED`
- **部分发货**保持 `SHIPPED`，前端按 `shipped_quantity < quantity` 显示「部分发货」

`ship()` 从「只认 PAID」放宽为「PAID 或 SHIPPED」，但**写法上仍然拒绝其余状态**（`PENDING_PAYMENT` 没付钱不能发、`REFUNDING` 退款中不能发、`COMPLETED` 不能补发）。

### 判断 4：发货单只有三个状态，没有草稿态

`SHIPPED → DELIVERED`，`SHIPPED → CANCELLED`。

不设 `CREATED` 草稿：草稿态意味着「占没占可发数量、占没占运单号」要另定一套规则，而运单号一旦申请就已经是消耗掉的资源。运营需要「先建单后打印面单」时，属于电子面单对接（本轮不做）。

### 判断 5：签收是内网回调 + 运营手工兜底，按发货单号幂等

- 内网：`POST /mall/internal/shipment/delivered`，载荷 `shipmentNo` / `deliveredTime`
- 运营：`POST /mall/shipment/{id}/delivered`（物流平台没接通时手工点）

幂等口径：已是 `DELIVERED` 直接返回成功、不重复写时间；`CANCELLED` 的单签收直接拒绝（包裹都作废了还签收，说明数据错乱）。

### 判断 6：作废要放回数量与库存，并且可能把订单退回 PAID

作废 = 货没发出去（错发/丢件/填错单号）。必须做三件事：

1. `mall_order_item.shipped_quantity` 回退（`shipment_item.quantity`）
2. 库存 `reserved_qty` 回补（`unship`：出库时减的预占加回来，可售不动——可售在下单时就扣了）
3. 若该订单**已无任何有效发货单**（全部作废），订单 `SHIPPED → PAID`，让它可以重新发货

第 3 条容易漏：不退回去的话订单显示「已发货」却没有一张发货单，运营再也发不出去（`SHIPPED` 状态下新建发货单被判断 3 放行了，但「已发货」的展示是假的）。

### 判断 7：运单号唯一，且必填

`uk_mall_shipment_tracking(tenant_id, carrier_code, tracking_no)`。同一张运单号挂在两张单上，99% 是填错了；剩下 1% 是真并发，也应让后到的失败。

`tracking_no` 不允许为空：没有运单号的发货单等于没发。自送（`SELF`）也填内部单号，仍必填。

### 判断 8：签收只在「全发满 + 全签收」时完结订单

只签收了一张、还有一行没发，订单不能完成——否则剩下的货永远发不出去（`COMPLETED` 不能再发货）。

判定条件写在一处：`Σ shipment_item.quantity（有效单） == Σ order_item.quantity` 且**所有有效发货单都 DELIVERED**。

## 3. 数据模型

```sql
mall_shipment
  id, tenant_id, shipment_no            -- MS + yyyyMMdd + 6 位流水，uk(tenant_id, shipment_no)
  order_id, order_no, channel_id
  carrier_code, carrier_name            -- 承运商编码 + 名称快照
  tracking_no                           -- 运单号，uk(tenant_id, carrier_code, tracking_no)
  status                                -- SHIPPED / DELIVERED / CANCELLED
  item_count, total_quantity
  shipped_time, delivered_time
  cancel_time, cancel_reason
  remark, create_time, update_time, deleted

mall_shipment_item
  id, tenant_id, shipment_id, order_id, order_item_id
  spu_id, sku_id, spu_name, sku_code, spec_json   -- 快照，与 mall_order_item 同口径
  quantity
  idx(tenant_id, shipment_id) / idx(tenant_id, order_item_id)

mall_order_item + shipped_quantity INT NOT NULL DEFAULT 0
```

`carrier_name` 落快照：承运商改名或枚举调整后，历史单据仍应显示当时的名字。

**不回填 `shipped_quantity`**：存量 `SHIPPED` 订单没有发货单，回填成 `quantity` 会造出一批「发满了但没有发货单」的孤儿数据，反而让判断 6 的「无有效发货单」逻辑错误触发。存量单维持「已发货但无单据」的历史事实，新单起才有单据。

## 7. 明确不做

- **物流轨迹明细表**（`mall_shipment_track`）与地图展示：轨迹是物流商的数据，自建一张表只会得到一份过期副本；本轮只存运单号，跳转承运商查询页
- **电子面单对接**（快递鸟/菜鸟/顺丰开放平台）与面单打印
- **逆向物流**：退货物流已由售后单 `return_logistics_no` 承载
- **多包裹合并发货、按仓库/发货地址自动拆单、超时未发货告警**
- **承运商运费结算与对账**
- **签收人姓名/手机号**（涉及个人信息采集，需单独设计授权与脱敏）

## 8. 实施结果（2026-11-07）

七步全部落地。与计划的偏差三处：

1. **`OrderStatus.canShip()` 放宽为 `PAID or SHIPPED`**（计划只说了 `ship()` 幂等）。不放宽的话第二张发货单在 `create` 入口就被 `SHIPMENT_ORDER_STATE_INVALID` 拦住，拆包根本走不到 `ship()`。幂等判定仍在 `ship()` 里返回 boolean。
2. **`ShipmentAppServiceImpl.cancel` 重新查库判定订单状态**。内存里的 `order` 可能是别处刚改过的旧值，`unShip()` 前重新 `findById` 一次，避免覆盖并发状态。
3. **错误码 45087 定为 `SHIPMENT_INVALID`**（计划写的是 `SHIPMENT_EMPTY`）。它同时覆盖「明细为空」「数量非正」「运单号为空」三种参数问题，叫 EMPTY 名不副实。

实测：单测 **205 项**（新增 25，计划未定量）、覆盖率行 **51.2%** / 分支 **46.7%**、`-Pcoverage-gate verify` BUILD SUCCESS、Checkstyle 0、ArchUnit 4/4（8 上下文）、前端 tsc + build + lint 全绿。

端点账：7 个新增 − 1 个移除 = 净增 6，54 → **60**。存量 `SHIPPED` 订单按计划**未回填** `shipped_quantity`。

第 7 节「明确不做」清单全部未做：没有轨迹表、没有面单对接、没有签收人信息采集。
