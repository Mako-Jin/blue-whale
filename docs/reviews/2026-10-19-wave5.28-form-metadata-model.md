# Wave 5.28 检查报告 · whale-form 动态表单元数据模型（三层分离 · 表:表单 1:N）

> 日期：2026-10-19 ｜ 作者：BlueWhale
> 规格：[wave5.28-form-metadata-model/spec.md](../plans/wave5.28-form-metadata-model/spec.md) ｜ 分解：[tasks.md](../plans/wave5.28-form-metadata-model/tasks.md)
> 触发：用户指令「有一个动态列的详情表（列/类型/长度/必填/可空/备注）……还有一个表单的属性详情表（显示/排序/属性类型/可编辑/关联字段）……表单和表有一个关联。是不是这样的，你优化一下。」
> 经 AskUserQuestion 冻结口径（详见 spec §七）：**(a) 表:表单 = 1:N**（一张表被多张表单视图共享）｜**(b) 选项独立表** `form_field_option`｜**(c) `schema_json` 保留为发布快照**｜**(d) 本轮仅后端元数据表 + 迁移**（前端设计器/动态渲染后置）。
> 依据：REQ-DOC-002（先落文档）、REQ-QA-002（变更后自检）、REQ-CICD-001（Checkstyle 门禁）、REQ-ARCH-003（服务自持前缀）。

## 一、背景与设计优化结论

用户提出的模型是**两张表**（列详情 + 表单属性详情）+ 一个关联。方向正确，但**两处必须拆开**，否则模型会退化（详见 spec §一）：

1. **存储类型 ≠ 控件类型**。Wave 5.27 的 `FormField.type` 一身二职（既是 DDL 列类型、又是前端控件），导致一个 `VARCHAR` 列无法既渲染「下拉」又渲染「单选」。本波拆为 `data_type`（存储/DDL）与 `widget_type`（前端控件）**互相独立校验**。
2. **选项必须独立成表**。下拉/单选/多选的候选值若塞进属性行 JSON，将无法按值检索、无法复用、无法约束 → 独立 `form_field_option`（label + value + sort）。

**优化后三层模型**：① 表定义层（`form_table_definition` 1—N `form_column_meta`）；② 表单视图层（`form_definition`〔+`table_definition_id`〕 1—N `form_field_config`，`form_field_config` N—1 `form_column_meta`，可为 NULL = 纯布局字段）；③ 选项层（`form_field_config` 1—N `form_field_option`）。

**为什么表:表单是 1:N 而不是 1:1**：同一物理表（如「学生表」）需要「新生登记表单」「成绩录入表单」「审批表单」等多张不同视图，各自控制字段可见性/可编辑性/控件类型/选项，共享同一份列定义与同一张物理表。

## 三、契约与交付物

### 轨 A · 表结构（4 新表 + 3 表兼容列）

| 项 | 交付 |
|---|---|
| A-a | `entity/{FormTableDefinition,FormColumnMeta,FormFieldConfig,FormFieldOption}`（均继承 `BaseEntity`；`FormColumnMeta.precision` 因 `precision` 是 MySQL 保留字，字段加 `@TableField("`precision`")`） |
| A-b | `mapper/{FormTableDefinitionMapper,FormColumnMetaMapper,FormFieldConfigMapper,FormFieldOptionMapper}` |
| A-c | 兼容列：`FormDefinition(+tableDefinitionId)`、`FormTableRegistry(+tableDefinitionId/tableCode/tableVersion)`、`FormData(+tableDefinitionId/tableCode/tableVersion/formDefinitionId)` |
| A-d | `whale-form/db/init.sql`：4 新表 + 3 表兼容列/键；**新增 `db/migration-5.28.sql`**（非破坏性增量脚本，`CREATE TABLE IF NOT EXISTS` + `ALTER TABLE ADD COLUMN` + `MODIFY COLUMN ... DEFAULT NULL`，供存量库升级） |

### 轨 B · 类型与编译

| 项 | 交付 | 关键约束 |
|---|---|---|
| B-a | `support/FormDataType` | `data_type` 白名单 `text/textarea/number/date/datetime/select/bool`；映射 `text→VARCHAR(n≤2000 默认255)`／`textarea→TEXT`／`number→DECIMAL(p,s)`（默认 18,4）／`date→DATE`／`datetime→DATETIME`／`select→VARCHAR(255)`／`bool→TINYINT`；`defaultWidget(dataType)` 缺省控件映射 |
| B-b | `support/FormWidgetType` | `widget_type` 白名单 `text/textarea/number/select/radio/checkbox/date/datetime/switch`（独立校验） |
| B-c | `support/FormMetadataCompiler` | 列元数据 + 字段配置 + 选项 → `schema_json` 编译快照（仅 `showInForm=1` 的数据字段；NULL 列 = 布局字段不入快照） |

### 轨 C · 元数据服务与接口

| 项 | 交付 |
|---|---|
| C-a/C-b | `dto/{FormTableDefinitionSaveRequest,FormColumnMetaDTO,FormFieldConfigDTO,FormFieldOptionDTO}` + `vo/{FormTableDefinitionVO,FormColumnMetaVO,FormFieldConfigVO,FormFieldOptionVO}` |
| C-c | `service/FormTableDefinitionService(+Impl)`：表定义（含列）聚合 CRUD（更新时整体替换列集合） |
| C-d | `controller/FormTableDefinitionController`：`/form/table-definition` CRUD + `/{id}/publish` + `/{id}/tables`（权限码 `sys:form:table:add/edit/delete/list/publish`） |
| C-e | `FormDefinitionService(+Impl)`：保存时持久化字段配置与选项 + 编译快照；详情返回 `tableDefinitionId` + `fields[]`（含 `options[]`） |
| C-f | `whale-auth/db/init.sql` 追加 `sys:form:table:*`（id **53–57**，注释形式附于 migration-5.28.sql） |

### 轨 D · 迁移

| 项 | 交付 |
|---|---|
| D-a | `service/FormMetadataMigrationService(+Impl)#migrateLegacy()`：`schema_json.fields[]` → 表定义（`table_code=form.code`、`version=form.version`）+ 列元数据 + 字段配置 + 选项（**幂等**）+ 回填 `form_definition.table_definition_id`（spec §3.11 明确入口为服务方法，**无 HTTP 端点**，仅单测覆盖） |

### 轨 E · 发布/提交改造

| 项 | 交付 |
|---|---|
| E-a | `FormPublishService(+Impl)`：`publishTableDefinition`（由列元数据建物理表 + 登记 registry，重复发布 400）／`publishMetadata`（视图发布编译快照 + 幂等确保表定义物理表已发布）／`publishLegacy`（`tableDefinitionId == null` 走 Wave 5.27 原路径） |
| E-b | `FormDataService(+Impl)`：按表单视图 `schema_json`（编译快照，仅 `showInForm=1`）选列校验（未知字段/必填/长度）+ 按 `(table_code, table_version)` 路由物理表 + 主表新列 `table_definition_id/table_code/table_version/form_definition_id` 落库 |
| E-c | `controller/FormController`：表定义发布/列表接线 + 定义详情带 `fields` |

- **物理表** `form_data_bw_demo_t_v1`：公共列（`id/tenant_id/definition_id/definition_version/biz_key/submitter/status/create_time/update_time/deleted`）+ 动态列 `name varchar(50)` / `grade varchar(255)` / `score decimal(10,2)` —— **与列元数据 `data_type/length/precision/scale` 完全一致**；`definition_id` 承载**所属表定义 ID**、`definition_version` 承载**表版本**（注释已更新为「所属表定义ID」/「表版本」）。
- **主表** `form_data` 行：`table_definition_id=2112153325071736834`、`table_code=bw_demo_t`、`table_version=1`、`form_definition_id=2112153325549887490`（视图 A）——**表维度路由 + 视图归属落库**。

- **`form_column_meta`**：3 行（name/grade/score，`length/precision/scale/nullable/required` 与提交一致）。

### 4.3 存量兼容（迁移同构性）

- **legacy 定义** `fm_smoke`（id `2112131083080241153`，`table_definition_id=NULL`，version 1）及其 `schema_json`（5 字段 name/age/birthday/memo/active）**原样保留**。
- 其物理表 `form_data_fm_smoke_v1` 仍为旧结构（`definition_id` 注释为「表单定义ID」），**未改动**。
- registry legacy 行 `table_definition_id=NULL`、`definition_code=fm_smoke`、`physical_table=form_data_fm_smoke_v1` **原样保留**。
- `form_data` 4 条历史行（`fm-e2e-526` / `fm-e2e-526v2` / `fm_smoke`）的 `table_definition_id/table_code/table_version/form_definition_id` **均为 NULL**（新旧路径互不干扰）。
- **迁移同构性得证**：因 `table_code == form.code` 且 `table_version == form.version`，迁移后物理表名 `form_data_{table_code}_v{version}` 与 Wave 5.27 的 `form_data_{form.code}_v{version}` **完全一致**，存量物理表与数据零改动。

结论：三层模型（表定义 / 表单视图 / 选项）落库与运行时行为**完全符合冻结契约**；1:N 视图共享同一物理表且快照各异得证；数据字段映射（`data_type` ↔ MySQL 列类型）正确；存量兼容成立。

## 五、缺陷与偏差

| 类别 | 内容 |
|---|---|
| 缺陷（已修 · 1） | **`precision` MySQL 保留字**：① 迁移/init 脚本列定义写为 `` `precision` ``（否则 `ERROR 1064`）；② 冒烟时 MyBatis-Plus 生成 `INSERT INTO form_column_meta (..., precision, ...)` 报 SQL 语法错误（HTTP 500）→ 实体加 `@TableField("`precision`")`，重建后通过（`precision=10/scale=2` 正确回读，证明 resultMap 映射正常） |
| 缺陷（已修 · 2） | **`FormMetadataMigrationServiceImplTest` 单测**：`MybatisPlusException: can not find lambda cache for this entity [FormDefinition]`（`LambdaUpdateWrapper.set` 立即解析列名）→ 测试加 `@BeforeAll initTableInfoCache()`（复用项目既有模式）后 44 tests 全绿 |
| 设计决策（DB 层不建 NOT NULL） | 动态列一律 `DEFAULT NULL`，**不建 DB NOT NULL**——因 1:N 视图可见性不同，强制 NOT NULL 会使隐藏列的表单无法提交；空值/必填约束统一由服务层按视图字段校验（spec §3.2「`required` 为服务层校验，不建 DB NOT NULL」） |
| 增量脚本（新增交付物） | `db/migration-5.28.sql`：`init.sql` 是 DROP+CREATE 全量脚本，不可用于存量库；新增非破坏性增量脚本（`CREATE TABLE IF NOT EXISTS` + `ALTER TABLE ADD COLUMN` + `MODIFY COLUMN ... DEFAULT NULL` 放宽 legacy 列）并在 `bluewhale_form` 实机应用 |
| 环境噪声（非本波缺陷） | whale-form 日志报 `Table 'bluewhale_form.api_log' doesn't exist`（common starter 的 ApiLogMapper 写入本库而该表缺失）；经证据确认**不影响响应**（控制器已正常执行并返回业务结果），登记为环境残余 |
| 偏差（构建） | 全量 `clean install` 需先释放运行中业务服务的 `target/*.jar` 锁 → 停进程释放后重建（属**环境占用**，非代码缺陷） |

## 七、非目标与残余

- **非目标（本轮明确不做）**：前端表单设计器与动态渲染页（用户自助拖拽建字段 / 客户端按控件类型渲染表单）、字段级索引自动优化、列删除/改类型的在线数据迁移（按要求「升版本建新物理表」）、跨表格/跨版本聚合查询、外键约束与字段级唯一约束、选项的运行时字典表（本轮选项仍随字段配置内联维护）。
- 遗留：`form_data.data_json` 仍双写（过渡），待前端设计器/渲染落地并切换读源后再评估收窄。
- **残余确认**：`migrateLegacy()` 无 HTTP 入口（spec §3.8 接口清单未列迁移端点），**仅单测覆盖**；如需实机迁移需临时以服务方法或临时端点触发。
- 后续候选：① 前端表单设计器（表定义可视化编排 + 视图字段配置）与动态渲染组件；② `form_data` 按版本 + 动态字段条件检索；③ 网关注入租户上下文；④ `service-catalog.md` 更新 8084/`bluewhale_form` 表清单（+4 新表 `form_table_definition`/`form_column_meta`/`form_field_config`/`form_field_option`）。
