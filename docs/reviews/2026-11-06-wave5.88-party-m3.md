## 三、验收口径核对（计划 §4）

| 验收项 | 落地方式 | 结论 |
|---|---|---|
| 同人同年同类慰问有次数与金额上限 | `UnionReliefAppServiceImpl.submit` 按「同人 + 同年 + 同类型 + `status IN (APPROVED, PAID)`」统计次数与金额，上限取 `PartyProperties.reliefCountLimit=2` / `reliefAmountLimit=5000.00`，超限抛 `UNION_RELIEF_LIMIT_EXCEEDED(43056)`；校验在服务端提交时执行，草稿不占额度 | 达成 |
| 福利发放名单与签收可对账 | 发放按「标准 + 名单」建单，明细唯一键 `uk_pty_union_welfare_item` 保证重复发放幂等跳过；签收按明细逐人登记并记签收人与时间，名单（应发）与签收（实发）可逐人比对 | 达成 |
| 活动报名不超名额且不重复 | 唯一键 `uk_pty_union_signup(activity_id, union_member_id)` + 报名前按已报名数校验名额（`UNION_SIGNUP_QUOTA_EXCEEDED`）；取消后再报名复用原行改回 `SIGNED`，不新增记录 | 达成 |
| 提案状态单向、办结不可回退 | `ProposalStatus` 五态只允许前进一步，`EVALUATED` 为终态；非法流转抛 `UNION_PROPOSAL_STATE_CONFLICT` | 达成 |
| 审批不可达时申请保存为草稿不丢失 | `WorkflowReliefApprovalGateway` 向上抛异常，应用层捕获后保留 `DRAFT`、写 `approval_hint`、返回 `approvalStarted=false`，不抛事务异常、不回滚 | 达成 |

## 四、关键设计复核

1. **会籍唯一性放在应用层而不是库唯一键**：`pty_union_member` 对 `employee_no` 不建唯一键。建库唯一键会让「退会 → 再入会」直接撞键，而工会会籍本来就允许中断后再加入；唯一性口径改为「同一员工同一租户仅一条 `ACTIVE`」，由应用层在入会时校验。
2. **慰问上限的统计范围**：只统计 `APPROVED` / `PAID`，不统计 `DRAFT` / `SUBMITTED` / `REJECTED`。若把待审也算进去，用户会因别人尚未处理或已被驳回的申请而失去额度；若只统计 `PAID`，已批未发的申请又会被重复提交绕过上限。
3. **审批降级的信号而不是异常**：workflow 不可达时返回 `approvalStarted=false` + `approvalHint`，而不是抛 500。前端据此提示「稍后重试」，申请仍在库里可再次提交；相比之下，抛异常让用户以为数据丢了，回滚则让已填内容一起消失。
4. **管理权限与自助动作分端点**：`list`/`manage` 只给 `union_admin`，园地浏览与「我的福利 / 我的报名 / 我的提案 / 我的活动」走 `/portal/**` 与 `/my`。若用一个端点兼两种权限语义，等于把管理权限隐式下放给全员，或让普通员工看不到自己的记录。
5. **`party_admin` 只有 1970 浏览权**：党建管理员能看工会栏目但不动工会业务；工会业务归 `union_admin`。角色边界不靠前端隐藏菜单，菜单权限码与服务端 `@RequirePermission` 同源。
6. **取消报名只作用于本人**：接口不接收目标会员参数，统一按当前登录人的在册会员定位，管理员也只能取消自己。避免出现「管理员代任意会员取消」的越权面；如需管理端清理名额，后续应以独立端点显式授权。
7. **编号取号沿用 `pty_sequence`**：会员号 `UN` / 申请号 `RF` / 发放单号 `WF` / 活动号 `UA` / 提案号 `UP`，不解析历史编码、不用 `MAX()`，规则变更不影响存量。
8. **依赖方向**：`union` 领域层不依赖 Spring/MyBatis；审批经 `ReliefApprovalGateway` 端口由 infrastructure 适配器调用 workflow，ArchUnit 上下文门禁通过。
