> 日期：2026-10-21 ｜ 作者：BlueWhale

---

## 一、评估结论

**不引入 Sentinel，GW-01 结案归档。**

现有「Redis 固定窗口限流（`RateLimitGlobalFilter`）+ resilience4j 熔断（`CircuitBreakerGlobalFilter`）」已满足 REQ-DIST-003/004 的契约（429 / 503 `Result` 体、按路由开启、指标可观测），Sentinel 在当前环境不具备落地前提，且会引入额外的运行时与运维负担。

---

## 二、评估维度

| 维度 | 事实 | 判断 |
|---|---|---|
| 依赖可得性 | 本机 Maven 仓库（`D:\repository\maven`）**无 `com.alibaba.csp` 制品**，当前网络环境离线安装不可行 | ❌ 阻塞 |
| Spring Boot 4 兼容 | Sentinel 官方 starter 面向 Boot 2/3 生态，Boot 4.0.8 + Spring Cloud 2025.1.2 组合**未验证**，需自行适配 `spring.factories` → `AutoConfiguration.imports` 与 WebFlux 过滤链 | ❌ 高风险、无验证样例 |
| Dashboard / 规则持久化 | 本机无 Sentinel Dashboard，也无可挂载的 Nacos 规则源联调环境；规则只能落本地内存/文件，无法验证集群推送 | ❌ 阻塞 |
| 能力覆盖 | 现有：QPS 固定窗口限流（全局 + 按路径特化）、按路由熔断（失败率/超时/半开）、Prometheus 指标、503/429 统一响应 | ✅ 已覆盖当前需求 |
| 额外能力 | Sentinel 的流控（Warm Up/排队等待/关联/链路）、系统自适应保护、热点参数限流 | 当前无场景；引入需先有真实流量画像 |
| 运维成本 | 引入 Sentinel 需同时维护 Dashboard、规则推送通道、客户端依赖与版本对齐；现有方案零额外组件（复用 Redis） | 不划算 |

---

## 三、决策与替代

1. **保留现状**：限流继续走 Redis 固定窗口（`whale.gateway.rate-limit.*`），熔断继续走 resilience4j（Wave 5.35 G2 已替换自研滑动窗口，契约与指标名不变）。
2. **可观测口径不变**：`gateway.circuit.calls` / `gateway.circuit.short_circuits` / `gateway.circuit.state`、`gateway.routes.rejected`。
3. **不删除评估结论**：后续若引入 Sentinel，按下方触发条件重新评估，避免重复调研。

---

## 四、重新评估的触发条件

满足任一条件时重开 GW-01（建议作为独立 wave 立项）：

- 具备可联网的 Maven 仓库或私有制品库，可拉取 `com.alibaba.csp:sentinel-spring-cloud-gateway-adapter` 等制品；
- 有 Docker/K8s 环境可运行 Sentinel Dashboard，并验证规则持久化到 Nacos；
- 出现现有方案无法覆盖的诉求（热点参数限流、链路级流控、系统自适应保护、集群流控）；
- 压测产生明确流量画像，需要 Warm Up / 排队等待等更细粒度策略。

## 五、若未来接入的落地要点（备忘）

| 项 | 要点 |
|---|---|
| 依赖 | `sentinel-core` + `sentinel-spring-cloud-gateway-adapter`（Boot 4 需自行提供自动配置） |
| 埋点 | `SentinelGatewayFilter` + `SentinelGatewayBlockExceptionHandler` 接入 WebFlux 链，保持 429 `Result` 体 |
| 规则 | 网关流控规则（`GatewayFlowRule`）按 routeId / API 分组配置，规则源优先 Nacos |
| 熔断 | 与 resilience4j 二选一，避免双层熔断导致阈值语义冲突 |
| 回退 | 配置开关切回现有 `RateLimitGlobalFilter` / `CircuitBreakerGlobalFilter`，两者并存期间以开关互斥 |
| 验证 | 429/503 契约、指标名、非法规则拒绝、规则热更新四项必须回归 |
