## 二、逐项检查结果

### 2.1 A 类 —— 协议与接口安全

| 编号 | 检查项 | 结论 | 证据与说明 |
|---|---|---|---|
| A1 | 凭据传输 | 通过 | JWT 只走标准 `Authorization` 换 ticket；WS URL 仅携带随机 UUID ticket，60s 有效且一次性，杜绝 JWT 落日志/落历史 |
| A3 | 越权防护 | 通过 | `POST /im/ws-ticket` 类级 `@RequirePermission("sys:im:chat")` + `UserContext.requireUserId`；ticket 值绑定 `userId`，握手成功即注入会话属性，客户端无法自行指定用户 |
| A5 | 水平越权（IDOR） | 通过 | 握手只认 ticket 中的用户；`message.new` 仅推送给成员表中的 `memberIds`，非成员收不到 |
| A11 | 错误信息 | 通过 | 握手失败仅返回 401，不区分「过期 / 已用 / 不存在」；Redis 故障文案为「即时通讯通道暂不可用，请稍后重试」 |
| A12 | 入参校验 | 通过 | ticket 缺失或空白直接拒绝握手；帧体非法 JSON 视为未知类型，回 `error` 帧而不抛异常 |
| A13 | 白名单最小化 | 通过 | 仅 `/im/ws` 免 JWT（浏览器 WS 限制所致），同前缀其余接口仍走 JWT + 权限码头 |

## 四、遗留与说明

- **单实例内存推送**：`WsSessionRegistry` 为进程内注册表，多实例部署时各实例只推自己连接的客户端；跨实例扇出需接 Redis Pub/Sub 或 MQ（规划二期）。
- **Redis 强依赖**：ticket 签发/消费与在线状态均依赖 Redis，Redis 不可用时 WS 通道整体不可用，REST 仍正常；符合「实时能力可降级、数据不丢」的取舍。
- **在线状态非强一致**：TTL 90s 被动过期，进程异常退出时最多滞后 90s 才显示离线；客户端心跳（30s）可保证正常场景及时续期。
- **未做连接数与限流**：单个用户多端连接数未设上限，WS 建连也未纳入网关限流（网关限流仅作用于 HTTP）。生产前建议在 `ImWsSessionRegistry.register` 增加用户级连接上限。
- **`bluewhale_im` 建库与 DDL 仍未执行**：属部署动作，联调前需执行 `db/init.sql` 与 `whale-auth/db/migration-5.52.sql`。
- **前端 WS 客户端未实现**：`whale-im` 8107 尚无 WS 连接、心跳、重连与 `afterSeq` 补拉逻辑，属 T6 之后的前端任务。
