# infra — 基础设施

不放业务代码。这里的东西决定项目能不能被一次可靠地跑起来、发出去、回滚掉。

| 目录 | 内容 |
|------|------|
| `docker/` | 各应用的 Dockerfile、本地开发用 docker-compose |
| `nginx/` | 反向代理、静态资源、网关路由配置 · **已有内容**：两条上报通道的限流（见 `nginx/README.md` 与 `docs/decisions/0027`） |
| `deploy/` | 环境变量模板、发布与回滚脚本 |

> **CI 不在这里。** GitHub Actions **只从 `.github/workflows/` 读取流水线** ——
> 这是平台的硬要求，不是我们的选择。所以本目录**不再预留 `ci/`**
> （留一个永远装不进内容的目录，只会让下一个人在错的地方找）。
> 流水线定义见 `.github/workflows/ci.yml`，分层的理由见 `docs/decisions/0036`。

## 约定

1. **环境变量全部走模板。** 真实密钥不入库，只提交 `.env.example`。
2. **本地一键起。** `docker/` 下应能一条命令拉起数据库、缓存、消息队列，不依赖开发者手工装中间件。
3. **发布可回滚。** `deploy/` 中的每个发布动作都要有对应的回滚路径。
4. **网关是统一入口。** 鉴权、限流、跨域在 `nginx/` 或后端网关层解决，不要散落在各应用里。

> **第 4 条不是一句口号，它是有限流就落在 `nginx/` 的原因。**
> 应用层**拿不到可信的客户端 IP** —— 后端 5 处注释写着 `X-Forwarded-For` 可被伪造、
> 不可作为鉴权或风控依据；那成立的原因是"应用无法判断自己前面有几跳、该信哪几跳"，
> 而 nginx 知道，因为它自己就是那个代理。详见 `docs/decisions/0027`。
>
> 改 `nginx/` 下的配置后跑 `node scripts/verify-nginx-config.mjs`
> —— 它能查出 `nginx -t` 查不到的那几类错。
